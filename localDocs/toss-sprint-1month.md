## P0 — 이게 없으면 서류가 죽는다 (약 45h)

### P0-1. BTL-005 댓글 목록 N+1 제거 + Before/After 측정 (30h)

**이번 달의 클라이맥스.** 공고의 "성능 최적화 지향"에 답하는 유일한 항목이다.

원인은 이미 코드 경로까지 확정돼 있다 — 댓글 M 개당 **3M+1 쿼리**.

```
CommentController.java:36  getComments()
 ├ CommentRepository.java:15  findByPost()  — JOIN FETCH 없음          → 1
 ├ CommentAnonymizationService → CommentDto.fromEntity()
 │   └ CommentDto.java:50  comment.getUser().getProfileUrl()
 │      Comment.java:23  user 는 LAZY, @BatchSize 없음                  → M
 └ CommentController.java:46~55 루프
     └ CommentReactionService.java:21~27  existsBy...(LIKE) + (DISLIKE) → 2M
```

**작업 순서**

| 단계 | 내용 | 시간 |
|---|---|---|
| a | `findByPost` 에 `join fetch c.user` 추가 | 2h |
| b | 반응 조회를 댓글별 `exists` 2회 → `where comment_id in (:ids) and user_id = ?` 한 방으로 | 6h |
| c | 쿼리 수 검증 단위 테스트 | 4h |
| d | **After 측정 — Before 와 같은 세션에서 연달아** | 8h |
| e | MDE 대비 판정 | 3h |
| f | 결과 정리 | 7h |

**완료 기준**
- 요청당 쿼리 수가 **한 자릿수**로 떨어진 것을 실측
- `comment_list` p95 개선폭이 **MDE 를 초과**함을 확인
- Before/After 가 **같은 세션 연속 실행**임이 `run.json` 으로 확인 가능

**반드시 지킬 것**
- **d 의 "연달아"가 조건이다.** `bottlenecks/README.md` 공통 선행조건 ② — 시간 방향
  드리프트가 있어 며칠 뒤에 재면 아무것도 안 고쳐도 느리게 나온다.
- Before 는 **2026-08-18 이후 코드로 새로 잰다** (S-26: 그 이전 실행은 RPS 분모 오류로
  qps/rps 비율이 과대평가돼 있다).

**정직하게 남길 한계**
데이터셋의 `comments_reactions` 가 **0건**이다(`run.stateCoreBefore`). 반응 조회가 빈
테이블을 훑으므로 **실제 서비스보다 낙관적**이다. 데이터를 채우면 데이터셋 fingerprint 가
바뀌어 과거 비교가 끊기므로 이번 달에는 현 데이터셋으로 재고 **한계를 문서에 명시**한다.
면접에서 먼저 말하면 오히려 신뢰가 오른다.

### P0-2. 엔드포인트별 요청당 쿼리 수 계측 (8h)

**P0-1 의 선행조건이자 그 자체로 면접 카드.**

현재 리포트의 "요청당 319.4 쿼리"는 `mysql.qps ÷ 전체 RPS` 라 **전체 요청 평균**이다.
`comment_list` 단독 값이 아니다. **"그 319개가 전부 댓글 조회에서 나온 건가요?"** 를
물으면 지금은 답할 수 없다. `BTL-005` 선행조건 ① 이기도 하다.

p6spy 는 이미 의존성에 있다(`p6spy-spring-boot-starter`).

**완료 기준**: 엔드포인트별 요청당 쿼리 수가 리포트 또는 로그 집계로 나온다.

### P0-3. 익명 `profileUrl` 노출 수정 (2h)

`toss-gap-analysis.md` S3. **익명 커뮤니티에서 익명성이 깨지는 것은 "인지하고 있다"로
방어가 안 된다.** 서비스 핵심 가치의 결함이므로 면접 전에 닫아야 하는 유일한 항목.

**완료 기준**: `isAnonymous=true` 인 댓글·게시글 응답에 `profileUrl`·`userId`·`author` 가

### P0-4. 대상 글의 댓글 수를 `COUNT(*)` 로 고정 (2h)

`BTL-005` 선행조건 ③④. 댓글 0건인 글이 섞이면 **빈 응답의 빠른 속도가 p95 를 끌어내려
개선 효과가 희석**된다(S-16). 비정규화 카운터(`PST_comment_count`)를 믿지 말고
`SELECT COUNT(*) FROM comments WHERE PST_id = ? AND is_valid = 1` 로 직접 세서
실험 문서에 기록한다(E-45).

**완료 기준**: Before/After 가 **같은 글 집합**을 대상으로 측정됐음이 문서로 확인 가능.

## B. 직무 인터뷰 대비 — 여기가 진짜 관문

**불합격 사례의 직접 원인이 CS 기초 부족이었다.** 8,000명이 쓰는 서비스를 운영한 지원자가
"자신 있게 대답한 질문이 거의 없었다"며 떨어졌다. 면접은 1~2시간, **2~3뎁스 추적 질문**이다.

한 달에 CS 전 범위는 불가능하다. **내 프로젝트에서 실제로 나오는 것만** 깊게 판다.

### B-1. 좁힌 CS 범위 (15h) ★필수

| 주제 | 왜 이것부터 | 내 실측 연결고리 |
|---|---|---|
| **JPA 영속성 컨텍스트 · 지연로딩 · OSIV** | N+1 개선의 직접 배경. 반드시 물어본다 | `spring.jpa.open-in-view` 기본값 true → 커넥션이 요청 전체에 묶임 |
| **스레드 · 컨텍스트 스위칭 · CPU 스케줄링** | 톰캣 스레드 ↔ HikariCP 대기 서사에서 파고든다 | 톰캣 busy 4/400, Hikari active 1.85/10 |
| **cgroup CPU 제한과 throttling** | 실측값을 들고 있으니 원리를 못 말하면 감점이 크다 | throttled 99.98% (포화 실행), 13.1% (정상 실행) |
| **JVM 메모리 구조 · GC** | | heap 810MB, GC overhead 0.25%, alloc 160MB/s |
| **TCP · 커넥션 재사용 · keep-alive** | 커넥션 풀 이야기의 하위 계층 | |
| **트랜잭션 격리 수준 · InnoDB 락** | 핫 로우 경합(BTL-003) 서사와 직결 | rowLockWaits 0, rowLockTime 679ms |
| **인덱스 · 실행계획** | N+1 vs 풀스캔 구분 | rows/query 0.865 → 풀스캔 아님을 실측으로 증명 |

**`toss-interview-concepts.md` 에 상당 부분이 이미 정리돼 있다.** 새로 만드는 게 아니라
**"말할 수 있는 수준"으로 끌어올리는** 작업이다.

### B-2. 꼬리질문 2~3뎁스 리허설 (8h) ★필수

`toss-interview-questions.md` §10 의 체인 3개를 **소리 내어, 녹음하며** 최소 3회.
합격 후기가 지목한 준비법이다. 각 답변에서 "그럼 왜 그렇게 했나 → 다른 방법은 →
규모가 커지면 → 장애가 나면"까지 이어지는지 확인한다.

### B-3. 아키텍처를 그림으로 설명하는 연습 (5h) ★필수

합격 후기가 합격 요인으로 직접 지목했다(Excalidraw 사용). 화이트보드나 화면 공유로
**측정 파이프라인 구조**와 **댓글 조회 요청의 흐름**을 즉석에서 그릴 수 있어야 한다.

### B-4. 30초 / 2분 소개 재작성 (3h) ★필수

현재 `toss-interview-questions.md` §0 의 30초 버전은 **"측정 시스템을 만들었다"로 끝난다.**
**"고쳤고 이만큼 빨라졌다"로 끝나야 한다.**

목표 문장:
> "댓글 목록 조회 한 건이 쿼리를 수백 개씩 날리고 있었습니다. 몇 개로 줄였고 p95 가
> X 에서 Y 가 됐습니다. 그게 노이즈가 아니라는 건 반복 측정으로 CV 를 먼저 잡고
> 확인했습니다."

앞 두 문장은 누구나 이해한다. **세 번째 문장이 나를 다른 지원자와 가른다.**

### B-5. 숫자 카드 10개 갱신 (3h)

`toss-interview-questions.md` 부록. 개선 전후 수치로 갈아끼운다.

### B-6. 규모 답변 스크립트 (2h) ★필수

공고 자격 요건 중 **두 개를 못 채운다**(고가용성 운영, 대규모 트래픽). 숨기면 약점,
먼저 말하면 강점이 된다.

> "트래픽 규모는 작았습니다. 대신 **그 규모에서 성립하는 판정 절차**를 만들었습니다.
> 절대 처리량이 아니라 '개선했다고 말할 자격이 있는가'를 시스템으로 답하게 한 것이
> 제가 한 일입니다. 큰 환경으로 옮기려면 부하 생성기 다중화와 노드 간 클럭 동기화가
> 추가로 필요하고, 판정 로직 자체는 그대로 씁니다."

## E. 병행 — 다른 회사 (즉시)

**토스 하나에 걸지 않는다.** 자유 이직 창이 2개월뿐이고, 토스 전형만 한 달이 걸린다.

### E-1. 즉시 5~10곳 지원 ★필수

**이력서 초안이 나오는 즉시 넣는다.** 완벽을 기다리다 창을 놓치는 게 가장 흔한 실패다.

찾는 곳: **병역일터(work.mma.go.kr) 채용공고 검색**(공식 창구), 원티드, 점핏, 잡코리아,
인크루트, Indeed

### E-2. 회사 선택 기준 — 미리 고정하고 기계적으로 거른다

| 조건 | 타협 가능? |
|---|---|
| **병역지정업체** | **불가** |
| **의미 있는 트래픽이 있는 제품 회사** | **불가** — "대규모 트래픽 경험"을 채울 유일한 방법 |
| Java/Kotlin + Spring | 가급적 유지 (스택 연속성) |
| 성능·인프라를 만질 수 있는 규모 | 가급적 |
| 잡플래닛 3.0 이상 (직군 필터 적용) | 권장 — 1점대는 1년 준비 후 재도전이 낫다는 조언이 있다 |
| 연봉 · 회사 인지도 · 위치 | **타협 가능** |

### E-3. 다른 곳을 먼저 넣는 이유

1. **면접 연습.** 불합격 사례의 원인이 "준비했는데 답할 기회를 못 살렸다"였다.
   실전 몇 번을 겪고 토스 면접에 들어가는 것과 아닌 것은 다르다.
2. **안전망.** 토스가 안 되어도 SI 에서 편입하는 것보다 압도적으로 낫다.
3. 마감이 있는 공고가 섞여 있다. 토스는 상시채용이라 급하지 않다.
