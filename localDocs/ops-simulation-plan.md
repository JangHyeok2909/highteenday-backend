# 운영 시뮬레이션 시스템 구축 계획

작성일 2026-09-14. 개정 2026-09-22. 실사용자가 없는 상태에서 운영 트래픽과 장애 대응을 다뤄
보기 위한 별도 환경의 구축 계획이다.

> **이 문서는 `performance/` 의 측정 시스템을 다루지 않는다.** 두 환경을 **격리**하는 것이 이
> 계획의 제약이고, 격리 규칙과 두 환경 사이에 무엇이 오갈 수 있는지는 6장에 있다.

**2026-09-22 개정에서 바뀐 것.** 초판은 실행 호스트를 정하지 않은 채 쓰였고, 그래서 자원·보존
기간·감시 구조를 측정 환경 값 그대로 가정했다. 호스트가 "이 컴퓨터는 측정, 별도 노트북은 운영"
으로 정해지면서 4장(실행 환경), 6장(격리와 왕래), 7장(켜기 전 결정), 8장(시뮬레이터 설계),
9장(관측 설정)이 새로 들어갔고, 5.1·5.3·5.5의 결정이 코드 확인 결과에 따라 정정됐다.

---

## 1. 이 문서가 답하는 질문

- 실사용자 없이 "운영해 본 경험"을 만들려면 무엇을 갖춰야 하는가
- 이미 있는 k6 부하 시스템으로는 왜 안 되는가
- 두 기계로 나눈 뒤 무엇이 달라지는가
- 켜고 나면 되돌릴 수 없는 결정은 무엇인가
- 무엇을 새로 설치하고 무엇은 직접 써야 하는가
- 검토했다가 버린 대안은 무엇이고 왜 버렸는가

---

## 2. 배경 — 있는 것과 없는 것

`performance/` 에는 k6 시나리오 16개, 사용자 여정 9종(`scenarios/lib/workload.js` 313줄),
Prometheus·Grafana, toxiproxy·pumba 기반 장애 주입(`resilience/` 4,853줄)이 있다. 부하를 만들고
재는 일은 이미 된다.

없는 것은 부하가 아니라 **루프**다. 운영 경험은 다음 여섯 칸이 한 바퀴 돌 때 생긴다.

```
트래픽이 흐른다 → 고장이 난다 → 안 보고 있을 때 알림이 온다
  → 지표에서 이상을 찾고 로그에서 원인을 찾는다 → 고친다 → 왜 늦게 알았는지 기록한다
```

현재 저장소는 1번 칸(k6)과 2번 칸(resilience)만 갖고 있다. 3번 칸이 비어 있는 게 결정적이다.
`environment/prometheus/prometheus.yml` 에 `rule_files` 도 `alerting:` 블록도 없고, 저장소의 어떤
compose 파일에도 Alertmanager·ntfy·Loki·Uptime Kuma 서비스가 없다(2026-09-22 재확인).
`locustfile` 도 없다. 지금 구조에서는 내가 Grafana 화면을 보고 있을 때만 이상을 안다. 그건
관찰이지 운영이 아니다. 실제 운영에서 배우는 것은 **다른 일을 하다가 알림을 받고 맥락 없이 상황
파악을 시작하는 경험**이기 때문이다.

## 3. 목표와 비목표

**목표**

- 며칠~몇 주 동안 끊기지 않는 트래픽을 흘려 데이터가 실제로 쌓이게 한다
- 예고 없이 고장을 내고, 알림으로 인지해 진단하고 복구하는 과정을 반복한다
- 그 과정을 기록해 같은 장애를 두 번째부터는 더 빨리 처리한다

**비목표**

- 성능 수치를 재지 않는다. 판정은 `performance/` 가 계속 담당한다
- 최대 부하를 찾지 않는다. 이 환경의 부하는 의도적으로 낮다(8.1 참고)
- 실사용자 운영을 대체하지 않는다. 못 주는 것은 11장에 적었다

## 4. 실행 환경 — 두 기계로 나눈다

### 4.1 역할 분담

| | 이 컴퓨터(개발 장비) | 별도 노트북(운영 장비) |
|---|---|---|
| 하는 일 | 개발, k6 부하 측정, 장애 실험 | 배포된 서비스를 상시 운영 |
| 실행 프로파일 | `perf` | `prod` |
| 데이터 정책 | 고정(`datasetGuard: strict`) | 성장. 시드 1회 후 초기화 없음 |
| 부하 생성 | k6 (실행마다 시작·종료) | Locust (상시 가동) |
| 가동 시간 | 필요할 때만 | 24시간, 2027년 3월까지 |
| 산출물 | 성능 판정 수치 | 사건 기록(포스트모템) |

AWS 구성(EC2 + RDS)은 요금 때문에 전부 내렸다. 그래서 운영 장비는 집에 두는 노트북 한 대이고,
필요하면 공유기에서 포트를 포워딩해 밖에 연다(4.3).

**기계가 다르므로 초판의 "두 환경을 동시에 돌리지 않는다"는 제약이 자동으로 지켜진다.** 측정
실행 중에 운영 트래픽이 배경 부하로 섞이는 일이 구조적으로 불가능해졌다. 대신 두 환경 사이에
무엇을 옮겨도 되는지를 정해야 하고, 그건 6장이다.

### 4.2 운영 노트북이 24시간 버티게 하는 것

- **절전과 최대 절전을 끈다. 뚜껑을 닫아도 안 자게 한다.** 안 하면 밤마다 트래픽이 끊기고,
  아침에 보면 야간 구간 지표가 통째로 비어 있다.
- **전용 장비라면 Ubuntu Server 를 깐다.** Windows 는 자동 재시작 시점을 통제해야 하고,
  WSL2 를 24시간 띄우면 메모리 반환이 지연되는 문제를 겪는다.
- **Docker 를 부팅 시 자동 시작으로 두고 컨테이너에 `restart: unless-stopped` 를 건다.**
  재시작 뒤 사람이 손대지 않아도 복구돼야 한다.
- **배터리가 짧은 정전을 대신 버틴다.** 노트북을 쓰는 실질적 이점이다. 다만 6개월 상시 충전은
  배터리 수명을 깎으므로, 제조사 도구에 충전 상한(80% 등)이 있으면 켠다.
- **메모리.** 측정 환경의 자원 한계를 그대로 쓰지 않는다는 전제(9장)에서, 앱·MySQL·Redis 에
  측정 환경과 같은 2,560 + 512 + 512 = 3,584MB 를 준다고 잡고, 관측 스택과 Locust 를 더하면
  **[추정]** 6~7GB 다. 8GB 는 빠듯하고 16GB 면 여유가 있다.
- **전기 요금.** 평균 소비를 30W 로 잡으면 0.03kW × 24시간 = 0.72kWh/일이고 180일이면 130kWh
  다. 누진 구간 단가를 300원/kWh 로 가정하면 6개월에 약 39,000원이다. 단가는 가정이고 가구
  사용량에 따라 구간이 달라진다. EC2 와 RDS 를 6개월 켜 두는 것보다는 확실히 싸다.
- **백업.** 6개월치가 노트북 SSD 한 장에 있다. 그 디스크가 죽으면 이 계획의 산출물이 한 번에
  사라진다. 전부 백업할 필요는 없다. 원고에 쓰이는 것은 포스트모템과 사건별 요약 지표이므로
  그것만 주기적으로 `localDocs/` 나 외부로 복사하면 된다.

### 4.3 공개 노출은 목적 셋 중 하나에만 필요하다

무엇 때문에 여는지에 따라 답이 다르다.

| 목적 | 인바운드 포트가 필요한가 |
|---|---|
| 휴대폰 알림(ntfy) | 필요 없다. 노트북이 밖으로 보내는 방향이다 |
| 밖에서 Grafana·Locust 화면 보기 | 열면 안 된다. Tailscale 같은 사설망으로 붙는다 |
| 진짜 크롤러와 취약점 스캐너 받기 | 이것만 필요하다 |

Grafana 와 Locust 웹 UI 를 포워딩하면 안 되는 이유는 분명하다. Grafana 는 기본 계정이 있고,
Locust 웹 UI 는 인증 없이 사용자 수와 생성률을 바꿀 수 있다. 공개되면 누구나 내 서버에 부하를
걸 수 있다.

세 번째를 원해서 연다면 **앱 포트 하나만** 연다. `application-prod.properties:35` 가
`management.server.port=8081` 을 지정하므로 prod 프로파일에서 actuator 는 8081 에 붙고 8080 에서는
404 다. 8080 만 포워딩하면 지표가 공개되지 않는다.

이 포트 분리가 유일한 방어선이다. `SecurityConfig.java:102` 가 `/actuator/**` 를 `permitAll()` 로
열어 두므로, 8081 이 어떤 경로로든 밖에서 닿으면 인증 없이 JVM·커넥션 풀·요청 지표가 나간다.
같은 파일 33줄 주석이 제안하는 `management.server.address=127.0.0.1` 을 함께 넣으면 실수로 열릴
여지가 준다.

집 네트워크라는 점이 클라우드와 다르다. 노출한 앱이 뚫리면 공격자가 같은 LAN 의 다른 기기를
본다. 공유기의 게스트 네트워크에 운영 노트북만 두는 정도는 해 둔다.

### 4.4 prod 프로파일이 요구하는 외부 의존 셋

`application-prod.properties` 가 환경변수로 받는 것 중 정해야 할 것이 셋이다.

- **S3**(`S3_BUCKET`, 81줄) — 실제 버킷을 쓰면 확정되지 않은 tmp 객체가 6개월간 쌓여 용량 요금이
  는다. 그 객체를 지우는 스케줄러가 없다는 것은 `localDocs/TODO.md` 1-C 에 적혀 있다. 노트북에
  MinIO 를 띄워 S3 호환 엔드포인트로 돌리면 요금이 0 이 된다. **[확인 필요]** 코드가 엔드포인트
  override 를 받는지.
- **NEIS**(`NEIS_API_KEY`, 92줄) — `SchoolMealScheduler` 가 6개월간 실제 외부 API 를 계속 호출한다.
  **[확인 필요]** 키의 호출 쿼터.
- **Google OAuth**(86~87줄) — 시뮬레이터는 `/api/user/login` 으로 로그인하므로 실제 호출은 없다.
  **[확인 필요]** 값이 비었을 때 앱이 뜨는지.

`spring.jpa.hibernate.ddl-auto=none`(52줄)이므로 스키마는 Flyway 가 소유한다. 이건 바라던 것이다.
**데이터가 이미 들어 있는 상태에서 마이그레이션을 돌리는 경험**이 6개월간 생긴다.

## 5. 구성 요소별 결정과 버린 대안

localDocs 기록 규칙에 따라 **버린 대안과 이유**를 각 항목에 함께 적는다.

### 5.1 트래픽 생성 — Locust

**결정**: `locustio/locust` 도커 이미지를 상주시키고 `locustfile.py` 를 직접 쓴다.

**k6 재사용을 버린 이유.** k6의 실행 모델이 상주 트래픽과 네 군데에서 어긋난다.

1. **VU 번호가 사용자 정체성을 대신한다.** `performance/scripts/lib/data.js` 의 `myUser()` 는
   `users[(exec.vu.idInTest - 1) % users.length]` 로 계정을 고른다. `normal-day.js` 의
   `preAllocatedVUs` 기본값이 100이므로 VU 번호는 1~100 범위에서만 나온다. large 데이터셋의
   계정 10,000개 중 실제 로그인하는 건 100개, 즉 1%다. 관측되는 증상은 `users` 테이블 행은
   10,000개인데 `posts.user_id` 의 distinct 값이 100개에 머무는 형태다.
2. **사용자별 상태가 프로세스보다 오래 못 산다.** k6 VU의 전역 변수는 프로세스 안에서만 산다.
   그래서 "어제 쓴 글에 오늘 댓글이 달려 원작자에게 알림이 가고, 원작자가 그걸 열어 답글을
   단다"는 연쇄가 안 만들어진다. 지금 `journeyEngage()` 는 `hotPost()` 로 인기글을 뽑아 댓글을
   다는데 그 글을 누가 썼는지는 보지 않는다. 알림 행은 쌓이지만 받는 쪽과 읽는 쪽이 안 이어진다.
   운영에서 터지는 상황이 대개 이 연쇄다. 인기 글 하나에 댓글 500개가 달리면 원작자 앞으로
   알림 500건이 쌓이고, 그 사람이 앱을 열 때 `/api/notifications/unread-count` 와
   `/api/notifications?page=0&size=20` 이 동시에 무거워진다.
3. **실행 중 부하를 못 바꾼다.** `options.scenarios` 의 stages 는 실행 시작 전에 확정된다.
4. **세션 사이 휴식이 없다.** `thinkTime()` 의 1~4초는 세션 *안*의 화면 전환 간격이다.

**Locust 가 이 넷을 어떻게 다루는가.**

| k6에서 안 되던 것 | Locust 쪽 처리 |
|---|---|
| ① VU 번호 = 사용자 | `User` 인스턴스가 사용자 하나. 인스턴스 속성이 태스크 사이 유지됨 |
| ② 상태 소멸 | `on_start` 에서 로그인하고 그 세션을 끝까지 씀. 프로세스를 띄워 두면 며칠 유지 |
| ③ 실행 중 부하 고정 | **`LoadTestShape` 로 풀지 않는다. 8.3 참고** |
| ④ 세션 간 휴식 없음 | 태스크 하나를 세션 전체로 만들고 `wait_time` 을 세션 간격으로 쓴다(8.2) |

**③의 처리를 초판에서 바꿨다.** 초판은 `LoadTestShape.tick()` 이 `(user_count, spawn_rate)` 를
반환하므로 실행 중 부하 조절이 된다고 적었다. 그런데 `user_count` 를 줄이면 Locust 가 User
인스턴스를 종료하고, 그 인스턴스가 들고 있던 상태가 함께 사라진다. 즉 ③의 해법이 ②를 깨뜨린다.
시간대별로 부하를 흔들면 사용자 상태가 하루에도 여러 번 초기화되고, Locust 를 고른 이유 자체가
없어진다. 대안은 8.3에 있다.

**Node 자작 데몬(700~900줄)을 버린 이유.** 이산 사건 스케줄러, 사용자 상태 저장, 비정상
포아송 도착 과정을 전부 직접 구현하는 안이었다. Locust 의 `User` 인스턴스와 이벤트 루프가 같은
일을 이미 하므로 순수 중복이다.

**k6/experimental/redis 나 xk6-kv 로 상태를 빼는 안을 버린 이유.** k6 자체에 VU 간 가변 상태
공유 수단이 없어서 나온 우회책이고 실제로 쓰인다. ①과 ②는 풀리지만 ③과 ④는 안 풀린다.
그리고 "누가 언제 접속하는가"를 정하는 스케줄러를 k6 밖에 둬야 하므로 k6는 요청을 쏘는
실행기 역할만 남는다.

**호스트에 파이썬을 설치하지 않는다.** 도커 이미지로만 쓴다.

### 5.2 알림 — Alertmanager + ntfy

**결정**: Alertmanager 컨테이너 → ntfy 로 휴대폰 푸시. 둘 다 운영 노트북 안에서 돈다.

**Grafana OnCall OSS 를 버린 이유.** 2025-03-11 유지보수 모드에 들어갔고 2026-03-24 저장소가
아카이브됐다. 아카이브 후 클라우드 연결이 끊겨 **모바일 푸시·SMS·전화 알림이 동작하지 않는다.**
몇 년 전 글들이 아직 OnCall 을 추천하는데 그대로 따라 하면 푸시가 안 온다.

ntfy 는 Go 바이너리 하나와 YAML 하나로 돌고 Android/iOS 앱이 긴 연결로 구독한다. 노트북에서
ntfy 서버로 나가는 방향이므로 인바운드 포트가 필요 없다.

**처음 넣을 규칙 4개**

- 5분 구간 5xx 비율 1% 초과
- 5분 구간 p95 응답시간이 평소의 3배 초과
- `up{job="spring-app"} == 0` 1분 지속
- HikariCP 커넥션 풀 사용률 90% 초과

4xx 는 규칙에 넣지 않는다. 이유는 8.5에 있다.

SLO 번레이트 알림(Sloth, Pyrra)은 뒤로 미룬다. 규칙 4개를 손으로 쓰는 것보다 도입 비용이 크고,
알림을 몇 번 받아 보고 "이 알림은 쓸모없다 / 이 상황은 안 잡힌다"를 겪은 다음이 순서다.

### 5.3 외부 감시 — 노트북 **밖**에 둬야 목적이 성립한다

**초판의 결정을 정정한다.** 초판은 `louislam/uptime-kuma:2` 컨테이너를 하나 띄워 "감시 시스템이
감시 대상과 함께 죽는 것을 막는다"고 적었다. 그 목적은 감시자와 감시 대상이 **다른 기계**에 있을
때만 성립한다. 지금 구성은 앱·Prometheus·Alertmanager·Uptime Kuma 가 전부 노트북 한 대에 있다.
정전이나 자동 재시작으로 노트북이 멈추면 전부 같이 멈추고, 휴대폰에는 아무것도 오지 않는다.

**이게 첫 2주의 최대 위험이다.** 이 계획이 지금 서두르는 이유는 데이터 누적 기간이고, 노트북이
죽은 것을 사흘 뒤에 알면 사흘치가 그대로 사라진다.

**결정**: 노트북이 외부 서비스로 주기 신호를 보내고 그 신호가 끊기면 휴대폰으로 알림이 오는
구성을 둔다(healthchecks.io 의 dead man's switch, UptimeRobot 등). 노트북에서 밖으로 나가는
방향이라 포트를 열 필요가 없다. Uptime Kuma 는 앱 안쪽 경로를 보는 용도로 노트북 안에 둬도 되지만,
**그것이 외부 감시를 대신하지는 않는다.**

### 5.4 로그 — Loki + Grafana Alloy

**결정**: Loki 와 Alloy 컨테이너를 붙이고 운영 노트북의 Grafana 에 데이터소스로 등록.

**왜 필요한가.** 지표는 "뭔가 이상하다"까지만 알려주고 "왜"는 로그에 있다. 장애 진단의 절반이
로그 검색이므로 이게 빠지면 훈련이 반쪽이다. 실제로 필요한 동작은 Grafana 대시보드에서 급등
구간을 드래그해 그 시각의 로그로 바로 넘어가는 것이고, 같은 Grafana 에 Loki 를 붙이면 된다.

### 5.5 고장 주입 — `resilience/` 를 **그대로 쓰지 못한다**

**초판의 결정을 정정한다.** 초판은 "`performance/resilience/` 의 toxiproxy + pumba 를 그대로 쓰고,
cron 으로 무작위 시각에 `fault-run.js` 를 실행한다"고 적었다. 코드를 보면 안 된다.

`fault-run.js`(1,101줄) 머리 주석 15~17줄이 구조를 설명한다. **주입 드라이버와 헬스 폴러를 시작한
뒤 k6를 자식 프로세스로 실행하고, k6의 setup 신호를 t0 로 삼아 장애 주입 타이머를 예약하며, k6가
끝나면 예약을 취소하고 정리한다.** 운영 노트북에는 부하가 Locust 로 이미 흐르고 k6가 없다. t0 를
줄 프로세스가 없으므로 이 실행기는 동작하지 않는다.

**결정**: 필요한 모듈만 뽑아 cron 에서 부르는 작은 실행기를 따로 만든다.

| 가져올 것 | 줄 수 | 하는 일 |
|---|---:|---|
| `lib/driver.js` | 199 | 계획된 시각에 주입과 복구를 실행 |
| `lib/docker.js` | 102 | 컨테이너 정지·재개 |
| `lib/toxiproxy.js` | 64 | 지연·끊김 주입 |
| `lib/health.js` | 73 | 헬스 폴링 |
| 합계 | 438 | |

버리는 쪽이 더 크다. `lib/report.js`(1,444줄)는 실행 보고서를 만드는데, 운영 환경의 산출물은
보고서가 아니라 포스트모템이고 지표는 Grafana 와 Loki 에 남으므로 쓸 데가 없다. `lib/plan.js`,
`lib/faultmetrics.js`, `lib/recovery.js`, `lib/integrity.js` 도 k6 실행 구간을 전제로 한다.

**`fault-run.js` 를 고쳐 두 모드를 지원하게 하지 않는다.** 측정 쪽 실행기가 운영 사정 때문에
바뀌면 과거 실행과의 비교가 깨질 위험이 있다. 그 실행기는 `performance/METHOD.md` 의 비교 계약을
지고 있다.

**Chaos Mesh 와 LitmusChaos 를 버린 이유.** 둘 다 쿠버네티스 커스텀 리소스로 동작해서
docker compose 환경에 못 쓴다.

**Chaos Toolkit 을 버린 이유.** 실험을 JSON 으로 선언하고 정상 상태 가설(steady state
hypothesis)을 먼저 검사한 뒤 고장을 넣는 구조인데, `resilience/faults/*.json` 과
`resilience/lib/invariants.js` 가 이미 같은 일을 한다.

**여기서 빠진 것은 도구가 아니라 스케줄이다.** 내가 시각을 정해 두면 예고 없는 장애가 아니다.

### 5.6 배포 — 주입 고장보다 현실적인 장애원

**초판에 없던 항목이다.** 두 기계로 나누면서 "운영 노트북에 배포한다"는 행위가 생겼다. 실제
서비스에서 장애 원인의 큰 축이 배포이므로, 주입하지 않아도 되는 장애원이 하나 열린다.

대신 규칙이 필요하다. `develop` 병합마다 자동으로 배포되면 이 컴퓨터에서 실험 중인 코드가 운영에
올라가고, 6개월 기록의 연속성이 깨진다. 11월에 난 장애를 나중에 설명할 때 그 시점에 무엇이 떠
있었는지 말할 수 없게 된다.

**결정**: 명시적으로 릴리스한 것만 올라가고, 무엇을 언제 올렸는지가 기록에 남는다. 세부는 6.2.

### 5.7 대응 기록 — 포스트모템 템플릿

**결정**: `dastergon/postmortem-templates` 의 템플릿을 가져와 장애 1건당 1개를 쓴다.

기록할 것: 타임라인, 알림에서 인지까지 걸린 시간, 인지에서 복구까지 걸린 시간, 재발 방지 항목.
혼자라도 쓴다. 이 기록이 없으면 같은 장애를 세 번 겪고도 매번 처음부터 진단하게 된다.

## 6. 두 환경의 격리와 왕래

### 6.1 격리 규칙

기계가 다르므로 동시 실행 자체는 문제가 안 된다. 남는 규칙은 **데이터와 설정을 섞지 않는 것**이다.

- 운영 노트북의 MySQL 볼륨을 측정 환경이 직접 쓰지 않는다. `performance/perf.config.json` 의
  `datasetGuard: strict` 는 데이터셋이 변하면 안 된다는 정책이고, 운영 데이터는 매일 변한다.
- 측정 환경의 자원 한계를 운영 노트북에 복사하지 않는다(9.1).
- 측정 환경의 수집 간격과 보존 기간을 운영 노트북에 복사하지 않는다(9.2).

**운영 노트북에서 나온 응답 시간은 성능 근거가 아니다.** 하드웨어도 자원 한계도 데이터셋 지문도
`performance/METHOD.md` 의 비교 조건과 다르다. 운영 환경에서 쓸 수 있는 문장은 "무엇이 언제
일어났고, 어떻게 알았고, 얼마 만에 복구했는가"이고, "얼마나 빨라졌는가"는 측정 환경이 답한다.

### 6.2 브랜치와 릴리스

**결정**: 기존 브랜치 규칙을 유지한다. `develop` 이 통합, `main` 이 배포다. **성능측정·장애테스트
용도의 장기 브랜치를 새로 만들지 않는다.**

장기 브랜치를 만들지 않는 이유 셋.

1. **앱 코드가 갈라지면 운영 기록이 어느 코드의 기록인지 말할 수 없다.** 측정 쪽에서 고친
   서킷브레이커나 DB 대기 상한이 운영 노트북에 없으면, 운영에서 본 장애가 이미 고친 것인지
   아닌지 구분이 안 된다. 6개월치 기록 전체의 해석이 흔들린다.
2. **갈라야 할 것은 코드가 아니라 설정·데이터·부하 생성기인데, 이미 디렉터리로 갈려 있다.**
   `performance/` 는 앱 코드가 아니고 앱 실행에 관여하지 않는다. 브랜치가 추가로 할 일이 없다.
3. **장기 브랜치의 비용은 병합 충돌이 아니라 측정 결과의 무효화다.** 3개월간 한쪽에서 잰 수치는
   다른 쪽 코드가 달라진 만큼 적용 근거를 잃는다.

실험 커밋이 통합 브랜치를 어지럽히는 것이 걱정이라면 그건 단기 작업 브랜치로 해결된다.
저장소 규칙의 `perf/` 접두사가 그 용도다.

**바꿔야 하는 것은 배포 트리거다.** 현재 `.github/workflows/deploy.yml` 은 `main` 푸시에서
ECR 로 이미지를 올리고 EC2 로 SSH 한다. 운영 노트북 구성에서는 둘 다 안 맞는다.

- **방향을 뒤집는다.** 노트북이 레지스트리에서 당겨오게 하면 인바운드 SSH 를 열지 않아도 된다.
- **트리거를 태그로 바꾼다.** `main` 푸시마다 자동 배포하면 배포 시각이 내 의도와 무관해진다.
  릴리스 태그를 밀 때만 배포하면 "언제 무엇을 올렸다"가 기록으로 남고, 배포 직후 지표가 나빠진
  것을 배포와 연결해 읽을 수 있다.
- **운영 노트북의 체크아웃을 태그에 고정한다.** 습관적으로 `git pull` 하면 배포 시점이 흐려진다.

`ci.yml` 은 그대로 둔다. `develop` PR 과 푸시에서 테스트를 돌리는 게이트이고, 운영 환경과 무관하다.

### 6.3 운영 → 측정 데이터 왕래

두 환경을 나누면 루프가 한 곳에서 끊긴다. 6개월 뒤 운영 노트북에서 목록 조회가 느려진 것을
발견했다고 하자. 고친 효과를 판정하려면 측정 환경에서 재야 하는데, 측정 환경의 데이터셋은 large
고정이라 6개월 자란 DB 와 행 수도 분포도 다르다. **발견은 운영에서 되는데 판정할 데이터가 측정
환경에 없다.**

**결정**: 운영 노트북의 MySQL 을 월 1회 덤프해 측정 환경의 새 데이터셋으로 등록한다. 지문이
다르므로 기존 기준선과 섞이지 않고 새 기준선이 생긴다. 그러면 "3개월치 데이터에서의 응답 시간"과
"6개월치에서의 응답 시간"을 같은 측정 환경에서 비교할 수 있다. 이게 데이터 증가를 근거 있는
수치로 바꾸는 유일한 경로다.

초기 시드도 같은 경로를 반대로 쓴다. `performance/datasets/snapshots/large-20260816-043326` 이
509MB 이고, 이걸 운영 노트북으로 옮겨 한 번 복원한 뒤로는 초기화하지 않는다.

## 7. 켜기 전에 정해야 하는 것 넷

**이 넷은 데이터에 굳으므로 켠 뒤에 못 바꾼다.** 나머지 항목은 늦게 알아도 고치면 되지만, 이 넷을
잘못 정하면 6개월치가 쓸 수 없는 모양으로 쌓인다.

### 7.1 시드 크기 — medium 이 아니라 large

초판은 medium 스냅샷 1회 시드를 지정했다. `performance/datasets/profiles.json` 의 값을 보면 두
군데가 안 맞는다.

| 프로파일 | 계정 | 게시글 | 댓글 | 반응 | 스냅샷 크기 |
|---|---:|---:|---:|---:|---:|
| medium | 1,000 | 10,000 | 40,000 | 100,000 | 110MB |
| large | 10,000 | 100,000 | 400,000 | 1,000,000 | 509MB |
| xlarge | 100,000 | 500,000 | 2,000,000 | 5,000,000 | 미생성 |

**첫째, medium 의 계정 1,000개로는 시뮬레이션 사용자 3,000명을 못 만든다.** 한 계정을 3명이
공유하게 되고, 그러면 5.1 ①이 k6를 버린 이유로 든 "번호가 사용자 정체성을 대신한다"가 형태만
바꿔 돌아온다.

**둘째, 자연 증가만으로는 절대 규모에 못 닿는다.** 하루 96,000 요청(8.1) 중 글 생성을 1%로 잡으면
960건/일이고, 180일이면 960 × 180 = 172,800건이다. medium 시드 10,000건에 더해도 182,800건이다.
초판 5장이 기대한 "게시글이 백만 행을 넘으면 OFFSET 페이징이 느려진다"에 닿으려면
(1,000,000 − 10,000) ÷ 960 = 약 1,031일, 2.8년이 걸린다.

교환 관계가 여기 있다. medium 에서 시작하면 증가 배수는 182,800 ÷ 10,000 = 18배로 크지만 절대
행수가 작아 규모에서 오는 성능 저하가 안 나온다. xlarge 에서 시작하면 규모 문제는 바로 보이지만
6개월 증가가 (500,000 + 172,800) ÷ 500,000 = 1.35배라 "자라서 느려졌다"는 관찰이 약해진다.

**결정**: large 로 시드한다. 계정 10,000개가 3,000명 시뮬레이션을 감당하고, 게시글은 100,000 →
272,800건으로 2.7배가 된다. 증가 배수와 절대 규모가 둘 다 쓸 만한 구간이다.

### 7.2 인기 쏠림 분포

실제 커뮤니티는 소수 글에 반응이 몰린다. 시뮬레이터가 읽을 글을 균등하게 고르면 6개월 뒤 모든
글에 댓글이 고르게 달린 DB 가 된다. 그런 DB 에서는 인기글 캐시 히트율과 HotScore 집계가 실제와
다르게 동작하고, 5.1 ②가 예로 든 "인기 글 하나에 댓글 500개, 원작자 앞으로 알림 500건" 같은
상황이 영원히 안 생긴다. 운영에서 터지는 게 대개 그 모양이다.

기존 `hotPost()` 가 인기글을 뽑아 주므로 시작점은 있다. 정할 것은 **새 글을 읽을 확률 대 인기글을
읽을 확률**이고, 이 비율이 6개월치 분포를 그대로 정한다.

### 7.3 신규 가입과 이탈

고정 3,000명으로 6개월을 돌리면 `users` 테이블이 안 자란다. 가입 흐름은
`UserController.java:108` 의 `POST /api/user/register` 로 있으므로 구현은 가능하다.

나중에 넣으면 안 되는 이유는 가입 시각이 전부 넣은 시점에 몰려, 가입 코호트별 분석이 불가능해지기
때문이다.

### 7.4 본문 길이 분포

디스크에 미치는 영향은 작다. 댓글 3,000건/일에 100바이트면 하루 300KB, 180일에 54MB다. 달라지는
곳은 둘이다. `/api/posts/search` 가 실제보다 짧은 본문을 검색하게 되고, 목록 응답의 직렬화 크기가
실제와 달라진다. 전부 "테스트 본문 1234"로 채우면 이 둘이 실제 서비스와 안 맞는다.

## 8. 시뮬레이터 설계

### 8.1 "수천 명"의 실체는 부하가 아니라 계정 다양성이다

고등학생 커뮤니티 앱에서 활성 사용자 3,000명, 1인당 하루 4세션, 세션당 8요청을 가정하면
하루 요청은 3,000 × 4 × 8 = 96,000건이다. 96,000 ÷ 86,400초 = **평균 1.11 요청/초**다.

요청 하나가 차지하는 시간을 think time 평균 2.5초로 잡으면, 어느 순간 실제로 세션 중인 사용자는
1.11 × 2.5 = **약 2.8명**이다. 나머지 2,997명은 다음 세션까지 86,400 ÷ 4 = 21,600초, 즉 6시간을
기다린다. Locust User 인스턴스를 3,000개 띄워도 CPU 를 쓰는 건 3명분이다.

**그러므로 이 구성에서 3,000명이 뜻하는 것은 동시 부하가 아니라 계정과 상태의 다양성이다.**
글쓴이가 3,000명으로 흩어지고 각자 다른 글 목록과 알림 이력을 갖는다는 뜻이다.

진짜 동시 접속 3,000명을 원한다면 요청률은 3,000 ÷ 2.5초 = 1,200 req/s 다.
`performance/scenarios/normal-day.js` 가 예상하는 45~55 req/s 의 1,200 ÷ 50 = 24배이고, 앱과 부하
생성기를 노트북 한 대에서 6개월 돌리는 구성으로는 불가능하다. 그 영역은 측정 환경의 breakpoint
실행이 담당한다.

### 8.2 시간 간격이 두 층이다

think time 1~4초는 세션 **안**의 화면 전환 간격이고, 세션 간격은 6시간이다. Locust 의 `wait_time`
은 태스크 사이 간격 하나뿐이므로 두 층을 직접 표현하지 못한다.

**구조**: 태스크 하나를 세션 전체(8요청 + 내부 sleep)로 만들고, `wait_time` 을 세션 간격으로 쓴다.
`workload.js` 의 여정 9종이 이미 그 모양이라 옮기기는 어렵지 않다. 다만 여정 하나를 태스크 하나로
잘못 쪼개면 6시간 간격이 여정마다 붙어 요청률이 9분의 1이 된다.

### 8.3 `user_count` 를 고정하고 활동 확률을 시간대로 바꾼다

5.1 ③에서 정정한 대로 `LoadTestShape` 로 사용자 수를 흔들면 상태가 사라진다.

**구조**: 사용자 수를 3,000명으로 고정한다. 각 사용자는 짧은 주기로 깨어나 그 시간대의 활동 확률
`p` 로 세션을 실행할지 정한다. 깨어나는 주기를 300초로 잡으면 초당 깨어남은 3,000 ÷ 300 = 10회고,
요청률은 10 × p × 8 = 80p req/s 다. 목표 요청률에서 `p` 가 바로 나온다.

| 시간대 | 목표 요청/초 | 활동 확률 p = 목표 ÷ 80 | 주된 행동 | 근거 |
|---|---:|---:|---|---|
| 01–06 | 0.2 | 0.0025 | 눈팅 | 심야, 거의 없음 |
| 07–08 | 4 | 0.05 | 급식·시간표 조회 | 등교길 |
| 12–13 | 6 | 0.075 | 눈팅 | 점심 |
| 16–18 | 3 | 0.0375 | 채팅 | 하교 후 |
| 21–24 | 5 | 0.0625 | 글쓰기·댓글 | 야간 |

깨어날 때마다 현재 시(hour)를 다시 읽으므로 시간대 전환이 자동으로 반영된다. 인스턴스는 죽지
않으므로 상태가 유지된다. 깨어남 자체는 대부분 아무 요청도 안 내므로 CPU 부담이 없다.

부하는 정직하게 낮게 잡는다. 평균 1.11 req/s 는 측정 환경이 예상하는 50 req/s 의 1/45 다.
운영 경험은 부하의 크기가 아니라 시간과 누적에서 나온다.

### 8.4 상태를 서버에서 복원한다

API 계약은 6개월간 최소 세 번 바뀐다. 멱등 전환이 반응·스크랩을 `PUT`/`DELETE` 로 바꾸고, 다중
인스턴스 전환과 브로커 교체가 또 건드린다. 그때마다 `locustfile.py` 를 고치고 Locust 를
재시작해야 하는데, 재시작하면 메모리에 있던 사용자 상태가 전부 사라진다.

**피할 수 있다.** `performance/scripts/mypage.js:26` 이 쓰는 `/api/mypage/posts` 와
`/api/mypage/comments` 가 "내가 쓴 글·댓글"을 돌려준다. `on_start` 에서 이 둘을 한 번 호출해
`self.my_post_ids` 를 복원하면 프로세스를 재시작해도 상태가 서버에서 되살아난다.

**상태를 메모리에만 두지 않는 것이 6개월 유지보수 비용을 가르는 지점이다.**

### 8.5 실패를 구분한다

6개월 중 어느 날 실패율이 오르면 "시뮬레이터가 잘못 짠 요청이라 400"인지 "서버가 고장나서
500"인지 알아야 한다. `performance/scripts/mypage.js:24` 주석이 같은 경험을 적어 뒀다.
`sortType` 을 빼면 400이 떨어져 부하가 조회 경로가 아니라 에러 경로를 때린다는 실측이다.

**결정**: 상태 코드대별로 따로 세고, 알림 규칙은 5xx 에만 건다(5.2). 4xx 급등은 대시보드에서만
보고, 첫 2주 튜닝 기간에 0에 가깝게 만든다. 공개 노출을 하면 스캐너 때문에 404 가 자연히 늘어나는데,
그것과 내 시뮬레이터의 400 을 구분하려면 경로별 분리도 필요하다.

### 8.6 최소판에 넣을 것과 나중에 늘릴 것

줄일 것은 여정 종류이지 7장의 결정 넷이 아니다.

**최소판에 넣는다**: 읽기 여정(`journeyBrowse`, `journeyMorning`), 쓰기 여정(`journeyWrite`),
그리고 **알림을 열어 내 글에 달린 댓글에 답하는 연쇄** 하나. 마지막 것이 k6로 못 만들던 바로 그
흐름이므로, 빠지면 Locust 를 쓸 이유가 없다.

**나중에 늘린다**: 채팅, 검색, 친구, 미디어 업로드. 여정 추가는 데이터 분포를 바꾸지 않으므로 켠
뒤에 붙여도 손실이 없다.

**WebSocket 채팅은 최소판에서 뺀다.** `scripts/chat-ws.js` 121줄에 `scripts/lib/stomp.js` 의
STOMP 프레이밍 직접 구현까지 포팅해야 해서 비용이 나머지 전부와 비슷하다. REST 채팅만으로도
채팅방과 메시지는 자란다.

### 8.7 분량

초판은 300줄 안팎으로 잡았다. 그 추정은 엔드포인트 호출 래퍼만 센 값이다. 8.2~8.5의 구조(세션
단위 태스크, 활동 확률, 상태 복원, 실패 분리)와 7장의 결정(쏠림 분포, 가입·이탈, 본문 생성)을
넣으면 **[판단] 최소판이 400줄 안팎, 여정을 다 넣으면 600~800줄**로 본다.

옮기는 자체는 어렵지 않다. `performance/scripts/*.js` 에서 `BASE_URL` 호출을 뽑아 중복 제거하면
엔드포인트 35개다(2026-09-14 grep). 그 파일들은 전부 1,309줄인데 절반 가까이가 k6의
`check`·`tags`·`Trend` 계측 코드다. Locust 의 `HttpUser` 는 내부적으로 `requests.Session` 을
쓰므로 쿠키를 알아서 들고 다니고, `scripts/lib/session.js` 의 쿠키 저장소 관리 코드가 통째로
필요 없어진다.

**OpenAPI 스펙으로 골격을 뽑을 수 있다.** `build.gradle:57` 의 springdoc 이 `/swagger/api-docs`
로 스펙을 낸다. 다만 스펙이 알려주는 건 "어떤 필드를 보내야 하는가"까지고 "어떤 순서로 얼마나
자주 하는가"는 안 나온다. 행동 확률은 `scenarios/lib/workload.js` 의 기존 여정 가중치를 옮긴다.

## 9. 관측 설정 — 측정 환경 값을 그대로 쓰지 않는다

### 9.1 자원 한계

`docker-compose.perf.yml` 의 한계값은 MySQL 2.0 CPU / 512MB, Redis 1.0 / 512MB, 앱 8.0 / 2,560MB
다. 이 값들은 최근 커밋이 **병목이 DB 에 닿도록** 일부러 좁힌 것이다. 운영 노트북에는 그 목적이
없다.

그대로 쓰면 무엇이 깨지는지가 분명하다. MySQL 버퍼 풀이 512MB 로 묶인 채 6개월간 데이터가 자라면,
느려진 원인이 데이터 증가인지 버퍼 풀 부족인지 구분할 수 없다. 이 환경이 만들려던 것은 전자인데
후자가 먼저 온다.

**결정**: 운영 노트북은 실제 서버에 가깝게 잡거나 한계를 걸지 않는다.

### 9.2 수집 간격과 보존 기간

`docker-compose.perf.yml:228` 이 Prometheus 에 `--storage.tsdb.retention.time=30d` 를 준다. 30일이
지난 지표는 삭제된다. **6개월을 돌려도 3월에 볼 수 있는 건 최근 30일뿐이고, 11월 장애 구간의
지표는 이미 없다.** 상시 가동의 산출물이 기록인데 그 기록이 자동으로 지워지는 설정이다.

보존을 늘리면 디스크가 문제가 되므로 수집 간격을 같이 손본다. `prometheus.yml` 의
`scrape_interval` 은 5초이고, 그 자리 주석이 이유를 적어 뒀다. 부하 테스트에서 스파이크를 놓치지
않기 위해서다. 운영 노트북은 분 단위 추세를 보므로 그 이유가 적용되지 않는다.

| 수집 간격 | 계열 하나의 하루 표본 | 계열 1만 개의 하루 표본 | 하루 디스크(표본당 2바이트) | 180일 |
|---|---:|---:|---:|---:|
| 5초 | 86,400 ÷ 5 = 17,280 | 172,800,000 | 약 346MB | 약 62GB |
| 30초 | 86,400 ÷ 30 = 2,880 | 28,800,000 | 약 58MB | 약 10GB |

계열 1만 개는 가정이다. 실제 값은 `prometheus_tsdb_head_series` 를 조회하면 나오고, 이 앱은
`application.properties:21~35` 에서 HTTP 요청·HikariCP·GC 에 히스토그램 버킷을 켜 두어 계열이
많은 편이다. **켜기 전에 이 값을 한 번 재고 보존 기간을 정한다.**

로그는 훨씬 작다. 1.11 req/s × 86,400초 = 약 96,000줄/일이고 줄당 200바이트면 하루 19MB,
압축하면 180일에 1GB 안팎이다.

## 10. 단계별 실행 계획

**초판과 순서가 다르다.** 초판은 알림이 1단계, Locust 가 4단계였고 이유는 "알림 없이 트래픽만
만들면 고장을 내가 화면을 보고 있을 때만 알게 된다"였다. 그런데 같은 문서가 **첫 2주는 고장을
넣지 않는다**고 정했으므로, 그 2주 동안 알림 규칙 4개가 잡을 주입 고장이 없다. 그 2주에 실제로
위험한 것은 노트북이 죽어 누적이 멈추는 것이고, 그건 규칙 4개가 아니라 외부 감시 하나가 잡는다
(5.3).

그래서 **외부 감시 → 트래픽 → 알림 규칙 → 로그 → 고장 → 기록** 순으로 바꾼다.

### 0단계 — 켜기 전 결정 (반일)

7장의 넷(시드 크기, 쏠림 비율, 가입·이탈 여부, 본문 길이 분포)을 정하고, 노트북의 RAM·SSD 여유와
Prometheus 계열 수를 확인한다.

**완료 조건**: 넷이 문서에 적히고, 보존 기간과 수집 간격이 숫자로 정해진다.

### 1단계 — 멱등 전환 (2일)

`localDocs/TODO.md` 1-A 의 토글 3개를 `PUT`/`DELETE` 로 바꾼다. `PostReactionService.java:35` 의
`likeReact()` 가 현재 상태를 읽고 뒤집는 코드가 그대로 남아 있다(2026-09-22 확인).

**왜 먼저인가**: 이 변경이 `locustfile.py` 가 부르는 엔드포인트의 계약을 바꾼다. 나중에 하면
locustfile 을 두 번 쓰게 된다.

**하지 않는 것**: 시뮬레이터에 재시도를 넣는 것. 멱등 전환 전에 재시도를 넣으면 그게 바로 데이터
오염이다. 재시도는 전환이 끝난 뒤에 붙인다.

### 2단계 — 노트북 준비 (1일)

OS, 절전 해제, Docker 자동 시작, 저장소 체크아웃, prod 환경변수 셋(4.4) 확정.

**완료 조건**: 노트북을 강제 재부팅했을 때 사람이 손대지 않아도 앱이 다시 뜬다.

### 3단계 — 서비스 기동과 시드 (1일)

앱·MySQL·Redis·Prometheus·Grafana 를 올리고 large 스냅샷(509MB)을 한 번 복원한다. 자원 한계와
보존 기간은 9장 값으로 바꾼다.

**완료 조건**: Grafana 에서 앱 지표가 보이고, `SELECT COUNT(*) FROM posts` 가 100,000 근처다.

### 4단계 — 외부 감시 (1시간)

노트북이 외부 서비스로 주기 신호를 보내고, 신호가 끊기면 휴대폰에 알림이 오게 한다.

**완료 조건**: 노트북 전원을 내렸을 때 휴대폰에 알림이 온다. **여기까지 되면 누적이 멈춘 것을
반드시 알게 되므로, 다음 단계부터 켜 두고 잊어도 된다.**

### 5단계 — 트래픽 (2~3일)

`locustfile.py` 최소판(8.6)을 쓰고 `locustio/locust` 와 `containersol/locust_exporter` 를 올린다.
`prometheus.yml` 에 `job_name: locust` 를 추가하고 Grafana 대시보드 ID **20462** 를 임포트한다.

**완료 조건 둘.** 24시간 곡선이 대시보드에 나타난다. 그리고 하루 뒤
`SELECT COUNT(DISTINCT user_id) FROM posts` 가 시드 시점보다 늘어난다. 5.1 ①이 지적한 "소수 계정만
활동" 문제가 재현되지 않는지 확인하는 것이다.

**여기서 시계가 시작된다.**

### 6단계 — 알림 규칙 (1일)

Alertmanager 와 ntfy 를 올리고 `prometheus.yml` 에 `rule_files` 와 `alerting:` 을 추가한다.
규칙 4개는 5.2, 4xx 를 빼는 이유는 8.5.

**완료 조건**: 앱 컨테이너를 손으로 중지했을 때 휴대폰에 알림이 도착한다.

### 7단계 — 로그 (반일)

Loki 와 Alloy 를 붙이고 Grafana 에 데이터소스로 등록한다.

**완료 조건**: 대시보드에서 지표 급등 구간을 드래그해 같은 시각의 앱 로그로 넘어간다.

### 8단계 — 무작위 고장 (1~2일)

5.5의 438줄을 추출해 cron 에서 부른다. 주 2~3회, 사전에 알 수 없는 시각에 주입하고 몇 분 뒤
되돌린다.

**완료 조건**: 내가 모르는 시각에 장애가 나고, 그것을 Grafana 가 아니라 알림으로 인지한다.

### 9단계 — 기록 (상시)

**완료 조건**: 장애 1건당 포스트모템 1건. 알림에서 인지까지, 인지에서 복구까지의 시간이 기록에
남는다.

### 첫 2주는 고장을 넣지 않는다

5단계까지 켜고 그냥 둔다. 아무것도 안 했는데 알림이 울리면 그건 규칙이 너무 민감하다는 증거이고,
임계값 튜닝이 8단계보다 먼저다. 잘못 튜닝된 상태로 고장을 넣으면 진짜 장애 알림이 평소 소음에
묻혀 인지 시간이 늘어난다. 같은 2주에 4xx 를 0에 가깝게 만든다(8.5).

### 합계

0~5단계까지 **약 7~8일**이다. 그중 이틀이 멱등 전환이고 사흘이 locustfile 이다.

## 11. 이 구성이 주지 못하는 것

합성 트래픽으로 얻는 것은 **장애 대응 훈련**이고 실사용자 운영과는 다르다. 구체적으로
다음이 안 생긴다.

- **예상 못 한 입력.** 시뮬레이터는 내가 쓴 코드대로만 요청하므로, 내가 상상 못 한 요청은
  영원히 안 온다.
- **크롤러와 취약점 스캐너.** 4.3의 세 번째 목적으로 포트를 열면 이건 생긴다. 열지 않으면 안
  생긴다.
- **기기와 네트워크의 다양성.** 끊기는 모바일 네트워크, 구버전 앱, 이상한 User-Agent.
- **네트워크 왕복 시간.** Locust 가 노트북 안에서 돌면 요청이 loopback 을 타서 왕복이 0.1ms
  수준이고 실제 모바일은 30~100ms 다. 서버 지표에는 거의 안 나타난다. 서버가 커넥션을 붙잡는
  시간은 처리 시간이 지배하기 때문이다. 달라지는 건 클라이언트 쪽 타임아웃과 재시도가 발동하는
  시점이다. 좁히려면 toxiproxy 로 상시 50ms 지연을 넣을 수 있다.
- **압박.** 내 실수가 남에게 영향을 준다는 감각은 합성 트래픽이 만들지 못한다.

**가장 효과가 큰 보완책은 실제로 공개해서 사용자를 열 명이라도 받는 것이다.** 열 명이면 부하는
없는 것이나 마찬가지지만 위 항목 대부분이 생긴다. 합성 트래픽은 그 위에 "부하가 있을 때의
거동"을 얹는 역할이다. 둘은 대체재가 아니라 보완재다.

이 계획의 결과를 밖에 설명할 때도 같은 구분을 유지한다. "장애 주입과 알림 기반 대응을 반복해
인지 시간과 복구 시간을 측정했다"는 사실이고, "실사용자 트래픽을 운영했다"는 사실이 아니다.
