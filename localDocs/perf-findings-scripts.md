# k6 스크립트·시나리오 발견 사항

- 최초 검토: 2026-08-05
- 추가 검증: 2026-08-11

검토 범위:

- `performance/scripts/`
- `performance/scenarios/`
- 공통 라이브러리 `performance/scripts/lib/`

라인 번호는 검토 당시 코드를 기준으로 한다. 코드가 바뀌면 함수명과 파일명을 먼저 찾는다.

## 이 문서가 답하는 질문

k6가 많은 요청을 보냈다고 해서 현실적인 성능 테스트가 되는 것은 아니다. 이 문서는 다음을
확인한다.

- 가상 사용자가 실제 사용자처럼 로그인하고 행동하는가?
- 선언한 저니 비율이 실제 요청 비율과 일치하는가?
- 인기글·첫 페이지·콜드 데이터가 의도한 비율로 선택되는가?
- 서버가 느려져도 같은 요청률을 유지하는가?
- 전체 p95와 쓰기 SLO가 정말 측정하려던 기능을 설명하는가?
- 실행이 진행되면서 데이터와 사용자 상태가 달라지지 않는가?

## 먼저 알아야 할 용어

- **iteration**: VU 한 명이 시나리오 함수를 처음부터 끝까지 한 번 실행한 단위
- **VU(Virtual User)**: k6에서 동시에 행동하는 가상 사용자
- **저니(journey)**: 조회, 반응, 글쓰기처럼 사용자 행동을 묶은 흐름
- **closed model**: VU 수를 고정하는 모델. 응답이 느려지면 같은 VU가 다음 요청을 늦게 보내 요청률도 줄어듦
- **open model**: 초당 도착률을 고정하는 모델. 서버가 느려져도 계획한 요청 도착률을 유지
- **coordinated omission**: 서버가 느릴수록 발생기가 요청을 덜 보내 가장 나쁜 지연을 놓치는 현상
- **breakdown**: 전체 지표를 기능·작업·엔드포인트별로 나눈 값
- **SLO**: 허용하려는 성능 목표. 예: 쓰기 요청 p95가 500ms 미만

## CRITICAL

### S-01. 매 iteration마다 BCrypt 로그인을 수행함 — 상태: 해결 (2026-08-11, 미커밋)

**쉽게 말하면**

게시글 성능을 재는 테스트가 사실은 매번 비밀번호 로그인을 하고 있었다. 서버가 느려진 주된
원인이 게시글 처리인지 BCrypt 비밀번호 검증인지 구분하기 어려웠다.

**수정 전 동작**

`scripts/lib/session.js`의 `ensureSession()`은 k6의 기본 쿠키 저장소를 확인했다. 이 저장소는
iteration이 끝날 때 초기화된다. `workload.js`는 모든 iteration의 시작에서
`ensureSession()`을 호출하므로, 모든 iteration이 다음 요청으로 시작했다.

```text
POST /api/user/login
```

`normal-day-2026-08-04T06-38-42` 실측값:

- iteration: 559회
- 로그인: 562회
- 전체 HTTP 요청 중 로그인 비율: 19.4%
- 시나리오가 의도한 재로그인 비율: 1%

즉 문서에는 browse·engage·write 비율이 적혀 있었지만 실제 요청의 약 5개 중 1개는 BCrypt
로그인이었다. 애플리케이션이 2 CPU로 제한돼 있어 로그인끼리 겹치면 다른 기능의 지연에도
영향을 줬다.

**해결 내용**

k6 v2.1.0에서 두 쿠키 저장소의 수명을 직접 비교했다.

| 저장소 | 첫 iteration | 다음 iteration |
|---|---|---|
| `http.cookieJar()` | 쿠키 존재 | 초기화됨 |
| 모듈 범위의 `new http.CookieJar()` | 쿠키 존재 | 유지됨 |

`config.js`에 VU마다 유지되는 `vuJar`를 만들고 모든 HTTP 요청이 같은 저장소를 사용하게 했다.
계정도 VU 번호로 고정 배정되므로 한 VU의 쿠키가 다른 계정과 섞이지 않는다.

`posts.js`, 20 VU, 60초, large 데이터셋 검증 결과:

| 엔드포인트 | 요청 수 | 비율 |
|---|---:|---:|
| `/api/posts/{postId}` | 654 | 68.1% |
| `/api/boards/{boardId}/posts` | 239 | 24.9% |
| `/api/posts/search` | 28 | 2.9% |
| `/api/user/login` | **20** | **2.1%** |
| `/api/posts` | 19 | 2.0% |

로그인은 iteration 수가 아니라 VU 수와 같은 20회만 발생했다.

**남은 문제: 시작 시 로그인 몰림**

20 VU가 시작과 동시에 로그인하면 BCrypt 20건이 한꺼번에 2 CPU를 경쟁한다. 실측 로그인
중앙값은 약 3.15초였고 최대 약 3.6초였다. 60초 실행에서는 로그인 20건이 전체 요청의 약
4%를 차지해 전체 p95에 다시 들어갈 수 있다.

따라서 반복 로그인 문제는 해결됐지만, **시작 직후 로그인 덩어리가 짧은 실행의 백분위를
오염하는 문제**는 남았다. 후보는 다음과 같다.

- VU를 서서히 늘려 로그인을 시간상 분산
- 첫 로그인 전에 VU별 작은 무작위 지연 적용
- 시작 구간을 warmup으로 분리하고 k6 집계에서도 제외

이 선택은 T-03의 측정 구간 설계와 함께 결정해야 한다.

### S-02. 쓰기 SLO가 실제로는 로그인 지연을 측정함 — 상태: 해결 (2026-08-11, `cad1cbc`)

**쉽게 말하면**

“쓰기 요청 p95”라는 이름만 보면 게시글·댓글·좋아요 쓰기 성능처럼 보인다. 하지만 측정값의
대부분은 로그인·로그아웃·토큰 갱신이었다.

**수정 전 동작과 근거**

`session.js`는 로그인, 로그아웃, 토큰 갱신에 모두 `op:write` 태그를 붙인다. 기준선 실행에서
`op:write`는 총 761건이었고 구성은 다음과 같았다.

- 인증 요청: 569건, 약 75%
- 실제 도메인 쓰기: 192건, 약 25%

그래서 다음 두 값이 거의 같았다.

- `breakdown.op.write.p95 = 95.8ms`
- `breakdown.feature.auth.p95 = 98.7ms`

**왜 문제인가**

좋아요 카운터 락, 댓글 쓰기, Hikari 연결 풀 포화가 느려져도 인증 요청에 약 3:1로 희석된다.
반대로 BCrypt가 느려지면 “도메인 쓰기 성능이 나빠졌다”고 오해할 수 있다.

로그인 한 요청에는 `name:login p95<800`과 `op:write p95<500`이라는 서로 다른 두 기준도
동시에 적용된다.

**해결 내용**

- 로그인, 토큰 갱신, 로그아웃의 태그를 `op:write`에서 `op:auth`로 변경했다.
- `http_req_duration{op:auth}`를 분해축 생성용 threshold에 추가해 인증 지연을 리포트에서
  계속 확인할 수 있게 했다. 이 threshold는 `p(99)<600000`인 관측용 항목이라 SLO 판정에는
  사용하지 않는다.
- `op:write`에는 게시글·댓글·반응 같은 도메인 쓰기만 남겼다.
- 요약 파서가 `op:auth`를 별도 breakdown으로 보존하는 회귀 테스트를 추가했다.

**Before / After 검증**

두 실행은 같은 Mac, 같은 `perf-app`, smoke 데이터셋, `posts.js`, 20 VU, 60초 조건에서
연속 실행했다. 변경 변수는 인증 요청의 `op` 태그뿐이다.

- Before 원자료: `performance/reports/runs/posts-2026-08-11T12-03-32/run.json`
- After 원자료: `performance/reports/runs/posts-2026-08-11T12-05-00/run.json`

| 지표 | Before (`auth → write`) | After (`auth → auth`) | 해석 |
|---|---:|---:|---|
| 전체 요청 수 | 545 | 549 | 요청량이 비슷해 비교 가능 |
| 완료 iteration | 137 | 140 | 사용자 진행량이 비슷함 |
| `feature:auth` p95 | 578.4ms | 470.8ms | 두 실행 모두 인증 자체는 수백 ms |
| `op:auth` p95 | 0ms | 470.8ms | After에서 인증 작업군이 독립적으로 생성됨 |
| `op:write` 평균 | 162.5ms | 13.7ms | 인증 표본 제거 후 도메인 쓰기 평균이 드러남 |
| `op:write` p95 | 571.4ms | 23.0ms | 약 96% 하락. 서버 가속이 아니라 분류 교정 효과 |
| `op:write` p99 | 579.6ms | 38.1ms | 느린 인증 꼬리가 쓰기 지표에서 제거됨 |
| write `p95<500ms` | FAIL | PASS | 인증 때문에 발생하던 거짓 실패 제거 |
| write `p99<1200ms` | PASS | PASS | 두 실행 모두 기준 충족 |

After에서 `op:auth`와 `feature:auth`의 평균·p90·p95·p99가 모두 정확히 일치했다. 인증 요청이
새 작업군으로 전부 이동했다는 실행 증거다. 반대로 `op:write`의 최대값은 581.4ms에서
44.0ms로 내려가, 로그인 지연이 더 이상 쓰기 분포에 들어가지 않음을 확인했다.

이 결과를 “서버 쓰기 성능이 96% 개선됐다”고 해석하면 안 된다. 애플리케이션 코드는 바뀌지
않았고 태그만 교정했다. 개선된 것은 **도메인 쓰기 SLO의 정확성과 원인 귀속 능력**이다.
또한 각 조건을 한 번씩 실행했고 Prometheus가 기동되지 않아 인프라 차이를 비교하지 않았다.
따라서 전체 p95와 RPS의 차이는 성능 개선 근거로 사용하지 않는다.

**남은 범위**

- 시작 시 VU 20개가 동시에 로그인하는 현상은 그대로다. 인증 분리는 전체 HTTP p95에서
  로그인을 제외하지 않으므로 S-01의 후속 문제와 T-03 측정 구간 설계에서 다룬다.
- 로그인·토큰 갱신·로그아웃은 비용 구조가 다르므로, 인증 SLO가 필요하면 `op:auth` 하나로
  묶기보다 `name:login`, `name:token_refresh`, `name:logout`별 기준을 둔다.
- 기능별 도메인 write SLO는 S-02의 필수 범위가 아니다. 필요해지면 다중 태그 지표
  (`feature:post,op:write` 등)로 별도 설계한다.

### S-03. 인기 데이터 선택 함수가 가장 인기 있는 항목을 절대 고르지 못함 — 상태: 미해결

**쉽게 말하면**

인기글에 요청을 집중하려고 만든 함수가 정작 1위 인기글은 한 번도 선택하지 않는다. 대신
두 번째 항목에 전체 요청의 약 20% 이상이 몰린다.

**현재 동작**

`scripts/lib/data.js`의 `zipfIndex()`는 다음과 비슷한 계산을 한다.

```text
floor(n ^ (u ^ 1.7)) % n
```

`u`는 0 이상 1 미만이므로 `n ^ (...)`는 항상 1 이상이다. 따라서 결과는 최소 1이고
`index 0`은 나올 수 없다.

**실제 분포**

- small, N=500: index 1이 약 27.5%
- large, N=100,000: index 1이 약 19%
- index 0: 0회

문서에는 Zipf `s≈1.07`, 80/20 분포라고 적혀 있지만 현재 수식은 해당 Zipf 분포의 역누적
분포 함수가 아니다. 데이터셋 크기가 바뀌면 분포 모양도 바뀐다.

**왜 문제인가**

- 시드에서 가장 인기 있는 `posts[0]`이 조회·반응·스크랩 테스트에서 제외된다.
- 특정 한 행에 과도한 락과 캐시 요청이 몰린다.
- 데이터셋 크기별 결과를 같은 인기 분포로 비교할 수 없다.
- BTL-003 핫로우와 Redis 적중률 분석의 전제가 달라진다.

**필요한 조치**

목표 Zipf 분포와 `s` 값을 먼저 정하고, 실제 역CDF 또는 검증 가능한 샘플러로 교체한다.
자동 테스트는 최소한 다음을 확인해야 한다.

- index 0이 선택되는가
- 범위를 벗어난 index가 없는가
- N이 달라도 목표 상위 20% 접근 비율이 유지되는가
- 고정된 대량 표본에서 허용 오차 안의 분포가 나오는가

### S-04. 게시판 첫 페이지를 한 번도 요청하지 않음 — 상태: 미해결

**쉽게 말하면**

실제 사용자가 가장 많이 보는 첫 페이지가 성능 테스트에서는 완전히 빠져 있다.

**현재 동작**

`posts.js`와 `workload.js`는 게시판 페이지를 `zipfIndex(5)`로 고른다. S-03 때문에 결과는
1~4만 나오며 0페이지는 선택되지 않는다. 약 61%는 1페이지에 몰린다.

**왜 문제인가**

첫 페이지는 일반적으로 가장 자주 조회되고 캐시 적중률도 높은 경로다. 이 경로를 빼고 깊은
페이지에 요청 100%를 보내면 다음 결론이 운영과 반대로 나올 수 있다.

- 게시판 목록 캐시가 얼마나 효과적인가
- 최신 글 목록의 p95가 얼마인가
- 페이지가 깊어질수록 DB 비용이 어떻게 증가하는가

**필요한 조치**

S-03 샘플러 수정과 함께 0~4페이지의 목표 비율을 명시한다. 실행 결과에는 실제 페이지별 요청
수를 남겨 선언한 비율과 일치하는지 확인할 수 있어야 한다.

### S-05. 실패 요청 수에 성공 요청 수를 저장함 — 상태: 해결 (2026-08-05)

**쉽게 말하면**

리포트의 “실패 요청 수” 칸에 성공한 요청 수가 들어가 있었다.

**원인**

k6 Rate 메트릭 `http_req_failed`에서 다음 이름은 직관과 반대다.

- `passes`: 조건이 참이었던 횟수, 즉 요청 실패 횟수
- `fails`: 조건이 거짓이었던 횟수, 즉 요청 성공 횟수

`summary.js`와 `migrate-raw.js`가 `fails`를 실패 요청 수로 읽었다.

실제 원자료가 다음과 같을 때:

```text
rate=0.5578, passes=4051, fails=3212
```

실패 요청은 4,051건인데 리포트에는 3,212건이 저장됐다. 같은 화면의 오류율과 실패 수가 서로
모순됐다.

**해결 내용과 남은 작업**

두 파일의 읽기 방향을 수정하고 회귀 테스트를 추가했다. 신규 실행은 정상이다.

과거 `run.json`에는 잘못된 값이 이미 저장돼 있다. 이 값은 1차 summary 단계에서 만들어져
단순 재수집만으로 고쳐지지 않는다. 과거 이력을 고치려면 `rawMetrics`에서 다시 계산해야 한다.

### S-06. 한계 탐색 테스트가 서버가 느려질수록 부하를 줄임 — 상태: 미해결

**쉽게 말하면**

서버의 한계를 찾으려는 테스트가 서버가 느려지면 자동으로 요청을 덜 보낸다. 가장 힘든 순간을
발생기가 피하는 구조다.

**현재 동작**

다음 시나리오는 `ramping-vus` 또는 `constant-vus`인 closed model을 사용한다.

- stress
- spike
- soak
- chaos
- failover

closed model에서 대략적인 도착률은 다음과 같다.

```text
도착률 ≈ VU 수 / (응답시간 + think time)
```

응답시간이 길어지면 같은 VU가 다음 요청을 늦게 보내므로 도착률이 떨어진다.

**왜 문제인가**

- stress 테스트가 실제 최대 처리량을 찾지 못한다.
- spike 테스트의 순간 요청 폭증이 서버 지연과 함께 사라진다.
- 느린 요청이 많은 구간이 표본에서 줄어 coordinated omission이 생긴다.

로그인 실패 시 iteration을 즉시 종료하는 동작도 왜곡을 키운다. 2026-08-05 normal-day 붕괴
실행에서는 오류율이 55.8%였는데도 실패한 iteration이 빨리 끝나 TPS가 정상처럼 보였다.

**필요한 조치**

- 한계와 스파이크를 찾는 시나리오는 arrival-rate 기반 open model로 바꾼다.
- 정상 사용자 체류를 보는 soak는 목적에 따라 closed model을 유지할 수 있다.
- `dropped_iterations`를 필수 지표와 게이트로 추가한다.
- 서버가 무너질 때 요청률이 유지됐는지 실제 arrival rate를 함께 기록한다.

## HIGH

### S-07. VU 수보다 계정 수가 적어 여러 사용자가 같은 계정을 공유함 — 상태: 미해결

**쉽게 말하면**

서로 다른 가상 사용자가 같은 계정으로 동시에 행동한다. 실제 사용자 경합이 아니라 테스트가
만든 인공 경합이 생긴다.

**현재 동작**

`myUser()`는 VU 번호를 사용자 배열 길이로 나눈 나머지로 계정을 고른다.

```text
users[(vu.idInTest - 1) % users.length]
```

small 데이터셋에는 계정이 100개지만 다음 시나리오는 이를 넘는다.

- normal-day: 최대 200 VU
- peak-hour: 최대 500 VU
- stress: 최대 1,000 VU
- breakpoint: 최대 2,000 VU

**영향**

- 동일한 사용자 행에 불필요한 DB 락이 생긴다.
- refresh token 행을 여러 VU가 동시에 갱신한다.
- 한 VU의 logout이 같은 계정을 쓰는 다른 VU에 영향을 줄 수 있다.
- 사용자별 캐시와 알림 상태가 비현실적으로 공유된다.

**필요한 조치**

프로파일별 최대 VU보다 충분히 많은 계정을 만들거나, 실행 전 계정 수가 부족하면 시작을
거부한다. 계정 공유 자체를 연구하려는 실험은 별도 시나리오로 분리한다.

### S-08. k6와 인프라 지표가 서로 다른 시간 구간을 설명함 — 상태: **해결** (2026-08-12, 미커밋)

> "측정 구간에 phase 태그를 붙여 k6와 Prometheus가 같은 구간만 집계"라는 이 항목의
> 필요 조치를 그대로 구현했다. 시나리오가 `scripts/lib/phases.js`의 `buildPhasePlan`으로
> warmup/measure/rampdown을 초 단위로 선언하고 `stagesFor()`가 그 값으로 k6 stages를
> 생성한다(하드코딩 제거) — normal-day는 기존과 동일하게 5분/20분/2분이 기본값이지만
> 이제 `-e WARMUP=<sec>`로 실제 stage 길이 자체를 바꿀 수 있다. `config.js`의 `tags()`/
> `check()`가 매 요청·체크마다 `phase` 태그를 동적으로 붙이고, `summary.js`가
> `k6.phases.{warmup,measure,rampdown}`으로 분리 집계한다. `collect.js`의
> `measureWindow()`가 `run.phasePlan.measureStartOffsetSec`/`measureSec`로 Prometheus
> 창을 계산해 `k6.phases.measure`와 정확히 같은 시간대를 본다 — `to`가 더 이상 무조건
> 실행 종료 시각이 아니라서 rampdown/`gracefulRampDown`도 인프라 창에서 제외된다.
> 리포트(`report.js`)는 "측정 구간" 메타 행, `Performance Summary`의 measure/전체 구간
> 라벨, Grafana 링크의 전체/measure 구간 분리, `infra.window.incomplete`(조기 종료) 경고를
> 추가해 "전체 실행 시간·warmup·실제 판정 구간"을 함께 보여준다.
>
> 상세 설계·대안 검토는 `perf-findings-tools.md`의 T-03에 적었다 — 같은 구현의 다른
> 관점 기록이라 여기서 반복하지 않는다. 검증도 T-03과 같다(`node --test tools/test/*.test.js`
> 100건 통과, 실제 k6 실행 미검증).

**쉽게 말하면**

한 리포트 안의 p95와 CPU가 같은 시간을 측정한 값이 아니다.

**현재 동작**

- k6 지표: 램프업·유지·램프다운 전체 구간
- Prometheus 인프라 지표: `--warmup`으로 앞 구간을 제외할 수 있음

normal-day에서는 램프업 5분과 램프다운 2분이 전체 실행의 약 26%를 차지한다. 유지 구간의 VU가
같아도 램프 시간을 바꾸면 전체 p95가 달라질 수 있다.

**왜 문제인가**

CPU 80%와 p95 300ms를 나란히 놓아도 실제로는 다른 시간 범위의 값일 수 있다. 코드 변경이
없는데 시나리오 단계 길이만 바꿔도 회귀가 발생한 것처럼 보일 수 있다.

**필요한 조치**

측정 구간에 phase 태그를 붙여 k6와 Prometheus가 같은 hold 구간만 집계하게 한다. 리포트에
전체 실행 시간, warmup, 실제 판정 구간을 함께 표시한다.

### S-09. 서버가 무너지는 시나리오에 기능별 분해가 없음 — 상태: 미해결

**쉽게 말하면**

“어디가 먼저 무너졌는지”를 알고 싶은 테스트에서 어느 기능이 느려졌는지를 기록하지 않는다.

**현재 동작**

stress, breakpoint, spike, chaos, failover는 자체 threshold를 정의하면서 공통
`DEFAULT_THRESHOLDS`를 버린다. k6는 threshold에서 참조한 태그 서브메트릭만 생성하므로
이 실행들에는 `feature:*`, `op:*` breakdown이 만들어지지 않는다.

시나리오마다 breakdown 구조도 달라 같은 엔드포인트의 추세를 비교하기 어렵다.

**필요한 조치**

- “서브메트릭 생성용 threshold”와 “실패 판정용 threshold”를 분리한다.
- 모든 시나리오가 공통 feature·op·name 축을 기록하게 한다.
- 한계 탐색형 시나리오에는 정상 부하 SLO와 다른 판정 규칙을 적용한다.

### S-10. 느린 실행을 기준선에서 제외해 상대 비교가 꺼짐 — 상태: 미해결

**쉽게 말하면**

성능을 개선하려고 비교하는데, 느린 “개선 전” 결과를 기준선으로 쓸 수 없게 막아뒀다. 그래서
개선 전과 개선 후가 모두 목표를 넘으면 두 결과의 차이를 영원히 비교할 수 없다.

**현재 동작**

`repository.js`는 `thresholdsPassed !== false`인 실행만 기준선 후보로 사용한다. 이 값은
checks, read p95·p99, write p95·p99 등 여러 threshold의 전체 AND 결과다.

성능이 느리다는 이유와 측정이 잘못됐다는 이유를 같은 boolean 하나로 취급한다.

**EXP-000 실측**

`posts.js`를 같은 조건으로 12회 실행했다.

- smoke 확인: 2회
- Before 반복 측정: 10회
- 기준선 선택 성공: 0회
- `thresholdsPassed=false`: 12회

12번째 실행에서도 리포트는 “이 시나리오의 첫 실행”이라고 표시했다.

원인 흐름은 다음과 같다.

```text
large 실측 p99 약 3.8초
        │
        ▼
DEFAULT_THRESHOLDS 여러 개 실패
        │
        ▼
thresholdsPassed = false
        │
        ▼
repository가 모든 이전 실행 제거
        │
        ▼
baseline = null, deltaPct = null
        │
        ▼
상대 회귀 판정 미실행
```

실제 비교 항목은 다음처럼 저장됐다.

```json
{
  "key": "k6.overall.p95",
  "current": 117.49,
  "baseline": null,
  "deltaPct": null,
  "verdict": "PASS"
}
```

여기서 PASS는 이전보다 좋아졌다는 뜻이 아니다. 비교 자체가 없고 절대 임계만 넘지 않았다는
뜻이다.

**현재 필터가 잘못된 실행도 막지 못하는 이유**

| 잘못된 실행 | 보통 나타나는 결과 | 현재 기준선 필터 |
|---|---|---|
| large 대신 smoke 사용 | 더 빠름 | 통과할 가능성이 높음 |
| VU 20 대신 2 사용 | 더 빠름 | 통과할 가능성이 높음 |
| 시딩 누락 | 데이터가 적어 더 빠름 | 통과할 가능성이 높음 |
| 스택 일부 장애 | 오류 증가 | 제외됨 |

실제로 기준선 오염을 만든 것은 “실패한 느린 실행”이 아니라 “조건이 다른 빠른 실행”이었다.
normal-day large 200 VU가 small 15 VU를 기준선으로 선택한 T-02가 대표 사례다.

**필요한 조치**

기준선 자격을 세 층으로 나눈다.

1. **비교 가능성:** dataset, VU, duration, scriptVersion, 측정 구간이 같은가
2. **측정 무결성:** 오류율, check rate, 최소 요청 수, 필수 지표 수집이 정상인가
3. **명시적 무효화:** 사람이 잘못된 실행을 제외했다고 기록할 수 있는가

threshold 통과 여부는 기준선 자격이 아니라 기준선의 당시 성능 상태로 표시해야 한다.

### S-11. 실행할 때마다 데이터가 변하지만 같은 데이터셋으로 기록됨 — 상태: 미해결

**쉽게 말하면**

첫 실행과 열 번째 실행은 같은 `large`라는 이름을 쓰지만 DB 안의 글·댓글·반응 수가 다르다.

**현재 동작**

쓰기 저니는 게시글, 댓글, 반응, 스크랩을 계속 추가한다. 실행 전후 setup·teardown이나 자동
재시드가 없다. MySQL 데이터는 실행 사이에 유지된다.

**영향**

데이터가 누적되면서 인덱스 크기, 페이지 깊이, 카운터 값, 캐시 상태가 달라진다. 시간이 지날수록
느려지는 현상을 코드 회귀로 오해할 수 있다.

**필요한 조치**

- 반복 비교용 실행은 DB snapshot 복원 또는 결정적 재시딩 사용
- 데이터셋 버전과 시작·종료 수량을 run metadata에 기록
- 데이터를 의도적으로 누적하는 soak 실험은 별도 시나리오로 분리

### S-12. 알림과 친구 저니가 실행 중간에 할 일을 잃음 — 상태: 미해결

**쉽게 말하면**

처음에는 알림 읽기와 친구 요청을 수행하지만, 상태를 모두 소모한 뒤에는 같은 저니가 실제 작업을
하지 않고 끝난다. 리포트는 이 변화를 알려주지 않는다.

**현재 동작**

- 알림 `readAll`·`readOne`은 읽지 않은 알림을 영구적으로 소진한다.
- friends는 가능한 NONE 관계를 소진하면 요청할 상대가 없어진다.
- 대상이 없을 때 저니가 스킵됐다는 전용 카운터가 없다.
- 친구 응답은 항상 `reqs[0]`을 골라 특정 요청자에 집중된다.

**영향과 조치**

실행 전반과 후반의 트래픽 구성이 달라지고 친구 쓰기·알림 팬아웃 부하는 조용히 사라진다.
상태를 보충하거나 순환시키고, `journey_skipped{reason:...}` 같은 카운터로 실제 실행·스킵 수를
기록해야 한다.

### S-13. WebSocket은 계획한 동시성보다 오래 점유하고 메시지 유실은 기록하지 않음 — 상태: 미해결

**쉽게 말하면**

채팅 저니의 선택 확률은 5%여도 한 번 선택되면 다른 저니보다 오래 VU를 붙잡는다. 그래서 실제
동시 접속 비율은 5%보다 높다. 돌아오지 않은 메시지는 RTT 통계에서도 사라진다.

**현재 동작과 근거**

- 일반 저니 평균: 약 9초
- WebSocket 저니: 15~30초
- 명목 가중치: 5%
- 실측 VU 시간 점유율: 10.6%

RTT는 돌아온 메시지만 기록한다. 브로커가 포화돼 메시지가 유실되면 가장 나쁜 메시지는 RTT
표본에 들어오지 않는다.

**필요한 조치**

- 채팅은 iteration 선택 확률이 아니라 목표 동시 연결 수로 모델링한다.
- 전송 수, 수신 수, timeout 수, 유실 수를 별도 Counter로 기록한다.
- RTT는 성공한 메시지뿐 아니라 timeout과 검열 여부를 함께 표시한다.

## MEDIUM

### S-14. 모든 행동에 같은 think time을 사용하고 일정한 페이싱이 없음 — 상태: 미해결

**쉽게 말하면**

검색, 글 읽기, 글쓰기, 알림 확인이 모두 1~4초 균등 분포로 쉰다. 실제 사용자의 긴 꼬리와
간헐적인 몰림이 사라진다.

**영향**

균등 분포는 요청을 지나치게 고르게 만들어 큐잉과 버스트를 약하게 재현한다. 채팅 타이핑 간격은
별도 하드코딩이라 공통 THINK 값을 바꿔도 WebSocket 강도는 바뀌지 않는다.

**필요한 조치**

행동별 관측 근거나 명시적 가정을 두고 log-normal, exponential 등 긴 꼬리를 가진 분포를
선택한다. 목표 iteration rate가 있다면 저니 종료 후 pacing을 적용한다.

### S-15. 문서가 말하는 쿼리와 실제 요청이 다르고 콜드 읽기 코드가 사용되지 않음 — 상태: 미해결

**쉽게 말하면**

문서에는 랜덤 페이지와 콜드 데이터를 측정한다고 적혀 있지만 실제 시나리오는 최근순과 핫 데이터
위주로만 요청한다.

**현재 동작**

- 보드 선택은 균등 분포다. 실제 자유게시판 집중 같은 차이를 반영하지 않는다.
- `posts.js`는 `sortType=RECENT`만 사용한다.
- 문서가 말하는 `isRandomPage=true` 경로를 호출하지 않는다.
- `randomPost()`는 호출처가 없는 죽은 코드다.

**영향과 조치**

### S-17. cache-warm 실행의 구간 혼합과 다중 태그 파싱 문제 — 상태: **해결** (2026-08-12 + 2026-08-13 후속 수정, 미커밋)

**쉽게 말하면**

캐시를 데우는 구간과 실제 측정 구간이 한 overall 지표에 섞여 있다. 과거에는 다중 태그 이름도
잘못 해석했다.

**해결된 부분**

`{phase:measurement,op:read}`처럼 태그가 여러 개인 서브메트릭을 단일 축으로 잘못 파싱하던
문제를 수정했다. summary와 migrate 경로에 같은 규칙과 테스트를 추가했다.

> **"남은 부분"까지 마저 해결.** `performance/scenarios/cache-warm.js`의 두 executor
> 태그를 `phase:'warmup'` / `phase:'measurement'` → `phase:'warmup'` / `phase:'measure'`로
> 통일하고(다른 모든 시나리오와 같은 phase 어휘를 쓰게), 관련 threshold 키도
> `{op:read,phase:measure}`(`buildSelector()`로 생성)로 옮겼다. `scripts/lib/summary.js`가
> phase 태그를 기준으로 `k6.phases.warmup`/`k6.phases.measure`를 완전히 분리 추출하므로
> — cache-warm은 이미 k6 네이티브 `scenarios.<name>.tags`로 두 executor를 나눠 뒀던 덕에
> checks·iterations를 포함한 모든 메트릭이 원래도 정확히 태깅돼 있었다. 이번 수정으로
> 그 분리가 리포트/게이트까지 실제로 이어지게 된 것이 핵심이다. 다른 일반 시나리오와
> 달리 이 파일만 `setActivePhasePlan()`(동적 phase 계산)을 호출하지 않는다 — 정적
> executor 태그와 동적 계산이 섞이면 충돌할 수 있어서, 이미 충분한 정적 태깅 위에
> 굳이 얹지 않기로 했다(대안 기각 사유).
>
> **왜 cold-start와의 비교가 성립하는지**: `measurementProfile` 조건(T-03)이
> `mode`(`'cache-warm'` vs `'cold-start'`)까지 비교하므로, 서로 다른 측정 설계를 가진
> 두 시나리오는 Node 회귀 게이트의 자동 기준선 비교 대상이 되지 않는다(의도된 동작 —
> 이 둘의 비교는 애초에 사람이 실측값을 나란히 놓고 보는 실험이지, 자동 회귀 판정
> 대상이 아니다).
>
> 검증: `tools/test/phases.test.js`의 `metricsByPhase` 테스트가 이 시나리오와 동일한
> 구조(`{phase:warmup}`/`{phase:measure}`/`{op:read,phase:measure}` 서브메트릭 공존)를
> 픽스처로 검증한다. 실제 `cache-warm.js` 실행으로 확인은 못 했다(k6 미설치 환경).

> **후속 수정 (2026-08-13, 미커밋) — 위 기록의 전제 하나가 틀렸다.**
>
> 위에서 "checks·iterations를 포함한 모든 메트릭이 원래도 정확히 태깅돼 있었다"고 적었는데,
> phase별 TPS는 k6 builtin `iterations`가 아니라 `scenarios/lib/workload.js`의
> `phase_iterations` 커스텀 Counter에서 나온다. 그 Counter는 `currentPhase()`가 null이 아닐
> 때만 증가하는데(`workload.js:290-291`), cache-warm은 정적 executor 태그를 쓰느라
> `setActivePhasePlan()`을 부르지 않아 `currentPhase()`가 항상 null이다. 결과적으로
> `k6.phases.warmup.tps`와 `k6.phases.measure.tps`가 항상 0으로 기록됐다. p95·오류율·
> checks·RPS는 정적 태그 덕에 정상이라 눈에 띄지 않았다.
>
> **무엇을 고쳤나**: `scripts/lib/phases.js`에 `iterationCountFor()`를 추가해 iteration 수
> 소스를 폴백 체인으로 만들었다 — ① `phase_iterations{phase:X}.count`가 0보다 크면 그 값,
> ② 아니면 `iterations{phase:X}.count`, ③ 둘 다 없거나 0이면 `null`. `metricsByPhase()`의
> 버킷 생성 guard에도 `iterations{phase:X}` 축을 넣어, 그 축만 있어도 버킷이 만들어지게 했다.
> `scripts/lib/config.js`의 `PHASE_DIAGNOSTIC_THRESHOLDS`에 `iterations{phase:X}`
> (`count>=0`, 판정에 영향 없음)를 선언해 k6가 그 서브메트릭을 만들도록 했다 — k6는
> threshold가 참조한 태그 조합에만 서브메트릭을 만들기 때문이다.
>
> **고민한 대안과 버린 이유**
> - *cache-warm에서도 `setActivePhasePlan()`을 호출한다*: 정적 executor 태그와 동적 시간
>   계산이 같은 `phase` 키를 두고 겹친다. 두 값이 대개 일치하더라도, iteration이 executor
>   경계를 넘는 순간 요청 태그(동적)와 메트릭 태그(정적)가 갈라진다. 위 원 기록에서 이미
>   기각한 방향이라 그대로 유지했다.
> - *`workload.js`에서 `exec.scenario.name`으로 phase를 추론해 Counter를 증가시킨다*:
>   워크로드 공통 코드가 특정 시나리오의 executor 이름을 알아야 해서, phase 정의가
>   `phases.js` 한 곳이라는 원칙이 깨진다.
> - *0을 그대로 두고 리포트에서만 숨긴다*: 저장되는 `run.json` 자체가 틀린 값을 갖게 된다.
>   `phases.js`가 지키는 "측정 안 된 값을 0으로 채우지 않는다" 원칙과도 어긋난다.
> - 폴백 순서를 builtin 우선으로 두는 안도 기각했다. 동적 태깅 시나리오 10개에서는 엔진이
>   builtin `iterations`에 스크립트의 요청 단위 태그를 싣지 않아 `iterations{phase:X}`가
>   0으로 남는다 — 순서를 뒤집으면 같은 0 문제가 그쪽으로 옮겨간다.
>
> **검증**: `cd performance && node --test tools/test/*.test.js` 전부 통과.
> `tools/test/phases.test.js`에 회귀 테스트 4개를 추가했다(파일 총 30개 통과) — ⑴ cache-warm
> 형태(커스텀 0 + builtin 값 있음)에서 TPS가 builtin으로 계산되는지, ⑵ 커스텀 Counter가
> builtin보다 우선하는지, ⑶ 둘 다 비면 `tps`/`iterations`가 `null`인지, ⑷ builtin 축만 있어도
> 버킷이 생기는지. 기존 `metricsByPhase` 테스트 4개는 수정 없이 통과 — 동적 태깅 시나리오
> 회귀 없음.
>
> **실측 검증 (2026-08-13)**: 이 폴백의 유일한 전제 —— "k6 네이티브
> `scenarios.<name>.tags`(정적 태그)가 builtin `iterations` 메트릭에도 붙는다" —— 를 실제
> k6 v2.1.0 실행으로 확인했다. 서버 없이 되는 최소 스크립트(HTTP 호출 없음, cache-warm과
> 같은 2-executor 구조 + 정적 phase 태그, 커스텀 Counter는 선언만 하고 증가시키지 않음)를
> 돌린 결과:
>
> ```
> iterations{phase:warmup}        count 2,252,354
> iterations{phase:measure}       count 3,540,531
> phase_iterations{phase:warmup}  count 0      ← cache-warm에서 벌어지던 상황 그대로
> phase_iterations{phase:measure} count 0
> → metricsByPhase(): warmup.tps 750,784 / measure.tps 885,132 (둘 다 0이 아님)
> ```
>
> 두 사실이 같이 확인됐다. ⑴ 정적 태그는 builtin `iterations`를 phase별로 정확히 가른다.
> ⑵ threshold로 선언된 `phase_iterations{phase:X}` 서브메트릭은 표본이 없어도 count 0으로
> 요약에 존재한다 — 즉 폴백 이전 코드에서 이 phase 버킷의 tps가 "없음"이 아니라 **0**으로
> 확정되던 것이 맞다(추론이 아니라 실측). iteration 수가 큰 것은 본문이 빈 함수라 초당

> 직접 부르면 정상 실행된다.
>

>   { phase:warmup }               24     ← executor 정적 태그가 builtin에 그대로 붙는다
>   { phase:measure }               2

### S-18. breakpoint가 서버 한계보다 k6의 VU 한계에 먼저 걸릴 수 있음 — 상태: 미해결

**쉽게 말하면**

서버가 더 처리할 수 있어도 k6가 필요한 VU를 만들지 못해 요청률을 올리지 못할 수 있다. 이때
그래프의 평평한 구간을 서버 최대 TPS로 오해하게 된다.

목표 300 iteration/s, 평균 iteration 약 9초라면 Little's law로 약 2,700 VU가 필요하다.
현재 `maxVUs=2000`이므로 130~200 iteration/s 부근부터 클라이언트 사유의
`dropped_iterations`가 생길 수 있다.

**필요한 조치**

예상 iteration 시간을 사용해 필요한 preAllocatedVUs와 maxVUs를 계산하고,
`dropped_iterations > 0`이면 서버 최대 처리량 판정을 중단한다.

### S-19. 저니 선택이 매번 달라지지만 실제 비율을 확인할 수 없음 — 상태: 미해결

**쉽게 말하면**

두 실행이 같은 40/15/10 가중치를 사용해도 실제 선택 횟수는 다르다. 그런데 무엇이 몇 번
선택됐는지 기록하지 않아 성능 차이가 코드 때문인지 트래픽 믹스 때문인지 알 수 없다.

**현재 동작**

- 모든 분기가 seed 없는 `Math.random()` 사용
- 저니별 Counter 없음
- Trend 서브메트릭에는 선택 횟수가 명확히 남지 않음
- TPS와 RPS는 ±10%로 게이트

500~2,500 iteration에서 12개 저니를 뽑으면 샘플링 차이만으로도 저빈도 저니의 비율이 크게
달라질 수 있다.

**필요한 조치**

저니별 선택·완료·스킵 Counter를 저장한다. 필요하면 재현 가능한 seed를 도입하고, 리포트에
“선언 가중치와 실제 실행 비율”을 나란히 표시한다.

### S-22. boards standalone만 인증 없이 실행됨 — 상태: 미해결

**쉽게 말하면**

같은 게시판 API를 한 테스트에서는 비로그인으로, 다른 테스트에서는 로그인 쿠키를 붙여 호출한다.
두 결과를 같은 엔드포인트 성능처럼 비교할 수 없다.

인증 필터, 세션 조회, 사용자별 응답이 비용에 영향을 줄 수 있다. standalone과 복합 시나리오의
인증 조건을 맞추거나 결과 이름에 인증 여부를 분명히 표시한다.

### S-23. 인증 재시도가 실패 수와 지연을 여러 번 부풀림 — 상태: 미해결

**쉽게 말하면**

요청 하나가 401을 받고 토큰을 갱신한 뒤 성공하면 사용자 관점에서는 복구된 요청 한 번이다.
현재 지표에는 401, refresh, 재시도가 각각 별도 요청으로 들어가 실패와 지연을 섞는다.

**현재 흐름**

```text
원 요청 401
   → refresh 요청
   → 원 요청 재시도
```

세 요청이 `http_req_failed`와 작업별 지연에 각각 반영된다. `auth_token_refreshes`는 존재하지만
복구 성공·복구 실패를 구분하거나 threshold로 사용하지 않는다.

**필요한 조치**

- 원 요청, refresh, 재시도를 서로 다른 태그로 분리
- 사용자 작업 기준의 최종 성공 여부 Counter 추가
- 복구 성공률과 refresh 지연을 별도 SLO로 정의
- 전체 HTTP 오류율과 사용자 작업 실패율을 나란히 표시

### S-24. cache-warm의 워밍업 VU가 리터럴이라 VUS를 낮추면 부하가 뒤집힘 — 상태: **해결** (2026-08-13, 미커밋)

> **발견 경위**: S-17 후속 수정을 실측 검증하려고 `-e VUS=5`로 cache-warm을 돌렸는데,
> measure 구간이 p95 32초·오류율 25%로 나왔다. 원인을 보니 워밍업 executor의 VU 수가
> `vus: 50` 리터럴이라 `VUS`를 낮춰도 그대로 50이었다. 저장된 레코드의 `run.loadProfile`이
> `warmup.vus = 50` / `measurement.stages.target = 5`로 그 역전을 그대로 보여준다.
>
> **왜 문제인가**: 단순히 무거운 게 아니라 시나리오의 전제가 깨진다. cache-warm은 캐시가
> 데워진 **정상 상태**를 재는 cold-start의 대조군인데, 워밍업이 앱을 포화시키면 measure
> 구간이 큐 적체·GC·커넥션 풀 고갈의 잔여 효과 위에서 시작한다. 또 짝인 cold-start는
> `VUS` 하나로 전체가 스케일되므로, `VUS`를 낮춘 순간 1:1 비교의 대칭성도 사라진다.
>
> **무엇을 고쳤나**: `scenarios/cache-warm.js`에 `WARMUP_VUS`를 도입해
> `Number(__ENV.WARMUP_VUS || Math.max(1, Math.round(VUS / 2)))`로 계산하고 warmup
> executor가 그 값을 쓰게 했다. 헤더의 "사용자" 줄도 고정 수치 대신 VUS 기준 표현으로 바꿨다.
>
> **고민한 대안과 버린 이유**
> - *워밍업도 VUS와 동일하게 맞춘다*: 기본 실행의 워밍업 부하가 50 → 100으로 바뀐다.
>   `run.loadProfile`은 k6가 해석한 최종 설정을 그대로 지문으로 쓰므로(`summary.js`의
>   `loadProfile()`), 과거 cache-warm 실행 전부와 blocking 불일치가 되어 기준선 비교가
>   끊긴다. 부하 설계를 바꿀 근거가 없는데 이력을 버리는 선택이라 기각.
> - *리터럴을 그대로 두고 "VUS를 낮추지 말 것"이라고 문서에만 적는다*: 사람이 매번
>   기억해야 하는 절차는 지켜지지 않는다는 게 이 저장소의 기본 입장이다(`perf-run.js`
>   래퍼가 존재하는 이유와 같다). 기각.
> - 비율을 1/2로 고른 이유는 기본값 보존이다 — VUS=100이면 계산 결과가 정확히 50이라
>   기존 동작·지문이 그대로 유지된다. 워밍업 강도만 따로 실험하려면 `WARMUP_VUS`로 덮는다.
>
> **검증**: `k6 inspect`로 해석된 옵션을 직접 확인했다(부하 실행 없이 init 컨텍스트만 평가).
>
> ```
> 기본값             warmup.vus = 50 | measure target = 100,100   ← 기존과 동일
> -e VUS=4           warmup.vus =  2 | measure target = 4,4       ← 비례
> -e VUS=4 -e WARMUP_VUS=1  warmup.vus = 1 | measure target = 4,4 ← 오버라이드
> ```
>
> **남은 작업**: 다른 시나리오에는 같은 문제가 없음을 확인했다(chaos·failover는
> `__ENV.VUS`, spike는 `SPIKE_VUS`, breakpoint는 `MAX_VUS`를 탄다). `MEASURE_RAMP_SEC=30`은
> 리터럴로 남겨 뒀다 — 시간 값이고 `measureSec`에 합산돼 phasePlan에 그대로 기록되므로
> VU 수와 달리 부하 강도를 왜곡하지 않는다.
