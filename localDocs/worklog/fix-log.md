## B-6. 테스트 · CI · 배포

### KI-12 — CI에 테스트 게이트가 없음

| | |
|---|---|
| **무엇이 문제였나** | 테스트가 깨진 채로 코드를 올려도 아무도 막지 않아 그대로 서버까지 배포됐다. |
| **어떻게 고쳤나** | 배포 워크플로 맨 앞에 테스트 잡을 넣고 "이게 통과해야만 이미지 빌드"로 묶었다. 병합 전에도 돌도록 PR용 워크플로를 따로 하나 더 뒀다. |
| **왜 그 방법인가** | 배포 워크플로는 `main` 푸시에만 돌아서, 거기서 처음 테스트하면 **이미 병합된 뒤**라 게이트가 아니다. 그래서 PR 단계용 `ci.yml`을 분리했다. Dockerfile의 `-x test`는 일부러 그대로 뒀다 — 게이트가 이미 통과한 뒤에만 이미지 빌드가 시작되므로 같은 검증을 두 번 할 이유가 없고 빌드 시간만 늘어난다. |
| **어떻게 검증했나** | `CiTestGateTest` — 워크플로 YAML을 실제로 파싱해 테스트 잡 존재·`needs` 연결·PR 트리거를 단언한다. 게이트를 지우면 이 테스트가 깨진다. |
| **바뀐 파일** | `.github/workflows/deploy.yml`, `.github/workflows/ci.yml`(신규), `Dockerfile`(주석), `src/test/java/.../ci/CiTestGateTest.java`(신규) |
| **면접용 한 줄** | "테스트가 CI에서 아예 안 돌고 있어서, 병합 전 게이트와 배포 전 게이트를 나눠서 넣었습니다." |
| **설명 난이도** | 낮음 |

### KI-05 — 소유권 검증 없음 (IDOR)

| | |
|---|---|
| **무엇이 문제였나** | 로그인한 사람이면 **누구나 남의 글과 댓글을 수정하거나 지울 수 있었다.** |
| **어떻게 고쳤나** | 글·댓글 수정/삭제 진입부에서 요청자가 작성자인지 확인하고, 아니면 403으로 막는다. |
| **왜 그 방법인가** | 컨트롤러가 아니라 **서비스 계층**에 넣었다. 같은 프로젝트의 `NotificationService`·`ChatService`가 이미 서비스에서 검증하고 있어 자리를 맞춘 것이고, 수정·삭제가 컨트롤러 외의 경로에서 불려도 같은 구멍이 다시 열리지 않는다. 댓글은 **글쓴이에게도 삭제 권한을 주지 않았다** — 신고·모더레이션 기능이 없는 상태에서 그 권한을 열면 "글쓴이가 불리한 댓글을 지운다"는 다른 문제가 생긴다. |
| **어떻게 검증했나** | `PostServiceTest.Ownership`·`CommentServiceTest.Ownership` 각 3건. 예외가 나는 것뿐 아니라 **본문·삭제 표시·캐시·댓글 수가 하나도 바뀌지 않았는지**까지 본다(던지고 나서 이미 바꿔 놓는 경우를 걸러내려고). |
| **바뀐 파일** | `services/domain/PostService.java`, `services/domain/CommentService.java`, 각 테스트 |
| **면접용 한 줄** | "소유권 검증을 서비스 계층에 넣었습니다. 알림·채팅 서비스에는 이미 있었고 게시글·댓글에만 빠져 있어서 일관성을 맞춘 겁니다." |
| **설명 난이도** | 낮음 |

### KI-04 — GET 전체가 공개인 블랙리스트 인가

| | |
|---|---|
| **무엇이 문제였나** | 조회 API를 새로 만들면 **아무 설정도 안 했는데 자동으로 전체 공개**가 됐다. 실수 하나가 그대로 정보 노출이 된다. |
| **어떻게 고쳤나** | "명시한 것만 공개, 나머지는 전부 인증"으로 뒤집었다. 공개 조회 경로 9개만 목록에 남겼다. |
| **왜 그 방법인가** | **기본값이 '차단'이어야 실수가 사고로 번지지 않는다.** 전환할 때 기존 엔드포인트의 공개 여부는 하나도 바꾸지 않았다 — 전후 인가 매트릭스가 동일하다. 함께 명시한 것 중 중요한 것은 `/actuator/**`다. 운영 서버는 관리 포트가 따로라 상관없지만 **성능 측정 프로파일은 같은 포트를 쓰기 때문에**, 이걸 빼면 Prometheus 수집이 401로 죽어 측정 파이프라인이 멈춘다. 예전에는 `GET /**` 공개가 그걸 가려 주고 있었다. |
| **어떻게 검증했나** | `AuthorizationMatrixTest`. 특히 **아직 만들지 않은 경로를 비로그인으로 호출**하는 테스트가 핵심이다 — 화이트리스트면 401, 블랙리스트로 되돌아가면 404가 되므로 구조가 되돌아가는 순간 깨진다. 성능 스크립트가 호출하는 경로 39개도 전부 대조했다. |
| **바뀐 파일** | `security/SecurityConfig.java`, `security/AuthorizationMatrixTest.java` |
| **면접용 한 줄** | "인가를 화이트리스트로 뒤집었습니다. 기본값이 '차단'이어야 새 엔드포인트를 추가할 때 실수가 사고로 안 번집니다." |
| **설명 난이도** | 낮음 |

### KI-18 — 리프레시 토큰이 로그에 평문으로 남음

| | |
|---|---|
| **무엇이 문제였나** | Redis에 장애가 나면 로그에 **아직 유효한 로그인 토큰이 그대로 찍혔다.** 로그를 볼 수 있는 사람은 그 계정으로 로그인할 수 있다. 게다가 코드 버그(NPE 등)까지 "Redis 장애"로 위장돼 조용히 삼켜졌다. |
| **어떻게 고쳤나** | 장애 로그에서 메서드 인자를 아예 빼고, 삼키는 예외 범위를 진짜 DB/Redis 접근 예외로 좁혔다. |
| **왜 그 방법인가** | **마스킹 규칙을 두는 대신 인자 자체를 뺐다.** 어떤 인자가 민감한지는 호출 지점마다 다르고, 규칙을 두면 새 메서드가 추가될 때마다 규칙을 갱신해야 해서 같은 사고가 다시 난다. 원인 파악에는 메서드 이름과 예외 종류로 충분하다. 예외 범위를 좁힌 쪽은, 그래야 **진짜 인프라 장애와 코드 버그가 갈린다** — 버그는 이제 삼켜지지 않고 500으로 드러난다. |
| **어떻게 검증했나** | `ResilientRedisAspectTest.FailureHandling` — 실제 로그 출력을 붙잡아 토큰 문자열이 없고 메서드 이름은 있는지, 그리고 NPE가 "Redis unavailable"로 위장되지 않고 그대로 올라오는지 확인한다. |
| **바뀐 파일** | `aop/ResilientRedisAspect.java`, `aop/ResilientRedisAspectTest.java` |
| **면접용 한 줄** | "장애 로그에 리프레시 토큰이 평문으로 남고 있어서 인자 로깅을 없애고, catch 범위를 좁혀 코드 버그가 인프라 장애로 위장되지 않게 했습니다." |
| **설명 난이도** | 낮음 |

### KI-56 — 게시판 글 개수가 만료 후 `1`로 되살아남

| | |
|---|---|
| **무엇이 문제였나** | 글이 5만 개인 게시판인데 **전체 개수가 갑자기 `1`이 됐다.** 그러면 페이지 목록이 1페이지로 접혀서 나머지 글을 아예 볼 수 없다. 게다가 한 번 그렇게 되면 최대 한 시간 동안 그대로였다. |
| **어떻게 고쳤나** | 개수를 올리거나 내릴 때 **캐시에 값이 없었다면** 그 증감 결과를 믿지 않고 DB에서 다시 세도록 했다. 그리고 캐시 수명이 생성 경로와 증감 경로에서 서로 달랐던 것을 하나로 통일했다. |
| **왜 그 방법인가** | 원인이 두 개 겹쳐 있다. ① Redis의 증가 연산은 **값이 없으면 0에서 시작**한다. 그래서 캐시가 만료된 뒤 글이 하나 써지면 총 개수가 `1`이 된다. ② 그 뒤로는 조회가 전부 캐시에 걸려서 다시 세지 않는다. 판정은 **증가 연산의 반환값이 증가분과 같은지**로 한다 — "값이 있는지 먼저 확인하고 증가"는 확인과 증가 사이에 만료될 수 있어 오히려 새 틈이 생긴다. 대가는 개수가 실제로 1이 되는 드문 경우에 DB를 한 번 더 세는 것뿐이고 결과는 같다. Lua 스크립트로 완전 원자화하는 안은 버렸다 — 얻는 게 그 낭비 한 번뿐인데 스크립트가 테스트·리뷰 대상 밖으로 나간다. |
| **어떻게 검증했나** | `RedisPostsCacheTest.CountDelta` 4건. 마지막 하나는 **생성 경로와 증감 경로의 수명이 실제로 같은 값인지**를 직접 비교한다 — 이게 없으면 수명이 다시 어긋나도 아무도 모른다. |
| **바뀐 파일** | `services/domain/redisService/RedisPostsCache.java`, 테스트 |
| **면접용 한 줄** | "캐시 TTL을 통일하고, 키가 없을 때는 증감 대신 DB 재집계를 하게 고쳤습니다. Redis INCRBY가 키 없으면 0부터 시작해서 총 개수가 1로 되살아나고 있었습니다." |
| **설명 난이도** | **높음** — Redis 증가 연산의 "키 없으면 0" 동작과 서로 다른 두 TTL이 **시간 순서로 맞물려** 생기는 문제라, 시나리오를 순서대로 따라가지 않으면 왜 `1`이 되는지 보이지 않는다. `docs/KNOWN-ISSUES.md` KI-56 원문에 분 단위 타임라인이 있으니 그것과 함께 읽을 것. |

## B-4. 트랜잭션 · 스케줄러

### KI-23 — 스케줄러 자기호출 + 조회수 드레인 유실

| | |
|---|---|
| **무엇이 문제였나** | 조회수를 DB에 반영하는 1분짜리 배치에서, **게시글 하나가 실패하면 그 주기 전체가 통째로 되돌아갔다.** 게다가 Redis의 조회수를 **먼저 지우고** DB에 쓰는 순서라, 반영이 실패하면 그 조회수는 복구할 방법 없이 사라졌다. |
| **어떻게 고쳤나** | 두 가지를 고쳤다. ① 게시글 하나를 반영하는 부분을 다른 클래스로 옮겨 진짜로 게시글당 트랜잭션 하나가 되게 했다. ② 순서를 **읽기 → DB 반영 → 반영한 만큼만 차감**으로 뒤집었다. |
| **왜 그 방법인가** | ① 스프링에서 같은 클래스 안의 메서드를 직접 부르면 트랜잭션 설정이 **무시된다.** 프록시 우회 트릭(자기 주입 등)도 있지만, 그건 "왜 이렇게 썼는지" 아는 사람만 유지할 수 있고 다음 사람이 원래대로 되돌리면 조용히 결함이 부활한다. 조회수를 더하는 건 원래 게시글 서비스의 일이라, 제자리로 옮기는 게 맞다. ② 삭제가 아니라 **차감**인 이유: 읽은 뒤 반영까지 사이에 들어온 새 조회수가 이미 카운터에 더해져 있어서, 키를 통째로 지우면 그것까지 사라진다. 반영한 값만 빼면 그 사이 증가분이 다음 주기로 넘어간다. |
| **어떻게 검증했나** | `ViewCountSchedulerTest.DrainOrder` 4건 — DB 반영이 차감보다 먼저인지(호출 순서 검증), 실패한 게시글이 차감 목록에서 빠지는지, 하나가 실패해도 나머지가 진행되는지, 삭제된 게시글은 정리되는지. |
| **바뀐 파일** | `schedulers/ViewCountScheduler.java`, `services/domain/PostService.java`, `domain/port/ViewCountStorePort.java`, `infrastructure/redis/RedisViewCountStore.java`, `services/domain/redisService/ViewCountService.java`, 테스트 2개 |
| **면접용 한 줄** | "자기호출이라 무효였던 트랜잭션 경계를 별도 빈으로 분리하고, Redis 카운터 삭제를 DB 반영 이후로 옮겼습니다." |
| **설명 난이도** | **높음** — 배경 지식 두 개가 동시에 필요하다. ① 스프링 AOP는 프록시로 동작해서 **같은 객체 안의 메서드 호출은 프록시를 안 거치고**, 그래서 `@Transactional`이 무시된다. ② Redis의 "읽으면서 지우기"는 그 자체로는 원자적이지만, **지운 뒤 DB 반영에 실패하면 되돌릴 수 없다**는 게 별개 문제다. 이 둘이 한 항목에 묶여 있어 여섯 줄로 압축되지 않는다. 면접에서 나온다면 ①만 떼어 설명하는 편이 안전하다. |

### KI-06 — 쿠키 인증 + CSRF 비활성

| | |
|---|---|
| **무엇이 문제였나** | 로그인 상태가 쿠키에 있고 그 쿠키가 다른 사이트에서 온 요청에도 딸려 간다. 그래서 **공격자 페이지가 사용자의 브라우저를 시켜 글 삭제 같은 쓰기 요청을 대신 보낼 수 있었다.** 사용자는 그 페이지를 열기만 하면 된다. |
| **어떻게 고쳤나** | 쓰기 요청(POST/PUT/PATCH/DELETE)에 대해 **요청이 어느 사이트에서 왔는지**(`Origin` 헤더)를 확인하고, 우리가 아는 사이트가 아니면 403으로 끊는 필터를 넣었다. |
| **왜 그 방법인가** | 표준적인 방법은 CSRF 토큰이지만, 그건 **프론트엔드가 토큰을 되돌려 보내도록 함께 고쳐야 한다.** 프론트는 별도 저장소라 백엔드만 바꾸면 모든 쓰기가 깨진다. Origin 검증은 프론트 변경 없이 지금 넣을 수 있고, 나중에 토큰 방식을 얹어도 충돌하지 않는다. **한계는 분명히 알고 써야 한다**: `Origin`도 `Referer`도 없는 요청은 통과시킨다 — 서버 간 호출이나 부하 스크립트는 이 헤더를 안 보내고, 막으면 정상 이용과 성능 측정이 죽는다. CSRF는 브라우저를 통해서만 성립하고 브라우저는 이 헤더를 생략하지 않으므로 방어에 구멍이 나지는 않지만, 토큰 방식보다 약한 방어인 건 맞다. |
| **어떻게 검증했나** | `CsrfOriginValidationFilterTest` — 판정 로직 9건은 **필터를 직접 호출해** 확인한다. MockMvc로 실제 요청을 보내면 스프링의 CORS 필터가 먼저 낯선 Origin을 403으로 끊어 버려서, 이 필터를 지워도 테스트가 통과해 회귀를 못 잡기 때문이다. 여기에 더해 **필터가 실제 보안 체인에 등록돼 있는지**를 별도로 단언한다. |
| **바뀐 파일** | `security/CsrfOriginValidationFilter.java`(신규), `security/SecurityConfig.java`, `security/CsrfOriginValidationFilterTest.java`(신규) |
| **면접용 한 줄** | "쿠키 인증에 SameSite=None인데 CSRF 방어가 없어서, 최소 방어로 쓰기 요청의 Origin 검증을 넣었습니다. 토큰 방식은 프론트를 함께 고쳐야 해서 다음 단계로 뒀습니다." |
| **설명 난이도** | 낮음 |

| **무엇이 문제였나** | 탈퇴하면 사용자 행을 DB에서 **완전히 지웠다.** 그 사람이 쓴 글이나 댓글이 남아 있으면 삭제가 실패해서 **탈퇴 자체가 안 됐다.** 성공하더라도 프로젝트의 다른 데이터와 규칙이 달랐다. |

| **왜 그 방법인가** | 지움 표시만 하고 이메일을 그대로 두면 **같은 이메일로 다시 가입할 수 없다** — 이메일에 중복 방지 제약이 걸려 있기 때문이다. 표식값으로 비켜 주면 스키마를 건드리지 않고 재가입이 가능해진다. 대가는 탈퇴 회원의 원래 이메일을 복구할 수 없다는 것이고, 그건 의도된 선택이다(탈퇴한 계정의 연락처를 계속 들고 있을 이유가 없다). 표식 도메인 `.invalid`는 표준이 "절대 실재하지 않는다"고 못박은 예약어라 실수로 메일이 나갈 수 없다. FK 위반을 잡던 예외 처리는 **제거했다** — DELETE를 안 하므로 발생할 수 없고, 일어날 수 없는 경우의 처리를 남겨 두면 읽는 사람을 오도한다. |
| **어떻게 검증했나** | `UserServiceTest.DeleteAccount` — 행이 지워지지 않고 지움 표시만 되는지, 이메일이 비켜서 재가입이 가능해지는지 확인한다. 물리 삭제를 전제하던 기존 테스트 3건은 그 예외가 더는 발생할 수 없어 함께 제거했다. |
| **바뀐 파일** | `domain/users/User.java`, `domain/users/UserRepository.java`, `services/domain/UserService.java`, `services/domain/UserServiceTest.java` |
| **면접용 한 줄** | "탈퇴를 soft delete로 바꾸면서 이메일을 표식값으로 비켜 뒀습니다. 안 그러면 유니크 제약 때문에 같은 이메일로 재가입이 막힙니다." |

## D. 측정 시스템 위생 — 확인 결과

**둘 다 "의도된 설계"가 아니라 실제 구멍이다.** 다만 **고치면 워크로드나 데이터셋이 바뀌어
지금까지 잰 Before 기준선이 무효가 된다.** 그 기준선은 C등급(이력서 서사)이라 판단을 넘긴다.
그래서 **코드는 손대지 않았고, 아래는 확인 결과만이다.**

### D-1 — 워크로드가 액션 9개를 한 번도 호출하지 않는다

`scenarios/lib/workload.js`의 여정 정의와 `scripts/*.js`의 export 목록을 대조했다.
아래 9개는 **스크립트에 함수로 존재하지만 어떤 여정도 부르지 않는다.** 그래서 호출 수가 0이다.

| 스크립트 | 미사용 함수 | 대응 액션 |
|---|---|---|
| `chat-rest.js` | `readStatus` | chat_read_status |
| `mypage.js` | `myComments` | my_comments |
| `scraps.js` | `myScraps` | scrap_list |
| `school.js` | `searchSchools` | school_search |
| `friends.js` | `searchFriend`, `requestFriend`, `respondFriend` | friend_search / friend_request / friend_respond |
| `timetable.js` | `listTemplates`, `listSubjects` | template_list / subject_list |

**판정: 커버리지 구멍이다.** 여정에서 의도적으로 뺐다는 흔적(주석·가중치 0)이 없고,
함수는 다 구현돼 있는데 `workload.js`의 import 목록에서만 빠져 있다.

**고칠 때의 대가**: 여정에 액션을 추가하면 여정당 요청 수가 늘어난다.
`workload.js` 주석이 스스로 밝히듯 이 프로젝트는 **여정당 요청 수를 유지하는 것을 규칙으로 삼고 있다**
("분기 확률을 재분배해 여정당 쓰기 1회를 유지한다… 그냥 덧붙이면 TPS·RPS 기준선이 통째로 어긋난다").
즉 **추가하면 기존 Before 기준선과 비교가 불가능해진다.**

**결정 필요**: (a) 지금은 그대로 두고 "이 9개는 측정 범위 밖"이라고 문서에 명시,
(b) P0-1 개선 측정이 끝난 뒤 별도 시나리오로 추가, (c) 지금 넣고 기준선을 다시 잰다.
**권장은 (a) 또는 (b).**

### D-2 — 데이터셋의 댓글 반응이 0건

`datasets/seed.js`가 만드는 반응은 **게시글 반응뿐이다**(`POST /api/posts/{id}/reaction`).
댓글 반응 API(`POST /api/comments/{id}/reaction`)는 시드 과정에서 한 번도 호출되지 않는다.
따라서 `comments_reactions`가 0건인 것은 데이터 유실이 아니라 **생성기가 애초에 안 만든다**는 뜻이다.

**원 기록보다 영향 범위가 좁다는 점을 정정한다.**
원문은 "P0-1 결과 해석에 영향"이라고 적었지만, 코드를 확인하니 그렇지 않다.

- 댓글 **목록** 조회(P0-1의 N+1 대상)는 이 테이블을 **읽지 않는다.**
- 이 테이블을 읽는 곳은 `CommentReactionService`의 `findByCommentAndUser` 하나뿐이고,
  그건 **반응 토글(쓰기) 경로**다.

따라서 낙관적으로 측정되는 것은 **댓글 반응 API**이지 댓글 목록 개선 효과가 아니다.
구체적으로 두 가지가 왜곡된다.

1. 조회가 항상 "없음"이라 인덱스 탐색이 사실상 공짜다.
2. 항상 **신규 생성** 경로만 타고 **취소(토글 해제)** 경로는 한 번도 안 탄다 — 분기 커버리지가 반쪽이다.

부하 실행 중에는 `journeyEngage`가 댓글 반응을 만들긴 하지만, **0에서 시작**하므로 실행 초반은 여전히 빈 테이블이다.

**결정 필요**: (a) 한계로 문서에 명시하고 그대로 진행, (b) 시드에 댓글 반응 생성을 추가하고 데이터셋 재생성.
(b)는 데이터셋을 다시 만들어야 하므로 **Before 기준선이 무효가 된다.**
**권장은 (a)** — 왜곡되는 대상이 이력서 서사(댓글 목록 N+1)가 아니기 때문이다.
