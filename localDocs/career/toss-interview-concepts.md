# PART 1. 성능·부하 테스트 (최대 무기 — 가장 깊게)

## 1.1 백분위수 (p50 / p95 / p99)
응답 시간을 정렬했을 때 하위 95%가 이 값 이하라는 뜻. 평균은 소수의 극단값에 희석되어 꼬리를 숨긴다. 사용자 100명 중 5명이 매번 느린 경험을 하는 것이 p95이고, 서비스 인상은 꼬리가 결정한다. 꼬리 지연의 전형적 원인: GC pause, 커넥션 풀 대기, CPU throttling, 락 대기 — 전부 "포화"의 신호라서 p99는 용량 문제의 조기 경보다.
- **프로젝트**: 회귀 규칙이 p95(+10% warn/+20% fail, 절대 500ms)와 p99(+15%/+30%, 절대 1200ms)를 게이트로 사용. avg 80ms인 API의 p99가 1.9초였던 실측 보유.
- 파고들기: "왜 p99.9는 안 보나?" — 표본 수가 적으면 p99.9는 노이즈. 우리 실행 규모(수천 요청)에선 p99까지가 통계적으로 의미 있음.

## 1.2 검열(censoring) — 타임아웃에 잘린 측정값
클라이언트 타임아웃이 60초면 실제 90초 걸릴 요청도 60초로 기록된다. p95=60000ms는 "측정값"이 아니라 "측정 상한"이며, 이후 시스템이 얼마나 더 나빠져도 지표가 움직이지 않아 회귀 비교가 무력화된다.
- **프로젝트**: 대규모 실행의 p95가 정확히 60001ms — 검열값임을 인지하고 발견 장부에 "타임아웃 검열 미감지"를 결함으로 기록.

## 1.3 RPS vs TPS, 스루풋과 레이턴시의 관계
RPS는 HTTP 요청 수, TPS는 우리 정의로 "사용자 여정(iteration) 완료 수". 요청 수는 같아도 여정이 중간에 실패하면 TPS가 떨어진다. 스루풋과 레이턴시는 포화 전까지 독립, 포화점을 넘으면 큐잉 때문에 레이턴시가 급등하며 스루풋은 정체(hockey stick 곡선).
- **프로젝트**: 회귀 규칙에서 둘 다 higher-is-better 방향으로 게이트(-10% warn/-20% fail).

## 1.4 Closed model vs Open model, 좌표 누락(Coordinated Omission)
Closed(VU 고정): 가상 유저가 응답을 기다렸다가 다음 요청 → 시스템이 느려지면 부하가 저절로 줄어 **시스템을 봐준다**. 이것이 좌표 누락 — 최악의 순간에 측정을 빼먹는 편향. Open(arrival rate): 응답과 무관하게 초당 n건 도착 → 실제 트래픽처럼 밀어붙여 한계를 드러낸다.
- **프로젝트**: 시나리오 16개 중 breakpoint만 ramping-arrival-rate(open). stress/spike가 closed인 것을 자체 결함(S-06)으로 기록 — "무너질수록 TPS가 정상으로 보였다"는 실측 사례 포함. 시니어 상대로 이 용어가 나오면 강한 인상.

## 1.5 Little's Law
L = λ × W (동시 사용자 수 = 도착률 × 체류 시간). 목표 처리량과 응답 시간에서 필요한 동시성(VU 수)을 역산할 수 있다.
- **프로젝트**: breakpoint 시나리오가 300 iter/s 목표에 maxVUs 2000으로 설정돼 있는데, Little's law로 계산하면 ~2700 VU가 필요해 상한이 부족하다는 것을 자체 발견(S-18).

## 1.6 부하 테스트 유형
- **load(normal/peak)**: 예상 트래픽에서 SLO 충족 확인 — normal-day 200VU, peak-hour 500VU
- **stress**: 계단식 증가로 한계와 붕괴 양상 확인 — 100→1000VU
- **spike**: 급증 순간의 거동과 회복 — 10초 만에 600VU
- **soak(endurance)**: 장시간 유지로 누수·드리프트 검출 — 150VU 2시간
- **breakpoint**: 도착률을 올려 무너지는 지점 탐색 — open model
- **프로젝트 추가 개념**: 워크로드를 "엔드포인트 나열"이 아니라 **사용자 여정 12종 × 가중치 프로파일**(브라우징 40%, 반응 15%, 글쓰기 5%…)로 모델링. 시험기간/등록일 같은 도메인 시나리오까지.

## 1.7 Zipf 분포 (트래픽 쏠림)
현실 접근은 균등하지 않다 — 소수 인기글이 대부분의 조회를 흡수(멱법칙). 부하 테스트가 균등 분포로 접근하면 캐시 적중률이 비현실적으로 낮고 핫로우 경합이 재현되지 않는다.
- **프로젝트**: 글 선택에 Zipf 샘플러 사용. 자체 결함 발견까지: 수식 버그로 최고 인기글(index 0)이 한 번도 선택되지 않았고, 특정 글 하나가 접근의 19~27%를 흡수하는 과도한 쏠림 — "분포를 썼다"가 아니라 "분포를 검증했다"까지 말할 수 있음.

## 1.8 SLI / SLO, 기준선(baseline)과 회귀(regression)
SLI는 측정 지표(p95, 오류율), SLO는 그 목표치(읽기 p95<300ms, 오류율<1%). 회귀 판정은 "직전 정상 상태 대비 악화"인데, 비교가 성립하려면 **같은 시나리오·같은 환경·같은 스크립트·같은 데이터 규모**여야 한다.
- **프로젝트**: 기준선을 수동 지정이 아니라 "같은 시나리오+환경의 직전 성공 실행"으로 자동 선택. 오탐 방지 5중 장치: ① 방향성(TPS 상승은 회귀 아님) ② 노이즈 플로어(2ms→3ms는 +50%여도 무시) ③ 기준선 하한(0에 가까운 분모 차단) ④ **절대 게이트**(매번 9%씩 나빠지며 영원히 통과하는 '삶은 개구리' 방지) ⑤ 스크립트 해시 지문(불일치 시 FAIL→WARN 강등, 비교 가능성 자체를 검증).

## 1.9 워밍업과 콜드 스타트
JIT 컴파일, 커넥션 풀 채움, 캐시 적재 전의 측정은 정상 상태가 아니다. 램프업 구간을 측정 윈도우에서 제외해야 한다.
- **프로젝트**: 인프라 지표는 warmup만큼 윈도우를 잘라내는데 k6 지표는 트림하지 않는 불일치를 자체 결함(T-03)으로 기록. cold-start vs cache-warm 시나리오 별도 보유.

## 1.10 측정 신뢰성 — "결과를 언제 믿으면 안 되는가"
면접에서 가장 급이 갈리는 주제. 체크리스트: ① 검증이 실제로 실패를 잡는가(check 100% + 오류율 55% 사건 — 400 응답의 응답시간을 재고 있었다) ② 부하 발생기가 SUT와 자원을 공유하는가(우리 실행 전부 같은 호스트 — 알려진 한계) ③ 측정 도구 자체에 버그는 없는가(32개 규칙 중 25개가 키 조회 버그로 한 번도 발동 안 함 → 발견 후 수정, 판정 로직에 단위테스트 28개 도입) ④ 한 번에 변수 하나(스크립트·빌드·스키마가 같은 날 바뀌어 61개 실행을 기준선에서 제외).

## 1.11 USE / RED 프레임워크
- USE(자원 관점): Utilization, Saturation, Errors — CPU/메모리/풀/디스크마다.
- RED(서비스 관점): Rate, Errors, Duration.
- **프로젝트**: 리포트가 정확히 이 구조 — k6가 RED(RPS/오류율/분위수), Prometheus가 USE(CPU throttling, heap%, 풀 포화도, Tomcat 워커 포화도).

## 1.12 병목 진단의 순서
증상(p99 급등) → 포화 지표 매칭 → 가설 → 대조 실험. 대표 시그니처:
- 풀 고갈: 획득 대기 p95가 타임아웃값에 수렴 + pending > 0 (실측: pending 205, acquire p95 = 30초 = 타임아웃)
- N+1: DB QPS / 앱 RPS 비율 폭주 (실측: 903 쿼리/요청)
- CPU throttling: 컨테이너 환경 p99 급등의 최대 원인 (실측: throttled ~100%)
- GC: pause max와 오버헤드%(전체 시간 중 GC 비율, 5% 경고)
- **프로젝트**: 이 시그니처들을 점수화한 "병목 힌트" 규칙 13개를 리포트에 자동 표시. 최상위(98점)는 성능이 아니라 **측정 신뢰성 경고**.

# PART 2. DB — MySQL / 트랜잭션 / 락

## 2.1 B+Tree 인덱스와 복합 인덱스
리프에 정렬된 키가 연결 리스트로 이어진 구조 — 등치+범위+정렬에 강함. 복합 인덱스는 **왼쪽 접두사 규칙**: (a, b, c)는 a, ab, abc 조건에만 유효. 배치 순서는 등치 조건 먼저, 정렬/범위 컬럼 마지막.
- **프로젝트**: 목록 쿼리 `WHERE board_id=? AND is_valid=? ORDER BY x DESC`에 맞춰 `(board_id, is_valid, 정렬컬럼)` 3종 — 인덱스가 정렬을 대신해 filesort 제거.
- 파고들기: 커버링 인덱스(인덱스만으로 응답, 테이블 접근 생략), 인덱스의 비용(쓰기마다 갱신, 카디널리티 낮으면 무용), `LIKE '%kw%'`는 인덱스 불가(우리 검색의 알려진 한계 — 풀텍스트 인덱스가 정석).

## 2.2 커서 vs 오프셋 페이지네이션
OFFSET n은 n행을 읽고 버림 — 깊이에 선형 비례로 느려지고, 동시 쓰기 시 행 밀림/중복. 커서(`WHERE id < ?last ORDER BY id DESC LIMIT n`)는 인덱스 시크라 깊이 무관.
- **프로젝트**: 하이브리드 — 무한 스크롤은 커서, 임의 페이지 점프는 오프셋. 채팅 메시지도 커서(+입장 시점 이전 메시지 차단용 하한 커서).
- 파고들기: 비유일 정렬 키(좋아요순)의 커서는 (like_count, id) 복합 커서 필요.

## 2.3 트랜잭션 ACID와 격리 수준
READ UNCOMMITTED(더티 리드) < READ COMMITTED(반복 불가 읽기) < REPEATABLE READ(팬텀 — MySQL은 갭 락으로 대부분 방지) < SERIALIZABLE. MySQL InnoDB 기본은 RR, MVCC(버전 체인 + 언두 로그)로 읽기는 락 없이 스냅샷.
- **핵심 통찰(프로젝트발)**: check-then-act 경쟁은 격리 수준으로 못 막는다 — 두 트랜잭션이 각자 스냅샷에서 "없음"을 보고 둘 다 INSERT. 막는 것은 유니크 제약(물리) 또는 원자적 단일 문장(upsert).

## 2.4 InnoDB 락
레코드 락(인덱스 레코드), 갭 락(레코드 사이 — RR에서 팬텀 방지), 넥스트키 락(둘의 합). `INSERT ... ON DUPLICATE KEY UPDATE`는 유니크 인덱스에서 충돌 검사와 갱신이 한 문장 — 우리 토글의 해법. 데드락: 상호 락 대기 사이클 — InnoDB가 감지해 한쪽 롤백.
- **프로젝트**: 비정규화 카운터(인기글 행)에 UPDATE가 몰리는 핫로우 경합으로 **시드 중 동시성 5에서도 데드락 실제 재현** — 재시도(백오프 6회)로 흡수하되 "경합 자체는 실험 대상이라 없애지 않음"이라는 판단까지.

## 2.5 Upsert와 affected rows
MySQL의 `ON DUPLICATE KEY UPDATE`는 INSERT면 1, UPDATE면 2를 반환 — 이 값으로 "신규 여부"를 원자적으로 알 수 있다.
- **프로젝트**: 스크랩 토글이 이 값으로 신규/재활성을 구분해 이벤트 중복 발행 방지.

## 2.6 정규화 vs 비정규화
정규화는 갱신 이상 방지, 비정규화는 읽기 경로 단축. 비정규화의 대가는 정합성 유지 책임 — 이중 쓰기, 드리프트.
- **프로젝트**: Post의 카운터 5종 + 닉네임 스냅샷. 드리프트 방지 전략이 특이점: 증감(+1)이 아니라 **토글 트랜잭션 안에서 실제 COUNT를 재조회해 덮어쓰기** — 경쟁이 겹쳐도 최종값이 실제 행 수와 일치. 비용(토글당 COUNT 2회)과의 트레이드오프, 그리고 검증용 정합성 체크 API 존재.

## 2.7 소프트 삭제
`is_valid` 플래그. 장점: 복구/증거/재활성(스크랩·재입장) 도메인과 자연스럽게 맞음. 단점: 전 쿼리에 필터 강제, 유니크 제약과의 상호작용(삭제된 행도 제약에 걸림 — 우리는 오히려 이걸 재활성에 이용), 데이터 증식.
- **프로젝트**: 기본 findById를 필터 포함 쿼리로 오버라이드(실수 방지). 전역 @Where를 안 쓴 이유 — 삭제된 행을 의도적으로 찾는 경로(채팅 재입장)가 있어서.

## 2.8 스키마 마이그레이션
Flyway 버전 관리(V1~V7), 프로덕션 ddl-auto=none. 제약 추가 마이그레이션의 안전 순서: **기존 위반 데이터 정리 → 파생값 백필 → 제약 추가**. 정리 시 어느 행을 남길지의 도메인 판단(유효 행 우선 — 반대면 스크랩이 조용히 취소된 것처럼 보임)까지.
- 파고들기: 무중단 마이그레이션(온라인 DDL, 대형 테이블 ALTER)은 미경험 영역 — 개념만: pt-online-schema-change, gh-ost.

## 2.9 MySQL 운영 지표
slow query log(우리 부하 환경 임계 0.1초), buffer pool hit ratio(99% 미만이면 디스크 읽기 — 워킹셋 > 풀), `innodb_flush_log_at_trx_commit`(1=커밋마다 fsync=내구성, 2/0=성능 — 시드 전용 오버라이드에서 2 사용 후 복원), threads_running, 풀스캔 카운터(Handler_read_rnd_next).

# PART 3. JPA / Hibernate / Spring

## 3.1 영속성 컨텍스트와 더티 체킹
1차 캐시 + 스냅샷 비교로 커밋(flush) 시 UPDATE 자동 생성. 우리 update류 메서드는 save() 호출 없이 도메인 메서드로 상태 변경만 한다.
- **치명 포인트(프로젝트발)**: flush가 제약 위반으로 실패하면 ① 영속성 컨텍스트에 id=null인 깨진 엔티티가 남고 ② 트랜잭션은 rollback-only — 같은 트랜잭션에서 예외를 잡아 복구해도 커밋 시점에 폐기된다. `don't flush the Session after an exception occurs`가 그 증상. **"catch로 유니크 충돌 복구"가 JPA에서 성립하지 않는 이유**를 설명할 수 있으면 상위 1%.

## 3.2 N+1과 해법 4종
목록 1쿼리 + 연관 N쿼리. 해법의 선택 기준까지: ① fetch join(연관을 실제로 쓸 때, 페이징과 컬렉션 fetch join은 상충 주의) ② @BatchSize/IN 배치(부분 완화) ③ **DTO 프로젝션**(연관 자체가 불필요할 때 — 조인 제거가 최선) ④ 집계는 GROUP BY 1쿼리로.
- **프로젝트**: 목록은 ③(+비정규화로 조인 원천 제거), 채팅은 ①, 미읽음은 ④. 남은 N+1(댓글별 반응 조회)을 실측(903쿼리/요청)과 실험 설계(EXP-005)로 관리 중 — "다 잡았다"보다 신뢰받는 답.

## 3.3 지연 로딩과 OSIV
전 연관 LAZY가 기본. OSIV(open-in-view) 켜져 있으면 컨트롤러까지 영속성 컨텍스트 유지 — 편하지만 커넥션을 뷰 렌더까지 점유해 풀 고갈을 악화. 우리 일부 조회 서비스가 트랜잭션 없이 OSIV에 의존하는 것이 알려진 개선점.

## 3.4 @Transactional의 동작 원리와 함정
프록시 기반 AOP → **self-invocation은 어드바이스 미적용**(내부 호출은 프록시를 안 거침). readOnly=true(플러시 생략, 드라이버 힌트), 전파(REQUIRED 기본, REQUIRES_NEW는 별도 트랜잭션).
- **프로젝트**: ① 스케줄러 내부 호출의 @Transactional이 self-invocation이라 건별 분리 의도가 무효 — 직접 발견한 함정 ② 알림 저장은 REQUIRES_NEW로 격리(알림 실패가 본 작업을 못 물귀신) ③ jakarta vs spring @Transactional 혼용이 남아 있는 것도 인지(전자는 readOnly 옵션 없음).

## 3.5 이벤트와 트랜잭션 경계
@TransactionalEventListener(AFTER_COMMIT): 커밋 성공 후에만 실행 — 롤백된 작업의 유령 알림 방지. 주의: AFTER_COMMIT 리스너 안에서 쓰기를 하려면 새 트랜잭션(REQUIRES_NEW)이 필요(원 트랜잭션은 이미 끝남).
- **프로젝트**: 댓글/친구/반응 이벤트 → AFTER_COMMIT 리스너 → 알림 저장(REQUIRES_NEW) + STOMP 푸시, 인기글 점수 갱신도 같은 경로.
- 파고들기: 프로세스 내 이벤트의 한계(재시작 시 유실, 재시도 없음) vs 메시지 브로커(Kafka: 영속, 컨슈머 그룹, 순서 보장 단위) — "지금 규모에선 브로커가 과했다"는 판단과 함께.

## 3.6 AOP 활용 3종 (프로젝트 실례)
① @ResilientRedis — Redis 예외 흡수 후 타입별 기본값 반환(장애 격리) ② 실행 시간 로깅(300ms 초과 WARN, 파라미터는 안 찍음 — 민감정보) ③ 스케줄러 계측 — 어드바이스 순서를 트랜잭션 어드바이저 **바깥**에 둬서 커밋 시간까지 측정. "AOP 순서(@Order)까지 고려했다"는 드문 소재.

# PART 4. Redis

## 4.1 자료구조와 프로젝트 매핑
- String + INCR: 조회수 버퍼(원자적 증가 — 다중 인스턴스 안전)
- String + SETNX(+TTL): 조회 중복 방지 락(유저×글, 1시간)
- List: 게시판별 글 ID 목록(최대 50, trim)
- Sorted Set: 인기글 랭킹(score=핫스코어, ZADD/ZREVRANGE)
- MGET: 글 미리보기 벌크 조회(라운드트립 1회)
- GETDEL: 버퍼 드레인(읽기+삭제 원자 — 유실/이중반영 방지)

## 4.2 캐시 패턴
Look-aside(cache-aside)가 우리 방식: 읽기 시 캐시 → miss면 DB → 채움. 쓰기는 무효화(evict) + TTL 이중 안전망. 대안(write-through/behind)과 비교 가능하게.
- 무효화 전략의 실제 판단: 글 생성 시 리스트에 push하지 않고 통째로 evict(다음 조회가 재구축) — 정합성 단순함 vs 첫 조회 비용의 트레이드오프.

## 4.3 캐시 3대 장애 패턴 (스탬피드/애벌랜치/페네트레이션)
- 스탬피드(thundering herd): 인기 키 만료 순간 동시 미스가 전부 DB로 — 해법: 분산락 단일 재빌드, 논리 만료, 확률적 조기 갱신
- 애벌랜치: 다수 키 동시 만료 — 해법: TTL jitter
- 페네트레이션: 존재하지 않는 키 반복 조회 — 해법: null 캐싱, 블룸 필터
- **프로젝트**: 셋 다 무방비임을 **스스로 카탈로그화(BTL-004)** 하고 콜드/웜 대조 실험(EXP-004)까지 설계 — "모르는 취약"이 아니라 "측정 예정인 알려진 취약".

## 4.4 Redis 장애와 폴백
Redis는 가속 계층이지 원본이 아니어야 한다. 우리 원칙: 죽으면 전 경로 DB 폴백(목록/인기글/토큰), 조회수 버퍼는 유실 수용. AOP로 예외 흡수 + 폴백 필요한 곳은 명시적 try-catch(자기호출 문제로 AOP 불가한 지점 구분까지).
- 파고들기: 단일 스레드 이벤트 루프(그래서 KEYS 같은 O(N) 명령이 전체를 블로킹 — 우리 드레인이 KEYS를 쓰는 게 알려진 개선점, SCAN이 정석), persistence(RDB/AOF), eviction 정책, 그리고 지금은 단일 노드 — HA(sentinel/cluster)는 미적용 인정.

## 4.5 분산 환경에서의 Redis
스케일아웃 시 필요해지는 것: 스케줄러 중복 실행 방지(분산락 — SET NX PX + 소유자 검증 해제, Redisson), pub/sub(채팅 브로커 외부화 후보). 현재 단일 인스턴스 전제임을 명확히 인지하고 있다는 게 포인트.

# PART 5. 인증·보안

## 5.1 세션 vs 토큰(JWT)
세션: 서버 상태, 즉시 무효화 가능, 확장 시 세션 스토어 공유 필요. JWT: 무상태 자기서명, 확장 용이, **발급 후 통제 불가**가 본질적 약점 — 그래서 수명을 짧게 + refresh를 서버 저장으로 절충하는 게 업계 표준이고 우리 구조.
- **프로젝트**: HS512 서명, access 30분/refresh 7일, refresh는 DB 저장(폐기 가능) + 재발급 시 rotation + Redis 캐시(miss 시 DB, 남은 TTL 재적재), 만료분 매일 새벽 배치 정리.
- 파고들기: HS(대칭) vs RS(비대칭 — 검증 서버가 여럿일 때), rotation의 목적(탈취된 refresh의 재사용 탐지 여지), 우리 약점(access/refresh 클레임 구조 동일 — 타입 클레임 부재).

## 5.2 쿠키 보안 속성
HttpOnly(JS 접근 차단 — XSS 내성), Secure(HTTPS만), SameSite(None/Lax/Strict — 크로스 사이트 전송 제어), Domain/Path. refresh 쿠키의 Path를 재발급 엔드포인트로 한정한 것은 노출 면적 축소.
- **프로젝트 약점(선제 인정용)**: 크로스 도메인 프론트 때문에 SameSite=None인데 CSRF 방어 부재 — 쿠키 인증에서는 CSRF 토큰 or Origin 검증이 필요. XSS/CSRF의 차이(훔치기 vs 시키기)와 각 방어를 매핑해서 말할 수 있어야 함.

## 5.3 OAuth2 Authorization Code Flow
인가 요청 → 사용자 동의 → redirect_uri로 code → 백엔드가 code+client_secret으로 토큰 교환 → 유저 정보 → 우리 계정과 연결(이메일 기준, 없으면 자동 가입) → **자체 JWT로 전환**. code를 쓰는 이유(토큰이 브라우저 URL에 노출되지 않게), 자체 토큰으로 바꾸는 이유(provider 독립적 수명/권한 관리).
- 파고들기: state 파라미터(CSRF 방지), PKCE(공개 클라이언트용).

## 5.4 비밀번호와 BCrypt
적응형 해시(cost factor로 의도적 저속) + 솔트 내장. 저속이 특징이자 비용 — **부하 테스트에서 로그인이 요청의 19%를 차지하며 CPU를 지배한 실측**, 시드 시 BCrypt 2만 회가 병목이라 시드 전용으로 CPU 한계를 올린 판단까지 연결하면 특급 소재.

## 5.5 인가 설계
화이트리스트(기본 거부) vs 블랙리스트(기본 허용). 우리는 GET 전체 permitAll인 블랙리스트 — 새 엔드포인트의 기본값이 "공개"라는 구조적 위험을 알려진 이슈로 관리. 리소스 소유권 검증은 서비스 계층(user.id == resource.user.id). 인가 규칙을 테스트로 고정하는 것(spring-security-test)이 재발 방지의 정석.

# PART 6. 실시간 통신

## 6.1 WebSocket / STOMP / SockJS
WebSocket: HTTP 업그레이드로 여는 전이중 연결. STOMP: 그 위의 프레임 프로토콜(SUBSCRIBE/SEND, destination 개념) — 순수 WS 대비 라우팅·구독 관리를 프레임워크가 대신. SockJS: WS 불가 환경 폴백.
- **프로젝트**: 발행 /app/**, 브로드캐스트 /topic/chat/room/{id}, 개인 큐 /user/{id}/queue. 인증은 핸드셰이크(쿠키 검증)와 **구독 시점**(방 참여자 검증 — 도청 차단) 2중.
- 실전 버그 소재: STOMP content-length는 **옥텟 수**인데 String.length(UTF-16 코드유닛)로 계산해 한글 본문마다 프레임 경계가 깨져 연결이 죽던 버그 — 모든 겉보기 신호가 정상이라 커스텀 메트릭(RTT/에러 카운터)으로만 검출.

## 6.2 메시지 전달 보장과 멱등성
at-most-once / at-least-once / exactly-once. 재전송(at-least-once) 전제에서 서버가 멱등 처리해 사실상 exactly-once로 수렴시키는 게 실무 패턴: 클라이언트 생성 ID(clientMsgId) + UNIQUE 제약 + 충돌 시 원본 반환.
- **프로젝트**: 그대로 구현. 추가로 읽음 위치 **단조 증가**(늦게 도착한 과거 요청이 상태를 되돌리지 못함 — 분산 시스템의 out-of-order 대응 기본기).

## 6.3 브로커와 수평 확장
인메모리 SimpleBroker는 서버 인스턴스 안에만 산다 — 2대가 되면 크로스 인스턴스 브로드캐스트 불가. 해법: 외부 브로커 릴레이(RabbitMQ STOMP) 또는 Redis pub/sub 버스. 우리의 알려진 한계(BTL-006)이자 스케일아웃 선결 과제.

# PART 7. JVM·인프라·운영

## 7.1 JVM 메모리와 컨테이너
힙(-Xms=-Xmx 고정: 런타임 리사이즈 노이즈 제거 — 성능 측정의 통제 변수) + 비힙(메타스페이스, 스레드 스택 ~1MB×스레드 수, GC 구조체, 다이렉트 버퍼). **컨테이너 메모리 한계는 힙보다 충분히 커야 한다** — 힙 1G에 한계 1.5G로 뒀다가 커널 강제 회수 992회를 겪고 2.5G로 조정한 실측 스토리(OOM Kill 0이어도 위험 상태일 수 있다는 것, anon vs file 메모리 구분까지).

## 7.2 GC (G1)
리전 기반, 목표 pause(-XX:MaxGCPauseMillis=200) 내에서 young/mixed 수집. 보는 지표: pause max(우리 임계 200/500ms)와 **오버헤드%**(전체 시간 중 GC 비율, 5%/10%) — 빈도×시간을 하나로 보는 지표. 실측: 정상 시 0.2% 미만, 붕괴 실행에서도 2.7%로 "GC는 범인이 아니었다"는 배제 진단 경험.

## 7.3 Tomcat 스레드 모델과 용량 계획
max-threads(동시 처리), accept-count(대기 큐), max-connections. **계층 간 균형이 핵심**: 스레드 400 vs DB 커넥션 10이면 390개는 풀 앞 대기자 — 실측으로 증명(pending 205, timeout 5,316). "병목 뒤 자원에 앞 계층을 맞춘다"는 원칙. HikariCP 크기 논리(적은 커넥션이 오히려 빠르다 — 디스크/코어 경합, core*2+spindle 휴리스틱).

## 7.4 CPU throttling (cgroup)
컨테이너 CPU 한계는 기간(period)당 쿼터 — 소진하면 다음 기간까지 강제 정지. **평균 사용률이 낮아도 버스트 순간마다 정지가 걸려 p99를 파괴**하는, 컨테이너 환경 꼬리 지연의 최대 원인. 우리 회귀 규칙에서 gate:true(1%/10%), 붕괴 실행 실측 ~100%.

## 7.5 관측 스택
Prometheus(pull 기반 스크레이프, 시계열) + exporter(mysqld/redis/cAdvisor) + Micrometer(앱 — 히스토그램 버킷 명시) + Grafana. 메트릭 타입(counter는 increase/rate로, gauge는 max/avg로). 함정 경험: 죽은 컨테이너의 시계열이 합산돼 "메모리 227% 포화"라는 불가능한 수치가 리포트에 실렸던 사건 — 쿼리를 max()로 감싸 수정하고 저장된 61개 실행 전부 재수집. "원자료(raw)를 보관했기에 소급 재처리가 가능했다"는 설계 교훈.

## 7.6 배포
GitHub Actions OIDC(정적 키 없이 IAM 역할 assume — 시크릿 유출 면적 제거) → ECR → EC2 compose. host 네트워크 모드(로컬 Redis 접근). 알려진 공백: CI 테스트 게이트 없음, 배포 후 헬스체크/롤백 없음, 단일 인스턴스 다운타임 — 각각의 해법(테스트 게이트, 헬스체크 후 트래픽 전환, 블루/그린)을 말할 수 있게.

## 7.7 무중단 배포 (개념 대비)
롤링(점진 교체 — 버전 혼재 허용 필요), 블루/그린(전체 이중화 후 전환 — 비용), 카나리(일부 트래픽 실험). 공통 전제: 헬스체크, 이전 버전과의 스키마 호환(expand-contract 마이그레이션).

# PART 8. 아키텍처·설계 일반

## 8.1 계층형 아키텍처와 포트/어댑터
컨트롤러(HTTP만) → 서비스(비즈니스+트랜잭션) → 리포지토리. 우리는 Redis 접근을 도메인 포트 인터페이스 + 인프라 어댑터로 분리(테스트 용이, 구현 교체 가능) — "헥사고날을 전면 도입하진 않고 외부 의존(Redis, S3)에만 적용"이라는 실용 판단.

## 8.2 DTO와 엔티티 분리
엔티티 직접 노출 금지 — 노출 사고(익명성!), 순환 참조, 스키마 결합. fromEntity 정적 팩토리 컨벤션. 익명화가 DTO 계층 규약이라는 약점(강제 안 됨)까지.

## 8.3 예외 설계
도메인 예외(ErrorCode enum + CustomException) → 전역 핸들러가 HTTP 상태로 변환. 로그 레벨 정책(4xx는 warn, 5xx만 스택트레이스). "도메인 오류를 삼키면 400이어야 할 응답이 500이 된다"는 원칙.

## 8.4 S3 tmp-promote 패턴
업로드는 임시 경로에 먼저 → 엔티티 저장 성공 시 최종 경로로 복사 → 임시 정리. 이유: 본문 저장 실패 시 고아 파일 최소화. 한계: S3는 트랜잭션에 참여하지 않음 — 완전한 원자성 불가(보상 정리로 절충).

## 8.5 스케줄러 설계
버퍼 flush(1분), 랭킹 재계산(5분), 토큰 정리(새벽), 외부 API 적재(월간). 논점: 실패 격리(한 건 실패가 배치 전체를 죽이면 안 됨 — self-invocation 함정과 연결), 다중 인스턴스 중복 실행(분산락 필요 — 현재 한계), 스케줄러 flush 버스트가 사용자 트래픽과 간섭할 가능성(soak로 관측 예정, BTL-007).

# PART 9. 토스 면접 형식 대비 메모

1. **꼬리질문 내성**: 토스는 "왜?"를 3~5번 반복한다. 모든 답의 끝에 "왜 그 선택이었나(대안 대비)"를 붙이는 연습. 모르면 "모르지만, 이렇게 접근하겠다"로 — 아는 척이 최악.
2. **숫자로 말하기**: 질문지 부록의 숫자 카드 10개를 체화. "빨라졌어요"가 아니라 "p95가 얼마에서 얼마로".
3. **약점 선제 공개**: 이 프로젝트의 최대 차별점은 결함 92건을 스스로 장부화했다는 것. "부끄러운 코드" 질문은 준비된 무대다.
4. **기본기 필터**: 위 개념 중 프로젝트와 무관하게도 나오는 단골 — 트랜잭션 격리 수준, 인덱스 원리, JWT vs 세션, N+1, TCP/HTTP(3-way handshake, keep-alive, HTTP/2 멀티플렉싱 정도는 별도 복습 권장 — 이 문서 범위 밖), 자바 동시성 기초(synchronized/volatile/Atomic — CAS까지).
5. **라이브 코딩/CS 대비는 별도**: 이 문서는 프로젝트 기반 기술면접 범위. 코딩테스트·CS 지필은 별도 준비 필요.
