## 0. 결론 — 진단 한 문단과 계측표

원고의 불릿은 어미가 명사형이라 겉보기엔 개조식이다. 그러나 **한 불릿이 실물의 2~3배 길이**이고, 그 안에 **실물 이력서에 한 건도 없는 영어 에세이의 수사**가 들어 있다. em dash로 절을 잇고, 화살표로 인과를 잇고, 문장 한가운데를 굵게 하고, "X가 아니라 Y"로 대조하고, 용어를 따옴표로 감싸고, 소제목을 문장으로 쓴다. 이력서 4,098자에서 이 다섯 가지가 47건이다. 여기에 전략 문서와 장부에서 쓰던 작업 어휘(장치·판정·자격·미끼·사건·거짓말)가 원고로 새어 들어왔고, "먼저 밝힙니다", "숨기지 않기" 같은 정직 과시 문장이 반복된다. **이 조합이 "AI가 썼다"는 인상의 실체다.** 번역투(~를 통해, ~에 있어)는 실물에도 있고 원고에는 오히려 적으니 그쪽을 고칠 일은 거의 없다. **2026-09-07 에 사용자가 확정한 최상위 규칙이 하나 더 있다. 추상적·문학적·생소한 표현을 쓰지 않고, 즉시 이해되는 표현과 널리 알려진 전문용어만 쓴다(2.12).**

| 항목 | 실물 4편 (편당) | 원고 이력서 (4,098자) | 원고 포트폴리오 (45,667자) |

| 문장 안 굵게 (레이블·표 제외) | 0 | **22** | **143** |
| "X가 아니라 Y" | 0 | **4** | **31** |
| 따옴표 강조 | 0 | 3 | 13 |
| 불릿 평균 길이 | 23~49자 | **112자** | 본문이 문단 |
| 90자 초과 불릿 | 0~1 | **12/22** | |

## 1. 문체 체계 — 어디에 어떤 문체를 쓰는가

실물 4편과 국내 지침(워니·원티드·링커리어·권시연)이 일치하는 체계다.

| 자리 | 문체 | 길이 | 근거 |
|---|---|---|---|
| **소개 문단** | "~습니다" 서술체. **직무 명사로 시작**("백엔드 개발자입니다" / "~년차 서버 개발자로"). 연차·규모·기술·관심사 | 3~5줄 | 실물 4/4 · 워니 2~5줄 · 원티드 3~5줄 · [rules-resume](rules-resume.md) 4절(TIH) |
| **회사·프로젝트 한 줄 설명** | 명사구 또는 서술체 1~2문장. 규모 수치 | 1~2줄 | 이동욱·김재녕·이재연 |
| **경력·프로젝트 불릿** | **명사형 종결** (구축·개선·도입·구현·단축·감소). 마침표 없음. 대명사 없음 | **1줄(≤90자, 평균 40자 안팎)**. 이유·방법은 둘째 줄 1줄 | 실물 4/4 · 링커리어 · 권시연 STAR 예시 |
| **불릿의 이유 줄** | 종결 어미 없이 명사형 또는 "~발생", "~처리"로 끝남 | 1줄 | 김재녕 |
| **프로젝트·장 제목** | **대상 + 행위 명사구** ("의료 진료 서비스 API 서버의 내결함성 개선") | 1줄 | 실물 4/4 |
| **포트폴리오 본문** | "~습니다" 서술체. 한 문장에 생각 하나. 문단 3~4문장 | | technical-writing.dev 7.2 · 우아한(구인본) "친구에게 이야기하듯" |
| **표·그림 캡션** | 명사구 | 1줄 | |

**혼용 금지.** 한 섹션 안에서 "~습니다"와 명사형을 섞지 않는다. 명사형 안에서도 순수 명사(개선·구축·도입)와 동명사형(~함·~음·~정함)을 섞지 않는다. 실물 4편은 순수 명사 위주다. KPI 카드·그림 캡션(html-raw 블록)은 계측기가 세지 않으므로 캡션이 명사구인지 직접 본다. 현재 원고의 이력서는 소개만 서술체이고 나머지가 명사형이라 체계 자체는 맞다. 포트폴리오도 서술체로 통일돼 있다. 문제는 체계가 아니라 문장 **안**이다(2절).

## 2. 쓰지 않는 것 — AI 티 목록, 각각의 교정법

실물 4편에서 0건인 것이 **강한 위반**이다. 계측기(`lint.js`)가 세는 항목과 같다. 각 항목에 원고의 실제 문장과 교정안을 붙였다.

### 2.1 em dash `—`

한국어 어문 규범에 없는 영어 문장 부호다(나무위키 "영문법식 문장 부호", [09](resume/09-korean-hiring-guides.md) 8절). 실물은 날짜 범위("2019년 1월 — 현재")에만 쓴다. **마침표·쉼표·괄호·조사("로", "때문에")로 바꾼다.** 대시 앞뒤를 두 문장으로 나누면 대부분 해결된다.

> 전: 측정을 믿어도 되는 조건을 코드로 정의했습니다 — 처치 없이 반복했을 때의 자연 편차를 먼저 재고 그보다 작은 차이는 개선이라 부르지 않는, **A/B 테스트의 판정 원리와 같은 순서**입니다.
> 후: 측정을 믿어도 되는 조건을 코드로 정의했습니다. 처치 없이 반복했을 때의 자연 편차를 먼저 재고, 그보다 작은 차이는 개선으로 세지 않습니다.

> 전: 278ms — 38배 차이는 코드가 아니라 대기줄
> 후: 278ms. 38배 차이는 커넥션 풀 대기 시간

### 2.2 접속 화살표 `→`

실물과 권시연 예시는 **수치 전후("11개 → 5개", "8 sec → 4 sec", "5초 -> 1.2초")에만** 화살표를 쓴다. 인과·순서를 잇는 화살표("추적 → 실제 원인은", "확인해 2차 대상을 정함 → 패치 조인으로")는 0건이다. **문장을 나눈다.**

> 전: 부하 테스트의 p95(평균 10,685ms)를 애플리케이션 지연으로 판단해 호스트 자원까지 닷새간 추적 → 실제 원인은 **도착률이 처리 용량을 넘긴 포화**(커넥션 획득 p95 6,364ms · 대기 145건 · CPU 상한 상시 도달).
> 후: 부하 테스트 p95 10,685ms를 애플리케이션 지연으로 오독해 닷새간 호스트 자원 추적
> 　　실제 원인은 커넥션 풀 포화(획득 p95 6,364ms, 대기 145건). 도착률을 초당 4요청으로 낮추면 같은 코드에서 278ms

### 2.3 문장 안 굵게

우아한(구인본): *"제목/강조에만 Bold"*. 실물에서 굵게는 **소개 문단의 규모 수치**(이동욱)와 **레이블**(`설명:` `개발 환경:`)뿐이다. 문장 한가운데 굵게는 0건. 굵게로 강조하고 싶은 것이 있으면 **그 자리에 수치를 넣거나 문장 맨 앞으로 옮긴다.**

> 전: **한 번에 하나씩.** 반응 일괄 조회로 1,507 → 112개, p95 226.7 → 57.2ms. 재계측으로 남은 112개 중 108개가 작성자 조회임을 확인해 2차 대상을 정함 → 패치 조인으로 112 → 3.9개, **p95 57.2 → 34.3ms(−40.1%, 검출 한계 16%를 넘어 노이즈로 설명되지 않음)**. 1차에 적어 둔 예측(약 108개)과 2차 실측(108.3개) 일치
> 후:
> - 반응 일괄 조회로 요청당 쿼리 1,507 → 112개, p95 226.7 → 57.2ms 개선
> - 재계측으로 남은 112개 중 108개가 작성자 조회임을 확인하고 패치 조인 적용, 쿼리 112 → 3.9개, p95 57.2 → 34.3ms(−40.1%) 개선
> 　　검출 한계 16%를 넘는 폭. 1차 예측(약 108개)과 2차 실측(108.3개) 일치

### 2.4 "X가 아니라 Y" 대조

포트폴리오에 31건(표 제외). 실물 0건. 이 구문은 독자가 X를 생각했다고 전제하고 바로잡는 수사라서, 반복되면 **가르치는 어조**가 된다. **Y만 쓴다.** X가 꼭 필요하면 다음 문장에서 사실로 쓴다.

> 전: 38배 차이는 코드가 아니라 대기줄이었습니다.
> 후: 38배 차이는 커넥션 풀 대기 시간이었습니다.

> 전: 포화를 판정(pass/fail)이 아니라 해석 조건(interpretation condition)으로 정의했습니다.
> 후: 포화를 해석 조건으로 정의했습니다. 결과를 버리지 않고, 그 결과로 주장할 수 있는 범위를 제한합니다.

### 2.5 따옴표 강조

"개선했다"고, "해석 불가"로, "+59,000% 회귀". 실물 0건. 용어는 따옴표 없이 쓰고, 꼭 구분해야 하면 **작은따옴표**(한국어 강조 규범). 숫자 인용은 따옴표 없이.

> 전: 회귀 판정기가 … **"+59,000% 회귀"를 오보**
> 후: 회귀 판정기가 +59,000% 회귀를 잘못 보고

### 2.6 문장형·문학적 제목

실물의 제목은 전부 **대상 + 행위 명사구**다. 원고는 "측정이 두 번 거짓말했고, 그 조건을 코드로 걸러내게 만듦", "사건 하나 — 닷새를 태운 오진", "'개선했다'고 말할 자격을 숫자로 정의하기", "버린 대안 — 이 기록이 본문입니다"처럼 **서사 제목**이다. 심사자는 제목만 훑으므로 제목이 문장이면 훑기가 안 된다.

| 전 | 후 |
|---|---|
| 사용자 행동을 모아 순위로 서빙하는 읽기 경로 (포트폴리오 2장) | 인기글 랭킹 읽기 경로 설계 (반응·조회 집계, Redis 정렬 집합) |
| 측정이 두 번 거짓말했고, 그 조건을 코드로 걸러내게 만듦 (포트폴리오 3~5장) | 부하 테스트 결과 오독 2건과 측정 유효성 판정 도입 |
| 진단한 병목 제거 — 요청당 쿼리 1,507개 → 3.9개 (포트폴리오 6장) | 댓글 목록 API N+1 제거 (요청당 쿼리 1,507 → 3.9개) |
| 동시성 결함의 장애 전파 경로 차단 (포트폴리오 8장) | 스크랩 토글 경쟁 상태로 인한 게시글 상세 조회 장애 해결 |
| 3. 사건 하나 — 닷새를 태운 오진 | 3. 부하 테스트 p95 오독과 포화 판정 도입 |
| 3.3 원인 — 신호는 처음부터 전부 있었다 | 3.3 원인 |
| 5. "개선했다"고 말할 자격을 숫자로 정의하기 | 5. 개선 판정 기준 정의 (변동계수와 최소 검출 가능 효과) |
| 6.4 버린 대안 — 이 장의 본문입니다 | 6.4 검토한 대안과 버린 이유 |
| 7. 목표를 다시 세우다 — "충분히 빠른가"를 정의하기 | 7. 엔드포인트 그룹별 지연 목표 설정 |

"(포트폴리오 n장)" 자기 참조는 이력서 소제목에서 뺀다. 필요하면 프로젝트 머리 한 줄에 "상세는 포트폴리오"라고 한 번만.

### 2.7 메타 담화와 정직 과시

technical-writing.dev 7.2: *"말에 대한 말"* 은 지운다. 원고에는 "먼저 밝힐 것이 있습니다", "가장 뼈아픈 부분입니다", "부작용을 숨기지 않기", "스스로 무효 처리한", "이 기록이 본문입니다", "이 장이 6장의 전제입니다", "여기서 한 판단 하나"가 반복된다. 정직함은 **사실을 그냥 쓰면** 전달된다. 정직하다고 말하면 오히려 의심을 산다. 이현섭의 "(현재 서비스 되고 있지 않음)"이 정직의 실물 형태다.

> 전: 이 사건에서 가장 뼈아픈 부분입니다. **필요한 지표는 하나도 빠짐없이 수집되고 있었습니다.**
> 후: 필요한 지표는 이미 전부 수집되고 있었습니다.

> 전: 먼저 밝힐 것이 있습니다. **이 프로젝트는 사용자 규모를 목표로 만든 서비스가 아닙니다.** 실사용자 지표를 올린 이야기가 여기에는 없습니다.
> 후: 이 프로젝트는 실사용자 지표를 올린 서비스가 아닙니다. 규모는 게시판 단위입니다.

전략 문서(`daangn-feed-infra.md`)·장부(`GAPS.md`, `resume-assets.md`)·메모리에서 쓰는 말이 원고에 그대로 들어왔다. 심사자에게는 내부 은어다.

|---|---|---|
| 장치 ("선언하는 장치", "판정 장치") | 장부 | 기능, 코드, 로직, 판정 규칙 |

| 오보, 승격 ("해석 조건으로 승격") | 장부 | 잘못 보고, 정의 |
| 서사, 미끼, 지반, 방어 | 전략·메모리 | **원고에 쓰지 않는다** (현재 원고에는 없음. 앞으로도) |
| 판정 | 측정 시스템의 도메인 용어(포화 판정, 회귀 판정) | **도메인 용어로는 유지.** "판정 자격", "판정 원리" 같은 비유 용법만 뺀다 |

### 2.9 한 불릿에 여러 절

원고 불릿 평균 112자, 실물 23~49자. 불릿 하나가 "~하고 ~해 ~함 ~이므로 ~" 로 이어진다. **불릿 하나 = 사실 하나.** 두 번째 사실은 새 불릿, 이유는 둘째 줄. 2절의 전후 예 대부분이 이 규칙의 적용이다. 90자를 넘으면 계측기가 잡는다.

### 2.10 사역·피동·도구 주어

"걸러내게 만듦", "선언하는 장치가 없었다", "~에 의해". 나무위키 4.12(사역)·technical-writing.dev 7.3(도구 주어 금지, 능동). **사람이 한 일은 능동으로**, 시스템 동작은 "~한다"로.

> 전: 측정이 두 번 거짓말했고, 그 조건을 코드로 걸러내게 만듦
> 후: 부하 테스트 결과를 두 번 잘못 읽었고, 그 조건을 코드로 걸러내도록 판정 규칙 추가

### 2.11 괄호 안 문장

괄호는 실물에도 많다(김재녕 92건). 실물의 괄호 안은 **수치·기술·기간**이다. 원고는 괄호 안에 어미가 있는 문장("~하지 못하는 중")이 들어간다. 괄호 안에는 명사만.

### 2.12 추상적·문학적·생소한 표현 금지 (2026-09-07 추가, 사용자 확정 규칙)

> **규칙 원문(사용자, 2026-09-07):** 추상적·문학적 표현, 생소한 표현 사용 금지. 무조건 직관적이고
> 즉시 이해되는 표현과 보편적으로 널리 알려진 전문용어를 사용할 것.

이 규칙은 이 문서의 다른 어떤 규칙보다 앞선다. 문장을 읽는 사람이 한 번에 뜻을 알 수 없으면
그 문장은 틀린 문장이다. 아래는 이 규칙이 잡는 세 가지 위반과 각각의 고치는 법이다.

사용자 판정: *"전문용어는 반드시 일반적으로 널리 사용하는 용어만 쓰고, 그렇지 않으면 누구든
쉽게 파악할 수 있도록 풀어 쓴다. 직관적으로 이해가 되도록 할 것."*

**두 종류의 위반이 있다.**

첫째, **국내 백엔드 개발자가 일상적으로 쓰지 않는 용어**를 그대로 쓰는 것. 다른 분야의
용어를 옮겨 온 것(추천 시스템의 explicit/implicit feedback → "명시적 신호/암시적 신호"),
영문 용어를 굳이 번역한 것(Sorted Set → "정렬 집합", fetch join → "패치 조인"), 작업 문서에서
만든 말("해석 조건", "게이팅", "운용점", "관문", "사슬", "장부", "방아쇠")이 여기 든다.

| 원고에 있던 말 | 바꾼 말 |
|---|---|
| 명시적 신호 / 암시적 신호 | 댓글·반응·스크랩(직접 한 행동) / 조회 |
| 정렬 집합 | Sorted Set (첫 등장에 Redis Sorted Set) |
| 패치 조인 | 페치 조인 (첫 등장에 fetch join) |
| 도착률 | 초당 요청 수 |
| 포화 (첫 등장) | 요청이 처리 용량을 넘겨 쌓인 상태(포화) |
| 해석 조건 | 그 실행의 수치를 인용하지 못하게 막는 표시 |
| 대조군 유효성 게이팅 | 비교해도 되는 실행만 고르는 검사 |
| 대조군 (첫 등장) | 대조군(비교 기준이 되는 이전 실행) |
| 체크-후-실행 경쟁 상태 | 조회와 삽입 사이에 다른 요청이 끼어드는 경쟁 상태 |
| 운용점 | 부하 |
| 관문 / 사슬 / 장부 / 계약 | 조건 / 연결 / 기록·목록 / 조건 |
| 방아쇠 | 계기 |
| 무차원 | 단위가 없는 비율 |
| 꼬리 | 가장 느린 쪽 요청 |
| 분위수 사이를 선형보간 | p50·p95·p99 값 사이를 직선으로 이어 |
| 리틀의 법칙 (첫 등장) | 리틀의 법칙(동시에 처리 중인 수 = 처리량 × 처리 시간) |

**그대로 두는 것**: 지연 로딩, 영속성 컨텍스트, 1차 캐시, 폴백, 멱등, 커넥션 풀, p95, 변동계수
(첫 등장에 "표준편차 ÷ 평균" 병기), 최소 검출 가능 효과(첫 등장에 뜻 한 문장 병기). JPA·통계
쪽에서 그 이름으로 통하고 다른 말이 없다.

둘째, **구체적인 이름이 있는데 대명사와 비유로 돌려 말하는 것.** "쉬운 척"하는 문장이 된다.

> 전: 두 문제의 위치가 다릅니다. 하나는 요청이 들어가는 길에서 자원을 기다린 것이고, 다른 하나는 응답을 만드는 길에서 쿼리가 더 나간 것입니다. 앞의 것은 애플리케이션 코드 바깥에서 일어나고, 뒤의 것은 코드로 짐작할 수는 있어도 얼마나 비싼지는 알 수 없습니다.
> 후: 두 문제는 생긴 자리가 다릅니다. 커넥션 풀 대기(3장)는 요청이 DB 에 닿기 전에 커넥션을 기다린 것이고, 추가 쿼리(6장)는 응답 DTO 를 만드는 중에 댓글마다 쿼리가 더 나간 것입니다. 커넥션 풀 대기는 애플리케이션 코드 밖에서 일어나므로 코드만 봐서는 알 수 없습니다.

> 전: 실행 조건을 비교 자체를 무효로 만드는 것과 신뢰도만 낮추는 것으로 나누고, 앞의 것만으로 같은 실험을 식별하는 해시를 만들었습니다. 조건은 분기문 대신 선언적인 표에 두었습니다.
> 후: 실행 조건을 두 묶음으로 나눴습니다. 부하 크기나 데이터셋처럼 다르면 비교 자체가 성립하지 않는 조건과, 다르더라도 비교는 되고 신뢰도만 낮아지는 조건입니다. 첫 번째 묶음의 값만 모아 해시를 만들고, 어느 조건이 어느 묶음인지는 코드의 if 문 대신 표 하나에 적어 두었습니다.

**제목과 그림 캡션도 같은 규칙이다.** "요청 하나가 지나는 길", "무엇을 어디서 재는가",
"남긴 것", "한 것", "물었던 것" 은 문학적이거나 뜻이 비어 있다. 기술 문서의 제목은 그 절이

## 3. 허용 — 과교정하지 말 것

- **"~를 통해"** — 김재녕·이재연 각 7건. 한국 개발자 글에서 자연스럽다. technical-writing.dev 는 "로"를 권하지만 위반이 아니다.
- **"및", "/"** — 이동욱 전편. 명사형 불릿의 표준 접속.
- **수치 전후 화살표** "1,507 → 3.9개", "8 sec → 4 sec".
- **괄호 안 수치·기술·기간**, **영문 기술명·약어**(첫 등장에 풀어 쓰기는 산문에서만).
- **명사형 종결 불릿** — 이건 개조식 관례이지 번역투가 아니다. technical-writing.dev 7.1의 "명사형 나열 지양"은 **산문**에만 적용한다.
- **소개 문단의 규모 수치 굵게**(이동욱), **레이블 굵게**(`**설명:**`).
- **소개·본문의 "~습니다"**.
- **동기 한 줄** "~필요해 참여", "~귀찮아서 개발" (이동욱). 짧고 사람 말이다. 원고의 이유 줄도 이 톤이 맞다.
- **범위 표시** "(현재 서비스 되고 있지 않음)", "규모는 게시판 단위" — 정직 과시(2.7)와 다르다. 사실만 쓴 것이다.

## 5. 포트폴리오 장 구조 — 국내 근거

우아한형제들(구인본)의 프로젝트 설명 7단계가 국내 1차 근거다. 해외 12단계([rules-portfolio](rules-portfolio.md) 0절)와 대응한다.

| 구인본 7단계 | 해외 12단계 | 원고 현재 |
|---|---|---|
| 1 문제 정의 | 1 문제를 수치로 | 있음. 다만 서사 제목·대시 |
| 2 원인 | 5 원인·방아쇠·감지 분리 | 있음. 방아쇠·감지 구분 없음 |
| 3 측정 (문제의 결과, 심각성) | 3 실증 | 있음 |
| 4 해결책 (연구 및 대안책) | 6 대안 표 | 6.4만 표. 나머지 산문 |
| 5 해결 과정 | 7 결정 · 8 검증 | 있음 |
| 6 평가 (해결되었는지 측정) | 8 검증·검산 · 9 결과 | 있음 |
| 7 비고 (회고, 부수효과) | 10 잘된 것/잘못된 것/운 · 12 결론 | "남은 한계"만. 결론 문단 없음 |

장 제목은 **명사구**(2.6 표). 본문은 서술체, 한 문장 하나, 문단 3~4문장. 분량은 프라임커리어(보조)가 "10장 내외, 2~3 프로젝트"라 하고 권시연은 프로젝트 1개를 자세히 썼다. 이 원고는 프로젝트 1개를 축약본 8~9쪽으로 쓰는 것이므로 국내 기준과 어긋나지 않는다.

## 6. 변환 예 — 원고의 실제 문장을 규칙대로 고치면

### 6.1 소개 문단

> 전: 가설을 세우고 **그 가설이 틀렸는지 데이터로 판정**하는 방식으로 일합니다. 개인 프로젝트에서 지연의 원인을 잘못 짚어 닷새를 쓴 뒤, 측정을 믿어도 되는 조건을 코드로 정의했습니다 — 처치 없이 반복했을 때의 자연 편차를 먼저 재고 그보다 작은 차이는 개선이라 부르지 않는, **A/B 테스트의 판정 원리와 같은 순서**입니다. 실사용자 지표를 올린 프로젝트는 아닙니다. 대신 사용자 행동을 모아 순위로 서빙하는 읽기 경로를 끝까지 만들었고, 그 위에서 성능을 고쳤습니다.
>
> 후: 백엔드 개발자입니다. Java와 Spring Boot로 익명 커뮤니티 서비스의 게시글·댓글·인기글 랭킹을 만들어 배포하고, 부하 테스트로 병목을 찾아 고쳤습니다. 지연의 원인을 잘못 짚어 닷새를 쓴 뒤로는 측정을 믿어도 되는 조건을 먼저 정하고, 반복 측정의 자연 편차보다 작은 차이는 개선으로 세지 않습니다. 실사용자 지표를 올린 프로젝트는 아니며 규모는 게시판 단위입니다.

바뀐 것: 직무 명사로 시작 · 대시 제거 · 굵게 제거 · "A/B 테스트 원리" 비유 제거(비유는 면접에서) · 4문장.

### 6.2 포트폴리오 1장 첫 문단

> 전: 처음 목표는 커뮤니티 서비스를 만드는 것이었습니다. 만들고 나서 부하를 걸어 보니 응답이 느렸고, **그 느림의 원인을 찾는 과정에서 더 큰 문제를 발견했습니다 — 제가 만든 측정 결과를 제가 믿을 수 없다는 것**이었습니다. 그래서 프로젝트의 질문이 바뀌었습니다. > **"성능을 개선했다"고 말하려면 무엇이 참이어야 하는가?**
>
> 후: 처음 목표는 커뮤니티 서비스를 만드는 것이었습니다. 만들고 나서 부하를 걸어 보니 응답이 느렸습니다. 느린 원인을 찾다가, 측정 결과 자체를 믿을 수 없다는 문제를 먼저 발견했습니다. 이 문서는 성능 개선을 주장하려면 무엇이 참이어야 하는지를 정하고, 그 위에서 병목을 고친 과정입니다.

### 6.3 포트폴리오 lead 한 줄

> 전: 측정이 거짓말을 했고, 그것을 잡는 절차를 만든 뒤에야 성능을 고쳤습니다.
> 후: 측정 결과를 믿어도 되는 조건을 먼저 정하고, 그 위에서 성능을 고쳤습니다.

### 6.4 9장 첫 문단

> 전: **동아리 프로젝트로 3명이 시작했고 제가 리드했습니다.** 백엔드에서는 사용자 엔티티와 인증 설정을 제외한 대부분 — 게시글·댓글·인기글·파일 업로드 — 을 맡았습니다. **4개월 뒤부터는 혼자 이어오고 있습니다.** 전체 715 커밋 중 519건이 제 것이고, `performance/` 의 158 커밋은 전부 단독 구간의 것입니다.
>
> 후: 동아리 프로젝트로 3명이 시작했고 제가 리드했습니다. 백엔드에서는 게시글·댓글·인기글·파일 업로드를 맡았고, 사용자 엔티티와 인증 설정은 다른 팀원이 맡았습니다. 4개월 뒤부터는 혼자 이어오고 있습니다. 전체 715 커밋 중 519건이 제 것이고, 성능 측정 디렉터리의 158 커밋은 전부 단독 구간에 만들었습니다.
