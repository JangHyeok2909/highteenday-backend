# 깊게 1. Tomcat 스레드 ↔ HikariCP 커넥션 풀

> 넷 중 가장 중요. 내 1등 숫자 카드(풀 대기 205)가 여기 있고, 이건 인프라가 아니라 **백엔드 기본기**로 분류되는 주제라 모르면 감점이 크다.

## 원리 — 요청 하나의 일생
1. 클라이언트 접속 → OS accept 큐 → Tomcat이 커넥션 수락 (`max-connections`까지 물고 있음)
2. **워커 스레드**가 배정되어 요청 처리 시작 (`max-threads`가 동시 처리 상한, 넘치면 `accept-count` 큐 대기)
3. 처리 중 DB가 필요하면 **HikariCP 풀에서 커넥션 대여** — 풀이 비어 있으면 스레드는 **블로킹 대기** (기본 타임아웃 30초)
4. 쿼리 실행 → 커넥션 반납 → 응답

핵심 문장: **"스레드는 커넥션을 기다리는 동안 아무 일도 못 하면서 응답 시간만 쌓는다. 그래서 계층 간 균형이 절대 규칙이다 — 앞 계층(스레드 400)이 뒤 계층(커넥션 10)보다 크면, 차이만큼이 전부 대기자가 된다."**

병목의 3대 시그니처 (지표로 읽는 법):
- `hikari pending > 0` — 풀 앞에 줄이 생겼다. 이것 하나만으로 경보.
- `획득 시간 p95가 타임아웃값에 수렴` — 대기자 다수가 끝까지 기다리다 실패 중.
- `hikari timeouts > 0` — 30초를 다 기다리고도 못 받아 SQLException으로 터진 요청 수.

## 내 실측
- 설정: Tomcat max-threads **400** / HikariCP **10** (의도적 통제 변수 — BTL-002 가설, EXP-002로 증명 예정이던 것)
- 대규모(200VU) 붕괴 실행: **pending 최대 205 / 획득 p95 = 정확히 30,000ms(=타임아웃) / 타임아웃 5,316건**
- 같은 조건 소규모(15VU): pending 0, 획득 p95 0.95ms — 부하가 임계 아래면 멀쩡하다는 대조군까지 보유

## 30초 답변 스크립트
"Tomcat 스레드가 400인데 DB 커넥션이 10개였습니다. 부하를 올리자 스레드 205개가 풀 앞에 줄을 섰고, 커넥션 획득 p95가 타임아웃값인 30초 그 자체로 찍혔습니다 — 대기 시간이 고스란히 응답 시간에 가산된 겁니다. 교훈은 스레드를 늘리는 게 아니라 병목 뒤 자원의 처리량에 앞 계층을 맞춰야 한다는 것이고, 그 전에 요청당 쿼리 수 903개를 줄이는 게 순서라고 판단했습니다."

## 예상 꼬리질문
- **"풀을 100으로 늘리면 되잖아요?"** → DB 코어는 한정 — 커넥션이 많아지면 DB 쪽 컨텍스트 스위칭·락 경합으로 오히려 전체 처리량이 떨어질 수 있다. HikariCP 권장은 `core*2 + spindle` 수준의 작은 풀. 그리고 우리 병목의 진짜 원인은 풀 크기가 아니라 **커넥션 점유 시간**(요청당 903쿼리) — 분자를 줄이는 게 먼저.
- **"그럼 Tomcat을 줄이면?"** → 대기가 풀 앞에서 accept 큐로 이동한다. 스레드 밖에서 기다리게 하면 스레드당 메모리(스택 ~1MB)와 컨텍스트 스위칭 낭비가 줄어든다. 단 큐가 넘치면 connection refused — 어디서 기다리게 할지의 선택 문제.
- **"커넥션 점유 시간을 줄이는 다른 방법은?"** → 트랜잭션 범위 축소(트랜잭션 밖 외부 호출 제거 — 우리는 S3 호출이 트랜잭션 안에 있는 게 알려진 이슈), OSIV off, readOnly 분리.
- **"pending을 어떻게 모니터링하나요?"** → Micrometer가 hikaricp_connections_pending을 내보내고, 우리 회귀 규칙에서 pending>0 warn, timeouts>0 fail(게이트).

# 깊게 2. CPU Throttling (컨테이너 CPU 한계)

> 붕괴 실행의 두 번째 범인(실측 ~100%). "컨테이너 환경 p99 급등의 최대 원인"이라는 한 문장 때문에 우리 회귀 규칙에서 몇 안 되는 게이트(gate:true)다.

## 원리
- 컨테이너 CPU 한계는 "코어 2개를 배정"이 아니라 **cgroup의 기간(period, 기본 100ms)당 사용 쿼터(quota)**다. `cpus: 2.0` = 100ms마다 200ms어치 CPU 시간.
- 쿼터를 다 쓰면 **다음 기간까지 모든 스레드가 강제 정지(throttled)**.
- 함정: **평균 사용률이 50%여도 버스트 순간마다 정지가 걸린다.** GC, 트래픽 스파이크, 스케줄러 배치 같은 순간 폭발이 기간 초반에 쿼터를 소진하면 나머지 시간은 얼어 있다 → 그 요청들의 응답만 튄다 → **평균은 멀쩡한데 p99만 나빠지는** 전형적 패턴.

핵심 문장: **"throttling은 사용률 지표에 안 보이고 꼬리 지연으로만 나타난다. 그래서 사용률(%)이 아니라 throttled 비율을 따로 봐야 한다."**

## 내 실측
- 앱 컨테이너 2.0 vCPU 제한. 붕괴 실행에서 **throttledPct ~100%** — 사실상 상시 정지 상태로 실행됨.
- 소규모 실행 대조: CPU 0.24코어(12%), throttled 0.075% — 여유.
- 회귀 규칙: throttledPct warn 1% / fail 10% (gate) — "1%만 넘어도 경고"로 둔 이유가 위 원리.
- 보조 스토리: 시드(BCrypt 2만 회)가 CPU 병목이라 **시드 전용 오버라이드에서만 6.0 vCPU로 올리고, 측정 시엔 2.0으로 복귀** — "측정 조건 통제" 소재.

## 30초 답변 스크립트
"컨테이너 CPU 한계는 기간당 쿼터라서, 평균 사용률이 낮아도 버스트 순간마다 강제 정지가 걸립니다. 정지당한 요청만 느려지니 평균은 멀쩡하고 p99만 나빠지는 게 특징입니다. 그래서 저는 사용률과 별개로 throttled 비율을 회귀 게이트로 뒀고, 대규모 실행에서는 이 값이 사실상 100% — 컨테이너가 상시 정지 상태로 돌고 있었다는 게 수치로 나왔습니다."

## 예상 꼬리질문
- **"어떻게 줄이나요?"** → ① 한계 증설 ② CPU 소모 자체 절감(우리 경우 쿼리 903개, BCrypt) ③ 버스트 원인 분산(스케줄러 시간대 분산) ④ k8s라면 limit 제거/완화 + request로 스케줄링(limit 없는 burstable) — 개념만 알면 충분.
- **"어디서 보나요?"** → cAdvisor가 내는 cgroup 카운터(throttled 기간/전체 기간 비율). 세부 구현까지는 안 물어봄.

# 깊게 3. JVM 메모리 — 힙 vs 비힙 vs 컨테이너 한계

> "메모리 한계 1.5G→2.5G 조정" 커밋 스토리를 말하려면 필요한 만큼만.

## 원리
- JVM 메모리 = **힙**(-Xmx) + **비힙**: 메타스페이스(클래스), **스레드 스택(스레드당 ~1MB — Tomcat 400스레드면 그것만 수백 MB)**, GC 자기 구조체, 다이렉트 버퍼, JIT 코드 캐시.
- 따라서 **컨테이너 한계는 힙보다 충분히 커야 한다.** 힙 1G = 컨테이너 1G가 아니라, 힙 1G + 비힙 수백 MB + 여유.
- `-Xms = -Xmx` 고정 이유: 런타임 힙 리사이즈로 인한 측정 노이즈 제거 — 성능 측정에서 힙은 통제 변수.
- 메모리 압박의 스펙트럼: 여유 → **커널 강제 회수(memory.events의 max 카운트 — 한계에 부딪혀 커널이 회수하며 버티는 중)** → OOM Kill. **"OOM Kill 0회"가 "안전"의 증거가 아니다.**
- anon vs file: anon(익명 메모리) = 프로세스 자체(JVM), file = 페이지 캐시(회수 쉬움). anon이 한계에 근접하면 진짜 위험.

## 내 실측 (스토리로 외울 것)
- 힙 1G 고정 + 컨테이너 한계 1536m로 운영 → 실측 anon 1518MB/file 4MB — **여유가 사실상 0**. OOM Kill은 0이었지만 **커널 강제 회수 992회**로 버티는 상태.
- 측정 비용이 더 컸다: **저장된 71개 실행 중 43개가 메모리 포화 100%로 기록** → 지표가 상시 빨간불이라 신호로서 사망.
- 조치: 한계만 2560m로 증설, **힙은 1G 유지** — GC 오버헤드가 최대 0.18%로 힙은 제약이 아니었고, 힙을 건드리면 이전 실행과 비교가 깨지므로.
- 커밋에 명시한 경고: "이 변경으로 SUT가 바뀌었으니 이전 실행과 비교 불가" — 비교 가능성 원칙의 실례.

## 30초 답변 스크립트
"힙 1기가에 컨테이너 한계를 1.5기가로 뒀는데, 실측하니 익명 메모리가 1.52기가 — 스레드 스택과 메타스페이스 같은 힙 밖 메모리까지 치면 여유가 0이었습니다. OOM Kill은 없었지만 커널이 992번 강제 회수를 하며 버티는 상태였고, 실행의 60%가 메모리 포화 100%로 찍혀 지표가 신호 구실을 못 했습니다. 힙은 GC 오버헤드 0.2% 미만이라 제약이 아니어서 그대로 두고 컨테이너 한계만 2.5기가로 올렸습니다."

## 예상 꼬리질문
- **"왜 힙을 안 줄였어요?"** → GC 지표상 힙은 문제가 아니었고, 고정 힙이 run-to-run 노이즈를 없애는 통제 변수라서.
- **"컨테이너에서 JVM이 한계를 인식하나요?"** → 최신 JVM은 컨테이너 인식(cgroup 한계 기준으로 기본 힙 계산). 우리는 명시적 -Xmx라 무관 — 한 줄이면 충분.

# 깊게 4. GC 지표 읽기 (배제 진단 수준)

> 튜닝 지식 불필요. "GC는 범인이 아니었다"를 지표로 말하는 수준이 목표.

## 원리
- G1 한 문단: 힙을 리전으로 나누고, 목표 pause(-XX:MaxGCPauseMillis=200) 안에 young/mixed 수집을 맞추려는 수집기. Java 17 기본.
- 보는 지표 2개:
  - **pause max** — 최악의 정지 시간. 정지 중 전 요청이 멈추므로 p99에 직결. (우리 임계: warn 200ms / fail 500ms)
  - **오버헤드%** — 전체 시간 중 GC가 쓴 비율. 빈도×시간을 하나로 합친 지표. (warn 5% / fail 10%) — "pause는 짧은데 너무 자주"도 잡아준다.
- 진단 논리: **p99가 튀었을 때 GC pause가 같이 안 튀었으면 GC는 용의선상에서 제외** — 이 배제가 GC 지표의 주 용도.

## 내 실측
- 정상 실행: 오버헤드 0.2% 미만, pause max 12ms — 완전 여유.
- 붕괴 실행조차: 오버헤드 2.68%, pause max 296ms — 나쁘지만 주범 아님(주범은 풀 대기 30초와 throttling). **"붕괴 상황에서도 GC를 범인에서 배제할 수 있었다"**가 포인트.
- 환경: GC 로그 상시 기록(rotate) + JFR 상시 — "느려졌을 때 소급 분석할 원자료를 미리 깔아둔다"는 한 줄 소재.

## 30초 답변 스크립트
"GC는 pause 최대값과 오버헤드 비율 두 개로 봅니다. 저희는 붕괴된 실행에서도 오버헤드 2.7%, pause 최대 296ms라 GC는 주범이 아니었고 — 진짜 범인인 커넥션 풀 대기 30초, CPU throttling 100%와 규모 자체가 달랐습니다. 성능 진단에서 GC 지표의 절반은 이런 배제 용도라고 생각합니다."

# 얕게 5. Prometheus 관측 구조 (그림 한 장 수준)

"측정 시스템을 만들었다"고 하면 수집 구조는 물어볼 수 있다. 이 그림 하나로 끝:

```
[Spring 앱]--Micrometer-->/actuator/prometheus  ─┐
[mysqld-exporter]  MySQL 상태를 메트릭으로 변환   ─┤ ← Prometheus가 5초마다
[redis-exporter]                                 ─┤    pull(스크레이프)해서
[cAdvisor]         컨테이너 cgroup 지표           ─┘    시계열로 저장
                                                        ↓
                                             Grafana 대시보드 / 수집 스크립트가 조회
```

알아둘 것 3개:
1. **pull 모델** — 서버가 밀어넣는 게 아니라 Prometheus가 긁어감. 대상이 죽으면 스크레이프 실패로 드러남.
2. **counter vs gauge** — counter(누적 증가: 요청 수, GC 횟수)는 increase/rate로 변화량을, gauge(현재값: heap, active 커넥션)는 max/avg로 본다. 이 구분만 알면 PromQL 문법은 몰라도 됨.
3. **재료 하나**: 죽은 컨테이너의 시계열이 산 것과 합산돼 "메모리 포화 227%"라는 물리적으로 불가능한 수치가 리포트에 실렸던 사건 — 쿼리를 max로 감싸 수정하고, 원자료를 보관한 덕에 저장된 61개 실행을 소급 재수집했다. (측정 신뢰성 질문에 재사용 가능한 만능 스토리)
