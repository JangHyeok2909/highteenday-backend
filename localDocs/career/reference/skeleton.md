# 모범 원고의 뼈대

기준 원고는 김재녕의 이력서 [jaenyeong-about.md](jaenyeong-about.md)다. 아래는 그 원고에서 잰 자리와 분량이다. 문장 규칙이 아니고, 문장은 본인이 쓴다.

## 1. 잰 값

Experience 절의 항목 18개를 2026-09-06에 스크립트로 셌다. 본문 글자는 공백을 빼고 **8,112자**다. 7년 경력 전체가 이 안에 있다.

| 무엇 | 값 |
|---|---|
| 항목 하나의 줄 수 | 최소 2, 중앙값 8, 최대 14 |
| 항목 하나의 불릿 수 | 최소 1, 중앙값 4, 최대 5 |
| 불릿 밑에 들여쓴 이유 줄 | 불릿 59개 중 23개에 있음 |
| 불릿 길이 | 중앙값 56자, 최대 132자 |
| 제목 길이 | 중앙값 61자 |
| 숫자가 들어간 불릿 | 72개 중 28개 |
| 그림 · 상호참조 · 교훈 문장 · 줄표 | 전부 0 |
| 표 | 자격증 표 하나 |
| 굵게 | 34곳. 전부 "설명:", "개발 환경:", "Contribute" 같은 라벨 |
| 링크 | 5개 |
| "다."로 끝나는 불릿 | 72개 중 0개 |

## 2. 항목 하나의 자리

```
##### {무엇을 했나} ({N개월} / {YYYY.MM~YYYY.MM})
**설명:** 왜 했나, 무엇을 위해. 한 줄.
**개발 환경:** 한 줄.

* 한 일. 한 줄에 주장 하나. 명사형으로 끝난다.
  왜 그랬나, 무엇이 원인이었나. 들여쓴 한 줄. 필요한 불릿에만 붙는다.
* ...(불릿 2~5개)

> **Contribute**
> 팀에 남긴 것. 1~4줄.
```

원고에서 그대로 옮긴 예다. 트러블슈팅 하나가 두 줄이다.

> * API 호출 트래픽 증가 시 API 서버의 K8s 파드 OOMKilled(137) 에러로 발생한 파드 다운 장애 개선
>   스프링 서버의 메모리 max 설정값이 K8s 파드의 메모리 limit 설정값보다 높아 발생

첫 줄이 증상과 결과, 둘째 줄이 원인이다. 수치는 불릿 안에서 전후 쌍으로만 나온다.

> * 기존 의료 데이터 약 1만 건을 FHIR 포맷으로 변환, 네이버 FHIR 서버로 일괄 전송하는 기능 구현
>   전송 데이터의 조회/변환 시(약 50초 소요) 발생하는 DB READ Timeout(30초)을 코틀린 컬렉션의 parallel(CommonThreadPool)과 스프링 @Async를 활용해 처리(약 10초)

## 3. 문서 전체의 자리

1. 이름과 연락처 2줄
2. 소개 3~4문장. 연차, 어디서 무엇을 해 왔나, 관심사
3. Skill 5줄
4. Career. 회사마다 제목 1줄과 문장 1~2개
5. Experience. 회사 → 항목. 최근 것이 먼저
6. Activity, Learn, Education, License

깊이는 Experience 항목의 들여쓴 줄에서 나온다. 그림과 표 없이 낸다.

## 4. 포트폴리오에 옮길 때 넓히는 자리

이력서보다 깊어야 하니 아래 자리만 넓힌다. 이 표의 오른쪽은 원고에서 잰 값이 아니고 우리가 정한 허용치다.

| 자리 | 이력서 원고 | 포트폴리오에서 |
|---|---|---|
| 트러블슈팅 하나 | 항목 1개, 8줄 안팎 | 항목 1개, 반 쪽~1쪽 |
| 불릿 밑 들여쓴 줄 | 1줄 | 1~3줄 |
| 캡처 | 0 | 항목당 1장. Grafana 패널, k6 출력, 실패한 테스트 출력 |
| 표 | 0 | 항목당 1개까지. 전후 비교 |
| 제목 | 무엇을 했나 + 기간 | 같다. 수치는 불릿에 둔다 |

## 5. 자리 시연

축약본 4장의 본인 초안을 이 자리에 얹으면 아래처럼 된다. 문장은 초안에서 잘라 옮겼고, 원고에 그대로 쓰지 않는다. 제목은 본인이 쓴다.

```
##### {제목} (2026.08)
**설명:** 같은 코드, 같은 데이터셋인데 며칠 뒤 다시 재니 세션 간 차이가 40%까지 벌어짐
**개발 환경:** k6, Spring Boot, HikariCP, Grafana

* 호스트 CPU 주파수, 코어 배치, 하이퍼바이저 스케줄링, 전원 관리, 가상 디스크 확인. 원인을 밝혀내지 못함
* 부하가 적은 시나리오는 편차 10% 안. 자원이 포화 상태일 때 편차가 극대화되는 것은 아닌지 의심
  도착률을 초당 3·4·5요청으로 바꿔 다시 잼. 부하를 25% 올리면 p95가 30배
* 사용자 수 200 고정 모델에서는 응답 시간이 사용자 수 ÷ 처리량. 처리량 변동이 그대로 응답 시간 편차가 됨
* 부하 모델을 도착률 고정으로 변경. 판정용 부하는 포화되지 않는 초당 4요청으로 고정
* 커넥션 대기, CPU 상한 도달, CPU 사용률, 커넥션 획득 시간 비중, 도달률 다섯 신호로 포화 여부를 실행마다 판정
  포화 실행에서는 p95 10,685ms 중 6,364ms가 커넥션 대기. 그 실행의 지연값은 인용하지 않음
* 4시간 간격 두 세트로 검증. 유휴 CPU 벤치는 18% 느려졌고 앱 p95 변화는 1.5%

[캡처: Grafana 커넥션 대기 패널]
```
