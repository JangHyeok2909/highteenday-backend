## 0. 결론 — 다섯 문장

**첫째, 이 공고는 연차를 묻지 않는 대신 "어떻게 일하는가"를 묻는다.** 필수 요건 6줄 중
기술 요건은 마지막 1줄뿐이고, 나머지 5줄은 전부 문제를 정의하고 가설을 세우고 데이터로
판정하는 **작업 방식**이다. 당근의 다른 백엔드 공고 5건이 전부 3~5년을 요구하는 것과
대조된다.

**둘째, 이 지원의 승패는 재프레이밍 하나에 달려 있다.**
`performance/` 를 **"성능 측정 시스템"** 으로 소개하면 우대 사항 1번(대규모 트래픽 분산
시스템)에서 죽는다 — 나에게 그 규모가 없기 때문이다. 같은 것을 **"실험 판정 시스템"** 으로
소개하면 담당 업무 3번(*"실험 한 번의 비용을 낮추는 시스템을 만들어요"*)과 우대 사항
3번(*"A/B 테스트 등 데이터 기반 실험을 설계하고 검증해 본 분"*)에 **정면으로 걸린다.**
그리고 이건 억지 전이가 아니다 — 4장에서 근거를 댄다.

**셋째, 그 재프레이밍의 실무 비용은 반나절이다.** 새 이력서가 아니다. 토스판 9줄 중
**3번 줄(S-3 CV/MDE)의 언어를 바꾸고 AI 활용 한 줄을 추가하면 끝난다.** 1·2번 줄
(S-1 오진 사건, N-1 개선 완주)은 그대로 쓴다.

**넷째, 실제 탈락 지점은 서류가 아니라 직무 면접의 시스템 설계다.** [후기] 기준으로
라이브 코딩은 *"상당히 쉬운 난이도"* 였고, 탈락자가 스스로 꼽은 이유는 시스템 설계
준비 부족이었다. 나는 그 준비가 0이다. **그러나 나에게는 남들에게 없는 재료가 있다 —
자기 서비스에서 직접 잰 숫자.**

**다섯째, 준비의 대부분은 이미 되어 있고 남은 것은 번역과 리허설이다.** 새로 구현할 것은
없다. Go·Kafka·Kubernetes를 지금 배우는 것은 **명백한 오답**이다(9장).

# 2. 팀이 실제로 무엇을 만드는가 — 공고 밖 정보

**공고만 읽고 지원하면 다른 지원자와 같은 정보를 갖는다.** 면접에서 차이를 만드는 것은
이 장의 내용이다. 전부 당근이 공개한 자료다.

## 2.1 Feed Infra 팀이 만든 세 개의 서비스 [블로그]

| 컴포넌트 | 하는 일 |
|---|---|
| **Feed Mixer** | 클라이언트 요청을 받아, 추천 모델을 거친 개인화 콘텐츠와 **아직 개인화를 붙일 만큼 크지 않은 서비스의 콘텐츠**를 섞고, 피드 정책에 따라 **페널티**를 적용한다 |
| **Feed Entity Service** | 당근의 모든 콘텐츠 제공자로부터 **피드에 노출될 수 있는 모든 엔티티를 수집·저장**하는 중앙 저장소 |
| **Feedback Service** | 콘텐츠에 대한 **명시적 피드백**(예: "이 글 숨기기")을 저장 |

**팀의 책임 범위 [블로그]: 추천 기능 자체를 뺀, 피드에 콘텐츠를 싣고 내보내는 모든 기술 요소.**

[판단] 이 구조는 **읽기 경로가 곧 제품인 시스템**이다. 여러 소스에서 모아서(fan-in),
정책을 적용해 조합하고, 지연 예산 안에 응답해야 한다. **한 소스가 느려지거나 죽었을 때
전체가 어떻게 되는가**가 이 팀의 핵심 문제다 — 6장 시스템 설계 준비의 출발점이 여기다.

## 2.2 Server Driven UI — 피드 엔티티와 뷰타입 [블로그]

- **피드 엔티티** = 실제 콘텐츠(중고거래 게시글, 알바 게시글 등)
- **뷰타입** = 그 콘텐츠를 **어떤 모양으로 보여줄지**

기존에는 아이콘 하나를 바꾸려 해도 **클라이언트 앱 배포를 기다려야 했다.** 서버가 뷰타입을
직접 통제하게 만들어 **앱 배포 없이 피드의 모양을 바꾸고 실험을 돌릴 수 있게** 했다.
파편화돼 있던 뷰타입을 통일해 조직 간 협업 효율도 올렸다.

[판단] **콘텐츠와 표현을 분리해 실험 비용을 낮춘 것**이다. 내가 한 일과 같은 형태의
판단이 여기 있다 — `performance/regression/rules.json`으로 **판정 규칙을 코드에서 빼
파일로 옮긴 것**(S-4)이 정확히 같은 종류의 결정이다. *"코드 수정 없이 이 파일만 고쳐서
기준을 바꾼다."* **이 대응은 면접에서 쓸 수 있는 카드다.**

## 2.3 피드실의 실험 문화 — 숫자가 있다 [블로그]

| 사실 | 값 |
|---|---|
| 홈 피드를 거치는 사용자 | 당근 앱을 켜는 **99%** |
| 개인화 도입 후 클릭수 | **133% ~ 456% 증가** |
| "숨기기" 기능 사용량 | 부정 피드백 학습 후 **40% 감소** |
| LLM 자동 분류 | 세부 카테고리 **약 1,000개** |
| 실험 주체 | *"데이터 분석가나 PM만이 아니라 **엔지니어까지 대부분이 각자 주도해서 실험을 열어요**"* |
| 실험 종류 | **A/A 테스트** 활용 — *"사용자가 보기에는 똑같지만 시스템이 더 효율화되는 방향"* |
| 안정성 태도 | *"다른 서비스가 다 죽어도 우리는 죽지 않아야 된다"*, *"겹겹이 대비 장치"* |
| 문서 문화 | *"PRD나 테크 스펙, 실험문서, 배포 결정 문서를 작성해서 누구나 문서만 보더라도 업무 맥락을 이해"* |

**여기서 반드시 읽어야 할 세 가지.**

**① A/A 테스트를 쓴다는 것은 이 조직이 "측정이 거짓말하는 경우"를 안다는 뜻이다.**
A/A 테스트는 **처치가 없는데도 차이가 나오는지**를 보는 것 — 즉 실험 판정계의 거짓 양성률을
재는 절차다. **내가 S-2에서 겪은 사건(대조군이 틀려 +59,000% 거짓 회귀)과 정확히 같은
문제를 방어하는 장치다.** 이 조직은 내 이야기를 이해할 준비가 되어 있다.

**② 엔지니어가 직접 실험을 연다.** 그래서 R2·R3이 필수 요건인 것이고, "시키는 걸
구현하는 사람"은 이 팀에 필요하지 않다.

**③ 문서로 맥락을 남기는 것이 일하는 방식이다.** 내 `localDocs/`·`performance/`·
`docs/defects/` 운영 방식이 **이 조직의 방식과 같은 형태다.** A-4(결함 장부 183건)를
"꼼꼼함"이 아니라 **"비동기로 협업하는 방식"** 으로 말해야 하는 이유다.

# 4. 핵심 전략 — 재프레이밍 하나가 이 지원의 전부다

## 4.1 "성능 엔지니어"로 지원하면 진다

토스 Product 공고에 맞춰 만든 서사는 **R3("장애 경험 및 문제해결")** 를 겨냥한다.
그 언어를 그대로 당근에 가져오면 이렇게 읽힌다.

> "부하 테스트 도구를 만들었고, 지표를 165개 수집하고, 병목을 찾아 고쳤다."

**이 문장이 당근 공고의 어느 줄에 걸리는지 보라.** 걸리는 곳은 P1(대규모 트래픽)뿐이고,
**나는 거기서 진다.** 4.6만 RPS를 다루는 팀에게 단일 인스턴스 성능 실험은 규모로
경쟁이 되지 않는다. 그리고 W1(대규모 서빙) 외의 담당 업무 세 줄과는 아예 접점이 없다.

## 4.2 "실험 판정 엔지니어"로 지원하면 이긴다

같은 자산을 이렇게 소개하면 걸리는 자리가 완전히 달라진다.

> "성능 개선 실험을 돌리는 시스템을 만들었는데, **그 시스템이 나에게 거짓말을 했다.**
> 대조군을 잘못 골라 부하 13배·데이터 100배 차이를 '+59,000% 회귀'로 보고했고,
> 포화 상태에서 잰 값을 애플리케이션 지연으로 읽어 닷새를 날렸다.
> 그래서 **실험 결과를 믿어도 되는 조건**을 코드로 정의했다 —
> 대조군 유효성 판정, 최소 검출 가능 효과(MDE) 산출, 해석 불가 실행의 자동 격리."

| 이 문장이 걸리는 곳 | 공고 원문 |
|---|---|
| **W2** | *"가설을 세우고, 실험을 설계·구현하고, **데이터로 검증**하는 전 과정"* |
| **W3** | *"**실험 한 번의 비용을 낮추는 시스템**을 만들어요"* |
| **R2** | *"직접 문제를 정의하고 가설을 세워"* |
| **R3** | *"실험으로 검증하고, **데이터를 근거로 다음 판단**"* |
| **P3** | *"**A/B 테스트 등 데이터 기반 실험을 설계하고 검증**해 본 분"* |

**공고의 다섯 줄에 동시에 걸린다.** 그리고 이건 소재를 바꾼 게 아니라 **같은 소재의
언어를 바꾼 것**이다.

## 4.3 번역표 — 문서의 표현을 공고의 언어로

| 지금 내 문서의 표현 | 당근에 쓸 표현 | 걸리는 줄 |
|---|---|---|
| 회귀 판정기가 잘못된 기준선을 골랐다 | **대조군이 유효하지 않으면 실험 결과는 의미가 없다.** 그 유효성을 코드로 판정하게 했다 | P3·W3 |
| CV(변동계수) 측정 | **아무것도 바꾸지 않았을 때의 자연 편차**를 먼저 쟀다 | P3 |
| MDE 확정 | **이 실험이 검출할 수 있는 가장 작은 차이**를 정의하고, 그보다 작은 변화는 개선으로 인정하지 않게 했다 | P3·R3 |
| 포화 판정기(`saturation.js`) | **측정 결과를 해석하면 안 되는 조건**을 실행마다 자동으로 붙였다 | W3·R3 |
| 성능 측정 시스템 | **실험 한 번의 비용을 낮추는 시스템** | W3 |
| `rules.json`으로 규칙 외부화 | **판정 기준을 코드에서 분리해 배포 없이 바꾼다** | W3 (SDUI와 같은 종류의 판단) |
| 요청당 쿼리 112 → 3.9 | **서빙 비용을 데이터 크기와 무관하게 만들었다** | W1 |
| 결함 장부 183건 운영 | **문서로 맥락을 남기는 방식으로 일한다** | R4·문화 |

## 4.4 이 재프레이밍이 정직한 이유

**억지 전이가 아니라는 근거가 세 가지 있다.** 면접에서 반드시 확인당하므로 미리 정리한다.

**① S-2는 문자 그대로 대조군 선택 문제였다.** [resume-assets.md](../resume-assets.md) §4 S-2에
이미 이렇게 적혀 있다 — 회귀 판정은 두 개의 다른 질문에 답해야 하는데,
*(a) 이력상 직전 실행은 무엇인가*(시간축 질문)와 *(b) 이 실행의 **대조군으로 유효한**
실행은 무엇인가*(**실험 설계 질문**)를 하나로 취급한 것이 원인이었다. **"실험 설계 질문"
이라는 말을 내가 이미 쓰고 있었다.** 당근 언어로 번역할 필요조차 없다.

**② S-3은 검정력 문제 그 자체다.** *"p95가 20% 나빠지면 실패"* 라고 말하려면 **아무것도
바꾸지 않고 반복했을 때의 편차가 20%보다 작아야 한다.** 이건 A/B 테스트에서 표본 수와
MDE를 정하는 절차와 같은 논리다. 게다가 나는 **자기 확정치(CV 3.12%)를 스스로 무효
처리**한 기록까지 갖고 있다 — 그 값이 포화 상태에서 측정된 것이었기 때문이다.

**③ 당근이 A/A 테스트를 쓴다는 사실이 이 대응을 확인해 준다.** A/A 테스트는 처치가 없는데
차이가 나오는지 보는 것, 즉 **판정계의 거짓 양성률 측정**이다. 내가 `noiseFloor`를
재산정한 이유(S-4)와 같다 — 순수한 노이즈가 *"평균 93ms ▲ +26.4%"* 로 리포트에 실리는
것을 막기 위해서였다.

## 4.5 하면 안 되는 과장 — 여기서 무너지면 전부 무너진다

| 쓰면 안 되는 말 | 대신 쓸 말 |
|---|---|
| "A/B 테스트를 설계·운영했다" | **"A/B 테스트 경험은 없습니다.** 다만 실험 결과를 신뢰할 수 있는 조건을 판정하는 문제를 성능 실험에서 직접 겪고 코드로 해결했습니다" |
| "대규모 트래픽을 처리했다" | 쓰지 않는다 |
| "실험 플랫폼을 만들었다" | "실험을 **판정하는** 부분을 만들었습니다. 실험 배정·분기는 없습니다" |
| "개인화/추천을 해봤다" | 쓰지 않는다 |

**이 표를 지키는 것이 4.2의 전략보다 중요하다.** [resume-assets.md](../resume-assets.md) 도입부에
적힌 대로, 불합격 사례의 직접 원인은 *"겉만 번지르르하고 깊이가 없었다"* 였다.
**전이 논리는 한 뎁스만 파고들면 진위가 드러난다.** 정직하게 경계를 먼저 그으면
전이 논리 전체가 신뢰를 얻는다.

# 5. 서류 — 무엇을 어떻게 쓰는가

## 5.1 결론: 새 이력서가 아니다. 3번 줄 교체 + 1줄 추가다

[resume-assets.md](../resume-assets.md) §7의 3축 9줄을 그대로 쓰되 아래만 바꾼다.

| 순서 | 토스판 | **당근판** | 왜 |
|---|---|---|---|
| 1 | S-1 포화 오진 → 판정 자동화 | **그대로** | 오진 → 반박 → 재발 방지 서사가 R2·R3를 한 줄에 채운다 |
| 2 | N-1 댓글 N+1 개선 | **그대로.** 단 첫 수치를 **요청당 쿼리 수**로 | *"최적화하는 데 재미를 느끼는 분"*[블로그]에 직결 |
| 3 | S-3 CV/MDE | **전면 재작성** → **"실험 판정 기준 설계"** 로. S-2(대조군 게이팅)와 한 묶음 | **P3·W3 직격. 여기가 당근판의 전부다** |
| 4~6 | I-1·I-2·I-3 정합성·동시성 | **그대로.** 프레이밍만 *"다른 서비스가 다 죽어도 우리는 안 죽는다"* 쪽으로 | 피드의 안정성 문화[블로그] |
| 7 | N-4 커서 페이징 | 그대로 | 서빙 비용 |
| 8 | A-4 결함 장부 183건 | **프레이밍 변경** → "꼼꼼함"이 아니라 **"문서로 맥락을 남기는 협업 방식"** | R4 · 피드실 문서 문화 |
| 9 | — | **신규: AI 활용 한 줄** | **R5 (필수 요건)** |

**작업량은 반나절이다.** 이건 이 문서에서 가장 실용적인 결론이다 — 당근 때문에 일정을
새로 짤 필요가 없다.

## 5.2 3번 줄 초안

> **실험 판정 기준 설계 —** 개선 여부를 판정하기 전에 **아무것도 바꾸지 않은 상태의
> 반복 편차(변동계수)** 를 먼저 측정해 최소 검출 가능 효과를 정의하고, 그보다 작은 변화는
> 개선으로 인정하지 않는 규칙을 도입. 또한 부하·데이터셋 조건이 다른 실행이 대조군으로
> 선택되어 **+59,000% 거짓 회귀**가 보고된 사건 이후, 비교 가능한 실행만 대조군이 되도록
> 조건을 선언적 표로 분리해 게이팅. 초기 확정치는 포화 상태에서 측정된 것으로 판명돼
> **스스로 무효 처리하고 재산정**.

## 5.3 9번 줄(AI) 초안 — 방어선을 문장 안에 넣는다

> **AI 도구 활용 —** 구현은 AI 에이전트에 맡기고 **판단과 검증을 직접 한다.** 예: 댓글
> 목록 최적화에서 구현안 5가지(패치 조인 / `@BatchSize` / 전역 배치 설정 / `@EntityGraph` /
> DTO 프로젝션)를 **쿼리 수와 폭발 반경 기준으로 비교해 직접 선택**하고, 버린 이유를
> 문서에 남김. 선택한 안이 실제로 동작하는지는 **패치 조인을 제거하면 실패하는 음성 대조
> 테스트**로 고정.

**이 문장이 R5의 모범 답안인 이유:** *"AI를 씁니다"* 는 누구나 쓴다. **무엇을 맡기고
무엇을 직접 판정하는지 경계를 그은 사람**은 드물다. 근거는 실재한다 —
`performance/optimizations/OPT-002-comment-author-fetch-join.md` §2-3의 대안 5개 비교표와
§3의 음성 대조 테스트.

## 5.4 문장 규칙 [후기 기반]

당근 전형 회고의 핵심 조언은 **"공고 키워드를 자기 경험과 1:1로 매칭"** 이었고, 실제로
그 방식으로 쓴 이력서가 면접 질문으로 그대로 이어졌다.

1. **공고의 단어를 그대로 쓴다.** "성능 측정"이 아니라 **"실험으로 검증"**, "회귀 판정기"가
   아니라 **"데이터를 근거로 판단"**.
2. **결과만이 아니라 맥락과 과정을 쓴다.** [후기]가 지목한 그 지점이다.
3. **숫자 앞에 사건을 둔다.** "112 → 3.9"보다 "쿼리가 코드에 보이지 않는 곳에서 나가고
   있었다"가 먼저다.
4. **A to Z로 아는 것만 적는다.**

# 6. 전형 대비 — 여기가 실제 관문이다

## 6.1 후기가 알려주는 것 [후기 · 표본 1건]

| 단계 | 형식 | 내용 | 결과 |
|---|---|---|---|
| 화상 | **1:1, 약 1시간 20분** | 이력서 기반 질문 + **라이브 코딩** | 50분 뒤 합격 통보 |
| 직무 | **3:1, 약 1시간 30분** | 이력서 기반 질문 + **시스템 디자인** | 2일 뒤 탈락 |

- 라이브 코딩: *"상당히 쉬운 난이도였으나 긴장으로 풀이가 순조롭지 않았다"*, 주석으로
  사고 과정을 설명하며 진행
- 질문 방향: 기술의 **What보다 How·Why**, 프로덕트 관점 포함, 꼬리 질문으로 예상 문제
  상황과 해결 방안을 요구
- **탈락 자평: 시스템 디자인 준비 부족** — *"관련 내용을 자세히 읽어본 적이 없던 상황"*

> **[확인 필요]** 표본 1건이고 팀도 다를 수 있다. 다른 후기에는 *"Database·Web·SpringBoot·Java
> 4개 카테고리 스피드 퀴즈 20문항"* 형식이 언급되지만 인턴 전형으로 보이고 교차 확인이
> 안 됐다. **경향으로만 쓰고 절차 자체는 공고 원문(1.7)을 기준으로 한다.**

## 6.2 라이브 코딩 — 준비 대상은 알고리즘 실력이 아니다

[판단] **난이도가 낮다면 변별점은 정답률이 아니라 "말하면서 푸는 능력"이다.** 후기가
꼽은 실패 요인도 *"긴장으로 순조롭지 않았다"* 였고, 강조한 대응도 *"긴 침묵을 피하고
지금 어디서 막혔는지 설명하는 것"* 이었다.

| 하는 것 | 하지 않는 것 |
|---|---|
| 하루 1시간, 쉬운~중간 난이도 문제를 **소리 내어 설명하며** 푼다 | 어려운 알고리즘 유형 정복 |
| 문제를 받고 **입력·출력·엣지 케이스를 먼저 되묻는 습관** | 암기식 유형 학습 |
| 막혔을 때 **"지금 이 부분이 안 풀립니다, 이렇게 접근해 보겠습니다"** 를 실제로 발화 | 침묵하고 혼자 해결 |
| 화면 공유 + 발화 상태로 **타이머 걸고 리허설** | 페이스 없이 문제 수만 늘리기 |

**비용:** 하루 1시간 × 6주. **알고리즘을 몇 달 준비하는 계획은 이 공고에서는 과투자다.**

## 6.3 시스템 설계 — 실제 탈락 지점이자, 내가 이길 수 있는 자리

**대부분의 지원자는 여기서 "캐시를 붙이겠습니다", "샤딩하겠습니다"를 말한다.
나는 그 다음을 말할 수 있는 거의 유일한 지원자다 — 그게 사실인지 어떻게 판정할 것인가.**

이게 과장이 아닌 이유: 나는 캐시·인덱스·배치를 붙인 뒤 **개선을 주장할 자격이 있는지**를
판정하는 절차(CV → MDE → 대조군 유효성)를 실제로 만들어 봤고, 그 절차가 **내 판단을
반박한 기록**까지 있다.

### 예상 주제 [판단]

팀이 만드는 것이 Feed Mixer·Feed Entity Service(2.1)이므로, 다음 형태가 나올 가능성이
가장 높다.

> **"여러 서비스의 콘텐츠를 모아 개인화 정렬해서 홈 피드를 반환하는 시스템을 설계하라."**

### 준비 방법 — 남의 사례가 아니라 내 프로젝트로 한다

**HighTeenDay의 게시글 목록을 홈 피드 구조로 다시 설계하는 연습**을 한다. 그러면 답변이
읽은 지식이 아니라 **직접 잰 숫자** 위에 선다.

| 설계 논점 | 내가 이미 가진 재료 | 위치 |
|---|---|---|
| **팬인 지연 예산** — 여러 소스 중 하나가 느리면 | 부분적. 타임아웃·폴백 설계 경험 없음 → **보강 대상 1** | — |
| **한 소스 장애 시 전체 붕괴** | **강함.** 스크랩 중복 행 하나가 게시글 상세 전면 장애로 전파된 사건 | `performance/bottlenecks/BTL-012-scrap-toggle-race-duplicate.md` |
| **페이지네이션** | **강함.** OFFSET의 문제와 커서 전환 | `BTL-001-random-pagination.md`, N-4 |
| **캐시와 무효화** | 중간. 스탬피드 진단 완료·미해결 | `BTL-004-cache-stampede.md` |
| **카운터 정합성** | **강함.** lost update 재현 → 원자 증감 | `docs/defects/KI-53-comment-counter-lost-update.md` |
| **멱등성·재시도** | **중간.** 진단 완료·**미구현**. 재시도가 상태를 되돌리는 것을 소스로 확정했고 PUT/DELETE 재설계안까지 적었으나 아직 고치지 않았다. 같은 표의 캐시(BTL-004)와 같은 처지다 — 구현하면 **강함**으로 오른다 | `docs/defects/KI-54-toggle-non-idempotent.md` |
| **조회 비용이 데이터 크기에 비례하는 문제** | **최강.** 112 → 3.9, 상수화 | `performance/optimizations/OPT-002-comment-author-fetch-join.md` |
| **실험 분기를 어떻게 수용하나** | **강함(번역 필요).** 조건 분리·규칙 외부화 | `conditions.js`, `regression/rules.json` |
| **개선을 어떻게 증명하나** | **최강. 다른 지원자에게 거의 없다** | `repeatability.js`, S-3 |

**보강 대상 1(타임아웃·폴백·부분 실패)이 유일한 진짜 공백이다.** 피드는 *"다른 서비스가
다 죽어도 우리는 죽지 않아야 된다"* 는 조직이므로 **여기를 못 말하면 감점이 크다.**
코드로 만들 필요는 없다 — **말할 수 있으면 된다.** 준비 범위: 타임아웃 예산 배분, 부분
응답(degraded response), 서킷 브레이커, 폴백 콘텐츠, 재시도와 폭풍 방지.

> **진행 상황 (2026-09-08).** 이 공백을 실측으로 메우는 계획을
> [resilience-test-plan.md](resilience-test-plan.md)에 적었다. Redis crash/hang 구분(R-01)이
> 첫 실험이고, 일정은 9/14 마감 기준 8장에 있다.

### 산출물 — 그림 3장

1. **요청 경로** — 요청 하나가 어디를 지나 무엇을 읽고 언제 응답하는가
2. **데이터 흐름** — 콘텐츠가 어떻게 수집·저장·조합되는가 (Feed Entity Service 대응)
3. **실패 모드** — 각 지점이 죽었을 때 무엇을 반환하는가

**3번이 핵심이다.** 1·2번은 누구나 그린다.

> **진행 상황 (2026-09-04).** 1번(요청 경로)과 3번(실패 모드)은 포트폴리오에
> 인라인 SVG 로 들어갔다 — 그림 1, **그림 8**(9.1 절). 2번(데이터 흐름)은 구현물이
> 아니라 가정 기반 설계라 포트폴리오에 넣지 않고 별도 문서로 뺐다 —
> [daangn-system-design.md](daangn-system-design.md).

| **당근 하나만 본다** | 이 문서는 당근 전용이다. 다른 지원과의 우선순위는 [military-service-company-ranking.md](../military-service-company-ranking.md) 4장 |
