# 시스템 설계 준비 — HighTeenDay 게시글 목록을 홈 피드로 다시 설계한다

> 만든 날: 2026-09-04 · 대상 전형: **당근 Feed Infra 백엔드 · 직무 면접(시스템 설계)**
> 답하는 질문: **"여러 소스의 콘텐츠를 모아 개인화 정렬해 반환하는 시스템을 설계하라"**
> 를 받았을 때, **내 프로젝트의 실측 위에서** 어떻게 답할 것인가.
> 짝 문서: [daangn-feed-infra.md](daangn-feed-infra.md) 6.3 절이 이 연습을 지시한다.

---

## ⚠️ 이 문서의 성격 — 먼저 읽을 것

**여기 그린 구조는 구현되어 있지 않다.** HighTeenDay 는 단일 소스(게시판 하나)를
조회하는 서비스이고, 피드 조합도 개인화 정렬도 없다.

이 문서는 **"만들었다"가 아니라 "만든 것을 이 구조로 옮기면 어디가 걸리는가"**를 적은
설계 연습이다. 면접에서 말할 때도 그 구분을 먼저 밝힌다.

> "제 서비스는 게시판 하나를 읽는 구조라 피드 조합이 없습니다. 그래서 **이걸 홈 피드
> 구조로 옮기면 어디가 문제가 되는지**를 미리 그려 봤습니다. 실제로 잰 숫자가 있는
> 부분과 아직 모르는 부분을 나눠서 말씀드리겠습니다."

**이렇게 열면 가정이 정직해지고, 뒤에 나오는 실측 수치의 신뢰도가 올라간다.**
반대로 구현한 것처럼 말하면 뎁스 2에서 "그래서 소스가 몇 개였나요"에 무너진다.

## 1. 지금 구조 — 여기는 사실이다

| 항목 | 현재 |
|---|---|
| 목록 엔드포인트 | `GET /api/boards/{boardId}/posts` (`BoardPostController.java:44`) |
| 소스 | **하나** — `posts` 테이블을 `boardId` 로 거른다 |
| 정렬 | 최신순·인기순 등 `SortType`. **개인화 없음** |
| 페이징 | OFFSET 기본, 조건이 맞을 때만 커서(`PostRepositoryCustomImpl.java:116`) |
| 캐시 | 게시판별 목록·개수를 Redis 에 (`board:{id}:posts`, `board:{id}:count`) |
| 별도 랭킹 | 인기글은 Redis ZSET + DB 폴백 (`HotPostService`) |

**즉 이미 "소스 두 개"가 있다** — 게시판 목록과 인기글 랭킹. 둘은 지금 **다른
엔드포인트로 따로 나간다.** 홈 피드는 이 둘을 하나로 합치는 일에서 시작한다.

**핵심은 ②(피드 항목 저장소)를 두는가다.** 지금처럼 요청 때마다 원본 테이블 넷을
조회해 합치면, 소스가 하나 늘 때마다 팬인 지연과 실패 확률이 같이 는다. 정규화된 항목을
미리 쌓아 두면 조회가 **소스 수와 무관**해진다. 대신 **쓰기 경로가 복잡해지고 지연 반영이
생긴다** — 그 교환을 말할 수 있어야 한다.

## 3. 설계 논점별 — 내가 댈 수 있는 근거

| 논점 | 내 재료 | 강도 |
|---|---|---|
| **조합 비용을 항목 수와 무관하게** | 댓글 목록에서 요청당 쿼리가 작성자 수에 비례하던 것을 패치 조인으로 **112 → 3.9 상수화**. 원인이 지연 로딩이라 코드만 봐서는 안 보였고 요청당 쿼리 수 계측을 만들어 찾았다 | **최강** |
| **한 지점의 결함이 전체로 번지는 경로** | 스크랩 토글 경쟁으로 생긴 중복 행 하나가 **게시글 상세 전면 장애**로 커진 사건. 쓰기 결함이 읽기 장애가 됐다 | **강함** |
| **비정규화 값의 정합성** | 댓글 카운터 lost update 를 데이터셋 검증에서 발견(13,284건 불일치) → 원자 증감으로 교체 | **강함** |
| **개선을 어떻게 증명하나** | 반복 세트의 변동계수로 검출 한계를 먼저 정하고, 그보다 큰 변화만 개선으로 인정. p95 −40.1% 는 한계(16%)의 2.5배 | **최강 · 차별점** |
| **실험 분기를 서빙에 수용** | 실행 조건을 선언적으로 분리(`conditions.js`)하고 판정 규칙을 코드 밖으로(`rules.json`) 뺀 경험 — **번역 필요** | 중간 |
| **페이지네이션** | OFFSET 비용을 진단하고 단일 소스 커서를 구현. **복합 커서는 미해결** | 중간 |
| **팬인 타임아웃·폴백** | **공백.** Redis 는 폴백 두 층이 있지만 DB 는 없다 | **약함 — 정직하게 말한다** |

## 4. 못 답하는 것 — 미리 정해 둔 답

**질문이 오면 이렇게 답한다.** 모르는 것을 아는 척하면 그 자리에서 끝난다.

| 질문 | 답 |
|---|---|
| "소스가 20개면 어떻게 하나요" | 겪어 보지 않았습니다. 다만 제 프로젝트에서 **비용이 데이터 크기에 비례하면 꼬리부터 무너진다**는 것은 실측으로 봤습니다. 소스 수에 비례하는 구간을 상수로 만드는 것이 먼저라고 봅니다 |
| "타임아웃 예산은 어떻게 나누나요" | 설계해 본 적이 없습니다. 지금 제 서비스는 DB 커넥션을 **30초** 기다린 뒤 500 을 냅니다 — 기본값을 그대로 쓰고 있었다는 걸 실패 모드를 그리면서 알았습니다 |
| "개인화 정렬은 어떻게" | ML 쪽은 모릅니다. 다만 **정렬 규칙을 코드 밖으로 빼서 배포 없이 바꾸는** 구조는 판정 규칙(`rules.json`)에서 해 봤습니다 |
| "캐시 히트율은" | 조합 결과를 개인화한 뒤 캐시하면 히트율이 낮아질 것 같습니다. 항목 단위 캐시와 조합 결과 캐시를 나누는 쪽을 먼저 보겠습니다. **측정 없이는 단정하지 않겠습니다** |

마지막 줄이 이 준비의 태도다. **"측정 없이는 단정하지 않는다"가 이 프로젝트 전체의
주제**이므로, 모른다고 말하는 것이 오히려 일관된다.

## 5. 면접에서의 진행 순서

1. **범위를 먼저 좁힌다** — 소스 몇 개, QPS 얼마, 개인화 수준. 묻지 않고 그리기 시작하면 감점
2. **요청 경로부터 그린다** — 포트폴리오 그림 1 의 형태를 그대로 쓴다
3. **데이터 흐름** — 이 문서 그림 ②. ②(저장소)를 둘지 말지의 교환을 명시
4. **실패 모드** — 포트폴리오 그림 8. **여기서 시간을 가장 많이 쓴다**
5. **어떻게 검증할 것인가** — 여기가 내 자리다. 대부분의 지원자는 3번에서 끝낸다

**4·5번이 다른 지원자와 갈리는 지점이다.** 캐시와 샤딩은 누구나 말한다.

## 6. 남은 준비

- [ ] 그림 3장을 **손으로 5분 안에** 그릴 수 있게 연습 (화이트보드/구두 전형 대비)
- [ ] 타임아웃 예산·부분 응답·서킷 브레이커 — **말할 수 있을 만큼**만 정리
- [ ] 복합 커서(여러 소스를 섞은 뒤의 페이지네이션) 한 문단 정리
