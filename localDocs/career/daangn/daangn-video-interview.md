## 0. 결론 — 여섯 문장

> **2026-09-05 갱신.** 표본을 후기 4건 → **17건**으로 늘리고 항목마다 확인 건수를 붙였다.
> 그 결과 **둘째 문장의 우선순위가 뒤집혔다.** 아래는 갱신본이다.

**첫째, 화상 인터뷰는 한 가지가 아니라 세 가지가 섞여 나온다.** 기초 CS 스피드 퀴즈 ·
라이브 코딩 · 이력서 기반 질문이고, **회차마다 조합이 다르다.** 후기 15건을 교차하면
어떤 사람은 퀴즈만, 어떤 사람은 라이브 코딩만, 어떤 사람은 둘 다 봤다.
**셋 다 준비하는 것 외에 방법이 없다.**

**둘째, 가장 확실하게 나오는 것은 퀴즈도 코딩도 아니라 이력서다 — 15건 중 12건.**
라이브 코딩(5건)의 두 배가 넘고, 스피드 퀴즈(2건)의 여섯 배다.
**어떤 회차를 만나도 이력서 심층 질문은 나온다.** 준비 시간을 여기에 가장 많이 준다.
(초판은 스피드 퀴즈를 1순위로 뒀다. **표본 4건 시절의 판단이었고, 지금 근거로는 3순위다.**
다만 공고가 *"기초 질문"* 을 명시했으므로 버리지는 않는다.)

**셋째, 그 이력서 질문의 실제 문장이 3명에게서 같은 모양으로 나왔다.**
*"어떻게 사용했는지, 왜 사용하는지, 어떻게 최적화 할 수 있는지"*(S7) ·
*"무엇을 어떻게 하였는지, 왜 그걸 사용하였는지"*(S12) ·
*"어떤 문제를 해결하려고 할 때 어떻게 하면 좋을까?"*(S15).
**서로 다른 직군·연도인데 같다.** 한 문장으로 압축하면
**"무엇을 · 어떻게 · 왜 골랐고 · 어떻게 더 낫게 할 것인가."**

**넷째, 백엔드 라이브 코딩은 알고리즘 문제가 아닐 수 있다.** 확인된 사례 하나는
**단순 구현 → 클래스 → 추상화 → 동시성**의 4문제 확장 구조였다. 프로그래머스식
알고리즘 준비와 **대비 방향이 다르다.**

**다섯째, 문제 원문을 미리 아는 길은 사실상 막혀 있다.** 라이브 코딩·과제를 실제로 치른
후기 **5건 중 4건이 문제를 의도적으로 공개하지 않았다.** 한 명은
*"대비할 수 있는 성격의 면접이 아니라고 판단했다"* 고 썼다.
**특정 문제를 외우는 대신, 어떤 문제가 와도 굴러가는 절차(4.3)를 몸에 붙인다.**

**여섯째, 이 단계의 평가 대상은 정답률이 아니다.** *"문제가 생겼을 때 소통 방식"*,
*"평소 프로그래밍 습관"* 을 본다고 면접관이 직접 말한 기록이 있다. **침묵이 최악이다.**
스피드 퀴즈 20문제 중 19개를 맞히고도 다음 단계에서 떨어진 후기가 있다(S3).
**잘 봐도 가산점이 없고 못 보면 그대로 끝난다.**

## 2.2 **출제 요소 빈도표** — 개발직군 15건 기준

**이 표가 이 문서의 핵심이다.** "몇 건에서 확인" 열이 준비 우선순위다.

**여기서 읽어야 할 것 넷.**

**① 압도적 1위는 퀴즈도 코딩도 아니라 이력서다 — 12/15.** 라이브 코딩(5)의 두 배가 넘는다.
**어떤 회차를 만나도 이력서 심층 질문은 나온다.** 준비 배분을 여기에 맞춰야 한다.

**② 스피드 퀴즈는 2/15고, 둘 다 2020·2022년 후기다.** 2024년 이후 후기(S4 S5 S8 S13)에는
퀴즈 언급이 **한 건도 없다.** [판단] 초판에서 *"가장 과소평가한 것은 스피드 퀴즈"* 라고 쓴
것은 **표본 4건 시절의 판단이고, 지금 표본으로는 근거가 약하다.** 다만 공고가 *"기초 질문"* 을
명시했으므로 **버리지는 않는다. 우선순위를 1위에서 3위로 내린다.**

**③ 시스템 디자인은 화상이 아니라 직무 단계다 — 2/15, 둘 다 직무.**
화상 단계에서 시스템 설계를 물은 후기는 **0건**이다. 공고 문장(*"직무 면접에서 시스템 설계"*)과
후기가 일치한다. **화상 준비에 설계를 넣지 않는다.**

**④ 정규직 상시 채용 경로에 온라인 코테는 0건이다.** 확인된 2건은 전부
프로그래머스 경유(데브매칭·윈터코딩) 인턴/신입 트랙이다. **내가 지원하는 경로에는 없다.**

**총 12개. 이게 공개 웹에 남아 있는 전부다.** 그중 **원문으로 남은 것은 6개(Q1 Q3 Q4 Q5 Q11 Q12)**.

**Q1·Q3·Q4가 사실상 같은 질문이다.** 셋을 합치면 하나의 문장으로 압축된다 —
**"무엇을 · 어떻게 · 왜 골랐고 · 어떻게 더 낫게 할 것인가."**
**서로 다른 3명이 서로 다른 직군·연도에 같은 걸 들었다.** 이 조사에서 가장 재현성 높은 신호다.

## 2.4 **문제를 공개하지 않은 후기가 압도적이다** — 이게 진짜 발견

라이브 코딩이나 과제를 **실제로 치른 후기 5건 중 4건이 문제 내용을 밝히지 않았다.**

| 출처 | 남긴 말 |
|---|---|
| S1 | *"상당히 쉬운 축에 속하는 문제였는데"* — **난이도만 말하고 문제는 안 씀** |
| S8 | *"구체적으로 어떤 질문이 있었는지 명시하기는 어렵고"* |
| S10 | *"자세히 말할 순 없지만 크게 어렵지 않았다"* |
| S11 | *"어디까지 공유해도 될지는 모르겠지만, 적어도 **대비할 수 있는 성격의 면접은 아니라고 판단했다**"* |

**[판단] 문제 원문이 안 나오는 이유는 검색을 덜 해서가 아니라, 후기 작성자들이
의도적으로 지웠기 때문이다.** 당근 지원자 커뮤니티에 그런 규범이 있다.
**따라서 "문제를 미리 알고 들어간다"는 전략은 성립하지 않는다.**
S11의 *"대비할 수 있는 성격이 아니다"* 를 그대로 받아들이는 편이 낫다 —
**특정 문제를 외우는 대신, 어떤 문제가 와도 굴러가는 절차(4.3)를 몸에 붙인다.**

## 2.5 그 밖에 새로 확인된 사실

**① 직무 인터뷰가 2회인 사례가 있다** [S5]. SRE 직군 기준 **직무 90분 × 2회 + 컬처핏 90분**.
초판은 직무 1회로 가정했다. **일정 계산이 최대 1회분(약 1주) 늘어날 수 있다.**

**② 면접관 수는 단계에 따라 다르다.** 화상은 **1:1이 3건**(S1 S2 S5), **2:1이 2건**(S7 S13).
직무는 **4:1이 2건**(S2 S3), **3:1이 2건**(S1 S5). **화상은 1~2명, 직무는 3~4명이 기본이다.**

**③ 화상 소요 시간 중앙값은 60분이다.** 30분(S3) · 60분(S2 S5 S7) · 80분(S1).
**초판이 쓴 "30~60분"은 하한이 맞고 상한이 틀렸다. 80분까지 잡아야 한다.**

**④ 결과 통보가 매우 빠르다.** 공식 FAQ 기준 서류 **7영업일 이내**,
화상·직무 **5영업일 내외**, 컬처핏 **10영업일 내외**. S1은 화상 종료 **50분 뒤** 합격을 받았고,
S5는 *"각 전형 진행 후 합격 안내 평균 하루"* 라고 적었다.
**→ 10/20 마감 일정 계산에 그대로 반영해야 한다.**

**⑤ 공식 FAQ가 과제 전형을 명문화했다.** *"5~7일 안에 작성 가능한 분량"*, 그리고
**"화상 인터뷰 또는 직무 인터뷰에서 과제가 함께 출제되는 경우도 있다."**
[판단] **"라이브 코딩"과 "과제"가 같은 것일 수 있다.** 리크루터 문의 항목에 이걸 추가한다.

**⑥ 고등학생이 경력 공고에 지원해 인턴 제안을 받은 선례가 있다** [S2].
CTO가 채용 설명회에서 *"경력보단 실력을 본다"* 고 말한 것을 근거로 지원했고,
직무 면접에서 불합격했으나 **"성장 가능성"** 을 이유로 3개월 인턴 제안을 받았다.
[판단] **탈락이 곧 끝이 아닌 경로가 실제로 존재한다.**

## 2.6 여기서 반드시 읽어야 할 세 가지 (초판 유지·갱신)

**① 구성이 고정돼 있지 않다.** S1·S4·S6·S10·S11은 라이브 코딩을, S2·S3은 스피드 퀴즈를 말한다.
**공고는 둘 다 있다고 했다.** [판단] 팀·직군·면접관에 따라 비중이 달라진다.

**② 스피드 퀴즈는 꼬리질문 연쇄다.** S2 원문 —
*"하나의 질문에 대해 답변하면 답변에 대해 또 다른 질문이 이어지는 식으로 대략 20문제가량"*.
**한 문제를 얕게 답하면 그 자리에서 더 깊이 들어온다.** 암기로는 두 번째 뎁스에서 끊긴다.

**③ 화상 단계는 What, 직무 단계는 Why·How** [S2]. 화상에서는 개념의 정의와 동작을
묻고, 직무에서 판단의 이유를 묻는다. **준비 방식이 다르다.**
단 **Q1·Q3·Q4를 보면 화상에서도 Why를 묻는다.** What만 준비하면 부족하다.

## 3.3 내 프로젝트로 어디까지 답할 수 있나

**이 표가 이 문서에서 가장 중요하다.** 남들은 교과서 답을 하는 자리에서
**나는 실측 답을 할 수 있는 곳**이 어디인지 가른다.

### 홈그라운드 — 교과서가 아니라 사건으로 답할 수 있는 것

| 예상 질문 | 내 답의 근거 | 강도 |
|---|---|---|
| **N+1 문제가 뭔가요, 해결책은?** | Fetch Join · `@EntityGraph` · `@BatchSize` · 전역 배치 설정 · DTO 프로젝션을 **실제로 비교하고 버린 이유를 기록**했다 (`performance/optimizations/OPT-002` §2-3) | **최강** |
| 지연 로딩과 프록시는 언제 풀리나요 | DTO 변환 중에 풀렸고, **비용이 댓글 수 N 이 아니라 작성자 수 U 에 비례**했다 — 1차 캐시 때문 | **최강** |
| 영속성 컨텍스트가 하는 일은 | 위와 같은 사건. 그리고 **테스트에서 `em.clear()` 를 빠뜨리면 N+1 테스트가 통과해 버린다**는 함정까지 | **최강** |
| **커넥션 풀이 왜 필요하고 부족하면 어떻게 되나요** | 커넥션 획득 p95 6,364ms · 대기 145건 · **같은 코드에서 38배 차이** | **최강** |
| 의미 없는 테스트란 | **패치 조인을 빼면 실패하는 음성 대조 테스트**를 만든 이유 그대로 | **최강** |
| Redis 를 어디에 썼나요 | 캐시 · 조회수 버퍼 · **정렬 집합 랭킹 + 시간 버킷 TTL** | 강함 |
| 트랜잭션 이벤트를 커밋 후에 받는 이유 | `AFTER_COMMIT` — **롤백된 행동이 순위에 남지 않게** (`HotPostEventListener`) | 강함 |
| 동시성 문제를 겪은 적 있나요 | 체크-후-실행 경쟁 상태 → 중복 행 → **읽기 경로 전면 장애**. 유니크 제약 + upsert | 강함 |
| 격리 수준을 올리면 막히나요 | **막히지 않는다.** 같은 키 삽입 충돌이기 때문 | 강함 |
| 스케줄러로 배치를 돌릴 때 실패 처리는 | **성공분만 정산하고 실패분은 버퍼에 남겨 재시도**, 삭제된 건은 무한 재시도 방지로 정리 | 강함 |
| GC 가 성능에 영향을 주나요 | 회차별 **GC 최대 정지 108ms vs 21~46ms** 를 이상치 판정 근거로 썼다 | 중간 |
| 멱등성이 뭔가요 | **KI-54 — 2026-09-11~13 구현 예정.** 그 전이면 "진단만 했다"고 답한다 | 구현 후 강함 |

### 공백 — 프로젝트로 답할 수 없다. 그냥 공부해야 한다

| 영역 | 대표 질문 | 상태 |
|---|---|---|
| **네트워크 하위 계층** | TCP/UDP 차이 · 3-way·4-way handshake · TLS handshake · OSI 7계층 | **공백** |
| **HTTPS·암호화** | 대칭키/비대칭키 · SSL 동작 · 인증서 | **공백** |
| **OS 심화** | 가상 메모리 · 페이지 교체 · 세마포어와 뮤텍스 · 컨텍스트 스위칭 비용 | **공백** |
| **Java 언어 기초** | JVM 메모리 영역 · HashMap 내부 동작 · String vs StringBuilder · Checked/Unchecked | **얕음** |
| **Spring 기초** | Bean 생성 과정 · Bean Scope · DispatcherServlet · Filter vs Interceptor | **얕음** |
| **디자인 패턴** | 싱글톤·전략·팩토리·빌더의 정의와 사용처 | **공백** |
| **당근 스택** | MongoDB · gRPC · Protocol Buffer · Kubernetes | **공백** |

> **[판단] 공백 중 우선순위.** Java·Spring 기초가 1순위다. **분량이 가장 많이 나오는 영역**이고
> 후기 둘 다 첫 카테고리로 꼽았다. 네트워크·OS 는 2순위. 디자인 패턴과 당근 스택은
> 화상 단계에서 나올 가능성이 낮으므로 **버린다**(직무 면접에서 필요하면 그때).

## 3.4 답변 원칙 — 꼬리질문을 견디는 법

1. **정의 → 동작 → 내 경험** 3단으로 답한다. 정의만 하면 다음 뎁스에서 끊긴다.
2. **홈그라운드로 끌어온다.** 위 표의 항목이 나오면 교과서 답 대신 사건으로 답한다.
   *"N+1 은 …입니다. 제 프로젝트에서 요청당 1,507개가 나왔는데, 그중 108개가…"*
3. **모르면 빨리 인정하고 접근을 말한다.** S3 에 **답이 없는 문제도 나왔다.**
   *"정확히는 모릅니다. 다만 이렇게 접근해 보겠습니다"* 가 침묵보다 낫다.
4. **20문제 / 30~60분이다.** 한 문제에 3분을 넘기면 뒤가 밀린다. **길게 말하지 않는다.**

# 4. Part B — 라이브 코딩

## 4.1 당근에서 확인된 것 [S1]

- 이력서 기반 질문과 **같은 세션**에서 진행 (1:1, 약 80분)
- 난이도: *"상당히 쉬운 난이도였으나 긴장으로 풀이가 순조롭지 않았다"*
- 저자의 대응: **주석으로 사고 과정을 설명하며** 진행
- 결과: **면접 50분 뒤 합격 통보**

**[판단] 난이도가 낮다면 변별점은 정답률이 아니라 과정이다.**

## 4.2 백엔드 라이브 코딩은 알고리즘이 아닐 수 있다 — **가장 중요한 발견**

당근 후기에는 문제 유형이 안 나온다. 그러나 다른 회사의 백엔드 라이브 코딩 사례
하나가 구조를 명확히 남겼다 [후기·다른 회사].

> **4문제 · 단순 구현 → 클래스 → 추상화 → 동시성**
> *"단순 구현부터 시작해 확장성이 증대되는 형태"*, 추상화 문제는
> *"스프링의 객체 지향 디자인 패턴 활용 필요"*

그리고 면접관이 평가 목표를 직접 밝혔다 —
*"검색 등 각종 능력을 활용하여 문제를 해결할 수 있는지 판단"*, *"문제 발생 시 소통 방식"*,
*"기본 자바 능력 검증"*. 즉 **개발 능력뿐 아니라 평소 프로그래밍 습관과 커뮤니케이션**을 본다.

**이 유형이라면 준비 방향이 프로그래머스와 다르다.**

| 알고리즘 준비 | 이 유형의 준비 |
|---|---|
| 자료구조·알고리즘 유형 정복 | **요구사항이 하나씩 추가될 때 구조를 어떻게 바꾸는가** |
| 시간복잡도 최적화 | **클래스 분리 · 인터페이스 추출 · 전략 교체** |
| 혼자 빨리 풀기 | **말하면서 짜기 · 힌트 요청** |
| — | **동시성** (락 · 원자 연산 · 스레드 안전) |

**[확인 필요] 당근이 이 유형인지 알고리즘형인지는 확인되지 않았다.**
**둘 다 대비하되 비중은 이 유형에 더 둔다** — 백엔드 직군이고, S1이 "쉬웠다"고 한 것도
알고리즘 난이도가 아니라 이런 유형이었을 가능성이 있다.

> **[판단] 이건 나에게 유리한 방향이다.** 동시성은 이미 사건(경쟁 상태·lost update)을 갖고 있고,
> 클래스 분리와 확장 지점 설계는 `HotPostRankingPort` 의 TTL 판단과 같은 종류의 사고다.

## 4.3 실전 5단계 [일반]

| 단계 | 무엇을 하나 | 흔한 실수 |
|---|---|---|
| **1. 문제 이해** | 입출력 타입·범위·예시 케이스를 **반드시 되묻는다** | 대충 읽고 짜다가 중간에 다시 푼다 |
| **2. 계획 발표** | *"이 자료구조로 이렇게 풀겠습니다"* 를 먼저 말한다. **브루트포스와 최적안을 같이 제시**하면 방향이 틀렸을 때 힌트를 받는다 | 무작정 코드부터 쓰다 방향을 잃는다 |
| **3. 설명하며 코딩** | 생각의 발전 과정을 계속 소리 내어 말한다. **실무 이상의 클린 코드** — 의미 있는 이름, 복잡한 로직 분해 | 빨리 풀려고 가독성을 버린다 |
| **4. 검증** | 주어진 케이스 실행 + **엣지 케이스 직접 추가** + 한 줄씩 설명하며 확인 | 테스트 없이 제출, 엣지 누락 |
| **5. 복잡도 분석** | 시간·공간 복잡도를 말하고 **개선 방향을 언급**한다. 시간이 없으면 **말로만이라도** | 분석 없이 끝낸다 |

**면접관이 보는 것은 "함께 일하고 싶은 동료인가"** 다. 3단계의 클린 코드가 그 판정에 들어간다.

## 4.4 실패 패턴 — 라이브 코딩 후기 셋이 공통으로 말한 것

**① 침묵.** 혼자 고민하면 면접관은 **무엇 때문에 막혔는지 알 수 없다.**
말하면 최소한 "풀려는 의지가 있다"는 판단을 받는다.

**② 힌트를 요청하지 않는다.** 한 후기의 반성 —
*"혼자 고민만 하지 말고 '힌트를 주실 수 있나요?' 라도 물어보기"*.

**③ 못 풀었을 때 과정도 못 보여준다.** 원문 —
*"못 풀어도 코드 작성 과정을 보여드려야 했는데 그것도 못 했다"*.

그리고 도구 문제로 무너진 사례가 있다 — **웹 에디터가 로컬 IDE 와 달라 로딩·버벅임에
당황**했다. 사전에 웹 에디터로 연습해 두는 것이 대비다.
