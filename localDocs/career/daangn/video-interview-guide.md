## 0. 이 문서를 쓰는 법

### 0.1 출제 요소별 비중과 근거

당근 개발직군 화상 인터뷰 후기 15건을 세어 보면 이력서 기반 심층 질문이 12건, 라이브 코딩이 5건,
CS 스피드 퀴즈가 2건입니다. 시스템 설계는 직무 면접 단계에서만 나왔고 화상 단계 후기에는 0건입니다.
그래서 이 문서는 이력서 문답에 절반을 쓰고, 시스템 설계는 다루지 않습니다.

세 명이 서로 다른 해에 같은 모양의 질문을 받았습니다. "무엇을 어떻게 했는지, 왜 그 기술을 골랐는지,
어떻게 더 낫게 할 수 있는지"입니다. 1장의 모든 카드는 이 순서로 꼬리질문을 배치했습니다.

| 출제 요소 | 후기 15건 중 확인 | 이 문서에서 다루는 장 |
|---|---:|---|
| 이력서·포트폴리오 심층 질문 | 12 | 1장, 2장, 3장 |
| 라이브 코딩 | 5 | 4장 |
| 꼬리질문 연쇄 | 4 | 1장 카드의 꼬리 1·2·3 |
| CS 스피드 퀴즈 | 2 | 5장 |
| 시스템 설계 | 0 (직무 면접에서 2) | 다루지 않음 |

### 0.2 카드 형식

1장의 카드 한 장은 이력서 한 줄에 대응합니다. 각 카드는 같은 순서로 구성했습니다.

| 칸 | 내용 | 공부할 때 |
|---|---|---|
| 이력서 문장 | 제출한 이력서의 원문 | 면접관이 이 문장을 보고 묻는다고 가정 |
| 먼저 이해할 것 | 이 줄에 나오는 개념을 쉬운 말로 설명 | 개념이 흐릿하면 여기부터 |
| 예상 질문과 30초 답변 | 소리 내어 말할 문장 | 파란 상자를 가리고 먼저 말해 본다 |
| 꼬리 1·2·3 | 무엇을, 왜 그 선택, 한계와 개선 | 한 단계씩 가리고 답한다 |
| 무너지는 자리 | 답이 아직 약한 곳과 그 이유 | 여기서 막히면 3장으로 |
| 말하면 안 되는 것 | 과장이나 오해를 부르는 표현 | 입에 붙지 않게 미리 확인 |

파란 상자 안의 문장은 전부 존댓말 스크립트입니다. 외우지 말고 뜻을 이해한 뒤 자기 말로 다시 만드십시오.
스크립트를 그대로 외우면 첫 꼬리질문에서 멈춥니다.

### 0.3 빨간 상자는 본인이 채우는 자리

문서 곳곳에 빨간 점선 상자가 있습니다. 회사 업무의 세부 사실, 팀 해체 사유, 입사 가능 시점처럼
저장소와 기록에 없어서 본인만 채울 수 있는 내용입니다. 빌드할 때마다 남은 개수가 콘솔에 나오고,
면접 전에는 0개여야 합니다.

### 0.4 읽는 순서

1. 1장 카드를 하루 4장씩, 가리고 답하는 방식으로 5일에 한 바퀴 돕니다.
2. 2장 통합표에서 판정이 "약함"인 질문만 골라 3장의 정직 답변과 연결합니다.
3. 4장 라이브 코딩은 매일 30분, 소리 내어 말하면서 코드를 씁니다.
4. 5장 CS 기초는 "공백" 표부터 하루 1시간씩 채웁니다.
5. 6장 숫자 카드는 면접 전날 한 번에 봅니다. 수치와 출처를 짝으로 외웁니다.
6. 7장 리허설 기록표에 날짜와 막힌 카드 번호를 적습니다.

## 1. 이력서 문답 카드 21장

카드 번호는 이력서의 위에서 아래 순서입니다. 카드 0은 소개 문단, 1~5는 인기글 서빙, 6~10은 댓글 N+1,

### 카드 0. 자기소개

**이력서 문장.** 백엔드 개발자입니다. Java와 Spring Boot로 익명 커뮤니티의 게시글·댓글·사용자 행동 집계와
인기글 서빙 경로를 구현했습니다. 기능을 만든 뒤 직접 계측을 붙여 댓글 목록의 N+1과 조회수 증가분이
유실되는 경로를 재현했습니다. 실패 테스트와 반복 부하 실험으로 개선 결과를 확인했습니다.

**먼저 이해할 것.** 면접 첫 질문은 거의 항상 "간단히 자기소개 해 주세요"입니다. 이 답은 이력서 소개 문단을
말로 옮긴 것이어야 합니다. 이력서와 다른 이야기를 하면 면접관이 두 개를 대조하느라 첫인상이 흐려집니다.
30초 안에 직무, 무엇을 만들었는지, 무엇을 고쳤는지, 어떻게 확인했는지 네 가지만 말합니다.

**예상 질문.** 간단히 자기소개 부탁드립니다.

> 백엔드 개발자 장혁입니다. Java와 Spring Boot로 고등학생 익명 커뮤니티의 게시글, 댓글, 인기글 기능을
> 만들었습니다. 사용자의 댓글, 반응, 스크랩, 조회를 모아서 인기글 순위를 내는 경로를 구현했고, 그 위에서
> 두 가지 문제를 직접 찾아 고쳤습니다. 하나는 댓글 목록 한 번에 쿼리가 1,507번 나가던 N+1 문제이고,
> 다른 하나는 조회수를 DB에 반영하다 실패하면 증가분이 사라지던 문제입니다. 고친 뒤에는 실패해야 하는
> 테스트와 같은 조건의 부하 실험 5회로 결과를 확인했습니다. 지금은 한국클라우드에서 백엔드 개발을
> 하고 있고, 보충역 산업기능요원으로 신규 편입이 가능합니다.

**꼬리 1 (무엇을).** 그 프로젝트에서 본인이 맡은 범위는 어디까지인가요?

> 동아리에서 세 명이 시작했고 제가 프로젝트를 이끌었습니다. 백엔드에서 게시글, 댓글, 인기글, S3 파일
> 업로드를 맡았고, 사용자 엔티티와 인증 설정은 다른 팀원이 맡았습니다. 4개월 뒤부터는 백엔드와 성능
> 측정 도구를 혼자 유지보수하고 있습니다.

**꼬리 2 (왜).** 기능을 다 만든 뒤에 왜 성능 측정을 붙였나요?

> 만들고 나서 부하를 걸어 보니 응답이 느렸습니다. 그런데 코드를 읽어서는 어디가 얼마나 느린지 알 수
> 없었습니다. 그래서 엔드포인트별로 요청 하나에 쿼리가 몇 번 나가는지, DB에서 시간을 얼마나 쓰는지
> 기록하는 계측을 먼저 붙였습니다. 그 값이 댓글 목록에서 1,507번이라고 알려줬고, 거기서부터 고쳤습니다.

**꼬리 3 (한계).** 실제 사용자는 있었나요?

> 실사용자 지표를 올린 프로젝트는 아닙니다. 부하 실험은 로컬 Docker 환경에서 생성한 데이터로 했고,
> 그 조건은 이력서와 포트폴리오에 적어 두었습니다. 그래서 수치는 전부 같은 조건에서 전후를 비교한
> 값이고, 운영 트래픽 수치는 아닙니다.

**무너지는 자리.** 실사용자가 없다는 점을 먼저 말하지 않으면 뒤에서 캐물립니다. 3장 3.2를 미리 익혀 둡니다.

### 카드 1. 댓글·반응·스크랩을 트랜잭션 커밋 뒤에 Redis 인기글 점수에 반영

**이력서 문장.** 댓글·반응·스크랩을 트랜잭션 커밋 뒤에 Redis 인기글 점수에 반영

**먼저 이해할 것.** 트랜잭션은 DB 작업 여러 개를 하나로 묶어 전부 성공하거나 전부 취소하는 단위입니다.
커밋은 그 묶음을 확정하는 순간이고, 롤백은 취소하는 순간입니다. Spring에는 "트랜잭션이 커밋된 뒤에만
이 코드를 실행하라"고 지정하는 기능이 있습니다. 애노테이션 이름은 `@TransactionalEventListener`이고,
단계를 `AFTER_COMMIT`으로 지정합니다. 이 프로젝트에서는 댓글 작성, 좋아요, 스크랩이 DB에 확정된 뒤에만
Redis의 인기글 점수를 올립니다.

**예상 질문.** 인기글 점수를 왜 트랜잭션이 끝난 뒤에 반영하나요?

> 댓글이나 좋아요가 DB에 저장되다 실패해서 롤백되면, 그 행동은 없었던 일이 됩니다. 그런데 점수를
> 트랜잭션 안에서 먼저 올리면 롤백된 행동이 인기글 순위에 남습니다. 그래서 커밋이 끝난 뒤에 실행되는
> 이벤트 리스너에서 점수를 갱신했습니다. Spring의 `@TransactionalEventListener`를 `AFTER_COMMIT`
> 단계로 썼습니다.

**꼬리 1 (무엇을).** 이벤트는 어디서 발행하고 어디서 받나요?

> 댓글 서비스, 반응 서비스, 스크랩 서비스가 각각 저장을 마치면서 이벤트를 발행합니다. 인기글 이벤트
> 리스너 하나가 세 이벤트를 받아서 해당 게시글의 일간 점수를 다시 계산해 Redis Sorted Set에 넣습니다.
> 알림 리스너는 그중 댓글 이벤트와 친구 요청 이벤트를 같은 방식으로 받습니다.

**꼬리 2 (왜 그 선택).** 그냥 서비스 메서드 안에서 Redis를 바로 호출하면 안 되나요?

> 가장 큰 이유는 롤백입니다. 메서드 안에서 호출하면 아직 커밋 전이라, 뒤에서 롤백될 행동이 점수에 먼저
> 들어갑니다. 커밋 뒤 리스너로 분리하면 확정된 행동만 점수에 반영됩니다. 일반적으로는 Redis 호출
> 실패가 원래 트랜잭션을 실패시키는 문제도 있는데, 이 프로젝트는 Redis 어댑터에 AOP로 예외를 흡수하는
> 코드가 따로 있어서 그 문제는 리스너 분리와 무관하게 막혀 있습니다.

**꼬리 3 (한계).** 커밋은 됐는데 리스너가 실행되기 전에 서버가 죽으면요?

> 그 경우 점수 갱신은 사라집니다. 지금 구현은 같은 프로세스 안에서 커밋 뒤에 실행하는 방식이라 프로세스가
> 종료되면 재처리하지 않습니다. 다만 5분마다 도는 스케줄러가 상위 50개 게시글의 점수를 다시 계산하므로
> 이미 순위권에 있는 글은 다음 주기에 맞춰집니다. 순위권 밖의 글은 다음 행동이 들어올 때까지 반영이
> 늦어집니다. 이걸 보장하려면 이벤트를 DB 테이블에 먼저 적고 별도 작업이 읽어서 처리하는 아웃박스
> 방식이 필요한데, 이건 구현하지 않았습니다.

**무너지는 자리.** 꼬리 3에서 아웃박스를 설명하라고 하면 개념까지만 답할 수 있습니다. 3장 3.4의 아웃박스
설명을 익혀 둡니다. 리스너가 동기 실행인지 비동기 실행인지 물으면 "동기 실행이고 별도 스레드 풀은 없다"고
답합니다.

**다음에 올 질문.** 동기 실행이면 리스너에서 Redis 예외가 났을 때 클라이언트는 무슨 응답을 받나요. 답은
"Redis 어댑터의 AOP가 예외를 흡수하므로 점수 갱신만 빠지고 응답은 정상입니다. 커밋은 이미 끝난 뒤라
저장도 유지됩니다"입니다.

**말하면 안 되는 것.** "이벤트 유실을 막았다". 롤백된 행동이 점수에 남는 것을 막은 것이지, 프로세스
종료 시 유실은 막지 못했습니다.

### 카드 2. 일간 Redis Sorted Set의 점수 순으로 상위 게시글을 조회하고 날짜별 키에 TTL 적용

**이력서 문장.** 일간 Redis Sorted Set의 점수 순으로 상위 게시글을 조회하고 날짜별 키에 TTL 적용

**먼저 이해할 것.** Redis Sorted Set은 항목마다 점수를 붙여 저장하고, 점수 순으로 정렬된 상태를 유지하는
자료구조입니다. 점수를 올리는 명령과 상위 N개를 꺼내는 명령이 각각 하나라서 순위표에 자주 씁니다.
TTL은 키가 자동으로 지워지기까지 남은 시간입니다. 이 프로젝트는 날짜마다 키를 하나씩 만들고
(`hot:leaderboard:day:20260908` 형태), 각 키에 2일의 TTL을 걸었습니다.

**예상 질문.** 인기글 순위를 어떻게 저장하고 조회하나요?

> 날짜별로 Redis Sorted Set 키를 하나씩 둡니다. 게시글 ID가 항목이고 인기 점수가 정렬 기준입니다.
> 댓글, 반응, 스크랩은 커밋 직후에, 조회는 60초 배치가 DB에 반영한 뒤에 그 게시글의 점수를 다시 계산해서
> 넣습니다. 같은 사용자의 조회는 1시간에 한 번만 셉니다. 조회할 때는 점수가 높은 순으로 상위 10개를
> 꺼냅니다. 그중 좋아요가 10개 이상인 글만 노출합니다. 키에는 2일짜리 TTL을
> 걸어서 지난 날짜의 키가 계속 쌓이지 않게 했습니다.

**꼬리 1 (무엇을).** 왜 하루가 아니라 2일인가요?

> 키 이름이 날짜라서 자정에 새 키로 넘어갑니다. TTL을 정확히 하루로 두면 그날 마지막 쓰기 직후에 키가
> 만료돼서, 남은 시간 동안 조회가 전부 DB로 넘어갈 수 있습니다. 2일로 두면 어느 시점에 써도 그날 내내
> 살아 있고, 남는 키는 최대 2개입니다.

**꼬리 2 (왜 그 선택).** 점수는 어떻게 계산하나요? 가중치는 검증했나요?

> 좋아요, 댓글, 스크랩, 조회에 가중치를 곱해 더하고 시간이 지날수록 낮아지게 했습니다. 다만 그 가중치는
> 실사용자 데이터로 검증하지 못했습니다. 같은 시간 조건이면 가중합에 로그를 씌워도 순서가 바뀌지 않는
> 것도 확인했습니다. 그래서 점수식은 제품 성과로 말하지 않고, 행동 데이터를 모아서 저장하고 순위로
> 서빙하는 경로를 구현한 근거로만 씁니다.

**꼬리 3 (한계).** Redis가 비어 있으면 무엇을 반환하나요? 상위 50개만 갱신하면 51위는요?

> Redis가 비면 DB의 일간 인기글 테이블에서 목록을 반환하는 코드가 있습니다. 그런데 그 테이블은 5분
> 스케줄러가 채우기 때문에 Redis 순위와 같은 결과를 보장하지 않고, 그 사이의 점수 갱신도 반영하지
> 않습니다. 그래서 이 경로를 믿을 수 있는 대체 경로라고 말하지 않습니다. 상위 50개만 시간 감쇠를 적용하기 때문에
> 51위 밖의 오래된 글은 점수가 낮아지지 않은 채 남아 있다가 재정렬 때 유리해질 수 있습니다. 이건
> 포트폴리오에 현재 한계로 적어 두었습니다.

**무너지는 자리.** "그럼 51위 문제는 어떻게 고칠 건가요"까지 오면 답을 준비합니다. 답의 방향은 두 가지입니다.

누적값"으로 저장하고 조회 때 감쇠를 적용하는 방법입니다. 둘 다 구현하지 않았다고 먼저 말합니다.

### 카드 3. 조회 증가분을 Redis에 모아 60초마다 DB에 반영

**이력서 문장.** 조회 증가분을 Redis에 모아 60초마다 DB에 반영해 게시글 행의 반복 갱신 축소

**먼저 이해할 것.** 게시글을 볼 때마다 DB의 조회수 컬럼을 1씩 올리면, 인기 게시글 한 행에 갱신이 몰립니다.
DB는 같은 행을 동시에 갱신하려는 요청을 줄 세우기 때문에 이 행이 병목이 됩니다. 그래서 조회는 Redis에
`INCR`(원자적으로 1 올리는 명령)로 먼저 모으고, 60초마다 스케줄러가 모인 값을 한 번에 DB에 더합니다.

**예상 질문.** 조회수를 왜 바로 DB에 쓰지 않고 Redis에 모으나요?

> 인기 게시글은 조회가 한 행에 집중됩니다. 요청마다 그 행을 갱신하면 DB가 같은 행의 갱신을 줄 세우고,
> 게시글 조회 자체가 느려집니다. 그래서 조회는 Redis에 게시글별 카운터로 모으고, 60초마다 스케줄러가
> 모인 증가분을 DB에 한 번에 더합니다. 조회수는 60초까지 늦게 보여도 되는 값이라 이 지연을 받아들였습니다.

**꼬리 1 (무엇을).** 스케줄러는 정확히 어떤 순서로 동작하나요?

> 먼저 Redis에서 대기 중인 게시글별 증가분을 읽습니다. 게시글마다 DB에 증가분을 더하고, 성공하면 그
> 게시글의 인기 점수를 갱신합니다. 마지막에 DB 반영에 성공한 값만 Redis에서 차감합니다. 이 세 단계가
> 60초 간격으로 반복됩니다.

**꼬리 2 (왜 그 선택).** 60초는 어떻게 정했나요?

> 측정으로 정한 값은 아닙니다. 조회수는 사용자가 근사값을 받아들이는 데이터라서 1분 지연을
> 허용했고, 주기를 짧게 하면 DB 갱신이 잦아지고 길게 하면 Redis 장애 시 잃는 양이 커지는 사이에서
> 고른 값입니다. 운영 데이터가 있다면 Redis 장애 허용 손실과 DB 갱신 빈도를 보고 다시 정하겠습니다.

**꼬리 3 (한계).** Redis가 죽으면 조회수는 어떻게 되나요?

> Redis가 내려간 동안의 조회 증가분은 잃습니다. 게시글 조회 자체는 Redis 예외를 무시하고 정상 응답하도록
> 했기 때문에 서비스는 계속 동작합니다. 조회수 정확성보다 게시글 조회 가용성을 우선한 선택입니다.
> 정확한 조회 기록이 필요하다면 별도 이벤트 로그가 필요합니다. 다만 Redis 연결 타임아웃을 따로
> 설정하지 않아 기본값을 쓰고 있습니다. Redis가 응답 없이 멈추면 요청 스레드가 그 시간만큼 기다리므로,
> 가용성을 우선한다고 말하려면 타임아웃을 짧게 잡는 설정이 함께 있어야 합니다. 이건 아직 안 했습니다.

**무너지는 자리.** "다중 인스턴스에서 스케줄러 두 개가 동시에 돌면요"라고 물으면 현재 단일 인스턴스
전제라고 먼저 말합니다. 3장 3.3에 준비된 답이 있습니다.

**말하면 안 되는 것.** "조회수 유실을 없앴다". 없앤 것은 DB 반영 실패 시의 유실이고, Redis 장애 시
유실은 받아들인 것입니다. 카드 4와 구분해서 말합니다.

### 카드 4. DB 반영 성공분만 Redis에서 차감하고 실패분을 다음 주기에 재시도

**이력서 문장.** DB 반영 성공분만 Redis에서 차감하고 실패분을 다음 주기에 재시도

**먼저 이해할 것.** 예전 코드는 Redis의 `GETDEL`(값을 읽으면서 동시에 삭제하는 명령)로 증가분을 꺼냈습니다.
읽는 순간 Redis에서 지워지므로, 그 뒤 DB 반영이 실패하면 지워진 값을 되돌릴 수 없었습니다. 고친 코드는
먼저 읽기만 하고, DB에 성공한 만큼만 `DECRBY`(지정한 수만큼 빼는 명령)로 차감합니다. 실패한 게시글의
값은 Redis에 그대로 남아 다음 주기에 다시 시도됩니다.

**예상 질문.** 조회수가 유실되던 문제는 정확히 무엇이었나요?

> 예전 스케줄러는 Redis에서 증가분을 읽으면서 바로 삭제하는 `GETDEL`을 썼습니다. 그다음 DB에 반영했는데,
> DB 반영이 실패하면 이미 삭제한 증가분을 복구할 수 없었습니다. 그래서 순서를 바꿨습니다. 먼저 읽기만
> 하고, 게시글별로 DB에 반영한 뒤, 성공한 값만 `DECRBY`로 차감합니다. 실패한 값은 Redis에 남아 다음
> 주기에 다시 시도됩니다.

**꼬리 1 (무엇을).** 왜 삭제 대신 차감인가요? 읽은 뒤 삭제하면 안 되나요?

> Redis 값을 읽고 DB에 반영하는 사이에도 새 조회가 계속 들어옵니다. 그 시점에 키를 삭제하면 새로 들어온
> 증가분까지 함께 사라집니다. 읽었던 값만큼만 빼면 그 사이에 들어온 증가분은 다음 주기에 남습니다.
> 차감 결과가 0이 되어 키를 지우는 순간에만 예외가 있는데, 그건 꼬리 3에서 말씀드리겠습니다.

**꼬리 2 (왜 그 선택).** 이걸 어떻게 검증했나요?

> 네 가지 조건을 테스트로 만들었습니다. 첫 게시글의 DB 반영이 실패하면 그 증가분은 차감되지 않아야
> 하고, 그다음 게시글은 정상 반영돼야 하고, 삭제된 게시글은 증가분을 정리하되 점수 갱신은 건너뛰어야
> 하고, 정상 반영 시 DB 반영 뒤에 Redis 차감이 호출돼야 합니다. 네 경우 모두 통과했습니다.

**꼬리 3 (한계).** DB에는 반영됐는데 차감 직전에 프로세스가 죽으면요?

> 그러면 Redis에 값이 남아 다음 주기에 한 번 더 더해집니다. 중복 반영입니다. DB 반영과 Redis 차감이
> 서로 다른 저장소의 연산이라 하나로 묶을 수 없기 때문입니다. 이걸 막으려면 정산 회차마다 ID를 두고
> 같은 ID는 두 번 반영하지 않는 멱등 기록이 필요한데, 구현하지 않았습니다. 조회수는 이 정도 오차를
> 허용하는 값이라 현재는 받아들였습니다. 또 차감 결과가 0 이하면 키를 삭제하는데, 차감과 삭제 사이에
> 조회가 들어오면 1건이 유실될 수 있습니다. 이것도 알고 받아들인 조건입니다.

**무너지는 자리.** 꼬리 3에서 "그럼 조회수가 정확하지 않은 거네요"라고 하면 "네, 근사값입니다. 그 대신 게시글 조회 응답 시간을 지켰습니다"라고 짧게 인정합니다.

**다음에 올 질문.** 0이 됐을 때 왜 굳이 키를 지우나요. 답은 "대기 키를 찾을 때 `KEYS` 명령으로 훑기 때문에

**말하면 안 되는 것.** "원자적으로 처리했다". Redis 단일 명령은 원자적이지만 DB 반영과 Redis 차감을 합친
과정은 원자적이지 않습니다.

### 카드 5. 게시글 한 건의 반영 실패가 나머지 게시글 처리를 중단하지 않도록 실패 격리

**이력서 문장.** 게시글 한 건의 반영 실패가 나머지 게시글 처리를 중단하지 않도록 실패 격리

**먼저 이해할 것.** 예전 스케줄러는 게시글 여러 개를 한 트랜잭션 안에서 처리했습니다. 그러면 한 게시글에서
예외가 나면 전체가 롤백되거나 중단됩니다. 고친 코드는 게시글마다 따로 서비스 메서드를 호출하고, 예외를
게시글 단위로 잡습니다. 삭제된 게시글은 다시 시도해도 성공할 수 없으므로 반영된 것으로 처리해 정리합니다.

**예상 질문.** 실패 격리라는 게 구체적으로 무엇인가요?

> 조회수 반영 스케줄러가 게시글 100개를 처리한다고 하면, 예전에는 그중 하나가 실패할 때 나머지 99개도
> 같이 멈췄습니다. 지금은 게시글 하나씩 DB 반영을 호출하고 예외를 그 게시글에서만 잡습니다. 실패한
> 게시글의 증가분은 Redis에 남겨 다음 주기에 다시 시도하고, 나머지는 정상 처리합니다.

**꼬리 1 (무엇을).** 삭제된 게시글은 어떻게 처리하나요?

> 삭제된 게시글은 다시 시도해도 계속 실패합니다. 그 값을 Redis에 남겨 두면 매 주기마다 같은 실패가
> 반복되므로, 게시글이 없다는 예외는 따로 잡아서 반영된 것으로 취급하고 증가분을 정리합니다. 인기 점수
> 갱신은 건너뜁니다.

**꼬리 2 (왜 그 선택).** 트랜잭션을 게시글별로 나눌 때 주의한 점이 있나요?

> Spring의 `@Transactional`은 프록시로 동작해서 같은 클래스 안에서 자기 메서드를 호출하면 적용되지
> 않습니다. 그래서 게시글별 반영은 별도 서비스인 `PostService`의 메서드로 빼서 호출했습니다. 그래야 게시글마다 트랜잭션이 따로 열립니다.

**꼬리 3 (한계).** 계속 실패하는 게시글이 있으면 어떻게 되나요?

> 삭제 외의 이유로 계속 실패하면 그 값은 매 주기마다 재시도됩니다. 재시도 횟수 제한이나 별도 보관소는
> 없습니다. 지금은 실패 로그만 남깁니다. 운영이라면 재시도 상한을 두고 넘은 건은 따로 기록해 사람이
> 보게 하는 편이 맞습니다.

**무너지는 자리.** 꼬리 2의 프록시 설명을 되물으면 5장 5.2의 `@Transactional` 항목으로 답합니다.

**다음에 올 질문.** 게시글마다 트랜잭션을 열면 커넥션 10개짜리 풀을 스케줄러가 얼마나 점유하나요, 부하

### 카드 6. 댓글별 반응 조회를 한 번의 일괄 조회로 바꿔 요청당 쿼리 1,507 → 112회

**이력서 문장.** 댓글별 반응 조회를 한 번의 일괄 조회로 바꿔 요청당 쿼리 1,507 → 112회

**먼저 이해할 것.** N+1 문제는 목록을 한 번 조회한 뒤, 목록의 항목마다 추가 쿼리가 한 번씩 더 나가는
현상입니다. 댓글 100개를 가져오면 댓글마다 "이 댓글에 내가 좋아요를 눌렀나"를 따로 조회해서 쿼리가
100번 더 나갑니다. 일괄 조회는 댓글 ID 100개를 한 번에 넘겨 `WHERE comment_id IN (...)` 한 쿼리로
가져오는 방식입니다. 1,507이라는 수는 부하 실행 5회에서 잰 요청당 평균이고, 단일 요청 하나의 값은
게시글의 댓글 수에 따라 다릅니다.

**예상 질문.** 쿼리가 1,507번 나갔다는 건 어떻게 알았고, 무엇이 문제였나요?

> 엔드포인트별로 요청 하나에 쿼리가 몇 번 나가는지 기록하는 계측을 붙였더니 댓글 목록 API가 요청당
> 평균 1,507번이었습니다. 원인은 두 가지였습니다. 댓글마다 좋아요와 싫어요 여부를 따로 조회했고,
> 댓글 작성자를 지연 로딩으로 하나씩 가져왔습니다. 댓글 수를 N, 서로 다른 작성자 수를 U라고 하면
> 요청당 쿼리는 3 + U + 2N회입니다. 댓글 4,047건에 작성자 450명인 글이면 8,547회입니다. 첫 단계로
> 댓글별 반응 조회를 댓글 ID 목록 한 번으로 바꿔서 112회로 줄였습니다.

**꼬리 1 (무엇을).** 서비스 코드에 반복문이 있었나요?

> 서비스와 컨트롤러에는 반복 쿼리가 보이지 않았습니다. 댓글 엔티티를 응답 DTO로 바꾸는 과정에서
> 댓글마다 반응 조회 메서드를 호출했고, 작성자는 지연 로딩 프록시가 DTO 변환 중에 풀리면서 쿼리가
> 나갔습니다. 그래서 코드를 읽어서는 몇 번인지 알 수 없었고, 계측이 먼저 필요했습니다.

**꼬리 2 (왜 그 선택).** 1,507개면 처음 설계가 잘못된 것 아닌가요?

> 맞습니다. 처음에 DTO 변환에서 조회가 나가도록 만든 것은 제 실수입니다. 제가 배운 것은, 코드를
> 읽어서는 그게 요청당 몇 번인지 알 수 없었다는 점입니다. 그래서 고치기 전에 요청당 쿼리 수를 기록하는
> 계측부터 붙였고, 고친 뒤에는 같은 계측으로 4회가 된 것을 확인했습니다.

**꼬리 3 (한계).** 112회 뒤에 남은 것은 무엇이었나요?

> 남은 112회 중 평균 108회가 작성자 조회였습니다. 댓글 수 N에 비례하는 항은 없어졌고 작성자 수 U에
> 비례하는 항이 남은 것입니다. 이 값을 보고 다음 개선 대상을 작성자 조회로 정했습니다. 그게 카드 7의
> 페치 조인입니다. 일괄 조회 쪽의 비용은 댓글 ID 4,046개가 `IN` 절 파라미터로 들어간다는 점인데, 그
> 쿼리의 실행 계획은 따로 확인하지 않았습니다. 응답 크기와 같은 이유로 페이징이 들어가야 줄어듭니다.

**무너지는 자리.** "한 요청에서 1,507번이었나요"라고 정확히 물으면 "부하 실행 5회의 요청당 평균이고, 부하가
여러 크기의 게시글을 섞어 보내서 평균이 그렇습니다. 댓글 4,047건 게시글 하나를 단독으로 재면 반응
일괄 조회 뒤에도 454회였습니다"라고 답합니다. 포트폴리오 4장 첫 문장이 "단일 요청에서 1,507회"로 읽힐
수 있는데, 이 답으로 바로잡습니다.

**말하면 안 되는 것.** "N+1을 다 잡았다". 이 API의 N+1을 잡은 것이고 다른 목록 API는 따로 재지 않았습니다.

### 카드 7. 작성자 지연 로딩에 ManyToOne 페치 조인을 적용해 요청당 쿼리 112 → 4회

**이력서 문장.** 작성자 지연 로딩에 `ManyToOne` 페치 조인을 적용해 요청당 쿼리 112 → 4회

**먼저 이해할 것.** JPA에서 댓글과 작성자의 관계는 댓글 여러 개가 작성자 한 명을 가리키는 `ManyToOne`입니다.
지연 로딩은 댓글을 가져올 때 작성자를 같이 가져오지 않고, 작성자 필드를 실제로 읽는 순간 쿼리를 보내는
방식입니다. 페치 조인(fetch join)은 댓글을 조회하는 JPQL에 `join fetch c.user`를 붙여 작성자를 같은
쿼리에서 한 번에 가져오는 방법입니다. 댓글 하나의 작성자는 한 명이므로 조인해도 결과 행 수가 늘지
않습니다.

**예상 질문.** 왜 `@BatchSize`가 아니라 페치 조인을 골랐나요?

> 채택안까지 포함해 여섯 가지를 비교했습니다. `@BatchSize`는 작성자 조회를 100명씩 묶어 주지만 작성자가 450명이면
> 쿼리가 5회 남고, 그 설정이 다른 조회 경로에도 영향을 줍니다. 전역 배치 설정은 애플리케이션 전체의
> 지연 로딩 동작을 바꿉니다. `@EntityGraph`는 쿼리를 1회로 만들지만 JPQL 필터 조건과 연관 로딩 정의가
> 두 곳으로 나뉩니다. DTO 프로젝션은 읽는 컬럼이 줄지만 호출부 세 곳을 바꿔야 해서 별도 과제로
> 뺐습니다. 작성자를 따로 일괄 조회하면 쿼리 왕복이 1회 더 생깁니다. `ManyToOne` 페치 조인은 바꾸는
> 범위가 쿼리 하나이고 결과 행 수가 그대로라서 채택했습니다.

**꼬리 1 (무엇을).** 남은 4회는 무엇인가요? 평균은 왜 3.92인가요?

> 인증 사용자 조회, 게시글 조회, 댓글 목록 조회, 반응 일괄 조회가 각 1회입니다. 댓글 수 N과 작성자 수
> U에 비례하는 항이 없어졌습니다. 부하 중 평균이 3.92로 4보다 작은 이유는 댓글이 없는 게시글에서는
> 반응 일괄 조회를 건너뛰어 3회이기 때문입니다.

**꼬리 2 (왜 그 선택).** 컬렉션 페치 조인은 왜 안 되나요?

> 댓글 하나에 반응이 여러 개 달리는 것처럼 일대다 관계를 페치 조인하면 조인 결과 행이 반응 수만큼
> 늘어나서 댓글이 중복되고 페이징도 깨집니다. 작성자는 다대일이라 댓글 한 행에 작성자 한 행이 붙을
> 뿐입니다. 그래서 작성자에만 페치 조인을 쓰고, 반응은 ID 목록으로 일괄 조회하는 쪽을 유지했습니다.

**꼬리 3 (한계).** 페치 조인의 비용은 없었나요?

> 있습니다. MySQL이 초당 읽은 행이 5,935에서 7,294로 22.9% 늘었습니다. 댓글마다 작성자 행을 조인해서
> 읽기 때문입니다. 같은 실행에서 요청당 DB CPU 시간은 8.43ms에서 6.35ms로 줄었습니다. 두 값은 함께
> 관측된 결과이고, 읽은 행이 늘어난 원인을 따로 분해하지는 않았습니다. 당시 버퍼풀 적중률이 100%라
> 디스크 읽기는 없었는데, 데이터가 버퍼풀보다 커지면 DTO 프로젝션이나 작성자 일괄 조회를 다시 비교해야
> 합니다.

**무너지는 자리.** "AI 없이 지금 페치 조인 쿼리를 쓸 수 있나요"라고 물으면 그 자리에서 씁니다. `@BatchSize`를

### 카드 8. 혼합 시나리오 전체 p95 226.7 → 34.3ms 관측, 단계별 동일 조건 5회 실행

**이력서 문장.** 혼합 시나리오 전체 p95 226.7 → 34.3ms 관측, 단계별 동일 조건 5회 실행

**먼저 이해할 것.** p95는 응답 시간을 작은 순으로 늘어놓았을 때 95% 지점의 값입니다. 요청 100개 중
느린 5개를 뺀 나머지가 이 시간 안에 끝났다는 뜻입니다. 평균은 극단값에 가려지지만 p95는 느린 쪽을
보여 줍니다. 혼합 시나리오는 게시글 목록, 상세, 댓글 목록, 반응 같은 사용자 행동을 비율대로 섞어
보내는 부하 시나리오입니다. 5회 실행은 같은 조건으로 다섯 번 재서 우연한 변동보다 큰 차이인지 보려는
것입니다.

**예상 질문.** 226.7ms에서 34.3ms는 어떤 조건에서 잰 값인가요?

> 로컬 Docker 환경에서 앱 CPU 2코어, 커넥션 풀 10개, 게시글 1만 건 규모의 medium 생성 데이터셋으로
> 쟀습니다. 부하는 서버 응답과 무관하게 초당 시나리오 4개를 새로 시작하는 open 방식이고, 시나리오
> 하나에 요청이 여러 개 들어 있습니다. 180초 예열 뒤 5분 측정입니다. 이 조건을 고정하고
> 단계마다 5회씩 실행했습니다. 226.7ms와 34.3ms는 혼합 시나리오 전체의 회차별 p95를 평균한 값입니다.
> 반응 일괄 조회 뒤가 57.2ms, 작성자 페치 조인 뒤가 34.3ms입니다.

**꼬리 1 (무엇을).** 한 번에 잰 값인가요?

> 아닙니다. 두 실험을 이은 값입니다. 1단계에서 고친 뒤로 잰 5회를 2단계에서는 고치기 전 값으로 그대로
> 썼습니다. 그래서 226.7, 57.2, 34.3 세 값이 실험 둘에서 나옵니다. 명령, 데이터셋, 부하 조건이 같았고
> 사이에 바뀐 코드는 enum 이름 변경 하나였기 때문에 이어서 비교했습니다. 두 실험을 잇는 판단은
> 제가 했습니다. 검사기는 각 실험 안의 전후만 비교했습니다.

**꼬리 2 (왜 그 선택).** open arrival-rate가 무엇이고 왜 그걸 썼나요?

> 부하를 주는 방식이 두 가지 있습니다. 가상 사용자 수를 고정하는 closed 방식은 사용자가 응답을 기다린
> 뒤 다음 요청을 보내서, 서버가 느려지면 부하가 저절로 줄어듭니다. 느린 순간을 봐주는 셈입니다. 초당
> 요청 수를 고정하는 open 방식은 응답과 무관하게 계속 보내서 실제 트래픽에 가깝습니다. 개선 전후를
> 같은 부하로 비교하려면 서버 상태에 따라 부하가 변하면 안 되므로 open 방식을 썼습니다.

**꼬리 3 (한계).** 5회로 충분한가요? 통계적으로 유의한가요?

> 유의성 검정은 하지 않았습니다. 평균, 표준편차, 변동계수만 계산했습니다. 5회 세트의 변동계수가 5~13%
> 정도였고 개선폭은 그보다 훨씬 커서 우연으로 보기 어렵다고 판단했지만, 표본 5개로 잰 표준편차 자체의
> 불확실성이 크다는 것을 압니다. 그래서 p95 수치는 같은 조건 5회에서 관측한 기술 통계로만 제시합니다.

**무너지는 자리.** "그럼 40% 개선이 우연이 아니라는 근거가 뭔가요"까지 오면 "쿼리 수 1,507에서 4는
결정적인 값이라 우연이 아니고, p95는 그 결과로 함께 움직인 관측값입니다"로 답합니다. 쿼리 수가 주된
근거이고 p95는 보조 근거입니다.

**말하면 안 되는 것.** "84.9% 개선했다"를 단독으로 말하지 않습니다. 두 실험을 이은 값이라는 설명 없이
말하면 꼬리 1에서 무너집니다. "MDE 16%"도 말하지 않습니다. 근거가 약해 제출본에서 뺐습니다.

### 카드 9. 영속성 컨텍스트를 비운 뒤 페치 조인 제거 시 실패하는 쿼리 수 테스트 추가

**이력서 문장.** 영속성 컨텍스트를 비운 뒤 페치 조인 제거 시 실패하는 쿼리 수 테스트 추가

**먼저 이해할 것.** 영속성 컨텍스트는 JPA가 한 트랜잭션 안에서 다룬 엔티티를 담아 두는 메모리 공간입니다.
1차 캐시라고도 부릅니다. 같은 ID의 엔티티를 다시 찾으면 DB에 가지 않고 여기서 꺼냅니다. 테스트에서
댓글과 작성자를 저장하면 그 작성자들이 이 공간에 남습니다. 그 상태로 댓글을 조회하면 작성자 쿼리가
나가지 않아서, 페치 조인이 없어도 쿼리 수가 적게 나옵니다. `em.clear()`는 이 공간을 비우는 호출입니다.

**예상 질문.** 그 테스트는 무엇을 검증하나요?

> 페치 조인이 실제로 쿼리를 줄이는지를 검증합니다. 테스트 준비 단계에서 저장한 작성자가 영속성

**예상 질문.** 비교 조건은 무엇이고 어떻게 구분했나요?

> 해시값)과 실행 전 DB 상태, 부하 프로파일, 부하 발생 위치, 예열과 측정과 종료 구간입니다. 경고만
> 붙이는 조건은 측정 중 호스트 상태를 재는 기준 벤치마크를 같이 돌렸는지, k6 지표를 외부로 전송했는지,
> 앱 이미지 지문, 스크립트 지문입니다. 어느 조건이 어느
> 묶음인지는 코드의 if 문 대신 표 하나에 적었습니다.

**꼬리 1 (무엇을).** 데이터셋 지문이라는 게 무엇인가요?

> 지문이 달라집니다. 실행 전 DB 상태도 같은 지문에 포함해서, 직전 실행이 데이터를 바꿔 놓은 상태에서
> 시작한 실행은 원래 상태에서 시작한 실행과 구분됩니다.

**꼬리 2 (왜 그 선택).** 조건에 관측값을 넣으면 안 되는 이유가 있나요?

> 분리되고 검사를 피하게 됩니다. 그래서 실행 전에 정한 시나리오, 부하, 데이터만 조건으로 씁니다.
> 실행 결과는 판정 대상이지 조건이 아닙니다.

**꼬리 3 (한계).** 조건이 늘어나면 과거 실행과 계열이 갈라지지 않나요?

> 옛 조건의 계열과 새 조건의 계열이 섞이지 않게는 했는데, 갈라진 뒤에
> 옛 실행을 새 계열로 옮기는 방법은 아직 없습니다. 지금은 조건이 바뀌면 그 뒤 실행부터 새 기준선을

> 채워 넣는 이관 작업이 필요합니다.

### 카드 18. 구현 전에 실패 조건과 수용 기준 정의, 변경 전후에 같은 측정과 검증 반복

**이력서 문장.** 구현 전에 실패 조건과 수용 기준 정의, 변경 전후에 같은 측정과 검증 반복

**먼저 이해할 것.** 수용 기준은 "이 조건을 만족하면 이 변경을 완료로 본다"는 기준입니다. 미리 정해 두지 않으면
고친 뒤에 좋아 보이는 수치를 골라 성공이라고 말하게 됩니다. 실패 조건은 "이 상황이 나오면 변경이
틀렸다"는 조건입니다. 이 프로젝트에서는 N+1 개선에 이 방식을 그대로 적용했습니다.

**예상 질문.** 수용 기준을 먼저 정한다는 게 실제로 어떻게 한 건가요?

> N+1 개선에서는 세 가지를 먼저 정했습니다. 요청당 쿼리 수가 댓글 수와 작성자 수에 비례하지 않을 것,
> 페치 조인을 빼면 실패하는 테스트가 있을 것, 응답 내용이 DB와 전량 일치하고 익명 작성자 정보가
> 새지 않을 것입니다. 이 세 가지를 만족해야 완료로 보기로 했고, 고친 뒤 셋 다 확인했습니다. 그다음에
> p95를 같은 조건으로 5회 재서 결과가 따라왔는지 봤습니다.

**꼬리 1 (무엇을).** 실패 조건의 예를 들어 주세요.

> 조회수 반영에서는 DB 반영이 실패했을 때 Redis 증가분이 사라지면 실패라고 정했습니다. 이 조건을
> 테스트로 만들고 옛 코드에서 실패하는 것을 확인한 뒤 고쳤습니다.

**꼬리 2 (왜 그 선택).** 왜 이 방식이 필요했나요?

> 잘못 추적한 경험 때문입니다. 지연 원인을 호스트 환경으로 짐작하고 닷새를 썼는데 원인은 포화였습니다.
> 그 뒤로는 먼저 무엇이 나오면 가설이 틀린 것인지 정하고 측정합니다.

**꼬리 3 (한계).** 이 방식이 안 맞는 경우도 있나요?

> 기준을 정하는 데 시간이 들어서 작은 수정에는 과합니다. 그리고 기준 자체를 잘못 정하면 잘못된 기준을
> 통과한 것이 됩니다. 저도 이 프로젝트 초기의 회귀 검사가 시나리오 이름만 조건으로 두어서 잘못된
> 기준선을 고른 적이 있습니다.

**무너지는 자리.** 추상적으로 들리기 쉬운 줄입니다. 반드시 N+1이나 조회수의 구체 사례로 답합니다. 수용
기준 세 가지에 왜 p95가 없는지 물으면 "쿼리 수는 결정적인 값이라 기준으로 삼을 수 있고, p95는 실행마다
변동이 있어 기대 결과로만 두었습니다. p95가 안 움직였다면 쿼리 수가 줄어도 병목이 다른
곳에 있다는 뜻이라 완료로 보지 않았을 겁니다"라고 답합니다.

**말하면 안 되는 것.** "TDD를 했다". 기준을 먼저 정한 것입니다.

### 카드 19. AI 에이전트에 구현·테스트·문서 초안을 맡기고 실패 테스트·DB 대조·실측으로 결과 검증

### 카드 20. 검토한 대안과 채택하지 않은 이유, 변경 후 부작용 기록

**예상 질문.** 채택하지 않은 대안을 왜 기록하나요?

> 조인 뒤 MySQL이 읽은 행이 22.9% 늘었다는 것과, 데이터가 버퍼풀보다 커지면 다른 대안을 다시 비교해야
> 한다는 조건입니다. 다음 사람이 그 조건이 왔을 때 어디서부터 보면 되는지 알 수 있습니다.

**꼬리 1 (무엇을).** 기록은 어디에 어떤 형식으로 남기나요?

> 이 기록에서 가져왔습니다.

**꼬리 2 (왜 그 선택).** 기각한 결정의 예를 하나 더 들어 주세요.

> 규칙은 2026년 9월 개선 기록부터 적용했고, 그 전인 8월 조사 기록은 날짜와 실행 번호로만 식별됩니다. 기록을 코드와 같이 고치지 않으면 어긋납니다. 그래서 개선 문서에 실행 ID를 넣어서 문서의

**무너지는 자리.** "결함 기록 183건" 같은 숫자는 말하지 않습니다. 세는 기준이 정해지지 않아 제출본에서 뺐습니다.

## 3. 정직 답변집

해 본 적 없는 것을 물으면 세 단계로 답합니다. 경계를 인정하고, 원리로 추론하고, 확인 방법을 말합니다.
최악은 둘입니다. 아는 척하다 두 번째 질문에서 무너지는 것과, "모르겠습니다" 한마디로 대화를 끊는 것입니다.

### 3.1 답변 틀

| 단계 | 문장 형태 | 예 |
|---|---|---|
| 1 경계 인정 | "직접 해 본 적은 없습니다" | "A/B 테스트를 운영해 본 적은 없습니다" |
| 2 가장 가까운 경험 | "다만 제 프로젝트에서 ~는 겪었습니다" | "실험 결과를 믿어도 되는 조건을 판정하는 문제는 성능 실험에서 겪었습니다" |
| 3 원리로 추론 | "원리로 추론하면 ~일 것 같습니다" | "A/B에서도 대조군이 유효하지 않으면 결과는 의미가 없다고 봅니다" |
| 4 확인 방법 | "실제로는 ~로 확인하겠습니다" | "실제 절차는 팀의 실험 문서와 통계 기준으로 확인하겠습니다" |

감점이 되는 답 네 가지입니다. 요구사항을 묻지 않고 답부터 하는 것, 기술 이름만 나열하는 것("Kafka와
Redis로 하겠습니다"), 대가를 말하지 않고 단정하는 것, 심화 질문에서 화제를 돌리는 것입니다.

### 3.2 운영 트래픽과 실사용자 부재

**질문.** 트래픽이 작은데 이 방법이 여기서 통할까요?

> 트래픽 규모는 작았습니다. 대신 그 규모에서 성립하는 판정 절차를 만들었습니다. 그리고 이 방법은
> 큰 시스템에서 오히려 더 필요하다고 생각합니다. 코드를 읽으면 의심 목록은 만들 수 있지만 그 목록에
> 순위를 매길 수는 없습니다. 제 N+1도 코드로 찾을 수 있는 종류였는데, 그것이 요청당 1,507개 중 몇
> 개인지는 세어야 나왔습니다. 큰 환경으로 옮기려면 부하 발생기 여러 대와 서버 간 시계 동기화가
> 추가로 필요하고, 판정 로직 자체는 그대로 씁니다.

**질문.** 큰 시스템에는 APM이 요청당 쿼리 수를 이미 세어 줍니다. 본인 계측의 차별점은 무엇인가요?

> 세는 것 자체는 APM이 더 잘합니다. 제가 만든 것은 센 값을 언제 믿어도 되는지 판정하는 부분입니다.
> 조건이 같은 실행끼리만 비교하고, 포화 상태에서 잰 값은 지연 비교에서 빼는 규칙입니다. APM이 있는
> 환경이라면 세는 부분은 APM에 맡기고 판정 부분만 그 위에 얹으면 됩니다.

**질문.** 고가용성 서비스를 운영해 본 적이 있나요?

> 사용자 규모가 있는 서비스를 운영해 본 적은 없습니다. 제가 문제로 잡은 것은 개발자 판단의
> 정확성이었습니다. 성능이 좋아졌다고 말하기 전에 그 말이 사실인지 판정하는 절차를 만들었고, 실제로
> 제 판단이 틀렸을 때 그 절차가 저를 반박했습니다. 피드처럼 실험을 자주 여는 조직에서는 이 문제가
> 사용자 가치와 직결된다고 생각합니다. 잘못된 실험 결과로 내린 결정은 사용자 경험을 나쁜 쪽으로
> 바꾸기 때문입니다.

**질문.** 포화 판정을 실제 서비스에서는 어떻게 쓰나요?

> 지금 구현은 로컬 부하 테스트용입니다. 운영에서는 두 가지로 쓸 수 있다고 봅니다. 하나는 배포 전
> 부하 테스트에서 포화 실행을 걸러내 비교를 막는 용도이고, 다른 하나는 운영 지표에 같은 신호를 붙여
> 커넥션 풀 대기와 CPU 제한 비율로 포화에 가까운 인스턴스를 표시하는 용도입니다. 운영 적용은 생각만
> 있고 해 보지 않았습니다.

### 3.3 다중 인스턴스와 분산 환경

**먼저 이해할 것.** 현재 프로젝트는 서버 한 대를 전제로 만들었습니다. 서버가 두 대가 되면 스케줄러가 두 대에서
동시에 돌고, 커밋 뒤 이벤트는 각 서버의 프로세스 안에서만 실행됩니다. Redis의 `INCR`은 서버가 몇 대든
안전하게 동작하지만, 60초 스케줄러의 "읽고 반영하고 차감"은 두 대가 겹치면 중복 반영이 생깁니다.

**질문.** 스케줄러가 인스턴스 두 대에서 동시에 돌면 어떻게 되나요?

> 지금 코드는 단일 인스턴스 전제라 두 대에서 동시에 돌면 같은 증가분을 두 번 반영할 수 있습니다.
> 조회 자체의 `INCR`은 Redis가 원자적으로 처리해서 안전하고, 문제는 60초마다 읽고 반영하고 차감하는
> 정산 구간입니다. 해결 방향은 두 가지입니다. 첫째, Redis에 `SET NX PX`로 만료 시간이 있는 잠금 키를
> 두고 잠금을 얻은 인스턴스만 정산하게 하는 분산 잠금입니다. NX는 키가 없을 때만 만들라는 뜻이고
> PX는 밀리초 단위 만료를 붙이라는 뜻입니다. 해제할 때는 자기가 건 잠금인지 값으로
> 확인해야 합니다. 둘째, ShedLock 같은 라이브러리로 같은 일을 DB 테이블로 하는 방법입니다. 둘 다
> 구현하지 않았고, 하게 되면 잠금 만료 시간을 정하는 것이 첫 결정입니다. 정산 시간보다 길게 잡으면
> 잠금을 가진 인스턴스가 죽었을 때 그만큼 정산이 멈추고, 짧게 잡으면 정산 도중 만료돼 두 대가 겹칩니다.
> 그래서 만료는 정산 시간의 몇 배로 두되 정산이 길어지면 잠금을 연장하는 방식이 무난하다고 봅니다.
> 조회수 정산은 한 번 더 반영돼도 근사값 범위라 겹침의 피해가 작은 편입니다.

**질문.** 커밋 뒤 이벤트는 프로세스 안인가요? 그 프로세스가 죽으면요?

> 프로세스 안입니다. 같은 스레드에서 커밋 직후 동기로 실행됩니다. 프로세스가 죽으면 그 이벤트는
> 사라지고 재처리는 없습니다. 인기 점수는 5분 스케줄러가 상위 50개를 다시 계산해서 순위권 글은
> 맞춰지지만, 알림처럼 한 번 놓치면 끝인 이벤트는 아웃박스가 필요합니다. 3.4에서 이어 말씀드리겠습니다.

**질문.** 인스턴스가 여러 대일 때 인기글 점수 갱신은 안전한가요?

> 점수 갱신은 게시글의 현재 카운트를 읽어서 점수를 계산하고 Sorted Set에 넣는 방식입니다. 두 대가
> 동시에 같은 글을 갱신하면 나중 것이 덮어쓰지만, 둘 다 같은 DB 값을 읽었다면 결과는 같습니다. 문제가
> 되는 것은 증감 연산을 쓰는 경우인데, 지금은 절대값을 다시 계산해 넣는 방식이라 덮어써도 틀리지
> 않습니다. 다만 이건 코드를 보고 추론한 것이고 두 대에서 실제로 돌려 본 적은 없습니다.

### 3.4 Kafka와 아웃박스 패턴

**먼저 이해할 것.** 아웃박스 패턴은 DB 변경과 "이벤트를 보내야 한다"는 기록을 같은 트랜잭션 안에서 같은 DB의
outbox 테이블에 함께 적는 방법입니다. 별도 작업이 그 테이블을 읽어 메시지 큐로 보내거나 직접 처리합니다.
DB 커밋이 됐으면 이벤트 기록도 반드시 남아 있으므로, 프로세스가 죽어도 나중에 다시 처리할 수 있습니다.
대가는 outbox 테이블을 읽는 작업이 하나 더 생기고, 이벤트 처리가 그만큼 늦어지고, 처리한 행을 정리해야
한다는 점입니다. Kafka는 이벤트를 디스크에 보관하고 여러 소비자가 순서대로 읽게 해 주는 메시지 시스템입니다.

**질문.** Kafka를 써 봤나요?

> 써 본 적 없습니다. 제 프로젝트는 커밋 뒤 이벤트를 같은 프로세스 안에서 처리하고, 프로세스가 죽으면
> 이벤트가 사라집니다. 지금 규모에서는 그 손실을 5분 재계산으로 덮었지만, 놓치면 안 되는 이벤트가
> 생기면 아웃박스 테이블에 먼저 적고 별도 작업이 Kafka 같은 큐로 보내는 구조가 필요하다고 이해하고
> 있습니다. Kafka 자체의 운영, 파티션 설계, 컨슈머 그룹은 문서 수준으로만 압니다.

**질문.** 아웃박스를 쓰면 무엇이 달라지나요?

> DB 커밋과 이벤트 기록이 한 트랜잭션에 묶여서, 커밋됐는데 이벤트가 없는 상태가 사라집니다. 대신
> 이벤트 처리가 outbox를 읽는 주기만큼 늦어지고, 같은 이벤트가 두 번 처리될 수 있어서 받는 쪽이
> 멱등해야 합니다. 제 인기 점수 갱신은 절대값을 다시 계산해 넣는 방식이라 두 번 처리돼도 결과가 같아
> 멱등합니다. 알림은 두 번 가면 안 되므로 이벤트 ID로 중복을 걸러야 합니다. outbox를 읽는 작업이 두 대에서
> 돌면 같은 행을 둘 다 읽을 수 있는데, 읽을 때 행을 잠그고 이미 잠긴 행은 건너뛰는 `SELECT ... FOR
> UPDATE SKIP LOCKED`로 나눠 읽는 방법을 알고 있습니다. 써 본 적은 없습니다.

### 3.5 A/B 테스트

**질문.** A/B 테스트 경험이 있나요?

> A/B 테스트 경험은 없습니다. 다만 실험 결과를 신뢰할 수 있는 조건을 판정하는 문제를 성능 실험에서
> 직접 겪고 코드로 해결했습니다. 대조군을 잘못 골라 조건이 다른 실행을 회귀라고 보고한 사건이 있었고,
> 그 뒤로 비교해도 되는 실행만 고르는 검사를 만들었습니다. A/B에서도 대조군이 유효하지 않으면 결과는
> 의미가 없다는 점은 같다고 봅니다. 실제 A/B의 배정, 표본 수 계산, 유의성 검정은 팀의 절차를 배워야
> 합니다.

**질문.** 성능 실험과 제품 A/B 테스트는 무엇이 다른가요?

> 성능 실험은 같은 시스템을 조건을 바꿔 여러 번 재고, 비교 대상이 시간축의 다른 실행입니다. A/B는
> 같은 시간에 사용자를 나눠 두 버전을 동시에 노출하고, 비교 대상이 사용자 집단입니다. 그래서 A/B에는
> 배정이 무작위인지, 두 집단이 서로 영향을 주지 않는지 같은 문제가 추가됩니다. 제가 겪지 않은 부분은
> 그 배정과 간섭 문제입니다. 겹치는 부분은 아무것도 바꾸지 않았을 때의 자연 편차를 먼저 알아야 차이를
> 말할 수 있다는 점입니다. 당근 피드실이 A/A 테스트를 한다고 읽었는데, 그게 바로 이 자연 편차를 재는
> 절차라고 이해했습니다. 제 실험에서 그에 해당하는 것은 코드를 바꾸지 않고 같은 조건으로 5회 반복해
> 변동계수를 잰 세트입니다. 그 값보다 작은 차이는 개선으로 세지 않았습니다.

**질문.** 실험을 동시에 여러 개 수용하려면 서빙 구조가 어때야 하나요?

> 실험 배정은 해 본 적 없다는 것을 먼저 말씀드립니다. 제 프로젝트에서 한 것은 회귀 판정 임계값을 코드에서
> 빼서 JSON 파일 하나로 두고 배포 없이 바꾸는 것까지입니다. 원리로 추론하면, 실험마다 어떤 사용자가 어느
> 군인지 결정하는 배정 계층과 그 결정에 따라 내용을 바꾸는 서빙 계층이 분리돼야 실험을 여러 개 겹칠
> 수 있을 것 같습니다. 실제 구조는 팀에서 배워야 합니다.

### 3.6 Go, Kubernetes, gRPC, MongoDB

> Go는 써 본 적 없습니다. 측정 도구를 Go로 옮길지 검토한 기록은 있는데, 성능 명분은 이 도구에서 근거가
> 없다고 먼저 기각했고 일부만 옮기는 계획을 적은 뒤 실행하지 않았습니다. Kubernetes, gRPC, MongoDB도 실무 경험은 없고
> 개념 수준입니다. 배우는 데 시간이 걸린다는 것을 알고 있고, Java와 Spring에서 문제를 계측하고 고쳐 본
> 방식은 언어가 바뀌어도 같다고 생각합니다.

면접 전에 새 언어를 얕게 공부해 아는 척하지 않습니다. 얕은 지식은 우대 요건을 채우지 못하고 "겉만 아는
사람"이라는 증거만 됩니다.

### 3.7 개인화, 추천, 다종 콘텐츠 피드

**질문.** 콘텐츠 타입이 세 개로 늘면 데이터 모델을 어떻게 바꾸나요?

> 지금 인기글은 게시글 한 종류만 다룹니다. 여러 종류가 되면 순위표의 항목이 콘텐츠
> 종류와 게시글 ID의 조합이어야 하고, 조회할 때 종류별로 다른 저장소에서 내용을 가져와 합쳐야 합니다. 그때
> 문제는 한 종류의 저장소가 느리면 전체 응답이 그 속도에 맞춰진다는 점이고, 종류별 타임아웃과 빠진
> 항목을 뺀 채 응답하는 규칙이 필요할 것 같습니다. 이건 설계해 본 적이 없고 추론입니다.

**질문.** 한 콘텐츠 공급자가 느릴 때 전체 피드를 어떻게 보호하나요?

> 겪어 보지 않았습니다. 제 프로젝트에서 겪은 것은 쓰기 결함 하나가 읽기 경로 장애로 번진 사건입니다.
> 스크랩 토글의 경쟁 상태로 같은 사용자와 게시글에 스크랩 행이 두 개 생겼고, 게시글 상세 조회가 그
> 스크랩을 단건으로 읽다가 결과가 2건이라는 예외를 던져 그 게시글 상세가 계속 500을 냈습니다. 원인이
> 되는 구간을 격리하지 않으면 무관한 조회까지 따라간다는 것을 그때 봤습니다. 원리로 추론하면 공급자마다
> 시간 제한을 두고, 제한을 넘긴 공급자는 이번 응답에서 빼고, 연속 실패하면 잠시 호출하지 않는 회로
> 차단이 필요합니다. 지금 제 서비스는 DB 커넥션을 기본값 30초 동안 기다린 뒤 실패하는데, 실패 시
> 동작을 그려 보다가 기본값을 그대로 쓰고 있었다는 것을 알았습니다. [[커넥션 획득 타임아웃을 지금
> 얼마로 두었는지, 그대로면 그대로라고]]

**질문.** 개인화나 추천을 해 봤나요?

> 해 본 적 없습니다. 인기글은 모든 사용자에게 같은 순위를 보여 줍니다. 규칙을 코드 밖으로 빼서
> 배포 없이 바꾸는 구조는 회귀 판정 임계값 파일에서 해 봤지만, 사용자별로 다른 순위를 만드는 것은 다른
> 문제입니다.

### 3.8 계측 도구를 직접 만든 이유와 프로파일러 부재

**질문.** 측정 시스템을 왜 직접 만들었나요? 있는 도구를 쓰지 그랬어요.

> 부하 도구, 지표 수집, 대시보드는 있는 것을 썼습니다. k6, Prometheus, Grafana입니다. 직접 만든 것은
> 그 사이를 잇는 부분입니다. 실행 조건을 기록하고, 조건이 같은 이전 실행을 골라 비교하고, 포화 여부를
> 붙여 보고서를 내는 부분입니다. 이 부분은 제 실행 조건과 데이터셋에 묶여 있어서 범용 도구에 없었습니다.
> 대가는 그 코드를 유지보수해야 한다는 것이고, 판정 로직에 단위 테스트를 두어 감당했습니다. 그 테스트는
> 규칙을 구현대로 적용하는지를 검증하는 것이고, 규칙 자체가 맞는지는 잘못 판정한 사건이 나올 때마다
> 사후에 고쳤습니다. 기준선 오선택이 그 예입니다.

**질문.** 코드는 안 읽으시나요? 계측이 없으면 못 찾나요?

> 읽습니다. 순서가 반대일 뿐입니다. 계측이 어디를 볼지 알려 주고, 코드는 왜 그런지 확인하러 엽니다.
> 계측이 없으면 의심 목록은 만들 수 있지만 순위를 매기지 못합니다. 그리고 지금 계측은 요청 단위와 DB
> 단위까지라, 메서드 단위로 어디서 시간을 쓰는지는 못 내려갑니다. 프로파일러 계층이 없는 것이 현재
> 한계입니다.

### 3.9 사용자 가치

**질문.** 실사용자가 없는데 사용자 문제를 어떻게 정의했나요?

> 실사용자 지표는 없습니다. 제가 정한 사용자 문제는 두 가지였습니다. 댓글이 많은 글을 열 때 느린
> 것과, 조회수처럼 눈에 보이는 숫자가 실제와 다르게 사라지는 것입니다. 둘 다 사용자가 직접 겪는
> 현상이라 우선순위를 여기에 뒀습니다. 다만 그 판단이 맞는지 사용자 데이터로 확인하지는 못했습니다.
> 댓글이 많은 글이 느린 문제라면 페이징이 더 직접적인 답인데, 이번에는 쿼리 수를 먼저 고치고 페이징은
> 익명 번호 규칙 때문에 미뤘습니다. 사용자 문제와 고친 범위가 완전히 겹치지는 않습니다.

**질문.** 실제 사용자가 있었다면 무엇을 지표로 봤을 건가요?

> 인기글이라면 인기글 목록에서 글을 연 비율과 그 글에 머문 시간, 그리고 인기글을 본 사용자가 다음 날
> 다시 오는 비율을 봤을 것 같습니다. 성능이라면 댓글 목록 응답 p95와 그 값이 나쁜 사용자의 이탈률을
> 같이 봐야 합니다. 어느 지표가 맞는지는 팀의 실험 문서에서 배워야 합니다.

**질문.** 인기글이 클릭을 늘리고 만족도는 낮추면 무엇을 선택하나요?

> 클릭만 보고 결정하지 않겠습니다. 클릭이 늘고 만족도가 떨어지는 조합은 자극적인 글이 위로 올라오는
> 경우일 가능성이 커서, 재방문이나 숨기기 같은 부정 신호를 같이 봐야 한다고 생각합니다. 당근 피드실이
> 숨기기를 학습에 반영해 숨기기 사용량을 줄였다는 글을 읽었는데, 그 방향이 맞다고 봅니다.

**질문.** 사용자에게 가치가 있을지 스스로 물어서 만들거나 만들지 않기로 한 것이 있나요?

### 3.11 우리 팀에서 무엇을 하고 싶나

**먼저 이해할 것.** Feed Infra 팀은 기술 블로그에서 세 가지 서비스를 밝혔습니다. 콘텐츠를 섞고 정책을 적용하는

> 세 서비스 중 Feed Entity Service가 제 경험과 가장 가깝습니다. 여러 공급자에서 항목을 모아 저장하는
> 서비스라고 이해했는데, 저장한 항목을 피드 요청마다 꺼내 줄 때 공급자 수나 항목 수에 따라 조회 횟수가

> 상수로 만든 경험이 그 문제의 작은 버전이라고 생각합니다. 실제 구조는 블로그 수준으로만 알고 있어서

## 4. 라이브 코딩

### 4.1 확인된 사실

라이브 코딩의 진행 방식(시간, 형식)까지 적은 당근 후기는 한 건입니다. 이력서 질문과 같은 세션에서 1:1로 약 80분 동안 진행됐고, 난이도는
쉬웠지만 긴장으로 풀이가 순조롭지 않았다고 썼습니다. 그 지원자는 주석으로 생각 과정을 적으며 풀었고
50분 뒤 합격 통보를 받았습니다. 난이도가 낮다면 변별점은 과정입니다.

문제 원문은 알 수 없습니다. 라이브 코딩이나 과제를 치른 후기 5건 중 4건이 문제를 공개하지 않았습니다.
특정 문제를 외우는 대신 어떤 문제가 와도 같은 절차로 푸는 습관을 만듭니다.

다른 회사의 백엔드 라이브 코딩 사례 하나는 문제 네 개가 단순 구현, 클래스 설계, 추상화, 동시성 순서로
확장되는 구조였습니다. 당근이 이 유형인지 알고리즘 유형인지는 확인되지 않았습니다. 둘 다 대비하되 비중은
확장 유형에 둡니다. 면접관이 밝힌 평가 목표는 검색 등을 활용해 문제를 해결하는지, 문제가 생겼을 때
소통하는 방식, 기본 Java 능력 세 가지였습니다.

### 4.2 실전 절차 다섯 단계

| 단계 | 할 일 | 흔한 실수 |
|---|---|---|
| 1 문제 이해 | 입력과 출력의 타입, 범위, 예시를 되묻는다. 무조건 두 개는 묻는다 | 대충 읽고 짜다가 중간에 다시 푼다 |
| 2 계획 말하기 | "이 자료구조로 이렇게 풀겠습니다"를 먼저 말한다. 단순한 방법과 나은 방법을 같이 제시해 방향이 틀리면 힌트를 받는다 | 코드부터 쓰다 방향을 잃는다 |
| 3 말하며 코딩 | 생각을 계속 소리 내어 말한다. 의미 있는 이름, 짧은 메서드 | 빨리 풀려고 가독성을 버린다 |
| 4 검증 | 주어진 예시에 더해 빈 입력, 하나짜리 입력, 경계값을 직접 넣어 본다 | 테스트 없이 끝낸다 |
| 5 복잡도와 개선 | 시간과 공간 복잡도, 개선 방향을 말한다. 시간이 없으면 말로만이라도 | 분석 없이 끝낸다 |

| 침묵 | 면접관이 어디서 막혔는지 알 수 없다 | "지금 두 가지 방법 사이에서 고민 중입니다. 하나는 ~, 다른 하나는 ~입니다" |

| 못 풀었을 때 과정도 못 보여준다 | 평가할 재료가 없다 | "여기까지는 됐고, 남은 부분은 이렇게 하려고 했습니다"라고 주석으로 남긴다 |

웹 에디터가 로컬 IDE와 달라 자동 완성이 없거나 느릴 수 있습니다. 브라우저 에디터로 미리 한 번 풀어 봅니다.

### 4.5 연습 세트 A. 조회수 카운터

내 프로젝트의 조회수 버퍼와 같은 문제입니다. 네 단계로 확장합니다.

| 단계 | 요구사항 | 무엇을 보여 주나 |
|---|---|---|
| 1 단순 구현 | 게시글 ID를 받아 조회수를 1 올리고, ID로 조회수를 돌려주는 함수 | `Map<Long, Long>` 사용, 없는 ID 처리 |
| 2 클래스 | `ViewCounter` 클래스로 묶고 증가, 조회, 전체 초기화 메서드 | 상태를 가진 객체, 불변 반환 |
| 3 추상화 | 저장소를 인터페이스로 분리. 메모리 구현과 Redis 구현을 바꿔 끼울 수 있게 | 인터페이스 추출, 생성자 주입 |
| 4 동시성 | 스레드 여러 개가 같은 ID를 동시에 올려도 정확해야 함 | 경쟁 상태 설명, 원자 연산 선택 |

4단계에서 말할 것입니다. `map.put(id, map.get(id) + 1)`은 읽고 더하고 쓰는 세 동작이 분리돼 있어 두
스레드가 겹치면 한 번이 사라집니다. 해결은 세 가지가 있고 각각의 대가를 말합니다.

```java
// 방법 1. synchronized: 단순하지만 모든 ID가 한 잠금을 공유해 병렬성이 없다
public synchronized void increase(long id) { counts.merge(id, 1L, Long::sum); }

// 방법 2. ConcurrentHashMap.merge: 키별로 잠금이 나뉘어 병렬성이 높다. 채택
private final ConcurrentHashMap<Long, LongAdder> counts = new ConcurrentHashMap<>();
public void increase(long id) { counts.computeIfAbsent(id, k -> new LongAdder()).increment(); }

// 방법 3. AtomicLong: ID 하나면 충분하지만 ID마다 객체가 필요하다
```

내 프로젝트와 잇는 말: "제 프로젝트는 인기 게시글 한 행에 갱신이 몰리는 것을 피하려고 Redis의 `INCR`로
모았습니다. Redis에 두면 서버가 여러 대가 돼도 카운터가 한 곳에 있다는 장점도 있습니다."

### 4.6 연습 세트 B. 인기글 순위표

| 단계 | 요구사항 | 무엇을 보여 주나 |
|---|---|---|
| 1 단순 구현 | (게시글 ID, 점수) 목록을 받아 점수 상위 N개 ID 반환 | 정렬, N이 목록보다 클 때 |
| 2 클래스 | `RankingBoard`에 점수 갱신과 상위 N 조회 메서드 | 갱신 시 재정렬 비용 |
| 3 추상화 | 점수 계산을 인터페이스로 분리. 가중합 전략과 시간 감쇠 전략 | 전략 패턴, 규칙을 바꿔 끼움 |
| 4 동시성 | 갱신과 조회가 동시에 들어와도 조회가 깨지지 않게 | 읽기 중 구조 변경 문제 |

2단계에서 자료구조를 말합니다. 갱신마다 전체 정렬은 항목 수에 비례해 느리므로, 점수를 키로 하는
`TreeMap`이나 우선순위 큐를 쓰면 갱신이 로그 시간입니다. 4단계는 `ConcurrentSkipListMap`이나 읽기 쓰기
잠금(`ReentrantReadWriteLock`)을 말하고, 내 프로젝트에서는 이 자료구조를 Redis Sorted Set이 맡는다고 잇습니다.

### 5.2 Java와 Spring

후기 둘 다 첫 영역으로 꼽았고 현재 상태가 "얕음"입니다. 1순위로 채웁니다.

#### JVM 메모리 구조

힙은 객체가 사는 곳이고 GC가 관리합니다. 스택은 스레드마다 하나씩 있고 메서드 호출 프레임과 지역 변수가
들어갑니다. 메타스페이스는 클래스 정보가 들어갑니다. 스레드가 많으면 스택 메모리가 스레드 수만큼 듭니다.
내 경험: 컨테이너 메모리 제한을 힙보다 조금만 크게 두면 힙 밖 메모리 때문에 위험해집니다. 힙 1GB에 제한
1.5GB로 뒀다가 2.5GB로 올렸습니다.

#### GC 기본

새 객체는 young 영역에 생기고, 살아남으면 old 영역으로 옮겨집니다. G1 GC는 힙을 작은 구역으로 나눠 목표
멈춤 시간 안에서 수집합니다. 볼 지표는 최대 멈춤 시간과 전체 시간 중 GC가 차지한 비율입니다. 내 경험:
개선 실험의 5분 측정에서 GC 정지 합계가 0.25~0.38초로 0.1% 수준이었고, 편차 조사 때는 느린 세션과
정상 세션이 모두 1.3%로 같아서 GC를 원인에서 뺐습니다.

#### HashMap 동작

키의 `hashCode`로 버킷 위치를 정하고, 같은 버킷에 여러 키가 들어오면 연결 리스트로 잇다가 8개를 넘으면
트리로 바꿉니다. 항목이 용량의 75%를 넘으면 두 배로 늘리며 재배치합니다. `equals`와 `hashCode`를 같이
재정의해야 같은 키를 찾습니다. `HashMap`은 스레드 안전하지 않아서 여러 스레드가 쓰면
`ConcurrentHashMap`을 씁니다.

#### String과 StringBuilder

`String`은 불변이라 더할 때마다 새 객체가 생깁니다. 반복문에서 문자열을 이어 붙이면 `StringBuilder`를 씁니다.
같은 리터럴은 문자열 풀에서 재사용되므로 `equals`로 비교합니다. `==`는 참조 비교입니다.

#### Checked와 Unchecked 예외

Checked 예외는 컴파일러가 처리를 강제하고(`IOException`), Unchecked는 강제하지 않습니다(`RuntimeException`).
Spring의 `@Transactional`은 기본적으로 Unchecked 예외에서만 롤백하고 Checked 예외에서는 롤백하지
않습니다. 내 프로젝트는 도메인 오류를 전부 `RuntimeException`을 상속한 `CustomException` 하나로 던져서
롤백 규칙이 단순합니다.

#### 인터페이스와 추상 클래스

인터페이스는 "무엇을 할 수 있는가"의 계약이고 여러 개를 구현할 수 있습니다. 추상 클래스는 공통 구현을
물려주고 하나만 상속합니다. 내 경험: 저장소를 인터페이스로 두고 메모리 구현과 Redis 구현을 바꿔 끼우는
구조를 라이브 코딩 세트 A에서 씁니다.

#### synchronized, volatile, Atomic

`synchronized`는 한 번에 한 스레드만 블록에 들어가게 합니다. `volatile`은 변수 값을 항상 메인 메모리에서
읽고 쓰게 해서 가시성을 보장하지만 원자성은 보장하지 않습니다. `AtomicLong`은 CAS(비교 후 교체) 명령으로
잠금 없이 원자적 증가를 합니다. 카운터에는 `LongAdder`가 경합에 더 강합니다.

#### Spring IoC와 DI

객체를 만들고 연결하는 일을 컨테이너가 합니다. 생성자 주입을 쓰면 필드를 `final`로 둘 수 있고
순환 참조가 시작 시점에 드러납니다. 내 프로젝트는 `@RequiredArgsConstructor`와 `final`
필드로 통일했습니다.

#### Bean 생명주기와 스코프

인스턴스 생성, 의존성 주입, 초기화 콜백(`@PostConstruct`), 사용, 소멸 콜백(`@PreDestroy`) 순서입니다. 기본
스코프는 싱글톤이라 컨테이너에 하나만 있고, 그래서 Bean에 요청별 상태를 필드로 두면 안 됩니다. 프로토타입은
요청할 때마다 새로 만들고, 웹에는 request와 session 스코프가 있습니다.

#### DispatcherServlet 요청 처리 흐름

요청이 들어오면 DispatcherServlet이 받아서 HandlerMapping으로 어느 컨트롤러 메서드인지 찾고,
HandlerAdapter로 실행하고, 반환값을 HttpMessageConverter로 JSON으로 바꿔 응답합니다. 예외는
`@ControllerAdvice`의 `@ExceptionHandler`가 잡습니다. 내 프로젝트의 `GlobalExceptionHandler`가 그
자리이고 `CustomException`의 `ErrorCode`를 HTTP 상태로 바꿉니다.

#### Filter와 Interceptor

Filter는 서블릿 컨테이너 단계라 DispatcherServlet 앞에서 동작하고 Spring Bean이 아니어도 됩니다.
Interceptor는 DispatcherServlet 안에서 컨트롤러 앞뒤에 동작하고 핸들러 정보를 알 수 있습니다. 인증처럼
Spring Security가 관여하는 것은 Filter 체인에서 처리합니다. 내 프로젝트의 JWT 검증은
`TokenAuthenticationFilter`입니다.

#### AOP 프록시와 자기 호출

`@Transactional`과 `@Async`는 프록시가 메서드 호출을 가로채서 동작합니다. 같은 클래스 안에서 자기 메서드를
호출하면 프록시를 거치지 않아 적용되지 않습니다. 내 경험: 스케줄러 안에서 게시글별 트랜잭션을 나누려고
자기 메서드에 `@Transactional`을 붙였는데 적용되지 않아서 별도 서비스로 뺐습니다 (카드 5).

#### @Transactional 전파와 readOnly

기본 전파는 REQUIRED로, 이미 트랜잭션이 있으면 합류하고 없으면 새로 엽니다. REQUIRES_NEW는 항상 새
트랜잭션을 열어서 바깥이 롤백돼도 따로 커밋됩니다. `readOnly = true`는 변경 감지를 생략해 조회 비용을
줄이고 드라이버에 읽기 전용 힌트를 줍니다. 내 프로젝트는 커밋 뒤 이벤트 리스너에서 알림을 저장하는데,
그 시점에는 원래 트랜잭션이 이미 끝나 있어서 새 트랜잭션을 열지 않으면 저장이 커밋되지 않습니다. 그래서
알림 저장을 REQUIRES_NEW로 두었습니다.

### 5.3 JPA

#### 더티 체킹

영속성 컨텍스트가 엔티티를 처음 읽었을 때의 스냅샷을 갖고 있다가 커밋 시점에 비교해서 바뀐 것만 UPDATE를
만듭니다. 그래서 `save()`를 부르지 않아도 엔티티의 필드를 바꾸면 반영됩니다. 조회 전용 메서드에
`readOnly`를 붙이면 이 비교를 생략합니다.

#### OSIV

open-in-view가 켜져 있으면 영속성 컨텍스트가 컨트롤러와 뷰까지 살아 있어 지연 로딩이 어디서든 됩니다.
편하지만 DB 커넥션을 응답이 끝날 때까지 잡고 있어서 커넥션 풀 고갈을 악화시킵니다. 내 프로젝트는 OSIV가
기본값으로 켜져 있고, 계측 필터 주석에 그 영향을 적어 두었습니다. 정식 결함 항목으로는 아직 올리지
않았습니다.

#### 플러시 실패와 롤백 전용

유니크 제약 위반으로 플러시가 실패하면 영속성 컨텍스트에 깨진 엔티티가 남고 트랜잭션은 롤백 전용으로
표시됩니다. 같은 트랜잭션 안에서 예외를 잡아 복구해도 커밋 시점에 롤백됩니다. 그래서 JPA에서 "삽입해 보고
충돌하면 catch로 복구"는 성립하지 않고, 충돌을 DB 한 문장(upsert)으로 처리해야 합니다.

### 5.4 Database

#### 인덱스와 복합 인덱스

B+Tree 인덱스는 정렬된 키를 트리로 두고 리프를 연결 리스트로 이어서 같음 조건, 범위 조건, 정렬에 모두
씁니다. 복합 인덱스 (a, b, c)는 a, ab, abc 조건에서만 쓰이고 b만으로는 못 씁니다. 같음 조건 컬럼을 앞에,
정렬이나 범위 컬럼을 뒤에 둡니다. 내 프로젝트는 목록 쿼리에 맞춰 (board_id, is_valid, 정렬 컬럼) 인덱스를
두어 정렬을 인덱스가 대신하게 했습니다. 인덱스는 쓰기마다 갱신되므로 공짜가 아닙니다.

#### 커서와 오프셋 페이징

OFFSET n은 n행을 읽고 버리므로 뒤로 갈수록 느려지고, 그 사이에 삽입이 있으면 행이 밀리거나 중복됩니다.
커서 방식은 마지막으로 본 ID를 조건으로 넣어(`WHERE id < ? ORDER BY id DESC LIMIT n`) 인덱스로 바로
찾습니다. 정렬 키가 유일하지 않으면(좋아요 순) (like_count, id) 조합 커서가 필요합니다. 순위 점수처럼 값이
계속 바뀌는 정렬은 커서 기준 자체가 움직이므로 조회 시점의 순위를 고정한 스냅샷을 두거나 페이지 경계를
따로 정의해야 합니다.

#### 트랜잭션 ACID와 격리 수준

원자성, 일관성, 고립성, 지속성입니다. 격리 수준은 낮은 순으로 READ UNCOMMITTED(커밋 안 된 값을 읽음),
READ COMMITTED(같은 행을 두 번 읽으면 값이 달라질 수 있음), REPEATABLE READ(같은 행은 같게 보임, MySQL
기본), SERIALIZABLE(직렬 실행과 같음)입니다. MySQL InnoDB는 MVCC로 읽기는 잠금 없이 스냅샷을 봅니다.
핵심: 격리 수준은 읽기 이상을 막는 것이지 "확인하고 삽입" 경쟁을 막지 못합니다. 두 트랜잭션이 각자
스냅샷에서 "없음"을 보고 둘 다 삽입합니다.

#### 락과 데드락

레코드 락은 인덱스 행 하나, 갭 락은 행 사이 간격, 넥스트키 락은 둘의 합입니다. REPEATABLE READ에서 팬텀을
막는 데 갭 락을 씁니다. 데드락은 두 트랜잭션이 서로의 잠금을 기다리는 상태이고 InnoDB가 감지해 한쪽을
롤백합니다. 내 경험: 인기글 한 행에 카운터 UPDATE가 몰리는 핫 로우에서, 데이터 생성기가 동시 5개로
돌 때 데드락이 실제로 났고 생성기 쪽 재시도로 흡수했습니다. 앱 코드에는 재시도가 없고 카운터는 COUNT를
다시 읽어 맞춥니다.

#### Upsert

`INSERT ... ON DUPLICATE KEY UPDATE`는 유니크 인덱스에서 충돌 검사와 갱신을 한 문장으로 합니다. 삽입이면
영향 행 1, 갱신이면 2를 돌려주어 신규 여부를 원자적으로 알 수 있습니다. 값이 같아 실제로 바뀐 것이 없으면
드라이버 설정에 따라 0이나 1이 올 수 있어서 경계 조건을 확인해야 합니다. 내 프로젝트의 스크랩 토글이
이 값으로 신규와 재활성을 구분합니다.

#### 정규화와 비정규화

정규화는 갱신 이상을 막고, 비정규화는 읽기 경로를 짧게 합니다. 비정규화의 대가는 두 곳의 값을 맞춰야 하는
책임입니다. 내 프로젝트는 게시글 행에 좋아요 수, 댓글 수 같은 카운터를 둡니다. 좋아요 수를 +1이나 −1로
바꾸지 않습니다. 토글 트랜잭션 안에서 반응 행을 COUNT로 다시 세어 그 값으로 게시글 컬럼을 덮어씁니다.
그래서 경쟁이 겹쳐도 최종값이 실제 행 수와 같습니다.

#### 소프트 삭제

행을 지우지 않고 `is_valid` 플래그로 표시합니다. 복구와 재활성이 쉽지만 모든 쿼리에 조건이 붙고 유니크
제약에 삭제된 행도 걸립니다. 내 프로젝트는 그 성질을 재활성에 이용했습니다.

### 5.5 Web과 네트워크

현재 상태가 "공백"입니다. 프로젝트로 답할 수 없으니 정의와 동작만 정확히 외웁니다.

#### TCP와 UDP

TCP는 연결을 맺고 순서와 도착을 보장하며 흐름 제어와 혼잡 제어를 합니다. UDP는 연결 없이 보내고 보장이
없어 빠릅니다. HTTP는 TCP 위에서 동작하고, HTTP/3는 UDP 위의 QUIC을 씁니다.

#### 3-way와 4-way handshake

연결 수립은 SYN, SYN-ACK, ACK 세 번입니다. 클라이언트가 연결 요청을 보내고, 서버가 수락과 함께 자기
요청을 보내고, 클라이언트가 확인합니다. 종료는 FIN, ACK, FIN, ACK 네 번입니다. 한쪽이 먼저 끝내도 다른
쪽이 보낼 데이터가 남을 수 있어서 양쪽이 각각 끝냅니다. 먼저 끝낸 쪽은 TIME_WAIT 상태로 잠시 기다립니다.

#### HTTPS와 TLS handshake

HTTPS는 HTTP를 TLS로 암호화한 것입니다. 순서는 이렇습니다. 클라이언트가 지원하는 암호 방식을 보내고,
서버가 인증서를 보냅니다. 클라이언트는 인증서의 서명을 신뢰하는 인증 기관의 공개키로 검증해 서버가
진짜인지 확인합니다. 그다음 둘이 세션용 대칭키를 만듭니다. 비대칭키는 느려서 키 교환에만 쓰고, 실제
데이터는 대칭키로 암호화합니다. 인증서는 도메인, 공개키, 인증 기관의 서명으로 이루어집니다.

#### 대칭키와 비대칭키

대칭키는 암호화와 복호화에 같은 키를 쓰고 빠르지만 키를 안전하게 전달해야 합니다. 비대칭키는 공개키로
암호화하면 개인키로만 풀 수 있어 키 전달 문제가 없지만 느립니다. TLS는 둘을 합쳐 씁니다.

#### HTTP 메서드와 상태 코드

GET은 조회, POST는 생성, PATCH는 부분 수정, PUT은 전체 교체, DELETE는 삭제입니다. GET과 PUT과 DELETE는
멱등해야 하고 POST는 아닙니다. 상태 코드는 2xx 성공, 3xx 이동, 4xx 클라이언트 오류(400 잘못된 요청, 401
인증 없음, 403 권한 없음, 404 없음, 409 충돌), 5xx 서버 오류입니다. 내 프로젝트는 스크랩에 유니크 제약을 넣은 직후 충돌을 409로 냈고, 그 뒤 upsert 한
문장으로 바꿔 충돌 자체를 없앴습니다. 토글 API가 멱등하지 않은 것은 결함으로 진단했습니다.

#### 쿠키, 세션, JWT

세션은 서버가 상태를 저장하고 클라이언트는 세션 ID만 쿠키로 갖습니다. JWT는 서버가 서명한 토큰에 정보를
담아 클라이언트가 갖고, 서버는 서명만 검증해 상태를 저장하지 않습니다. 대신 발급한 토큰을 즉시 무효화하기
어렵습니다. 내 프로젝트는 Access Token은 짧게, Refresh Token은 DB에 저장해 무효화할 수 있게 했습니다.
쿠키는 HttpOnly로 스크립트 접근을 막고 Secure로 HTTPS에서만 보내며 SameSite로 다른 사이트에서의 전송을
제한합니다.

#### CORS

브라우저가 다른 출처(도메인, 포트, 프로토콜이 다름)로의 요청을 막는 규칙입니다. 서버가 허용할 출처를 응답
헤더로 알려 주면 브라우저가 허용합니다. 쿠키를 함께 보내려면 서버가 출처를 정확히 지정해야 합니다. `*`로는 안 됩니다. 내 프로젝트는 `app.cors.allowed-origins`로 허용 출처를 설정합니다.

### 5.6 OS

현재 상태가 "공백"입니다. 2순위로 채웁니다.

#### 프로세스와 스레드

프로세스는 실행 중인 프로그램으로 독립된 메모리 공간을 갖습니다. 스레드는 프로세스 안의 실행 흐름으로
힙과 코드는 공유하고 스택만 따로 갖습니다. 공유하기 때문에 통신이 빠르고, 같은 이유로 동기화가 필요합니다.
JVM 애플리케이션은 프로세스 하나에 스레드 여러 개입니다.

#### 컨텍스트 스위칭

CPU가 실행 중인 스레드를 바꿀 때 레지스터와 실행 위치를 저장하고 다른 스레드의 것을 복원하는 일입니다.
비용은 저장과 복원 자체보다 캐시가 비워지는 데서 크게 듭니다. 스레드가 코어 수보다 훨씬 많으면 이 비용이
커집니다. 커넥션을 기다리는 스레드는 대기 상태라 전환 비용은 작지만, 요청은 그만큼 줄을 섭니다. 내
경험: 포화 실행에서 커넥션 대기 스레드가 145개였고, 이 대기 시간이 응답 시간의 대부분이었습니다.

#### 뮤텍스와 세마포어

뮤텍스는 한 번에 하나만 들어가는 잠금이고 잠근 쪽이 풀어야 합니다. 세마포어는 정해진 수만큼 동시에
들어가게 하는 카운터입니다. 커넥션 풀은 세마포어와 같은 구조입니다. 커넥션 10개면 10개까지 들어가고
11번째는 기다립니다.

#### 데드락 네 조건

상호 배제, 점유 대기, 비선점, 순환 대기 넷이 모두 성립해야 데드락이 납니다. 하나라도 깨면 막을 수 있고,
보통 잠금 획득 순서를 통일해 순환 대기를 깹니다. DB는 감지 후 한쪽을 롤백하는 방식입니다.

#### 가상 메모리와 페이지 교체

각 프로세스에 실제보다 큰 연속된 주소 공간을 주고, 페이지 단위로 물리 메모리에 올립니다. 없는 페이지를
접근하면 페이지 폴트가 나고 디스크에서 가져옵니다. 물리 메모리가 부족하면 페이지 교체가 일어나며 LRU(가장
오래 안 쓴 것부터)가 대표 정책입니다. 내 경험: 컨테이너 메모리 제한에 걸려 커널이 페이지를 강제로 회수한
횟수가 992회였던 것을 보고 제한을 올렸습니다. OOM Kill이 0이어도 위험할 수 있습니다.

#### 스레드 풀

스레드를 미리 만들어 두고 작업을 큐에 넣어 재사용합니다. 생성 비용을 아끼고 동시 실행 수를 제한합니다.
Tomcat의 max-threads가 처리 스레드 수, accept-count가 대기 큐 길이입니다. 뒤 계층(DB 커넥션 수)에 앞 계층
(스레드 수)을 맞춰야 대기가 안 쌓입니다.

### 5.7 Test

#### 단위 테스트와 통합 테스트

단위 테스트는 클래스 하나를 의존성 없이 검증하고 빠릅니다. 통합 테스트는 DB나 Spring 컨테이너를 띄워 실제
연결을 검증합니다. 내 프로젝트는 서비스 로직은 Mockito 단위 테스트, 쿼리 수 검증은 실제 DB를 쓰는
`@DataJpaTest`입니다.

#### 테스트 더블

목(mock)은 호출 여부와 인자를 검증하고, 스텁(stub)은 정해진 값을 돌려줍니다. 내 프로젝트의 조회수 스케줄러
테스트는 DB 반영 실패를 목으로 만들어 실패 격리를 검증합니다 (카드 4).

#### 실패해야 하는 테스트

개선을 검증하는 테스트는 개선을 되돌렸을 때 실패해야 합니다. 통과만 확인한 테스트는 구현이 틀려도
통과할 수 있습니다 (카드 9).

### 5.8 Redis

#### 자료구조와 용도

String과 `INCR`은 카운터, List는 최근 목록, Set은 중복 없는 집합, Sorted Set은 점수 순위표, Hash는 객체
필드입니다. 내 프로젝트는 조회수 버퍼에 String `INCR`, 게시판별 글 목록에 List, 인기글에 Sorted Set을
씁니다.

#### 단일 스레드와 KEYS

Redis는 명령을 한 스레드에서 순서대로 처리해서 명령 하나하나가 원자적입니다. 대신 `KEYS`처럼 전체를
훑는 명령은 그동안 다른 명령을 막습니다. `SCAN`은 조금씩 나눠 훑습니다. 내 프로젝트의 조회수 스케줄러가
`KEYS`를 쓰는 것이 알려진 개선점입니다 (카드 3).

#### 캐시 패턴과 세 가지 장애

읽을 때 캐시를 먼저 보고 없으면 DB에서 읽어 채우는 look-aside가 기본입니다. 쓰기는 캐시를 지우고 TTL을
안전망으로 둡니다. 장애 세 가지는 인기 키가 만료되는 순간 요청이 한꺼번에 DB로 가는 스탬피드, 많은 키가
동시에 만료되는 애벌랜치, 없는 키를 반복 조회하는 페네트레이션입니다. 대응은 각각 재구축 잠금이나 조기
갱신, TTL에 무작위 여유 추가, 없음 자체를 캐시하거나 블룸 필터입니다. 내 프로젝트는 셋 다 방어가 없고, 아직 정식
결함 항목으로 올리지 않았습니다.

#### 장애와 폴백

Redis는 가속 계층이어야 합니다. 원본은 DB입니다. 내 프로젝트는 Redis 예외를 AOP로 흡수합니다. 게시판
목록은 DB로 폴백하고, 인기글은 DB 대체 경로가 있으나 순위 일치를 보장하지 않으며, 조회수 버퍼는 유실을
받아들입니다. 지금은 단일 노드라 Sentinel이나 Cluster 같은 고가용성 구성은 없습니다.

|---|---|

| Feed Entity Service | 모든 콘텐츠 공급자로부터 피드에 노출될 수 있는 항목을 수집해 저장하는 중앙 저장소 |
| Feedback Service | "이 글 숨기기" 같은 명시적 피드백 저장 |
| 팀 범위 | 추천 기능 자체를 뺀, 피드에 콘텐츠를 싣고 내보내는 모든 기술 요소 |
| Server Driven UI | 서버가 뷰타입(보여 줄 모양)을 통제해 앱 배포 없이 피드 모양을 바꾸고 실험 |
| 홈 피드 사용자 | 앱을 켜는 사용자의 99%가 홈 피드를 거침 |
| 개인화 효과 | 도입 후 클릭 수 133%에서 456% 증가 |
| 숨기기 | 부정 피드백 학습 뒤 숨기기 사용량 40% 감소 |
| 실험 주체 | 데이터 분석가와 PM만이 아니라 엔지니어까지 대부분이 직접 실험을 엶 |
| A/A 테스트 | 사용자가 보기에는 같지만 시스템이 더 효율화되는 방향의 실험 |
| 안정성 태도 | 다른 서비스가 다 죽어도 우리는 죽지 않아야 한다, 겹겹이 대비 |
| 문서 문화 | PRD, 테크 스펙, 실험 문서, 배포 결정 문서를 써서 누구나 문서만으로 맥락 이해 |

이 사실과 내 경험을 잇는 문장은 세 개입니다. A/A 테스트는 아무것도 바꾸지 않았을 때의 자연 편차를 재는
절차이고 내 비교 조건 검사와 같은 문제를 다룹니다. 엔지니어가 실험을 직접 열기 때문에 실험 결과를 믿어도
되는지 판정하는 능력이 필요합니다. 문서로 맥락을 남기는 문화는 내 개선 기록 방식과 같습니다.
