# 당근 Feed Infra 산업기능요원 지원 분석

> 기준일: 2026-09-07  
> 대상 공고: Software Engineer, Backend - 피드 (피드 인프라)  
> 지원 형태: 보충역 신규 편입  
> 산출물: `resume-feed-infra.md`, `portfolio-feed-infra.md`

## 0. 결론

이 공고는 연차를 적지 않았지만 신입 공고로 명시되지도 않았습니다. 지원 가능성과 합격 가능성은
구분해야 합니다. 공고가 실제로 보는 것은 사용자 문제 정의, 제품 실험, 콘텐츠 서빙, 안정성,
직군을 넘나드는 실행력입니다. 현재 프로젝트는 사용자 행동 집계, Redis 인기글 서빙, N+1 제거,
부하 실험 검증 경험으로 일부를 증명할 수 있습니다.

가장 큰 약점은 실사용자 지표, A/B 테스트, 여러 종류의 콘텐츠를 조합한 피드, 운영 트래픽입니다.
이력서와 포트폴리오에서는 이 경험이 있는 것처럼 표현하지 않습니다. 대신 현재 가진 증거를 다음
세 문장으로 정리합니다.

1. 댓글·반응·스크랩·조회 데이터를 모아 인기글을 서빙하는 경로를 구현했습니다.
2. 데이터 유실과 N+1을 재현하고, 실패 테스트와 반복 측정으로 개선을 확인했습니다.
3. AI로 구현 속도를 높이되 문제 정의, 수용 조건, 실험 설계와 결과 해석은 직접 결정했습니다.

## 1. 공고가 요구하는 결과

### 1.1 홈 피드 서빙

- 중고거래, 동네생활, 부동산, 중고차 등 서로 다른 콘텐츠의 수집·저장·조합·서빙
- 장애가 발생해도 홈 화면을 비우지 않는 안정성
- 새 콘텐츠 타입과 실험을 빠르게 수용할 수 있는 유연한 구조
- 추천 모델을 제외한 콘텐츠 입출력 경로의 책임

### 1.2 제품 실험

- 사용자 문제 발견
- 가설 설정
- 실험 설계와 구현
- 행동 데이터 수집
- 데이터에 따른 배포 또는 다음 실험 결정
- Server Driven UI와 여러 동시 실험을 통한 실험 비용 절감

### 1.3 지원자 역량

- 기술보다 사용자 가치와 목적을 먼저 보는 판단
- 문제를 직접 정의하고 해결까지 끝내는 실행력
- 기획·디자인·ML 영역까지 필요한 만큼 파고드는 태도
- AI 도구를 사용한 구현·검증 속도 향상
- 하나 이상의 언어와 웹 프레임워크 숙련도

### 1.4 우대 경험

- 분산 시스템 또는 마이크로서비스의 설계·운영
- 피드·추천·개인화 등 콘텐츠 서빙
- A/B 테스트 설계와 검증
- 프로덕트 엔드투엔드 개발
- Go, Kafka, Kubernetes 사용 경험

## 2. 산업기능요원 지원 조건

공고는 산업기능요원 채용 가능 범위를 현역 전직, 보충역 신규 편입, 보충역 전직으로 명시합니다.
현재 지원자는 보충역 4급이며 편입 전이므로 보충역 신규 편입에 해당합니다. 이력서 머리글에
`보충역 4급 · 산업기능요원 신규 편입 가능`을 표시합니다.

채용 가능 문구만으로 실제 편입 행정이 확정되는 것은 아닙니다. 합격 뒤 다음 사항을 채용 담당자와
관할 병무청에 확인해야 합니다.

- 입사일과 편입 신청일
- 현재 회사의 편입 신청 전 퇴사 처리 기한
- 당근의 해당 연도 보충역 편입 처리 일정
- 정보처리 분야 편입 서류와 제출 주체

## 3. 현재 증거와 공고의 대응

| 공고 평가축 | 현재 증거 | 판단 | 서류 반영 |

| 콘텐츠 서빙 | Redis Sorted Set 일간 인기글 조회 | 부분 충족 | 개인화·다종 콘텐츠가 없음을 명시 |

| 성능 최적화 | 요청당 쿼리 1,507회에서 4회, 혼합 시나리오 전체 p95 감소 | 강한 증거 | 이력서 첫 수치와 포트폴리오 핵심 사례 |

| 엔드투엔드 | 백엔드 API, Vue 화면, AWS 배포 경험 | 부분 충족 | 경력·프로젝트 범위에 사실만 기재 |
| AI 활용 | 사람이 수용 조건과 검증 방법을 정하고 구현·초안을 위임 | 강한 증거 | 별도 한 줄과 실제 검증 사례 연결 |
| Java·웹 프레임워크 | Java 17, Spring Boot 3.4, JPA, QueryDSL | 충족 | 기술 목록과 프로젝트 불릿 교차 |
| Go·Kafka·Kubernetes | 없음 | 미충족 | 기술 목록에 넣지 않음 |
| A/B 테스트 | 없음 | 미충족 | 성능 실험을 A/B 테스트로 부르지 않음 |
| 운영 트래픽 | 실사용자·운영 성능 지표 없음 | 미충족 | 로컬 부하 환경으로 범위 제한 |
| 다종 콘텐츠 피드 | 없음 | 미충족 | 인기글 목록을 홈 피드로 부르지 않음 |

## 4. 서류에서 사용할 지원자 정의

### 사용할 정의

> 사용자 행동 데이터가 콘텐츠 서빙으로 이어지는 경로를 구현하고, 성능과 데이터 유실 문제를
> 재현 가능한 실험으로 개선한 Java/Spring 백엔드 개발자

### 사용하지 않을 정의

- 대규모 트래픽 경험자
- A/B 테스트 플랫폼 개발자
- 추천 시스템 개발자
- 분산 시스템 운영 경험자
- 실시간 데이터 파이프라인 개발자
- 피드 인프라 전문가

현재 증거보다 큰 명칭을 사용하면 첫 꼬리질문에서 전체 수치의 신뢰까지 잃습니다.

## 5. 이력서 구성 원칙

### 첫 화면

- 지원 가능한 병역 형태
- Java와 Spring Boot
- 사용자 행동 집계와 Redis 서빙
- 요청당 쿼리 1,507회에서 4회
- 데이터 정합성을 확인한 방법

### 프로젝트 순서

1. 사용자 행동 집계와 인기글 서빙
2. 조회수 반영 실패 시 데이터 유실 방지
3. 댓글 목록 API N+1 제거
4. 비교 가능한 부하 실행만 선택하는 검사
5. AI 활용과 사람의 판단 범위

### 삭제할 주장

- 변동계수만으로 산출했다는 MDE 16%
- Hikari acquire p95를 전체 p95로 나눈 원인 비중
- `log10`이 조회수와 좋아요의 순서를 교정한다는 설명
- 전체 테스트 725개 통과
- 저장된 실행 108건
- 전체 커밋 715건 중 519건
- 스크랩 토글이 완전히 해결됐다는 주장

## 7. 현재 문서에서 바로 고쳐야 하는 사실

- `portfolio-daangn.pdf`는 빈 12쪽과 원시 SVG/HTML이 노출된 마지막 두 쪽 때문에 제출 금지
- `portfolio-daangn-short.pdf`도 12쪽이라 핵심 사례를 찾는 시간이 길음
- PDF 메타데이터가 포트폴리오까지 `이력서`로 저장됨
- 헤더 링크가 클릭되지 않음
- 인기글 가중치의 제품 근거가 없음
- Redis ZADD와 EXPIRE가 한 연산으로 묶이지 않음
- Redis가 비었을 때 DB fallback이 점수가 아닌 생성 시각으로 정렬됨
- 상위 10개를 가져온 뒤 좋아요 기준을 적용해 10개 미만을 반환할 수 있음
- 상위 50개 밖의 게시글은 시간 감쇠 점수가 오래된 상태로 남음
- `@TransactionalEventListener(AFTER_COMMIT)`는 현재 동기 실행이며 outbox와 재처리 경로가 없음
- 조회수 정산의 `DECRBY`와 `DELETE` 사이에 새 증가가 끼면 1건이 유실될 수 있음
- `KEYS post:views:*`는 키가 많아지면 Redis를 블로킹할 수 있음

이 항목은 숨기지 않되 본편의 성과처럼 길게 설명하지 않습니다. 현재 검증한 개선과 다음 설계 과제를
분리합니다.

## 9. 예상 면접 질문

### 사용자와 제품

- 실사용자가 없는데 사용자 문제를 어떻게 정의했나요
- 왜 최신글 목록과 별도로 인기글이 필요하다고 판단했나요
- 가중치는 어떤 데이터로 정했나요
- 실제 사용자가 있었다면 무엇을 지표로 봤을 건가요
- 인기글이 클릭을 늘리고 만족도는 낮추는 경우 무엇을 선택하나요

### 콘텐츠 서빙

- Redis가 비면 무엇을 반환하나요
- 상위 목록의 중복·삭제·순서 변경을 어떻게 처리하나요
- 콘텐츠 타입이 세 개로 늘면 데이터 모델을 어떻게 바꾸나요
- cursor와 순위 점수가 동시에 변할 때 다음 페이지를 어떻게 정의하나요
- 한 콘텐츠 공급자가 느릴 때 전체 피드를 어떻게 보호하나요

### 안정성

- AFTER_COMMIT 이후 프로세스가 죽으면 이벤트는 어떻게 복구하나요
- 조회수의 정확성과 게시글 조회 가용성 중 무엇을 선택했나요
- Redis 장애 중 발생한 조회 행동은 어떻게 처리하나요
- DB fallback이 Redis 순위와 같은 결과를 보장하나요
- 스케줄러가 여러 인스턴스에서 동시에 실행되면 어떻게 조정하나요

### 실험

- 성능 실험과 제품 A/B 테스트는 무엇이 다른가요
- 실험군 오염과 사용자 간 간섭은 어떻게 다루나요
- p95 개선이 우연이 아니라고 어떻게 판단하나요
- 부하 모델을 closed에서 open으로 바꾼 이유는 무엇인가요
- 개선 전후 실행 순서의 시간 추세를 어떻게 통제하나요

### AI 활용

- AI가 만든 코드 중 잘못된 것을 잡은 사례는 무엇인가요
- AI에 맡기지 않는 판단은 무엇인가요
- 생성한 테스트가 실제 결함을 검증한다는 것을 어떻게 확인하나요
- 코드 전체를 설명하지 못하는 부분은 없나요
