## 0. 컨설턴트의 진단 — 스프린트를 끝낸 지금의 위치

**서류는 통과권이다. 승부는 직무 인터뷰의 2~3번째 꼬리질문이고, 문화적합성과 편입 행정은
"준비만 하면 되는" 단계다.**

| 단계 | 스프린트 완료 후 상태 | 남은 위험 |
|---|---|---|
| 서류 | 개선 실적 1건(수치 보유) + 측정 시스템 + 이력서 초안 | **밀도 조정.** 두꺼운 것을 얇게 만드는 일이 남았다 |
| 직무 인터뷰 | CS 범위 정리, 체인 3개 리허설, 규모 답변 스크립트 | **3뎁스의 약한 지점.** 그리고 "너무 적게 / 너무 많이 말하기" |
| 문화적합성 | 몰입 경험·이직 사유·AI 활용 답변 뼈대 | 핵심가치 8개 중 **약한 3개**를 어떻게 말하나 |
| 레퍼런스·처우 | 후보 확보 여부 미정 | **수습 중 이직** 구조 |
| 편입 | 신체등급 확인(보충역 4급) | **정보처리 분야 편입대상** 여부 |

토스가 직접 밝힌 인터뷰 철학이 이 문서 전체의 기준이다.

> **"기술을 넘어, 문제 해결의 방식이 궁금해요."** — 토스 서버 개발자 인터뷰 안내
>
> 면접관이 꼬리질문으로 확인하려는 것: **왜 그 선택을 했는가, 문제를 어떻게 객관적으로
> 정의했는가, 어떤 대안을 고려했는가.** 그리고 **"성과 너머에 있는 사람 자체"** —
> 지금의 완성도보다 잠재력과 성장 마인드셋.

내 소재는 정확히 이 형식으로 만들어져 있다 — 오진 → 반박 → 규명 → 재발 방지, 그리고
버린 대안이 문서로 남아 있다. **소재가 아니라 전달이 승부다.**

# 1. 전형 지도 — 각 단계의 형식과 거르는 것

```
서류 ─→ 직무 인터뷰 ─→ 문화적합성 ─→ 레퍼런스 체크 ─→ 처우협의 ─→ 합류 ─→ 편입
 │         │              │              │                            │
 PDF만     1.5h 화상      가치관 대화     약 1주                        고용계약 → 7일 내 신청
 자소서 X   같은 직군      핵심가치 8개                                  병무청 2일 심사
 코테 X     결과 익일      가 채용 기준                                  보충역: 자격증 불요
```

| 단계 | 형식 (사실) | 거르는 것 (추론) | 위험도 |
|---|---|---|---|
| **서류** | 자유 양식 PDF. "경험 속의 임팩트와 러닝 포인트를 구체적으로". 개발 직군은 스택 명시 | 이력서 밀도. 규모 없는 신입 대부분이 여기서 탈락 | 중 |
| **직무 인터뷰** | **1.5시간 화상, 같은 직군 팀원**이 진행. 제출한 경력 기술 기반. 실제 2시간+ 사례. **엑스칼리드로우로 그리며 설명.** 결과 익일 유선 | **문제 해결의 방식.** 선택의 이유, 대안, 내부 동작. **성공뿐 아니라 실패한 프로젝트**도 묻는다 | **최고** |
| **문화적합성** | "일방적 검증이 아니라 진솔한 대화". **"모든 토스팀원은 핵심 가치를 기준으로 채용하고 평가하고 피드백"** | 일하는 태도, 의사결정 기준, 협업 방식 | 하~중 |
| **레퍼런스 체크** | 지원자 동의 후 약 1주 | 실제 협업자 평가 | 중 |
| **처우협의** | 현황 자료 제출 후 협의 | — | `[확인]` 병특 급여 체계 |
| **편입** | 고용계약 → 업체가 7일 내 신청 → 병무청 2일 심사 | 정보처리 분야 편입대상 | **확인 필요** |

**전부 온라인이다.** 조용한 장소, 유선 인터넷, 카메라·마이크, 화면 공유 시 보일 창 정리.

## 2.1 토스가 공개한 평가 축 대조

서버 챕터 FAQ "직무 인터뷰에서 어떻게 역량을 파악하나요"의 답을 축으로 쓴다.

| 토스가 본다고 밝힌 것 | 내 상태 (스프린트 완료 후) |

| **"서비스 운영 노하우가 많아 장애 대응에 능숙한 분인지"** | ○ 프로덕션 장애는 없다. "현상 → 오진 → 반증 → 규명 → 재발 방지" 사례 여러 건 |
| 대용량 트래픽 경험 | ✗ 채울 수 없다. **먼저 인정한다** (§4.6) |
| 서버 설계 능력 | △ 모놀리식. 설계 판단의 근거는 있다 |
| **"일에 대한 이해도" — 목표와 업무의 연관성** | ◎ "왜 이걸 만들었는가"가 준비돼 있다 |
| **"기술에 대한 호기심이 많고, 진행한 프로젝트에 대한 이해도가 높은 분"** | ◎ 가장 잘 맞는 축 |
| **"연차가 높은 분보다 미래에 더 빠르게 성장할 것으로 기대되는 분"** | ○ 이력서가 아니라 인터뷰 태도로 증명한다 |

## 3.3 프로젝트 페이지 — 네 문장 구조

```
① 상황  : 무엇이 문제였나 (수치)
② 판단  : 무엇을 의심했고, 무엇이 그 판단을 반박했나       ← 차별점
③ 행동  : 무엇을 어떻게 바꿨나 + 버린 대안 한 줄
④ 결과  : 수치 + 남은 한계 한 줄                          ← 한계를 쓰는 신입은 드물다
```

**실패 항목을 하나 넣는다.** 토스가 "실패한 프로젝트도 준비하라"고 명시했다.
후보: **"MDE 확정치(CV 3.12%)를 포화 상태에서 잰 값이라 무효 처리한 것"** —
실패이면서 동시에 판정 체계의 증거다. 또는 **"환경 가설 8개로 닷새를 쓴 것."**

## 4.2 "왜 이것인가" 표 — 이력서의 모든 명사에 세 칸

스프린트 B-1 의 산출물을 이 형식으로 정리했다는 전제다. **행이 비면 이력서에서 뺀다.**

| 기술 | 왜 이것인가 | 버린 대안 | 내부 동작 한 가지 |
|---|---|---|---|
| **HikariCP 풀 10** | 기본값. "왜 10인가" → 리틀의 법칙: 사용량 = RPS × 응답시간 = 17.76 × 0.104 ≈ 1.85. 부족해 보인 건 포화의 그림자 | 풀 확대 — 병목이 아니었다 | acquire 대기·pending 의 의미, 타임아웃 |
| **OSIV 기본 true** | **의도한 선택이 아니었다고 인정.** 커넥션이 요청 전체에 묶임을 실측으로 안다 | false + 서비스 계층 fetch 전략 — **개선 후보** | 인터셉터가 영속성 컨텍스트를 뷰까지 유지 |
| **N+1 해결 방식** | *(OPT-001 에서 고른 방법과 이유)* | `@BatchSize` / `@EntityGraph` / `join fetch` / DTO 프로젝션 — 각각 언제 맞나 | 프록시 초기화, **컬렉션 fetch join 의 페이징 문제** |
