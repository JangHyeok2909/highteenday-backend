## 2026-09-09 · 이력서 경력 불릿을 회사 커밋으로 채웠다

46행의 미완성 불릿 `- 외부 API 장애 `를 아래 한 줄로 교체했다. 2026-09-09 심사에서
세 심사자 모두 첫 결함으로 지목한 자리다.

> 정부 주소 검색 API 장애가 다른 요청까지 멈추지 않도록 타임아웃과 서킷 브레이커 도입 (RestTemplate, Redis)

근거 커밋은 2026-08-14 작업 네 건이다. 사내 비공개 저장소라 링크는 이력서에 넣지 않는다.

| 커밋 | 저장소 | 내용 |
|---|---|---|
| d5ad053 | palette3-backend | `URL.openStream()`을 전용 RestTemplate으로 교체. 연결 3초·응답 5초·커넥션 풀 대기 1초 |
| b04a122 | palette3-backend | Redis 카운터로 서킷 브레이커 구현. 실패 5회에 60초 차단, 실패 카운터 TTL 300초 |
| a8fefe8 | palette3-backend | 승인키 만료를 `API_UNAVAILABLE`로 변환하고 ERROR 로그 추가 |
| 9c495e5 | palette3-frontend | 장애 코드 수신 시 주소 직접 입력으로 전환 |

면접 답변에 쓸 사실.

- `connectionRequestTimeout` 기본값이 -1(무한)이라 `readTimeout`만으로는 풀 대기를 막지 못한다.
- 풀 20개가 격벽이 되고 요청당 스레드 점유가 최대 9초로 확정된다. 3020ms·5009ms는 실측,
  풀 대기 1초는 미실측이다.
- 실패 카운터 TTL을 차단 시간보다 길게 두어 별도 상태 없이 half-open이 된다.
- Redis에 상태를 두어 인스턴스가 여러 대여도 차단 상태를 공유한다. 다중 인스턴스 공백을
  메우는 유일한 소재다.
- 통신 장애만 실패로 센다. 승인키 만료를 실패로 세면 서킷이 계속 열린 채로 남는다.
- Redis 오류 시에는 호출을 허용한다(fail-open).

공개 README는 2026-09-09에 반영했다. `origin/main`에 커밋 7건을 체리픽으로 올렸다
(8117c21..f9d70d3). 9행의 검출 한계 16%와 279행의 GETDEL 서술이 사라져 포트폴리오
3장과 일치한다. 공개 트리에 localDocs와 `.claude`·`.agents`·`.codex`의 이력서 도구는
없다(추적 파일 0). 올리지 않은 커밋은 735480a, 9e0aae4, d3bde00, 1fef3d7이다. 앞의 둘은
main의 더 나중 작업을 되돌리고, d3bde00은 이력서 작성 에이전트 설정이라 공개 저장소에
넣지 않았다. `origin/develop`은 main보다 7커밋 뒤에 있다.

같은 날 `Deploy to EC2` 워크플로의 build 잡에 저장소 변수 `DEPLOY_ENABLED` 스위치를
달았다. EC2와 ECR이 없어 main 푸시마다 빨간 X가 붙던 것을 끊었다. 이제 테스트만 돌아
초록으로 남는다. 면접에서 저장소를 열어 볼 때 실패 표시가 보이지 않는다.

## 2026-09-08 · Feed Infra 포트폴리오 표현 교정

[portfolio-feed-infra.md](portfolio-feed-infra.md)를 Feed Infra 면접관이 읽는 기준으로 다시 검토했다.
Redis Sorted Set, DECRBY, 페치 조인, p95, VU 같은 통용 기술어는 유지하고, 내부 문서에서만 통하는
표현과 인과가 한 번에 드러나지 않는 문장을 실제 동작으로 바꿨다.

| 수정 | 판단과 결과 |
|---|---|

| 인기글 구현 결정 표 | Sorted Set의 한계처럼 적었던 상위 50개 재계산 문제를 별도 행으로 분리. Redis 장애 시 DB 목록을 실제로 반환하는 동작과도 표현을 일치시킴 |
| 조회수 실패 처리 | `미차감`, `대기 중인 값`, `다중 인스턴스 조정`을 Redis에 남는 값과 중복 처리 위험이 보이는 문장으로 교체 |
| N+1 검증 | 4,040건과 4,046건의 차이는 데이터 주석으로 분리하고, `em.clear()` 테스트가 실패하는 조건을 제목에 명시 |
| 포화 실행 설명 | 처리율 변동 원인은 미확인이고 포화가 p95 편차를 증폭하는 조건은 확인했다는 두 결론을 분리. 누락됐던 10,685ms 표본도 복원 |

## C-2 정정 (2026-09-05): 이미 고친 것을 안 고쳤다고 적고 있었다

이 표는 KI-53을 *"해결 후보 4가지가 문서에 있고 구현 전"*이라고 적어 두었다. 틀렸다.

코드에서 확인한 사실. `domain/posts/PostRepository.java:41-48`에 원자 증감이 들어가 있다.

```java
@Modifying(flushAutomatically = true, clearAutomatically = true)
@Query("update Post p set p.commentCount = p.commentCount + 1 where p.id = :postId")
int incrementCommentCount(@Param("postId") Long postId);
```

감소는 `where p.commentCount > 0`으로 하한까지 DB가 보장한다. `Post.java:104`에는 *"댓글 수 증감 메서드는 여기 없다. `PostRepository.incrementCommentCount()`를 쓴다"*는 주석이 남아 있고, `CommentService.java:82·106`이 그 메서드를 호출한다. `docs/KNOWN-ISSUES.md:426`의 갱신 줄은 2026-08-14 해소로 기록돼 있다.

오기록이 생긴 이유. 이 장부를 쓸 때 KNOWN-ISSUES의 갱신 줄을 확인하지 않고 결함 제목만 보고 "미해결"로 옮겼다. 장부끼리 어긋나면 이력서에서 성과가 통째로 빠진다. 실제로 완성된 개선 하나가 두 원고 모두에서 `<!-- CUT -->` 아래에 대기 중이었다.

남은 공백은 재현 테스트다. KNOWN-ISSUES는 *"동시 요청 30건 재현으로 원인을 확정한 뒤 고쳤다"*고 적었지만, 그 재현은 저장소에 테스트로 남아 있지 않다. `src/test` 전체에 `ExecutorService`·`CountDownLatch`·`CompletableFuture`가 0건이다. `CommentServiceTest`는 Mockito 호출 검증(`verify(postRepository).incrementCommentCount(100L)`)이라 동시성을 증명하지 못한다.

그래서 할 일이 "구현"에서 "이미 한 구현의 근거를 저장소에 남기기"로 바뀐다. 비용이 훨씬 싸고, 끝나면 이력서의 "동시성 결함" 절이 1건에서 2건이 된다. 두 건은 성격이 다르다. 경쟁 상태가 장애를 만든 것(스크랩 중복 행 → 상세 조회 실패)과, 경쟁 상태가 값을 틀리게 만든 것(카운터 유실, `large` 실측 13,284건 부족)이다.

# L. 서사 결정: 계측 → 코드 → 계측 (2026-09-04)

사용자가 *"코드를 보지 않고 계측 시스템만으로 병목의 원인을 파악해낸 경험"*을 소재로 제안한 데서 나온 결정이다. 소재를 새로 만든 것은 아니다. 세 문서에 흩어져 있던 관찰을 주장으로 승격했다. 당시 위치는 `resume.md:69`, `portfolio.md:140`, `portfolio.md:448`이다.

## L-1. 채택한 문장과 버린 문장

| | 문장 | 판정 |
|---|---|---|
| 버림 | "코드를 보지 않고 계측만으로 원인을 파악했습니다" | 한 뎁스에 무너진다. *"그럼 `fromEntity`가 프록시를 푼다는 건 어떻게 아셨죠?"* 한 마디면 된다. 엔지니어에게 "코드를 안 봤다"는 미덕이 아니고, 신입이 말하면 "코드를 못 읽는다"로 오독될 여지가 있다 |
| 버림 (2차) | "아래 두 병목 모두 코드에는 단서가 없었습니다" | 사용자 지적으로 철회. N+1은 코드를 꼼꼼히 읽으면 찾을 수 있는 종류다. 이 문장은 사실이 아니고, *"저는 코드만 보고도 찾겠는데요"*라는 반문에 바로 무너진다 |
| 채택 | "계측이 어디를 볼지 알려주고, 코드가 왜 그런지 알려주고, 다시 계측이 그 설명을 검증한다" | 주어를 사람에서 문제로 옮긴다. 계측과 코드 읽기를 대립 대신 순서로 놓아 "코드는 안 보시나요"를 문장 자체가 차단한다 |
| 채택 (근거절) | "코드는 무엇이 의심스러운지까지 알려주지만, 그중 무엇이 실제로 비싼지는 알려주지 않는다" | 철회한 문장보다 강하다. 발견 가능성을 부정하지 않으면서 계측의 고유한 값(비용의 크기와 우선순위)을 정확히 짚는다. 코드를 읽어 N+1을 찾아도 그것이 요청당 1,507개 중 몇 개인지, 지금 고칠 값이 있는지는 알 수 없다 |

## L-2. 사실 판정: 어디까지 참인가

| 단계 | 계측만으로 되나 | 근거 |
|---|---|---|
| 발견 (이런 문제가 있나) | 아니다 | S-1(커넥션 풀 대기)은 애플리케이션 코드 바깥이라 코드로는 못 찾는다. 그러나 N+1은 코드를 꼼꼼히 읽으면 찾을 수 있다. 이 칸을 "계측만 가능"이라고 쓰면 거짓이다 |
| 우선순위 (그중 무엇이 비싼가) | 그렇다 | 요청당 1,507개, 그중 반응 조회 2N과 작성자 조회 U의 비중, 1차 이후 남은 112개 중 108개. 전부 세어야 나오는 값이다. 여기가 계측의 고유 영역이고 채택 문장이 서 있는 자리다 |
| 규명 (왜 그런가) | 아니다 | "비용이 댓글 수 N 대신 작성자 수 U에 비례한다"는 설명은 영속성 컨텍스트 1차 캐시 동작을 알아야 나오고 `CommentDto.fromEntity`를 열어야 확정된다 |
| 검증 (그 설명이 맞나) | 그렇다 | 모델 `3+U+1`을 세 게시글에서 대조해 오차 0 |
| 수정 | 아니다 | 당연히 코드를 봤다 |

주장은 두 번째 줄 하나에만 걸어야 한다. 발견과 규명까지 계측의 공으로 돌리면 한 뎁스에 무너진다.

## L-3. N+1 하나 안에서 이 왕복이 두 번 돌았다

| 단계 | 무엇이 알려줬나 |
|---|---|
| 요청당 쿼리 1,507개 | 계측 (코드에는 쿼리처럼 보이는 것이 없었다) |
| 원인 둘: 반응 조회 2N, 작성자 조회 U | 코드 |
| 1차 적용 후 남은 112개 중 약 108개가 작성자 조회 | 계측. 이 값이 2차 대상을 정했다 |
| 왜 N 대신 U인가 | 코드 (1차 캐시) |
| 모델 `3+U+1` 검증 → 세 게시글에서 오차 0 | 계측 |
| 1차의 예측(약 108개 제거) 대 2차 실측(108.3개) | 계측이 코드에 대한 설명을 검증한 자리. 사후 서술이 아닌, 미리 반증 가능한 예측을 남긴 증거다 |

# O. 맹검 평가 반영 (2026-09-05): 이력서만 읽은 심사자의 판정

평가 방식. 이 프로젝트를 전혀 모르는 평가자에게 이력서 본문(CUT 위 전문)과 공고 원문만 주고 당근 Feed Infra 기술 리더 역할로 심사시켰다. 맥락을 가진 쪽이 읽으면 빈칸을 아는 것으로 메워 읽게 되므로, 맥락이 0인 독자가 유일하게 정직한 독자다.

## O-1. 판정: 서류 합격 추정 30%, "약한 콜"

> *"측정 방법론과 자기 오류 정정은 신입 중 최상위인데 피드·규모·Go가 0이고 '실험'이 전부 벤치마크임. 스택 무시하고 사고방식 볼 거면 콜, 아니면 패스."*

## P-9. 용어와 돌려 말하기 — 사용자 지적 반영 (2026-09-07)

사용자가 두 가지를 지적했다. ① *"명시적 신호, 암시적 신호"* 가 한국 개발자가 자주 쓰는
말인가. 전문용어는 널리 쓰는 것만 쓰고 아니면 풀어 써라. ② 2.2 의 *"하나는 요청이 들어가는
길에서… 앞의 것은… 뒤의 것은…"* 문단이 쉬운 척만 하고 즉시 이해가 안 된다. **직관적으로
이해되게 할 것.**

**반영**

- `rules-korean-prose.md` 2.12 절을 새로 썼다. 바꾼 말 17쌍의 표와 그대로 두는 용어의 기준,
  돌려 말하기의 전후 예 2건, 검사법("앞의 것·그것·이 조합" 자리에 실제 이름을 넣어 본다).
- `lint.js` 에 "통용되지 않는 용어(확인)" 항목을 추가했다(약한 위반). 두 원고 모두 0.
- `/career-docs` 스킬의 글쓰기 규칙 요약에 두 줄을 추가했다.
- 원고: 명시적/암시적 신호 → 댓글·반응·스크랩(직접 한 행동) / 조회. 정렬 집합 → Sorted Set.
  패치 조인 → 페치 조인(fetch join). 도착률 → 초당 요청 수. 해석 조건 → "수치를 인용하지
  못하게 막는 표시". 게이팅 → 검사. 방아쇠 → 계기. 관문·사슬·장부·계약 → 조건·연결·기록·조건.
  체크-후-실행 → "조회와 삽입 사이에 다른 요청이 끼어드는". 대조군·리틀의 법칙·변동계수·최소
  검출 가능 효과는 첫 등장에 뜻을 병기.
- 2.2 문단은 "커넥션 풀 대기(3장)" 와 "추가 쿼리(6장)" 라는 이름으로 다시 썼다. 4.2·4.3 의
  "시간축 질문 / 실험 설계 질문", "비교를 무효로 만드는 것 / 신뢰도만 낮추는 것", "선언적인
  표" 도 같은 이유로 "바로 앞 실행 / 같은 조건의 실행", "부하 크기나 데이터셋처럼 다르면 비교가
  성립하지 않는 조건", "if 문 대신 표 하나" 로 바꿨다.

**계측기가 못 잡는 것**: 돌려 말하기(둘째 종류)는 사람이 봐야 한다. 이번에 pronoun 검색으로
잡은 것은 2.2, 4.2, 4.3, 6.6("양쪽"), 10.3("그것") 이다.

### "포화 → 편차 증폭" 과 5.3 "포화에서 CV 3.12%" 의 모순 — 분석과 제안

**둘은 다른 편차다.** 원장부의 수치를 나란히 놓으면 이렇다.

| 편차의 종류 | 포화(고정 200 VU) | 포화 이하(RATE=4) | 출처 |
|---|---:|---:|---|
| 세트 안 상대 편차(CV) | 3.12% (EXP-001, n=5) · 7.07% (#90~98, n=9) | 9.62% (n=3) · 15.82% (Before-B) · 3.2% (댓글 p95, n=4) | drift 8-b.2, findings-scripts, drift 0.6 |
| 세트 안 절대 편차(SD) | 369ms · 755ms | 27~58ms | 같은 곳 |
| **세트 간 레벨 편차** | **45~48%** (하루 안 10,979 → 16,269 → 10,685ms) | **1.5%** (4시간 간격) | drift 0절, 8-b.5, 0.6 |
| 처리율 CV | 6.26% | 0.38% | findings-scripts |

**포화는 세트 안 편차를 눌러서 작게 보이게 하고, 세트 간 편차를 키운다.** 같은 원인(R = N/X)이
두 방향으로 작용한다. 처리량이 CPU 상한에 눌려 고정되면 한 세트 안에서는 지연이 큐 깊이로
고정돼 안정적으로 나온다(원장부: *"포화된 닫힌 큐는 원래 값이 안정적으로 나온다. CV 3.12% 가
낮은 데는 시스템이 한계에 눌려 있다는 사실도 기여한다"*, drift 부록 A). 반면 세션이 바뀌어
호스트 유효 처리량이 10~20% 움직이면 절벽(4→5 req/s 에 30배) 양쪽을 넘나들어 레벨이 통째로
바뀐다. 그래서 3.12% 는 "낮은 편차" 가 아니라 **"잘못된 대상을 잰 값"** 이다. 사실상 처리율의
변동계수(6.26%)를 재고 있었다.

**제안 (5.3 을 이렇게 고친다, 승인 대기):**
① 첫 문단: "3.12% 는 낮은 편차가 아니라 잘못된 대상을 잰 값이었다. 포화 상태의 고정 VU 부하에서
   p95 는 처리량의 역수라, 세트 안 변동계수는 사실상 처리율의 변동계수였다."
② 표에 "세트 간 편차" 행 추가: 45~48% → 1.5%.
③ 마지막 문단: "세트 안 변동계수는 9.6~15.8% 로 커졌지만 그것이 실제 편차이고, 세트 간 편차가
   세트 안보다 작아졌으므로 이제 세트 안 변동계수로 MDE 를 정할 수 있다."
이렇게 하면 3장("세션 간 편차 증폭")과 5장("세트 안 CV 는 눌려 있었다")이 같은 말을 한다.
3.3 에는 이미 다리 문단("같은 이유로 한 세션 안에서는 p95 가 오히려 안정적으로 나옵니다 … 5장의
첫 확정치 3.12% 는 이렇게 눌린 값이었습니다")을 넣어 두었다.

**주의할 수치**: 5.3 의 "표준편차 6~14배 감소(369ms → 27~58ms)" 는 세트 안 절대 편차라 그대로
참이다. 4시간 간격 −1.5% 는 댓글 목록 p95 기준(Before-A n=2, Before-B n=4)이라 인용할 때
그 조건을 붙인다.

`//` 로 시작하는 줄은 원고 주석으로 정하고 `build.js`(PDF 제외)와 `lint.js`(계측 제외)에 반영했다.

## P-16. 3장 원인 단정 철회와 포화 실행 분리 (2026-09-08)

이력서. 인적사항 1줄 → 소개 2~3줄(무엇을 해 왔나 + 가장 강한 사실 하나) → 기술 스택 2~3줄 → 경력·프로젝트(서비스 한 줄 → 기간·인원·역할 → 성과 불릿 3~5개, 각 1~2줄, 수치 포함) → 학력·자격. 명사형 종결. 굵게는 제목과 수치에만. 2쪽.

## Q-2. 왜 AI가 쓴 글로 읽히는가: 남아 있던 다섯 가지

1. 문장이 길고 모양이 같다. 평균 123자. 상당수가 "A인데, B라서, C했습니다" 3절 구조다. 9장의 한 문장: *"전역 목표를 80ms로 완화하는 안(게시판 목록이 12ms에서 60ms로 나빠져도 통과), 로그인만 통계에서 빼는 안(예외가 예외를 부르고, 느린 로그인은 실제 사용자 경험), 세션을 늘려 로그인 횟수를 줄이는 안(지연 목표 때문에 인증 수명을 늘리는 것은 순서가 거꾸로)도 버렸습니다."* 괄호 셋에 판단 셋이 한 문장에 들어 있다. 사람은 이걸 표로 만들거나 세 문장으로 쓴다.
2. 대비 구문과 도치. "코드가 아니라 포화", "코드를 읽어서가 아니라 측정으로", "성능 최적화가 아니라 보안 결정", "없었던 것은 … 코드였습니다". 9회. LLM 산문의 가장 알려진 지문이다.
3. 절마다 교훈으로 닫는다. "이 일에서 배운 것은 …는 점입니다", "…을 배웠습니다", "검증 방법을 먼저 정하는 것이 이 순서의 핵심입니다", "AI는 통과하는 테스트를 빨리 만들어 주지만, 무엇이 실패해야 하는지는 제가 정해야 했습니다", "이 목록이 있어야 … 말할 수 있다고 생각합니다". 교훈은 면접에서 말로 하는 것이고, 문서가 대신 말하면 설교로 읽힌다.
4. 이중 제목. "원인. 지표는 다 있었고, 해석이 없었다", "고친 것. 포화 여부를 실행마다 자동 판정", "개선 판정 기준. 노이즈부터 재기". 줄표를 마침표로 바꿨을 뿐 "라벨 + 경구" 골격이 그대로다(16개). 사람이 쓰는 제목은 "포화 판정 자동화" 한 덩어리다.
5. 문서가 자기 자신을 안내한다. "이 원칙은 뒤에서 … 검증 기준으로도 씁니다(7.5)", "6장에서 제가 확정했던 값을 스스로 무효 처리한 것도 이 순서 덕분이었습니다", "여기에 4장(포화 여부), 5장(대조군 유효성), 6장(노이즈 대비 크기)의 판정이 붙습니다". 24개. 글이 논증을 조립하고 있다는 느낌을 주는데, 사람의 기록에는 이런 배선이 없다.

여기에 날것이 하나도 없었다. 캡처 0장, 로그 0줄, 커밋 해시 0개, 날짜는 "2025년 5월/9월" 둘뿐. 모든 근거가 코드로 그린 SVG 3장과 표 13개였다. 정돈된 표만 있는 문서는 그 자체로 생성물처럼 보인다. 사람 기록의 표지는 Grafana 캡처, k6 요약 출력, 실패한 테스트 출력, 리포트에 실제로 찍힌 "+59,000%" 같은 것이다.

## Q-3. 왜 바로 이해가 안 되는가

- 1쪽에 정의 없는 용어 4개. 1.2 표: 포화, 대조군, 변동계수, 검출(최소 검출 가능 효과). 포화가 무엇인지는 4장에 가야 나온다. 첫 화면은 채용 담당자와 비전공 면접관도 읽는 자리다.
- 제목이 결과를 말하지 않는다. "트러블슈팅 1. 부하 테스트 결과를 잘못 읽어 닷새를 쓴 일"은 실수를 말하고, 무엇을 고쳤는지는 4.4까지 가야 나온다. 목차만 훑는 독자는 "이 사람이 뭘 했나"를 못 얻는다.
- 읽는 순서를 강제한다. 머리말이 "순서대로 적었습니다"라 하고, 2장은 4장·7장을 미리 가리키고, 6장은 4장을, 9장은 7.7과 11장을 가리킨다. 워니·이동욱 방식(훑고 → 걸리는 곳만 다시)이 불가능하다.
- 같은 비교에 숫자가 둘. 4장은 38배(10,685 → 278), 6장은 "분모인 평균이 43배 작아졌기 때문"(변동계수 세트 기준 11,827 → 275). 독자는 같은 비교로 읽고 걸린다.
- 계산이 안 맞는 곳. 4.3 "전체 p95의 57%가 커넥션을 기다린 시간". 6,364 / 10,685 = 59.6%. 맹검 평가자가 38배를 검산했듯 면접관도 이걸 검산한다. 분모가 다른 실행이면 그 실행의 p95를 같이 적는다.
- 4 RPS. 4.2 "도착률만 초당 4요청으로", 4.3 "실측 17~28 RPS". 용량(포화 시 실측 17~28 RPS)을 같은 자리에서 한 줄로 밝히지 않으면 "초당 4요청짜리 시스템"으로 읽힌다.
- 3.9와 4. 1.2는 "4개(5회 평균 3.9개)"로 정리했는데 그림과 7.2 표는 3.9다. 이력서 결정(4로 통일)을 그림·표에도 적용한다.
- 715/519 커밋. 맹검 평가(O-3)에서 "왜 둘은 나갔나"만 부른다고 이력서에서 뺐는데 1.1에 다시 들어갔다. 한쪽으로 통일한다.

# R. 4장(포화)의 서술이 요점을 비껴간 문제. 해결 (2026-09-05 밤)

## R-1. 지적: "부하를 낮춰 응답 시간이 줄어든 게 무슨 의미냐"

사용자 지적: *"응답 시간이 매우 큰 것 자체는 아무런 문제가 되지 않았다. 애초에 빡센 부하를 성능 개선으로 버텨보자는 게 취지였다. 가장 큰 문제는 편차가 큰 것이었다. 포화일 때 편차가 증폭되어 개선 판정의 최소 크기가 무의미해지는 것 때문에 곤욕을 치렀는데, 원고는 '응답 시간을 애플리케이션 지연으로 오판했다'만 강조한다."*

맞는 지적이다. 이전 판 4장은 이렇게 읽혔다.

| 이전 판이 말한 것 | 왜 이상한가 |
|---|---|
| 증상 = p95 10,685ms (느리다) | 느린 것은 의도한 부하의 결과다. 문제가 아니었다 |
| 반박 = 도착률만 낮추니 278ms | 부하를 줄여 응답 시간이 줄어든 것은 성과가 아니다 |
| 그림 = 10,685 대 278 대비 상자 | 38배가 성능 개선처럼 보인다 |
| 편차 25~45% | 한 줄로만 나오고, 그것이 판정을 막았다는 말이 없다 |

## R-2. 고친 것: 축약본 4장 전면 교체, 마스터본 동기화

| 자리 | 바꾼 것 |
|---|---|
| 4장 제목 | "닷새를 쓴 오판과 포화 자동 판정" → "실행마다 25~45% 흔들려 개선을 판정할 수 없던 측정" |
| 4.1 | 흔들림 폭(25~45%)이 노리던 개선폭(10~40%)보다 크다는 것을 증상으로 세움. 아무것도 바꾸지 않은 실행이 이만큼 흔들리면 효과와 잡음을 가를 수 없다 |
| 4.2 | 대비 상자를 빼고 용량 곡선 3점 표(초당 3·4·5요청 → 690ms, 402ms, 11,871ms. 도달률 99, 101, 77%)로 교체. 부하 25% 증가에 p95 30배, `1/(1-ρ)` 발산, 200 VU가 용량의 1.5배 |
| 4.2 끝 | 호스트 처리 능력이 10~20% 오르내리는 것이 포화 직전에서는 p95를 배로 바꾼다는 증폭 구조를 명시 |
| 4.3 | 부하 모델(closed model)을 원인에 추가. `사용자 수 ÷ 처리량`, `200 ÷ 처리량`과 p95의 상관 0.962(커넥션 획득 0.944보다 높음) |
| 4.4 | 고친 것을 넷으로: 도착률 고정 전환, 판정용 부하 초당 4요청(앱 CPU 37~45%, 커넥션 대기 0건, 획득 1ms), 포화 자동 판정, 저장된 119건 재판정해 49건 분리 |
| 4.4 끝 | 높은 부하 실행은 지금도 쓰고, 거기서는 처리량·도달률·에러율을 보고 지연값만 인용을 막는다는 문단 추가 |
| 4.5 | 검증 절 신설: 환경이 18% 느려진 4시간 사이 앱 p95 변동 1.5%, 실행 직전 CPU 벤치와 p95의 상관 −0.006 |
| 6.1 | 3.12%가 한자리에서 몰아 잰 5회 안의 값이고, 몇 시간 뒤에는 25~45% 달랐다는 문단 추가. 포화에서는 노이즈 크기 자체가 재현되지 않아 기준이 유지되지 않았다 |
| 1.3 KPI | "오판했던 p95 10,685ms의 실제 원인" 행을 편차, 용량 1.5배, 재현 차이 1.5%로 교체 |
| 이력서 | 성능 불릿 1개를 3개로 분리(흔들림 → 원인 두 가지 → 고친 것과 검증). 요약 문단도 편차 기준으로 수정 |

마스터본에도 같은 내용을 넣고 검증 절을 새로 만들었다. 2026-09-05 밤 재작성(S장)에서 마스터본 4장은 축약본과 같은 절 구성이 됐다. 순서는 사용자가 축약본 4.1·4.2에 직접 쓴 것을 따랐다. 편차가 측정 시스템을 무의미하게 만든 것이 문제였고, 부하가 낮은 시나리오의 편차가 10% 안이라는 관찰에서 포화 가설이 나왔다.
