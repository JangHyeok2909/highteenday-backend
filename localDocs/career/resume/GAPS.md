## C-2 정정 (2026-09-05) — **이미 고친 것을 안 고쳤다고 적고 있었다**

이 표는 KI-53을 *"해결 후보 4가지가 문서에 있고 구현 전"* 이라고 적어 두었다. **틀렸다.**

**코드에서 확인한 사실.** `domain/posts/PostRepository.java:41-48` 에 원자 증감이 들어가 있다.

```java
@Modifying(flushAutomatically = true, clearAutomatically = true)
@Query("update Post p set p.commentCount = p.commentCount + 1 where p.id = :postId")
int incrementCommentCount(@Param("postId") Long postId);
```

감소는 `where p.commentCount > 0` 으로 **하한까지 DB가 보장**한다. `Post.java:104` 에는
*"댓글 수 증감 메서드는 여기 없다 — `PostRepository.incrementCommentCount()` 를 쓴다"* 는
주석이 남아 있고, `CommentService.java:82·106` 이 그 메서드를 호출한다.
`docs/KNOWN-ISSUES.md:417` 의 갱신 줄은 **2026-08-14 해소**로 기록돼 있다.

**왜 이 오기록이 생겼나.** 이 장부를 쓸 때 KNOWN-ISSUES 의 갱신 줄을 확인하지 않고
결함 제목만 보고 "미해결"로 옮겼다. **장부끼리 어긋나면 이력서에서 성과가 통째로 빠진다** —
실제로 완성된 개선 하나가 두 원고 모두에서 `<!-- CUT -->` 아래에 대기 중이었다.

**남은 진짜 공백은 재현 테스트다.** KNOWN-ISSUES 는 *"동시 요청 30건 재현으로 원인을
확정한 뒤 고쳤다"* 고 적었지만, **그 재현은 저장소에 테스트로 남아 있지 않다.**
`src/test` 전체에 `ExecutorService`·`CountDownLatch`·`CompletableFuture` 가 **0건**이다.
`CommentServiceTest` 는 `verify(postRepository).incrementCommentCount(100L)` 형태의
Mockito 호출 검증이라 **동시성을 증명하지 못한다.**

**그래서 할 일이 바뀐다.** "구현"이 아니라 **"이미 한 구현의 근거를 저장소에 남기기"** 다.
비용이 훨씬 싸고, 끝나면 이력서의 "동시성 결함" 절이 **1건 → 2건**이 된다.
두 건의 성격이 서로 달라서 나열이 아니라 분류가 된다 —
**경쟁 상태가 장애를 만든 것**(스크랩 중복 행 → 상세 조회 실패)과
**경쟁 상태가 값을 틀리게 만든 것**(카운터 유실, `large` 실측 13,284건 부족).

# L. 서사 결정 — "계측 → 코드 → 계측" (2026-09-04)

사용자가 *"코드를 보지 않고 계측 시스템만으로 병목의 원인을 파악해낸 경험"* 을 소재로
제안한 데서 나온 결정이다. **소재를 새로 만든 것이 아니라, 세 문서에 흩어져 있던 관찰을
주장으로 승격한 것이다** (`resume.md:69` · `portfolio.md:140` · `portfolio.md:448`).

## L-1. 채택한 문장과 버린 문장

| | 문장 | 판정 |
|---|---|---|
| 버림 | "코드를 보지 않고 계측만으로 원인을 파악했습니다" | **한 뎁스에 무너진다.** *"그럼 `fromEntity` 가 프록시를 푼다는 건 어떻게 아셨죠?"* 한 마디면 된다. 게다가 엔지니어에게 "코드를 안 봤다"는 미덕이 아니고, 신입이 말하면 **"코드를 못 읽는다"로 오독될 여지**가 있다 |
| **버림 (2차)** | "아래 두 병목 모두 **코드에는 단서가 없었습니다**" | **사용자 지적으로 철회.** N+1 은 코드를 꼼꼼히 읽으면 찾을 수 있는 종류다. 이 문장은 사실이 아니고, *"저는 코드만 보고도 찾겠는데요"* 라는 반문에 바로 무너진다 |
| **채택** | **"계측이 어디를 볼지 알려주고 → 코드가 왜 그런지 알려주고 → 다시 계측이 그 설명을 검증한다"** | 주어를 **사람에서 문제로** 옮긴다. 계측과 코드 읽기를 대립이 아니라 **순서**로 놓아 "코드는 안 보시나요"를 문장 자체가 차단한다 |
| **채택 (근거절)** | **"코드는 무엇이 의심스러운지까지 알려주지만, 그중 무엇이 실제로 비싼지는 알려주지 않는다"** | **철회한 문장보다 강하다.** 발견 가능성을 부정하지 않으면서 계측의 고유한 값(**비용의 크기와 우선순위**)을 정확히 짚는다. 코드를 읽어 N+1 을 찾아도 그것이 요청당 1,507개 중 몇 개인지, 지금 고칠 값이 있는지는 알 수 없다 |

## L-2. 사실 판정 — 어디까지 참인가

| 단계 | 계측만으로 되나 | 근거 |
|---|---|---|
| **발견** (이런 문제가 있나) | **아니다** | S-1(커넥션 풀 대기)은 애플리케이션 코드 바깥이라 코드로는 못 찾는다. 그러나 **N+1 은 코드를 꼼꼼히 읽으면 찾을 수 있다.** 이 칸을 "계측만 가능"이라고 쓰면 거짓이다 |
| **우선순위** (그중 무엇이 비싼가) | **그렇다** | 요청당 1,507개, 그중 반응 조회 2N 과 작성자 조회 U 의 비중, 1차 이후 남은 112개 중 108개 — **전부 세어야 나오는 값**이다. **여기가 계측의 고유 영역이고 채택 문장이 서 있는 자리다** |
| **규명** (왜 그런가) | **아니다** | "비용이 댓글 수 N 이 아니라 작성자 수 U 에 비례한다"는 설명은 영속성 컨텍스트 1차 캐시 동작을 알아야 나오고 `CommentDto.fromEntity` 를 열어야 확정된다 |
| **검증** (그 설명이 맞나) | **그렇다** | 모델 `3+U+1` 을 세 게시글에서 대조해 오차 0 |
| **수정** | 아니다 | 당연히 코드를 봤다 |

**주장은 두 번째 줄 하나에만 걸어야 한다.** 발견과 규명까지 계측의 공으로 돌리면
한 뎁스에 무너진다.

## L-3. N+1 하나 안에서 이 왕복이 두 번 돌았다 — 반영한 근거

| 단계 | 무엇이 알려줬나 |
|---|---|
| 요청당 쿼리 1,507개 | **계측** (코드에는 쿼리처럼 보이는 것이 없었다) |
| 원인 둘 — 반응 조회 2N · 작성자 조회 U | **코드** |
| 1차 적용 후 남은 112개 중 **약 108개가 작성자 조회** | **계측.** 이 값이 2차 대상을 정했다 |
| 왜 N 이 아니라 U 인가 | **코드** (1차 캐시) |
| 모델 `3+U+1` 검증 → 세 게시글에서 오차 0 | **계측** |
| **1차의 예측(약 108개 제거) vs 2차 실측(108.3개)** | **계측이 코드에 대한 설명을 검증한 자리.** 사후 서술이 아니라 **미리 반증 가능한 예측을 남긴** 증거다 |

## L-4. 어디에 반영했나
