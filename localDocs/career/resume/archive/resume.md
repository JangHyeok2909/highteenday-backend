### HighTeenDay 익명 커뮤니티 백엔드

2025.05 ~ 진행 중 · github.com/JangHyeok2909/highteenday-backend

**설명**: 고등학생 대상 익명 커뮤니티. 게시글·댓글·반응·인기글 랭킹·알림·채팅, S3 파일 업로드.
동아리에서 3명으로 시작해 4개월 뒤부터 단독 개발, 전체 715 커밋 중 519건 작성.
근거와 버린 대안은 포트폴리오에 수록
**개발 환경**: Java 17, Spring Boot 3.4, JPA, QueryDSL, MySQL 8, Redis, Docker, AWS(EC2, S3) 배포

#### 실시간 인기글 랭킹 설계 (반응·조회 집계, Redis Sorted Set)

- 댓글·반응·스크랩은 트랜잭션 커밋 이후 이벤트로 점수에 반영, 롤백된 행동이 순위에 남는 문제 제거
- 조회는 Redis 에 모아 1분 주기로 반영, 인기 게시글 한 행에 쓰기가 몰리는 문제 회피
- 점수는 좋아요 5·댓글 3·스크랩 2·조회 1·싫어요 −2 가중합을 log10 으로 압축해 산출
  시간 감쇠는 (경과 시간 + 2)^1.5 로 나눠 적용
- 행동이 없어도 순위가 내려가야 하므로 5분 주기 배치로 현재 상위 50개 점수 재계산
- Redis 키를 날짜별로 나눠 당일 활동이 있는 글만 랭킹 후보로 유지
- Sorted Set 만료 시간을 저장 요청 쪽이 넘기도록 변경, 키 종류 추가 시 어댑터 수정 불필요
- 조회수는 성공분만 정산하고 실패분은 버퍼에 남겨 재시도, 삭제된 게시글의 반복 실패는 별도 정리
- 개인화·추천 없음. 상위 50위 밖의 반응 취소 보정은 미구현

#### 댓글 목록 API N+1 제거 (요청당 평균 쿼리 1,507 → 3.9개)

- 엔드포인트별 요청당 쿼리 수 계측을 먼저 붙여 원인 두 곳 확인 (댓글별 반응 조회, 작성자 지연 로딩)
- 반응 일괄 조회로 쿼리 1,507 → 112개, p95 226.7 → 57.2ms 개선
- 페치 조인(fetch join)으로 쿼리 112 → 3.9개, p95 57.2 → 34.3ms 개선 (JPA)
  40.1% 감소는 측정 오차 16% 를 넘는 폭
- 1차 예측 108개와 2차 실측 108.3개 일치, 쿼리 수는 데이터 크기와 무관 (댓글 6개 글과 4,040개 글이 같은 4개)
- 페치 조인을 빼면 실패하는 테스트로 고정, 응답 4,046건 DB 전량 대조 불일치 0, 익명 작성자 노출 0
- 응답 크기는 여전히 댓글 수에 비례. 댓글 페이징은 익명 번호 규칙과 얽힌 별도 과제

#### 스크랩 토글 경쟁 상태로 인한 게시글 상세 조회 장애 해결

- 조회 후 삽입 사이의 경쟁 상태로 생긴 중복 행 한 건이 게시글 상세 조회 전체를 실패시킨 장애 해소
- 유니크 제약과 upsert 적용, 분산 락 대신 고른 근거를 대안 비교로 기록 (MySQL)
- 격리 수준 상향으로는 같은 키의 삽입 충돌이 막히지 않는다는 점을 함께 기록

### HighTeenDay · 고등학생 익명 커뮤니티 백엔드

2025.05 ~ 현재 · github.com/JangHyeok2909/highteenday-backend · 측정 대시보드 janghyeok2909.github.io/highteenday-backend

게시글·댓글·반응·스크랩·인기글·알림·채팅과 소셜 로그인이 있는 커뮤니티 서비스입니다. 동아리 회장으로 프로젝트를 이끌었고, 백엔드 3명 중 게시글·댓글·인기글·S3 업로드를 맡았습니다. 2025.09부터는 혼자 개발하고 있으며, 아래의 부하 테스트 환경 구축과 성능·정합성 개선은 전부 혼자 진행했습니다.

#### 인기글 랭킹 파이프라인 설계·구현

- 댓글·반응·스크랩은 트랜잭션 커밋 후 이벤트(AFTER_COMMIT)로 인기 점수에 반영. 롤백된 행동이 순위에 남지 않음
- 조회수는 Redis에 모아 1분 주기로 DB 반영. 실패한 게시글만 버퍼에 남겨 재시도하고, 삭제된 게시글은 반복 실패하지 않도록 정리
- 순위는 Redis Sorted Set에 일별·5분 버킷으로 유지. 버킷의 만료 시간(TTL)은 호출자가 지정해, 버킷을 추가할 때 저장소 코드를 고치지 않아도 되도록 설계

#### 댓글 목록 API N+1 제거: 요청당 쿼리 1,507개 → 4개, p95 226.7ms → 34.3ms

- 서비스 코드에 쿼리가 보이지 않아 엔드포인트별 요청당 쿼리 수 계측을 먼저 추가. DTO 변환 중 댓글마다 내 반응 조회(댓글 수 × 2)와 작성자 지연 로딩(작성자 수만큼)이 나가는 것을 확인
- 1차: 반응을 일괄 조회로 바꿔 1,507 → 112개, p95 57.2ms. 재계측으로 남은 112개 중 108개가 작성자 조회임을 확인
- 2차: 작성자를 fetch join으로 함께 읽어 112 → 4개, p95 34.3ms. 댓글 6개인 글과 4,040개인 글이 같은 쿼리 4개를 사용
- @BatchSize, @EntityGraph, DTO 프로젝션 등 대안 5개를 쿼리 수와 영향 범위로 비교해 선택
- fetch join을 빼면 실패하는 테스트로 고정하고, 응답 4,046건을 DB와 전량 대조(불일치 0건, 익명 작성자 노출 0건)

#### 부하 테스트 결과를 믿을 수 있게 만든 과정

- 같은 코드의 p95가 실행마다 25~45% 흔들려 개선 판정이 불가능하던 상태. 흔들림의 원인을 호스트 CPU·하이퍼바이저 설정에서 찾다가 닷새를 소모
- 실제 원인은 용량의 1.5배 부하와 사용자 수 고정 부하 모델. 부하 25% 증가에 p95가 30배(402ms → 11,871ms)로 뛰는 용량 곡선과 p95·처리량 역수의 상관 0.962로 확정
- 부하 모델을 도착률 고정으로 전환하고, 판정용 부하를 포화 이하인 초당 4요청(포화 시 실측 17~28요청)으로 결정
- 검증: 호스트가 18% 느려진 4시간 사이 앱 p95 변동 1.5%, 실행 직전 CPU 벤치와 p95의 상관 −0.006
- 실행마다 포화(요청이 처리 용량을 넘어 줄을 선 상태) 여부를 4단계로 자동 판정. 포화 실행의 지연값은 리포트에서 인용되지 않도록 차단하고, 저장된 실행 119건을 재판정해 49건 분리
