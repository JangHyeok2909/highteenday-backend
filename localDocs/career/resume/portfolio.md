## 1. 이 프로젝트가 답하려 한 질문

처음 목표는 커뮤니티 서비스를 만드는 것이었습니다. 만들고 나서 부하를 걸어 보니
응답이 느렸고, **그 느림의 원인을 찾는 과정에서 더 큰 문제를 발견했습니다 —
제가 만든 측정 결과를 제가 믿을 수 없다는 것**이었습니다.

그래서 프로젝트의 질문이 바뀌었습니다.

> **"성능을 개선했다"고 말하려면 무엇이 참이어야 하는가?**

이 문서는 그 질문에 답해 가는 과정입니다. 순서대로 세 가지를 했습니다.
**① 측정을 해석해도 되는 조건을 정의하고 → ② 그 조건 위에서 병목을 고치고 →
③ 고쳤다는 주장이 측정 오차보다 큰지 확인**했습니다.

### 왜 사용자 가치가 아니라 이 질문이었나

먼저 밝힐 것이 있습니다. **이 프로젝트는 사용자 규모를 목표로 만든 서비스가 아닙니다.**
실사용자 지표를 올린 이야기가 여기에는 없습니다.

대신 제가 문제로 잡은 것은 **개발자 판단의 정확성**이었습니다. 만들면서 반복해서 겪은 것이
"고쳤다고 생각했는데 아니었다", "원인을 찾았다고 생각했는데 아니었다" 였기 때문입니다.
**그리고 이 둘은 이어져 있습니다** — 잘못된 실험 결과로 내린 결정은 결국 사용자 경험을
나쁜 방향으로 바꿉니다. 실험을 자주 여는 조직일수록 이 비용이 큽니다.

### 일하는 순서 — 계측 → 코드 → 계측

**코드를 읽으면 무엇이 의심스러운지까지는 알 수 있습니다. 그러나 그중 무엇이 실제로
비싼지는 알 수 없습니다.** 6장의 N+1 도 코드를 꼼꼼히 읽으면 찾을 수 있는 종류였습니다.
문제는 발견 여부가 아니라 **판단 근거**입니다 — 찾았더라도 그것이 요청당 1,507개 중
몇 개인지, 지금 고칠 값이 있는지를 코드는 말해 주지 않습니다. 커넥션 풀 대기(3장)는
아예 애플리케이션 코드 바깥에서 일어났습니다. 그래서 순서가 이렇게 굳었습니다.

> **계측이 어디를 볼지 알려주고 → 코드가 왜 그런지 알려주고 → 다시 계측이 그 설명이
> 맞는지 검증한다.**

세 번째 단계가 빠지면 "코드를 읽고 그럴듯한 설명을 붙였다"에서 끝납니다.
**6장의 N+1 개선이 이 왕복을 두 번 돈 기록**이고, 두 번 모두 마지막 단계에서
**검증 가능한 예측**을 남겼습니다(6.2 · 6.7).

### 숫자 요약

| 무엇 | 값 |
|---|---|
| 댓글 목록 API 요청당 쿼리 수 | **1,507 → 3.9개** (−99.7%) |
| 같은 API 종단 p95 | **226.7ms → 34.3ms** |
| 쿼리 수와 데이터 크기의 관계 | 비례 → **무관**(댓글 6개 글과 4,040개 글이 같은 4개) |
| 오진했던 지연의 실제 원인 | 애플리케이션 지연 아님. **도착률이 처리 용량을 넘긴 포화 — 같은 코드에서 38배 차이** |
| 회귀 판정의 신뢰성 | 잘못된 대조군으로 **“+59,000% 회귀”** 오보 → 대조군 유효성 게이팅 도입 |
| 개선 판정 기준 | 반복 측정의 변동계수로 **최소 검출 가능 효과**를 산출해 정의 |
| 저장된 부하 실행 기록 | 108건 |
| 테스트 | 725개 통과 |

## 2. 시스템과 측정 환경

### 2.1 서비스

고등학생 대상 익명 커뮤니티입니다. 게시글·댓글·반응·스크랩·알림·채팅과
소셜 로그인이 있습니다. 설계에서 신경 쓴 것은 두 가지입니다.

- **익명성이 응답 어디에서도 새지 않을 것** — 익명 글·댓글은 작성자 식별자와 프로필
  이미지를 노출하지 않습니다. 뒤에서 이 규칙을 **최적화 검증의 기준**으로도 씁니다(6.5).
- **읽기가 압도적으로 많은 트래픽 모양** — 목록 조회에 캐시를, 조회수·인기글에는
  Redis 버퍼와 스케줄러 반영을 씁니다.

| 층 | 사용 기술 |
|---|---|
| 애플리케이션 | Java 17 · Spring Boot 3.4 · Spring Security · JPA(Hibernate) · QueryDSL |

**신호를 두 종류로 나눠 다루는 것이 이 경로의 출발점입니다.**

- **명시적 신호** — 댓글·반응·스크랩. **트랜잭션이 커밋된 뒤**(`AFTER_COMMIT`) 이벤트로
  받아 점수에 반영합니다. 커밋 전에 반영하면 **롤백된 행동이 순위에 남습니다.**
- **암시적 신호** — 조회. 요청마다 DB 를 쓰면 인기 게시글 한 행에 쓰기가 몰리므로
  Redis 에 모아 두고 **1분 주기로 반영**합니다.

#### 여기서 한 설계 판단 — 만료를 누가 정하는가

정렬 집합의 TTL 을 **어댑터가 아니라 호출자가 넘기게** 했습니다.

버킷은 종류마다 수명이 다릅니다. 일자 리더보드는 하루가 지나면 다시 읽히지 않고,
5분 실시간 버킷은 몇십 분이면 끝납니다. 어댑터가 **키 이름을 보고 수명을 추측**하게
만들면 **새 버킷을 하나 추가할 때마다 어댑터를 고쳐야 합니다.**
**수명을 아는 쪽이 직접 말하게 한 것**이고, 확장 지점을 인터페이스 바깥에 둔 판단입니다.

#### 실패한 것만 남겨 다시 시도합니다

조회수 반영은 게시글마다 따로 실패할 수 있습니다. 그래서 **성공한 것만 정산하고 실패분은
버퍼에 남겨** 다음 주기에 다시 시도합니다. 다만 **삭제된 게시글은 재시도해도 성공하지
않으므로** 반영된 것으로 쳐서 정리합니다 — 그러지 않으면 같은 실패가 매 분 반복되면서
로그만 쌓이고 버퍼는 영원히 비지 않습니다.

#### 이 경로에도 결함이 하나 있었습니다

초기에는 정렬 집합 키에 만료가 없었습니다. 지나간 날짜와 시각의 순위가 **영구히 남아
Redis 메모리가 단조 증가**합니다. 결함 장부(KI-20)에 등록한 뒤 TTL 을 넣어 해소했습니다.
**랭킹 경로에도 다른 장들과 같은 "발견 → 기록 → 수정" 사이클이 있었습니다.**
<!-- /FULL -->

#### 무엇이 없는지 먼저 밝힙니다

**개인화도 추천도 없습니다.** 점수는 모든 사용자에게 같고 모델을 쓰지 않습니다.
규모도 게시판 단위입니다. 이 절이 말하는 것은 규모나 정교함이 아니라,
**콘텐츠를 모아 점수를 매겨 순위대로 내보내는 경로를 처음부터 끝까지 만들어 봤다**는 것입니다.

**포화를 만드는 것이 목적**이기 때문입니다. 거기서 포화가 실패라면 그 시나리오는 항상
실패합니다.

그래서 포화를 **판정(pass/fail)이 아니라 해석 조건(interpretation condition)** 으로
정의했습니다. 결과를 버리는 것이 아니라 **그 결과로 무엇을 주장할 수 있는지를 제한**합니다.

## 4. 사건 둘 — 회귀 탐지기가 보고한 “+59,000% 성능 저하”

### 4.1 무슨 일이 있었나

성능 회귀를 자동으로 잡는 판정기를 만들어 두었습니다. 어느 날 이 판정기가
**p95 가 101ms 에서 60,001ms 로 나빠졌다 — +59,000% 회귀**라고 보고했습니다.

실제로는 회귀가 아니었습니다. 판정기가 **부하 13배 · 데이터 100배인 실행을 대조군으로
골랐던 것**입니다. 조건이 다른 두 실행을 비교했으니 차이는 당연했습니다.

### 4.2 원인 — 두 개의 다른 질문을 하나로 취급했다

회귀 판정은 **서로 다른 두 질문**에 답해야 합니다.

| | 질문 | 성격 |
|---|---|---|
| (a) | 이력상 **직전 실행**은 무엇인가 | 시간축 질문 |
| (b) | 이 실행의 **대조군으로 유효한** 실행은 무엇인가 | **실험 설계 질문** |

오래도록 (a)만 구현돼 있었고, (b)는 *"같은 시나리오면 어련히 같겠지"* 라고 **가정**돼
있었습니다. **그 가정이 코드가 아니라 머릿속에만 있었다는 것**이 문제의 전부였습니다.

### 4.3 남긴 것 — 조건을 데이터로 분리

실행 조건을 **비교 자체를 무효로 만드는 것**과 **신뢰도만 낮추는 것**으로 나누고,
앞의 것만으로 "같은 실험"을 식별하는 해시를 만들었습니다. 대조군은 그 해시가 같은 실행
중에서만 고릅니다.

조건을 분기문이 아니라 **선언적인 표**로 뺐습니다. 조건이 하나 늘면 표에 한 줄을 더하는
것으로 **대조군 선택 · 리포트 · 추세 계열 분리가 전부 따라옵니다.**

## 5. “개선했다”고 말할 자격을 숫자로 정의하기

### 5.1 문제

*"p95 가 20% 나빠지면 회귀"* 라고 말하려면 전제가 필요합니다 —
**아무것도 바꾸지 않고 같은 조건을 반복했을 때의 자연 편차가 20%보다 작아야** 합니다.
그 편차를 모르면 20% 는 근거 없는 숫자입니다.

### 5.2 한 것

같은 조건을 N회 반복 실행해 **변동계수(표준편차 ÷ 평균)** 를 재고, 거기서
**최소 검출 가능 효과(MDE)** 를 구했습니다. 그보다 작은 변화는 개선으로 인정하지 않습니다.

변동계수는 무차원이라 **절대 지연이 달라진 환경끼리도 비교할 수 있습니다.**
측정 환경 자체를 바꾼 전후를 비교할 수 있는 유일한 축이라 이 지표를 골랐습니다.


### 5.3 스스로 무효 처리한 확정치

처음 확정한 변동계수는 **3.12%** 였습니다. 그런데 이 값이 **포화 상태에서 측정된 것**임을
뒤늦게 알았습니다(3장과 같은 원인). 그래서 **제가 낸 확정치를 스스로 무효 처리하고**
포화 이하 운용점에서 다시 쟀습니다.

| | 이전(포화) | 이후(포화 이하) |
|---|---|---|
| p95 의 변동계수 | 3.12% | **9.6 ~ 15.8%** |
| p95 의 **절대 표준편차** | 369ms | **27 ~ 58ms** |

**퍼센트는 나빠졌는데 실제 흔들림은 6~14배 줄었습니다.** 분모인 평균이 43배 작아졌기
때문입니다. 재현성이 나빠진 것이 아니라 **퍼센트로 말할 때의 문턱이 높아진 것**입니다.

이 구분을 못 하면 "측정 환경을 고쳤더니 변동계수가 3배가 됐다"는 잘못된 결론에 도달합니다.

## 6. 개선 — 요청당 쿼리 1,507개에서 3.9개로

### 6.1 문제 — 코드에 보이지 않는 쿼리

댓글 목록 API 한 번에 쿼리가 **1,507개** 나갔습니다. 그런데
**서비스에도 컨트롤러에도 쿼리처럼 보이는 코드가 없었습니다.**

```java
// dtos/CommentDto.java · fromEntity
.userId(comment.getUser().getId())            // 지연 로딩 프록시 초기화 → SELECT 1회
.author(comment.getUser().getNicknameValue()) // 이미 초기화됨 → 추가 쿼리 없음
```

쿼리는 **DTO 를 만드는 순간** 나가고 있었습니다. 두 종류였습니다.

- **내 반응 확인** — 댓글 한 건마다 좋아요/싫어요를 따로 조회 (댓글 수 × 2)
- **작성자 조회** — 지연 로딩 프록시가 하나씩 풀림 (**서로 다른 작성자 수**만큼)

작성자 조회가 댓글 수가 아니라 **작성자 수**에 비례한다는 점이 중요합니다. 같은 사람이
댓글을 여러 개 달았으면 두 번째부터는 영속성 컨텍스트의 1차 캐시에서 나오기 때문입니다.
**이 구분은 코드로 짐작할 수 있지만, 그것이 요청당 1,507개 중 어느 정도인지는
세어 봐야 압니다.**

그래서 먼저 **엔드포인트별 요청당 쿼리 수를 재는 계측**을 붙였습니다. 개선보다 계측이
먼저였습니다.

### 6.2 두 번에 나눠 고쳤다

```html-raw
<div class="fig">
  <div class="bar-row"><span class="bar-label">최초</span><span class="bar-track"><span class="bar-fill" style="width:100%"></span></span><span class="bar-val">1,507</span></div>
  <div class="bar-row"><span class="bar-label">반응 일괄 조회 후</span><span class="bar-track"><span class="bar-fill" style="width:7.4%"></span></span><span class="bar-val">112</span></div>
  <div class="bar-row"><span class="bar-label">작성자 패치 조인 후</span><span class="bar-track"><span class="bar-fill after" style="width:0.26%"></span></span><span class="bar-val">3.9</span></div>
  <div class="fig-cap">그림 7. 댓글 목록 API 의 요청당 쿼리 수. 마지막 막대는 전체의 0.26% 라 선으로만 보인다.</div>
</div>
```

| 단계 | 무엇을 바꿨나 | 요청당 쿼리 | 종단 p95 |
|---|---|---|---|
| 최초 | — | 1,507 | 226.7ms |
| 1차 | 반응 확인을 댓글별 조회에서 **일괄 조회**로 | **112** (−92.6%) | 57.2ms (−74.8%) |
| 2차 | 작성자를 목록 쿼리에서 **패치 조인**으로 함께 읽기 | **3.9** (−96.5%) | **34.3ms** (−40.1%) |

**두 번에 나눈 것은 원칙 때문만이 아니라 절차 때문이기도 합니다.**
"한 번에 변수 하나"를 지키려는 이유도 있었지만, 실제로 **2차의 대상을 정한 것은 재계측**
이었습니다. 1차를 적용하고 다시 재니 남은 112개 중 **약 108개가 작성자 조회**였고,
그 값이 다음에 무엇을 열어야 할지 알려줬습니다. 코드만 봐서는 "작성자를 U번 읽는다"까지는
알 수 있어도 **그것이 전체 비용의 96% 인지**는 알 수 없습니다.

그리고 1차 문서에 **없앨 쿼리 수를 약 108개로 예측해 적어 두었고, 2차 실측이 108.3개**
였습니다. 계측이 코드에 대한 제 설명을 검증한 자리입니다 — 이 절차가 사후 서술이 아니라
**미리 반증 가능한 예측을 남기는 방식**이라는 증거이기도 합니다. (예측이 빗나간 자리도
있습니다. 6.7 참조.)

**2차 변경의 실제 크기는 리포지토리 쿼리 한 줄입니다.**

```java
// 변경 전
@Query("select c from Comment c where c.isValid=true and c.post=:post")
// 변경 후
@Query("select c from Comment c join fetch c.user where c.isValid=true and c.post=:post")
```

`@ManyToOne` 패치 조인이라 **결과 행 수가 변하지 않습니다.** 댓글 한 건에 작성자는
한 명뿐이라 조인이 행을 부풀리지 않고, 컬렉션 패치 조인에서 필요한 중복 제거도,
"페이징을 메모리에서 한다"는 경고도 발생하지 않습니다.
`left join` 이 아니라 내부 조인을 쓴 것은 작성자 컬럼이 `nullable = false` 라
외부 조인이 걸러낼 행이 없기 때문입니다.

### 6.3 진짜 성과는 백분율이 아니다

```
요청당 쿼리 수 (회차별)
Before   120.5  109.8  114.4  109.5  106.9    ← 표본 게시글의 작성자 수에 따라 흔들림
After      3.9    3.9    3.9    3.9    3.9    ← 데이터와 무관한 상수
```

| 게시글 | 댓글 수 | 서로 다른 작성자 | 개선 전 | **개선 후** |
|---|---:|---:|---:|---:|
| A | 6 | 5 | 9 | **4** |
| B | 492 | 130 | 134 | **4** |
| C | 4,040 | 450 | 454 | **4** |

**쿼리 수가 데이터 크기와 무관해진 것**이 이 최적화의 실제 결과입니다.
남은 4개는 인증 1 · 게시글 1 · 댓글 목록 1 · 반응 일괄 1 이고,
여기에는 댓글 수에도 작성자 수에도 비례하는 항이 없습니다.

### 6.4 버린 대안 — 이 기록이 본문입니다

같은 자리를 다시 볼 때 "왜 이렇게 했지"에 답하기 위해 남긴 표입니다.

| 대안 | 쿼리 수 | 버린 이유 |
|---|---|---|
| `@BatchSize(100)` | 1 + ⌈U/100⌉ | **1 로 내려가지 않습니다.** 작성자 450명이면 5개가 남습니다. 게다가 엔티티에 붙는 설정이라 그 연관을 쓰는 **모든 경로**의 동작이 함께 바뀝니다 |
| 전역 배치 페치 크기 | 1 + ⌈U/n⌉ | 같은 문제에 폭발 반경만 넓습니다. 애플리케이션 전체의 지연 로딩 방식이 바뀌어 **"한 번에 변수 하나" 원칙**을 지킬 수 없습니다 |
| `@EntityGraph` | 1 | 효과는 같습니다. 다만 이 메서드는 이미 JPQL 을 직접 쓰고 있어, **무엇을 거르는지(JPQL)와 무엇을 함께 읽는지(애너테이션)가 두 곳으로 갈립니다** |
| DTO 프로젝션 | 1 | **가장 좋은 안입니다.** 필요한 컬럼만 읽어 전송량까지 줄어듭니다. 그런데 호출부 셋이 엔티티를 받아야 동작해서 같이 고쳐야 하고, 그러면 **변수가 둘 이상이 되어 측정이 무의미해집니다.** 별도 과제로 남겼습니다 |
| 작성자만 2차 일괄 조회 | 2 | 사용자 행이 중복 없이 전송됩니다. 왕복이 하나 더 필요한 대가로 얻는 것이 전송량뿐이라 지금은 버렸습니다. **6.6 의 균형이 깨지면 이 안으로 돌아옵니다** |

### 6.5 검증 — 세 겹

**① 음성 대조 테스트.** 핵심 계약이 "결과가 맞다"가 아니라 **"작성자를 함께 읽는다"** 라서,
Hibernate 통계로 **실행된 문장 수 자체**를 테스트로 고정했습니다.
**패치 조인을 다시 빼면 문장 수가 1 → 4 로 늘며 테스트가 실패하는 것**까지 확인했습니다.

> 이 검증에서 가장 중요한 코드 한 줄은 영속성 컨텍스트를 비우는 `em.clear()` 입니다.
> 비우지 않으면 준비 단계에서 저장한 사용자들이 1차 캐시에 남아 **패치 조인이 없어도
> 추가 쿼리가 나가지 않습니다.** 그 상태의 테스트는 통과하지만 아무것도 검증하지 못합니다.

**② 부하 없는 단일 요청 실측.** 잡음이 0이라 통계가 필요 없습니다. 위 표의 세 게시글에서
모델과 실측이 **오차 0** 이었습니다.

**③ 응답 정합성 전량 대조.** 쿼리 모양이 바뀌었으므로 응답이 같은 값을 내는지 DB 와
직접 맞췄습니다. 댓글 4,046건짜리 게시글에서

```
응답 댓글 수 4,046건 = DB 4,046건
실명 댓글 1,586건의 (댓글 id, 작성자 id, 닉네임)  →  API 에만 있는 조합 0건 · DB 에만 있는 조합 0건
익명 댓글 2,460건  →  작성자 식별자 노출 0건 · 프로필 이미지 노출 0건
```

**익명성 규칙을 최적화 검증의 기준으로 쓴 것**이 이 대조의 핵심입니다.
쿼리를 바꿔도 익명성이 유지되는지는 성능과 별개로 반드시 확인해야 합니다.

### 6.6 부작용을 숨기지 않기

패치 조인은 댓글 행마다 작성자 행을 붙여 읽습니다. 댓글 4,040개에 작성자 450명이면
**같은 사용자 행을 평균 9회 중복해서 읽습니다.** 착수 전에 이것이 이득을 상쇄할 수 있다고
봤고, **측정은 양쪽을 다 보여줬습니다.**

| 지표 | Before | After | 변화 |
|---|---|---|---|
| MySQL 초당 읽은 행 | 5,935 | 7,294 | **+22.9%** ← 중복 읽기의 직접 증거 |
| MySQL 초당 쿼리 | 544.3 | 274.8 | −49.5% |
| 요청당 DB CPU 시간 | 8.43ms | 6.35ms | **−24.6%** |

**행 읽기는 23% 늘었는데 DB CPU 시간은 25% 줄었습니다.** 왕복 108회를 없앤 이득이
추가 행 읽기 비용보다 컸기 때문입니다. 행 읽기가 싼 이유는 버퍼풀 적중률이 100% 라
중복 읽기가 디스크 접근을 만들지 않기 때문이고, **데이터가 버퍼풀보다 커지면 이 균형은
달라질 수 있습니다.** 그때 돌아갈 안이 6.4 표의 마지막 줄입니다.

또 하나 — **쿼리당 DB 시간은 0.198ms 에서 1.272ms 로 6.4배가 됐습니다.** 악화가 아니라
**없앤 108개가 가장 싼 쿼리(기본 키 1행 조회)였기 때문**입니다. 싼 쿼리가 분모에서 빠지면
남은 쿼리의 평균 단가는 올라갑니다. **쿼리당 비용은 이런 최적화의 성패를 판정하는 데
쓸 수 없습니다.** 봐야 할 것은 요청당 총량이고, 그것은 22.22ms → 4.98ms 로 줄었습니다.

### 6.7 예측이 틀린 지점

착수 전에 개선 상한을 계산해 뒀습니다. 대조하면 이렇습니다.

| 항목 | 예측 | 실측 | 판정 |
|---|---|---|---|
| 없앨 쿼리 수 | 약 108 | 108.3 | 맞음 |
| 없앨 DB 시간 | 약 21ms | 17.2ms | 거의 맞음 |
| **종단 p95 개선폭** | **20% 안팎이 상한** | **40.1%** | **상한을 2배 초과** |

**엔드포인트 수준 예측은 맞았는데 종단 백분율만 틀렸습니다.** 상한을 *평균* 절감치로
계산했기 때문입니다. 그런데 시스템의 p95 를 만드는 것은 평균적인 요청이 아니라
**댓글이 많은 게시글의 요청**이고, 그런 요청에서 없앤 쿼리는 평균 108개가 아니라 최대 450개입니다.

> **평균 기반 상한은 평균의 상한이지 꼬리의 상한이 아닙니다.**
> 비용이 데이터 크기에 비례하는 문제는 꼬리에 편중돼 있어서, 평균으로 환산한 예측이
> 구조적으로 개선폭을 과소평가합니다. 다음에 착수 여부를 판단할 때는 **꼬리 요청의
> 절감치를 따로 계산해야 합니다.**

### 6.8 부수적으로 확인된 것

남아 있던 N+1 을 마저 걷어냈는데도 **느린 쿼리 건수는 그대로였습니다(+1.1%).**
느린 쿼리의 원인은 N+1 이 아니라 대부분 검색의 `LIKE` 라는 앞선 판단이
두 번째로 확인된 것입니다. **개선이 예상 밖의 것을 건드리지 않았다는 증거**이기도 합니다.

### 6.9 반증이 다음 병목을 지목했습니다 — 같은 계측, 다른 종류

6.8 의 "느린 쿼리는 N+1 과 무관하다"는 반증은 거기서 끝나지 않았습니다.
**그 판단이 다음에 무엇을 봐야 하는지 알려줬습니다** — 게시글 검색입니다.

**두 병목은 성격이 정반대입니다.**

| | 댓글 목록 (6장) | **게시글 검색** |
|---|---|---|
| 문제의 모양 | **싼 쿼리를 여러 번** | **비싼 쿼리 한 번** |
| 요청당 쿼리 수 | 112개 → 3.9개 | **6.2개** (원래 적다) |
| 쿼리당 DB 시간 | 1.27ms | **13.6ms** |
| 요청당 DB 시간 | 22.22ms | **81.37ms** |
| DB 시간 비중 | 61.5% | **95%** — 앱에서 하는 일이 없다는 뜻 |
| 고치는 방법 | 왕복을 줄인다 | 쿼리 자체를 바꿔야 한다 |

검색은 **5회차 전부 최솟값이 65.7~78.9ms** 로, **단 한 건도 30ms 아래로 내려간 적이
없습니다.** 전체 요청의 1.06% 인데 응답 시간 총합의 **6.1%** 를 씁니다.

원인은 `LIKE '%키워드%'` 입니다. 앞이 와일드카드라 B-tree 인덱스를 탈 수 없고,
옵티마이저에게 남는 선택지는 전체 스캔뿐입니다. **데이터가 커질수록 선형으로 나빠집니다.**

<!-- FULL -->
**아직 고치지 않았고, 고르지도 않았습니다.** 후보를 비교만 해 두었습니다.

| 후보 | 효과 | 버리는 것 |
|---|---|---|
| **FULLTEXT + ngram 파서** | 전체 스캔 제거. 한국어는 형태소가 아니라 n-gram 으로 쪼개므로 ngram 이 필요 | **검색 결과의 순서와 매칭 규칙이 달라진다.** 성능이 아니라 기능이 바뀌는 부분이라 별도 검증이 필요 |
| 접두사 검색(`LIKE '키워드%'`) | 일반 인덱스를 탄다. 변경이 가장 작다 | **기능 축소.** "시험" 으로 "기말시험" 을 못 찾는다 |
| 검색 엔진 분리 | 가장 빠르고 랭킹·오타 보정까지 | 운영 구성요소가 늘고 색인 동기화 문제가 생긴다. **현재 규모에 맞지 않는다** |
| 결과 캐싱 | 반복 키워드에 효과 | 검색어가 롱테일이면 적중률이 낮다. **근본 원인을 두고 증상만 가린다** |

1순위는 FULLTEXT + ngram 이지만, **성능 변경이 아니라 검색 기능 변경**이라
착수 전에 확인할 것이 남아 있습니다.

### 6.10 응답 시간이 DB 시간으로 설명되지 않는 곳 — 쓰기 경로

같은 계측이 세 번째 것을 드러냈습니다. **쓰기 엔드포인트의 응답 시간 대부분이
DB 밖에서 나옵니다.**

| 엔드포인트 | 요청당 DB 시간 | 응답 시간 | **비-DB 시간** | 비중 |
|---|---:|---:|---:|---:|
| 댓글 작성 | 3.55ms | 41.66ms | **38.11ms** | **91%** |
| 게시글 작성 | 2.29ms | 23.89ms | 21.59ms | 90% |
| 반응 등록 | 5.81ms | 28.17ms | 22.36ms | 79% |
| *(대조) 읽기 엔드포인트* | — | — | *3~5ms* | — |

**읽기는 비-DB 시간이 3~5ms 인데 쓰기만 한 자릿수가 다릅니다.**

<!-- FULL -->
**원인 후보가 둘이고, 각각의 몫은 아직 재지 않았습니다.** 이 상태 그대로 적습니다.

**후보 A — 응답에 필요 없는 후처리를 요청 스레드가 기다립니다.**
댓글 생성 이벤트에 리스너가 둘 붙어 있는데(알림 생성, 인기글 점수 갱신)
**둘 다 비동기가 아닙니다.** `@TransactionalEventListener` 는 **동기가 기본**이고,
`AFTER_COMMIT` 은 *"커밋 뒤에"* 를 뜻할 뿐 *"다른 스레드에서"* 를 뜻하지 않습니다.
클라이언트는 자기가 받아 가지도 않을 알림 저장과 점수 갱신이 끝날 때까지 기다립니다.

**후보 B — 커밋 fsync 가 비-DB 시간에 숨습니다.**
`innodb_flush_log_at_trx_commit=1` 과 `sync_binlog=1` 이라 커밋 한 번에 fsync 두 번입니다.
그런데 댓글 생성은 **커밋을 두 번** 합니다 — 본 트랜잭션 하나, 그리고 알림 저장이
`REQUIRES_NEW` 라 별도 트랜잭션으로 한 번 더. **요청 하나에 fsync 4회**입니다.

**둘을 가르지 않은 채로 고치면 무엇이 효과였는지 알 수 없습니다.** 그래서 아직
착수하지 않았습니다 — 5장에서 정한 규칙(한 번에 변수 하나)이 여기에도 적용됩니다.

## 7. 목표를 다시 세우다 — "충분히 빠른가"를 정의하기

6장까지가 *"개선했다고 말할 자격"* 이었다면, 이 장은 **"무엇을 목표로 삼을 자격"** 입니다.

### 7.1 물었던 것

OPT-002 로 전체 p95 가 34.3ms, p99 가 80.9ms 가 된 시점에 물었습니다.

> **"p99 를 30ms 안에 넣으려면 무엇을 더 해야 하나?"**

### 7.2 답 — 도달할 수 없고, 도달하게 만드는 방법이 성능 개선이 아니다

산술로 먼저 막혔습니다.

```
측정 구간 전체 요청   34,471건 (After 5회 합계)
30ms 초과            4,053건 = 11.76%
목표                   345건 이하 = 1.00%
```

여기서 **로그인 하나가 상한을 만듭니다.**

```
login 최솟값   71.4  70.6  74.8  73.2  73.7 ms   (5회차 전부)
login 건수     585건 = 전체의 1.70%
```

**가장 빠른 로그인조차 목표의 2.4배**이고, 로그인이 전체의 **1.70%** 입니다.
목표 허용치는 1.00% 입니다. **1.70% > 1.00% 이므로 다른 모든 요청이 0ms 가 되어도
전역 p99 는 로그인 분포 안에 떨어집니다.** 전역 p99 의 하한이 약 71ms 라는 뜻입니다.

그리고 원인이 쿼리가 아닙니다. 비밀번호 해싱이 **BCrypt strength 10** 이고,
**70~90ms 는 설계대로 나온 값**입니다. 무차별 대입을 늦추려고 일부러 느린 알고리즘입니다.

> **strength 를 낮추면 목표에 가까워지지만, 그것은 성능 최적화가 아니라
> 비밀번호 해싱 강도를 낮추는 보안 결정입니다.** 지연 목표를 맞추려고 할 일이 아닙니다.

### 7.3 버린 대안 — 이 장의 본문입니다

| 대안 | 버린 이유 |
|---|---|
| BCrypt strength 10 → 8 | 약 4배 빨라져 20ms 대가 되지만 **해싱 강도가 1/4 이 된다.** 지연 목표와 맞바꿀 성질의 값이 아니다 |
| 전역 목표를 80ms 로 완화 | 숫자는 맞출 수 있지만 **정보가 사라진다.** 게시판 목록(현재 p99 12ms)이 60ms 로 나빠져도 통과한다 |
| 로그인만 통계에서 제외 | 제외 규칙이 하나 생기면 다음 예외도 정당화된다. 그리고 **로그인이 느린 것은 실제 사용자 경험**이라 안 재는 것이 답이 아니다 |
| 로그인 결과 캐싱·세션 연장 | 인증 설계 변경이다. **지연 목표 때문에 인증 수명을 늘리는 것은 순서가 거꾸로다** |

### 7.4 결정 — 그룹별 목표

| 그룹 | 목표 p99 | 현재 | 무엇을 고쳐야 도달하나 |
|---|---|---|---|
| 읽기 (상세·게시판 목록·채팅방) | **30ms** | 12~24ms | 유지 |
| 목록 (댓글·게시글·인기글) | **30ms** | 48~97ms | 댓글 목록 페이징 |
| 쓰기 (작성·반응) | **50ms** | 84~135ms | 6.10 |
| 검색 | **30ms** | 206ms | 6.9 |
| 인증 (로그인) | **150ms** | 910ms | 큐잉 완화 — **해싱 강도는 건드리지 않는다** |

**이렇게 나누면 각 목표가 "무엇을 고쳐야 도달하는지"와 직접 연결됩니다.**
전역 하나짜리 목표에서는 로그인 때문에 전체가 실패로 찍히고, 그 신호가
*"어디를 고쳐라"* 를 가리키지 않았습니다.

**쓰기만 50ms 로 다른 이유**는 커밋 fsync 가 하한을 만들기 때문입니다.
내구성을 유지하는 한 이 비용은 없앨 수 없고, **없애는 선택은 성능이 아니라
데이터 보존에 관한 결정**입니다.

<!-- FULL -->
### 7.5 목표를 포기했다고 느린 요청이 사라지지는 않습니다

전역 목표를 버린 대신, **남은 30ms 초과 요청이 무엇으로 구성돼 있는지**를 같이 적었습니다.

| 요청 | 30ms 초과 지분 | 진단 |
|---|---:|---|
| **댓글 목록** | **41.8%** | 쿼리는 상수 4개인데 **응답 크기가 댓글 수에 비례**. 4,046건 글의 응답이 1.6MB |
| 로그인 | 14.4% | BCrypt — 7.2 |
| 검색 | 9.0% | 6.9 |
| 댓글 작성 | 7.6% | 6.10 |
| 그 외 | 27.2% | 일부 미진단 |

**가장 큰 항목이 여전히 댓글 목록이고, 성격이 바뀌었습니다.** 쿼리 수를 1,507 → 3.9 로
만들어 DB 문제는 끝났는데, 이제 **댓글을 DTO 로 만들고 익명화 루프를 돌고 JSON 으로
직렬화하는 앱 비용**이 남았습니다. 중앙값은 7.1ms 로 이미 빠르고 꼬리만 느립니다 —
전형적인 페이징 부재 형태입니다.

**그런데 댓글 목록 페이징은 쿼리 튜닝이 아니라 도메인 설계 변경입니다.**
익명 번호("익명3")의 N 이 **게시글 전체 댓글의 등장 순서**라, 페이지로 자르면
2페이지의 "익명3" 이 1페이지의 "익명3" 과 다른 사람이 됩니다.
**익명 번호를 페이지와 무관하게 결정하는 방법을 먼저 정해야 페이징을 할 수 있습니다.**

> **초과 건수는 추정입니다.** 개별 요청 시간을 세지 않고 회차별 분위수 사이를
> 선형보간해 계산했습니다. 순위와 규모는 신뢰할 수 있지만 건수 자체를 인용할 때는
> 이 한계를 함께 적어야 합니다. 로그인과 검색의 100% 만은 최솟값이 30ms 를 넘으므로
> 추정이 아니라 확정입니다.

### 8.2 배운 것 — 쓰기의 결함이 읽기의 장애로 번진다

정합성 결함은 그 자리에서 조용히 틀린 값으로 남는 것이 아니라,
**그 값을 읽는 다른 경로를 통해 전면 장애로 커질 수 있습니다.**
쓰기 경로 하나의 경쟁 상태가 서비스의 핵심 화면을 죽였습니다.

### 8.3 왜 유니크 제약인가

DB 유니크 제약을 걸고 삽입을 upsert 로 바꿔 해소했습니다. **분산 락을 쓰지 않았습니다.**

| 방법 | 왜 안 골랐나 |
|---|---|
| 애플리케이션 동기화 | 인스턴스가 늘면 무력합니다 |
| 분산 락(Redis 등) | **구성 요소를 하나 더 늘리고, 락 획득 실패·만료·시계 문제를 새로 떠안습니다.** 지금 구조에서 얻는 것보다 비용이 큽니다 |
| 격리 수준 상향 | 이 경쟁 상태는 **같은 키의 삽입 충돌**이라 격리 수준을 올려도 막히지 않습니다 |
| **유니크 제약 + upsert** | **DB 가 이미 제공하는 직렬화 지점을 씁니다.** 중복이 애초에 저장되지 않고, 재시도도 필요 없습니다 |

**"단일 인스턴스에서는 유니크 제약이 정답"** 이라고 말할 수 있는 것 자체가 판단의 근거입니다.
구성 요소를 늘리는 해법이 항상 더 나은 해법은 아닙니다.

## 9. 일하는 방식

**동아리 프로젝트로 3명이 시작했고 제가 리드했습니다.** 백엔드에서는 사용자 엔티티와
인증 설정을 제외한 대부분 — 게시글·댓글·인기글·파일 업로드 — 을 맡았습니다.
**4개월 뒤부터는 혼자 이어오고 있습니다.** 전체 715 커밋 중 519건이 제 것이고,
`performance/` 의 158 커밋은 전부 단독 구간의 것입니다.

그래서 아래 규칙들은 두 구간을 모두 거쳐 남았습니다. **여럿일 때는 서로의 판단을
따라가기 위해 필요했고, 혼자가 된 뒤에는 몇 달 전의 내 판단을 따라가기 위해 필요했습니다.**
세 가지 모두 **"나중에 다른 사람이 이 자리를 다시 볼 때"** 를 위한 장치라
**팀 규모가 커질수록 값이 커집니다.**

### 9.1 결함을 성격별로 나눠 기록합니다

세 장부를 분리해 운영합니다. 경계는 **무엇이 잘못됐는가**입니다.

| 장부 | 다루는 것 | 예 |
|---|---|---|
| 결함 | **틀린 것** | 카운터가 유실됨, 익명 정보가 노출됨 |
| 병목 | **느린 것** | 댓글 목록 N+1, 깊은 페이지 조회 |
| 측정 시스템 발견 | **잘못 재는 것** | 대조군 오선택, 노이즈 하한이 낡음 |

셋을 한 곳에 모으면 "지금 무엇을 믿을 수 없나"를 훑을 수 없습니다. **읽는 목적이 다르면
문서를 나눕니다.**

**장부는 셋이 아니라 여섯 갈래로 갈라져 있습니다.** 병목(BTL) 14건 · 실험(EXP) 7건 ·
최적화(OPT) 2건 · 결함(KI) · 결정 기록(ADR) · 측정 시스템 발견입니다.
**세 축(BTL → EXP → OPT)이 하나의 사슬**이고, 사슬이 끊기면 최적화 대장에 올리지 않습니다.

### 9.2 결정은 코드가 아니라 문서에 남깁니다

성능 문서 밖에도 **설계 결정 기록(ADR)이 넷** 있습니다.

| ADR | 무엇을 정했나 |
|---|---|
| 반응 카운트에 락을 쓰지 않는다 | 정합성보다 처리량을 택한 자리와 그 근거 |
| 조회수는 Redis 버퍼를 거친다 | 인기 게시글 한 행에 쓰기가 몰리는 문제 |
| **게시글 목록은 커서+오프셋 하이브리드** | 이전/다음은 커서, 페이지 점프는 오프셋 |
| S3 는 임시 업로드 후 승격 | 실패한 업로드가 고아 객체로 남지 않도록 |

**하이브리드 페이징 ADR 은 스스로 *"소급 채록 — 결정 당시 기록이 아니라 README·코드에서
재구성"* 이라고 밝히고 있습니다.** 나중에 복원한 기록과 당시 기록을 구분해 두지 않으면,
문서 전체의 신뢰도가 같은 수준으로 떨어지기 때문입니다.

### 9.3 버린 대안을 본문으로 씁니다

최적화 기록에는 채택안뿐 아니라 **검토하고 버린 대안과 그 이유**를 함께 적습니다(6.4).
채택안만 적힌 문서는 몇 달 뒤에 "왜 이렇게 했지"에 답하지 못합니다.
**효과가 없었던 시도도 같은 형식으로 남깁니다** — 같은 삽질을 반복하지 않기 위해서입니다.

### 9.4 설계와 검증 방법을 정하고, 구현과 문서화를 AI 에 위임합니다

AI 에이전트를 적극적으로 씁니다. **다만 순서가 중요합니다 — 무엇을 만들지와 그것이
맞는지 어떻게 확인할지를 먼저 정하고, 그다음에 위임합니다.**

| 제가 먼저 정하는 것 | 위임하는 것 |
|---|---|
| **무엇을 문제로 볼 것인가** — 이 병목을 지금 고칠 값이 있는가 | 코드 작성 |
| **기능 범위와 경계** — 무엇을 바꾸고 무엇을 건드리지 않을 것인가 | 정형 변환·반복 작업 |
| **대안 비교와 선택** — 6.4 의 표는 제가 만든 판단입니다 | 테스트 골격 |
| **검증 방법 설계** — 단위·통합 테스트, 음성 대조, 응답 전량 대조 | 문서 초안·보고 |

**검증 방법을 먼저 정하는 것이 이 순서의 핵심입니다.** 6.5 의 음성 대조 테스트는
*"패치 조인을 다시 빼면 실패해야 한다"* 는 조건을 **구현 전에 정해 둔 것**이고,
그 조건이 없었다면 `em.clear()` 를 빠뜨린 채 통과하는 테스트가 만들어졌을 것입니다.
**AI 는 통과하는 테스트를 잘 만들지만, 무엇이 실패해야 하는지는 정해 주지 않습니다.**

6.4 의 대안 다섯 개를 쿼리 수와 영향 범위로 비교해 고른 것, 6.6 에서 부작용을 먼저
예상하고 측정으로 확인한 것, 6.7 에서 제 예측이 틀린 이유를 규명한 것이
**위임할 수 없었던 부분**입니다.

### 9.5 지키는 규칙 몇 가지

- **한 번에 변수 하나.** 두 가지를 같이 바꾸면 어느 쪽 효과인지 알 수 없습니다.
  6장의 두 최적화를 굳이 두 번에 나눈 이유입니다.
- **수치 없는 최적화는 기록하지 않습니다.** 실험 없이 "좋아 보여서" 적용한 변경은
  최적화 대장에 올리지 않습니다.
- **스키마는 마이그레이션으로만 바꿉니다.** 운영에서 자동 DDL 을 쓰지 않습니다.
- 현재 테스트 **725개**가 통과합니다.

유효한지를 밝히지 않으면 그 수치들이 과장으로 읽히기 때문입니다.

| **검색과 쓰기 경로를 아직 안 고쳤습니다** | 진단과 대안 비교까지 끝났고 착수 전입니다(6.9 · 6.10) | 검색은 FULLTEXT 검증, 쓰기는 두 원인의 몫부터 가르기 |

**기본값이 우연히 안전한 것이 아니라, 안전한 쪽이 기본값이 되도록 호출부를 배치한 것**이
이 설계의 요점입니다.

# 여기부터는 PDF 에 들어가지 않는다 (초안 메모)

## 구현이 끝나면 8장에 넣을 절 (2026-09-11~13 예정)

### 8.4 토글 API 를 멱등하게 (KI-54)

> 같은 요청을 두 번 보내면 상태가 뒤집히는 토글 API 를 멱등하게 재설계했습니다.
> 네트워크 재시도 한 번에 사용자가 의도하지 않은 상태가 되는 문제입니다.
> PUT/DELETE 로 의미를 나눠 "무엇을 원하는가"를 클라이언트가 말하게 했고,
> 수정 전에는 실패하고 수정 후에는 통과하는 재현 테스트를 먼저 만들었습니다.
> — 대안: 요청 식별자 기반 중복 제거(상태 저장 비용), 낙관적 버전(사용자 의도와 무관)

### 8.5 카운터 lost update (KI-53)

> 동시에 댓글이 달릴 때 댓글 수 카운터가 유실되는 lost update 를 **재현 테스트로 먼저
> 증명**하고 원자 증감으로 해결했습니다. 읽고-더하고-쓰는 방식은 두 트랜잭션이 같은 값을
> 읽으면 한쪽 증가가 사라집니다.
> — 대안 비교: 비관 락(경합 시 대기), 낙관 락(재시도 폭풍), 원자 UPDATE(선택)
> — 같은 코드의 다른 문제와 구분: 락 대기는 **느려지는 것**, lost update 는 **틀려지는 것**
