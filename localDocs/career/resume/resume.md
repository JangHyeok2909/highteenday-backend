## 소개

가설을 세우고 **그 가설이 틀렸는지 데이터로 판정**하는 방식으로 일합니다. 개인 프로젝트에서
지연의 원인을 잘못 짚어 닷새를 쓴 뒤, 측정을 믿어도 되는 조건을 코드로 정의했습니다 —
처치 없이 반복했을 때의 자연 편차를 먼저 재고 그보다 작은 차이는 개선이라 부르지 않는,
**A/B 테스트의 판정 원리와 같은 순서**입니다. 실사용자 지표를 올린 프로젝트는 아닙니다.
대신 사용자 행동을 모아 순위로 서빙하는 읽기 경로를 끝까지 만들었고, 그 위에서 성능을 고쳤습니다.

#### 사용자 행동을 모아 순위로 서빙하는 읽기 경로 (포트폴리오 2장)

- 명시적 신호(댓글·반응·스크랩)는 **트랜잭션 커밋 이후 이벤트**로 인기 점수에 반영해 롤백된
  행동이 순위에 남지 않게 하고, 암시적 신호(조회)는 Redis 에 모아 **1분 주기**로 반영.
  순위는 정렬 집합에 일자·5분 시간 버킷으로 유지
- 정렬 집합의 만료를 어댑터가 아니라 **호출자가 지정** — 버킷마다 수명이 달라, 어댑터가 키
  이름으로 수명을 추측하면 버킷을 추가할 때마다 어댑터를 고쳐야 하기 때문
- 조회수 반영은 **성공분만 정산하고 실패분은 버퍼에 남겨 재시도**. 삭제된 게시글은 재시도해도
  성공하지 않으므로 반복 실패를 따로 정리. 개인화·추천은 없고 규모는 게시판 단위

#### 측정이 두 번 거짓말했고, 그 조건을 코드로 걸러내게 만듦 (포트폴리오 3~5장)

- 부하 테스트의 p95(평균 10,685ms)를 애플리케이션 지연으로 판단해 호스트 자원까지 닷새간
  추적 → 실제 원인은 **도착률이 처리 용량을 넘긴 포화**(커넥션 획득 p95 6,364ms · 대기 145건 ·
  CPU 상한 상시 도달). 같은 코드를 포화 이하 운용점(도착률 초당 4요청)에서 재면 **278ms — 38배 차이는
  코드가 아니라 대기줄**. 지표는 처음부터 있었고, 없던 것은 그 조합을 **"해석 불가"로 선언하는 장치**
- 실행마다 포화 여부를 4단계로 자동 판정해 포화 구간의 지연값은 성능 근거로 인용 차단.
  포화를 실패가 아니라 **해석 조건**으로 둔 것은 한계 탐색 시나리오는 포화가 목적이기 때문
- 회귀 판정기가 부하 13배·데이터 100배인 실행을 대조군으로 골라 **"+59,000% 회귀"를 오보**.
  "직전 실행"과 "유효한 대조군"을 같은 것으로 취급한 것이 원인 — 비교를 무효로 만드는 조건과
  신뢰도만 낮추는 조건을 분리해 **유효한 대조군만 선택되도록 게이팅**
- 판정 문턱을 정하기 전에 **무처치 반복 5회의 자연 편차(변동계수)부터 재어 최소 검출 가능 효과
  약 16%를 산출**, 그 아래 차이는 개선으로 표기하지 않음. 처음 확정한 3.12%는 포화 상태 값임이
  드러나 **스스로 무효 처리하고 재산정** — 퍼센트는 9.6~15.8%로 나빠졌지만 절대 표준편차는
  369ms → 27~58ms 로 줄었음

#### 진단한 병목 제거 — 요청당 쿼리 1,507개 → 3.9개 (포트폴리오 6장)

- 서비스·컨트롤러 어디에도 쿼리처럼 보이는 코드가 없는데 요청당 1,507개. **엔드포인트별 요청당
  쿼리 수 계측을 먼저 붙여** 확인하고 그 값을 근거로 코드에서 원인 둘(댓글마다 반응 조회 ·
  작성자 지연 로딩)을 특정 — 코드는 무엇이 의심스러운지까지 알려주지만 그중 무엇이 실제로
  비싼지는 세어 봐야 알기 때문
- **한 번에 하나씩.** 반응 일괄 조회로 1,507 → 112개, p95 226.7 → 57.2ms. 재계측으로 남은
  112개 중 108개가 작성자 조회임을 확인해 2차 대상을 정함 → 패치 조인으로 112 → 3.9개,
  **p95 57.2 → 34.3ms(−40.1%, 검출 한계 16%를 넘어 노이즈로 설명되지 않음)**. 1차에 적어 둔
  예측(약 108개)과 2차 실측(108.3개) 일치
- 쿼리 수가 데이터 크기와 무관해짐(댓글 6개 글과 4,040개 글이 같은 4개). **패치 조인을 빼면
  실패하는 음성 대조 테스트**로 계약 고정, 응답 4,046건을 DB 와 전량 대조해 불일치 0 · 익명
  작성자 노출 0. 응답 크기는 여전히 댓글 수에 비례 — **댓글 페이징은 익명 번호 규칙과 얽힌
  별도 과제**(포트폴리오 7장)

#### 동시성 결함의 장애 전파 경로 차단 (포트폴리오 8장)

- 스크랩 토글의 체크-후-실행 경쟁 상태로 생긴 **중복 행 한 건이 게시글 상세 조회 전체를 실패**시킴.
  유니크 제약 + upsert 로 해소
- 분산 락이 아니라 유니크 제약을 고른 이유, 격리 수준을 올려도 막히지 않는 이유(같은 키의
  삽입 충돌)를 대안 비교로 기록

#### 일하는 방식 (포트폴리오 9장)

- 결함을 성격별 장부로 나눠 기록(**틀린 것 / 느린 것 / 잘못 재는 것**)하고 병목 → 실험 → 최적화
  기록을 사슬로 유지. 실험 없이 적용한 변경은 최적화 기록에 올리지 않고, **버린 대안과 그 이유**를 함께 적음
- 무엇을 문제로 볼지 · 기능 범위 · **검증 방법(단위·통합 테스트, 음성 대조, 응답 전량 대조)** 을
  먼저 정하고 구현과 문서화를 AI 에이전트에 위임. 구현안 다섯을 쿼리 수와 영향 범위로 비교해
  고른 것, 그 선택이 동작하는지 확인할 방법을 정한 것이 직접 한 판단

## 버린 문장 (다시 넣지 않기 위해 남긴다)

- "대규모 트래픽 환경에서 성능을 개선했습니다" — 규모가 없다. 우대사항에서 정면으로 진다.
- "성능 측정 시스템을 구축했습니다" — 도구를 만든 이야기로 읽힌다. 문제를 해결한 이야기여야 한다.
- "A/B 테스트를 설계했습니다" — 사실이 아니다. 통계 절차가 같다는 주장까지만 한다.
- **"1인 개발"** — **사실이 아니다.** 3명이 시작했고 저장소를 공개하면 기여자 목록이 보인다.
- "코드에는 단서가 없었다" — N+1 은 코드를 꼼꼼히 읽으면 찾을 수 있다. 대신
  **"코드는 무엇이 의심스러운지까지 알려주지만 그중 무엇이 실제로 비싼지는 알려주지 않는다"**.
- Go 이식 / 오픈소스화 — 하지 않았다. 물어보면 검토 기록으로만 답한다.
- 지표 165개 / PromQL 79개 — 도구 규모 자랑으로 읽힌다. 면접 꼬리질문 카드로만 남긴다.
