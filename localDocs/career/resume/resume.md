## 프로젝트

### HighTeenDay — 익명 커뮤니티 백엔드

2025.05 ~ 진행 중 · [github.com/JangHyeok2909/highteenday-backend](https://github.com/JangHyeok2909/highteenday-backend)

동아리에서 3명으로 시작해 **4개월 뒤부터 혼자 이어오고 있는 프로젝트**입니다.
전체 715 커밋 중 519건이 제 것이고, **아래 측정·개선 작업은 전부 단독 구간의 것**입니다.
사용자 행동을 모아 점수로 순위를 매겨 서빙하는 읽기 경로가 중심이고,
**계측이 어디를 볼지 알려주고 → 코드가 왜 그런지 알려주고 → 다시 계측이 그 설명을 검증하는**
순서로 일합니다. 코드는 무엇이 의심스러운지까지 알려주지만, 그중 무엇이 실제로 비싼지는
알려주지 않기 때문입니다. *상세 과정과 버린 대안은 별도 포트폴리오 문서에 있습니다.*

#### 지연의 원인을 오진했고, 그 오진을 막는 장치를 코드로 남김

- 부하 테스트의 p95 10,000~17,000ms 를 애플리케이션 지연으로 판단, 호스트 자원까지
  닷새간 추적 → 실제 원인은 **커넥션 풀 대기**. 도착률만 낮춰 재측정 시 **278ms, 38배 차이**
- 필요한 지표는 처음부터 수집 중이었음(커넥션 획득 p95 6,364ms · 대기 145건 ·
  CPU throttling 99.86%). 없던 것은 **그 조합을 "이 실험은 해석 불가"로 선언하는 장치**
- 실험마다 포화 여부를 4단계로 자동 판정, 포화 구간의 지연값은 성능 근거로 인용 차단.
  **포화를 실패가 아니라 해석 조건으로 정의** — 한계 탐색 시나리오는 포화가 목적이므로

#### 진단한 병목 제거 — 요청당 쿼리 1,507개 → 3.9개

- 쿼리가 서비스·컨트롤러 어디에도 보이지 않는 곳(DTO 변환)에서 발생.
  **엔드포인트별 요청당 쿼리 수 계측을 먼저 구축**해 1,507개 확인, 그 값을 근거로 코드에서
  원인 둘(반응 조회·작성자 조회) 특정
- **한 번에 하나씩 개선.** 반응 일괄 조회로 1,507 → 112개. **재계측으로 남은 112개 중
  108개가 작성자 조회임을 확인해 2차 대상 결정** → 패치 조인으로 **112 → 3.9개(−96.5%)**,
  종단 p95 226.7ms → **34.3ms**. 1차에 기록한 예측(약 108개 제거)과 2차 실측(108.3개) 일치
- **쿼리 수가 데이터 크기와 무관해짐** — 댓글 6개인 글과 4,040개인 글이 동일하게 4개 사용.
  **패치 조인 제거 시 실패하는 음성 대조 테스트**로 계약 고정, 응답 4,046건을 DB 와 전량
  대조해 불일치 0건 · 익명 댓글의 작성자 노출 0건 확인

#### 개선을 주장하기 전에 실험 판정 기준부터 수립

- 회귀 판정기가 **부하 13배·데이터 100배 실행을 대조군으로 선택해 "+59,000% 회귀" 오보.**
  원인은 "직전 실행"과 "대조군으로 유효한 실행"을 동일 취급한 것 — **시간축 질문과 실험
  설계 질문의 미분리**. 비교를 무효로 만드는 조건과 신뢰도만 낮추는 조건을 분리해
  **유효 대조군만 선택되도록 게이팅**
- 판정 문턱 설정 전 **무처치 반복 실험의 자연 편차(변동계수)부터 측정**해 최소 검출 가능
  효과 산출. 위 개선폭 40.1% 는 5회 반복 실험의 검출 한계 약 16% 의 2.5배.
  **이 조건을 통과하기 전에는 "개선"으로 표기하지 않음**
- 초기 확정치가 **포화 상태 측정값으로 판명되어 자체 무효 처리 후 재산정.**
  퍼센트는 악화(3.12% → 9.6~15.8%)했으나 절대 표준편차는 369ms → 27~58ms 로 감소

#### 사용자 행동을 모아 순위로 서빙하는 읽기 경로 구축

- 명시적 신호(댓글·반응·스크랩)는 **트랜잭션 커밋 이후 이벤트**로 인기 점수에 반영,
  암시적 신호(조회수)는 Redis 버퍼링 후 **1분 주기 반영**. 순위는 정렬 집합에
  **일자·5분 단위 시간 버킷**으로 유지하고 5분 주기 재계산
- 정렬 집합의 **만료를 어댑터가 아닌 호출자가 지정**하도록 설계 — 버킷마다 수명이 다르므로
  어댑터가 키 이름으로 수명을 추측하면 **버킷 추가 시마다 어댑터를 수정해야 하기 때문**
- 조회수 반영은 **성공분만 정산하고 실패분은 버퍼에 잔류시켜 재시도**. 삭제된 게시글은
  재시도해도 성공하지 않으므로 **매 주기 반복 실패 방지 처리**

#### 동시성 결함의 장애 전파 경로 차단

- 스크랩 토글의 **체크-후-실행 경쟁 상태**로 생성된 중복 행 한 건이 게시글 상세 조회 전체를
  실패시킴. 유니크 제약 + upsert 로 해소
- 분산 락이 아닌 유니크 제약을 선택한 이유, 격리 수준 상향으로는 차단되지 않는 이유를
  대안 비교로 기록

#### 일하는 방식

- 결함을 성격별 장부로 분리 운영(**틀린 것 / 느린 것 / 잘못 재는 것**),
  **병목 → 실험 → 최적화 기록 체인** 유지. 실험 없이 적용한 변경은 최적화 기록에서 제외,
  문서에는 **버린 대안과 그 이유**를 함께 기록
- **기능 범위와 검증 방법(단위·통합 테스트, 음성 대조, 응답 전량 대조)을 직접 설계하고
  구현·문서화를 AI 에이전트에 위임.** 구현안 다섯 가지를 쿼리 수와 영향 범위로 비교해
  선택한 것, 그 선택이 실제로 동작하는지 검증할 방법을 정한 것이 직접 한 판단
- **실험은 한 번에 변수 하나만 변경.** 테스트 725개 통과, 스키마는 Flyway 로만 변경

## 버린 문장 (다시 넣지 않기 위해 남긴다)

- "대규모 트래픽 환경에서 성능을 개선했습니다" — 규모가 없다. 우대사항에서 정면으로 진다.
- "성능 측정 시스템을 구축했습니다" — 도구를 만든 이야기로 읽힌다. 문제를 해결한 이야기여야 한다.
- "A/B 테스트를 설계했습니다" — 사실이 아니다. 통계 절차가 같다는 주장까지만 한다.
- **"1인 개발"** — **사실이 아니다.** 3명이 시작했고 저장소를 공개하면 기여자 목록이 보인다.
- "코드에는 단서가 없었다" — N+1 은 코드를 꼼꼼히 읽으면 찾을 수 있다. 대신
  **"코드는 무엇이 의심스러운지까지 알려주지만 그중 무엇이 실제로 비싼지는 알려주지 않는다"**.
- Go 이식 / 오픈소스화 — 하지 않았다. 물어보면 검토 기록으로만 답한다.
- 지표 165개 / PromQL 79개 — 도구 규모 자랑으로 읽힌다. 면접 꼬리질문 카드로만 남긴다.
