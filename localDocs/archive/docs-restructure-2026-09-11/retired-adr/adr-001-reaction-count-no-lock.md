# ADR-001. 좋아요/싫어요 카운트에 락을 걸지 않는다

상태: 소급 채록 (결정 당시 기록이 아니라 README·코드에서 재구성) — 마지막 검증일: 2026-09-07

## 배경

게시글 목록 조회 성능을 위해 좋아요/싫어요 수를 `Post`의 비정규화 컬럼(`PST_like_count`, `PST_dislike_count`)으로 관리한다 (`domain/posts/Post.java`). 여러 트랜잭션이 동시에 같은 게시글에 반응하면 같은 row를 읽고 갱신하는 과정에서 lost update가 발생해, 실제 반응 데이터와 카운트가 어긋나는 문제가 있었다 (README 트러블슈팅: "100명의 유저가 동시에 좋아요/싫어요 요청" 시 drift 발생).

## 검토한 대안

README 트러블슈팅 표가 보고하는 비교 결과다. 당시 k6 스크립트가 남아 있지 않아 현재 재현 가능한 근거로 사용하지 않는다.

| 방식 | 정합성 | 실패율 | 처리량 | p95 |
|---|---|---|---|---|
| 락 없음 | 불일치 발생 | 1.68% | 205/s | 579ms |
| 낙관적 락 | 유지 | 79% (충돌 시 실패) | 81/s | 1.3s |
| 비관적 락 | 유지 | 0% | 68/s | 951ms |

- 낙관적 락: 정합성은 지키지만 인기 게시글처럼 충돌이 잦은 워크로드에서 실패율이 급증해 재시도 로직이 필수.
- 비관적 락: 정합성 완벽하나 처리량이 1/3로 감소하고 응답 지연 증가.

## 결정

락을 적용하지 않는다 (성능 우선). 좋아요/싫어요는 강한 정합성이 필수인 데이터가 아니고 일부 오차가 허용되므로, 동기화로 정합성을 보완한다 (README "최종 선택").

## 결과·트레이드오프

- 현재 코드는 반응이 일어날 때마다 `syncCounts()`가 DB `COUNT` 쿼리로 재계산한 값을 컬럼에 덮어쓴다. 증분 방식이 아니므로 드리프트는 다음 반응에서 다시 계산될 수 있지만 마지막 반응 이후에는 남을 수 있다.
- 트레이드오프: 반응마다 COUNT 쿼리 2회가 추가되고 `posts` 행 UPDATE가 인기 게시글에 집중된다. 이 영향은 [Case 후보 목록](../../performance/cases/#아직-case가-아닌-후보)에서 추적한다.
- 행 생성은 `INSERT ... ON DUPLICATE KEY UPDATE`를 사용하고 유니크 제약으로 중복을 막는다. 댓글 수 카운터는 별도의 원자 UPDATE를 사용한다.
- `Post`·`PostReaction` 어디에도 `@Version`(낙관적 락)이나 `@Lock`(비관적 락)이 없다.
