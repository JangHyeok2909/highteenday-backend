# BTL-005: 댓글 목록 N+1 쿼리

> 유형: N+1 / JPA / Query
> 상태: **해소** (2026-09-04)
> 관련: EXP-005

> **해소 기록.** 이 병목은 두 갈래였고 각각 따로 측정해서 없앴다.
> **① 반응 확인 2N — [OPT-001](../optimizations/OPT-001-comment-reaction-batch.md).**
> 댓글마다 좋아요·싫어요를 각각 묻던 것을 댓글 id 전체를 넘기는 일괄 조회 1회로 바꿨다.
> 요청당 쿼리 1,507 → 112, 전체 p95 226.7ms → 57.2ms.
> **② 작성자 지연 로딩 U — [OPT-002](../optimizations/OPT-002-comment-author-fetch-join.md).**
> `CommentRepository.findByPost` 에 `join fetch c.user` 를 넣었다.
> 요청당 쿼리 112 → 3.9, 전체 p95 57.2ms → 34.3ms.
>
> **위 "해결 방법" 표에서 전역 `default_batch_fetch_size` 를 버린 이유**는 쿼리가
> 1+N/100 으로 남아 상수가 되지 않고, 애플리케이션 전체의 지연 로딩 동작이 같이 바뀌어
> 변수 하나 원칙을 지킬 수 없기 때문이다. DTO 프로젝션은 컨트롤러·익명화 서비스·반응
> 조회가 모두 엔티티를 받아야 동작해서 변경 규모가 문제 크기를 넘는다 — 별도 과제로 남겼다.
> 자세한 대안 비교는 OPT-002 §2-3 에 있다.
>
> **검증:** 부하 없는 단발 요청에서 댓글 6개·492개·4,040개짜리 게시글이 전부 쿼리 4개를
> 썼다(OPT-002 §4). 요청당 쿼리 수가 데이터 크기와 무관해졌다는 뜻이다.
> 부하 5회 세트에서 Before·After 의 p95 범위가 겹치지 않는다(OPT-002 §5-1).

## 증상

댓글이 많은 인기글일수록 `GET /api/posts/{id}/comments`가 선형으로 느려지고,
동일 RPS에서 DB `questions/s`(총 쿼리량)가 비정상적으로 높다.

## 원인

전 엔티티 `FetchType.LAZY` 원칙(CLAUDE.md) 하에서 댓글 목록 → DTO 변환 시
`comment.getUser()`, `comment.getParent()` 등 연관 접근이 댓글마다
개별 SELECT로 풀리는 패턴. 목록 경로에 `JOIN FETCH`가 적용됐는지 미검증.
익명 댓글 분기(`isAnonymous`)로 User 접근이 조건부라 테스트에서 안 드러났을 가능성.

## 영향

- 인기글(=댓글 많은 글)일수록 악화 — Zipf 접근과 정확히 역상관인 최악 조합
- 마이페이지 내 댓글, 채팅방 목록(방별 집계) 등 유사 패턴 경로에 동반 의심

## 재현 방법

```bash
# 부하 없이 확정 가능: 댓글 5개 글 vs 100개 글 각 1회 호출, p6spy 로그 쿼리 수 비교
curl -s "localhost:18080/api/posts/<id>/comments" > /dev/null
# 쿼리 수가 댓글 수에 비례하면 확정
```

관찰 지표: 요청당 쿼리 수(p6spy), `comment_list` P95,
`rate(mysql_global_status_questions[1m])` / k6 RPS 비율.

## 개선 전 선행 조건

공통 조건 넷은 [`README.md`의 "개선 전 공통 선행 조건"](README.md#개선-전-공통-선행-조건)에 있다.
이 병목에만 걸리는 것은 아래 넷이다.

### ① 부하 테스트보다 코드 레벨 확정이 먼저다

이 병목의 1차 근거는 **요청당 쿼리 수**이고, 그 값은 Prometheus가 아니라 p6spy 앱 로그에서
나온다. 위 "재현 방법"대로 댓글 5개 글과 100개 글을 각각 한 번 호출하면 부하 없이 확정된다.

**부하를 걸어 p95를 재는 것은 그다음이다.** 순서를 뒤집으면 p95가 왜 나빠졌는지 후보가
여러 개 남는다 — N+1인지, 캐시 미스인지, 풀 대기인지 가릴 근거가 없다.

### ② 2026-08-18 이전 실행을 Before로 쓰지 말 것 (S-26)

자동 병목 힌트가 `mysql.qps / rps > 10`을 N+1 신호로 쓴다. 그 분모인 **구간별 RPS가 전체
실행 시간을 분모로 쓰던 오류**가 2026-08-18에 수정됐다(S-26).

그 이전 실행의 RPS는 과소평가돼 있고, 따라서 qps/rps 비율은 **과대평가**돼 있다.
수정 이전 실행을 Before로 삼으면 개선 후 비율이 내려간 것이 N+1 해소인지 분모 수정인지
구분할 수 없다. **Before를 수정 이후 코드로 다시 잰다.**

### ③ 댓글 없는 글이 섞이면 효과가 희석된다 (S-16)

N+1 비용은 댓글 수에 비례하는데, 지금은 `200 []`도 성공으로 집계된다. 댓글이 0건인 글을
조회한 요청은 **빠른 응답**으로 기록되어 p95를 끌어내린다.

개선 전후를 비교하려면 **대상 글의 댓글 수를 고정**해야 한다. 인기글을 겨냥하는 것만으로는
부족하다 — 어느 글이 뽑혔는지에 따라 매번 달라지기 때문이다.

### ④ 대상 글의 댓글 수는 `COUNT(*)`로 확인할 것

`PST_comment_count`(비정규화 카운터)를 그대로 믿지 않는다. 2026-08-13 large DB에서
활성 댓글 399,956건 대비 카운터 합이 386,672건으로 **13,284건 부족**했고, 게시물 70개가
어긋나 있었다(E-45). 인기 게시물 ID 3에서는 차이가 11,096건이었다.

2026-08-16 재생성 후 `verify.sh`의 카운터 항목은 불일치 0건으로 통과했으므로 지금은 해소된
것으로 보이지만, **E-45의 상태가 아직 `미해결`로 남아 있다.** 개선 대상 글을 고를 때
`SELECT COUNT(*) FROM comments WHERE PST_id = ? AND is_valid = 1`로 직접 세고 그 값을
실험 문서에 기록한다.

### 선택 — 유사 패턴 경로

마이페이지 내 댓글, 채팅방 목록(방별 집계)에 같은 패턴이 의심된다. **한 번에 하나만 고친다** —
두 경로를 같이 바꾸면 어느 쪽 효과인지 알 수 없다.

## 해결 방법

| 후보 | 효과 | 트레이드오프 |
|------|------|--------------|
| repository에 `JOIN FETCH` | 해당 경로 1쿼리화 | 페이징과 fetch join 충돌 주의 (컬렉션 fetch 시) |
| `default_batch_fetch_size=100` 전역 설정 | 전 경로 IN 배치화 — 최소 수정 최대 효과 | 쿼리가 1+N/100으로 남음 (완전 제거는 아님) |
| QueryDSL DTO 프로젝션 | 필요한 컬럼만, 엔티티 로드 자체 제거 | 코드량 증가 |
