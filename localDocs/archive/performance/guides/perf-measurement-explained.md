# 이 성능 시스템은 무엇을 측정하고 있는가 — 처음부터 끝까지

작성일: 2026-08-20
대상: `performance/` 디렉터리 전체 (k6 스크립트 · Prometheus 카탈로그 · 수집기 · 판정 엔진)

---

## 0. 이 문서를 읽는 법

### 목적

이 문서의 목적은 단 하나, **읽는 사람이 이 측정 시스템을 완전히 이해하는 것**이다.
설득하거나 요약하려 하지 않는다. 코드를 열지 않고도 "무엇을 왜 재고 있는지"를 끝까지
따라갈 수 있도록 쓴다.

### 박스 규칙

전문 용어나 배경 개념은 **그 말이 처음 나오기 전에** 아래와 같은 박스로 먼저 설명한다.
박스를 건너뛰지 않고 순서대로 읽으면 사전 지식 없이 끝까지 읽힌다.

> **📘 개념 — 박스**
>
> 이렇게 생긴 것이 개념 박스다. 여기 나온 설명은 이후 본문에서 그 용어를 아무 부연 없이
> 쓴다는 뜻이다.

### 전제 지식

Java와 Spring을 다뤄 봤고, 데이터베이스에 쿼리를 날리면 시간이 걸린다는 정도만 알면 된다.
성능 테스트, 모니터링, 통계 용어는 전부 이 문서 안에서 설명한다.

### 문서에서 쓰는 표기

- `파일경로:줄번호` — 실제 코드 위치. 확인하고 싶을 때 그 줄을 열면 된다.
- **사실** / *추론* / 권고 — 마지막 장에서는 이 셋을 구분해서 적는다.

## 1. 한눈에 보기 — 측정은 네 단계로 이뤄진다

이 시스템은 "부하를 걸고 결과를 본다"가 아니라, 네 개의 분리된 단계로 되어 있다.
각 단계는 앞 단계가 죽어도 결과를 잃지 않도록 파일로 끊어져 있다.

```text
 ┌─────────────────────────────────────────────────────────────────┐
 │ 1단계  부하 발생 + 클라이언트 관점 측정            도구: k6      │
 │        "사용자 입장에서 얼마나 걸렸는가"                        │
 │        결과물: reports/runs/<runId>.k6.json                     │
 └───────────────────────────┬─────────────────────────────────────┘
                             │ (파일로 끊김 — k6가 죽어도 원본은 남음)
 ┌───────────────────────────▼─────────────────────────────────────┐
 │ 2단계  서버 관점 측정                     도구: Prometheus      │
 │        "그동안 서버 안에서는 무슨 일이 있었는가"                │
 │        157개 지표를 같은 시간 구간으로 조회                     │
 └───────────────────────────┬─────────────────────────────────────┘
                             │
 ┌───────────────────────────▼─────────────────────────────────────┐
 │ 3단계  판정                        도구: tools/lib/regression   │
 │        "이전보다 나빠졌는가 / 기준을 넘겼는가 / 믿을 수 있는가" │
 └───────────────────────────┬─────────────────────────────────────┘
                             │
 ┌───────────────────────────▼─────────────────────────────────────┐
 │ 4단계  저장 + 보고                                              │
 │        reports/runs/<runId>/run.json + report.html              │
 └─────────────────────────────────────────────────────────────────┘
```

**핵심 설계 사상 하나만 먼저 기억하면 된다.** 이 시스템은 "숫자를 만드는 것"보다
**"그 숫자를 믿어도 되는지 판단하는 것"에 훨씬 많은 코드를 쓴다.** 뒤에 나오는 비교
가능성·포화 판정·측정 상태가 전부 그 목적이고, 실제로 지표 정의보다 그쪽 코드가 더 길다.

## 2. 준비 개념 — 부하 테스트는 정확히 무엇을 하는가

> **📘 개념 — 부하 테스트(load test)와 부하 발생기(load generator)**
>
> 부하 테스트는 **실제 사용자가 몰린 상황을 인위적으로 만들어** 서버가 어떻게 반응하는지
> 보는 실험이다. 이때 가짜 사용자를 만들어 요청을 쏘는 프로그램을 부하 발생기라고 한다.
>
> 이 프로젝트가 쓰는 부하 발생기는 **k6**다. JavaScript로 시나리오를 쓰면 그걸 수천 개의
> 가상 사용자로 동시에 실행해 준다.

> **📘 개념 — VU(Virtual User, 가상 사용자)와 iteration(반복)**
>
> **VU**는 가짜 사용자 한 명이다. VU 20개로 테스트하면 20명이 동시에 앱을 쓰는 상황이 된다.
>
> **iteration**은 그 사용자가 하는 **한 바퀴의 행동**이다. 예를 들어 "게시판 목록을 보고 →
> 글 하나를 열고 → 댓글을 읽고 → 좋아요를 누른다"가 1 iteration이다. VU는 iteration을
> 계속 반복한다.
>
> 그래서 두 가지 처리량 지표가 생긴다.
> - **RPS** (Requests Per Second) = 초당 HTTP 요청 수. 서버가 처리한 낱개 요청.
> - **TPS** (Transactions Per Second) = 초당 완료된 iteration 수. **사용자 여정 완주 횟수.**
>
> 이 시스템은 둘을 따로 저장한다(`performance/scripts/lib/summary.js:242-246`). 용량 산정은
> 보통 TPS로 한다 — "몇 명이 서비스를 쓸 수 있는가"에 답하는 값이기 때문이다.

> **📘 개념 — think time(생각 시간)**
>
> 실제 사람은 페이지를 열자마자 다음 버튼을 누르지 않는다. 읽는 시간이 있다. 그 멈춤을
> 흉내 내는 것이 think time이다. 이게 없으면 VU 한 명이 사람 수십 명분 부하를 만들어
> 비현실적인 결과가 나온다.
>
> 이 프로젝트는 **1~4초 사이 균등분포**로 잡았다(`performance/scripts/lib/config.js:41-44`,
> 환경변수 `THINK_MIN`/`THINK_MAX`로 조절).

### 2.1 부하를 거는 두 가지 방식 — 이 구분이 결과를 완전히 바꾼다

> **📘 개념 — closed model과 open model**
>
> **closed model(닫힌 모델)**: VU 수를 고정한다. VU는 이전 요청의 **응답을 받아야** 다음
> 요청을 보낸다. k6의 `ramping-vus` executor가 이 방식이다.
>
> **open model(열린 모델)**: **도착률**(초당 몇 건의 요청이 새로 도착하는가)을 고정한다.
> 앞의 요청이 끝났든 말든 정해진 속도로 새 요청이 들어온다. k6의 `ramping-arrival-rate`가
> 이 방식이다.
>
> 실제 웹 서비스는 open model에 가깝다. 서버가 느려진다고 사용자가 접속을 자제하지 않는다.

> **📘 개념 — coordinated omission(조율된 누락)**
>
> closed model의 치명적 함정이다. **서버가 느려지면 부하 발생기가 스스로 요청을 줄인다.**
> VU가 응답을 기다리느라 다음 요청을 못 보내기 때문이다.
>
> 결과가 두 가지로 왜곡된다.
> 1. "같은 부하에서 처리량이 25% 줄었다"고 말할 수 없다. **부하 자체가 달랐다.**
> 2. 가장 느린 요청들이 통계에서 빠진다. 서버가 막힌 동안 요청이 아예 발생하지 않으므로,
>    최악의 구간이 측정되지 않고 그냥 사라진다.

> **📘 개념 — 리틀의 법칙(Little's Law)**
>
> 대기 행렬 이론의 기본 공식이다.
>
> ```
> 시스템 안에 동시에 머무는 요청 수(N) = 도착률(λ) × 요청 1건의 체류 시간(R)
> ```
>
> 이걸 뒤집으면 `R = N / X` (X는 처리량)가 된다. **closed model에서 VU가 고정이면 N이
> 고정이므로, 응답 시간 R은 처리량 X의 그림자로 기계적으로 결정된다.** 코드가 좋아지거나
> 나빠져서가 아니라, 산수 때문에 그렇게 나온다.

**이 프로젝트에서 실측된 사례**(`performance/scripts/lib/phases.js:96-107` 주석):
VU를 200으로 고정한 실행에서 `200 ÷ 처리율`과 실제 p95의 상관계수가 **0.962**였다.
즉 p95가 성능 지표가 아니라 처리량의 재표현이었다. 호스트의 작은 변동이 p95의 큰 차이로
증폭된 것도 이 구조 탓이다.

그래서 이 시스템은 **open model로 옮겨 가는 중**이다. 도착률을 고정하면 시스템이 못
따라올 때 부하가 줄어드는 대신 `dropped_iterations`(보내지 못한 요청 수)로 드러난다.
숨지 않고 신호가 된다.

### 2.2 부하의 내용 — 어떤 요청을 어떤 비율로 보내는가

> **📘 개념 — Zipf 분포와 멱법칙(power law)**
>
> 현실의 인기는 고르게 퍼지지 않는다. 게시글 1,000개가 있으면 조회수 대부분이 상위 몇 개에
> 몰린다. 이 쏠림을 수학적으로 표현한 것이 Zipf 분포다.
>
> ```
> 순위 r인 항목이 선택될 확률 ∝ 1 / r^s
> ```
>
> `s`(지수)가 클수록 상위 집중이 심해진다. `s=1.07`이면 1등이 2등보다 약간 더 인기 있고,
> `s=1.7`이면 1등이 전체의 38%를 독식한다.
>
> **왜 중요한가**: 쏠림 정도가 캐시 적중률과 DB 버퍼풀 적중률을 직접 결정한다. 균등하게
> 요청하면 캐시가 아무 소용이 없고, 너무 쏠리면 모든 게 캐시에 들어가 DB를 안 건드린다.
> 둘 다 현실과 다른 결과가 나온다.

이 시스템은 **세 가지 쏠림 축**을 따로 선언한다
(`performance/scripts/lib/sampling.js`).

| 축 | 상수 | 값 | 무엇을 결정하는가 | 근거 |
|---|---|---|---|---|
| 글 인기도 | `HOT_SKEW` | 1.07 | 어느 **글**에 조회·댓글·반응이 몰리는가 | 데이터셋 크기와 무관하게 고정 (비교 실험의 전제) |
| 작성 활동량 | `AUTHOR_SKEW` | 1.3 | 어느 **사람**이 많이 쓰는가 | 옛 DB 실제 분포와의 연속성 — **잠정값** |
| 목록 페이지 | `PAGE_WEIGHTS` | `[0.55, 0.20, 0.12, 0.08, 0.05]` | 1~5페이지 요청 비율 | **실측 아님. 업계 통념에 기댄 가정** |

세 번째 줄의 "실측 아님"은 내가 붙인 평가가 아니라 코드 주석에 그대로 적혀 있는 말이다
(`performance/scripts/lib/sampling.js:100-110`). 운영 액세스 로그가 쌓이면 교체할 대상으로
표시되어 있다.

## 3. 1단계 — k6가 재는 것 (클라이언트 관점)

여기서 나오는 값은 전부 **"부하 발생기가 밖에서 본 것"**이다. 서버 안 사정은 모른다.

### 3.1 응답 시간을 다섯 조각으로 나눈다

> **📘 개념 — HTTP 요청의 시간 구성**
>
> "응답 시간 200ms"는 한 덩어리가 아니다. k6는 이걸 다섯 구간으로 쪼갠다.
>
> | 구간 | k6 지표 | 무슨 시간인가 |
> |---|---|---|
> | blocked | `http_req_blocked` | 커넥션을 얻으려고 **대기한** 시간 (커넥션 풀이 꽉 참) |
> | connecting | `http_req_connecting` | TCP 연결을 맺는 시간 |
> | sending | `http_req_sending` | 요청을 밀어 넣는 시간 |
> | **waiting** | `http_req_waiting` | **요청을 다 보내고 첫 응답 바이트가 올 때까지** — 서버가 실제로 일한 시간 |
> | receiving | `http_req_receiving` | 응답 본문을 다 받는 시간 |
>
> **`waiting`이 서버 성능에 가장 가깝다.** 전체(`http_req_duration`)가 느린데 `waiting`이
> 정상이면 병목은 서버가 아니라 네트워크나 부하 발생기 쪽이다.

이 시스템은 `waiting`의 평균과 p95를 따로 저장한다
(`performance/scripts/lib/summary.js:270-273`). 실제로 이 구분이 결정적이었던 사례가 있다 —
k6를 Windows 네이티브로 돌렸을 때 전체 평균 200ms 중 **서버 측은 21ms, 경로 오버헤드가
179ms**였다(`performance/tools/lib/conditions.js`의 loadgen 조건 주석).

### 3.2 평균이 아니라 분포로 본다

> **📘 개념 — 백분위수(percentile), p95 / p99**
>
> 요청 1,000건을 응답 시간 순으로 줄 세웠을 때,
> - **p95** = 아래에서 950번째 값. "95%의 요청이 이 값보다 빨랐다"
> - **p99** = 990번째 값. "1%의 요청은 이보다 느렸다"
>
> **왜 평균을 쓰면 안 되는가**: 요청 99건이 10ms, 1건이 10초여도 평균은 약 110ms다.
> 평균만 보면 "빠르다"가 되지만, 실제로는 100명 중 1명이 10초를 기다린 것이다.
> 사용자 100명이 하루에 100번 요청하면, 그 1%는 거의 모두가 하루에 한 번씩 겪는다.
>
> **p99가 특히 중요한 이유**: 한 화면이 API 10개를 부르면, 그 화면이 느릴 확률은
> 1%가 아니라 약 10%다. 꼬리(tail)는 곱해진다.

이 저장소는 **판정에 평균 사용을 금지**한다(`performance/README.md` 7절). 저장은 하되
게이트는 p95/p99로 건다.

> **📘 개념 — 측정되지 않은 값을 0으로 채우면 안 되는 이유**
>
> k6는 옵션에 따라 p99를 아예 계산하지 않는다. 이때 코드에서 `?? 0`으로 메우면
> **"P99 = 0ms"라는 거짓 데이터**가 만들어지고, 그게 그대로 회귀 판정을 통과한다.
>
> 이 시스템은 없는 값을 `null`로 남기고, 어떤 분위수가 빠졌는지를
> `missingPercentiles` 배열에 따로 기록한다
> (`performance/scripts/lib/phases.js:159-178`, `summary.js:246`).
> **"0"과 "못 쟀음"은 다른 사실**이라는 원칙이 코드 전반에 일관되게 적용돼 있다.

### 3.3 구간을 나눈다 — warmup / measure / rampdown

> **📘 개념 — JIT 워밍업(warm-up)**
>
> Java는 처음에 바이트코드를 한 줄씩 해석(interpret)하며 실행한다. 같은 코드가 여러 번
> 반복되면 그때서야 JIT 컴파일러가 기계어로 번역해 훨씬 빠르게 만든다.
>
> 그래서 **JVM 애플리케이션은 시작 직후가 정상 상태보다 몇 배 느리다.** 커넥션 풀도 아직
> 안 채워졌고, 캐시도 비어 있고, DB 버퍼풀도 차갑다.
>
> 이 구간을 성능 측정에 포함시키면 **개선 여부와 무관하게 결과가 나빠진다.**

그래서 이 시스템은 실행을 세 구간으로 선언한다(`performance/scripts/lib/phases.js`).

| 구간 | 역할 | 판정에 쓰는가 |
|---|---|---|
| **warmup** | JIT·커넥션 풀·캐시가 정상 상태에 도달할 때까지 | ❌ 제외 |
| **measure** | 실제 판정 대상 | ✅ **여기만** |
| **rampdown** | 부하를 줄이며 마무리 | ❌ 제외 |

중요한 점 두 가지.

**첫째, warmup은 사후에 잘라내는 게 아니라 실행 계획 자체다.** `--warmup 300`을 주면 k6의
ramp-up 단계가 300초짜리로 만들어지고, 그 값이 `phasePlan`이라는 객체로 결과 파일에 기록된다
(`performance/scripts/lib/summary.js:105`). 2단계 수집기는 CLI 인자를 다시 받지 않고 **이
기록만 읽어** Prometheus 조회 구간을 계산한다(`performance/tools/collect.js:80-120`).
그래서 나중에 재수집해도 **같은 창이 정확히 재현된다.**

**둘째, 구간마다 값이 따로 저장된다.** `measure`만 남기고 버리는 게 아니라 warmup과
rampdown 통계도 진단용으로 보관한다.

> **⚠️ 이 시스템이 실제로 밟은 지뢰 — k6의 `rate`를 쓰면 안 된다**
>
> k6는 카운터의 `rate`(초당 값)를 계산할 때 **언제나 전체 테스트 시간으로 나눈다.**
> `phase:measure` 태그가 붙은 값이어도 그렇다. 그래서
> `http_reqs{phase:measure}.rate`는 "measure 구간의 요청 수 ÷ **전체** 실행 시간"이라는,
> 분자와 분모의 구간이 어긋난 값이 된다.
>
> 실측(measure 1,200초 / 전체 1,649초, 요청 29,650건):
> - k6의 rate: **17.98** (29,650 ÷ 1,649) ← 틀림
> - 직접 계산: **24.71** (29,650 ÷ 1,200) ← 맞음
>
> 워밍업이 길수록 오차가 커진다. 이 코드는 직접 나눈다
> (`performance/scripts/lib/phases.js:283`).

### 3.4 태그로 쪼갠다 — "어느 기능이 느렸는가"

> **📘 개념 — 태그(tag)와 서브메트릭(sub-metric)**
>
> **태그**는 요청에 붙이는 라벨이다. "이건 게시글 기능", "이건 읽기 작업" 같은 표시다.
> 태그가 붙으면 나중에 그 축으로 결과를 쪼개 볼 수 있다.
>
> **k6의 특이한 제약**: k6는 태그를 붙였다고 자동으로 쪼개 주지 않는다.
> **threshold(임계값)에 그 태그 조합을 명시적으로 선언한 경우에만** 서브메트릭
> (`http_req_duration{feature:post}` 같은 것)을 만들어 준다.

그래서 이 시스템은 **판정에 영향을 주지 않는 아주 느슨한 임계값**을 일부러 걸어 둔다.
`p(99)<600000`(10분)처럼 절대 실패할 수 없는 값이다. 목적은 통과/실패가 아니라
**집계 축을 만들어 내는 것**이다(`performance/scripts/lib/thresholds.js:22-38`).

현재 선언된 분해 축은 다음과 같다.

| 축 | 값 | 답하는 질문 |
|---|---|---|
| `feature` | auth, post, comment, board, reaction, scrap, notification, friend, mypage, school, timetable, chat, hot (13개) | 어느 **기능**이 느렸는가 |
| `op` | read, write, auth | 읽기가 느렸나 쓰기가 느렸나 |
| `page` | 0, 1, 2, 3, 4 | 목록 **몇 페이지**를 요청했는가 |
| `phase` | warmup, measure, rampdown | 어느 **구간**이었는가 |

> **⚠️ 여기서도 실제 사고가 있었다 — 지연과 요청 수는 다른 메트릭에서 온다**
>
> 처음에는 `http_req_duration`(지연)만 축으로 선언했다. 그랬더니 페이지별 지연은 다
> 나오는데 **요청 수 칸이 전부 비었다.** 그래서 정작 검증하려던 "선언한 페이지 비율대로
> 실제 요청이 갔는가"에 답할 수 없었다. 실제로 0페이지가 한 번도 요청되지 않던 버그(S-03)를
> 리포트만 봐서는 알 방법이 없었다.
>
> 요청 수는 `http_reqs`라는 **별도 메트릭**이라 그 축도 따로 선언해야 한다
> (`performance/scripts/lib/thresholds.js:53-66`).

> **📘 개념 — 카디널리티(cardinality) 폭발**
>
> 태그 값의 **가짓수**를 카디널리티라고 한다. 태그를 붙이면 값 조합마다 별도의 시계열이
> 생기므로, 가짓수가 많은 축(게시글 ID 등)을 태그로 쓰면 메모리가 터진다.
>
> 게시글이 10만 개인데 `postId`를 태그로 붙이면 시계열이 10만 개 생긴다. 그래서 태그는
> **값이 많아야 수십 개인 축에만** 쓴다(`performance/scripts/lib/config.js:85-89`).

### 3.5 기준을 건다 — threshold와 SLO

> **📘 개념 — SLO(Service Level Objective, 서비스 수준 목표)**
>
> "이 정도는 지키겠다"고 스스로 정한 성능 약속이다. 예: "읽기 요청의 95%는 300ms 안에
> 응답한다." 지키면 통과, 넘으면 실패다.
>
> SLO가 없으면 "빠르다/느리다"가 주관이 되고, 성능 작업이 언제 끝나는지 알 수 없다.

이 프로젝트의 SLO(`performance/scripts/lib/thresholds.js:110-115`):

```javascript
http_req_failed:                ['rate<0.01']              // 오류율 1% 미만
'http_req_duration{op:read}':   ['p(95)<300', 'p(99)<800']  // 읽기
'http_req_duration{op:write}':  ['p(95)<500', 'p(99)<1200'] // 쓰기
checks:                         ['rate>0.99']              // 응답 내용 검증 성공률
```

근거는 Google RAIL 모델(사용자가 1초 이내 응답을 "즉각적"으로 느낀다)이다.

**SLO는 measure 구간에만 적용된다.** 전체 구간에도 같이 걸면 warmup의 JIT 컴파일·커넥션 풀
확장·캐시 미스로 생긴 느린 응답이 실행 전체를 실패시킨다. 그걸 빼려고 warmup을 선언한
것이므로 이중 적용은 선언 자체를 무의미하게 만든다(`thresholds.js:180-192`).

### 3.6 1단계가 실제로 남기는 것

한 번의 실행이 끝나면 `reports/runs/<runId>.k6.json`에 이런 구조가 남는다.

```text
run:                실행 메타데이터
  ├ scenario        어떤 시나리오였나 (normal-day 등)
  ├ commit/branch   어떤 코드였나
  ├ dataset         어떤 데이터였나 (+ 지문)
  ├ loadProfile     어떤 부하를 걸기로 선언했나 (executor, stages)
  └ phasePlan       warmup/measure/rampdown 길이

k6:
  ├ all             전체 구간 요약 (참고용 — 판정에 안 씀)
  ├ phases          warmup / measure / rampdown 각각의 요약  ← 판정은 여기
  │   └ measure     avg/min/med/max/p90/p95/p99, rps, tps,
  │                 errorRate, httpReqs, iterations, checkRate
  ├ breakdown       feature/op/page 축별 분해
  ├ thresholds      각 임계값의 통과 여부
  ├ checks          응답 내용 검증 결과 (이름별 통과/실패 수)
  └ rawMetrics      k6 원본 전체 (나중에 새 지표가 필요해질 때를 위해 통째로 보존)
```

마지막 `rawMetrics`가 중요하다. **지금 안 쓰는 값도 통째로 남긴다.** 나중에 새로운 관점이
필요해졌을 때 과거 실행을 다시 계산할 수 있어야 하기 때문이다
(`performance/scripts/lib/summary.js:304`).

## 4. 2단계 — Prometheus가 재는 것 (서버 관점)

k6는 밖에서만 본다. 안에서 무슨 일이 있었는지는 Prometheus가 본다.

### 4.1 Prometheus라는 도구를 먼저 이해하기

> **📘 개념 — Prometheus, 시계열, 스크랩**
>
> **Prometheus**는 시계열 데이터베이스다. 감시할 대상들을 주기적으로 찾아가 현재 값을
> 물어보고, `(시각, 값)` 쌍으로 쌓아 둔다.
>
> - **시계열(time series)**: 하나의 지표가 시간에 따라 변한 기록. 예: "CPU 사용률"의
>   초 단위 기록.
> - **스크랩(scrape)**: Prometheus가 대상에게 "지금 값이 뭐야?"라고 물으러 가는 행위.
>   이 프로젝트는 **5초 간격**이다(`performance/environment/prometheus/prometheus.yml`).
>   기본값 15초로는 부하 테스트의 스파이크를 놓치기 때문이다.

> **📘 개념 — 라벨(label)**
>
> 시계열을 구분하는 꼬리표다. 같은 이름의 지표라도 라벨이 다르면 다른 시계열이다.
>
> ```
> container_cpu_usage_seconds_total{name="perf-app"}    ← 앱 컨테이너의 CPU
> container_cpu_usage_seconds_total{name="perf-mysql"}  ← MySQL 컨테이너의 CPU
> ```
>
> **핵심**: Prometheus는 **라벨을 붙여 놓은 만큼만 쪼갤 수 있다.** 라벨 없이 수집한 값은
> 나중에 어떻게 해도 쪼갤 수 없다. 이 사실이 9장의 가장 큰 문제로 이어진다.

> **📘 개념 — exporter(익스포터)**
>
> Prometheus는 HTTP로 특정 형식의 텍스트를 읽어 올 뿐이다. MySQL이나 Redis는 그런 형식을
> 직접 내놓지 않으므로, **중간에서 통역해 주는 프로그램**이 필요하다. 그게 exporter다.
>
> 예: `mysqld-exporter`는 MySQL에 `SHOW GLOBAL STATUS`를 날리고, 그 결과를 Prometheus가
> 읽을 수 있는 형식으로 바꿔 준다.

> **📘 개념 — 카운터(counter)와 게이지(gauge)**
>
> 지표는 성질에 따라 두 종류다.
>
> - **카운터**: 계속 **누적**되기만 하는 값. "지금까지 처리한 총 요청 수" 같은 것.
>   절대 줄지 않는다(재시작 제외). 현재 값 자체는 의미가 없고 **변화량**이 의미 있다.
> - **게이지**: 오르내리는 **현재 상태** 값. "지금 사용 중인 커넥션 수", "현재 메모리
>   사용량" 같은 것.
>
> 이 구분이 중요한 이유는 다루는 방법이 다르기 때문이다.

> **📘 개념 — `rate()`와 `increase()`**
>
> 카운터를 쓸모 있게 만드는 두 함수다.
>
> - `rate(x[5m])` = 최근 5분 동안의 **초당 증가율**. "초당 몇 건 처리했나"
> - `increase(x[5m])` = 최근 5분 동안의 **총 증가량**. "5분간 몇 건 처리했나"
>
> 게이지에는 이걸 쓸 수 없다(오르내리는 값의 "증가율"은 의미가 없다). 대신
> `avg_over_time`, `max_over_time`, `quantile_over_time`으로 구간 통계를 낸다.

> **📘 개념 — 히스토그램(histogram)과 버킷(bucket)**
>
> 응답 시간 같은 값의 **분포**를 저장하는 방식이다. 개별 값을 다 저장하는 대신
> "5ms 이하 몇 건, 10ms 이하 몇 건, 50ms 이하 몇 건..." 식으로 구간별 개수만 센다.
> 이 구간 하나하나를 버킷이라고 한다.
>
> 버킷이 있으면 `histogram_quantile(0.95, ...)`로 **나중에** 임의 구간의 p95를 계산할 수
> 있다. 버킷이 없으면 못 한다.
>
> **대가는 시계열 개수다.** 버킷 하나가 시계열 하나다. 그래서 이 프로젝트는 관심 구간을
> 좁혀 버킷 수를 제한한다 — 예를 들어 HTTP 응답 시간은 5ms~10s만 본다
> (`src/main/resources/application.properties:21-23`).
>
> **왜 계산된 p95를 그냥 저장하면 안 되는가**: 분위수는 합산되지 않는다. 서버 3대의 p95를
> 평균 내도 전체 p95가 아니다. 원본 버킷을 보관해야 정확하다.

### 4.2 다섯 개의 눈 — 어디서 수집하는가

| 수집원 | 무엇을 아는가 | 관점 |
|---|---|---|
| **Spring Actuator + Micrometer** (`app:8080/actuator/prometheus`) | JVM 힙, GC, 스레드, HikariCP, Tomcat, HTTP 응답 시간 | 애플리케이션이 **자기 자신에 대해** 아는 것 |
| **mysqld-exporter** | 쿼리 수, slow query, 락 대기, 버퍼풀 적중률, 풀스캔 횟수 | MySQL이 **스스로 센** 값 |
| **redis-exporter** | 명령 처리량, 적중률, eviction, 메모리 | Redis가 스스로 센 값 |
| **cAdvisor** | 컨테이너별 CPU/메모리/네트워크/디스크, cgroup 한계와 throttling | **커널이 밖에서 본** 값 |
| **node-exporter** | 머신 전체 CPU, load average, iowait, 컨텍스트 스위치 | **VM 전체**가 얼마나 밀렸는가 |

**출처가 다르면 답하는 질문이 다르다.** 이게 이 설계의 핵심이다. mysqld-exporter는 "쿼리를
몇 번 처리했나"를 알고, cAdvisor는 "그러느라 CPU를 얼마나 태웠나"를 안다. 둘을 나누면
**"쿼리당 CPU 비용"**이라는 새 정보가 나온다.

> **⚠️ "호스트"라는 말의 함정**
>
> 이 스택에서 node-exporter가 보는 "호스트"는 **Windows가 아니라 WSL2 VM**이다. 앱·MySQL·
> Redis는 그 안에 있으니 정확히 측정되지만, **VM 바깥에서 벌어지는 일은 이 시스템이 볼
> 방법이 없다.**
>
> 특히 `host.stealPct = 0`은 **외부 경합이 없다는 증거가 아니다.** Hyper-V는 KVM과 달리
> steal time을 게스트에 보고하지 않기 때문에, Windows 쪽이 CPU를 가져가도 게스트에서는
> 0으로 보인다(`performance/tools/lib/hostprobe.js:1-20`).

### 4.3 무엇을 재는가 — 14개 그룹 157개 지표

지표 정의는 코드가 아니라 **데이터**로 관리된다
(`performance/tools/lib/metrics-catalog.js`). 지표 하나 추가 = 이 파일에 한 줄 추가다.
수집기는 카탈로그를 순회해 실행만 한다.

| 그룹 | 개수 | 답하는 질문 |
|---|---|---|
| `cpu` | 10 | 앱이 CPU를 얼마나 썼나, 한계에 걸렸나 |
| `memory` | 7 | 컨테이너 메모리 실사용량과 한계 |
| `heap` | 9 | JVM 힙 사용량, 누수 징후(live data) |
| `gc` | 10 | GC가 앱을 얼마나 멈췄나, 할당률, Old 승격률 |
| `jvm` | 17 | JIT 컴파일 시간, 스레드 상태(BLOCKED/WAITING), JVM 프로세스 CPU |
| `mysql` | 28 | 쿼리 수, slow query, 락 대기, 풀스캔, 버퍼풀, DB 컨테이너 CPU |
| `redis` | 17 | 처리량, 적중률, eviction, 메모리, Redis 컨테이너 CPU |
| `pool` | 13 | HikariCP active/pending/획득 시간/타임아웃, Tomcat busy 스레드 |
| `network` | 4 | 앱 컨테이너 송수신 대역폭과 에러 |
| `disk` | 3 | DB 컨테이너 디스크 읽기/쓰기/I/O 시간 |
| `host` | 11 | VM 전체 CPU, 코어당 run queue, iowait, steal, 컨텍스트 스위치 |
| `loadgen` | 7 | **부하 발생기 자신이** 얼마나 자원을 썼나 |
| `k6ts` | 13 | k6 지표를 시계열로 다시 본 값 (사후 재질의용) |
| `efficiency` | 8 | **요청 1건당** 자원 비용 |

각 지표는 보통 **avg / max / p95 세 가지**로 저장된다.

> **📘 왜 셋을 다 저장하는가**
>
> - **평균만** 보면 병목을 놓친다. CPU 평균 40%인데 max 100%면 "여유 있음"이 아니라
>   "주기적으로 포화됨"이다.
> - **최대만** 보면 순간 스파이크에 과잉 반응한다.
> - **p95**가 그 사이에서 "지속적으로 높았는가"를 판별한다. 실무 용량 산정은 대개 p95를 쓴다.

### 4.4 컨테이너 환경에만 있는 함정 — throttling

> **📘 개념 — cgroup, CPU quota, CFS throttling**
>
> **cgroup**은 리눅스가 프로세스 그룹의 자원 사용을 제한하는 기능이다. Docker의
> `cpus: 2` 설정이 이걸 쓴다.
>
> 그런데 제한 방식이 직관과 다르다. CPU를 "2코어만 쓰게" 만드는 게 아니라, **아주 짧은
> 주기(기본 100ms)마다 정해진 양의 CPU 시간을 배정하고, 다 쓰면 그 주기가 끝날 때까지
> 강제로 재운다.** 이 강제 정지를 **CFS throttling**이라고 한다.
>
> **왜 무서운가**: CPU 사용률이 100%에 안 닿아도 throttling이 일어난다. 앞부분에서 몰아
> 쓰고 뒷부분에 자면 평균은 낮게 나온다. 그런데 그 "잠든 순간"에 걸린 요청은 최대 100ms를
> 통째로 기다린다. **"CPU 여유 있는데 왜 p99가 튀지?"의 답이 대개 여기 있다.**

그래서 이 시스템은 throttling을 1급 지표로 승격시켰고, `cpu.throttledPct`는 **게이트 대상**
이다(`performance/regression/rules.json`의 `infra.flat.cpu.throttledPct`, `warn>1% / fail>10%`).

### 4.5 파생 지표 — 포화도

> **📘 개념 — 포화도(saturation)**
>
> **"한계 대비 얼마나 찼는가"**를 백분율로 나타낸 값이다.
>
> ```
> CPU 포화도 = 실제 사용 코어 수 ÷ cgroup 상한 × 100
> ```
>
> **왜 절대값 대신 비율을 쓰는가**: "CPU 1.4코어"는 환경이 바뀌면 의미가 없다. 4코어
> 머신에서는 여유롭고 2코어 머신에서는 포화다. **"한계의 70%"는 환경이 달라져도 그대로
> 비교된다.** 회귀 판정과 병목 지목에 이식성이 생긴다.

원시 값에서 8개의 포화도가 계산된다(`metrics-catalog.js:867-885`):
CPU(최대/평균), 메모리, 힙, HikariCP, Tomcat, MySQL 커넥션, Redis 메모리.

> **⚠️ 100%를 넘은 포화도는 자원 문제가 아니라 측정 오류다**
>
> 포화도는 정의상 100%를 넘을 수 없다. 넘긴 자원은 OOM Kill이나 throttling으로 강제
> 회수되지, 초과한 채 유지되지 않는다.
>
> 실제로 **메모리 포화도 227%**(3.66GB / 1.61GB)가 리포트에 실린 적이 있고, 그 값이 그대로
> "OOM Kill 위험"이라는 병목 가설로 승격됐다. 원인은 컨테이너 재생성 직후 cAdvisor가 죽은
> 컨테이너의 시계열을 같이 노출해 **분자만 합산**된 것이었다.
>
> 지금은 105%를 넘으면 값을 버리고 사유만 남긴다. 코드 주석의 표현이 정확하다 —
> **"그럴듯한 오보는 결측보다 나쁘다. 결측은 조사를 멈추게 하지만 오보는 엉뚱한 곳으로 몇
> 시간을 보낸다."**

### 4.6 효율 그룹 — 왜 따로 있는가

이게 이 시스템에서 가장 흥미로운 설계다.

**문제**: 앱 컨테이너가 CPU 상한(2코어)에 완전히 붙어서 돈다. 그래서 measure 300초짜리
실행의 CPU 소비량은 **항상 600 CPU초로 고정**이다. 세션이 빠르든 느리든 `cpu.cores.avg`는
1.998로 똑같이 나온다.

**즉 CPU가 포화된 상태에서는 사용률이 신호가 아니다.** 그 상태에서 실제로 달라지는 것은
"같은 CPU로 몇 건을 처리했나"뿐이고, 그건 사용률이 아니라 **총소비량 ÷ 처리량**으로만
보인다.

| 지표 | 계산 | 무엇을 잡아내나 |
|---|---|---|
| `efficiency.appCpuMsPerReq` | 앱 CPU초 ÷ 요청 수 | 요청 1건이 비싸졌는가 |
| `efficiency.dbCpuMsPerReq` | MySQL CPU초 ÷ 요청 수 | DB 쪽이 비싸졌는가 |
| `efficiency.stackCpuMsPerReq` | (앱+DB+Redis) ÷ 요청 수 | 병목이 옮겨 다녀도 총비용은 그대로 보인다 |
| `efficiency.dbCpuUsPerQuery` | MySQL CPU초 ÷ **쿼리 수** | 쿼리가 **늘어난 것**과 쿼리 **하나가 비싸진 것**을 가른다 |
| `efficiency.queriesPerReq` | 쿼리 수 ÷ 요청 수 | **N+1 탐지기** — 급증하면 쿼리가 요청당 늘어난 것 |

**실제로 이 값 하나가 조사를 뒤집은 적이 있다.** 자원 지표는 전부 평평했는데 요청당 CPU가
앱 +27%, MySQL +21%로 **함께** 올라 있었다. 사용률만 보면 아무 일도 없었던 것으로 읽히는
상황을, 이 지표만이 "요청 하나가 비싸졌다"로 바꿔 보여 줬다.

> 그 조사의 최종 원인은 컨테이너 아래 층이 아니라 **포화 상태에서 측정한 것**으로 밝혀졌다
> (2026-08-21). 이 값이 유용했다는 사실은 그대로다 — 다만 "요청당 비용이 올랐다"는 관측이
> 곧 "하드웨어가 느려졌다"는 뜻은 아니라는 점도 같이 기억해야 한다. 큐가 길어져도 요청당
> 비용은 오른다.

> **📘 개념 — N+1 문제**
>
> 게시글 목록 20개를 가져오는 쿼리 1번을 날리고, 각 게시글의 작성자를 가져오려고 다시
> 20번의 쿼리를 날리는 상황이다. 총 21번(=N+1). 개별 쿼리는 다 빠르지만 왕복 횟수 때문에
> 전체가 느려진다.
>
> **평균 응답 시간으로는 안 보인다.** "1ms짜리 100번"은 지연 지표에 안 잡히고 쿼리 **개수**로만
> 보인다. 그래서 `queriesPerReq`가 필요하다.

## 5. 3단계 — 두 관점을 같은 시간에 정렬한다

k6가 아는 시간과 Prometheus가 아는 시간이 어긋나면 모든 게 무의미해진다.

### 5.1 왜 k6가 Prometheus를 직접 조회하지 않는가

이유가 세 가지다(`performance/scripts/lib/summary.js:1-22`).

1. **스크랩 지연.** 테스트가 끝난 직후에 조회하면, 마지막 5초 스크랩이 아직 Prometheus에
   안 들어와 있다. **부하가 가장 높았던 종료 직전 구간이 통째로 빈다.**
2. **k6 런타임 제약.** `handleSummary`는 동기 함수다. 재시도가 필요한 네트워크 호출을
   제대로 감쌀 수 없고, 실패하면 20분짜리 테스트 결과를 통째로 잃는다.
3. **관심사 분리.** 부하 발생기는 부하만 생성해야 한다. 수집기가 죽어도 원본은 남아야 하고,
   수집 로직이 바뀌어도 과거 원본으로 리포트를 다시 만들 수 있어야 한다.

그래서 수집기는 **기본 15초를 기다린 뒤**(5초 간격 × 3회) 조회한다
(`performance/tools/collect.js:52`).

### 5.2 조회 구간 계산

```text
실행 시작 ─────┬──────────────┬───────────────┬────── 실행 종료
              │   warmup     │    measure    │  rampdown
              │              │               │
              └──────────────┴───────────────┘
                             ↑               ↑
                          from             to      ← Prometheus 조회 구간
```

`from`은 시작 시각 + warmup 길이, `to`는 `from` + measure 길이다. **`to`를 실행 종료 시각으로
두지 않는 것이 중요하다** — 그러면 rampdown 구간이 인프라 지표에 섞인다.

조기 종료(패닉·타임아웃)로 measure가 온전히 안 돌았으면, "계획대로 다 쟀다"고 하지 않고
실제 가용 구간으로 잘라내며 `incomplete: true`로 표시한다. 그 실행은 기준선 자격에서
탈락한다.

## 6. 4단계 — 판정

### 6.1 판정은 서로 독립된 세 개의 축이다

이 구분이 이 시스템에서 가장 중요한 부분이다.

| 축 | 답하는 질문 | 값 |
|---|---|---|
| **verdict** (판정) | 성능이 나빠졌는가? | PASS / WARN / FAIL |
| **measurementStatus** (측정 상태) | 판정할 만큼 데이터가 있었는가? | MEASURED / UNMEASURED |
| **saturation** (포화 상태) | 이 숫자를 애플리케이션 성능으로 읽어도 되는가? | HEADROOM / NEAR_LIMIT / SATURATED / UNKNOWN |

**세 축이 왜 분리돼야 하는가**: 예전에는 지표를 못 읽으면 그 규칙을 그냥 건너뛰었고,
건너뛴 규칙은 실패를 만들지 않았다. 그래서 **CPU·MySQL·Redis 지표가 전부 비어 있어도
테스트가 PASS로 통과했다.** "측정 못 했다"와 "측정했는데 괜찮다"가 같은 결과가 된 것이다.

지금은 게이트 지표(`gate: true`)의 값이 없으면 `UNMEASURED`가 되고, 그 실행은 기준선
자격도 잃는다. 종료 코드도 분리돼 있다 — `1`은 성능 회귀(개발자 책임), `3`은 측정 불가
(측정 인프라 책임)다(`performance/tools/collect.js:24-31`).

### 6.2 비교 가능성 — 조건이 다르면 아예 비교하지 않는다

> **📘 개념 — 기준선(baseline)과 회귀(regression)**
>
> **기준선**은 "이번 결과를 무엇과 비교할 것인가"의 대상이다. 보통 직전 실행이다.
>
> **회귀**는 "이전보다 나빠졌다"는 뜻이다. 성능 회귀 테스트는 매번 실행 결과를 기준선과
> 비교해 나빠졌는지 자동으로 판정한다.

문제는 **아무 실행이나 기준선이 될 수 없다**는 것이다. 데이터셋이 다르면 p95를 나란히
놓는 것 자체가 비교가 아니다.

그래서 실행 조건을 1급 개념으로 분리했다(`performance/tools/lib/conditions.js`).

| 조건 | 등급 | 왜 |
|---|---|---|
| 시나리오 | blocking | 다른 시나리오는 다른 실험이다 |
| 환경 | blocking | 환경이 다르면 절대값이 다르다 |
| 데이터셋 | blocking | **이름 + 생성 지문 + 실행 시작 시점의 DB 상태 지문** |
| 부하 프로파일 | blocking | executor, stages 등 **선언된** 부하 |
| 부하 발생기 위치 | blocking | local(Windows→포트포워딩) vs docker(VM 내부) — **경로 오버헤드 179ms 실측** |
| 측정 프로파일 | blocking | warmup/measure 길이 |
| 스크립트 지문 | degrading | 대개 주석 한 줄이라 수치는 유효 — 경고만 |

- **blocking**: 수치가 **무의미**해진다. 기준선 자격 박탈, 상대 비교 생략.
- **degrading**: 수치가 **의심스럽다**. 비교는 하되 경고를 띄우고 FAIL을 WARN으로 낮춘다.

> **⚠️ 조건에는 "선언된 의도"만 넣고 "측정 결과"는 절대 넣지 않는다**
>
> 처음 떠오르는 방법은 k6가 보고한 `vusMax`(최대 VU 수)를 조건에 넣는 것이다. 하지만 이건
> 설정값이 아니라 **관측값**이다.
>
> `ramping-arrival-rate` 시나리오는 목표 도착률을 유지하려고 VU를 동적으로 할당하므로
> **서버가 느려질수록 vusMax가 올라간다.** 조건으로 쓰면 이렇게 된다.
>
> ```
> 진짜 회귀 발생 → vusMax 변화 → 기준선 부적격 → 비교 생략 → 게이트 통과
> ```
>
> **회귀가 심할수록 면제되는, 스스로를 무력화하는 필터**가 된다. 그것도 한계 탐색이 목적인
> 유일한 시나리오에서.

### 6.3 회귀 규칙 — 오탐을 줄이는 네 가지 장치

부하 테스트 수치는 본질적으로 흔들린다. "직전보다 나빠졌다"를 그대로 회귀로 부르면 오탐이
쏟아지고, 결국 아무도 결과를 안 본다(**경보 피로**).

판정 규칙은 코드가 아니라 `performance/regression/rules.json`에 데이터로 있다. 오탐 방지
장치는 네 가지다.

| 장치 | 하는 일 | 예시 |
|---|---|---|
| **방향성** | 지표마다 어느 쪽이 나쁜지 명시 | TPS는 올라야 좋고, P95는 내려야 좋고, **MySQL QPS는 (RPS가 그대로면) 오르면 나쁘다** (N+1) |
| **노이즈 플로어** | 절대 변화가 작으면 비율이 아무리 커도 무시 | 2ms → 3ms는 +50%지만 의미 없음 |
| **기준선 하한** | 기준값 자체가 너무 작으면 비율 비교를 건너뜀 | 0에 가까운 분모 문제 |
| **절대 게이트** | 직전보다 개선됐어도 SLO를 넘으면 실패 | **삶은 개구리 방지** — 매번 9%씩 나빠지며 영원히 통과하는 문제 |

현재 게이트(CI를 멈추는) 규칙은 다음과 같다.

| 지표 | 상대 임계 | 절대 임계 |
|---|---|---|
| P95 응답 시간 | warn +10% / fail +20% | fail > 500ms |
| P99 응답 시간 | warn +15% / fail +30% | fail > 1,200ms |
| 평균 응답 시간 | warn +10% / fail +25% | — |
| 오류율 | warn +50% | warn > 0.1% / fail > 1% |
| TPS | warn −10% / fail −20% | — |
| RPS | warn −10% / fail −20% | — |
| Check 성공률 | — | fail < 99% |
| CPU throttling 비율 | — | warn > 1% / fail > 10% |
| MySQL slow query 수 | warn +20% / fail +100% | — |
| 커넥션 타임아웃 | — | fail > 0 |

나머지 20여 개 규칙은 `gate: false`(참고용 경고)다.

> **📘 `gate: true`가 두 가지 뜻인 이유**
>
> 게이트 지정은 "CI를 멈춘다"인 동시에 **"이 지표가 없으면 판정이 성립하지 않는다"**는
> 필수 선언이다. 그래서 게이트를 늘리면 그 지표가 빠진 실행이 전부 `UNMEASURED`가 된다.
>
> 실제로 이 이유 때문에 몇몇 유용한 지표가 일부러 게이트에서 빠져 있다. 예를 들어
> **부하 발생기 throttling**은 "측정이 오염됐다"는 강력한 신호지만, `--loadgen local`로 돌린
> 실행에는 값이 없어 전부 UNMEASURED가 되므로 `gate: false`로 둔다.

### 6.4 포화 판정 — 닷새를 날린 오류에서 나온 축

이 부분은 배경을 알아야 이해가 된다.

**무슨 일이 있었나**: 2026-08-15~19에 저장된 `normal-day` 실행의 p95는 10,000~17,000ms였다.
이 시스템은 그 값을 **애플리케이션 지연**으로 읽고, 왜 25~45%씩 흔들리는지를 호스트·커널·
전원 관리·하드웨어 카운터에서 찾았다.

**실제로는 큐 대기였다.** 같은 앱·같은 데이터·같은 커밋을 포화 이하(도착률 4/s)에서 재면
**278ms**다. **38배 차이**이고, 차이의 정체는 코드가 아니라 대기줄이었다.

신호는 처음부터 전부 있었다.

```
pool.hikariAcquireP95Ms  6,364ms   ← 전체 p95의 57%가 커넥션 대기
pool.hikariPending.avg      145    ← 커넥션 10개를 145개 스레드가 대기
cpu.throttledPct         99.86%    ← 거의 매 주기 강제 정지
cpu.cores.avg          1.998/2.0   ← 완전 포화
실측 RPS                17~28      ← 시나리오 문서의 기대치는 45~55
```

**문제는 아무도 이 조합을 "측정 무효화 조건"으로 선언하지 않았다는 것이다.**
`measurementStatus`는 지표 **결측**만 본다. 지표가 멀쩡히 다 있으면서 **그 값의 의미가
달라지는** 경우는 보지 않았다. 그래서 경고 없이 닷새가 갔다.

그래서 추가된 것이 `performance/tools/lib/saturation.js`다. 다섯 개의 신호를 본다.

| 신호 | 주의 | 포화 | 의미 |
|---|---|---|---|
| DB 커넥션 대기 스레드 (`hikariPending.avg`) | ≥1 | ≥5 | 대기가 있다 = 정의상 큐가 생겼다 |
| 앱 CPU throttled 비율 | ≥30% | ≥80% | 처리율이 상한에 묶였다 |
| 앱 CPU 사용률(상한 대비) | ≥75% | ≥90% | 작은 변화가 큰 지연으로 증폭되는 구간 |
| **커넥션 획득이 p95에서 차지하는 비율** | ≥20% | ≥40% | 40% 넘으면 "지연의 절반이 대기" |
| 도착률 달성도 (open model만) | <98% | <90% | **부하 발생기가 계획한 부하를 못 넣었다는 직접 증거** |

**중요한 설계 판단**: 포화는 **판정이 아니라 해석 조건**이다. 포화 자체가 실패는 아니다 —
`stress`·`breakpoint` 시나리오는 포화를 만드는 것이 목적이다. 그래서 게이트를 실패시키지
않고, **"이 실행의 p95를 애플리케이션 지연으로 읽으면 안 된다"**를 표시한다.

그리고 포화 상태가 서로 다른 두 실행은 비교하지 않는다. 포화 영역의 p95는 `R = N/X`로
결정되고 비포화 영역의 p95는 서비스 시간이다. **서로 다른 물리량**이므로 증감률을
계산해도 의미가 없다.

## 7. 측정 환경 자체를 측정하는 장치들

이 시스템에는 "서버를 재는 것"이 아니라 **"측정이 오염되지 않았는지 재는"** 장치가 따로 있다.

### 7.1 hostprobe — VM 바깥을 본다

Windows에서 `typeperf`(기본 제공 성능 카운터 도구)를 **1초 간격**으로 돌려 Windows 전체
CPU와 코어별 사용률을 기록한다. node-exporter가 못 보는 층을 메우는 유일한 수단이다.

> **⚠️ `% Processor Performance`를 물리 클럭으로 읽지 말 것**
>
> 실측으로 확인됐다. 최소 프로세서 상태를 5%→100%로 올렸는데 이 카운터는 오히려
> 114.8%→102.5%로 **내려갔고**, Windows 전체 CPU(44%→27%)와 같은 방향으로 움직였다.
> 물리 주파수가 아니라 **시스템 활동 수준의 대리 지표**에 가깝다.

이 프로브도 한 번 잘못된 인과 결론을 냈다가 철회했다. 원인이 네 가지였다.

1. **창 불일치** — 요약이 전체 구간 평균인데 p95는 measure 구간만이었다.
2. **자기 오염** — 아래의 loadbench(2코어 40초)가 같은 창 안에서 돌았다.
3. **`_Total`만 봄** — 이기종 CPU(P코어 6 + E코어 8)에서 전체 집계는 유휴 코어까지 섞는다.
4. **원시 소실** — 요약만 남기고 지워서 사후 재질의가 불가능했다.

지금은 원시 표본을 보존하고 구간별로 잘라 쓴다.

### 7.2 loadbench — 순환을 깨는 장치

**문제**: 4.6절에서 봤듯 CPU 상한에 붙어 있으면 "요청당 자원" 지표는 `600,000 ÷ 요청 수`가
되어 **처리량을 다른 단위로 다시 쓴 값**일 뿐이다(실측 오차 0.5~1.9%). 분자가 고정이고
분모만 변하므로, 아무리 조합해도 "왜 처리량이 떨어졌는가"에 답할 수 없다. **순환이다.**

**해법**: 부하가 도는 동안 **알려진 고정량의 일**(캐시 안에서 도는 해시 계산 등)을 시키고
걸린 시간을 잰다. 분자가 "일의 양"으로 고정되므로 처리량과 순환하지 않는다.

```
벤치도 같은 비율로 느려짐  → 원인은 컨테이너 밖 공유 층 (클럭·캐시·메모리)
벤치는 평소값인데 앱만 느림 → 원인은 컨테이너 또는 JVM 안
```

**왜 warmup 구간에 넣는가**: 벤치 자체가 2코어를 태우므로 measure 안에서 돌리면 그 실행을
오염시킨다 — 환경을 확인하려다 환경을 바꾸는 셈이다. warmup은 **부하는 이미 걸려 있는데
통계에는 잡히지 않는 구간**이라 두 조건을 동시에 만족한다.

이 우회가 필요한 이유는 WSL2에서 하드웨어 성능 카운터를 쓸 수 없기 때문이다. 코어 PMU가
없고, `aperf`/`mperf`로 실효 주파수를 읽을 수도 없고, RAPL 전력 이벤트도 비어 있다.
**IPC·캐시 미스·실효 클럭을 직접 재는 경로가 전부 막혀 있고, 고정 작업량 벤치가 유일하게
남은 계측 수단이다.**

### 7.3 데이터셋 상태 지문

> **📘 개념 — 지문(fingerprint)**
>
> 데이터의 내용을 요약한 짧은 문자열이다. 내용이 조금이라도 다르면 지문이 달라진다.
> "이 두 실행이 정말 같은 데이터로 돌았는가"를 이름이 아니라 내용으로 확인하는 장치다.

**이름이 같은 `large`라도 앞선 쓰기 테스트가 데이터를 3만 건 추가했으면 다른 데이터셋이다.**
그래서 두 겹의 지문을 쓴다.

- **생성 지문**: "어떻게 만들었나"(생성 규칙과 파라미터)
- **상태 지문**: **실행 직전에 DB를 직접 세어** "지금 무엇이 들어 있나"

기본 모드는 `strict`다 — 스냅샷과 다르면 되돌린 뒤 실행한다.

### 7.4 부하 발생기 계측

k6를 컨테이너(`--loadgen docker`)로 돌리면 cAdvisor가 그 CPU·메모리를 따로 잰다.
기본값인 Windows 네이티브 `k6.exe`는 **아무도 측정하지 못한다** — cAdvisor는 컨테이너만
보고, node-exporter가 보는 "호스트"는 WSL2 VM이라 그 밖의 프로세스가 잡히지 않는다.

`loadgen.throttledPct`가 0이 아니면 **그 실행의 지연은 서버가 아니라 부하 발생기가 만든
것일 수 있다.** 서버를 아무리 개선해도 사라지지 않는 가짜 병목이다. 그래서 임계값이
앱(warn 1% / fail 10%)보다 훨씬 낮다(warn 1% / fail 5%) — 앱의 throttling은 "측정된
사실"이지만 발생기의 throttling은 "측정이 오염됐다는 신호"라서 적은 양에도 반응해야 한다.

# 9. 현재 계측 시스템의 문제점과 부족한 것

앞 장까지가 "무엇을 재고 있는가"였다면, 이 장은 **"무엇을 못 재고 있는가"**다.

각 항목은 **문제 / 왜 문제인가 / 근거 / 지금 할 수 있는 것**으로 나눠 적는다.
**사실**과 *추론*을 구분했다.

---

## 9-1. 가장 큰 구멍 — "무엇이" 자원을 썼는지 모른다

### 문제

**157개 지표가 전부 "시스템 전체 합계"인 스칼라 값이다.** 어느 API, 어느 서비스 메서드,
어느 쿼리가 그 자원을 소비했는지 알려주는 지표가 **하나도 없다.**

즉 이 시스템은 다음 질문에 답한다.

- ✅ "CPU가 포화됐는가?" → 답한다
- ✅ "커넥션 풀에 대기가 있었는가?" → 답한다
- ❌ **"어느 API가 그 커넥션을 붙잡고 있었는가?"** → **답하지 못한다**

### 왜 문제인가

자원이 포화되면 **모든 API가 함께 느려진다.** 한 API가 커넥션을 독점하면, DB와 아무 상관
없는 요청까지 커넥션 획득 단계에서 대기하고, 그 대기가 톰캣 스레드를 점유해 정적 응답까지
큐에 쌓인다.

이 상태에서 지연 순위표를 보면 **원인과 결과가 똑같이 "느린 요청"으로 보인다.** 오히려
원래 1ms에 끝나던 가벼운 엔드포인트가 큐 대기에 가장 민감하게 반응해 지연 1위로 올라온다.
그걸 조사하면 시간만 버린다.

병목을 짚으려면 **지연 순위가 아니라 "자원 점유 총량" 순위**가 필요하다.

```
점유 총량 = 호출 수 × 1건당 점유 시간   (리틀의 법칙)
```

**이 값을 계산할 데이터가 현재 리포트에 없다.**

### 근거 (사실)

- `performance/tools/lib/metrics-catalog.js`에 `http_server_requests` 계열이 **0건**이다.
  수집기는 카탈로그만 순회하므로, 엔드포인트별 데이터는 `run.json`에 **남지 않는다.**
- 애플리케이션은 이 데이터를 **이미 노출하고 있다.**
  `src/main/resources/application.properties:21-23`에서 히스토그램 버킷을 켜 두었고,
  Micrometer가 `uri`/`method`/`status` 라벨을 자동으로 붙인다.
- Grafana 대시보드에는 패널이 하나 있다
  (`performance/metrics/dashboards/perf-overview.json:115`).
  즉 **실시간으로 보고 있을 때만 볼 수 있고, 리포트에는 안 남는다.**
- k6 쪽 `feature`/`op`/`page` 축은 **시간만** 쪼갠다. 자원 소비는 쪼개지 않는다.
- `tags()`가 붙이는 `name` 태그(`performance/scripts/lib/config.js:91`)는 threshold에
  선언되지 않아 **서브메트릭이 아예 생성되지 않는다.**

### 이미 인지된 문제인가

**그렇다.** `performance/docs/design/perf-metrics-catalog-plan.md`가 정확히 이 질문을 표제로 달고 있고
(*"무엇이 포화됐는가가 아니라, 어느 요청·Repository 메서드·SQL·Redis 명령·배치가 그
포화를 만들었는가?"*), `infra.attribution`이라는 별도 층을 설계해 뒀다.
**상태는 "적용 범위 결정 완료, 구현 전"이다.**

### 지금 할 수 있는 것 (권고)

카탈로그에 `endpoint` 그룹을 추가하는 것이 가장 저렴하다. 앱은 이미 데이터를 내고 있으므로
**카탈로그 파일에 몇 줄 추가하는 것으로 끝난다.**

```javascript
// 엔드포인트별 톰캣 스레드-초 소비량 = 용의자 랭킹
// 동기 서블릿 모델에서는 응답 시간 = 워커 스레드 점유 시간이므로,
// 이 값이 곧 "그 엔드포인트가 소비한 스레드 자원"이다.
`topk(15, sum by (uri) (increase(http_server_requests_seconds_sum{job="spring-app"}[$RANGE])))`
```

단, 현재 수집기는 결과를 **스칼라 하나로 접는다**(`one()`, `reduce`). 라벨이 여러 개인
벡터를 담으려면 저장 구조가 필요하다 — 이것이 계획 문서가 "별도 벡터 구조 필요"라고 적어
둔 지점이다.

## 9-2. CPU 포화 환경이라 지표 상당수가 정보를 잃었다

### 문제

앱 컨테이너가 CPU 상한(2코어)에 **상시 붙어서** 돈다. 그 결과:

- `cpu.cores.avg`가 세션이 빠르든 느리든 **항상 1.998**로 나온다.
- `efficiency.*` 지표는 정의상 `600,000ms ÷ 요청 수`가 되어, **처리량을 다른 단위로 다시
  쓴 값**일 뿐이다. 실측 오차 0.5~1.9%로 확인됐다.

### 왜 문제인가

포화 상태에서는 **사용률이 신호가 아니다.** 그런데 `cpu` 그룹 10개, `efficiency` 그룹 8개,
그리고 포화도 파생 지표 상당수가 이 조건에서 독립적인 정보를 주지 못한다.
*(추론)* 157개 중 실질적으로 판별력을 가진 지표는 그보다 훨씬 적을 가능성이 높다.

### 근거 (사실)

`performance/tools/lib/loadbench.js:1-25`에 이 문제가 그대로 적혀 있다. 그리고
`efficiency.queriesPerReq`도 같은 함정에 있다 — 부하와 무관한 배경 작업(스케줄러 등)이
기준 실행 전체 쿼리의 **약 44%**를 차지해서, 처리량이 떨어지면 이 지표가 **기계적으로**
오른다.

### 무엇이 부족한가

**N+1 탐지기(`queriesPerReq`)가 배경 작업 44%에 오염돼 있다.** 스케줄러 쿼리와 요청 처리
쿼리를 분리하는 계측이 없다. 현재로선 이 지표의 변화를 N+1로 해석하기 어렵다.

`loadbench`가 순환을 깨려고 도입됐지만, 이건 **환경이 느려졌는지 판별**할 뿐 **어느 코드가
비싼지**는 여전히 답하지 못한다.

## 9-3. 애플리케이션 내부가 사실상 비어 있다

### 문제

| 항목 | 상태 |
|---|---|
| 커스텀 Micrometer 계측 (`MeterRegistry`, `@Timed`, `@Counted`) | **0건** |
| 분산 트레이싱 (micrometer-tracing, OpenTelemetry, Zipkin) | **없음** |
| 메서드 단위 시계열 | **없음** |

메서드 단위 정보는 **로그에만** 있다. `src/main/java/.../aop/ExecutionLoggingAspect.java`가
컨트롤러와 `services.domain` 전체 메서드의 실행 시간을 재지만, **300ms를 넘는 경우만 WARN
로그로 남긴다**(임계값: `application.properties`의 `app.execution-logging.slow-threshold-ms=300`).

### 왜 문제인가

로그는 시계열이 아니다. 그래서 다음을 할 수 없다.

- 추세 확인 — "이 메서드가 지난주보다 느려졌나"
- 집계 — "이 메서드가 전체 시간의 몇 %를 차지하나"
- 회귀 판정 — 게이트에 걸 수 없다
- **299ms짜리는 아예 기록되지 않는다.** 100번 호출되면 29.9초인데도 보이지 않는다.

### 무엇이 부족한가 (권고)

`ExecutionLoggingAspect`는 **이미 포인트컷이 컨트롤러와 서비스 전체에 걸려 있다.**
`MeterRegistry`를 주입해 타이머를 추가하면 메서드 단위 시계열이 생긴다.

다만 서비스 레이어 **전체**에 붙이면 카디널리티가 위험하다. 클래스 단위로 묶거나
(`class` 라벨만, `method` 제외) 무거운 경로만 선별하는 편이 안전하다. 그리고 이 값은
"메서드 실행 시간"이지 "자원 점유"가 아니라는 한계는 그대로 남는다.

## 9-4. 커넥션 풀은 "대기"만 알고 "점유"를 모른다

### 문제

현재 수집하는 HikariCP 지표는 다섯 가지다: active, pending, max, **획득 대기** p95, timeout.

**빠진 것: 커넥션 보유 시간(`hikaricp.connections.usage`)이다.** Micrometer가 기본으로
노출하는데 카탈로그에 없다(`performance/` 전체 검색 결과 0건).

### 왜 문제인가

이 둘이 갈리지 않는다.

- **풀이 작아서** 대기가 생긴 것인가 → 풀 크기를 늘리면 해결
- **트랜잭션이 길어서** 커넥션을 오래 붙잡은 것인가 → 풀을 늘려도 소용없고 코드를 고쳐야 함

**대기 시간이 긴 쪽은 피해자, 점유 시간이 긴 쪽이 범인**이라는 판별이 지금 불가능하다.

### 이미 인지된 문제인가

**그렇다.** `performance/docs/design/perf-metrics-catalog-plan.md`의 적용 판단 표에 *"Hikari 커넥션 보유
시간 — **즉시 적용** — 풀 부족과 긴 트랜잭션을 구분"*으로 올라와 있다. **미구현이다.**

## 9-5. DB와 캐시 내부가 총계뿐이다

### 문제

| 아는 것 | 모르는 것 |
|---|---|
| slow query가 **몇 건** 있었는가 | **무슨 쿼리**였는가 |
| 풀스캔이 **몇 번** 일어났는가 | **어느 테이블**이었는가 |
| 락 대기 총시간이 얼마인가 | **어느 행**에서 경합했는가 |
| Redis 명령을 초당 몇 건 처리했는가 | **어느 명령**이 느렸는가 |

`mysqld-exporter`는 `SHOW GLOBAL STATUS`의 전역 카운터만 읽는다.
`performance_schema.events_statements_summary_by_digest`(쿼리 종류별 총 실행 시간)와
Redis SLOWLOG는 수집하지 않는다.

### 왜 문제인가

**"slow query가 40건에서 90건으로 늘었다"는 알람은 조사 시작점을 주지 못한다.**
어느 쿼리인지 알려면 매번 사람이 DB에 직접 붙어야 하고, 그때는 이미 부하가 끝나 있다.

### 이미 인지된 문제인가

**그렇다.** 계획 문서에 *"SQL digest 상위 20개 — **매 실행 자동 저장** — 작고, 실행별 느린
SQL을 가장 직접적으로 설명"*으로 결정돼 있다. **미구현이다.**

## 9-6. 결측이 "정상 동작"이라 조용히 퍼진다

### 문제

실행 방식에 따라 **157개 지표 중 27개가 통째로 비는 것이 설계상 정상**이다.

| 그룹 | 개수 | 비는 조건 |
|---|---|---|
| `loadgen` | 7 | `--loadgen local`(**기본값**)로 실행하면 전부 null |
| `k6ts` | 13 | `--no-remote-write`거나 remote-write 도입 이전 실행이면 전부 null |
| `efficiency` | 7/8 | 분모(k6 요청 수)가 remote-write에서 오므로 위와 함께 사라짐 |

### 왜 문제인가

*(추론)* 결측 자체는 의도된 설계다 — 코드 주석은 "그 결측이 곧 '측정하지 않았다'는 정확한
기록"이라고 정당화한다. 이 논리는 맞다.

문제는 **기본값으로 그냥 실행하면 27개가 비는데, 그 27개에 "이 측정을 믿어도 되는가"를
판정하는 지표가 몰려 있다는 것**이다. `loadgen.throttledPct`는 "부하 발생기가 병목이었다"를
잡는 유일한 신호인데, 기본 실행에서는 항상 null이다.

즉 **가장 중요한 안전장치가 기본값에서 꺼져 있다.**

### 지금 할 수 있는 것 (권고)

결측을 없애기보다, **결측이 판정에 미치는 영향을 리포트 최상단에 명시**하는 편이 현실적이다.
"이 실행은 부하 발생기를 측정하지 않았으므로, 지연의 원인이 서버라고 단정할 수 없다"를
한 줄로 띄우는 것이다. 지금은 개별 지표가 `—`로 표시될 뿐 그 함의가 문장으로 나오지 않는다.

## 9-7. WebSocket이 판정 체계 밖에 있다

### 문제

`performance/README.md` 7절은 SLO에 **"WS RTT P95 < 500ms"**를 명시한다.
그런데 이 SLO를 판정하는 장치가 없다.

### 근거 (사실)

- `performance/scripts/chat-ws.js:25-27`이 커스텀 메트릭 3개를 정의한다:
  `chat_ws_rtt`(왕복 시간), `chat_ws_messages_sent`, `chat_ws_errors`.
- 이 이름을 `summary.js`, `metrics-catalog.js`, `rules.json`에서 검색하면 **전부 0건**이다.
- 즉 `record.k6.all`과 `k6.phases`의 구조화된 필드에 WebSocket 값이 **없다.**
  `rawMetrics`에 원본은 남지만 판정·리포트·회귀 비교에는 들어가지 않는다.

### 왜 문제인가

`chat-heavy` 시나리오를 돌려도 **채팅 성능이 나빠졌는지 자동으로 알 수 없다.**
HTTP 지표는 정상인데 WebSocket만 무너진 상황이 PASS로 나온다.

*(추론)* 선언된 SLO 중 하나가 판정되지 않는 상태는, 실제 회귀보다 **"판정 체계를 믿는
습관"** 쪽에 더 위험하다.

## 9-8. 오류의 내용을 모른다

### 문제

`errorRate`는 **비율**만 알려준다. 어떤 상태 코드였는지, 어느 엔드포인트에서 났는지가
리포트 구조에 없다.

`checks`(응답 내용 검증)는 이름별 통과/실패 수가 저장되지만
(`performance/scripts/lib/summary.js:213-227`), 회귀 규칙은 **전체 성공률 하나만** 본다
(`checkRate < 0.99`).

### 왜 문제인가

*(추론)* "오류율 0.8%"는 SLO(1%) 안이라 통과한다. 그런데 그 0.8%가 특정 엔드포인트에
100% 몰려 있다면 그 기능은 완전히 죽은 것이다. 지금 구조로는 구분되지 않는다.

또한 **애플리케이션 에러 로그 증가량**을 수집하지 않는다. HTTP 200으로 응답하면서 내부적으로
예외를 삼키고 있는 경우를 잡을 방법이 없다. 계획 문서에는 *"에러·경고 로그 증가량 —
**즉시 적용** — 비용이 거의 없고 HTTP 성공 뒤에 숨은 실패를 잡음"*으로 올라와 있다.
**미구현이다.**

## 9-9. 부하 모델의 근거가 실측이 아니다

### 문제

| 파라미터 | 값 | 근거 |
|---|---|---|
| `PAGE_WEIGHTS` (목록 페이지 비율) | `[0.55, 0.20, 0.12, 0.08, 0.05]` | **업계 통념. 실측 아님** |
| `AUTHOR_SKEW` (작성 활동 쏠림) | 1.3 | **옛 DB 분포와의 연속성 — 잠정값** |
| `THINK` (생각 시간) | 1~4초 균등분포 | 코드에 근거 기록 없음 |
| `HOT_SKEW` (글 인기 쏠림) | 1.07 | 크기 무관 고정 (비교 실험의 전제로서는 타당) |

### 왜 문제인가

쏠림 정도가 **캐시 적중률과 버퍼풀 적중률을 직접 결정한다.** 실제 트래픽이 더 균등하면
지금 결과보다 나쁘고, 더 쏠려 있으면 더 좋다. **절대 수치를 운영 예측에 쓸 수 없다.**

*(추론)* 다만 이 한계가 상대 비교(개선 전후)를 무효화하지는 않는다. 규칙이 고정돼 있으면
"같은 조건에서 나아졌다"는 여전히 성립한다. 위험한 것은 절대 수치를 인용할 때다.

### 근거 (사실)

이건 숨겨진 문제가 아니라 코드 주석에 명시돼 있다
(`performance/scripts/lib/sampling.js:100-110`):
*"성능 시스템에서 가장 위험한 건 틀린 숫자가 아니라 근거 없이 확정된 것처럼 보이는 숫자다."*

## 9-10. 측정 환경이 구조적으로 운영과 다르다

### 문제

| 항목 | 측정 환경 | 운영 |
|---|---|---|
| 토폴로지 | 단일 호스트에 앱+DB+Redis+부하발생기 | EC2 + RDS + ElastiCache 분리 |
| 앞단 | 없음 | ALB + CloudFront |
| CPU | WSL2 VM 위 2코어 상한 | EC2 인스턴스 |
| 부하 발생기 | **측정 대상과 같은 머신** | — |

### 왜 문제인가

**부하 발생기가 측정 대상과 자원을 다툰다.** 이미 장부에 E-01로 등록된 문제다.
`--loadgen docker`로 돌리면 최소한 얼마나 먹었는지는 기록되지만, 경쟁 자체가 사라지지는
않는다. 그리고 두 모드는 네트워크 경로가 달라 서로 비교되지 않는다.

**결론적으로 이 시스템은 "운영 용량 예측"에 쓸 수 없다.** `performance/docs/planning/perf-review-summary.md`가
이미 그렇게 판정해 두었다("운영 용량 예측 — 현재 불가").

*(추론)* 이건 고칠 수 있는 결함이라기보다 **범위의 한계**다. 문제는 한계 자체가 아니라,
리포트가 절대 수치(p95 278ms 등)를 출력하기 때문에 그 한계가 매번 잊히기 쉽다는 점이다.

## 9-11. 판정 축의 남은 빈틈

### (a) 새 지표가 판정에 못 들어온다

`k6ts`(13개)와 `efficiency`(8개)와 `jvm`(17개) 그룹은 전부 `gate: false`다.
이유는 코드에 적혀 있다 — **게이트 지정은 "필수 지표" 선언이기도 해서, 과거 실행에 값이
없으면 전부 `UNMEASURED`가 되기 때문**이다.

*(추론)* 이 설계는 안전하지만 부작용이 있다. **가장 유용한 신규 지표일수록 게이트에 못
들어가고, 결국 사람이 리포트를 눈으로 읽어야만 발견된다.** 지표를 추가할수록 자동 판정의
비중이 줄어드는 구조다.

**권고**: 게이트 승격의 조건("N회 연속으로 값이 존재하면 승격")을 규칙 파일에 표현할 수
있게 하거나, 필수 여부를 게이트와 분리된 필드로 두는 것이 방향이다.

### (b) 포화 실행의 절대 게이트

포화 판정은 게이트를 실패시키지 않는다(설계 의도대로다). 그런데 절대 게이트
(`p95 > 500ms → FAIL`)는 **포화 여부와 무관하게 그대로 돈다.**

*(추론)* 그래서 포화 실행은 "이 p95는 애플리케이션 지연이 아니다"라는 경고와
"P95 SLO 위반 FAIL"을 **동시에** 낸다. 두 메시지가 서로를 부정하는데, 어느 쪽을 따라야
하는지는 사람이 판단해야 한다. 실제로 이 조합이 닷새를 날린 오해의 출발점이었다.

### (c) 기준선이 없는 실행이 흔하다

blocking 조건이 여섯 개고, 데이터셋 조건에는 **실행 시작 시점의 DB 상태 지문**까지 들어간다.
조건이 엄격할수록 정확하지만, *(추론)* 그만큼 **상대 비교가 성립하는 실행 쌍이 드물어진다.**
`performance/docs/planning/perf-review-summary.md`도 "기준선 자체가 없는 경우가 흔하다"고 적고 있다.

## 부록: 자주 헷갈리는 개념 정리

| 용어 | 한 줄 정의 |
|---|---|
| VU | 가상 사용자 한 명 |
| iteration | 사용자 여정 한 바퀴 |
| RPS | 초당 HTTP 요청 수 |
| TPS | 초당 완료된 iteration 수 |
| p95 / p99 | 응답 시간을 줄 세웠을 때 95% / 99% 지점의 값 |
| closed model | VU 수 고정 — 서버가 느려지면 부하도 줄어든다 |
| open model | 도착률 고정 — 서버가 느려져도 부하는 그대로 |
| coordinated omission | closed model에서 최악 구간이 통계에서 사라지는 현상 |
| 리틀의 법칙 | 동시 요청 수 = 도착률 × 체류 시간 |
| warmup / measure / rampdown | 준비 / 판정 대상 / 마무리 구간 |
| 태그 | 요청에 붙이는 분류 라벨 |
| 서브메트릭 | 태그로 쪼갠 지표 (k6는 threshold 선언이 있어야 만든다) |
| threshold | k6의 통과/실패 기준 |
| SLO | 스스로 정한 성능 약속 |
| 카운터 / 게이지 | 누적만 되는 값 / 오르내리는 현재 값 |
| rate / increase | 초당 증가율 / 구간 총 증가량 |
| 히스토그램 버킷 | 분포를 구간별 개수로 저장한 것 |
| 카디널리티 | 라벨 값의 가짓수 (많으면 메모리 폭발) |

| 포화도 | 한계 대비 사용률(%) |
| 기준선 | 이번 결과를 비교할 대상 실행 |
| 회귀 | 이전보다 나빠진 것 |
| 노이즈 플로어 | 이보다 작은 변화는 회귀로 보지 않는 하한 |

| 지문 | 내용을 요약한 짧은 문자열 (같은 데이터인지 확인용) |
| N+1 | 목록 1회 + 항목별 N회 쿼리가 나가는 문제 |
| 귀속(attribution) | "이 자원을 누가 썼는가"를 밝히는 것 |
