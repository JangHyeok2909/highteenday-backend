# 밤새 실행 중 수정한 문제

기록일: 2026-08-18  
범위: `localDocs/NEXT-DAY-PERF-TASKS.md`의 「밤새 무인으로 돌려 둘 실행 목록」 실행 중 발견해 실제로 수정한 사항만 기록한다.

이 문서는 실행 결과 보고서가 아니다. 무엇이 실패했고, 어떤 코드나 실행 절차를 고쳤으며,
어떻게 검증했는지만 남긴다. 성능 수치는 각 `performance/reports/` 산출물을 원본으로 삼는다.

## 수정 1 — 무효 반복측정 세트가 성공으로 처리되는 문제

- 발견 상황: 이전 밤새 실행의 반복측정 산출물 두 개가 모두 `0/5 valid`였지만 바깥 실행기는 종료 코드 0을 받아 완료로 기록했다.
- 원인: `performance/tools/repeatability.js`가 내부 회차의 유효 개수와 상관없이 정상 종료했다.
- 수정: 요청 회차가 전부 유효할 때만 종료 코드 0을 반환하고, 일부 또는 전부 무효이면 종료 코드 2를 반환하도록 했다.
- 효과: 무인 실행기가 측정값이 없는 세트를 성공으로 오인해 다음 작업으로 넘어가지 않는다.
- 검증: `5/5 → 0`, `4/5 → 2`, `0/5 → 2` 단위 테스트를 추가했고 성능 도구 전체 테스트 241개가 통과했다.
- 관련 발견 항목: `localDocs/perf-findings-tools.md`의 T-34.

## 수정 2 — 유효 표본 1개를 CV 0%로 표시하는 문제

- 발견 상황: 반복측정에서 유효 회차가 하나만 남으면 실제로는 분산을 계산할 수 없는데도 CV 0%로 표시됐다.
- 원인: 표본 수가 2보다 작을 때 표준편차를 0으로 대입했다.
- 수정: 유효 표본이 1개면 표준편차와 CV를 `null`로 유지하고, 콘솔에 `유효 표본 부족(1회)`이라고 표시한다.
- 효과: 표본 부족을 “흔들림이 전혀 없음”으로 잘못 해석하지 않는다.
- 검증: 표본 1개와 2개 경계 단위 테스트를 추가했고 성능 도구 전체 테스트 241개가 통과했다.
- 관련 발견 항목: `localDocs/perf-findings-tools.md`의 T-33.

## 이후 추가 수정

### 수정 3 — 두 성능 실행이 같은 스택에서 동시에 진행되는 문제

- 발견 상황: PID 파일의 셸은 종료됐지만 자식 `bash → node perf-run` 프로세스가 계속 실행됐다. 새로 시작한 `exam-week`와 기존 실행기의 `chat-heavy`가 겹쳤고, 한쪽 데이터셋 복원이 MySQL과 앱을 재시작해 다른 쪽 요청이 `connection refused`가 됐다.
- 원인: 문서에는 “동시에 두 개 이상 돌리지 않는다”는 규칙만 있었고 `perf-run.js` 자체에는 동시 실행 방지가 없었다. PID 파일도 실제 자식 프로세스를 가리키지 않아 살아 있는 실행을 놓쳤다.
- 즉시 조치: 정확한 부모·자식 명령줄을 확인한 뒤 기존 무인 실행기 프로세스 트리만 종료했다. 중복 시간대의 `chat-heavy`, 수동 `exam-week`, `notification-heavy`는 완료로 세지 않는다.
- 수정: `performance/tools/lib/run-lock.js`를 추가해 같은 저장소의 `perf-run`은 하나만 실행되도록 배타 잠금을 건다. 살아 있는 PID의 잠금이면 두 번째 실행을 종료 코드 2로 거부하고, 비정상 종료로 남은 잠금은 PID가 죽은 것을 확인한 뒤 자동 교체한다.
- 효과: 데이터셋 복원, MySQL·앱 재시작, k6 부하가 서로 겹쳐 측정값과 실행 상태를 오염시키는 일을 실행기 수준에서 막는다.
- 검증: 동시 획득 거부, 정상 해제 후 재획득, 죽은 PID의 잠금 복구, 현재 PID 생존 판정 테스트를 추가했다. 전체 245개 테스트가 통과했다.

### 수정 4 — 강제 종료 뒤 고아 `perf-k6`가 남아 후속 실행을 막는 문제

- 발견 상황: 기존 무인 실행기 프로세스 트리를 종료한 뒤 `perf-k6` 컨테이너만 6분 넘게 계속 실행됐다. 새 `chat-heavy`는 같은 컨테이너 이름을 만들 수 없어 Docker 종료 코드 125로 실패했다.
- 원인: k6 컨테이너에는 `--rm`이 있지만 Docker 클라이언트를 프로세스 트리째 강제 종료하면 컨테이너까지 정상 종료 신호가 전달되지 않을 수 있다.
- 즉시 조치: `docker ps`로 이름과 실행 명령을 확인한 뒤, 결과를 회수할 부모가 사라진 `perf-k6` 하나만 중지했다. `--rm` 정책에 따라 컨테이너는 함께 제거됐다.
- 재검증: `chat-heavy`를 다시 실행해 Run #76으로 저장했다. `MEASURED/PASS`, measure 요청 50건, HTTP 오류 0건, WebSocket 오류 0건, Prometheus 인프라 수집 정상이다.

### 수정 5 — 무인 실행기가 실패 뒤에도 다음 실험으로 넘어가는 문제

- 발견 상황: 기존 실행기는 스모크가 즉시 실패해도 다음 시나리오를 계속 실행했고, 반복측정 `0/5 valid`도 당시 종료 코드 0이라 장시간 항목으로 넘어갔다.
- 수정: `performance/tools/overnight-runner.js`를 별도로 만들었다. 각 항목을 한 번에 하나만 실행하고, 종료 후 새 실행 레코드 수·시나리오·`measurementStatus`·`phases.measure` 표본·`infra.flat` 항목을 검증한다. 유효하지 않으면 즉시 중단하며 다음 항목으로 넘어가지 않는다.
- 환경 보호: 스모크가 모두 끝난 뒤 CPU 단일 스레드 벤치가 문서의 정상 범위(4,950~5,050ms)에 들어와야 장시간 비교 측정을 시작한다. 기다리는 동안 측정값을 `reports/idle-cpu-bench.jsonl`에 남긴다.
- 재개 범위: 이미 검증된 `read-heavy`, `peak-hour`, `exam-week`, `chat-heavy`는 완료로 기록하고 `notification-heavy`부터 재개한다.
