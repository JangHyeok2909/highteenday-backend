# 실행 리포트 전면 진단과 리뉴얼 방안

> 기준 시점: 2026-08-25
> 답하는 질문: **"지금 리포트는 왜 읽히지 않는가? 어떻게 바꾸면 병목을 실제로 찾을 수
> 있는가?"**
> 성격: **설계 문서.** 결함 개별 항목은 발견 장부(T-38 ~ T-41)에 있고, 여기는
> **전체 진단 + 재설계안 + 그 안에 대한 자기 리뷰**를 담는다.
> 대상: `tools/lib/report.js` 가 만드는 `reports/runs/<runId>/report.html`
> 짝 문서: [perf-findings-tools.md](perf-findings-tools.md)(T-38~T-41),
> [perf-trust-levels.md](perf-trust-levels.md)(MDE·판정 지표),
> [perf-beginner-guide.md](perf-beginner-guide.md)(리포트 읽는 법)

## 0. 한 줄 결론

**이 리포트는 "값을 보여주는 것"과 "판단을 돕는 것"을 구분하지 않는다.** 165개 지표를
나열하면서 각 값이 좋은지 나쁜지는 화면에 없다. 그래서 읽는 사람은 판단할 수 없고,
판단할 수 없으니 안 읽게 되고, 안 읽으니 진짜 신호도 함께 묻힌다.

고칠 것은 개별 섹션이 아니라 **"화면에 남길 자격"의 기준**이다.

## 1. 사용자 관찰 — 실제로 무엇을 읽고 무엇을 버리는가

이 문서는 추측이 아니라 실사용자 진술에서 출발한다.

> 인간인 내가 이 리포트를 봤을 때 바로 파악 가능한 것들은 **응답시간들과 응답시간의 변화율 /
> 인프라 자원들을 얼마나 사용했고 포화된 건 없는가** 딱 이 정도임. 심지어 변화율은 절대값
> 자체가 작을 경우 **노이즈에도 마치 엄청난 변화처럼 표시되어 점점 무시하게 됨.** 인프라
> 값들은 사용 비율 정도만 확인하게 되고, 표로 여러 개 나와 있는 숫자들의 경우엔 **그 숫자가
> 좋은지/나쁜지에 대해 여기서 아무것도 알리지 않으니** 리뷰하는 입장에서도 모호한 정보들만
> 많은 것 같아 읽히지 않고 **중요하지 않다고 속으로 판단하게 되어버림.**

핵심 세 가지가 여기 다 있다.

1. **실제로 소비되는 정보는 극소수다** — 응답시간, 변화율, 자원 사용률/포화 정도
2. **변화율이 신뢰를 잃었다** — 노이즈를 큰 변화로 표시해 무시 대상이 됨
3. **판정 없는 숫자는 정보가 아니다** — 좋고 나쁨을 모르면 읽지 않게 되고, 그 습관이
   중요한 값까지 덮는다

3번이 가장 중요하다. **읽히지 않는 것은 양의 문제가 아니라 판정 부재의 문제다.**

## 2. 정량 진단 — 문서 구조

`normal-day-2026-08-20T12-20-57` 기준. 괄호 안은 문서 내 위치(%)다.

```
 11%  병목 가설                    ← 답
 12%  Performance Summary          ← 전체 p95 368ms
 13%  지연 분포 / 처리량·검증
 14%  Regression
 32%  Infrastructure Summary  ┐
 32%  자원 포화도             │
 34%  CPU                     │
 37%  Memory                  │
 39%  JVM Heap                │
 41%  GC                      │  ← 인프라 12개 섹션이
 44%  JVM 내부                │     문서의 44% 를 차지
 49%  MySQL                   │
 56%  Redis                   │
 61%  Connection Pool         │
 65%  Network                 │
 66%  Disk                    │
 67%  호스트                  │
 70%  부하 발생기             ┘
 72%  k6 시계열
 76%  효율 (요청당 자원 비용)
 79%  Breakdown ─ 기능별           ← 진짜 원인이 여기
 86%  Breakdown ─ 오퍼레이션별
 90%  Trend
 96%  SLO Thresholds
```

### 2.1 문서 순서가 진단 순서의 정확한 역순이다

권장 읽기 경로(`perf-beginner-guide.md` 및 세션 논의)를 위치에 대보면 이렇다.

| 진단 단계 | 봐야 할 섹션 | 문서 위치 |
|---|---|---:|
| 0. 이 실행을 믿어도 되나 | 포화 판정 | **없음** (§2.2) |
| 1. 무엇이 느린가 | Breakdown 기능별 | **79%** |
| 2. 왜 느린가 | 효율 (요청당 비용) | **76%** |
| 3. 자원이 부족한가 | Infrastructure | 32% |
| 4. 검산 | 병목 가설 | **11%** |

**79% → 76% → 32% → 11%.** 문서를 거슬러 올라가야 한다.

그리고 **가장 자주 "이상 없음"인 섹션이 가장 큰 자리를 차지한다.** 인프라 12개 섹션이
44% 를 쓰는데, 이 실행에서는 CPU 50%·Hikari 30%·Heap 71% 로 전부 여유였다.

### 2.2 포화 판정이 정상일 때는 아예 표시되지 않는다

```
정상 실행(HEADROOM) 리포트에서 "HEADROOM" 검색   →  0건
포화 실행(SATURATED) 리포트에서 검색             →  6건
```

`saturation.js` 는 **포화일 때만** 경고를 띄우도록 설계됐다. 그래서 **정상임을 확인할 방법이
리포트에 없다.** `run.json` 이나 `index.json` 을 열어야 한다.

**이것이 왜 심각한가.** E-46 이 닷새를 소모한 이유가 *"아무도 이 조합을 측정 무효화 조건으로
선언하지 않았다"* 였다. 그래서 포화 감지를 만들었는데, **사람이 보는 화면에서는 절반만 볼 수
있다.** 경고가 없는 것과 "확인했고 정상"은 다르다 — 전자는 판정이 아직 안 붙은 옛 실행일
수도 있다.

### 2.3 "포화"라는 말이 두 가지 뜻으로 쓰인다

| 화면 이름 | 실제 의미 | 이 실행의 값 |
|---|---|---|
| **자원 포화도** (32%) | 자원 사용률 (한계 대비) | CPU 50%, 메모리 65%, Hikari 30% |
| **포화 판정** (`saturation.status`) | **측정 체제** — p95 를 앱 지연으로 읽어도 되는가 | `HEADROOM` |

E-46 의 교훈이 정확히 이 구분이었다 — **지표가 있는가(무결성)** 와 **그 값이 무엇을
뜻하는가(체제)** 는 다른 축이다. 그런데 화면에서 이름이 겹쳤다.

### 2.4 전체 p95 와 기능별 p95 가 연결되지 않는다

```
Performance Summary (12%)   전체 p95   368ms   ▼ -1.9%
Breakdown 기능별  (79%)     comment    2,185ms
```

**5.9배 차이**인데 문서 양 끝에 떨어져 있고 어디에도 나란히 놓이지 않는다.

상단만 보고 *"p95 368ms, 직전 대비 −1.9%, 안정적"* 이라 판단하면 끝난다. 79% 까지 내려가야
comment 가 2.1초라는 걸 안다.

이 단절은 **왜 p99(2,148ms)가 p95(368ms)보다 6배 크고 CV 는 오히려 안정적인지**의 답을
가린다 — 답이 기능별 표에 있는데 리포트가 그 연결을 만들지 않는다.

## 3. 정량 진단 — 개별 결함 (T-38 ~ T-41 요약)

상세는 [perf-findings-tools.md](perf-findings-tools.md).

| ID | 결함 | 사용자에게 보이는 증상 |
|---|---|---|
| **T-38** | `op` 축 `byPhase` 미처리 | read·write 응답시간이 **0** 으로 표시. auth 만 보임 |
| **T-39** | `name` 태그를 붙이고도 수집 안 함 | **어느 API 가 병목인지 알 수 없음** |
| **T-40** | 임계가 세 곳에 하드코딩, 30배 불일치 | "포화 아닌데 왜 병목 1순위인가" |
| **T-41** | `noiseFloor` 가 실측 노이즈의 1/4~1/11 | 노이즈가 `▲ +26.4%` 로 표시 → 무시하게 됨 |

### 3.1 T-38 이 지금 분석을 직접 방해한다

| op | 실제 p95 | 실제 p99 | 요청 수 | 리포트 |
|---|---:|---:|---:|---|
| **read** | **436.9ms** | **2,179ms** | 6,840 | **0** |
| write | 49.2ms | 90.8ms | 602 | **0** |
| auth | 347.6ms | 602.6ms | 154 | 정상 |

전체 p99 가 2,148ms 인데 `read` p99 가 2,179ms 다. **p99 를 만드는 것이 read 라는 결정적
단서를 리포트가 감춘다.** 화면에는 요청의 2% 인 auth 만 보인다.

### 3.2 T-39 — 병목을 좁히는 마지막 단계가 통째로 없다

`comment` 하나에 엔드포인트가 **4개**(목록 조회·작성·수정·삭제) 들어 있다. 성격이 완전히
다른 요청들이 한 값으로 뭉개진다.

그런데 **태그는 이미 붙고 있다** — `config.js:90` 의 `tags(feature, op, name)` 이
`name: 'comment_list'` 를 실어 보낸다. 다만 `thresholds.js` 가 그 축의 서브메트릭을 선언하지
않아 **집계되지 않는다**(수집된 86개 중 `name:` 0개).

**태그 비용은 매 요청 지불하면서 수확을 안 하는 상태다.**

### 3.3 T-41 — 변화율이 신뢰를 잃은 정확한 이유

| 지표 | 실측 표준편차 | `noiseFloor` | 배율 |
|---|---:|---:|---:|
| p95 | 26.7 ~ 57.6ms | 5ms | 5~11배 작음 |
| p99 | 58.6 ~ 104.9ms | 15ms | 4~7배 작음 |
| avg | 2.6 ~ 11.3ms | 3ms | 경계 |

`rules.json` 주석이 막으려던 현상이 그대로 일어난다.

> 상대 변화율만 쓰면 이런 항목이 매 실행마다 회귀로 잡히고, 팀은 곧 그 알림을 무시하게
> 된다(경보 피로).

**장치는 옳게 설계됐고 값만 실측에서 나오지 않았다.**

## 4. 설계 원칙 — 무엇을 기준으로 다시 짜는가

### 원칙 1. 판정할 수 없는 숫자는 기본 화면에서 뺀다

모든 숫자에 셋 중 하나가 붙어야 한다.

| 종류 | 예 | 표시 방식 |
|---|---|---|
| **임계가 있는 지표** | slow query, throttled, hikariPending | 값 + **판정색** + 임계 병기 |
| **비교 대상이 있는 지표** | p95, p99 | 값 + 변화율 (**노이즈 초과 시에만**) |
| **맥락 수치** | `max_connections 200` | **접어둔다** |

현재 MySQL 섹션의 `Threads running avg/max/p95` 3줄은 전부 3~4 다. 상한 대비 의미를 모르면
읽을 이유가 없다. **165개 중 대부분이 이 부류다.**

### 원칙 2. 변화율은 노이즈를 넘을 때만 화살표로 보여준다

```
지금:  평균 93ms  ▲ +26.4%
제안:  평균 93ms  (노이즈 범위 · ±23ms)
```

**숨기지 않는다.** 숨기면 "왜 안 보이지"가 되고, 화살표로 보여주면 무시하게 된다.
**판정 결과 자체를 문자로 표시한다.**

### 원칙 3. 판정 규칙은 한 곳에서만 나온다

```
지금:  rules.json  +  saturation.js  +  regression.js:489   (세 곳, 30배 불일치)
제안:  rules.json 이 유일한 임계 출처. 나머지는 읽기만 한다
```

`rules.json` 주석의 설계 의도 그대로다 — *"코드 수정 없이 이 파일만 고쳐서 기준을 바꾼다."*

### 원칙 4. 문서 순서 = 진단 순서

읽는 순서대로 배치한다. 되돌아가게 만들지 않는다.

### 원칙 5. "이상 없음"은 한 줄로 접는다

정상인 섹션이 지면을 차지하면 안 된다. **비정상만 펼친다.**

## 5. 리뉴얼안 — 화면 구조

```
┌─ ① 이 실행을 믿어도 되나                                    [항상 1줄]
│    측정 MEASURED · 체제 HEADROOM · 도달률 99.5% · 오류 0%
│    ※ 하나라도 벗어나면 붉은 배너로 확대되고 아래를 접는다
│
├─ ② 결과                                                     [항상]
│    p99  2.15s  ▲ +6.7%        ← 판정 지표를 먼저 (p95 아님)
│    p95   368ms  (노이즈 범위)
│    ⚠ 가장 느린 기능: comment 2,185ms — 전체 p95 의 5.9배
│    ⚠ 가장 느린 API : comment_list 2,340ms (1,340건)   ← T-39 해결 시
│
├─ ③ 어디가 느린가                                            [항상]
│    API 별 (T-39) → 기능별 → op 별 → page 별
│    ※ T-38 수정으로 read/write 가 정상 표시
│
├─ ④ 왜 느린가
│    ├ 자원이 부족한가 → 임계 초과 항목만. 없으면 "여유 있음 (12개 정상)" 1줄
│    └ 일이 많은가     → 효율(요청당 비용). queriesPerReq 275 ⚠ (기준 대비 30배)
│
├─ ⑤ 병목 가설                                                [접힘 기본]
│    임계 대비 초과 배율로 점수화. rules.json 을 읽는다
│
└─ ⑥ 전체 지표 165개                                          [접힘]
```

### 5.1 각 변경의 근거

| 변경 | 해결하는 문제 |
|---|---|
| ①을 신설하고 항상 표시 | §2.2 — 정상일 때 확인 불가 |
| ②에서 p99 를 먼저 | MDE 4~6% 로 판정 가능한 유일한 지연 지표 |
| ②의 "가장 느린 기능/API" 한 줄 | §2.4 — 전체 p95 가 감추는 문제 |
| ③을 인프라 앞으로 | §2.1 — 순서 역전 |
| ④의 "임계 초과만" | 원칙 5 — 44% 를 차지하는 정상 섹션 |
| ⑤를 접고 배율 점수로 | T-40 |
| 노이즈 범위 문자 표시 | T-41 |

### 5.2 "자원 포화도" → "자원 사용률" 로 개명

`saturation.status` 만 "포화"라는 말을 쓴다. §2.3 의 용어 충돌 해소.

## 6. 자기 리뷰 — 이 안이 정말 최선인가

여기서 위 안을 스스로 공격한다. **네 가지 약점이 나왔고 그중 두 개는 안을 수정해야 한다.**

### 반론 1. "가장 느린 기능 한 줄"은 잘못된 지목을 할 수 있다 — **유효. 수정한다**

`comment 2,185ms` 를 상단에 올리면 강력한 신호가 된다. 그런데 **요청 수가 적은 기능이
1위가 되면 오도한다.** 예를 들어 30건짜리 관리 API 가 3초라면 1위로 올라오지만 사용자
체감 영향은 거의 없다.

**수정안: 단순 p95 최댓값이 아니라 기여도로 고른다.**

```
기여도 = (기능 p95 − 전체 중앙값) × 요청 수
```

또는 더 단순하게 **"요청 수 상위 80% 안에서 가장 느린 것"** 을 고른다. 이 실행이라면
comment(1,340건) 가 그대로 1위다 — 결과는 같지만 규칙이 방어된다.

### 반론 2. p99 를 먼저 올리는 것이 항상 옳은가 — **부분 유효. 조건을 단다**

p99 를 먼저 두는 근거는 "이 환경에서 MDE 가 4~6% 로 가장 낮다"였다. 그런데 **그건
`normal-day` + RATE=4 라는 한 조합의 실측**이다. 다른 시나리오·다른 운용점에서는 p95 가
더 안정적일 수 있다.

**수정안: 어느 지표를 먼저 둘지 하드코딩하지 않는다.** 실행마다 저장된 반복 세트 CV 가
있으면 그걸로 정하고, 없으면 기본값(p95, p99 나란히)을 쓴다. **"이 실행에서 판정 가능한
최소 개선 폭"을 각 지표 옆에 병기**하는 편이 더 정직하다.

```
p99  2.15s  ▲ +6.7%   (판정 가능 하한 4~6%)
p95   368ms  노이즈 범위 (판정 가능 하한 12~20%)
```

이러면 **왜 p95 를 못 믿는지**가 화면에서 바로 보인다. 지표를 대신 골라주는 것보다 낫다.

### 반론 3. 접기(collapse)가 정보를 숨겨 새 문제를 만들지 않나 — **기각**

*"165개를 접으면 나중에 필요할 때 못 찾는다"* 는 우려는 타당해 보이지만, **지금도 못 찾고
있다.** 사용자 진술이 그 증거다 — *"읽히지 않고 중요하지 않다고 속으로 판단하게 되어버림."*

**접힌 정보는 펼칠 수 있지만, 신뢰를 잃은 정보는 펼쳐 있어도 안 읽힌다.** 접기는 정보를
줄이는 것이 아니라 **읽을 이유가 있는 것과 없는 것을 구분**하는 장치다.

단, 조건이 하나 붙는다 — **접힌 섹션의 요약 줄이 "정상"임을 판정으로 말해야 한다.**
"인프라 (12개 섹션)" 이 아니라 **"자원 여유 있음 — 12개 지표 전부 임계 이하"** 여야 한다.
전자는 접은 것이고 후자는 판정한 것이다.

### 반론 4. 임계를 `rules.json` 으로 일원화하면 게이트와 표시가 결합된다 — **유효. 수정한다**

`rules.json` 은 **게이트(CI 를 실패시킬 기준)** 다. 그런데 표시용 판정색은 게이트보다
느슨해도 된다. 예를 들어 slow query 730건이 게이트를 통과하더라도 화면에서는 주황일 수 있다.

**둘을 한 파일에 두면 "화면에 주황을 띄우려고 게이트 임계를 낮추는" 압력이 생긴다.**
그러면 거짓 FAIL 이 늘고 T-41 의 경보 피로가 재발한다.

**수정안: `rules.json` 에 `gate` 와 `display` 두 단계를 둔다.**

```json
{
  "key": "infra.flat.mysql.slowQueries",
  "gate":    { "fail": { "gt": 2000 } },
  "display": { "warn": { "gt": 300 }, "attention": { "gt": 1000 } }
}
```

**출처는 한 곳으로 유지하되 용도는 분리한다.** 원칙 3 을 지키면서 결합은 피한다.

### 반론 5. 이 리뉴얼이 T-39 에 의존하는가 — **의존한다. 순서를 명시한다**

②와 ③의 "가장 느린 API" 는 T-39 가 해결돼야 나온다. 그리고 T-39 는 **재측정이 필요**하다
(저장된 실행에 `name` 서브메트릭이 없음).

따라서 리뉴얼은 **두 단계로 나뉜다.**

| 단계 | 내용 | 재측정 |
|---|---|---|
| **A** | T-38·T-40·T-41 + 화면 구조 재배치 | **불필요** (재생성만) |
| **B** | T-39(API 축) + ②③에 API 줄 추가 | **필요** |

A 만 해도 §2 의 구조 문제는 전부 해결된다.

## 7. 수정된 최종안

자기 리뷰 결과를 반영한 것이다. 반론 1·2·4 를 수용했다.

```
┌─ ① 이 실행을 믿어도 되나                                    [항상 1줄]
│    측정 MEASURED · 체제 HEADROOM · 도달률 99.5% · 오류 0%
│
├─ ② 결과                                                     [항상]
│    p99  2.15s  ▲ +6.7%      (판정 가능 하한 4~6%)     ← 하한 병기
│    p95   368ms  노이즈 범위  (판정 가능 하한 12~20%)
│    ⚠ 가장 느린 기능: comment 2,185ms  (요청 1,340건, 전체 27%)
│       ※ 요청 수 상위 80% 안에서 선정                   ← 기여도 기준
│
├─ ③ 어디가 느린가                                            [항상]
│    [B단계] API 별 → 기능별 → op 별 → page 별
│
├─ ④ 왜 느린가
│    ├ 자원 — 여유 있음 (12개 지표 전부 임계 이하)      [접힘 + 판정 요약]

├─ ⑤ 병목 가설                                                [접힘]
│    rules.json 의 display 임계 대비 초과 배율로 점수화
│
└─ ⑥ 전체 지표 165개                                          [접힘]
```

`rules.json` 은 `gate` / `display` 두 단계를 갖는다.

## 8. 실행 순서와 비용

| 순서 | 작업 | 파일 | 재생성 | 재측정 |
|---:|---|---|---|---|
| 1 | **T-38** `byPhase` 정규화 | `report.js` | 필요 | 불필요 |
| 2 | **T-41** `noiseFloor` 재산정 + "노이즈 범위" 표시 | `rules.json`, `report.js` | 필요 | 불필요 |
| 3 | **T-40** 임계 일원화(`gate`/`display`) | `rules.json`, `regression.js`, `saturation.js` | 필요 | 불필요 |
| 4 | 화면 구조 재배치 + 접기 | `report.js` | 필요 | 불필요 |
| 5 | **T-39** API 축 | `thresholds.js`, `summary.js`, `report.js` | 필요 | **필요** |

**1~4 는 저장된 레코드만으로 끝난다.** 5 만 재측정을 부른다.

### 8.1 언제 할 것인가

**KI-27 실험 이후를 권한다.** 근거는 셋이다.

1. 지금 `report.js` 를 고치면 Before 세트 재생성이 필요하고, `collect.js --all --force` 는
   **재렌더가 아니라 재판정**이다. 실험 도중에 기준이 흔들린다.
2. 재생성은 현재 **34/73 실행에서 실패한다**(`k6.all` 미보유 옛 스키마). 이것도 함께
   고쳐야 한다.
3. After 세트가 생기면 **T-41 의 `noiseFloor` 를 잡을 근거 데이터가 하나 더 늘어난다.**

**예외 검토 — T-38 은 먼저 할 만하다.** `op` 축이 0 으로 나오면 지금 하려는 병목 분석에서
`read` 가 p99 를 만든다는 사실을 못 본다. Before 4회만 재생성하는 선택지가 있다.

### 8.2 T-39 를 언제 넣을 것인가 — 검토 필요

Before 세트를 다시 재야 API 축이 붙는다. 두 선택지다.

| 안 | 내용 | 대가 |
|---|---|---|
| **지금 Before 재측정** | API 축을 켜고 Before 5회를 다시 잼 | 약 1시간. 기존 Before 4회는 참고용으로 남음 |
| **After 부터 적용** | Before 는 기능별까지만, After 는 API 별까지 | **양쪽 축이 달라 직접 비교 불가** |

**전자를 권한다.** "어느 API 가 좋아졌는가"를 말하려면 Before 에도 그 축이 있어야 한다.
`thresholds.js` 는 지문 대상이 아니라 `scriptVersion` 이 바뀌지 않으므로 **계열도 갈리지
않는다**(`perf-run.js:241` 의 `TRAFFIC_SHAPING_FILES` 에 없음).

## 9. 열어 둔 것

- **접기 기본값을 무엇으로 할 것인가.** 항상 접힘인지, 이상 있을 때만 펼침인지.
  후자가 낫지만 "이상"의 정의가 `display` 임계에 의존한다.
- **`display` 임계를 어디서 가져올 것인가.** 게이트 임계는 SLO 에서 왔지만 표시 임계는
  근거가 약하다. 실측 분포의 백분위를 쓰는 방법이 있으나 표본이 아직 적다.
- **API 축이 서브메트릭 수를 얼마나 늘리는가.** 현재 86개. 엔드포인트 수만큼 증가하고
  k6 메모리·remote-write 부하에 영향을 준다. smoke 로 먼저 확인해야 한다.
- **Trend(최근 10회) 섹션을 유지할 것인가.** 조사 화면(`trends/<계열>.html`)이 생겨
  역할이 겹친다. 단일 실행 리포트에서는 뺄 수 있다.
