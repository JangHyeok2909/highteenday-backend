## 0. 결론 — 네 문장

**첫째, 순서를 정하는 기준이 바뀌었다.** 당근 마감이 있을 때는 "이번 심사에 값이 매겨지는가"가
기준이었다. 30주가 생기면 다섯 항목을 전부 할 수 있으므로 그 기준은 아무것도 못 거른다.
남는 기준은 **늦게 시작하면 그만큼 결과가 줄어드는 일인가**다.

**둘째, 그 기준으로 1순위는 운영 시뮬레이션 상시 가동이다.** 오늘 켜면 2027년 3월까지
약 6개월치 기록이 쌓이고, 3개월 뒤에 켜면 3개월치만 쌓인다. 되돌릴 수 없다.
**데이터가 자라야 생기는 고장은 주입으로 못 만들기 때문이다.**

**셋째, 원고 작업을 3월에 몰아넣지 않는다.** 당근은 **서류에서 떨어졌다.** 서류 통과의 유일한
도구가 한 번 실패했는데 원인을 모르므로, 3월에 4주 안에 고치면 고친 결과를 검증할 시간이 없다.
**원고 진단을 9월에 하고, 작업이 하나 끝날 때마다 갱신한다.**

**넷째, 가장 큰 미확인은 탈락 원인이다.** 연차 필터·TO·미충족 항목·원고 중 무엇이었는지
표본 1건으로는 구분할 수 없다. **구분이 안 되므로 경력 축적과 원고 수정을 둘 다 한다.**
둘은 시간을 두고 경쟁하지 않는다. 6장 참조.

## 2. 순서를 정한 기준

마감이 없으므로 "무엇을 먼저 하는가"는 **시작을 늦추면 결과가 줄어드는가**로 정한다.

| 항목 | 늦게 시작하면 | 되돌릴 수 있나 |
|---|---|---|
| 운영 시뮬레이션 상시 가동 | 늦은 개월 수만큼 기록이 그대로 줄어듦 | 못 함 |
| 오픈소스 공개 | 공개일부터 외부 반응까지 몇 달. 늦은 만큼 반응 기간이 줄어듦 | 못 함 |
| 다중 인스턴스 전환 | 구축은 몇 주. 그 위에서 운영한 기간이 줄어듦 | 절반만 |
| 장애 테스트 마무리 | 며칠이면 끝남. 결과 동일 | 함 |
| 멱등 API 전환 | 이틀이면 끝남. 결과 동일 | 함 |

**[판단] "데이터가 자라야 생기는 고장은 주입할 수 없다"가 이 표의 근거다.** 지금까지 한 장애
테스트는 Redis를 20초 멈추는 것처럼 전부 주입한 고장이다. 반면 테이블 행이 6개월 쌓여 인덱스
없는 쿼리가 느려지는 것, Redis 키가 삭제되지 않고 누적되어 메모리가 차는 것, 로그가 디스크를
채우는 것, 데이터가 이미 들어 있는 상태에서 마이그레이션을 돌려야 하는 것은 주입으로 못 만든다.
시간이 지나야 생긴다. 운영 경험이라 부르는 것의 상당 부분이 이쪽이다.

#### T-01. 장애 실험 before/after 표 완성 — 상태: 미착수

**무엇을** — R-01(Redis stop vs pause)과 R-03(MySQL slow) 두 실험을 수정 전후 코드에서 각각
돌려 한 표에 넣는다.

**왜** — 관측과 수정이 이미 따로 존재하는데 한 표로 묶이지 않았다. smoke에서 Redis를 20초 pause
했을 때 오류율 0%, p95 19.5초, HikariCP active 10 / pending 8, 헬스 UNREACHABLE을 관측했다.
오류가 0%인데 p95가 19.5초라는 것은 요청이 실패하지 않고 매달렸다는 뜻이고, pending 8은 Redis
장애가 DB 커넥션 풀 고갈로 전파됐다는 뜻이다. 그 뒤 세 커밋이 이것을 고쳤다. `2f1c030`이 Lettuce
명령 타임아웃을 기본 60초에서 100ms로 지정했고, `de0d207`이 인프라 실패를 401·500과 분리해
503으로 돌려주며, `4062222`가 Redis 폴백이 돈 횟수를 메서드별로 센다. **표가 없으면 이 셋이
무엇을 바꿨는지 숫자로 말할 수 없다.**

**어디를** — `performance/resilience/faults/redis-crash.json`, `redis-slow.json`, `mysql-slow.json`.
기존 실행 원자료는 `performance/resilience/reports/` 아래 6개 디렉터리에 있다.

**먼저 할 것** — `reports/` 의 실행 6건 중 어느 것이 수정 전이고 어느 것이 수정 후인지 실행
시각과 커밋 시각을 대조해 가른다. 수정 커밋이 전부 2026-09-14이므로 같은 날 실행들이 섞여 있다.

**완료 기준** — 장애 유형별로 수정 전후의 오류율·p95·Hikari pending·폴백 횟수·헬스 상태가 한
표에 들어가고, 각 칸이 어느 실행 디렉터리에서 나왔는지 적혀 있다.

**하지 않는 것** — R-04~R-07 완주. 이 표가 답하려는 질문("장애가 나면 어떻게 되고 무엇을
고쳤나")은 두 실험으로 답해진다. 나머지는 T-07이 켜진 뒤 상시 환경에서 훨씬 싸게 나온다.

#### T-02. 멱등 API 전환 — 상태: 미착수

**무엇을** — [TODO.md](TODO.md) 1번의 토글 3개를 "지금 상태를 뒤집어라"에서 "이 상태를 원한다"로

**왜** — **T-07을 켜기 전에 끝나야 한다.** 상시 트래픽에 장애를 섞으면 타임아웃이 나고 클라이언트가

도착하면 방금 누른 좋아요가 취소된다. 스크랩(`ScrapService.java:58`)과 댓글 반응도 같은 모양이다.
**이 상태로 6개월을 돌리면 오염된 데이터가 6개월치 쌓이고, 그 위에서 뽑은 수치는 못 쓴다.**

**완료 기준** — 같은 요청을 두 번 보냈을 때 DB에 남는 최종 상태가 한 번 보냈을 때와 같다는 것을
테스트가 확인한다. 그리고 R-08 실행에서 재시도가 실제로 발생한 상황의 상태 수렴이 관측된다.

**얻는 것** — "고장을 재현하고, 고치고, 같은 방법으로 확인했다" 구조. 장애 주입 중 타임아웃 →
재시도 → 상태 뒤집힘 관측 → 계약 변경 → 같은 주입에서 수렴 확인이 한 줄로 이어진다.

몇 달 1대로 돌린 뒤 전환하면 결과가 **"돌아가는 시스템을 무중단으로 다중 인스턴스로 바꿨고 그
과정에서 무엇이 깨졌다"**가 된다. [판단] 후자가 면접 소재로 훨씬 강하고, 같은 트래픽 모델에서
전환 전후 데이터가 나온다는 실질적 이점도 있다. T-10 참조.

**왜 지금인가** — 2장의 기준에 따라 이 항목만 시작 시점이 결과 크기를 직접 정한다. 10월에 켜면
2027년 3월까지 약 6개월, 1월에 켜면 3개월이다.

**격리 규칙 (P0 제약)** — `performance/` 와 별도 compose 프로젝트·볼륨을 쓴다. 측정은 데이터가

같이 돌리면 성능 기준선이 깨진다. 세부는 [ops-simulation-plan.md](ops-simulation-plan.md) 5장.

**선행** — T-02(멱등), T-06(알림).
