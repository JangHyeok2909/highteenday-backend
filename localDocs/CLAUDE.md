# localDocs 작업 규칙

이 디렉토리는 성능 테스트 시스템 리뷰의 **발견 장부**이자 작업 백로그다.
발견 사항(`T-##` 도구 / `S-##` 스크립트 / `E-##` 환경)을 손댈 때 아래 규칙을 따른다.

> **이 장부는 측정 시스템의 결함만 다룬다.** 성능 테스트를 돌리다 **애플리케이션 자체의
> 결함**(정합성, 기능 오류)을 발견했다면 여기가 아니라 저장소의
> `docs/KNOWN-ISSUES.md`에 `KI-nn`으로 등록한다. 분량이 필요하면 `docs/defects/`에 상세
> 문서를 둔다. 성능 병목은 `performance/bottlenecks/`다.
> 셋의 경계: **틀린 것**(KNOWN-ISSUES) / **느린 것**(bottlenecks) / **잘못 재는 것**(이 장부).

---

## 발견 사항을 해결하면 반드시 기록한다

발견 사항 하나를 수정했으면 — 커밋 여부와 무관하게 — 해당 항목의
**제목 줄 `상태:` 를 갱신**하고, **제목 바로 아래 인용블록(`>`)** 에
해결 기록을 남긴다. 코드만 고치고 문서를 그대로 두지 않는다.

인용블록에 담을 내용:

1. **무엇을 어떻게 고쳤나** — 변경한 파일·함수와 접근 방식
2. **고민한 대안과 버린 이유** — 다른 선택지를 왜 안 골랐는지. *이게 이 기록의 핵심이다.*
   나중에 같은 자리를 다시 볼 때 "왜 이렇게 했지"에 답할 수 있어야 한다
3. **어떻게 검증했나** — 테스트, 재분석 결과, 실측 수치 등 근거
4. **남은 부작용 / 후속 작업** — 예: 저장된 과거 런은 재판정 필요

3·4번은 해당 없으면 생략해도 되지만, 1·2번은 항상 쓴다.

**커밋 여부는 적지 않는다.** 이 장부가 답해야 하는 질문은 "고쳤는가"이지
"올렸는가"가 아니다. 커밋 여부는 git이 이미 알고 있어 장부가 중복으로 들고 있을
이유가 없고, 실제로 그렇게 해 본 결과 이미 커밋된 항목이 계속 `미커밋`으로 남아
**장부 쪽이 틀린 정보를 들고 있게 됐다.** 어느 커밋에 들어갔는지 알아야 하면
`git log -S '<바뀐 코드 조각>' -- <경로>`로 언제든 찾을 수 있다.

### 형식 예시

기존 T-01 기록에 **2번(고민한 대안과 버린 이유)을 덧붙여 본** 예시다. 실제 T-01에는
아직 그 부분이 없다 — 앞으로는 이 수준까지 적는다.

```markdown
### T-01. infra 규칙 25/32개가 한 번도 작동한 적 없음 — 상태: **해결** (2026-08-05)
> `pick()`을 "남은 경로 전체가 키로 존재하면 우선" 방식으로 수정. 회귀 테스트 추가
> (tools/test/regression.test.js). **대안이었던 `infra.flat` 자체를 중첩 객체로 펴는 안은
> 버렸다** — collect.js가 저장한 과거 런 23개의 스키마가 전부 깨져 재수집이 필요해지기 때문.
> 읽는 쪽만 고치는 게 저장 포맷 호환을 지킨다. 실측 검증: 문제의 normal-day 런 재분석 시
> skipped 25→0, throttling·hikari 게이트 6건 FAIL 정상 발동.
> **저장된 과거 런의 판정은 여전히 옛 결과** — 필요 시
> `node tools/collect.js --all --force --no-wait`로 재판정.
```

## 조사가 커지면 별도 문서로 뺀다

한 발견 항목의 조사가 **실험 여러 건 + 기각된 가설 여러 개** 규모가 되면 장부 항목 하나에
담지 않는다. `investigations/perf-<주제>.md` 로 조사 기록을 분리하고, 장부에는 이것만 남긴다.
(발견 장부 자체는 `findings/` 에 있다. 디렉터리 계열은 `README.md` 의 "문서들의 관계" 참고.)

1. 무엇이 문제인가 (한두 문단 + 핵심 수치 표)
2. 왜 이 등급인가 — 실무에 어떤 제약이 생기는가
3. 현재 결론과 남은 후보 (요약)
4. 해결 전까지의 운용 규칙 (요약)
5. **상세 문서 링크**

분리 기준은 분량이 아니라 **읽는 목적**이다. 장부는 "지금 무엇을 믿을 수 없나"를 훑는
곳이고, 조사 기록은 "이걸 이어서 파려면 무엇을 이미 해 봤나"를 찾는 곳이다. 두 목적이 한
항목에 섞이면 양쪽 다 못 읽는다.

분리했으면 [README.md](README.md) 의 **문서 지도**에 한 줄 추가하고, 옮긴 내용을 가리키던
다른 문서의 링크를 새 위치로 고친다. 발견 ID(`E-46` 등)는 그대로 두어 기존 상호참조가
깨지지 않게 한다.

**선례**: E-46(세션 간 성능 편차) → [perf-session-drift.md](../performance/docs/investigations/perf-session-drift.md)

## 상태 값

`localDocs/README.md`의 상태 규칙을 그대로 따른다.

- **미해결** — 발견만 된 상태 (초기값)
- **수정중** — 브랜치에서 작업 중
- **해결** — 수정 + (P0는) 테스트 완료. 날짜를 병기
- **보류** — 의도적으로 안 고치기로 결정. **사유를 반드시 병기**

`보류`도 해결과 똑같이 인용블록에 이유를 적는다. "왜 안 고치기로 했나"가
"어떻게 고쳤나"만큼 중요한 기록이다.

## 함께 갱신할 것

- 발견 사항의 상태를 바꿨으면 [perf-review-summary.md](../performance/docs/planning/perf-review-summary.md)의
  P0/P1/P2 실행 계획에서 해당 항목 상태도 같이 맞춘다 — 두 문서가 어긋나면
  백로그로서 신뢰를 잃는다
- 학습 장부([perf-mastery-checklist.md](guides/perf-mastery-checklist.md))의 **결정 안건**에서
  나온 결정으로 상태가 바뀐 경우, 인용블록에 어느 안건에서 나온 결정인지 적는다

## 하지 말 것

- 리뷰 시점(2026-08-05) 기준으로 적힌 **라인 번호를 임의로 갱신하지 않는다.**
  코드가 바뀌어 어긋나면 인용블록에 새 위치를 적을 것 — 원문은 발견 당시의 기록이다
- 해결 기록을 요약해서 짧게 줄이지 않는다. 이 문서는 분량보다 **재구성 가능성**이 목적이다

## 측정 도구를 고쳤으면 smoke 로 먼저 확인한다

`performance/tools/`·`scripts/lib/`·`scenarios/` 를 고친 뒤에는 **긴 실행을 걸기 전에
3~5분짜리 smoke 실행으로 배관을 확인한다.**

```bash
node tools/perf-run.js scripts/posts.js --dataset smoke --vus 5 --duration 1m --loadgen docker
```

확인 대상은 성능이 아니라 **도구가 망가지지 않았는지**다.

- 지표가 채워지는가 (`measurementStatus`, `infra.flat` 항목 수)
- 값의 범위가 맞는가 (`phases.measure` 가 비어 있지 않은가)
- 게이트와 리포트 생성이 끝까지 도는가

**왜 규칙이 필요한가.** S-26(RPS 분모)·T-31(범위 혼재)은 산술·배관 오류라 부하 테스트가
필요 없었는데도 2시간 반짜리 실행에 검증을 묶어 두고 있었다. 실제로는 저장된 레코드에
새 코드 경로를 적용해 보는 것만으로 몇 초 안에 확인됐다.

smoke 로 충분한 이유: 도구 결함은 **데이터 규모와 무관**하다. 반대로 성능 판정은 smoke 로
할 수 없다 — 게시글 50건은 전부 버퍼풀에 들어가 medium(10,000건)과 다른 병목이 나온다.
**smoke 는 도구 확인용, 판정은 medium 이상.**

`README.md` 실행 순서의 "2. 스모크 확인"이 이미 이 단계인데, 도구를 고칠 때는 밟지 않고
있었다.
