> "왜 그렇게 했나 → 트레이드오프는 → 규모가 커지면 → 장애가 나면"으로 파고든다.

## 0. 이 프로젝트를 한 문단으로 말하기 (반드시 준비)

면접은 "프로젝트 소개해주세요"로 시작한다. 30초 버전과 2분 버전을 외워둘 것.

**30초 버전 예시:**
"고등학생 익명 커뮤니티 백엔드입니다. Spring Boot + MySQL + Redis로 게시판·댓글·좋아요·실시간 채팅·알림을 만들었고, 실제 배포해 운영 중입니다. 이 프로젝트에서 가장 공들인 부분은 **성능을 감으로 말하지 않는 것**입니다. k6 + Prometheus 기반 부하 테스트 파이프라인을 직접 만들어 23회 이상 측정을 기록했고, 그 과정에서 스크랩 토글 동시성 버그로 인한 장애, 커넥션 풀 고갈, 요청당 900개 쿼리가 나가는 N+1을 **수치로** 찾아냈습니다."

**말하지 말아야 할 것:** "AI 도구를 활용해서" 같은 말로 시작하지 말 것. 도구 얘기가 아니라 판단 얘기를 할 것.
(AI 활용 여부를 직접 물으면 정직하게: "코드 생성에 활용했고, 그래서 오히려 검증 체계 — 테스트, 부하 측정, 발견 장부 — 를 더 엄격하게 만들었다. 판정 로직 110KB에 테스트가 0개인 걸 발견하고 직접 단위테스트를 넣은 게 그 예다"라고 답하는 게 강하다.)

## 1. 개요·설계 결정

### Q1. 왜 이 기술 스택(Spring Boot / MySQL / Redis)을 골랐나요?
- [의도] 스택을 "배워서"가 아니라 "문제에 맞춰" 골랐는지.
- [뼈대] 커뮤니티는 읽기:쓰기 비율이 극단적으로 읽기 우세(우리 워크로드 모델 기준 브라우징 40% vs 글쓰기 5%) → RDB에 정규화된 원본 + Redis에 읽기 경로 캐시/카운터 버퍼. 트랜잭션과 유니크 제약이 필요한 도메인(반응, 스크랩, 채팅 멱등성)이 많아 RDBMS가 원본이어야 했다.
- [꼬리] "MySQL 대신 PostgreSQL이었다면?" / "Redis가 없었다면 어떤 문제가 생기나?"

### Q2. 게시글에 좋아요 수·댓글 수를 컬럼으로 갖고 있다고 했는데(비정규화), 왜 그렇게 했고 무엇을 포기했나요?
- [의도] 정규화/비정규화 트레이드오프를 실제로 겪었는지.
- [뼈대] 목록 조회가 최다 빈도 경로인데 매번 COUNT 조인을 하면 목록 한 페이지에 N번의 집계가 붙는다. Post에 likeCount/commentCount 등 5개 카운터를 두고 목록은 단일 테이블 + DTO 프로젝션으로 처리(User 조인조차 없앰 — 닉네임도 작성 시점 스냅샷). **포기한 것: 쓰기 시 정합성 책임.** 그래서 증감(+1/-1) 대신 "토글 후 실제 COUNT를 다시 세서 덮어쓰기"로 드리프트를 구조적으로 차단했고, 검증용 정합성 체크 엔드포인트도 뒀다.
- [꼬리] "그 카운터 컬럼이 핫로우 락 경합의 원인이 되지는 않나?" → **된다.** 인기글 하나에 반응이 몰리면 같은 행 UPDATE 경합. 부하 테스트 시드 과정(동시성 5)에서 실제 데드락을 재현해 병목 카탈로그(BTL-003)에 "확정"으로 기록했고, 개선 후보로 ① Redis 버퍼링+주기 flush(조회수는 이미 이 방식) ② `SET like_count = like_count + 1` 원자 UPDATE ③ 카운터 테이블 분리를 비교 실험(EXP-003)으로 설계해둔 상태다. — 이 답이 나오면 면접관은 멈춘다.

### Q3. 소프트 삭제를 쓴 이유는? 단점은?
- [뼈대] 익명 커뮤니티 특성상 신고/복구/증거 보존 요구 + 스크랩·반응·채팅 참여는 "취소했다가 되살리는" 도메인이라 행을 지우면 안 됨(재참여 시 이전 대화 가리기 등 상태가 행에 붙어 있음). 단점: 모든 조회 쿼리에 is_valid 필터를 강제해야 하고 누락하면 삭제 데이터 노출. 기본 findById 자체를 필터 포함 쿼리로 오버라이드해 실수 표면적을 줄였다. Hibernate @Where를 안 쓴 이유: "나간 참여자를 찾아 되살리는" 예외 경로가 있어 전역 필터가 오히려 방해.
- [꼬리] "데이터가 계속 쌓이면?" → 파티셔닝/아카이빙은 미래 과제로 인정.

### Q4. 익명 커뮤니티인데 익명성은 어떻게 보장하나요?
- [뼈대] 응답 DTO 계층에서 차단: 익명 글은 userId=null·작성자 "익명", 댓글은 등장 순서대로 "익명N"(글쓴이는 "익명(글쓴이)" 고정) 매핑을 서버에서 계산. 원본 작성자는 DB에만 있고 응답으로 안 나간다.
- [꼬리] "DTO에서 막는 방식의 약점은?" → 새 DTO를 만들 때 강제되지 않는 규약이라는 것. 실제로 익명 글에서 profileUrl이 새는 지점을 자체 점검에서 발견했고, 이런 게 정책을 계층 규약이 아니라 타입/테스트로 강제해야 하는 이유라고 답하면 됨.

## 2. 성능 — 이 프로젝트의 최대 차별점. 여기서 승부한다

### Q5. "부하 테스트를 했다"고 썼는데, 구체적으로 뭘 어떻게 측정했나요?
- [의도] 대부분의 지원자는 "k6 돌려봤다" 수준. 파이프라인·기준선·회귀 개념이 나오면 급이 달라진다.
- [뼈대] 3층 구조로 설명:
  1. **부하 정의** — 기능별 스크립트 13개 + 이를 가중치로 조합한 워크로드 시나리오 16개(normal-day, peak-hour, spike, stress, soak, breakpoint…). 사용자 여정(브라우징 40%·반응 15%·글쓰기 5%…) 단위로 모델링, 인기글 쏠림은 Zipf 분포로 재현.
  2. **수집** — k6 결과(p95/p99/RPS/TPS/오류율)와 Prometheus 인프라 지표(CPU throttling, heap/GC, HikariCP pending, MySQL slow query/QPS, Redis hit ratio)를 실행 단위로 합쳐 JSON+HTML 리포트로 저장. 데이터셋 규모도 5단계 프로파일(2만~500만 행)로 통제.
  3. **판정** — 직전 성공 실행을 기준선으로 32개 규칙(p95 +20% FAIL, 오류율 절대 1%, 커넥션 풀 타임아웃 0건 등)으로 자동 회귀 판정. 오탐 방지 장치 5개(방향성/노이즈 플로어/기준선 하한/절대 게이트/스크립트 버전 지문).
- [꼬리] Q6~Q12 전부.

### Q6. 그래서 결과가 어땠나요? 숫자로 말해보세요.
- [의도] 측정을 "했다"와 "읽을 줄 안다"의 차이.
- [뼈대] 대비되는 두 실행을 외워둘 것:
  - **소규모(100명/500글, 15VU)**: p95 101ms, 오류 0%, CPU 12%, 풀 대기 0 — 전 SLO 통과.
  - **대규모(1만 명/10만 글/반응 100만, 200VU)**: **p95 60초(타임아웃 검열값), 오류율 55.8%로 붕괴.** 원인 체인이 지표에 그대로: 커넥션 풀 10개에 대기 스레드 205개, 풀 획득 p95가 타임아웃값 30초 그 자체, CPU throttling ~100%, **요청당 평균 903개 쿼리**(N+1), 요청 1000건당 slow query 115건.
  - 즉 "정상일 때 얼마나 좋은가"가 아니라 **"어디서 어떻게 무너지는가"를 재현 가능하게 만들었다**는 게 핵심 메시지.
- [꼬리] "그 병목을 고쳤나요?" → 정직하게: 병목 카탈로그(12건)와 가설-실험 설계(5건)까지가 현재이고, 수정은 "기준선 실험 없이 고치지 않는다"는 원칙으로 순서를 지키는 중이다. 이미 고친 것: 스크랩/반응 upsert 전환, 시드 데이터 정합. (Q2 꼬리의 BTL-003 답과 연결)

### Q7. Tomcat 스레드가 400인데 DB 커넥션이 10개면 어떻게 되나요? (혹은: 커넥션 풀 크기는 어떻게 정하나요?)
- [의도] 리소스 불균형에 대한 감각.
- [뼈대] 우리 실측이 그 답이다: 400개 스레드가 들어와 10개 풀 앞에 줄을 서고, 풀 대기 205 / 획득 타임아웃 5,316건 / 대기 시간이 그대로 응답 시간에 가산 → p99 급등. 스레드를 늘리는 게 아니라 **병목 뒤 자원(DB)의 처리량에 앞 계층을 맞춰야** 한다 — Tomcat을 줄여 대기를 accept 큐로 옮기거나 풀을 코어 수 기반으로 조정. 풀 10은 실수로 둔 게 아니라 "가설(BTL-002)을 실험(EXP-002)으로 증명하기 전까지 유지"한 통제 변수였다는 것까지 말하면 좋다.
- [꼬리] "풀을 그냥 100으로 늘리면?" → DB 쪽 컨텍스트 스위칭·락 경합으로 오히려 악화 가능. HikariCP 권장 공식(core*2+spindle)과 "늘리기 전에 요청당 쿼리 수 903을 먼저 줄이는 게 순서" 언급.

### Q8. p95, p99를 보는 이유는? 평균은 왜 안 보나요?
- [뼈대] 평균은 꼬리를 숨긴다. 우리 실측에서 avg 80ms인 기능의 p99가 1.9초였던 예가 있다. 사용자 경험은 꼬리가 결정하고, 꼬리는 포화(풀 대기, GC, throttling)의 조기 신호다. 추가로 **검열(censoring) 함정**도 안다고 보여줄 것: p95가 60000ms로 찍히면 그건 측정값이 아니라 타임아웃 상한이다 — 이후 얼마나 더 나빠져도 지표가 안 움직이므로 회귀 판정이 무력화된다. 이걸 발견 장부에 미해결 결함으로 기록해뒀다.
- [꼬리] "오류율 55%인데 응답한 45%의 p95는 의미가 있나?" → 생존 편향. 그래서 오류율을 별도 절대 게이트(1%)로 둔다.

### Q9. 부하 테스트 결과를 언제 "믿으면 안 되는지" 아나요?
- [의도] 시니어가 진짜 궁금해하는 것. 이 프로젝트의 최강 소재 — **스스로 자기 측정 시스템의 결함 92건을 장부로 만들었다.**
- [뼈대] 사례 3개만 골라 말한다:
  1. **check는 100%인데 오류율 55%** — 검증이 상태코드만 느슨하게 봐서 400 응답의 응답시간을 재고 있었다. "측정 신뢰성 경고"를 병목 힌트 최상위 규칙으로 넣었다.
  2. **closed 모델의 좌표 누락(coordinated omission)** — VU가 응답을 기다리는 동안 부하가 저절로 줄어서, 시스템이 무너질수록 오히려 TPS가 정상으로 보였다. 한계 탐색용 breakpoint 시나리오만 arrival-rate(open) 모델로 분리했다.
  3. **비교 가능성** — 부하 스크립트가 바뀌면 이전 실행과 비교 자체가 무효라서, 스크립트 해시를 실행마다 기록하고 불일치 시 FAIL을 WARN으로 강등한다. 컨테이너 메모리 한계를 바꾼 커밋에는 "이 이후 실행은 이전과 비교 불가"를 명시했다.
- [꼬리] "측정 시스템 자체는 어떻게 검증하나?" → 판정 로직에 테스트가 0개인 걸 발견하고 단위테스트 28개를 넣었다 + 32개 규칙 중 25개가 키 조회 버그로 한 번도 발동한 적 없었다는 걸 스스로 찾아 고친 이야기.

### Q10. 조회수는 어떻게 처리하나요? 조회수 어뷰징은?
- [뼈대] 쓰기 폭을 Redis로 흡수: `SETNX(유저:글, TTL 1h)`로 중복 조회 차단 → 통과 시 `INCR` 버퍼 → 60초 스케줄러가 `GETDEL`(원자적 읽기+삭제)로 드레인해 DB에 일괄 반영. DB UPDATE 경합이 초당 수백 회에서 글당 분당 1회로 줄어든다. 유실 허용 범위(최대 1분치)는 조회수라는 도메인 특성상 수용.
- [꼬리] "Redis가 죽으면 조회수는?" → 유실 수용 + 서비스는 계속(아래 Q13). / "스케줄러가 여러 인스턴스면?" → GETDEL이 원자적이라 이중 반영은 없지만, 스케줄 중복 실행 제어(분산락/리더 선출)는 현재 단일 인스턴스 전제 — 한계로 인정.

### Q11. 인기글 산정은 어떻게 하나요?
- [뼈대] Redis Sorted Set. 반응/댓글/스크랩 이벤트마다 점수 재계산해 ZADD, 5분 스케줄러가 상위 50개를 재채점(시간 감쇠 반영). 점수 = 가중합(좋아요 5, 댓글 3, 스크랩 2, 조회 1, 싫어요 -2)에 로그 스케일을 씌우고 `(경과시간+2)^1.5`로 나눠 최신성 반영 — Reddit/HN 랭킹 계열. 좋아요 10개 미만 컷. **Redis가 비면 DB 폴백 테이블**(스케줄러가 상위권을 주기 저장)에서 서빙.
- [꼬리] "왜 로그 스케일?" → 좋아요 1000짜리가 100짜리의 10배 좋은 글은 아니라서. / "감쇠 지수 1.5는 어떻게 정했나?" → 휴리스틱임을 인정하고, 실험으로 조정할 값이라고.

### Q12. 이 측정 시스템을 만들면서 가장 크게 배운 것은?
- [의도] 회고 능력.
- [뼈대] 후보: "측정 코드도 프로덕션 코드다 — 판정 로직에 버그가 있으면 좋은 데이터가 있어도 결론이 틀린다(25개 규칙 상시 미발동 사건)" / "부하 테스트는 성능보다 먼저 **기능 버그**를 찾아낸다(장애급 버그 5건이 부하에서 발견됨)" / "한 번에 변수 하나 — 스크립트·빌드·스키마가 같은 날 바뀌자 61개 실행을 기준선에서 제외해야 했다".

## 3. 동시성·정합성 — 두 번째 승부처

### Q13. 동시성 문제를 실제로 겪어본 적 있나요? (또는: 좋아요 따닥 누르면 어떻게 되나요?)
- [의도] 교과서 답(synchronized, 낙관락)인지 실전 답인지.
- [뼈대] **스크랩 토글 사건**을 스토리로: 같은 유저의 동시 토글 2건이 check-then-act 사이를 뚫고 둘 다 INSERT → 중복 행 → 이후 단건 조회가 NonUniqueResult로 터져 **게시글 상세가 영구 장애**. 수정은 3단계: ① 중복 행 정리(유효 행 우선 보존) → ② 카운터 백필 → ③ UNIQUE(user, post) 제약. 그리고 애플리케이션은 조회-후-저장 대신 **`INSERT ... ON DUPLICATE KEY UPDATE` 단일 문장**으로. affected rows(1=신규, 2=갱신)로 신규 여부를 판정해 이벤트 중복 발행도 막았다.
- [꼬리] "예외를 잡아서 복구하면 안 되나?" → **JPA에서는 성립하지 않는다.** flush가 제약 위반으로 실패하면 트랜잭션이 rollback-only가 되어 같은 트랜잭션에서의 복구가 커밋 시점에 폐기된다. 실제로 그 방식이 코드에 있었고 부하에서 `don't flush the Session after an exception` 오류로 죽는 걸 확인했다. 단위테스트가 못 잡은 이유까지: repository를 모킹해 영속성 컨텍스트 없이 돌리니 깨진 복구가 정상으로 보였다 — 서비스 테스트에서 DB를 모킹하지 않는다는 규칙이 생긴 배경.

### Q14. 락은 안 썼나요? 왜요?
- [뼈대] 비관락·낙관락 모두 안 썼다. 우리 경합은 전부 "같은 (user, resource) 쌍의 중복 생성" 유형이라 **DB 유니크 제약 + upsert + 사후 COUNT 동기화**가 락 없이 정확성을 보장하고 대기도 없다. 채팅도 동일 패턴: 1:1방 중복 생성은 pairKey UNIQUE로 승자 결정, 메시지 재전송은 clientMsgId UNIQUE로 멱등 처리.
- [꼬리] "낙관락이 맞는 경우는?" / "재고 차감이라면?" → 개념 문서의 락 섹션으로 대비.

### Q15. 이벤트를 쓴 곳이 있다던데(알림), 왜 동기 호출이 아니라 이벤트인가요?
- [뼈대] 알림 저장 실패가 댓글 작성을 실패시키면 안 됨(부수 기능이 핵심 기능을 물귀신). `AFTER_COMMIT` 리스너 + 알림 저장은 `REQUIRES_NEW` 트랜잭션으로 격리 → 원 트랜잭션 롤백 시 유령 알림도, 알림 실패 시 본 작업 롤백도 없다. 저장 후 STOMP로 실시간 푸시.
- [꼬리] "AFTER_COMMIT 리스너에서 예외가 나면?" → 이미 커밋된 뒤라 본 작업은 안전, 알림만 유실 — 재시도 큐가 없다는 게 현재 한계. / "Kafka 같은 메시지 브로커로 바꾼다면 뭐가 달라지나?" → 프로세스 내 이벤트는 서버 재시작 시 유실, 브로커는 영속/재시도/컨슈머 확장 — 지금 규모에선 과했다는 판단까지.

### Q16. 채팅 메시지가 중복 전송되면? 순서는? 읽음 처리는?
- [뼈대] 멱등성 2중 방어: clientMsgId(클라이언트 UUID) 사전 조회 + UNIQUE 충돌 catch 시 먼저 저장된 쪽 반환 — at-least-once 재전송을 서버에서 exactly-once로 수렴. 순서는 auto-increment PK 기준(단일 DB라 전역 순서 보장). 읽음 위치는 **단조 증가만 허용** — 네트워크로 늦게 도착한 과거 읽음 요청이 상태를 되돌리지 못하게. 미읽음 수는 참여자들의 읽음 위치를 정렬 배열로 만들어 메시지당 이진 탐색 O(log M), 방 목록은 GROUP BY 집계 쿼리 1방.
- [꼬리] "서버가 2대가 되면 채팅은?" → Q20.

## 4. 캐시·Redis

### Q17. 뭘 캐싱했고, 무효화는 어떻게 하나요?
- [뼈대] 게시판 목록 처음 5페이지(최신순만) — 전체 트래픽이 몰리는 곳만. 구조는 2단: 게시판별 글 ID 리스트(최대 50개, TTL 60분) + 글별 미리보기 JSON(TTL 30분), 조회는 MGET 벌크 + miss만 DB IN 조회로 채움. 무효화는 글 생성/삭제 시 리스트 폐기, 스크랩/반응 시 해당 글 미리보기만 폐기. TTL을 이중 안전망으로.
- [꼬리] "왜 5페이지만?" → 접근 분포가 머리에 쏠림(Zipf) — 꼬리 페이지 캐싱은 메모리만 먹는다. / "정렬이 좋아요순이면?" → 캐시 안 탐, 쓰기마다 순위가 바뀌는 정렬의 무효화 비용이 이득보다 커서.

### Q18. 캐시 스탬피드(cache stampede)라고 아세요? 이 시스템은 안전한가요?
- [의도] 캐시를 "쓴" 사람과 "이해한" 사람의 경계선 질문.
- [뼈대] **안전하지 않다 — 그리고 그걸 스스로 병목 카탈로그(BTL-004)에 올려뒀다.** TTL 만료·evict 직후 동시 요청이 전부 DB로 몰리는 문제. 콜드 vs 웜 대조 실험(EXP-004)을 설계해뒀고 개선 후보는 분산락 기반 단일 재빌드, TTL jitter, 캐시 워밍. "모른다"가 아니라 "알고 있고 측정 계획이 있다"로 답할 수 있는 것 자체가 무기.

### Q19. Redis가 죽으면 서비스는 어떻게 되나요?
- [뼈대] 설계 원칙: **Redis는 있으면 빠르고 없으면 느린 계층, 죽어도 서비스는 산다.** 목록 캐시·인기글은 DB 폴백(인기글은 전용 폴백 테이블), 토큰 캐시는 DB 재조회, 조회수 버퍼는 유실 수용. 구현은 AOP(@ResilientRedis)로 Redis 예외를 흡수해 기본값 반환 + 폴백이 필요한 조회는 명시적 try-catch로 DB 경로.
- [꼬리] "그럼 Redis 복구 직후엔?" → 콜드 캐시 → 스탬피드 위험(Q18과 연결). / "AOP로 예외를 삼키는 방식의 위험은?" → 장애가 조용해진다 — 메트릭/알림으로 가시성을 별도 확보해야 한다는 점 인정.

## 5. DB·JPA

### Q20. 페이지네이션을 어떻게 구현했나요? OFFSET의 문제는?
- [뼈대] 하이브리드: 무한 스크롤(최신순 다음 페이지)은 커서(`id < lastSeen`), 임의 페이지 점프는 OFFSET. OFFSET n은 n행을 읽고 버리므로 뒤 페이지일수록 선형으로 느려지고, 쓰기 중엔 행 밀림/중복 노출. 커서는 인덱스 시크라 깊이 무관 O(페이지 크기).
- [꼬리] "좋아요순 정렬에서 커서는?" → (like_count, id) 복합 커서 필요 — 현재는 OFFSET, 한계 인정.

### Q21. 인덱스는 어떤 기준으로 걸었나요?
- [뼈대] 쿼리 패턴에서 역산: 목록 조회가 `WHERE board_id=? AND is_valid=1 ORDER BY {id|like|view} DESC`라 정렬별 복합 인덱스 3개 `(board_id, is_valid, 정렬컬럼 DESC)` — 등치 조건 선두, 정렬 컬럼 후미로 filesort 제거. 채팅은 `(room_id, msg_id DESC)`로 커서 페이징 커버.
- [꼬리] "인덱스가 많으면 뭐가 나쁜가?" / "그 인덱스가 실제로 타는지 어떻게 확인했나?" → EXPLAIN + slow query log(임계 0.1초) + 미인덱스 쿼리 로깅을 부하 환경에 켜뒀다. 대규모 실측에서 요청 1000건당 slow query 115건이 나온 걸 지표로 잡고 있다.

### Q22. N+1 문제를 설명하고, 어떻게 해결했는지 말해보세요.
- [뼈대] 해결책을 상황별로 골라 쓴 걸 보여주기: ① 목록은 fetch join이 아니라 **DTO 프로젝션 + 비정규화로 조인 자체 제거** ② 채팅 메시지·참여자는 fetch join ③ 방별 미읽음 수는 GROUP BY 집계 1쿼리 ④ 친구 관계 페이지는 N명 관계를 쿼리 3개로 확정. 전 연관관계 LAZY.
- [꼬리] "지금 남아있는 N+1은 없나?" → **있다.** 댓글 목록에서 로그인 유저의 반응 여부를 댓글마다 조회하는 루프 — 대규모 실측의 "요청당 903쿼리"에 기여한 용의자이고 EXP-005로 실험 설계돼 있다. 남은 문제를 아는 것이 더 신뢰를 산다.

### Q23. 트랜잭션 격리 수준과, 이 프로젝트에서 격리 수준이 문제 된 지점이 있나요?
- [뼈대] MySQL 기본 REPEATABLE READ. 스크랩 중복 사건이 사실상 격리 수준 문제의 실례다 — check-then-act는 어떤 격리 수준으로도 (SERIALIZABLE 빼고) 안 막히고, 막으려면 제약/원자적 연산이어야 한다는 결론. COUNT 재동기화 방식도 "동시 토글 시 마지막 커밋이 정확한 값을 쓰게" 하는 선택.
- [꼬리] 팬텀 리드/갭 락 정의 질문 → 개념 문서로 대비.

### Q24. @Transactional은 어떻게 동작하나요? 주의할 점을 겪어봤나요?
- [뼈대] 프록시 기반 AOP — 그래서 **self-invocation은 트랜잭션이 안 걸린다.** 실제로 스케줄러 내부 호출에서 건별 트랜잭션 분리가 의도대로 동작하지 않는 지점을 발견했다(한 건 실패가 배치 전체 롤백으로 번질 수 있는 구조). readOnly 최적화, REQUIRES_NEW(알림 격리), AFTER_COMMIT(이벤트) 사용처를 예로.

## 6. 인증·보안

### Q25. 왜 세션이 아니라 JWT인가요? JWT의 단점은?
- [뼈대] 무상태 → 서버 확장 시 세션 공유 불필요. 단점(즉시 무효화 불가)을 알고 보완: access 30분 단명 + refresh 7일은 **DB에 저장(서버 측 폐기 가능)** + 재발급 시 rotation. refresh 검증은 Redis 캐시(miss 시 DB, 남은 TTL로 재적재). 로그아웃/탈퇴 시 서버 측 삭제.
- [꼬리] "access 토큰 탈취되면 30분간은 못 막지 않나?" → 맞다, 그게 만료를 30분으로 짧게 둔 이유고, 완전 즉시 차단이 필요하면 블랙리스트가 필요 — 무상태 이점과의 트레이드오프. / "그럼 매 요청 DB로 유저를 조회하면 무상태 의미가 있나?" → 현재 인증 필터가 요청마다 유저를 DB 조회하는 건 자체 발견한 개선 대상(토큰 클레임만으로 인증 객체 구성 또는 캐시).

### Q26. 토큰을 왜 헤더가 아니라 쿠키에 담았나요?
- [뼈대] XSS로 JS가 토큰을 못 훔치게 HttpOnly 쿠키. 프론트가 별도 도메인이라 SameSite=None + Secure + Domain 설정. refresh 쿠키는 Path를 재발급 엔드포인트로 한정해 노출 면적 축소.
- [꼬리] "SameSite=None이면 CSRF는요?" → **정직하게 인정할 것.** CSRF 방어가 현재 비활성 상태로, 쿠키 인증 + SameSite=None 조합에서는 CSRF 토큰이나 Origin 검증이 필요하다 — 알려진 이슈로 기록해둔 상태. 변명하지 말고 "지금 고친다면 이렇게"를 말하는 게 낫다.

### Q27. OAuth2 로그인 흐름을 설명해보세요.
- [뼈대] Authorization Code 흐름: 인가 요청 → 동의 → 콜백으로 code → 서버가 code를 토큰으로 교환 → 유저 정보 조회 → 이메일로 조회해 없으면 자동 회원가입 → 자체 JWT 발급 쿠키로 전환 → 신규/기존에 따라 리다이렉트 분기. "provider 토큰을 그대로 쓰지 않고 자체 토큰으로 바꾸는 이유"(provider 독립적 권한 체계·수명 관리)를 말할 수 있어야 함.

### Q28. 인가(authorization) 설계에서 아쉬운 점이 있다면?
- [의도] 자기 시스템의 보안 구멍을 아는지.
- [뼈대] 선제적으로: GET 전체를 permitAll로 두는 블랙리스트 구조라 새 GET 엔드포인트의 기본값이 "공개"다 — 화이트리스트로 뒤집고 인가 규칙 자체를 테스트(spring-security-test)로 고정하는 게 올바른 방향. 리소스 소유권 검증은 서비스 계층에서 수행 중.

## 7. 실시간·확장성

### Q29. WebSocket 채팅 구조를 설명해보세요. 서버가 2대가 되면 어떻게 되나요?
- [뼈대] STOMP over WebSocket(+SockJS 폴백), 발행 `/app/chat/send`, 구독 `/topic/chat/room/{id}`, 개인 알림 `/user/{id}/queue`. 핸드셰이크에서 쿠키 인증 + **구독 시점에 방 참여자 검증**(아무나 구독으로 도청 불가). 현재 브로커는 인메모리 SimpleBroker — **서버 2대면 A서버 접속자에게 B서버발 메시지가 안 간다.** 해법: 외부 브로커 릴레이(RabbitMQ/Redis pub-sub)로 교체. 스스로 병목 카탈로그(BTL-006)에 올려둔 한계.
- [꼬리] "메시지 유실은?" → DB가 원본이고 브로드캐스트는 전달 최적화 — 재접속 시 커서 페이징으로 복구. "알림도 같은 문제?" → 같음, 동일 해법.

### Q30. 트래픽이 10배가 되면 뭐부터 무너지나요?
- [의도] 시니어 단골. 병목의 순서를 아는지.
- [뼈대] 실측 기반으로 답할 수 있는 드문 위치다: 순서는 ① DB 커넥션 풀 고갈(실측: 대기 205, 타임아웃 5,316) ② 요청당 쿼리 수(903) 때문에 DB CPU ③ 카운터 핫로우 락. 대응 순서도: 쿼리 수 절감(N+1 제거) → 풀/스레드 재조정 → 읽기 복제본 분리 → 카운터 Redis 버퍼링 → 그다음이 서버 수평 확장(그 전에 채팅 브로커·스케줄러 중복 실행부터 풀어야 함).

### Q31. 스케일 아웃하면 지금 구조에서 깨지는 게 뭐죠?
- [뼈대] 목록으로 즉답: ① SimpleBroker(채팅/알림 브로드캐스트) ② 스케줄러 4종 중복 실행(조회수 flush는 GETDEL이라 안전하지만 인기글 재채점·급식 로드는 중복 수행) ③ 없음 — 세션은 무상태라 안전. 해법: 브로커 외부화, 스케줄러는 분산락(예: Redis 기반) 또는 리더 선출.

## 8. 운영·배포·장애

### Q32. 배포 파이프라인을 설명해보세요. 배포 중 서비스는 끊기나요?
- [뼈대] GitHub Actions → 도커 빌드 → ECR push(정적 키가 아니라 **OIDC로 역할 assume**) → EC2에서 compose pull & up. **끊긴다** — 단일 인스턴스 recreate 방식이라 재기동 시간만큼 다운타임. 개선 방향: 헬스체크 게이트 + 롤백 + 블루/그린(또는 ASG 롤링). CI에 테스트 게이트가 없는 것도 알려진 이슈로 기록.
- [꼬리] "왜 개선 안 했나?" → 우선순위 판단(사용자 규모 대비)임을 말하되, 뭘 해야 하는지는 구체적으로.

### Q33. 장애를 겪어본 적 있나요? 어떻게 찾고 고쳤나요?
- [뼈대] 사례 풀에서 2개: ① 스크랩 중복 행 → 상세 조회 영구 장애(Q13 스토리) ② 엔티티-테이블명 불일치 (Linux MySQL 대소문자 구분) → 로그인 전면 장애 — 로컬(Windows)에선 재현 안 되는 이유까지. ③ (성능 쪽이 필요하면) STOMP content-length를 문자 수로 계산해 한글 메시지 첫 전송마다 연결이 죽던 버그 — 모든 겉보기 신호(핸드셰이크·체크)는 정상이라 커스텀 메트릭으로만 잡혔다.
- [꼬리] "재발 방지는?" → 부하 테스트가 회귀 게이트를 겸함 + 발견 장부 운영.

### Q34. 모니터링은 뭘 보나요? 알람 기준은?
- [뼈대] Prometheus + Grafana. 애플리케이션(요청 p95/p99, 오류율), JVM(heap, GC pause/오버헤드), 풀(HikariCP active/pending — **pending > 0 자체가 경보**), DB(slow query, QPS, buffer pool hit), Redis(hit ratio, eviction), 컨테이너(CPU throttling — p99 급등의 최대 원인). "무엇을 보는가"보다 "**임계값을 왜 그렇게 정했나**"가 나오면 강함(예: 32개 규칙 중 게이트를 10개만 남긴 이유 — 전부 게이트로 만들면 상시 빨간불이 되고, 그러면 아무도 안 본다).

## 9. 정직성이 필요한 질문 (여기서 뒤집힌다)

### Q35. 이 프로젝트에서 가장 부끄러운 코드는?
후보를 미리 정해둘 것. 추천: "인가 설정의 GET 전체 공개(블랙리스트 구조)" 또는 "인증 필터가 예외를 삼켜서 401이 제대로 안 나가는 것". 고르는 기준: **원인 → 영향 → 고치는 법**을 3문장으로 말할 수 있는 것.

### Q36. 테스트는 어떻게 작성했나요? 커버리지에 자신 있나요?
- [뼈대] 서비스 계층 위주 단위테스트 ~480개, @Nested + 한글 DisplayName BDD 스타일. 자신 없는 부분을 먼저: 인가 규칙 테스트 부재, CI에 테스트 게이트 부재. 강한 부분: "모킹 때문에 진짜 버그를 놓친 사건(Q13)" 이후 서비스 테스트에서 DB를 모킹하지 않는 규칙, 모든 컨트롤러 핸들러의 public 여부를 검사하는 아키텍처 테스트(프록시+AOP 조합의 실제 사고에서 나온 것).

### Q37. 혼자 만든 프로젝트인데, 협업 능력은 어떻게 보여줄 건가요?
- [뼈대] 협업의 산출물은 "다른 사람이 이어받을 수 있는 상태"다: ADR(아키텍처 결정 기록), 병목 카탈로그와 실험 설계 문서, 알려진 이슈 장부, 마이그레이션 규약(정리→백필→제약 순서), 커밋 메시지에 증상→원인→근거→부작용을 남기는 습관. 실제 문서를 예로 들 수 있다.

### Q38. 왜 토스인가요? / 토스에서 뭘 하고 싶나요?
- 기술 외 질문이지만 반드시 온다. 이 프로젝트와 연결하라: "감이 아니라 측정으로 말하는 문화", 대규모 트래픽에서 내 가설(풀 고갈, 핫로우, 스탬피드)이 실제로 어떻게 나타나는지 검증하고 싶다는 것. 토스 SLASH 발표(서버 부하/장애 관련 세션) 1~2개는 보고 가면 좋다.

## 10. 꼬리질문 체인 리허설 (모의면접용)

실전은 단발 질문이 아니라 체인이다. 아래 3개를 소리 내어 연습할 것.

**체인 A — 좋아요에서 시작해 끝까지**
좋아요 누르면 무슨 일이? → 동시에 두 번 누르면? → 왜 락이 아니라 unique+upsert? → 예외 잡아 복구하면 안 되나? (JPA rollback-only) → 카운트는 왜 +1이 아니라 재집계? → 그 카운터 행에 트래픽 몰리면? (핫로우) → 그건 어떻게 측정하고 개선할 건가? (EXP-003: Zipf vs 균등 대조, row_lock_waits 상관)

**체인 B — 목록 조회에서 시작**
목록 API 흐름은? → 캐시 구조는? → 무효화는? → TTL 만료 순간 동시 요청 몰리면? (스탬피드) → Redis가 죽으면? → 복구 직후엔? → 그 캐시가 실제로 얼마나 벌어주는지 어떻게 아나? (EXP-004 콜드/웜 대조)

**체인 C — "느려요"라는 제보에서 시작**
어디부터 보나? (p95/p99 → 오류율 → 포화 지표 순) → 평균 말고 분위수를 보는 이유? → p95가 60초로 찍혔다, 무슨 뜻? (검열) → 풀 대기 205는 뭘 의미? → 스레드/풀 크기 조정 방향은? → 조정했는지 어떻게 확인? (기준선 대비 회귀 판정, 비교 가능성 조건)
