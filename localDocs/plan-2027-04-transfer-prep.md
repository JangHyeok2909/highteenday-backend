## 1. 판단

프로젝트는 이미 신입·저연차 지원자가 보여 줄 수 있는 범위를 넘어서 있다. N+1 개선, 부하 측정,
Redis·MySQL 장애 주입, timeout, circuit breaker, readiness, 재시도 문제를 재현했다. 지금 부족한
것은 새 기술 하나가 아니라 다음 세 가지다.

1. 제한 시간 안에 AI 없이 문제를 풀고 코드를 작성하는 능력
2. 운영체제·네트워크·DB·Java 동시성의 원리를 처음 보는 상황에 적용하는 능력
3. 사이드 프로젝트보다 강한 회사 업무 사례와 채용 전형 통과 경험

따라서 앞으로는 프로젝트를 4주 안에 닫고 코딩 테스트, 요구사항 기반 구현, 실행형 CS 학습,
지원 준비에 시간을 배분한다.

### 30주 동안 하지 않는 것

- 6개월 상시 트래픽 운영
- 성능 측정 도구 npm CLI 추출과 공개
- Kafka 도입
- 장기간 멀티 인스턴스 운영
- 새로운 제품 사이드 프로젝트
- 일본어 학습
- Go 또는 Kotlin을 주 코딩 테스트 언어로 전환

위 항목이 나쁘기 때문이 아니다. 2027년 4월 전직의 서류·코딩·면접 통과율보다 우선순위가 낮기
때문이다.

## 3. 프로젝트 종료선

프로젝트의 마지막 주제는 다음 한 문장으로 고정한다.

> 장애와 재시도가 발생하는 환경에서 데이터 정합성과 서비스 안정성을 어떻게 지켰는가

### 반드시 완료

1. **멱등 API 전환**
   - 게시글·댓글 반응과 스크랩의 토글 계약을 PUT·DELETE 기반 목표 상태 계약으로 변경
   - 같은 요청을 반복해도 최종 DB 상태가 같은 통합 테스트 추가
   - 응답 유실 뒤 재시도하는 R-08 조건에서 상태 수렴 확인
   - Refresh Token rotation과 생성 API의 Idempotency-Key는 별도 백로그로 남김
2. **반응 카운터 경합 해소**
   - 실제 DB에서 lost update를 재현하는 동시성 테스트 추가
   - 비관적 락과 원자적 증감 중 하나를 선택하고 기각한 대안 기록
   - 수정 뒤 `counter-drift` 증가분 0 확인
3. **고부하 500 분류**
   - 예외 클래스 확인
   - 재시도로 복구 가능한 503인지 애플리케이션 결함인 500인지 판단
4. **장애 수정 전후 표**
   - Redis와 MySQL 대표 실행의 오류율, p95, Hikari pending, fallback, health 비교
   - 모든 수치에 실행 ID 또는 원자료 경로 연결
5. **프로젝트 설명 자료 갱신**
   - README와 대표 case 문서 갱신
   - 5분 설명 순서와 예상 후속 질문 작성

### 시간이 남을 때만 완료

- 앱 중단을 감지하는 알림 경로 1개
- 한 인스턴스에서 두 인스턴스로 늘릴 때 깨지는 항목을 설계 문서로만 정리

알림은 1일, 다중 인스턴스 설계는 반나절을 넘기지 않는다. 코드와 운영 환경 확장은 하지 않는다.

### 동결 조건

위 다섯 항목의 완료 기준을 충족하면 기능 동결 날짜를 README와 이 문서에 적는다. 이후 새 기능,
새 브로커, 새 언어 도입은 2027년 4월까지 보류한다.

## 4. 학습 시스템

### 4.1 코딩 테스트

주 언어는 Java를 유지한다. 알고리즘 학습과 언어 학습을 동시에 바꾸지 않는다.

- LeetCode 패턴 문제 70%
- 프로그래머스·백준의 구현과 시뮬레이션 20%
- 알고리즘 라이브 코딩 10%

문제 수보다 다음 수치를 기록한다.

- 처음 풀이 성공 여부
- 첫 실행 가능한 코드까지 걸린 시간
- 힌트 사용 여부
- 틀린 원인: 접근, 구현, 경계 조건, 시간 복잡도
- 7일 뒤 재풀이 성공 여부

### 4.2 요구사항 기반 무AI 구현

별도 비공개 연습 저장소 `backend-live-coding-kata`를 사용한다. Spring 없이 Java와 JUnit으로
구현한다.

한 회차의 순서는 고정한다.

1. 요구사항과 공개 API만 확인
2. 60~75분 동안 AI·검색 없이 구현
3. 미완성이어도 첫 시도 저장
4. 테스트 실행과 실패 분류
5. AI와 자료를 사용해 리뷰
6. 직접 수정
7. 다음 주에 실패한 핵심 부분을 빈 파일에서 재구현

AI는 첫 시도 뒤에만 사용한다. AI의 코드를 복사해 통과시키는 것은 완료로 세지 않는다.

5~16주에는 연습 저장소의 12개 kata를 번호 순서대로 주 1개씩 처음 구현한다. 17주부터는 이미
푼 문제의 핵심 부분 재구현과 처음 보는 변형 문제를 섞는다. 같은 문제를 다듬는 데 시간을 계속
쓰지 않고, 첫 시도 실패 원인이 다음 시도에서 반복되는지를 확인한다.

### 4.3 실행형 CS 학습

공개용 `backend-systems-lab`에 실험 6개를 만든다.

1. TCP RST·무응답·connect/read timeout·keep-alive
2. MySQL lost update·격리 수준·비관적 락·원자적 UPDATE
3. MySQL deadlock·락 순서·탐지·rollback·retry
4. JVM visibility·atomicity·`volatile`·`synchronized`·CAS
5. thread pool·connection pool·bounded queue·backpressure
6. 복합 인덱스·selectivity·`EXPLAIN ANALYZE`

실험 하나는 최대 4시간이다. 실행 환경, 예상, 재현 절차, 실제 결과, 예상과 달랐던 점, 운영에서의
선택을 남긴다. 수치를 꾸미거나 실행하지 않은 결과를 쓰지 않는다.

### 4.4 CS 백지 복원

실험으로 다룰 수 없는 질문은 카페나 도서관에서 30분 단위로 공부한다.

1. CS 지도에서 질문 3개 선택
2. 자료를 보지 않고 15분 동안 답 작성
3. 책·공식 문서·코드로 10분 검증
4. 처음 답의 오류와 빠진 조건을 5분 동안 수정
5. 다음 복원 날짜 기록

처음부터 모범 답안을 필사하지 않는다. 처음 답과 수정 답의 차이가 학습 기록이다.

1~4주에는 193문항을 깊게 공부하지 않고 1차 판정만 끝낸다. 5주에 지원 직무와 가까운 핵심
80문항을 고른다. 이후 주 6~8문항을 백지 복원하고, 17~22주에 실제 사람의 후속 질문으로 최종
검증한다.

### 4.5 실제 말하기와 라이브 코딩

혼자 녹음하는 훈련은 기본 계획에서 제외한다. 지원 10~12주 전부터 3~4명 규모의 오프라인
백엔드 면접 스터디를 구한다. 주 1회 스터디룸에서 다음을 반복한다.

- 요구사항 기반 40~60분 구현
- 상대방 코드의 경계 조건과 동시성 문제 질문
- CS 실험 결과에 대한 후속 질문
- 시스템 설계 문제의 요구사항과 트레이드오프 논의

실제 면접이 말로 진행되므로 이 단계는 생략하지 않는다. 혼자 매일 말하는 대신 외부 약속 6회로
검증한다.

## 5. 회사 업무에서 확보할 증거

개인 학습 시간과 별도로 회사 업무에서 다음 경험을 우선한다.

- 배포 뒤 실제 지표를 확인할 수 있는 변경
- Redis·DB·외부 API·네트워크 장애 처리
- 모니터링·알림·CI/CD 자동화
- 설계부터 배포까지 직접 책임지는 기능
- 시니어의 코드·설계 리뷰

매주 별도 문서를 쓰지 않는다. 월말에 다음 다섯 줄만 남긴다.

1. 문제와 사용자 영향
2. 내가 맡은 범위
3. 선택한 방법과 기각한 대안
4. 배포 뒤 결과와 수치
5. 함께 일한 사람과 받은 피드백

회사 기밀, 사용자 정보, 내부 URL, 공개할 수 없는 수치는 기록하지 않는다.

## 6. 주간 시간 배분

회사 업무를 제외하고 주 15시간을 기준으로 한다. 실제 시간이 적으면 비율을 유지한다.

| 기간 | 프로젝트 | 코테 | 무AI 구현 | CS·Lab | 지원·정리 | 영어 |
|---|---:|---:|---:|---:|---:|---:|
| 1~4주 | 5시간 | 5시간 | 2시간 | 2시간 | 0시간 | 1시간 |
| 5~16주 | 0시간 | 6시간 | 3시간 | 4시간 | 1시간 | 1시간 |
| 17~22주 | 0시간 | 5시간 | 3시간 | 3시간 | 3시간 | 1시간 |
| 23~30주 | 0시간 | 4시간 | 3시간 | 2시간 | 5시간 | 1시간 |

영어는 별도 시험 준비를 하지 않는다. AI와 짧은 대화, 공식 문서 읽기, 주 1회 기술 요약 정도로
유지한다. 일본어는 이 기간에 시작하지 않는다.

### 최소 주간 기준

야근과 일정으로 15시간을 확보하지 못한 주에는 다음만 지킨다.

- 시간제한 코딩 1회
- 알고리즘 문제 풀이 2회
- 무AI 구현 또는 라이브 코딩 1회
- CS 백지 복원 1회
- 진행 상황 10분 갱신

빠진 시간을 다음 주에 두 배로 보충하지 않는다. 다음 주의 정상 리듬으로 돌아간다.

## 8. 지원 회사 판단 기준

회사 이름보다 실제 팀을 본다. 아래 여섯 항목을 면접과 처우 협의에서 확인한다.

1. 배포와 운영을 개발자가 직접 담당하는가
2. 정기적인 코드 리뷰와 설계 리뷰가 있는가
3. 배울 수 있는 시니어 백엔드·플랫폼 개발자가 있는가
4. 장애 분석, 모니터링, 성능 개선을 업무로 경험할 수 있는가
5. 단순 유지보수·SI성 납품이 아니라 제품과 지표를 책임지는가
6. 해당 병역 유형의 전직을 실제로 받을 수 있고 복무관리가 안정적인가

당근·토스 공고가 열리면 상향 지원한다. 두 회사만 기다리지는 않는다. 같은 준비로 통과할 수 있는
좋은 병역특례 스타트업을 주력 지원군으로 유지한다.

## 9. 월말 점검

매월 마지막 학습일에 다음 질문에 답한다.

- 이번 달 처음 보는 코테 문제의 통과율은 얼마인가
- AI 없이 완성한 구현은 몇 개인가
- 처음 답과 수정 답이 달랐던 CS 오개념은 무엇인가
- 실행한 CS Lab의 예상과 실제 결과가 어디서 달랐는가
- 회사 업무에서 새로 확보한 수치와 결정 사례는 무엇인가
- 지원 가능한 공고와 병역 조건이 바뀌었는가
- 다음 달 계획에서 삭제할 항목은 무엇인가

계획을 지키는 것보다 전직 합격률을 높이는 것이 목적이다. 실제 전형에서 약점이 확인되면 다음 달
시간 배분을 바꾸되 프로젝트 확장으로 돌아가지는 않는다.
