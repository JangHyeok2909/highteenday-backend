> 기준: "토스 서버 면접관이 이 프로젝트와 나를 봤을 때 아쉬워할 것"을 전부 나열하고,
> **면접 임팩트 ÷ 필요 노력** 순으로 우선순위를 매겼다.
> 등급: ★★★ = 지원 전 반드시 / ★★ = 하면 확실히 차별화 / ★ = 여유 있으면 or 말로만 준비

> 자매 문서: `toss-interview-questions.md`(예상 질문), `toss-interview-concepts.md`(개념 정리)

# 제0장. 단 하나만 고른다면 — 스토리의 마지막 조각이 없다

**현재 상태: "측정했다"는 압도적인데 "그래서 고쳤고, 이만큼 빨라졌다"가 0건이다.**

- 병목 카탈로그 12건, 가설-실험 설계 5건(EXP-001~005)까지 만들어놓고 **실험 실행 기록이 0건**.
- 최적화 기록 디렉터리(`performance/optimizations/`)는 템플릿만 있고 **비어 있다**.
- 면접관의 마지막 질문은 반드시 "그래서 성능이 얼마나 좋아졌어요?"다. 지금은 이 질문에 답이 없다.

**→ 최우선 행동: EXP-001(기준선) → EXP-002(풀 고갈) or EXP-005(댓글 N+1) 중 1~2개를 실제로 실행하고, 개선 1건의 Before/After 수치를 만든다.**

이게 강력한 이유: 재료가 전부 준비돼 있다. 파이프라인 있음, 데이터셋 있음, 가설 있음, 예상 수치까지 있음(풀 대기 205, 903쿼리/요청). 실행만 하면 된다. 예상 산출물 예시:

> "댓글 목록의 반응 조회 N+1을 벌크 조회로 바꿔 요청당 쿼리를 X→Y개로 줄였고, 같은 부하에서 p95가 A→B ms가 됐습니다. 회귀 게이트가 이 개선을 기준선으로 잠갔습니다."

이 한 문장이 이 프로젝트의 모든 준비를 완성한다. **아래 다른 어떤 항목보다 먼저.**

# 제2장. 도입하면 좋은 기술 스택

> 원칙: **"있어 보이려고" 도입하면 역효과.** 토스 면접관은 "왜 도입했어요?"를 반드시 묻고,
> 필요 없는 걸 도입한 것은 필요한 걸 안 한 것보다 나쁘게 본다.
> 아래는 전부 **이 프로젝트에 이미 존재하는 문제**를 명분으로 갖는 것들만, 임팩트 순.

## 2-1. Redis Pub/Sub 채팅 브로드캐스트 버스 — ★★★ (추천 1순위)

- **현재 문제**: SimpleBroker가 인메모리라 서버 2대면 채팅/알림 브로드캐스트 단절 (자가 인지: BTL-006)
- **도입**: 메시지 저장 후 Redis 채널에 publish → 각 인스턴스가 subscribe해서 자기 접속자에게 STOMP 전달. 이미 Redis가 있어 신규 인프라 0개.
- **면접 스토리**: "스케일아웃 하려면?"의 모범 답을 **말이 아니라 코드로** 보유하게 됨. 실제 2-인스턴스 + nginx로 부하 테스트까지 돌리면(chat-heavy 시나리오 재사용) 완벽.
- **노력**: 중간(2~4일). 대안인 RabbitMQ STOMP 릴레이는 인프라가 늘어 이 규모에선 과함 — "왜 RabbitMQ 안 썼나"의 답까지 세트로.

## 2-2. Kafka (또는 최소 Transactional Outbox) — ★★ (토스 적합도 최고, 비용도 최고)

- **현재 문제**: 알림/랭킹 이벤트가 in-process — 재시작 유실, 재시도 없음, 컨슈머 확장 불가 (A2)
- **도입**: 이벤트 발행을 Kafka로: `comment.created` 등 토픽 → 알림 컨슈머/랭킹 컨슈머 분리. **반드시 outbox 패턴과 함께**(DB 트랜잭션과 발행의 원자성 — 이게 면접 포인트의 8할).
- **면접 스토리**: 토스 기술 블로그/SLASH에서 Kafka는 상수다. "왜 Kafka"(유실 방지·재시도·소비자 독립 확장)와 "왜 지금까지 안 썼나"(규모 대비 과잉 — AFTER_COMMIT으로 충분했다) **양쪽을 다 말할 수 있는 게 최상급**.
- **노력**: 큼(1~2주, 운영 개념 학습 포함). 시간 없으면 **outbox 테이블 + 폴링 릴레이만이라도**(Kafka 없이 유실 문제 해결, 3일) — "브로커 도입 전 단계로 outbox부터"라는 서사가 오히려 성숙해 보임.
- **주의**: 도입만 하고 파티션/컨슈머 그룹/재처리 질문에 못 버티면 역효과. 도입하면 개념을 깊게.

## 2-3. ShedLock 또는 Redisson 분산락 — ★★★ (가성비 최고)

- **현재 문제**: 스케줄러 4종이 다중 인스턴스에서 중복 실행 (A1의 ②)
- **도입**: ShedLock(스케줄러 전용, 어노테이션 한 줄) 또는 Redisson(범용 — 캐시 스탬피드 재빌드 락과 겸용 가능해서 이쪽 추천).
- **면접 스토리**: "분산락 써봤어요?"에 Yes + SET NX PX·소유자 검증 해제·락 만료 vs 작업 시간 문제까지. A3(스탬피드 방어)와 한 번에 해결하면 도입 하나로 스토리 두 개.
- **노력**: 작음(1~2일).

## 2-4. Testcontainers — ★★★ (테스트 서사 완성)

- **현재 문제**: "repository 모킹 때문에 upsert 버그를 단위테스트가 못 잡았다"는 최고급 스토리를 갖고 있으면서, 정작 실 DB 통합 테스트가 없음(T4) — 교훈에서 행동이 안 나온 상태.
- **도입**: MySQL(+Redis) Testcontainers로 upsert 동시성 테스트(스레드 2개 동시 토글 → 행 1개 검증), 커서 페이징, 익명화 통합 테스트. H2 테스트의 한계(MySQL 방언·upsert 문법 차이)를 말할 수 있게 됨.
- **면접 스토리**: "그 사건 이후 뭘 바꿨나요?" → "동시성이 걸린 경로는 실 MySQL 컨테이너로 테스트합니다" — 완벽한 마무리.
- **노력**: 작음~중간(2~3일).

## 2-5. datasource-proxy / p6spy 쿼리 카운트 테스트 — ★★

- **현재 문제**: N+1을 부하 테스트(903쿼리/요청)로만 검출 — 재발 방지 장치가 없음.
- **도입**: 테스트에서 "이 API는 쿼리 N개 이하" assert. N+1 수정(P2)과 세트로 넣으면 "고치고, 재발 방지까지"가 됨.
- **노력**: 작음(1일).

## 2-6. MySQL FULLTEXT (ngram) — ★★ / Elasticsearch — ★

- **현재 문제**: LIKE '%kw%' 풀스캔 (A4).
- **추천**: **FULLTEXT 인덱스 먼저**(인프라 추가 없이 해결 + Before/After 측정 소재 — 부하 파이프라인으로 검색 p95 전후 비교 가능). Elasticsearch는 이 규모에선 "왜 도입했나"를 방어하기 어려움 — "FTS로 부족해지는 시점(형태소 분석, 오타 교정, 랭킹)에 간다"는 로드맵 답변으로 충분.
- **노력**: FTS 작음(1~2일), ES 큼(1주+).

## 2-7. Resilience4j — ★

- **현재 문제**: Redis 장애 대응이 수제 AOP(@ResilientRedis) — 잘 만든 편이지만 서킷브레이커/타임아웃/폴백의 표준 어휘가 아님.
- **판단**: 도입해도 좋고, 안 해도 "수제로 만들며 원리를 이해했고, 팀에서는 표준 라이브러리를 쓰겠다"는 답이 오히려 매력적. 서킷브레이커 상태 전이(closed→open→half-open)는 개념으로 반드시 알아둘 것.

## 2-8. 도입하지 말 것 (물어보면 "안 한 이유"로 답)

| 스택 | 안 하는 이유 (면접 답변용) |
|---|---|
| MSA 전환 | 단일 팀·단일 도메인에서 분산 트랜잭션·운영 비용만 증가. "모놀리스를 잘 만드는 게 먼저, 경계는 이미 서비스 계층에 있다" |
| Kubernetes | 인스턴스 1~2대에 오케스트레이션은 과잉. compose→ECS/k8s 전환 경로만 인지 |
| MongoDB 등 NoSQL | 우리 데이터는 관계·제약이 핵심(유니크 제약이 정합성 전략의 중심) |

# 부록: "부족한 걸 묻는 질문"에 쓰는 법

이 문서의 내용은 숨길 게 아니라 **면접 무기**다. "아쉬운 점은?"류 질문에:

- 나쁜 답: "시간이 없어서 못 했습니다."
- 좋은 답 공식: **[인지] 무엇이 부족한지 정확히 + [분석] 왜 문제인지 + [계획] 어떻게 고칠지 + [우선순위] 왜 그 순서인지.**
- 예시: "가장 아쉬운 건 측정에서 개선까지의 루프를 완주하지 못한 것입니다. 병목 12건을 수치로 카탈로그화하고 대조 실험까지 설계했는데, 기준선 실험 없이 고치지 않는다는 원칙을 지키느라 실행이 뒤로 밀렸습니다. 지금은 EXP-001을 돌려 댓글 N+1부터 잡는 중이고, 회귀 게이트가 그 개선을 잠그게 하는 것까지가 한 사이클입니다."

단, **S3(익명성 노출) 같은 건 "아쉬운 점"으로 말하면 안 되고 면접 전에 고쳐야 한다** — 서비스 핵심 가치의 결함은 "인지하고 있다"로 방어가 안 된다.
