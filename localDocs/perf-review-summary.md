# 성능 테스트 시스템 리뷰 — 현재 결론과 실행 순서

- 최초 검토: 2026-08-05
- 마지막 갱신: 2026-08-11

## 한 문장 결론

이 시스템은 **성능 데이터를 모으는 능력은 충분하지만, 그 데이터를 비교하고 PASS/FAIL로
판정하는 과정에는 아직 신뢰성 문제가 있다.** 따라서 현재 결과는 원자료와 기능별 지표를
중심으로 분석하고, 자동 판정은 기준선·결측·측정 구간을 확인한 뒤 사용해야 한다.

## 무엇을 믿을 수 있고, 무엇을 조심해야 하나

| 결과 | 현재 판단 | 이유 |
|---|---|---|
| k6 원시 지표 | 조건부로 사용 가능 | 실제 요청 결과지만 사용자 모델과 집계 구간의 영향을 받음 |
| Prometheus 원시 시계열 | 조건부로 사용 가능 | 수집된 값은 유용하지만 cAdvisor 등 환경에 따라 빠지는 지표가 있음 |
| 기능별·작업별 breakdown | 원인 분석에 유용 | 전체 p95보다 어떤 기능이 느렸는지 분리해서 볼 수 있음 |
| 저장된 PASS/FAIL | 그대로 신뢰하면 안 됨 | 과거에는 인프라 규칙 누락, 현재는 기준선 자격과 결측 처리 문제가 남아 있음 |
| 이전 실행 대비 증감률 | 기준선 상태 확인 후 사용 | 조건이 다른 실행은 이제 자동으로 제외되지만, 기준선 자체가 없는 경우가 흔함 |
| 운영 용량 예측 | 현재 불가 | 로컬 단일 호스트와 운영 EC2·RDS 토폴로지가 다름 |

여기서 “조건부로 사용 가능”은 숫자가 가짜라는 뜻이 아니다. **숫자가 설명하는 조건을 같이
봐야 한다**는 뜻이다. 예를 들어 p95가 1초라는 값은 사실이어도, 그 p95가 게시글 조회가 아니라
로그인 요청에 의해 만들어졌다면 “게시글 조회 p95가 1초”라고 말할 수 없다.

## 현재 가장 중요한 문제 6개

### 1. 상대 비교가 아예 이뤄지지 않을 수 있음

관련: T-02(해결), S-10(미해결)

기준선 선택은 원래 “같은 조건에서 실행한 직전 결과”를 찾아야 한다. 원래 두 문제가 있었고,
그중 하나는 해결됐다.

- ~~데이터셋과 VU가 다른 실행을 기준선으로 선택할 수 있다.~~ → **해결**(T-02, 2026-08-09).
  실행 조건을 일급 개념으로 분리해, 시나리오·환경·데이터셋·부하 프로파일이 다르면 기준선에서
  제외하고 그 사유를 리포트에 남긴다.
- threshold에 실패한 실행은 여전히 기준선 후보에서 제외된다. → **미해결**(S-10).

두 번째 문제는 T-02 수정으로 오히려 더 두드러진다. EXP-000에서는 동일한 `posts.js` 실행
12건이 모두 threshold에 실패했다. 그 결과 12번째 실행에서도 기준선을 찾지 못했고, 리포트는
매번 “첫 실행”으로 표시했다. 즉 상대 증감률 계산이 한 번도 실행되지 않았다.

반대로 부하를 너무 약하게 주거나 작은 데이터셋을 사용해 빠르게 나온 실행은 threshold를
통과해 기준선이 될 수 있다. 현재 필터는 “정상적으로 측정됐는가”보다 “충분히 빨랐는가”를
기준선 자격으로 사용하고 있다.

다만 기준선을 못 찾은 사실 자체는 이제 숨겨지지 않는다. T-02 작업에서 `baselineStatus`
(`compared` / `incomparable` / `first-run`)를 도입해 리포트에 상태와 탈락 사유를 표시한다.
저장된 과거 실행은 조건 정보가 없어 기준선 후보에서 제외되는데, 이는 의도된 동작이다.

### 2. 짧은 실행의 전체 p95가 BCrypt 로그인에 지배됨

관련: S-01, S-02(해결), T-03, EXP-000

기존에는 매 iteration마다 로그인해 전체 요청의 약 20%가 BCrypt였다. 2026-08-11 수정으로
VU마다 한 번만 로그인하도록 바뀌어 로그인 비율은 2.1%까지 내려갔다.

그러나 20 VU가 시작과 동시에 로그인하면 2코어 애플리케이션에서 BCrypt 작업이 한꺼번에
경합한다. 60초처럼 짧은 실행에서는 이 느린 로그인 20건이 여전히 전체 p95 또는 p99에 들어갈
수 있다. S-02 수정으로 인증은 `op:auth`, 도메인 쓰기는 `op:write`로 분리됐지만, 전체 HTTP
지표에는 둘 다 계속 포함된다. 따라서 다음 두 값은 구분해 읽어야 한다.

- 게시글 기능 자체의 지연
- 시나리오 시작 시 세션을 만드는 비용

### 3. 필수 지표가 없어도 결과가 통과할 수 있음

관련: T-08, T-18, E-10

지표를 읽지 못하면 현재 판정기는 대체로 SKIP 처리한다. SKIP은 최종 FAIL을 만들지 않으므로,
CPU·MySQL·Redis 지표가 비어 있어도 테스트가 통과할 수 있다.

특히 Windows Docker Desktop에서는 cAdvisor가 컨테이너별 시계열을 만들지 못하는 경우가 있다.
이 상황을 “CPU 문제가 없다”로 읽으면 안 된다. 정확한 의미는 “CPU를 측정하지 못했다”이다.

### 4. k6가 만드는 사용 패턴이 실제 사용 패턴과 다름

관련: S-03, S-04, S-06, S-07, S-11~S-19

대표적인 예는 다음과 같다.

- Zipf 샘플러가 가장 인기 있는 `index 0`을 절대 선택하지 못한다.
- 게시판 첫 페이지가 한 번도 조회되지 않는다.
- 한계 탐색 시나리오가 closed model이라 서버가 느려질수록 발생 요청도 줄어든다.
- VU 수가 계정 수보다 많아 여러 VU가 같은 계정을 공유한다.
- 쓰기·알림·친구 저니가 데이터를 소모하지만 실행 사이에 복원하지 않는다.

이 문제들은 서버 코드가 같아도 측정 결과를 바꾼다. 따라서 “부하를 많이 보냈다”보다
“어떤 사용 행동을 어떤 비율과 시간 분포로 보냈는가”를 먼저 확인해야 한다.

### 5. 부하 발생기와 측정 대상이 같은 컴퓨터를 사용함

관련: E-01, E-02, E-09

k6, 애플리케이션, MySQL, Redis, Prometheus, Grafana가 같은 Windows 데스크톱에서 CPU와
메모리를 나눠 쓴다. EXP-000이 확인한 BCrypt CPU 경합은 k6가 같은 호스트의 CPU를 추가로
사용할 때 더 심해질 가능성이 있다.

호스트 지표를 수집하는 node_exporter도 없어 오염 정도를 숫자로 확인할 수 없다. 절대 성능을
주장하려면 발생기를 분리해야 하고, 당장 분리가 어렵다면 최소한 호스트 자원 사용량을 기록해야
한다.

### 6. CI가 실제 품질 게이트로 연결되지 않음

관련: E-23~E-31

성능 회귀 워크플로 초안은 있지만 `.github/workflows/`에 설치되지 않았다. 그대로 설치해도
PR 트리거가 없고, 시딩 절차는 bootstrap을 건너뛰어 실패하며, 공유 러너의 성능 노이즈도 크다.

현재 성능 테스트는 “자동으로 머지를 막는 게이트”가 아니라 “로컬에서 실행해 분석하는 도구”다.
로컬 측정 무결성을 먼저 고친 뒤 CI 역할을 결정해야 한다.

### P1 — 숫자의 의미와 재현성 개선

- k6와 Prometheus의 측정 구간을 같은 시간대로 맞춘다. (T-03, S-08)
- stress·spike·breakpoint 계열을 목적에 맞는 open model로 정리한다. (S-06)
- 시나리오군별 판정 규칙을 분리한다. (T-22)
- 실행마다 데이터 상태를 복원하거나 데이터셋 버전과 달성 수량을 기록한다. (S-11, E-19, E-20)
- MySQL 락·트랜잭션·풀스캔 지표를 수집 카탈로그에 등록한다. (T-29)
- PromQL이 짧은 피크와 컨테이너 재시작을 놓치지 않도록 수정한다. (T-18)

### P2 — 운영 자동화

- 부하 발생기를 분리하거나 node_exporter로 호스트 오염을 기록한다. (E-01, E-09)
- 데이터셋에서 빠진 채팅 메시지와 알림을 생성하고 medium 프로파일을 완성한다. (E-15, E-16)
- k6·seeder·환경 설정 버전을 실행 기록에 남긴다. (E-20, E-31, E-33)
- 로컬 측정 신뢰성이 확보된 뒤 CI의 역할을 선택한다. (E-23~E-27)
- Pages에 게시하기 전 executor와 내부 메타데이터를 제거하거나 마스킹한다. (E-29)

## 다음 실험을 시작할 수 있는 조건

다음 조건을 만족하기 전에는 “개선 전과 개선 후의 차이”를 확정적인 회귀 결과로 발표하지 않는다.

- 비교 대상의 데이터셋·부하 프로파일·스크립트 버전이 일치한다. 이 검사는 T-02 수정으로
  자동화됐지만, 리포트에 표시된 조건을 눈으로 한 번 더 확인한다.
- 기준선이 실제로 선택됐다. 즉 `baselineStatus`가 `compared`이고 `baselineRunId`가 기록돼 있다.
  `incomparable`이나 `first-run`이면 상대 증감률은 존재하지 않는다.
- 필수 인프라 지표의 결측 여부가 리포트에 표시된다.
- 같은 조건을 여러 번 실행해 평균뿐 아니라 분산과 CV를 확인한다.
- 전체 p95와 함께 기능별 p90·p95·p99, 요청 수를 기록한다.
- 테스트 중 timeout 상한에 걸린 값은 검열된 값으로 표시한다.
- 작업 트리가 깨끗하고 실행 기록의 commit에 `+dirty`가 붙지 않는다.
