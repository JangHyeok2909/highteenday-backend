# 성능 테스트 시스템 리뷰 — 총평 및 실행 계획 (2026-08-05)

## 총평

설계 문서(PERFORMANCE-MANAGEMENT.md)는 수준이 높다 — 2단계 수집, 노이즈 플로어,
절대 게이트, 병목 가설 분리는 전부 옳은 판단이다. 문제는 **구현을 검증하는 장치가
전혀 없다**는 것: 판정을 내리는 JS ~110KB에 테스트가 0개이고, 그 결과 치명적 버그들이
시스템 탄생 이래 한 번도 발각되지 않았다. 문서가 스스로 한계를 솔직히 적어둔 점은
훌륭하지만, 적힌 한계 중 어느 것도 코드로 강제되거나 런 기록에 남지 않는다.

**결론: 현재까지 기록된 23개 런의 판정(PASS/FAIL)은 신뢰할 수 없다.**
단, 원자료(run.json의 infra.flat, k6 rawMetrics)는 유효하며 이미 병목을 실측하고 있다.

## 판정을 무효로 만드는 5대 결함 (요약)

1. **infra 규칙 25/32개가 한 번도 작동 안 함** — `pick()`이 점 포함 평면 키를 못 읽음 → 전부 SKIP → PASS ([T-01])
2. ~~**기준선이 데이터셋/VU를 무시** — large 200VU 런이 small 15VU 런과 비교됨 ([T-02])~~ → **해결** (2026-08-09)
3. **요청의 ~19%가 BCrypt 로그인** — 매 iteration 재로그인, 쓰기 SLO의 75%가 auth ([S-01, S-02])
4. **Zipf 샘플러가 index 0을 못 뽑음** — 최고 인기글과 0페이지가 한 번도 조회된 적 없음 ([S-03, S-04])
5. **CI 게이트 미설치 + 설치해도 머지 못 막음 + seed 단계는 확정 실패** ([E-23, E-24, E-25])

## 오픈소스 CLI 계획과의 관계

이 발견들은 CLI 추출 계획의 가치를 깎는 게 아니라 **추출 전 정리 로드맵**이다.
P0의 수정+테스트가 곧 추출 준비 작업이고, "정교한 설계 → 검증 부재로 침묵 버그 →
테스트 도입으로 회복"이라는 서사 자체가 도구의 신뢰성 스토리가 된다.
하드코딩 목록(컨테이너명, localhost, Grafana 가정)은 E 문서의 E-36 참조.
