# 아카이브 — 포화 상태에서 측정된 실행

**보관일: 2026-08-21 · 49건**

## 왜 옮겼나

여기 있는 실행들은 **애플리케이션의 용량을 넘긴 부하에서 측정**됐다. 그래서 기록된 p95 는
애플리케이션 처리 시간이 아니라 **큐 대기 시간**이다.

같은 앱·같은 데이터셋·같은 커밋을 포화 이하(도착률 4/s)에서 재면 p95 가 **278ms** 인데,
여기 있는 `normal-day` 실행들은 **10,000~17,000ms** 다. 38배 차이이고 차이의 정체는 코드가
아니라 대기줄이다.

구체적으로 이런 상태였다.

```
200 VU (closed model)  →  Tomcat 400 스레드  →  Hikari 10  →  MySQL 2코어
                              앱 CPU 1.998 / 2.0 완전 포화
                              Hikari 10/10, 대기 145 스레드
                              커넥션 획득이 p95 의 57%
```

closed model 에서 VU 가 고정이면 리틀의 법칙에 따라 `R = N / X` 가 기계적으로 성립한다.
실측 상관 0.962 로, **p95 는 애플리케이션 지연이 아니라 처리량의 그림자**였다.

배경과 전체 분석: [localDocs/perf-session-drift.md](../../../localDocs/perf-session-drift.md) 0절·8-h절

## 무엇에 쓸 수 있고 무엇에 못 쓰나

**못 쓴다.**
- **기준선(baseline)** — 포화 영역과 비포화 영역의 p95 는 서로 다른 물리량이라 증감률에
  의미가 없다.
- **애플리케이션 성능 인용** — "이 앱의 p95 는 12초" 같은 진술의 근거로 쓰면 안 된다.
- **개선 전후 비교의 Before** — 새 운용점에서 다시 재야 한다.

**쓸 수 있다.**
- **포화 영역의 거동 연구** — 대기행렬 절벽이 어떻게 생겼는지의 실측 자료다.
- **도구 결함 조사의 원자료** — T-36·T-37·S-27·E-46 의 근거가 여기 있다.
- **역사적 기록** — 무엇을 어떻게 측정했고 왜 틀렸는지의 증거.

## 되돌리는 방법

디렉터리를 옮겼을 뿐 지우지 않았다. 인덱스도 `archive/index.json` 에 그대로 있다.

```bash
# 특정 실행 하나를 되돌린다
mv reports/archive/runs/<runId> reports/runs/

# 전부 되돌린다
mv reports/archive/runs/* reports/runs/
```

인덱스까지 복원하려면 `archive/index.json` 의 해당 항목을 `reports/index.json` 의 `runs`
배열에 다시 넣거나, `node tools/collect.js --all --force --no-wait` 로 재수집한다.

## 주의

`reports/runs/` 에 남은 70건도 **전부 안전한 것은 아니다.**

- `NEAR_LIMIT` 6건은 큐가 생기기 시작한 상태다. 해석에 주의한다.
- `UNKNOWN` 2건은 판정에 필요한 지표가 없어 포화 여부를 알 수 없다.
- 무엇보다 **`normal-day` 외 시나리오는 용량 곡선을 그려 본 적이 없다.** `read-heavy`·
  `write-heavy` 등도 기본 설정이 용량을 넘을 가능성이 있고, 지금 `HEADROOM` 으로 나온 것은
  그 실행의 부하가 가벼웠기 때문일 수 있다.
