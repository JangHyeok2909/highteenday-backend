# Archive — 기준선으로 쓰면 안 되는 실행 61건

2026-07-30 ~ 07-31에 기록된 실행들이다. **삭제하지 않고 격리만 했다.**

`reports/runs/`가 아니라 여기 있으므로 `tools/lib/repository.js`의 `listRunIds()`가
찾지 못한다. 즉 인덱스 재생성·기준선 자동 선택·추세 그래프 어디에도 들어가지 않는다.
보고서 HTML은 그대로 열린다.

## 왜 뺐나

2026-08-04에 세 가지가 **동시에** 바뀌었다. 이 프로젝트의 원칙인 "한 번에 변수 하나"를
세 번 어긴 셈이라, 이 실행들과 이후 실행의 차이는 무엇 때문인지 분해할 수 없다.

| 층 | 무엇이 바뀌었나 |
|----|-----------------|
| 부하 스크립트 | 여정 분기 재분배(댓글 반응·단건 알림 읽음 편입), 친구 신청이 닉네임 → id 기반으로 전환 |
| 앱 코드 | 07-31 빌드 → 현재 develop. 친구 API 변경, BTL-008/009/010/012 수정 |
| DB 스키마 | Flyway V4~V7 적용. 특히 `scraps`에 유니크 인덱스가 생겨 쓰기 비용이 달라짐 |

## 그런데 왜 안 지웠나

**이관 도구가 실제로 동작했다는 증거다.** 이 61건은 원래 `reports/raw/`의 k6 summary로만
있던 것을 `tools/migrate-raw.js`가 새 파이프라인 형식으로 옮긴 결과이고, Prometheus
보관 기간 안이라 운영 지표까지 소급해서 채워졌다. 원본(`k6.json`)을 남기고 수집을 2단계로
분리한 설계가 값을 한 지점이다.

**수집기 수정이 과거까지 닿는다는 증거이기도 하다.** 이 실행들의 `run.json`은
컨테이너 지표 중복 시계열 버그를 고친 뒤 전량 재계산됐다. 그 전에는 메모리 포화도 227%
같은 물리적으로 불가능한 값이 "OOM Kill 위험"이라는 병목 가설로 리포트에 실려 있었다.
`reports/raw/`의 원본과 대조하면 무엇이 어떻게 바뀌었는지 볼 수 있다.

**그리고 사례로 쓸 값이 있다.** 여기에는

- 오류율 55.6%인데 check 성공률 100%로 보고된 실행이 있다 (`school-2026-07-31T04-27-11`).
  단정이 400을 통과시켜 급식 조회가 아니라 에러 응답 시간을 재고 있었다.
- iteration 6~20회짜리 20초 실행의 p95를 20% 임계로 비교해 회귀로 잡힌 실행들이 있다.
  노이즈 플로어는 "값이 작을 때"는 막아 주지만 "표본이 적을 때"는 막지 못한다.

둘 다 지금 판정 체계가 어떤 함정을 넘어야 하는지 보여주는 실물이라, 문서의 설명보다 낫다.

## 다시 보려면

```bash
# 개별 보고서 (그대로 열린다)
performance/reports/archive/<runId>/report.html

# 수치만 뽑기
node -e "console.log(require('./reports/archive/<runId>/run.json').k6.overall)"
```

기준선 후보로 되살릴 일은 없어야 하지만, 필요하다면 디렉터리를 `reports/runs/`로
되돌리고 `node tools/history.js --rebuild`를 실행하면 된다.

(`normal-day` 200 VU · 램프 5분 · 유지 20분)로 한 번 더 실행해야 나온다.
