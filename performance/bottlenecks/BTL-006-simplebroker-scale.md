# BTL-006: SimpleBroker 인메모리 브로커의 수평 확장 한계

> 유형: WebSocket / Architecture
> 상태: 의심
> 관련: chat-heavy 시나리오

## 증상

- 동시 WebSocket 세션 증가에 따라 힙 사용량과 브로드캐스트 지연(`chat_ws_rtt`) 상승
- **앱을 2대로 늘리는 순간 기능 장애**: A 서버 접속자가 보낸 메시지를
  B 서버 접속자가 못 받는다 (인메모리 브로커는 서버 간 공유가 없음)

## 원인

`WebSocketConfig`: `registry.enableSimpleBroker("/topic", "/queue")` —
Spring 내장 SimpleBroker는 구독 정보와 메시지 라우팅이 **해당 JVM 안에만** 존재.

- 세션·구독 레지스트리가 힙에 상주 → 세션 수 ∝ 힙
- 브로드캐스트는 broker 채널 스레드 풀에서 처리 → 방 인원 × 메시지율에 비례한 팬아웃 비용
- ALB 뒤에 인스턴스를 늘려도 채팅은 확장 불가 (스티키 세션으로도 방 단위 분산 불가)

## 영향

- 단일 인스턴스: chat-heavy에서 세션 수백~수천부터 RTT 저하 예상 (실측 필요)
- 수평 확장: 채팅 기능이 스케일 아웃의 구조적 차단벽

## 재현 방법

```bash
# 단일 인스턴스 한계: VU를 늘려가며 RTT 관찰
k6 run scenarios/chat-heavy.js -e VUS=400 -e DATASET=medium
k6 run scenarios/chat-heavy.js -e VUS=800 -e DATASET=medium
```

관찰 지표: `chat_ws_rtt` P95, `jvm_memory_used_bytes`(세션당 힙 증분),
`jvm_threads_live_threads`, 브로커 채널 큐 적체(스레드 덤프).

## 개선 전 선행 조건

공통 조건 넷은 [`README.md`의 "개선 전 공통 선행 조건"](README.md#개선-전-공통-선행-조건)에 있다.
이 병목에만 걸리는 것은 아래 넷이며, **이 병목이 일곱 중 측정 준비가 가장 덜 된 항목이다.**

### ① 메시지 유실을 세지 않는다 (S-13) — 이게 최대 문제

브로커 한계는 **정확히 유실로 발현되는데, 지금 계측에 유실이 나타나지 않는다.**

`scripts/chat-ws.js`가 만드는 커스텀 지표는 셋이다.

| 지표 | 무엇을 세는가 |
|---|---|
| `chat_ws_messages_sent` (Counter) | 보낸 메시지 수 |
| `chat_ws_errors` (Counter) | WS 오류 |
| `chat_ws_rtt` (Trend) | **돌아온** 메시지의 왕복 지연 |

**수신 카운터가 없다.** 그래서 브로커가 메시지를 떨어뜨리면 `chat_ws_rtt`의 **표본 수만
조용히 줄고** 오류로도 실패로도 나타나지 않는다. 남은 메시지들의 RTT는 오히려 좋아 보일 수
있다 — 부하가 줄었으므로.

개선 전에 `sent − received`를 계산할 수 있어야 한다. 이것 없이 RTT만 비교하면
**유실을 성능 개선으로 오독한다.**

### ② 서버측 세션 수 지표가 없다

"세션 수 ∝ 힙"이 이 병목의 원인 설명인데, WebSocket 세션 수를 재는 지표가 없다
(`metrics/README.md`가 "커스텀 게이지 필요(개선 항목)"으로 남겨 둔 항목이다).

임시로 `jvm_threads_live_threads`와 k6측 VU 수를 대리 지표로 쓸 수 있지만, **대리 지표라는
사실을 실험 문서에 명시**해야 한다. 스레드 수는 세션 수와 비례하지 않을 수 있다.

### ③ 선언한 VU와 실제 동시 세션 수가 다르다 (S-13)

WS 저니는 계획한 것보다 오래 연결을 점유한다. 그래서 `-e VUS=400`으로 돌린 실행의 동시 세션
수가 400이 아니다. **한계점을 VU 숫자로 말하면 틀린 값이 기록된다** — "800 VU에서 RTT가
무너졌다"가 아니라 "동시 세션 N개에서"라고 말할 수 있어야 한다.

### ④ 수평 확장 장애는 부하 테스트로 재현되지 않는다

이 문서가 지적한 두 문제는 성격이 다르다.

| 문제 | 재현 방법 |
|---|---|
| 단일 인스턴스 RTT 저하 | `chat-heavy` VU를 올려가며 측정 — 부하 테스트로 가능 |
| **A 서버 발신을 B 서버 수신자가 못 받음** | **부하가 아니라 구성 문제.** 앱 2대 이상이 필요하다 |

현재 `docker-compose.perf.yml`은 앱 단일 인스턴스다. 두 번째 문제는 **인스턴스를 2대로 띄운
구성을 먼저 만들어야** 검증도 개선 확인도 가능하다. 부하를 아무리 올려도 단일 인스턴스에서는
드러나지 않는다.

### 실험이 배정돼 있지 않다

BTL-001~005는 EXP가 붙어 있지만 이 항목은 `chat-heavy 시나리오`만 적혀 있다. 개선을 기록으로
남기려면 `experiments/TEMPLATE.md`로 실험 문서를 먼저 만들어야 한다 — 가설·반증 조건 없이
실행한 수치는 이 프로젝트에서 개선으로 인정하지 않는다.

## 해결 방법

| 후보 | 효과 | 트레이드오프 |
|------|------|--------------|
| Redis Pub/Sub 릴레이 (이미 Redis 보유) | 서버 간 브로드캐스트 공유 — 최소 변경 스케일 아웃 | at-most-once (유실 가능), 구독 관리 직접 구현 |
| 외부 STOMP 브로커 (RabbitMQ) — `enableStompBrokerRelay` | 표준적 해법, 내구성 옵션 | 인프라 추가 운영 비용 |
| Kafka 기반 팬아웃 | 대규모·재생 가능 | 소규모 서비스엔 과설계 |

단일 인스턴스 실측 한계(세션 수)를 먼저 확정하고, 그 수치가 성장 로드맵보다
작을 때만 브로커 교체를 진행한다 — **측정 없는 아키텍처 교체 금지.**
