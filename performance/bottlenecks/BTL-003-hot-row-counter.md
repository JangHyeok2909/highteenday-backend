# BTL-003: 인기글 비정규화 카운터 단일 row 락 경합

> 유형: Lock / DB
> 상태: **확정** — `datasets/seed.js`의 Zipf 편중 댓글/반응/스크랩 생성 중
> concurrency=5의 낮은 동시성에서도 실제 데드락이 재현됨(아래 로그 원문).
> 2026-08-16 large 생성(동시성 10, 150만 요청)에서 **재시도 9,437회 / 최종 실패 1건**으로
> 규모를 처음 계측했다 — 아래 "규모 실측" 참고. 크기 자체는 EXP-003이 정상 부하 조건에서
> 다시 재야 한다(시더의 동시성은 부하 시나리오의 VU 수와 다르다).
> 관련: EXP-003, [KI-53](../../docs/defects/KI-53-comment-counter-lost-update.md)(같은 코드의
> 정합성 문제 — 느린 것과 틀린 것은 다른 축이다), KI-55

## 증상

반응(좋아요)/댓글 API의 P99만 유독 나쁘고, 부하가 특정 인기글에 쏠린 시간대에
`innodb_row_lock_waits`가 함께 뛴다. 최악의 경우 데드락 로그.

## 규모 실측 — large 재생성 중 (2026-08-15~16)

**재시도 6회로도 살아남는 데드락이 존재한다.** 깨끗한 DB에 large 데이터셋을 생성하면서
단계별 재시도 횟수를 셌다. 시더는 지수 백오프(최대 800ms) + 지터로 데드락을 흡수한다.

| 단계 | 요청 수 | 재시도 | 재시도율 | 최종 실패 | 공유 행 갱신 |
|---|---:|---:|---:|---:|:---:|
| register / login / school | 30,000 | 0 | 0% | 0 | 없음 |
| posts | 100,000 | 0 | 0% | 0 | 없음 |
| **comments** | **400,000** | **3,488** | **0.87%** | 0 | **있음** |
| **reactions** | **1,000,000** | **5,949** | **0.59%** | **1** | **있음** |
| **scraps** | **80,000** | **1,570** | **1.96%** | 0 | **있음** |
| friendships | 30,000 (×3 요청) | 0 | 0% | 0 | 없음 |
| chat-rooms | 9,000 | 0 | 0% | 0 | 없음 |

**재시도가 발생한 단계는 정확히 셋뿐이고, 그 셋만 `posts` 행의 비정규화 카운터를 갱신한다.**
회원가입·게시글 생성·친구·채팅은 서로 다른 행을 다루므로 총 269,000건에 재시도 0이다.
이 대조가 "경합의 원인은 DB 일반 부하가 아니라 **그 카운터 컬럼**"이라는 것을 보여 준다.

게시글 생성은 서로 다른 행을 INSERT하므로 재시도가 0이다. 반면 **댓글·반응은 같은
`posts` 행의 카운터를 갱신**해 경합이 생긴다 — 이 표가 그 구조적 차이를 그대로 보여 준다.

> **댓글과 반응의 재시도율을 직접 비교하지 말 것.** 이 실행에서 두 단계는 **서로 다른
> 갱신 방식**을 썼다.
>
> | | 갱신 방식 | 코드 |
> |---|---|---|
> | 댓글 | 원자 UPDATE (한 컬럼만) | `PostRepository.incrementCommentCount()` — KI-53에서 교체 |
> | 반응 | 더티 체킹 (행 전체) | `PostReactionService.syncCounts()` → `post.syncReactionCounts()` |
>
> 게다가 부하 모양도 다르다. 반응은 `(사용자, 게시글)` 유니크 제약 때문에 한 글이 받을 수
> 있는 최대치가 사용자 수(10,000)로 묶여 **자연히 분산**되지만, 댓글에는 그 상한이 없어
> 같은 작성자가 인기글에 반복해서 달 수 있다. 즉 댓글 쪽이 더 집중된 부하다.
>
> 두 변수가 동시에 다르므로 이 표에서 "원자 UPDATE가 효과 있었다/없었다"를 결론지을 수
> 없다. 그 비교는 **반응도 원자 증감으로 바꾼 뒤 같은 조건에서 다시 재야** 성립한다
> (KI-55와 함께 다룰 항목이다).

### 집중도까지 같이 봐야 한다 — 스크랩이 재시도율 1위인 이유

재시도율만 보면 스크랩(1.96%)이 반응(0.59%)보다 3배 나쁘다. 요청 수는 오히려 1/12인데도
그렇다. **한 행에 얼마나 몰렸는가**를 같이 보면 설명된다.

| 종류 | 가장 뜨거운 글의 건수 | 전체 | 최상위 비중 | 재시도율 | 갱신 경로 |
|---|---:|---:|---:|---:|---|
| 댓글 | 34,084 | 400,000 | **8.52%** | 0.87% | 원자 UPDATE (한 컬럼) |
| 반응 | 9,999 | 999,998 | **1.00%** | 0.59% | 2×`COUNT(*)` + 행 전체 UPDATE |
| 스크랩 | 5,022 | 79,998 | **6.28%** | 1.96% | `COUNT(*)` + 행 전체 UPDATE |

**반응의 1.00%는 실제 인기 편중이 아니다.** `(사용자, 게시글)` 유니크 제약 때문에 한 글이
받을 수 있는 활성 반응의 상한이 사용자 수(10,000)다. 가장 뜨거운 글이 9,999에서 **막혀**
나머지가 아래로 퍼진다. 댓글·스크랩에는 그 상한이 없어 Zipf 그대로 6~8%가 한 행에 몰린다.

이 사실이 두 가지를 뜻한다.

#### ① 반응으로 잰 경합은 실제보다 약하다 — EXP-003 설계에 영향

유니크 제약이 **부하 분산기 역할**을 해서 핫로우 경합을 가린다. 그런데 운영 트래픽에는
그 제약이 없다 — 한 사용자가 좋아요를 눌렀다 취소했다 다시 누를 수 있고, 그때마다 같은
`posts` 행이 갱신된다. **반응 시나리오만으로 BTL-003을 재면 크기를 과소평가하게 된다.**

EXP-003은 유니크 제약에 막히지 않는 경로(댓글, 또는 토글을 반복하는 반응)로 재야 한다.
생성 문제 11이 "유니크 제약이 반응 분포를 평평하게 만든다"고 지적한 것이 여기서는
**측정을 왜곡하는 방향**으로 나타난 셈이다.

#### ② 원자 UPDATE가 경합을 줄이는 것으로 보인다 (가설)

집중도로 나눠 보면 방향이 뚜렷하다.

```text
댓글   0.87% ÷ 8.52% = 0.10   ← 원자 UPDATE (KI-53 적용)
스크랩 1.96% ÷ 6.28% = 0.31   ← COUNT + 행 전체
반응   0.59% ÷ 1.00% = 0.59   ← 2×COUNT + 행 전체
```

댓글은 **가장 집중된 부하를 받으면서도 단위 집중도당 재시도가 가장 적다.** 한 컬럼만
건드리는 UPDATE가 행 전체를 다시 쓰는 것보다 락 보유 구간이 짧기 때문이라는 설명과 맞는다.

**다만 이건 가설이지 결론이 아니다.** 세 단계는 트랜잭션 모양 자체가 다르다 — 댓글은
`INSERT` + 원자 UPDATE, 스크랩은 `SELECT COUNT` + upsert + UPDATE, 반응은 `COUNT` 두 번이
더 붙는다. 위 나눗셈은 집중도만 보정했을 뿐 그 차이는 보정하지 못했다. 스크랩은 재개 실행에서
**혼자** 돌아 시스템 상태도 달랐다.

확정하려면 **반응·스크랩도 원자 증감으로 바꾼 뒤 같은 조건에서 다시 재야** 한다.
그 변경은 KI-55(카운터가 1씩 어긋남)와 원인이 같으므로 함께 다루는 것이 자연스럽다.

최종 실패 1건의 원문:

```text
reaction 500: Deadlock found when trying to get lock; try restarting transaction
  [update posts set brd_id=?,pst_comment_count=?,pst_content=?,pst_dislike_count=?,...]
```

**주목할 점은 UPDATE 문의 모양이다.** 카운터 하나만 바꾸는데 JPA 더티 체킹이 `posts` 행의
**모든 컬럼을 다시 쓴다**. 갱신 대상 컬럼이 넓을수록 락 보유 구간과 언두 로그가 커지므로,
경합이 실제보다 나쁘게 나타난다. 카운터를 원자 UPDATE로 바꾸면(댓글은 KI-53에서 이미
그렇게 했다) 이 부분이 줄어든다 — **락 경합 자체는 남지만 크기는 달라진다.**

### 이 수치를 어떻게 읽어야 하나

- **경합이 존재한다**는 것은 확정이다. 동시성 10, 정상 부하도 아닌 데이터 생성만으로
  100만 건 중 1건이 재시도 6회를 모두 소진했다.
- **크기는 아직 확정이 아니다.** 이 실측은 `AUTHOR_SKEW=1.3` / `HOT_SKEW=1.07` 새 분포에서
  나왔지만, 시더의 동시성(10)은 실제 부하 시나리오의 VU 수와 다르다. EXP-003이 정상 부하
  조건에서 다시 재야 한다.
- **옛 관측치는 과대평가일 가능성이 높다.** 옛 샘플러에서는 2위 글 하나가 댓글의 19~27%를
  받았다. 새 분포에서 1위 몫은 약 8.6%다. 같은 경합을 재더라도 이전 수치보다 작게 나오는
  것이 정상이며, 그 차이는 서버 개선이 아니라 **부하 분포 교정** 때문이다.

## 원인

읽기 최적화를 위해 `Post`가 `likeCount, dislikeCount, commentCount, scrapCount`를
컬럼으로 비정규화(README/CLAUDE.md 명세). 좋아요 1건 = post row 1건 UPDATE.

트래픽은 Zipf 분포로 소수 인기글에 몰리므로, **논리적으로 분산된 쓰기가
물리적으로 같은 row 하나에 직렬화**된다. InnoDB row lock은 트랜잭션 커밋까지
유지되므로 트랜잭션 길이만큼 후속 요청이 줄을 선다.

## 영향

- write-heavy / peak-hour, 그리고 실서비스에서 "글이 터졌을 때" 정확히 재현
- 반응 API 자체 + 같은 커넥션 풀을 쓰는 다른 쓰기 경로로 2차 전파 (BTL-002와 결합 시 증폭)

## 재현 방법

```bash
# reactions.js는 Zipf(hotPost)로 이미 편중 설계됨
k6 run scripts/reactions.js -e VUS=100 -e DURATION=5m -e DATASET=medium
```

관찰 지표: `post_reaction` P99, `mysql_global_status_innodb_row_lock_waits`,
부하 중 스냅샷 `SELECT * FROM performance_schema.data_lock_waits;`

### 실측 재현 기록 (2026-07-30)

`datasets/seed.js --profile smoke`(동시성 5, VU가 아니라 단순 병렬 클라이언트 수준)로
댓글 150건 + 반응 300건 + 스크랩 40건을 50개 게시글에 Zipf 편중 생성했을 때,
**k6/VU 부하 없이 시드 스크립트 단계에서만도** 다음 데드락이 다수(comments 15건,
reactions 6건, scraps 3건 실패) 발생했다:

```
org.springframework.dao.CannotAcquireLockException: could not execute statement
[Deadlock found when trying to get lock; try restarting transaction]
[update posts set brd_id=?,pst_comment_count=?,pst_content=?,pst_dislike_count=?,
 pst_is_anonymous=?,is_valid=?,pst_like_count=?,usr_nickname=?,pst_scrap_count=?,
 pst_title=?,upt_id=?,upt_date=?,usr_id=?,pst_view_count=? where pst_id=?]
```

동시성 5라는 극히 낮은 부하에서도 재현된다는 것은, 실제 k6 부하(수십~수백 VU)에서는
이 데드락이 훨씬 더 빈번할 것이라는 강한 신호다. 원인은 Hibernate가 `Post` 엔티티
전체를 더티 체킹으로 UPDATE하기 때문에(단일 카운터 컬럼만 바꾸는 게 아니라 title,
content 등 전체 컬럼을 매번 다시 쓴다) 락 보유 시간과 충돌 표면이 더 넓어진 것으로
보인다 — `update posts set brd_id=..., pst_content=..., pst_title=..., ...` 전체
컬럼이 SET 절에 나열되는 것이 그 증거. 이는 개선 우선순위를 더 높인다: 단순 원자적
`UPDATE posts SET like_count = like_count + 1 WHERE id = ?`로 바꾸면 락 보유 시간이
크게 줄어 이 데드락 빈도도 함께 낮아질 가능성이 높다.

## 해결 방법

| 후보 | 효과 | 트레이드오프 |
|------|------|--------------|
| Redis INCR 버퍼 + 주기 flush | row 경합 소멸 (조회수와 동일 기존 패턴 재사용) | 카운트 표시 지연(초 단위), flush 실패 시 유실 대비 필요 |
| 원자 UPDATE (`SET like_count=like_count+1`) | 엔티티 로드/더티체킹 제거 → 락 보유 시간 최소화 | JPA 우회(@Modifying), 영속성 컨텍스트 정합 주의 |
| 카운터 테이블 분리 | 본문 조회와 락 분리 | 조인 or 2차 조회 추가 |
| 낙관적 락 + 재시도 | 데드락 방지 | 재시도 비용, 고경합 시 오히려 악화 |
