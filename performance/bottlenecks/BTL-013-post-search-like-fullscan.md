# BTL-013: 게시글 검색의 LIKE 전체 스캔

> 유형: Index / DB
> 상태: 확정
> 관련: EXP-005(H2 기각 과정에서 "slow query 의 진짜 주인"으로 지목) · OPT 미착수

## 증상

`GET /api/posts/search` 는 **가장 빠른 요청조차 65.7ms** 다. normal-day 5회 세트에서
회차별 최솟값이 65.7 · 66.3 · 78.9 · 67.2 · 65.8ms 로, **단 한 건도 30ms 를 넘지 않은 적이
없다.** 평균 87.5ms, p95 110.9ms, p99 206.1ms.

전체 요청의 1.06% 에 불과한데 **응답 시간 총합의 6.1%** 를 쓴다.

## 원인

`LIKE '%키워드%'` 는 앞이 와일드카드라 B-tree 인덱스를 탈 수 없다. 옵티마이저가 남는
선택지는 전체 스캔뿐이다.

**쿼리 개수의 문제가 아니라 쿼리 한 개가 느린 문제다.** 서버 측정이 이를 명확히 가른다.

| 지표 | 값 | 읽는 법 |
|---|---:|---|
| 요청당 쿼리 수 | 6.2개 | N+1 이 아니다 — 댓글 목록은 개선 전 112개였다 |
| 요청당 DB 시간 | **81.37ms** | 응답의 거의 전부 |
| 요청당 응답 시간 | 85.95ms | |
| DB 시간 비중 | **95%** | 앱에서 하는 일이 없다는 뜻 |

쿼리 6개가 81ms 를 쓰므로 **쿼리당 13.6ms** 다. 같은 실행에서 댓글 목록의 쿼리당 시간은
1.27ms, 게시글 상세는 0.39ms 였다.

## 영향

- **slow query 로그의 주인이다.** EXP-005 는 H2(인덱스 미사용 풀스캔)를 기각하면서
  "풀스캔은 실재하지만 그 대부분이 `post_search` 의 LIKE 검색이고 비중이 낮다"고 적었다.
  그 판단이 두 번 확인됐다 — N+1 을 완전히 걷어낸 OPT-001·OPT-002 전후로 slow query 가
  659 → 653 → 660건으로 **전혀 변하지 않았다.**
- **데이터가 커질수록 선형으로 나빠진다.** 전체 스캔이므로 게시글 수에 비례한다.
  medium(게시글 10,000건)에서 81ms 이고, large 규모에서는 그만큼 더 걸린다.
- 전체 p99 를 30ms 로 낮추려는 목표에서 이 엔드포인트는 **단독으로 1.06%p 를 차지**한다
  (목표 허용치가 1.00%).

## 재현 방법

```bash
# 1) 부하 없이 — 단발 요청의 DB 시간 비중을 본다
curl -s "localhost:18080/api/posts/search?keyword=<임의 단어>" -o /dev/null
curl -s localhost:18080/actuator/prometheus | grep 'http_server_query_time.*posts/search'

# 2) 실행 계획 확인 — type=ALL 이면 전체 스캔이다
docker exec perf-mysql mysql -uroot -pperfroot -D highteenday \
  -e "explain select * from posts where PST_title like '%시험%' and is_valid=1;"

# 3) 부하 — normal-day 에 이미 포함되어 있다
node tools/perf-run.js scenarios/normal-day.js --dataset medium --warmup 180
```

관찰 지표: `http.server.queries` / `http.server.query.time`(엔드포인트별),
`mysql.slowQueries`, `mysql.selectScan`.

## 해결 방법

| 후보 | 효과 | 트레이드오프 |
|------|------|--------------|
| **MySQL FULLTEXT 인덱스 + ngram 파서** | 전체 스캔 제거. 한국어는 형태소가 아니라 n-gram 으로 쪼개므로 `ngram` 파서가 필요하다 | 인덱스 저장 공간 증가. `MATCH ... AGAINST` 로 쿼리를 바꿔야 하고 **검색 결과 순서·매칭 규칙이 달라진다** — 성능이 아니라 기능이 바뀌는 부분이라 별도 검증이 필요하다 |
| 접두사 검색으로 제한 (`LIKE '키워드%'`) | 일반 B-tree 인덱스를 탄다. 변경이 가장 작다 | **기능 축소.** "시험" 으로 "기말시험" 을 찾을 수 없게 된다. 커뮤니티 검색으로는 받아들이기 어렵다 |
| 검색 엔진 분리 (Elasticsearch 등) | 가장 빠르고 랭킹·오타 보정까지 얻는다 | 운영 구성요소가 하나 늘고 색인 동기화 문제가 생긴다. **현재 규모에 맞지 않는다** |
| 결과 캐싱 | 반복 키워드에 효과 | 검색어 분포가 롱테일이면 적중률이 낮다. 근본 원인을 두고 증상만 가린다 |

**FULLTEXT + ngram 이 1순위다.** 다만 착수 전에 확인할 것이 둘 있다.

1. **실행 계획을 먼저 뜬다.** 위 재현 방법 2번으로 `type=ALL` 을 확인해야 "전체 스캔"이
   추론이 아니라 사실이 된다. 현재 근거는 DB 시간 비중 95% 와 `LIKE '%...%'` 라는 코드
   형태이며, **실행 계획은 아직 뜨지 않았다.**
2. **검색 결과가 달라지는 것을 기능 변경으로 다룬다.** `MATCH AGAINST` 는 매칭 규칙과
   정렬이 `LIKE` 와 다르다. 성능 실험과 같은 커밋에 넣으면 "느려졌나 빨라졌나"와
   "결과가 맞나"가 한 변수로 섞인다.
