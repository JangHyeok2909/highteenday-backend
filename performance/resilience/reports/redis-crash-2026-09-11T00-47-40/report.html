규칙. pre 기준은 pre 구간 표본의 중앙값이다(앞 30초는 웜업이라 뺀다). 정상 대역은 기준 × 배수 와 기준 ± 고정폭 중 느슨한 쪽이다 — 기준이 0 에 가까운 지표(Hikari pending, 오류율)에서 곱셈만 쓰면 잡음 하나가 미회복이 된다. 회복 시각은 장애 제거 이후 대역 안으로 들어와 30초 연속 머문 첫 표본이고, 회복까지는 그 시각에서 장애 제거 시각을 뺀 값이다. 잠깐 정상으로 보였다가 다시 튀는 구간(복구 직후 빈 캐시 스탬피드)을 회복으로 읽지 않으려고 유지 조건을 둔다.
⚠ 이동창 30초 포함 이 붙은 지표는 30초 이동창에서 계산된다 — 장애 중 표본이 창에서 빠질 때까지 값이 안 내려오므로, 실제 회복은 표의 값보다 최대 30초 빠르다. 창을 쓰지 않는 게이지(Tomcat busy · Hikari pending · MySQL threads_running)에는 이 지연이 없다. 이 표는 판정이 아니라 그래프를 읽는 규칙을 고정한 것이다 — 규칙이 같아야 고치기 전과 후의 값을 비교할 수 있다.

⚠ 유실 은 조회수 검사에서만 나온다. 식은 올랐어야 할 수 − 실제로 오른 수 이고, 올랐어야 할 수는 부하 발생기가 센다 — Redis 가 죽으면 조회수 증가가 아예 시도되지 않아 서버 어디에도 흔적이 없기 때문이다. 함께 적히는 불확실 건수는 타임아웃된 요청이다: 서버가 올렸는지 알 수 없다. Redis 버퍼는 이 식에 안 들어간다. 끝에 버퍼가 비었는지 확인하는 용도이고, 안 비었으면 숫자를 내지 않는다 — 아직 안 간 것과 사라진 것을 구분할 수 없어서다.

두 값이 어긋나는 이유는 둘 중 하나다. 어느 쪽인지는 사람이 정한다. ① 요청이 서버에 닿지 못했다 — 연결이 거부됐거나 앱이 응답을 끝내지 못해 서버 계측이 그 요청을 아예 세지 못한 경우다. 클라이언트의 "응답 없음(status 0)"이 많은데 서버 기록이 적으면 이쪽이다. ② 구간 경계에서 갈렸다 — k6 는 요청을 시작한 시각의 구간에 넣고, 서버 계측은 응답을 끝낸 시각에 센다. 장애 중 수십 초 매달린 요청은 k6 에서는 fault, 서버에서는 post 로 기록된다. post 의 서버 실패 건수가 클라이언트 실패보다 많으면 이쪽을 먼저 의심한다.
Spring Boot 의 http_server_requests 계측이다. /actuator 는 뺐다 — 헬스 폴러의 200 이 사용자 트래픽을 가린다. 예외 열이 비어 있는 것은 정상이다: 이 앱은 도메인 오류를 GlobalExceptionHandler 가 잡아 응답으로 바꾸므로 Micrometer 에는 "처리된 예외"로 남아 라벨이 none 이 된다. 예외 클래스가 여기 뜬다면 그건 핸들러를 거치지 않고 새어 나간 예외라는 뜻이라, 뜨는 것 자체가 신호다.

MySQL 소켓 읽기 타임아웃 0 (무한) 설정 없음 → 프레임워크 기본값 이미 실행 중인 쿼리가 응답 없는 소켓에서 풀려나는 시간. 0 이면 영원히 매달리며, 그 커넥션은 풀로 돌아오지 않는다.
MySQL 접속 타임아웃 30000ms 설정 없음 → 프레임워크 기본값 새 커넥션을 만들 때 TCP 연결에 쓰는 시간. 프록시가 연결을 끊은 뒤 재연결 시도에서 드러난다.
Redis 명령 타임아웃 (Lettuce) 60s (Lettuce RedisURI 기본) 설정 없음 → 프레임워크 기본값 Redis 가 응답하지 않을 때 명령 하나가 여기까지 매달린다. 실패 지연이 60,000ms 근처면 이 값이다.
Redis 접속 타임아웃 (Lettuce) 10s (Lettuce 기본) 설정 없음 → 프레임워크 기본값 Redis 컨테이너가 죽은 뒤 재연결 시도가 실패로 확정되기까지의 시간이다.
Tomcat 최대 워커 스레드 400 저장소 파일 src/main/resources/application.properties 한 의존성의 지연이 스레드를 모두 먹으면 무관한 엔드포인트까지 막힌다 — 폭발 반경의 상한이다.
Tomcat 커넥션 타임아웃 20s 설정 없음 → 프레임워크 기본값 스레드가 모두 묶였을 때 대기열의 연결이 서버 쪽에서 끊기는 시점이다.
헬스 폴러 응답 상한 (관측 도구) 4000ms 관측 도구 설정 (resilience/lib/health.js) 이 시간을 넘기면 표본이 "무응답"으로 기록된다. 앱이 죽었다는 뜻이 아니라 헬스 응답이 이 상한보다 느렸다는 뜻이다.
헬스 폴러 주기 (관측 도구) 5000ms 관측 도구 설정 (resilience/lib/health.js) 상태 전이 시각의 해상도다. 이 주기보다 짧은 장애는 표본 사이로 빠져나갈 수 있다.
노란 줄 7건은 컨테이너·JDBC URL·프로퍼티 파일 어디에도 값이 없어 프레임워크 기본값을 적어 둔 것이다. 실측이 아니라 가정이므로, 이 값을 근거로 결론을 쓰려면 먼저 명시적으로 설정하고 다시 돌리는 편이 낫다.
⚠ 출처가 "저장소 파일"인 값은 작업 트리의 파일에서 읽은 것이다. 앱 이미지가 소스보다 낡았다면(위 9번) 실제 적용된 값과 다를 수 있다.
