# EXP-005: 댓글 조회 쿼리 폭발 (N+1) 검증

> 상태: 계획 — **다음 실행 대상** (스프린트 P0-1). 자세한 순서는 [experiments/README.md](../README.md)
> 날짜: | 담당: | 관련: BTL-005

## 1. 목적

댓글 목록 API가 댓글 수에 비례해 쿼리를 발행하는지(N+1) 확인하고,
있다면 JOIN FETCH/배치 로딩으로 개선해 효과를 수치화한다.

## 2. 가설

리포트에서 관측된 것은 셋이다 — ① slow query 로그에 쌓인 쿼리가 많다, ② 초당 읽은 행 수가
크다, ③ MySQL 의 CPU·메모리는 여유인데 커넥션 풀만 포화다. 아래 **H1~H3 은 ①②를 설명하는
경쟁 가설**이고, **H4 는 그것들이 어떻게 ③으로 이어지는지에 대한 가설**이다.

따라서 이 실험의 일은 "N+1 이 있는지 보는 것"에서 **"셋 중 무엇이 지배적인지 가르는 것"**
으로 넓어진다. 채택된 하나만 `optimizations/OPT-XXX` 로 승격한다 — 한 번에 하나만 고친다.


> **normal-day-2026-08-26T00-06-28 기준 판단**
> **H1 N+1** 
> comment_list가 가장 응답요청이 느림. 요청수도 가장많음. read 오퍼레이션의 응답시간이 p99:2.22s 로 매우느림
> 결정적으로 요청당 쿼리수가 319로 많음+Slow query 수가 많음(759)
> 
>
> - 

> **H2 인덱스 미사용 풀스캔**  
> Rows read/sec = 4910/S로 초당 읽은 row의 수가 비정상적으로 많음 + 풀테이블 스캔수 = 997 
> 인덱스 풀스캔  의심됨
> 
> **검증**
> 풀스캔이 발생한 것은 맞으나 *쿼리당 읽은 수 = 초당 읽은 행 수/초당쿼리수* 로 봤을때 쿼리당 읽은 행수가 약 1행 정도가 나옴.
> 풀스캔으로 지연이 발생했다면 쿼리당 읽은 행수가 많이 나와야 정상.
> 거기다 풀스캔이 발생하는 부분이 post_search의 Like 검색인데 이는 비중이 매우 낮음.
> 

>


> **H3 트랜잭션 길이가 길다.**
> MySQL의 CPU,메모리 등등의 자원은 포화되지 않고 넉넉하다. 단지 커넥션풀만 포화되었으므로,
> 포화의 원인은 H1,H2로 인한 응답속도 지연으로 트랜잭션이 길어져 커넥션을 오래쓰고 있는 탓일거다.
> 
> **검증**
> run-ID = 2026-08-29의 결과들
> 커넥션 풀을 늘려도 응답시간에 변화가 없으며 애초에 다른 이전 실행에서도 커넥션풀 포화는 가끔 일어날뿐 대부분 커넥션 풀이 포화되지 않았다(rate=4로 의도적 조정해둔 탓).
> MYSQL 컨테이너의 CPU 사용량이 커넥션 풀을 2배로 늘려도 거의 변화가 없음.
> 
> 리포트로 확인한것: 응답시간이 커넥션 고갈로 인한 문제였다면 커넥션 획득 p95의 값이 원인이 되어 응답시간을 증가시키므로 해당 값이 커야만한다.
> 하지만 커넥션 획득 대기시간은 커넥션이 포화되지 않았을때와 거의 같음. -> 커넥션풀로 인한 응답 대기시간 증가가 아님.
> 커넥션 풀 max사용 수가 찍히므로 단순 한순간의 스파이크 였던 것으로 예상됨




## 3. 배경

p6spy가 이미 의존성에 있다(`p6spy-spring-boot-starter`) — 쿼리 수 계측에 그대로 사용.

## 4. 테스트 환경

| 항목 | 값 |
|------|-----|
| 데이터셋 | medium — Zipf 편중으로 최상위 인기글엔 댓글 수백 개 존재 |
| 캐시 상태 | warm |

## 5. 시나리오 / 실행 방법

```bash
# 1단계 (기능 검증): 단일 요청의 쿼리 수 세기 — 부하 없이
#   댓글 5개 글 vs 100개 글 각각 curl 1회 → p6spy 로그의 쿼리 수 비교
docker logs perf-app --tail 0 -f | grep -c "select" &   # 또는 spy.log 확인
curl -s "localhost:18080/api/posts/<댓글5개글>/comments" > /dev/null
curl -s "localhost:18080/api/posts/<댓글100개글>/comments" > /dev/null

# 2단계 (부하 검증): 댓글 열람 편중 부하에서 지연 분포
node tools/perf-run.js scripts/comments.js --dataset medium -e VUS=50 -e DURATION=5m --loadgen docker
```
