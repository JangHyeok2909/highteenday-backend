# EXP-000: 부하 발생기 이주가 측정 신뢰도를 높이는가

> 상태: **사전 판정 기준 작성 / M1 Before 측정 완료 / After 미실행**
>
> 최초 작성 및 Before 측정: 2026-08-11
> 관련 발견: E-01, E-02, E-09, E-26, T-02, T-03, T-29

이 실험은 애플리케이션 성능을 개선하는 실험이 아니다.
Windows에서 실행 중인 k6를 Docker Compose 환경으로 옮기는 B안이 **성능 측정 자체를 더 안정적이고 설명 가능하게 만드는지** 검증한다.

---

## 0. 먼저 알아야 할 핵심

### 이 실험이 묻는 질문

현재 실행 구조는 다음과 같다.

```text
Windows
├─ k6
└─ WSL2 VM
   ├─ Spring 애플리케이션
   ├─ MySQL
   ├─ Redis
   └─ Prometheus, Grafana, 익스포터
```

k6와 서버는 같은 물리 장비의 CPU와 디스크를 공유한다. 하지만 k6는 Windows 프로세스이고 서버는 WSL2 안의 컨테이너다.

이 구조에서는 다음을 확인하기 어렵다.

- k6가 CPU를 얼마나 사용했는가
- k6가 자원 부족 때문에 목표 부하를 만들지 못했는가
- Docker Desktop의 포트 프록시가 얼마나 지연을 추가했는가
- 같은 호스트의 IDE나 브라우저가 결과에 영향을 줬는가

B안은 k6를 Compose 컨테이너로 옮겨 같은 관측 범위 안에 넣고, CPU 예산과 자원 지표를 명시하는 방안이다.

### 이 실험이 증명하려는 것

B안 적용 후 다음이 개선되는지 확인한다.

1. 같은 조건을 반복했을 때 결과가 덜 흔들리는가
2. 호스트에 CPU 간섭이 생겼을 때 원인을 더 정확히 구분할 수 있는가
3. Windows와 WSL2 사이의 요청 경로에서 발생하는 추가 비용이 줄어드는가
4. 지금은 보이지 않는 k6 자원 사용량을 수집할 수 있는가

### 이 실험이 증명하지 않는 것

B안은 애플리케이션 코드를 바꾸지 않는다. 따라서 단순히 응답 시간이 빨라졌다는 사실만으로 B안이 성공했다고 판단할 수 없다.

요청 경로 자체가 다음처럼 바뀌기 때문이다.

```text
Before: Windows k6 → localhost:18080 → Docker Desktop 포트 프록시 → WSL2 → app
After:  WSL2 k6 컨테이너 → app:8080
```

After가 빨라지는 것은 예상 가능한 결과다. 중요한 것은 절대 지연이 아니라 **반복 편차, 간섭 배율, VU 증가에 따른 오버헤드 변화, 관측 가능성**이다.

### 사전 등록에 관한 주의

이 문서는 결과를 본 뒤 합격 기준을 유리하게 바꾸는 일을 막기 위해 사전 등록 형식을 사용한다. 판정 기준은 6장에 모아 두며, 변경이 필요하면 이유와 시점을 변경 이력에 남긴다.

다만 현재 작업 트리에서 이 실험 디렉터리는 아직 Git에 추적되지 않는다. 따라서 Git 이력만으로는 6장의 기준이 Before 측정 전에 확정됐다는 사실을 독립적으로 증명할 수 없다.

- 이 문서에는 당시 작성한 기준을 그대로 유지한다.
- 이 재작성에서는 판정 수치를 변경하지 않는다.
- After 측정 전에 문서와 Before 원자료를 버전 관리에 남겨야 이후 변경을 감사할 수 있다.

EXP-000이라는 번호를 사용한 이유도 여기에 있다. 측정 시스템을 믿을 수 없다면 EXP-001의 기준선도 의미가 없으므로, 논리적으로 먼저 검증해야 한다.

## 1. 실험 목적

다음 주장을 수치로 검증한다.

> k6를 Windows 네이티브 프로세스에서 Compose 컨테이너로 옮기면 성능 측정의 반복 정밀도와 원인 귀속 능력이 개선된다.

여기서 “반복 정밀도”는 같은 코드와 같은 조건으로 여러 번 실행했을 때 결과가 비슷하게 나오는 정도를 뜻한다.

“원인 귀속”은 결과가 느려졌을 때 애플리케이션, k6, 호스트, 네트워크 경로 중 어디에서 문제가 발생했는지 구분할 수 있는 정도를 뜻한다.

## 2. 검증할 가설

### M1. 반복 정밀도

**예상**

같은 시나리오를 10회 반복했을 때 전체 요청 p95의 변동계수(CV)가 B안 적용 후 감소할 것이다.

**이유**

현재 k6는 CPU 제한이 없는 Windows 프로세스다. 실행 시점의 브라우저, IDE, Claude Code 등 다른 프로세스 상태에 따라 확보하는 CPU가 달라질 수 있다.

k6를 컨테이너로 옮기고 CPU 상한을 지정하면 이 변동을 제한하고 자원 사용량도 기록할 수 있다.

**판정 지표**

```text
p95 CV = 10회 p95의 표본 표준편차 ÷ 10회 p95의 평균
```

CV는 단위가 없는 비율이다. 평균 지연이 달라진 두 환경의 반복 편차를 비교할 때 사용할 수 있다.

### M2. CPU 간섭에 대한 내성과 원인 구분

**예상**

테스트 중 호스트에 같은 CPU 부하를 주입했을 때 다음 차이가 나타날 것이다.

- Before: 애플리케이션 지연이 크게 흔들릴 수 있음
- After: k6가 자신의 CPU 한계에 먼저 도달하고, 부하 발생 미달 신호가 나타남

**확인할 k6 신호**

- `dropped_iterations`
- k6 CPU 포화
- 목표 RPS 또는 iteration 미달

**의미**

After에서도 애플리케이션 p95만 Before와 비슷하게 증가하고 k6 측 포화 신호가 없다면, B안이 간섭 원인을 분리하는 데 도움이 되지 않은 것이다.

### M3. VU 증가에 따른 요청 경로 오버헤드

**예상**

VU가 증가할수록 k6가 측정한 왕복 시간과 서버가 측정한 처리 시간의 차이가 커질 수 있다. B안은 Docker Desktop 포트 프록시를 제거하므로 이 증가 기울기를 낮출 것이다.

**측정값**

```text
경로 오버헤드 상한 = k6 평균 응답 시간 - 서버측 평균 처리 시간
```

이 값은 포트 프록시 비용만 의미하지 않는다. 다음 시간이 모두 섞여 있다.

- 네트워크 이동
- 연결 수립
- Docker Desktop 포트 프록시
- Tomcat 요청 수용 대기
- k6 VU 스케줄링
- 그 밖의 클라이언트 측 대기

따라서 이 값을 “포트 프록시 비용”이라고 부르면 안 된다. 여러 경로 비용을 합친 **상한값**으로 해석해야 한다.

판정에는 절대값이 아니라 VU를 올릴 때 이 값이 증가하는 기울기의 Before/After 비율을 사용한다.

### M4. k6 자원 관측 가능성

**예상**

- Before: cAdvisor가 Windows 프로세스인 k6를 볼 수 없음
- After: k6가 컨테이너가 되므로 CPU와 메모리 시계열을 수집할 수 있음

B안 적용 후에도 k6 자원 지표가 없다면 관측 공백을 해결하지 못한 것이다.

## 3. 실험 배경

### 3-1. 현재 환경의 구조적 문제

`performance/environment/README.md:31-32`는 부하 발생기와 대상 서버를 분리하는 것을 원칙으로 선언한다. 하지만 현재 23개 실행은 모두 한 물리 호스트에서 수행됐다.

| 항목 | 현재 상태 | 왜 문제인가 |
|---|---|---|
| k6 실행 | Windows 네이티브 프로세스 | cgroup CPU 제한과 컨테이너 지표를 적용할 수 없음 |
| SUT 실행 | WSL2 VM 안의 컨테이너 8종 | k6와 다른 운영체제 스케줄링 영역에 있음 |
| k6 자원 관측 | 불가 | WSL2 안의 cAdvisor는 Windows k6를 볼 수 없음 |
| k6 CPU 상한 | 없음 | 호스트 상태에 따라 k6가 사용하는 CPU가 달라질 수 있음 |
| WSL2 총 자원 예산 | 미정의 | `.wslconfig`가 없어 기본값을 사용함 |
| 요청 경로 | `localhost:18080` 경유 | Docker Desktop 포트 프록시가 측정 경로에 포함됨 |
| 관측 도구 상한 | 없음 | Prometheus, Grafana, 익스포터, cAdvisor가 제한 없이 자원을 사용할 수 있음 |

### 3-2. 왜 일반적인 Before/After 비교를 하면 안 되는가

일반적인 성능 실험은 코드만 바꾸고 환경은 같아야 한다. 그래야 응답 시간 차이를 코드 변경 효과로 해석할 수 있다.

하지만 B안은 요청 경로와 실행 위치를 바꾼다. 따라서 다음 비교는 의미가 없다.

```text
After p95가 Before p95보다 낮다
→ B안이 측정 신뢰도를 높였다
```

After p95가 낮은 이유는 단순히 포트 프록시가 빠졌기 때문일 수 있다.

이 실험은 대신 다음 비율을 비교한다.

- p95 CV의 After/Before 비율
- CPU 간섭 시 p95 상승 배율
- 경로 오버헤드 기울기의 After/Before 비율
- k6 자원 시계열의 존재 여부

기울기 자체의 단위는 ms/VU다. 다만 After 기울기를 Before 기울기로 나눈 최종 비교값은 단위가 없는 비율이다.

### 3-3. 서버측 처리 시간 수집 가능 여부

Spring 애플리케이션의 서버측 지연 지표는 이미 Prometheus에 들어오고 있다.

```text
http_server_requests_seconds_bucket
http_server_requests_seconds_sum
http_server_requests_seconds_count
```

현재 지표 카탈로그에는 등록되지 않았지만 직접 PromQL로 조회할 수 있다.

```promql
1000 * sum(rate(http_server_requests_seconds_sum{job="spring-app"}[$RANGE]))
     / clamp_min(
         sum(rate(http_server_requests_seconds_count{job="spring-app"}[$RANGE])),
         0.0001
       )
```

평균끼리 빼는 이유가 중요하다.

```text
k6 p95 - 서버 p95
```

이 계산은 “차이의 p95”가 아니다. 서로 다른 요청이 각 백분위에 들어갈 수 있으므로 통계적으로 올바른 경로 오버헤드가 되지 않는다.

따라서 M3에서는 다음 평균 차이만 사용한다.

```text
k6 평균 - 서버 평균
```

## 5. M1 Before 실행 방법

### 5-1. 스택 시작

```bash
cd performance

docker compose \
  -f environment/docker-compose.perf.yml \
  --env-file environment/.env.perf \
  up -d
```

### 5-2. 같은 조건으로 10회 반복

```bash
K6_BIN="C:/ProgramData/chocolatey/lib/k6/tools/k6-v2.1.0-windows-amd64/k6.exe" \
node tools/repeatability.js scripts/posts.js \
  --runs 10 \
  --vus 20 \
  --duration 90s \
  --dataset large \
  --env perf-mi-before \
  --reset restart \
  --note "EXP-000 before (k6 native on Windows)"
```

### 5-3. 반복 사이 초기화

`tools/repeatability.js`는 각 실행 사이에 다음 절차를 수행한다.

1. `perf-app` 컨테이너 재시작
2. `/actuator/health`가 UP이 될 때까지 대기
3. Redis `FLUSHALL` 실행
4. 지정된 안정화 시간만큼 대기
5. 다음 반복 실행

이 절차는 매번 JVM과 캐시가 차가운 상태에서 시작하게 한다. 운영 중 웜 상태를 재현하는 방법은 아니지만, 현재 문서화된 실험 절차와 일치시키기 위해 의도적으로 선택했다.

### 5-4. 환경 이름 분리

Before와 After는 다음 환경 이름을 사용한다.

- Before: `perf-mi-before`
- After: `perf-mi-after`

기존 `perf` 이력과 섞이면 T-02 때문에 부하 조건이 다른 실행을 기준선으로 선택할 수 있다.

## 6. 사전 판정 기준

이 장의 표를 판정 기준의 정본으로 사용한다. Before 결과를 해석하더라도 이 수치는 바꾸지 않는다.

### 6-1. 판정표

| 가설 | 1차 지표 | 합격 | 부분 개선 | 기각 |
|---|---|---|---|---|
| M1 | p95 CV 비율 | After ≤ Before × 0.5 | After ≤ Before × 0.75 | After > Before × 0.9 |
| M2 | CPU 간섭 시 p95 상승 배율과 k6 포화 신호 | After 상승 배율이 더 작고 k6 신호도 관측 | 상승 배율만 개선 | 상승 배율이 개선되지 않거나 k6 신호가 없음 |
| M3 | 경로 오버헤드 기울기 비율 | After ≤ Before × 0.5 | After ≤ Before × 0.75 | After > Before × 0.75 |
| M4 | k6 자원 시계열 | Before 없음, After 있음 | 해당 없음 | Before에도 수집 가능하거나 After에도 없음 |

### 6-2. M1 기준의 미분류 구간

원래 등록한 M1 기준에는 다음 구간의 판정이 없다.

```text
Before × 0.75 < After ≤ Before × 0.9
```

이 재작성에서 새 기준을 만들면 Before 결과를 본 뒤 규칙을 추가하는 일이 된다. 따라서 해당 구간이 나오면 임의로 합격이나 기각으로 분류하지 않고 **사전 기준만으로 판정 불가**라고 기록한다.

Before p95 CV가 108.77%이므로 실제 경계값은 다음과 같다.

| 결과 | After p95 CV |
|---|---:|
| 합격 | 54.39% 이하 |
| 부분 개선 | 54.39% 초과, 81.58% 이하 |
| 사전 기준상 미분류 | 81.58% 초과, 97.89% 이하 |
| 기각 | 97.89% 초과 |

### 6-3. M3 기준 문구 정리

초판의 가설 설명에는 “After 기울기가 Before의 0.5배를 넘으면 기각”이라고 적힌 문장이 있었다. 하지만 같은 초판의 정식 판정표는 0.5배까지 합격, 0.75배까지 부분 개선, 0.75배 초과를 기각으로 정했다.

이 문서는 정식 판정표를 정본으로 사용한다. 0.5배 초과를 즉시 기각한다는 문장은 표와 충돌하므로 제거했다. 판정표의 숫자는 변경하지 않았다.

## 8. M1 Before 결과

**M1 Before 기준값은 p95 CV 108.77%다.**

CV 108.77%는 p95의 표준편차가 평균보다 더 크다는 뜻이다.

실제 p95는 같은 코드와 같은 설정에서 110.1ms부터 1052.4ms까지 약 9.6배 차이가 났다. 반면 요청 수 CV는 0.98%이므로 실행마다 부하량이 크게 달라진 것은 아니다.

### 8-2. p95만 불안정한 이유: 지연 분포의 절벽

p90과 p99는 안정적인데 그 사이에 있는 p95만 크게 흔들렸다.

```text
빠른 요청                                        느린 요청
p50 ≈ 16ms ───── p90 ≈ 94ms ────── [큰 빈 구간] ────── p99 ≈ 3824ms
                                      ↑
                                p95가 이 경계에 위치
```

요청 지연이 부드럽게 증가한다면 느린 요청 몇 개가 늘어도 p95가 조금만 움직인다.

하지만 요청이 “빠른 집단”과 “매우 느린 집단”으로 갈라져 있으면 상황이 다르다. p95가 두 집단의 경계에 있을 때 느린 요청 비율이 조금만 변해도 p95는 빠른 집단에서 느린 집단으로 건너뛴다.

이상치 한두 개만 제거해도 문제가 완전히 사라지지 않는다.

| 사용한 표본 | p95 CV |
|---|---:|
| 전체 10회 | 108.77% |
| 1회차 제외 | 71.94% |
| 1회차와 5회차 제외 | 31.90% |

두 번의 큰 값을 제외해도 p95 CV는 31.90%다. 따라서 단순한 이상치 하나의 문제가 아니라 분포 구조의 문제다.

### 8-3. 기능별로 나누면 로그인 지연이 보임

k6의 `feature` 태그를 사용해 로그인 요청과 게시글 요청을 분리했다.

| 요청 집단 | 10회 평균 | CV | 해석 |
|---|---:|---:|---|
| 전체 p95 | 277.3ms | **108.77%** | 두 요청 집단을 합친 값 |
| auth 중앙값 | 85.2ms | **0.78%** | 일반적인 로그인은 매우 안정적 |
| auth p90 | 1934.2ms | 18.34% | 느린 로그인 집단이 존재 |
| auth p95 | 2537.0ms | 13.56% | 로그인 느린 꼬리는 반복해서 나타남 |
| post 중앙값 | 12.6ms | 4.94% | 일반 게시글 요청은 빠르고 안정적 |
| post p95 | 108.1ms | 21.17% | 대부분의 게시글 요청은 108ms 이내 |
| post p99 | 3862.1ms | 7.88% | 게시글 요청에도 매우 느린 소수의 꼬리가 존재 |

이 표에서 직접 확인할 수 있는 사실은 다음과 같다.

1. 로그인 중앙값은 약 85ms로 안정적이다.
2. 로그인 p90은 약 1.9초다.
3. 로그인 요청은 하나의 부드러운 분포가 아니라 빠른 집단과 느린 집단으로 갈라져 있다.
4. 게시글 요청도 p99에는 약 3.9초의 느린 꼬리가 있다.
5. 전체 p95가 불안정한 반면 각 집단의 고정된 백분위는 상대적으로 훨씬 안정적이다.

“구성 요소는 안정적인데 합계만 흔들린다”는 말은 모든 구성 요소의 CV가 작다는 뜻은 아니다. 전체 p95의 108.77%와 비교하면 auth 및 post 백분위의 반복 편차가 훨씬 작다는 뜻이다.

### 8-4. 왜 게시글 시나리오가 매번 로그인하는가

`performance/scripts/posts.js`는 iteration 시작 시 `ensureSession()`을 호출한다.

k6는 현재 설정에서 iteration이 끝날 때 VU의 쿠키 저장소를 초기화한다. 다음 iteration이 시작되면 accessToken 쿠키가 없으므로 `ensureSession()`은 다시 전체 로그인을 수행한다.

실측값은 다음과 같다.

| 값 | 10회 평균 |
|---|---:|
| iterations | 187.2 |
| HTTP 요청 | 904.9 |
| 로그인 요청 | 약 187.2 |
| 로그인 비율 | **20.69%** |

각 iteration에서 로그인 한 번이 발생하므로 로그인 요청 수는 iteration 수와 거의 같다.

```text
187.2 ÷ 904.9 ≈ 0.2069
```

즉 게시글 시나리오에서 발생한 HTTP 요청 약 다섯 개 중 하나가 로그인이다.

### 8-5. 로그인 처리 경로와 BCrypt

로그인 요청은 다음 코드 경로를 지난다.

1. `POST /api/user/login` 요청
2. 이메일로 사용자 조회
3. `passwordEncoder.matches()`로 비밀번호 검증
4. JWT 쿠키 생성
5. 응답 반환

`AppConfig`의 `passwordEncoder`는 `BCryptPasswordEncoder`다. 따라서 각 iteration은 BCrypt 비밀번호 검증을 한 번 수행한다.

BCrypt는 비밀번호 대입 공격을 어렵게 만들기 위해 의도적으로 CPU를 많이 사용하는 알고리즘이다.

이번 실행의 애플리케이션 CPU 지표는 다음 범위였다.

- 최대 CPU 사용량: 1.47~1.65코어
- 컨테이너 CPU 한계: 2코어
- CPU throttling: 3.27~11.02%

20개 VU가 비슷한 시점에 새 iteration을 시작하면 BCrypt 검증도 동시에 몰릴 수 있다. 2코어 안에서 동시에 처리하지 못한 로그인은 앞선 BCrypt 계산이 끝날 때까지 기다리게 된다.

이 모델은 다음 관측과 일치한다.

- 한산할 때의 로그인: 중앙값 약 85ms
- 로그인이 겹칠 때의 느린 집단: p90 약 1.9초, p95 약 2.5초

다만 현재 데이터에는 `passwordEncoder.matches()` 자체의 실행 시간이나 대기열 길이가 없다.

따라서 결론을 두 단계로 구분해야 한다.

**실측으로 확인된 결론**

> 전체 지연의 절벽은 로그인 요청 집단과 강하게 연결돼 있다.

**현재 증거에 가장 잘 맞는 원인 설명**

> 반복적인 동시 로그인으로 BCrypt CPU 작업이 몰리고, 2코어 제한 안에서 대기열이 생긴다.

BCrypt 큐잉을 직접 증명하려면 메서드 실행 시간, 동시 실행 수 또는 프로파일러 결과가 추가로 필요하다.

### 8-6. 전체 p95가 로그인 분포의 중간을 자른다는 계산

전체 요청 중 로그인 비율은 약 20.69%이고 나머지 요청은 약 79.31%다.

대부분의 게시글 요청이 관련 로그인 요청보다 빠르다고 단순화하면 전체 백분위를 로그인 집단 안의 위치로 근사할 수 있다.

#### 전체 p90

```text
(0.90 - 0.7931) ÷ 0.2069 ≈ 0.5166
```

전체 p90은 로그인 집단의 약 51.7번째 백분위에 해당한다.

로그인 중앙값은 85.2ms이고 실제 전체 p90은 93.7ms다. 서로 가까우므로 이 근사 모델과 맞는다.

#### 전체 p95

```text
(0.95 - 0.7931) ÷ 0.2069 ≈ 0.7583
```

전체 p95는 로그인 집단의 약 75.8번째 백분위에 해당한다.

이 위치는 빠른 로그인 집단과 2~3초짜리 느린 로그인 집단 사이의 급격한 경계에 걸려 있는 것으로 보인다.

예를 들어 다음과 같은 차이만 있어도 전체 p95가 크게 바뀔 수 있다.

```text
실행 A: 로그인 중 77%가 빠름 → 76번째 백분위도 빠른 집단
실행 B: 로그인 중 74%가 빠름 → 76번째 백분위가 느린 집단
```

로그인 충돌 비율이 3%p만 달라져도 전체 p95는 약 100ms에서 1초 이상으로 이동할 수 있다.

#### 이 계산의 한계

이 계산은 auth와 post 요청이 속도순으로 완전히 분리된다고 가정한 근사다.

실제로 post p99가 약 3.9초이므로 두 분포는 겹친다. 현재 저장된 요약 백분위만으로는 “전체 p95가 정확히 auth p75.8이다”라고 증명할 수 없다. 정확한 위치를 확인하려면 요청별 원시 지연 분포가 필요하다.

따라서 75.8%는 정확한 등식이 아니라 다음 현상을 설명하는 모델로 사용한다.

> 로그인 요청이 전체의 약 20%이고 로그인 분포에 큰 절벽이 있기 때문에, 전체 p95가 그 절벽의 영향을 크게 받는다.

### 8-7. 다른 지표를 이용한 교차 확인

전체 p90은 CV 2.73%로 안정적이다. 앞의 근사에 따르면 전체 p90은 로그인 중앙값 근처를 자른다. 로그인 중앙값도 CV 0.78%로 매우 안정적이다.

전체 p99는 CV 6.81%로 안정적이며 평균 약 3.8초다. post p99도 평균 약 3.9초, CV 7.88%다. 따라서 가장 느린 상위 1% 구간은 게시글 요청의 느린 꼬리와 연결돼 있음을 알 수 있다.

이 두 교차 확인은 다음 해석을 지지한다.

- p90: 안정적인 빠른 로그인 경계
- p95: 빠른 로그인과 느린 로그인 사이의 절벽
- p99: 반복적으로 나타나는 게시글 요청의 느린 꼬리

### 8-8. 쓰기 지표도 로그인 영향을 받음

로그인 요청은 `feature=auth`이면서 `op=write`로 태깅된다. 따라서 write 지표는 게시글 작성·수정·삭제뿐 아니라 로그인도 포함한다.

예를 들어 10회차 실행에서는 다음 값이 나왔다.

| 지표 | 값 |
|---|---:|
| write p90 | 110.8ms |
| write p95 | 1791.6ms |

5개 백분위만 이동했는데 지연이 약 16배 증가한다. 이는 “쓰기 SLO”가 실제 게시글 쓰기 성능뿐 아니라 로그인 BCrypt 지연에도 크게 좌우됨을 보여준다.

10회 평균은 write p90 285.8ms, write p95 1987.9ms다. p90 평균이 큰 이유는 일부 실행에서 p90 자체가 느린 로그인 집단으로 넘어갔기 때문이다.

### 8-9. 초판 해석의 정정

초판은 p95 편차의 주원인을 Zipf 선택과 랜덤 검색어 같은 시나리오 무작위성으로 추정했다.

기능별 분해 후 이 설명은 주원인으로 보기 어렵게 됐다.

- post p95 CV는 21.17%다.
- auth 중앙값과 상위 백분위는 각각 비교적 안정적이다.
- 전체 p95만 108.77%로 크게 흔들린다.
- 전체 p95가 로그인 분포의 절벽을 자른다는 혼합 모델이 p90과 p99 결과에도 부합한다.

따라서 현재 가장 강한 설명은 다음과 같다.

> p95 편차는 무작위 게시글 선택보다 매 iteration 로그인과 로그인 지연의 이중 분포에 더 크게 좌우된다.

고정 난수 시나리오는 여전히 무작위성의 기여분을 분리하는 데 쓸 수 있지만, 현재 결과만 보면 최우선 후속 실험은 아니다.

### 8-10. 이 정정이 M1 해석에 미치는 영향

초판은 시나리오 무작위성이 원인이라면 k6 이주가 p95 CV를 줄이기 어렵다고 예상했다.

현재 분석은 다르다.

로그인 절벽이 CPU 경합과 연결돼 있다면 k6가 같은 물리 CPU를 사용하는 방식도 BCrypt 대기열에 영향을 줄 수 있다. 따라서 B안이 p95 CV를 줄일 가능성은 실제로 있다.

다만 M1은 이제 순수한 “k6 측정기 편차”만 측정하지 않는다. 다음 두 효과가 합쳐진 결과를 측정한다.

1. k6 실행 위치와 자원 제한이 만드는 측정 환경 편차
2. 애플리케이션의 반복 로그인과 BCrypt CPU 큐잉 편차

After p95 CV가 줄어들면 B안이 전체 측정 편차를 줄였다고 말할 수 있다. 하지만 그 감소가 포트 프록시 제거, k6 CPU 제한, BCrypt 충돌 감소 중 무엇 때문인지는 p95 하나만으로 구분할 수 없다.

따라서 After에서는 최소한 다음 지표를 함께 비교한다.

- auth 중앙값
- auth p90
- auth p95
- post p95
- post p99
- 앱 CPU 사용량
- CPU throttling
- k6 CPU 사용량
- iterations와 총 요청 수

6장의 M1 판정 기준은 그대로 유지한다.

### 8-11. 부수 발견: 현재 p95 회귀 게이트는 이 워크로드에 맞지 않음

`performance/regression/rules.json`의 p95 규칙은 직전 실행보다 20% 악화하면 FAIL한다. 노이즈 하한은 5ms다.

하지만 아무것도 변경하지 않은 10회 반복에서 p95 CV는 108.77%였다.

예를 들어 같은 코드에서도 p95가 110ms인 실행 다음에 203ms인 실행이 오면 약 85% 악화로 보인다. 실제 회귀가 없어도 20% 게이트를 쉽게 넘는다.

반면 다음 지표는 비교적 안정적이었다.

- p90 CV: 2.73%
- p99 CV: 6.81%
- 평균 CV: 4.80%
- TPS CV: 2.05%

따라서 이 워크로드의 전체 p95를 직전 한 번의 실행과 비교하는 현재 게이트는 정상 편차와 회귀를 구분하기 어렵다.

이 발견은 B안의 성공 여부와 별개로 유효하다.

## 11. 알려진 한계

### 11-1. 표본 수가 10회임

10회로 계산한 CV는 신뢰구간이 넓다. Before와 After CV 차이가 우연일 가능성을 배제할 수 없다.

이 실험으로 통계적 유의성을 주장하지 않는다. 정직한 결론 범위는 “등록한 조건에서 감소 또는 증가하는 방향이 관측됐다”까지다.

### 11-2. 매번 콜드 스타트로 시작함

각 반복 전에 애플리케이션을 재시작하므로 JIT 컴파일, 커넥션 준비, 캐시 미스 편차가 CV에 포함된다.

Before와 After에서 같은 리셋 절차를 사용하면 비교 조건은 유지된다. 하지만 운영 중 웜 상태의 반복 편차를 대표하지는 않는다.

### 11-3. M1에 애플리케이션 로그인 동작이 강하게 섞임

전체 p95는 k6 자체 편차만 측정하지 않는다. 매 iteration 로그인과 BCrypt 큐잉이 큰 영향을 준다.

B안이 전체 편차를 줄였는지는 판단할 수 있지만, 측정기 개선과 애플리케이션 큐잉 개선을 p95 하나로 분리할 수 없다.

### 11-4. BCrypt 큐잉은 직접 계측하지 않음

로그인 분포와 CPU 지표는 BCrypt 큐잉 설명과 일치한다. 하지만 `passwordEncoder.matches()` 실행 시간과 동시 실행 수를 직접 수집하지 않았다.

따라서 “로그인 절벽”은 실측 결론이고 “BCrypt 큐잉”은 가장 강한 원인 가설이다.

### 11-5. 백분위 혼합 계산은 근사임

auth와 post 분포는 겹친다. 전체 p95를 auth의 정확한 75.8번째 백분위라고 단정할 수 없다.

요청별 원시 지연 데이터가 없으므로 계산은 분포 구조를 설명하는 근사 모델로만 사용한다.

### 11-6. M2 판정이 완전히 정량화되지 않음

“After 상승 배율이 Before보다 비슷한가”를 구분할 숫자 기준이 없다. CPU 부하 주입 방식도 아직 정하지 않았다.

After 데이터를 보기 전에 절차를 확정하지 않으면 M2는 해석자 판단에 의존하게 된다.

### 11-7. M3에 필요한 VU 단계가 정해지지 않음

기울기를 계산하려면 여러 VU 값이 필요하다. 현재는 M1용 VU 20 실행만 있다.

VU 단계와 각 단계의 반복 횟수를 Before/After 데이터 수집 전에 확정해야 한다.

### 11-8. 경로 오버헤드는 여러 지연을 합친 상한임

`k6 평균 - 서버 평균`에는 프록시 외의 대기 시간도 포함된다. B안 전후에 섞인 성분이 동일하지 않으면 기울기 차이를 포트 프록시 제거 효과만으로 해석할 수 없다.

### 11-9. 단일 시나리오만 사용함

현재 결론은 `posts.js`에만 적용된다. 로그인 비율과 요청 조합이 다른 시나리오에서도 같은 결과가 나온다는 보장은 없다.

## 12. 후속 작업

### 우선순위 1: M2와 M3 절차를 사전 확정

After 구현과 측정 전에 다음을 정한다.

- CPU 부하 주입 명령과 강도
- 간섭 실험 반복 횟수
- VU 단계와 단계별 반복 횟수
- k6 컨테이너 CPU 및 메모리 한계

### 우선순위 2: 로그인과 게시글 측정을 분리

별도 후속 실험에서 다음 방법을 검토한다.

- iteration 사이에서 세션을 유지하는 시나리오
- 로그인 전용 시나리오
- 로그인 포함 결과와 제외 결과를 동시에 보고하는 방식

EXP-000 진행 중에 `posts.js` 동작을 바꾸면 Before와 After 조건이 달라지므로 이 실험에서는 변경하지 않는다.

### 우선순위 3: BCrypt 대기열 직접 계측

다음 중 하나로 원인 가설을 검증한다.

- `passwordEncoder.matches()` 실행 시간 측정
- 동시 로그인 수 측정
- 짧은 프로파일러 실행
- 로그인 전용 VU 단계별 실험

### 우선순위 4: 고정 난수 시나리오

게시판, Zipf 인덱스, 검색어 선택을 고정해 무작위성의 기여분을 별도로 측정할 수 있다.

현재 증거는 무작위성이 주원인이 아니라고 가리키므로 로그인 분리와 BCrypt 계측보다 우선순위가 낮다.

### 우선순위 5: 반복 측정 도구 유지

`performance/tools/repeatability.js`를 환경 변경 전후에 계속 실행하면 측정 품질의 추세를 남길 수 있다.

### 우선순위 6: k6 지표 정식 등록

M4가 채택되면 k6 CPU와 메모리 지표를 `metrics-catalog.js`에 등록한다. T-29의 MySQL 지표 추가와 함께 관리할 수 있다.

### 우선순위 7: CI 러너 편차 측정

같은 반복 실험을 CI 러너에서 수행하면 E-26의 CI 전용 노이즈 기준을 만들 수 있다.
