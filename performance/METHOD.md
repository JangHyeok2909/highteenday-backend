# 측정 방법

성능 수치는 실행 조건과 관측 범위를 함께 제시할 때만 의미가 있다. 빠르거나 느린 숫자보다
같은 질문을 같은 조건에서 다시 측정할 수 있는지가 우선이다.

## 이 규칙이 생긴 이유

이 저장소에서는 측정 결과를 두 번 잘못 해석했다. 한 번은 회귀 판정 도구가, 한 번은 사람이 틀렸다.

- 회귀 판정기가 같은 시나리오라는 이유만으로 직전 실행을 기준선으로 골랐다. 그 결과 200 VU·large
  데이터셋 실행이 15 VU·small 데이터셋 실행과 비교돼, p95 101.21ms → 60,000.96ms를 +59,183.7% 회귀로
  보고했다. 부하와 데이터 크기의 차이를 코드 성능 저하로 읽은 것이다. 기준선은
  [normal-day-2026-08-04T06-38-42](reports/runs/normal-day-2026-08-04T06-38-42/run.json), 대상은
  [normal-day-2026-08-05T09-39-43](reports/archive/runs/normal-day-2026-08-05T09-39-43/run.json)이고, 보고 값은
  대상 실행의 `regression.comparisons`에 남아 있다. 지금은 아래 "비교 가능한 실행"의 도구 강제 조건이
  같은 실행만 기준선으로 고른다([comparability.js](tools/lib/comparability.js), [conditions.js](tools/lib/conditions.js)).
- 2026-08-15~19에 저장한 평상시 시나리오의 p95 10,000~17,000ms를 사람이 애플리케이션 지연으로 읽고
  호스트 환경에서 원인을 찾았다. 실제로는 도착률이 처리 용량을 넘겨 요청이 커넥션 풀 앞에서 기다린
  상태(포화)였고, 같은 코드를 도착률 4/s로 다시 재면 278ms였다. 278ms 실행의 ID는 기록하지 않았고,
  수치는 [saturation.js](tools/lib/saturation.js) 머리 주석에 남은 값이다. 지금은 앱 CPU 제한 비율,
  커넥션 대기, 목표 도착률 달성도로 포화 여부를 판정하고, 포화 실행에는 비포화 실행과 비교할 수
  없다고 리포트에 표시한다.

아래 규칙은 이 두 오류를 다시 만들지 않기 위한 조건이다.

## 실행 전에 고정할 것

- 앱 이미지와 소스 커밋
- dirty 작업 트리와 이미지 생성 시각
- 데이터셋 이름과 상태 지문
- 시나리오, 부하 모델, 도착률과 구간
- 앱, MySQL, Redis의 자원 한계
- 부하 발생기 위치
- Redis 초기 상태

앱 이미지가 소스보다 오래됐거나 데이터 상태가 다르면 실행은 보존하되 코드 변경의 효과로
귀속하지 않는다.

## 데이터와 워크로드

데이터셋은 행 수뿐 아니라 인기 데이터 편중, 관계 무결성, 파생 카운터를 포함한 실행 조건이다.
`datasets/verify.sh`를 통과하지 못한 데이터로 원인을 판단하지 않는다. 쓰기 실행 뒤 상태가
달라졌다면 같은 프로필 이름이어도 같은 데이터셋으로 보지 않는다.

개선 효과는 처리 용량 아래에서, 응답과 무관하게 정해진 도착률로 요청을 넣는 open model로 비교한다. 용량 한계를 찾는 실험만 도착률을
단계적으로 높인다. 응답이 빠르더라도 대상 코드 경로를 실행하지 않은 `200 []` 같은 결과는
성공 표본에서 제외한다.

## 비교 가능한 실행

Before와 After의 조건은 도구가 강제하는 것과 사람이 확인하는 것으로 나뉜다.

도구([conditions.js](tools/lib/conditions.js))는 다음 조건이 하나라도 다르면 기준선에서 빼고 상대 비교를
생략한다(blocking).

- 시나리오
- 실행 환경
- 데이터셋
- 부하 모델
- 부하 발생기 위치
- 측정 구간 구성(준비·측정·종료 구간 길이와 판정 구간)

다음 조건은 달라도 비교는 하되 경고를 남기고 `FAIL`을 `WARN`으로 낮춘다(degrading).

- 앱 이미지
- 시나리오 스크립트 지문
- 측정 중 대조 벤치 실행 여부
- k6 지표의 Prometheus 전송 여부

컨테이너 자원 한계와 캐시 상태는 도구가 비교하지 않으므로 사람이 Compose 파일과 실행 기록으로 확인한다.
조건이 다르면 각 실행을 독립 관측으로만 사용한다. 가장 최근 실행이라는 이유로 기준선을 선택하지 않는다.

## 지표를 읽는 순서

1. 실행 신원, 데이터셋과 주입 성공 여부를 확인한다.
2. check, 오류율, timeout과 dropped iteration을 확인한다.
3. p95와 p99가 timeout 상한에 잘렸는지 확인한다.
4. 앱 CPU, Tomcat busy, HikariCP active와 pending을 같은 시간축에서 본다.
5. MySQL QPS, 실행 스레드, lock wait와 rows read를 확인한다.
6. Redis 명령 지연, hit ratio, blocked client와 eviction을 확인한다.
7. 기능별 영향 범위를 좁힌 뒤 코드, 로그 또는 대조 실험으로 원인을 확인한다.

전체 지표 정의는 [metrics-catalog.js](tools/lib/metrics-catalog.js), 회귀 임계값은
[rules.json](regression/rules.json)에서 관리한다.
`rules.json`과 `regression/perf-regression.yml`의 머리 주석에는 아직 "직전 실행 대비"라는 옛 설명이 남아 있다.
실제 기준선은 위 비교 조건이 같은 실행이다.

## 포화와 timeout

포화 상태에서는 작은 환경 차이가 큐 길이와 지연을 크게 바꾼다. 이 구간은 용량 한계를
설명할 수 있지만 일반적인 코드 개선 Before/After에는 부적합하다.

timeout에 붙은 p95는 상한에서 잘린 값이므로 실제 처리 시간의 백분위로 읽지 않는다. 상태 코드,
무응답 수, 완료 iteration과 함께 해석한다. 클라이언트 timeout은 서버가 작업을 취소하거나
커밋하지 않았다는 증거가 아니다.

## 결론의 강도

| 표현 | 필요한 근거 |
|---|---|
| 관측 | `run.json`에 직접 기록된 값이다 |
| 지지 | 여러 지표가 설명과 일치하지만 다른 원인이 남아 있다 |
| 확인 | 코드, 로그 또는 대조 실험이 원인 고리를 직접 보여 준다 |
| 판정 불가 | 조건, 표본 또는 계측이 부족하다 |

상관관계를 원인으로 쓰지 않는다. 원인 설명에는 그 설명이 틀렸을 때 나타날 결과를 함께
적는다.

## 회귀 판정

비교 조건을 충족한 기준선이 없으면 상대 판정을 하지 않는다.

판정은 세 가지다.

- `PASS`: 상대 임계와 절대 한계를 넘지 않았다.
- `WARN`: 사람이 확인해야 하는 변화가 있다.
- `FAIL`: gate 지표가 실패 조건을 넘었다.

판정과 별도로 측정 상태를 기록한다. 필수 지표가 빠지면 `UNMEASURED`, 선택 지표가 빠지거나 측정 구간이
불완전하면 `PARTIAL`, 모두 있으면 `MEASURED`다([regression.js](tools/lib/regression.js)).

작은 절대 차이는 noise floor 아래에서 회귀로 판정하지 않는다. 실행 결과를 본 뒤 해당
실행만 통과하도록 임계값을 바꾸지 않는다.

## 사례 작성

[사례 문서](cases/README.md)에는 다음 항목만 둔다.

1. 사용자 영향과 가장 짧은 결론
2. 재현 조건과 비교를 제한하는 조건
3. 증거별 원인 고리와 확신도
4. 설명을 반증할 조건
5. 변경과 같은 조건의 재검증
6. 남은 위험과 원자료 링크

실패한 실행도 삭제하지 않는다. 무엇을 주장할 수 없는지만 명확히 남긴다.
