# CASE-005: 댓글 목록의 쿼리 수가 댓글 수에 비례함

> 상태: `closed`
> 영향도: 높음
> 확인일: 2026-09-04
> 수정 커밋: `d346714`, `d3b4eb5`

## 결론

댓글 목록은 댓글마다 반응 상태와 작성자를 다시 조회했다. 반응 조회를 한 번의 일괄
조회로 바꾸고 작성자를 fetch join으로 가져오면서 요청당 쿼리가 1,507개에서 3.9개로
줄었다. 작은 글과 큰 글이 모두 4개 안팎의 쿼리를 사용하므로 쿼리 증폭은 해소됐다.

댓글 전체를 한 응답으로 보내는 비용은 별개다. 댓글이 많은 글은 DTO 생성과 직렬화 비용이
남아 있으며, 이를 해결하려면 익명 번호 규칙을 보존하는 페이지네이션 설계가 필요하다.

## 영향과 검증

| 단계 | 요청당 쿼리 | 전체 p95 | 변경 |
|---|---:|---:|---|
| Before | 1,507 | 226.7ms | 댓글마다 반응·작성자 조회 |
| 1차 수정 | 112 | 57.2ms | 반응 상태 일괄 조회 |
| 2차 수정 | 3.9 | 34.3ms | 작성자 fetch join |

부하 없는 단발 요청에서도 댓글 6개, 492개, 4,040개인 글이 모두 4개 쿼리를 사용했다.
두 부하 세트의 p95 범위도 겹치지 않았다.

## 원인 사슬

| 단계 | 설명 | 근거 | 확신도 |
|---|---|---|---|
| C1 | 댓글마다 좋아요와 싫어요를 각각 조회함 | 수정 전 호출 구조와 쿼리 계측 | 확인 |
| C2 | DTO 생성 중 LAZY 작성자를 댓글별로 조회함 | 쿼리 계측과 fetch join 대조 | 확인 |
| C3 | 댓글 수가 늘수록 DB 왕복이 선형 증가함 | 크기가 다른 글의 단발 계측 | 확인 |

## 적용한 변경

1. 댓글 ID 목록으로 현재 사용자의 반응을 한 번에 조회했다.
2. 댓글 목록 쿼리에서 작성자를 fetch join했다.
3. 호출 횟수와 SQL 수를 테스트로 고정했다.

## 남은 위험

- 댓글 응답 크기는 여전히 댓글 수에 비례한다.
- 익명 사용자의 표시 번호가 전체 댓글 순서에 의존하므로 단순 페이지 분할은 의미를 바꾼다.
- 이 Case는 쿼리 증폭 해소만 검증했다. 응답 크기 문제는 새 Case에서 다뤄야 한다.
