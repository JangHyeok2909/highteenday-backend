# CASE-006: DB 커넥션 풀이 장애 전파 지점이 됨

> 상태: `observed`
> 영향도: 높음
> 최초 관측: 2026-08-29
> 관련: [CASE-007](../CASE-007-redis-failure-cascade/)

## 결론

Tomcat은 최대 400개 요청 스레드를 받지만 성능 환경의 HikariCP 풀은 10개다. 풀을 20개로
늘린 실험에서는 간헐적인 커넥션 대기 경고가 사라졌지만 전체 p95는 유의하게 개선되지
않았다. 당시 정상 부하의 커넥션 획득 p95가 약 1ms였기 때문이다.

따라서 풀 크기 10 자체를 모든 지연의 원인으로 볼 수 없다. 다만 DB 커넥션을 오래 점유하는
경로가 생기면 10개가 빠르게 소진되고, 이후 모든 DB 접근이 같은 대기열에 들어간다.
CASE-007의 Redis 장애에서 이 전파가 실제로 관측됐다.

## 관측

| 조건 | 결과 |
|---|---|
| HikariCP 10, 정상 부하 | 5회 중 1회 pending 최대 20, 획득 p95 0.96ms |
| HikariCP 20, 같은 부하 설정 | 3회 모두 pending 0, 획득 p95 0.95ms |
| 종단 지연 | 두 세트의 p95 범위가 겹쳐 개선을 확인하지 못함 |
| Redis 장애 | active 10/10, 시계열 pending 최대 177, 30초 획득 실패 발생 |

풀 확대 실험은 호스트 CPU 속도가 달랐고 실행 메타데이터가 실제 이미지와 정확히 대응하지
않았다. 그러므로 지연·CPU 비교는 제한적이며, pending 제거만 직접 관측으로 채택한다.

## 원인 사슬

| 단계 | 설명 | 근거 | 확신도 |
|---|---|---|---|
| C1 | 요청 처리 동시성이 DB 커넥션 수보다 큼 | Tomcat 400, HikariCP 10 | 확인 |
| C2 | 평상시에는 짧은 점유 시간 때문에 풀 10으로도 대기가 작음 | 정상 부하 획득 p95 | 확인 |
| C3 | 커넥션 점유가 길어지면 풀이 전부 사용되고 다른 요청이 대기함 | CASE-007 자원 시계열 | 확인 |
| C4 | 풀을 크게 만들면 전체 지연도 줄어듦 | 정상 부하 대조에서 확인되지 않음 | 반증됨 |

## 조치 원칙

1. 풀을 늘리기 전에 커넥션 점유 시간을 늘린 호출을 제거한다.
2. 커넥션 획득 타임아웃을 사용자 요청 상한과 맞춘다.
3. 풀 크기를 바꾸면 MySQL 동시 실행, CPU, lock wait를 함께 본다.
4. Tomcat 스레드 수는 허용 가능한 대기열 깊이와 함께 결정한다.

## 다음 검증

- Redis 호출을 트랜잭션 밖으로 옮긴 뒤 CASE-007을 다시 실행한다.

- 풀 크기만 바꾼 대조는 동일 앱 이미지와 동일 호스트 상태에서 다시 수행한다.
