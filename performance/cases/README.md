# 성능·장애 사례

HighTeenDay 백엔드에 부하와 장애를 넣어 찾은 문제를 한 문제당 한 문서로 기록한다. 각 문서는 관측,
원인, 조치, 재검증, 남은 위험을 한곳에 이어 쓰고, 수치에 실행 ID와 원자료를 붙인다. 사례 대부분은 운영
트래픽이 없는 로컬 Docker Compose 실험에서 나왔고, 반응 쓰기 사례 하나는 코드 검토에서 나왔다. 영향도는
같은 결함이 운영에서 생겼을 때의 추정이다.

| 상태 | 뜻 | 건수 |
|---|---|---:|
| 해결 | 수정 뒤 재실행에서 문제가 사라짐. 전후 조건이 다르면 사례에 기록 | 4 |
| 부분 해결 | 일부 경로만 수정, 나머지는 남음 | 2 |
| 원인 확인 | 원인을 특정했고 수정 전. 코드 판독이나 크기 어림으로 특정했으면 상태 줄에 기록 | 4 |
| 조사 중 | 현상은 재현했고 원인은 확정하지 못함 | 6 |

| 영향도 | 뜻 |
|---|---|
| 치명 | 의존성 하나의 장애가 그 의존성을 쓰지 않는 기능까지 실패시키거나 수십 초씩 멈추게 함 |
| 높음 | 장애·고부하에서 요청이 실패하거나 수 초 지연되고, 오류율·헬스 같은 지표만으로는 드러나지 않거나 잘못 판정됨 |
| 중간 | 서비스는 동작하지만 일부 값이 틀리거나, 특정 조건에서만 느려지거나, 운영 판단을 흐림 |

## 사례 문서의 구조

모든 사례는 맨 앞에 상태, 영향도, 실행 ID를 두고 요약 3~5문장으로 문제, 원인과 확신도, 조치,
결과, 남은 것을 먼저 말한다. 본문은 문제와 영향, 탐지 과정, 원인과 확신도, 조치와 검증, 남은 위험,
후속 조치, 근거 순서로 쓴다. 짧은 사례는 탐지와 원인, 남은 위험과 후속 조치를 한 절로 합친다.
해결하지 못한 사례는 조치 결과 대신 다음 실험과 검증 계획을 적는다.
근거에는 실행 원자료 폴더와 관련 코드 링크를 둔다. 장애 실험 리포트(`report.html`)는 GitHub
화면에서 열리지 않으므로 실행 폴더에서 내려받아 브라우저로 연다. 일반 부하 실행 리포트는
[실행 기록 대시보드](https://janghyeok2909.github.io/highteenday-backend/)에서 바로 볼 수 있다.

## 여러 실행을 읽는 법

`redis-crash`의 여러 실행은 각각 타임아웃, 고부하 완화, 조회수, 헬스 판정이라는 서로 다른 문제를
검증한다. `redis-slow`와 `redis-hang`도 주입 방식이 달라 각 관측을 해당 사례에
따로 연결했다. 조건이 다른 실행의 수치는 한 줄의 개선율로 합치지 않는다.

MySQL의 `slow`, `hang`, `crash`, `freeze`도 주입 방식과 완료 요청 수를 함께 읽는다. 오래 기다리던
요청이 빠른 503으로 끝나면 오류율은 오르지만 대기는 줄어든다. 그래서 오류율만으로 변경 효과를
판정하지 않는다. 비교 조건과 표현의 강도는 [측정 방법](../METHOD.md)을 따른다.
