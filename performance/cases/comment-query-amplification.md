# 댓글 목록 쿼리 증폭

> 상태: closed — 댓글 수에 따른 쿼리 증폭 제거 확인
> 확인일: 2026-09-04
> 수정 커밋: `d346714`, `d3b4eb5`

## 요약

댓글 목록을 읽을 때 각 댓글의 반응 상태와 작성자를 다시 조회해 한 실행에서 요청당
쿼리 1,507개가 기록됐다. 반응 상태를 일괄 조회하고 작성자를 fetch join으로 가져온 뒤
요청당 쿼리는 평균 3.9개가 됐다. 댓글 6개, 492개, 4,040개인 게시글의 단발 요청도
모두 4개 안팎의 쿼리를 사용했다.

## 문제 개요와 영향

기존 댓글 목록 경로에서는 댓글이 늘수록 반응 상태 조회와 LAZY 작성자 조회가 반복됐다.
변경 전 반복 실행에서 요청당 쿼리 1,507개와 전체 p95 226.7ms가 기록됐다. 이 수치는
당시 실행의 관측값이며 현재 서비스의 기준선으로 쓰지 않는다.

## 탐지와 진행 순서

| 단계 | 요청당 쿼리 | 전체 p95 | 확인한 동작 |
|---|---:|---:|---|
| 변경 전 | 1,507개 | 226.7ms | 댓글마다 반응 상태와 작성자 조회 |
| 반응 일괄 조회 후 | 112개 | 57.2ms | 반응 상태를 한 번에 조회 |
| 작성자 fetch join 후 | 3.9개 | 34.3ms | 작성자 LAZY 조회 반복 제거 |

## 원인과 촉발 요인

반응 상태 조회와 작성자 지연 로딩이 댓글별로 반복된 것이 쿼리 증폭의 원인이다.
댓글 수가 큰 게시글을 읽을 때 반복 횟수가 늘어나면서 문제가 드러났다. 단계별 변경
뒤 쿼리 수가 1,507개 → 112개 → 3.9개로 내려간 결과도 두 반복 조회의 기여를
뒷받침한다.

## 조치와 검증 결과

`CommentReactionService`에서 반응 상태를 일괄 조회하고 `CommentRepository`에서 작성자를
fetch join으로 함께 가져오도록 바꿨다. 댓글 6개, 492개, 4,040개인 게시글의 단발 요청이
모두 4개 안팎의 쿼리를 사용해 댓글 수에 따른 선형 증폭이 사라졌는지 확인했다.
서비스와 repository 테스트로 호출 횟수와 실행 SQL 수를 고정했다.

표의 p95는 각 단계의 실행에서 함께 기록한 값이다. 이 Case의 확인된 결론은 **쿼리 수의
선형 증폭 제거**이며, 과거 p95를 현재 응답 시간이나 처리 용량으로 일반화하지 않는다.

## 배운 점과 남은 위험

쿼리 수를 일정하게 만들어도 응답 크기와 DTO 직렬화 비용은 댓글 수에 비례한다.
익명 표시 번호가 전체 댓글 순서에 의존하므로 페이지네이션을 도입할 때 번호 계약도
함께 검토해야 한다. 이 Case에서는 그 비용과 계약을 검증하지 않았다.
