# Datasets — 부하 테스트 시드 데이터

## 설계 원칙

부하 테스트 결과는 **데이터 분포**에 극도로 민감하다. 균등분포 데이터로는
현실의 병목(단일 row 락 경합, 캐시 히트 편중, 헤비 유저 팬아웃)이 재현되지 않는다.

| 축 | 분포 | 근거 |
|----|------|------|
| 작성 활동량 | 사용자별 Zipf(`AUTHOR_SKEW = 1.3`) | 커뮤니티의 1% 법칙 — 소수 헤비 유저가 콘텐츠 대부분 생산. 값의 근거는 아래 참고 |
| 게시글 인기도 | 게시글별 Zipf(`HOT_SKEW = 1.07`) | 조회/반응이 상위 글에 집중 (Hot Data). 크기와 무관하게 고정 — 규칙과 규모를 동시에 바꾸지 않기 위해서다 |
| 친구 관계 | 학교 내 80% 클러스터링 | 실제 서비스는 같은 학교끼리 연결됨 → 채팅/알림 팬아웃도 클러스터 안에서 발생 |
| 반응 종류 | LIKE 85% : DISLIKE 15% | 일반 커뮤니티 비율 |
| 익명 여부 | 글 50%, 댓글 60% | 익명 커뮤니티 특성 |

k6 스크립트도 같은 분포로 **접근**한다: `scripts/lib/data.js`의 `hotPost()`가
Zipf 샘플링으로 인기글을 편중 조회하므로, 생성 분포와 접근 분포가 함께 Hot Data를 만든다.

### 작성 활동과 게시글 인기는 다른 분포다

두 축은 답하는 질문이 다르다 — "어느 **사람**이 많이 쓰는가"와 "어느 **글**에 몰리는가".
같은 지수를 써야 할 근거가 없어 `sampling.js`가 두 상수를 따로 선언한다.

**`AUTHOR_SKEW`는 1.3이다. 이 문서가 오래 적어 온 `s≈1.7`이 아니다.** 그 1.7은 검증된
모델링 값이 아니라 옛 버그 수식(`floor(n^(u^1.7)) % n`)의 상수를 Zipf 지수로 잘못 읽은
것이었다. 진짜 Zipf에 그대로 넣으면 옛 코드가 실제로 만들던 것보다 훨씬 극단적이 된다.

large(사용자 10,000 / 게시글 100,000) 시뮬레이션:

| s | 글 쓴 사용자 | 최다 작성자 비중 | 상위 100명 비중 |
|---:|---:|---:|---:|
| 1.07 | 7,996 | 9.9% | 58.0% |
| **1.3 (채택)** | **4,893** | **19.9%** | **79.9%** |
| 1.7 | 1,361 | 38.4% | 96.2% |
| *옛 DB(버그 수식 실측)* | *7,438* | *21.8%* | *66.7%* |

1.7이면 한 사람이 전체 게시글의 38%를 쓰고 10,000명 중 8,639명은 글이 0건이다. 작성자
기반 조회(마이페이지·작성글 목록)가 사실상 1,361명만 대상이 되고, 단일 사용자 행의
핫로우가 정작 재려던 인기글 경합(BTL-003)을 가린다.

1.3은 **최다 작성자 비중이 옛 DB에 가장 가깝다**(19.9% vs 21.8%). 다만 옛 분포는 순수
Zipf가 아니라 모든 지표가 맞지는 않는다 — 작성자 수는 더 적고(4,893 vs 7,438) 상위 100명
비중은 더 높다(79.9% vs 66.7%). 머리는 더 무겁고 꼬리는 더 얇은 셈이다.

이번 재생성의 목적은 "옛 규칙 세대 데이터를 **올바른 수식으로** 교체"하는 것이지 부하 모델
자체를 바꾸는 것이 아니다. 모델까지 같이 바꾸면 재생성 후 성능 차이를 수식 교정 탓인지
모델 변경 탓인지 분리할 수 없다.

운영 액세스 로그가 쌓이면 실측 작성 분포로 교체할 것. 그때까지 이 값은 **옛 데이터와의
연속성**을 근거로 한 잠정값이다.

## 스케일 프로파일 (`profiles.json`)

| 프로파일 | 사용자 | 게시글 | 댓글 | 반응 | 친구쌍 | 용도 |
|---------|-------:|-------:|-----:|-----:|-------:|------|
| smoke | 20 | 50 | 150 | 300 | 20 | 스크립트 동작 확인 (1분 내) |
| small | 100 | 500 | 2k | 5k | 200 | 로컬 개발 반복 실험 |
| medium | 1,000 | 10k | 40k | 100k | 3k | 표준 실험 (EXP 기본값) |
| large | 10,000 | 100k | 400k | 1M | 30k | 인덱스/페이징 병목 재현 |
| xlarge | 100,000 | 500k | 2M | 5M | 200k | 운영 1년 후 규모 가정 |

## 생성 방법

```bash
# 서버가 떠 있어야 한다 (environment/ 참고)
node datasets/seed.js --profile medium --base http://localhost:18080 --concurrency 10
```

- **API 기반 생성**이다. SQL 직접 삽입보다 느리지만:
  - 스키마 변경에 깨지지 않는다 (엔티티 컬럼명 하드코딩 없음)
  - 서비스 로직(비정규화 카운터, 알림 팬아웃, HOT 점수)이 실제와 동일하게 만들어진다
  - 생성 과정 자체가 1차 쓰기 부하 테스트를 겸한다
- 결정론적 PRNG(고정 시드)라 **같은 프로파일 → 항상 같은 데이터** (재현성).
- Node 18+ 가 필요하다 (전역 `fetch` 사용).
- `large` 이상은 시간이 오래 걸린다(수 시간). 야간 실행을 권장하며,
  더 빠른 적재가 필요하면 `SHOW CREATE TABLE`로 스키마를 덤프한 후 SQL 벌크 삽입으로
  전환하되, **비정규화 카운터(likeCount 등)와 Redis 상태를 수동으로 정합시켜야 한다.**

### 실패 정책 — 목표 수량을 채우지 못하면 실패다

시더는 "요청을 보낸 도구"가 아니라 **"정확히 만들었음을 증명하는 도구"**다. 단계마다 목표
수량을 채웠는지 검문하고, 못 채우면 다음 단계로 넘어가지 않는다. 예전에는 1단계가 통째로
실패해도 2단계가 그대로 시작돼 오류가 단계마다 증폭됐다 — 닉네임 길이 제한 때문에 10,000명
중 100명만 가입했는데 이후 전 단계가 그 100명 위에서 돌아 데이터셋이 무너진 실측 사례가 있다.

설정은 **서로 다른 두 축**이다.

| 옵션 | 답하는 질문 | 기본값 |
|---|---|---|
| `--tolerance <pct>` | 무엇을 실패로 볼 것인가 (단계별 허용 실패율) | `0` |
| `--on-failure <mode>` | 허용치를 넘겼을 때 어디서 멈출 것인가 | `stage` |

```bash
# 데드락이 잦은 large 에서 0.1% 까지 허용하고, 넘기면 즉시 중단
node datasets/seed.js --profile large --tolerance 0.1 --on-failure immediate
```

**`--on-failure` 모드**

| 모드 | 동작 | 언제 |
|---|---|---|
| `stage` (기본) | 진행 중인 단계는 끝까지 돌리고 다음 단계 전에 멈춘다 | 실패 건수를 다 보고 원인 파악 |
| `immediate` | 허용치를 넘는 순간 그 단계도 중단한다 | 오래 걸리는 생성에서 설정 오류 조기 발견 |
| `continue` | 끝까지 돌린 뒤 요약만 보고한다 | "무엇이 얼마나 실패하는가" 한 번에 조사 |

**허용치(`--tolerance`)의 규칙**

- **단계마다 따로** 적용된다. 전체 합으로 보면 "반응 단계만 100% 실패"가 다른 단계의
  성공에 묻힌다.
- 허용 건수는 **내림**이다 — 목표 50건에 1%면 0건이다. 반올림하면 "1%를 줬는데 2%가 통과"한다.
- 기본이 0인 이유: 데이터셋이 명세에 미달하면 그 위에서 잰 수치가 근거를 잃고, 미달을
  허용하면 "그 몇 건이 어느 리소스인가"를 추적할 방법이 없다.
- 그래도 여는 이유: BTL-003 인기글 카운터 데드락처럼 **서버가 실제로 갖고 있는 병목** 때문에
  large 규모에서 소수 손실이 반복된다. 병목을 고치기 전까지의 타협점을 명시적으로 고를 수 있어야 한다.
- 허용치가 단계를 살렸다면 로그와 `meta.json` 양쪽에 남는다. 조용히 넘어가면 0%로 만든
  데이터셋과 구별되지 않는다.

**종료 코드**: `0` 모든 단계가 허용치 안 · `1` 허용치 초과 · `2` 실행 오류/잘못된 인자.
허용치를 넘긴 경우 **어느 모드든 JSON 산출물을 쓰지 않는다** — 반쪽짜리 데이터셋이 파일로
남으면 다음 실행이 그걸 정상으로 착각한다.

**기존 산출물은 생성 시작 시점에 지운다.** 그 순간부터 디스크의 JSON은 지금 만들고 있는
DB와 맞지 않기 때문이다. 성공하면 새로 쓰고 실패하면 남지 않으므로, "파일이 있으면 현재
DB를 설명한다"가 항상 성립한다. 이 처리가 없을 때 실제로 이런 일이 있었다 — 볼륨을 폐기하고
재생성하다 중단됐는데 **폐기 이전 세대의 `posts.json`이 남아** 새 DB에 없는 게시글 ID를
가리켰다. `meta.json`이 없어 지문 비교는 막히지만 k6는 `posts.json`을 직접 읽는다.

### 중단된 생성을 이어서 하기 (`--resume`)

`large` 생성은 20시간이 넘는다. 마지막 단계에서 죽으면 그때까지 만든 게시글 10만·댓글
40만·반응 100만이 DB에 그대로 있는데도, 누적을 피하려면 볼륨을 지우고 처음부터 해야 했다.
실제로 그렇게 21시간을 두 번 날렸다(2026-08-15·16).

```bash
node environment/bootstrap.js --profile large --resume --tolerance 0.001
```

시더가 단계를 하나 끝낼 때마다 `datasets/.checkpoint-<profile>.json`에 "어디까지 했는지"를
기록한다. `--resume`은 그 파일을 읽어 **이미 목표를 채운 단계를 건너뛴다.**

- 산출물(`generated/`)과 다른 것이다. 산출물은 완성된 데이터셋의 색인이라 실패 시 남기면
  안 되지만, 체크포인트는 작업 메모라 **실패해도 남아야** 쓸모가 있다.
- 회원가입·로그인·학교 배정은 재개해도 다시 한다 — 세션이 있어야 뒤 단계가 돌아가고,
  중복 가입은 409로 성공 처리되므로 비용은 로그인 시간뿐이다(large 기준 수 분).
- 게시글 목록은 체크포인트가 들고 있다. auto-increment ID라 생성 순서 = ID 순서이고,
  `posts.json`의 "인기순 정렬" 전제가 유지된다.
- 친구와 채팅은 한 덩어리다 — 채팅방은 친구 쌍 목록이 필요하므로, 친구만 완료된 상태면
  친구 단계를 다시 돌려 쌍을 얻는다.

**생성기 지문이 다르면 재개를 거부한다.** 샘플러나 시더를 고친 뒤 재개하면 앞 단계는 옛
규칙, 뒤 단계는 새 규칙으로 만들어진 **잡종 데이터셋**이 된다. 그건 어느 쪽 규칙으로도
설명할 수 없어 지문의 의미가 사라진다.

**재개한 데이터셋은 한 번에 만든 것과 난수 소비 순서가 다르다.** 건너뛴 단계가 쓰지 않은
난수만큼 뒤 단계의 선택이 달라진다. 분포는 같은 규칙에서 나오므로 통계적으로는 같지만,
바이트 단위 동일 재현은 애초에 보장하지 않는다. `meta.json`의 `resumed` 항목에 어느 단계를
이어받았는지 남으므로 나중에 추적할 수 있다.

### 장시간 생성과 토큰 만료

액세스 토큰 수명은 30분인데 `large` 생성은 그보다 오래 걸린다. `Session`이 401을 받으면
토큰을 갱신하고 한 번 다시 보내는데, **같은 세션의 동시 요청이 각자 갱신하면 서로를
무효화한다** — 서버가 refresh token 회전을 하므로 먼저 성공한 하나가 나머지의 토큰을 깬다.

실측(2026-08-14): large 생성이 댓글 400,000건 중 **401 23건**으로 중단됐다. 앞선 단계
(회원가입·로그인·학교·게시글 100,000)는 전부 성공한 뒤였고, 실패율은 0.006%였지만 허용치가
0이라 멈췄다. 그때까지의 수 시간이 날아갔다.

`Session.refreshOnce()`가 세션당 갱신을 하나로 합쳐 이 경쟁을 없앤다. 추가로 401을 재시도
대상에 넣었다 — 401은 인증 거절이라 서버가 일을 하지 않은 것이 확실해 중복이 생기지 않는다.

"목표"는 작업 목록 길이가 아니라 **프로파일이 선언한 수량**이다. `uniquePairs()`가 유일
조합을 다 못 찾아 작업이 300건에서 148건으로 줄면, 148건을 다 성공해도 **152건 미달**로
잡힌다. 계획 단계의 부족과 실행 단계의 실패는 원인이 다르지만 결과는 같다.

### 재실행 안전성 — 두 종류의 위험

- **누적형**(회원·게시글·댓글): 다시 돌리면 더 만들어진다. 깨끗한 DB에서 시작하는 것이 전제다.
  다만 이미 존재하는 계정의 중복 가입(409)과 이미 성립한 친구 관계(409)는 **성공으로 센다** —
  시더가 만들려는 것은 "요청을 보냈다"가 아니라 "그 상태가 성립한다"이기 때문이다.
- **토글형**(반응·스크랩): 같은 요청을 두 번 보내면 **취소된다**([KI-54](../../docs/defects/KI-54-toggle-non-idempotent.md)).
  응답을 못 받은 요청을 그냥 재시도하면 서버가 이미 만든 상태를 되돌린다.

토글형은 그래서 재시도 정책이 다르다. `ensureToggled()`가 실패를 두 갈래로 가른다.

| 실패 종류 | 예 | 처리 |
|---|---|---|
| 확실히 적용 안 됨 | 데드락(롤백), 커넥션 고갈, `ECONNREFUSED` | 그대로 재시도 |
| 적용 여부 모름 | `ECONNRESET`, `socket hang up`, `fetch failed` | **재요청하지 않고** `GET /api/posts/{id}`로 상태 조회 |

조회 결과가 목표 상태면 첫 요청이 적용된 것이므로 성공 처리하고, 목표 상태가 아니면 적용되지
않은 것이 확인됐으므로 그때 재시도한다. 조회마저 실패하면 아무것도 단정할 수 없으므로
재시도하지 않고 실패로 남긴다 — **불확실하면 다시 보내지 않고 확인한다**가 원칙이다.

```
├── users.json    # [{email, nickname}]  — 비밀번호는 전 계정 공통 PerfTest123!
├── posts.json    # [{id, boardId}]      — 인기순 정렬 (index 0 = 최고 인기글)
├── boards.json   # [{id, name}]
└── meta.json     # 생성 지문 — "같은 규칙과 같은 규모로 만든 데이터인가"
```

`users.json`에는 **세션이 확인된 계정만** 들어간다. 예전에는 생성 계획을 그대로 썼기 때문에
가입에 실패한 계정이 파일에 남아 k6가 존재하지 않는 계정으로 로그인을 시도했다. 세션이
잡혔다는 것은 가입·로그인·학교 배정을 전부 통과했다는 증거다.

`meta.json`의 `fingerprint`는 **생성기 코드(`seed.js` + `sampling.js`) · 프로파일 파라미터 ·
단계별 실제 생성 개수(`stageCounts`)**를 해싱한 값이다.

`stageCounts`가 지문에 들어가는 것이 허용치(`--tolerance`)를 열 때 특히 중요하다. 예전
지문에는 users·posts·boards 개수만 들어가서, **댓글이 5% 모자란 데이터셋과 온전한
데이터셋의 지문이 같았다.** 그러면 회귀 판정이 두 실행을 같은 조건으로 비교한다.
지금은 단계 하나만 미달해도 지문이 갈린다.

허용 정책 자체(`tolerance.pct`)는 지문에 **넣지 않는다.** 지문이 답해야 하는 질문은 "이
데이터가 무엇인가"이지 "어떤 설정으로 만들었나"가 아니다 — 허용치 1%로 돌렸는데 손실이 0이면
0%로 돌린 것과 같은 데이터이므로 같은 지문이어야 한다. 대신 `tolerance` 항목에 사람이 읽을
기록으로 남는다(어느 단계가 몇 건 부족한 채 통과했는지). `perf-run.js`가 이 값을 읽어 실행 레코드에 싣고, 비교
조건에서 프로파일 이름과 **함께** 판정한다(blocking). 이름만 조건이던 시절에는 샘플러를
고쳐 데이터를 다시 만들어도 값이 그대로 `large`라, 인기 분포가 완전히 달라진 데이터셋이
옛 실행과 같은 조건으로 비교됐다.

생성 시각은 지문에 넣지 않는다. 같은 생성기·같은 프로파일로 다시 시드하면 LCG 시드가
고정이라 통계적으로 동일한 데이터셋이 나오고, 그걸 매번 다른 것으로 취급하면 재시드할
때마다 기준선이 전부 무효가 되어 정작 막으려던 것과 무관하게 비교가 끊긴다. 반면 시드가
부분 실패하면 생성 개수가 달라져 지문이 바뀐다 — 그건 실제로 다른 데이터셋이 맞다.

k6에서 `-e DATASET=<profile>` 로 선택한다. `generated/`는 `.gitignore` 대상
(데이터가 아니라 **생성기와 프로파일**이 버전 관리 대상이다).

## 실측으로 확인한 문제: 세션 실패가 데이터셋을 조용히 무너뜨렸다

`seed.js`는 작성자를 `zipf(users.length)`로 뽑은 뒤 그 사용자의 세션이 없으면
**작업을 조용히 버렸다**(`if (!s) return`). 예외를 던지지 않으니 실패로 집계되지 않고
"완료" 카운터만 올라가, 데이터가 크게 미달해도 성공으로 보고됐다.

Zipf는 낮은 인덱스(헤비 유저)를 압도적으로 자주 뽑으므로 **상위 몇 명만 실패해도 손실이
증폭**된다. small 프로파일 실측:

| | 명세 | 수정 전 | 수정 후 |
|---|---:|---:|---:|
| users | 100 | 92 | **100** |
| posts | 500 | **187** (실패 0으로 보고) | **500** |
| comments | 2000 | **729** | **1902** (미생성 98건을 명시 보고) |
| 작성자 분포 | Zipf | 12, 12, 11, 8, 8 (**균등**) | 158, 64, 35, 19, 14 (**멱법칙**) |

분포가 균등해지면 이 프로젝트가 전제하는 Hot Data가 사라져 **BTL-001(랜덤 페이지네이션),
BTL-003(핫 로우 경합), BTL-004(캐시 스탬피드)가 재현되지 않는다.**

수정: 살아있는 세션만 모아(`liveAuthors()`) 그 위에서 Zipf를 돌린다. 개수와 분포 형태가
모두 보존된다. 아울러 `pooled()`는 "처리 개수"가 아니라 **실제 생성 개수**를 보고하고,
목표에 미달하면 경고한다.

> 남은 미생성분은 앱의 실제 결함이다 — 대부분 핫 로우 UPDATE 데드락(BTL-003)이고
> 일부는 `Could not open JPA EntityManager`(커넥션 풀 고갈, BTL-002). 시드 단계의
> 낮은 동시성에서도 재현된다는 점 자체가 관측 결과다.

## 인기 편중 샘플러는 `scripts/lib/sampling.js` 하나만 쓴다

`seed.js`는 예전에 자체 `zipf()`를 갖고 있었고, 부하 스크립트(`scripts/lib/data.js`)에도
**글자까지 같은 식**이 복제돼 있었다. 그 식 `floor(n^(u^1.7)) % n`은 `u < 1`이라 결과가
항상 1 이상이어서 **index 0을 구조적으로 뽑지 못했다**(S-03).

결과가 이랬다. `posts.json`은 인기순으로 정렬되므로 위 산출물 표대로 index 0이 최고
인기글이어야 하는데, 실제로는 **댓글·반응·스크랩이 하나도 붙지 않은 글**이 그 자리에
있었다. 진짜 최고 인기글은 index 1이었고, 그 한 글에 전체 참여의 19~27%가 몰렸다
(정상 분포에서 1위의 몫은 8~13%다). 즉 핫 로우 경합 실험의 대상과 강도가 모두 틀려 있었다.

이제 규칙은 `scripts/lib/sampling.js`에만 있고 `seed.js`와 `data.js`가 함께 가져다 쓴다.
한쪽만 고치면 "가장 인기 있는 글을 조회했는데 댓글이 0건"인 모순이 생기기 때문이다.
`tools/test/sampling.test.js`가 이 단일 출처를 구조적으로 강제한다.

> **이 변경 이후 생성한 데이터셋만 위 산출물 표의 설명("index 0 = 최고 인기글")과 일치한다.**
> 이전에 만들어 둔 `generated/<profile>/`은 index 0이 여전히 비어 있는 글이다.
> 재생성 전에는 인기 편중을 전제한 실험(BTL-003 등)의 결과를 그대로 믿으면 안 된다.

### small 프로파일의 한계: 반응 편중은 사용자 수에 갇힌다

반응은 (사용자, 게시글) 쌍이 유일하고 재요청은 토글이라, **한 글의 최대 반응 수 = 사용자 수**다.

### ① 비정규화 카운터가 실제 행 수와 일치하는가 — 가장 중요

```sql
SELECT
  (SELECT SUM(PST_comment_count) FROM posts WHERE is_valid=1) AS stored_comments,
  (SELECT COUNT(*) FROM comments c JOIN posts p ON c.PST_id=p.PST_id
   WHERE c.is_valid=1 AND p.is_valid=1) AS actual_comments,
  (SELECT COUNT(*) FROM (
     SELECT p.PST_id FROM posts p LEFT JOIN comments c ON c.PST_id=p.PST_id AND c.is_valid=1
     WHERE p.is_valid=1 GROUP BY p.PST_id, p.PST_comment_count
     HAVING p.PST_comment_count <> COUNT(c.CMT_id)) x) AS mismatched_posts;
```

**댓글은 불일치 0건이어야 한다.** 예전에는 large에서 13,284건이 부족했다(KI-53, 원자 증감
으로 해결). 반응·스크랩은 재계산 방식의 좁은 경쟁 창 때문에 게시글 몇 건이 1씩 어긋날 수
있다(KI-55) — 오차가 1을 넘거나 건수가 많으면 다른 문제다.

### ② 참조 무결성과 중복

```sql
SELECT 'orphan comments' AS chk, COUNT(*) AS cnt
  FROM comments c LEFT JOIN posts p ON c.PST_id=p.PST_id WHERE p.PST_id IS NULL
UNION ALL SELECT 'orphan reactions', COUNT(*)
  FROM posts_reactions r LEFT JOIN posts p ON r.PST_id=p.PST_id WHERE p.PST_id IS NULL
UNION ALL SELECT 'orphan scraps', COUNT(*)
  FROM scraps s LEFT JOIN posts p ON s.PST_id=p.PST_id WHERE p.PST_id IS NULL
UNION ALL SELECT 'dup reaction pairs', (SELECT COUNT(*) FROM (
  SELECT USR_id,PST_id FROM posts_reactions WHERE is_valid=1
  GROUP BY USR_id,PST_id HAVING COUNT(*)>1) d)
UNION ALL SELECT 'dup scrap pairs', (SELECT COUNT(*) FROM (
  SELECT USR_id,PST_id FROM scraps WHERE is_valid=1
  GROUP BY USR_id,PST_id HAVING COUNT(*)>1) d)
UNION ALL SELECT 'users without school', COUNT(*) FROM users WHERE SCH_id IS NULL;
```

전부 **0이어야 한다.** 중복 쌍이 나오면 유니크 제약(V7)이 빠졌거나 토글 재시도가 상태를
되돌린 것이다.

재생성할 때마다 확인한다. 예전에는 이 자리가 참여 데이터가 하나도 없는 글이었고,
`datasets/README.md`가 그 자리를 "최고 인기글"이라 선언한 것과 어긋난 채로 유지됐다.

```bash
node -e "console.log(require('./generated/small/posts.json').slice(0,3).map(p=>p.id).join(', '))"
```

```sql
-- 참여도 상위 5건. 1위 PST_id가 위 index 0 과 같아야 하고, 순서도 대체로 일치해야 한다.
SELECT p.PST_id, p.PST_comment_count AS comments,
       (p.PST_like_count + p.PST_dislike_count) AS reactions,
       p.PST_scrap_count AS scraps,
       (p.PST_comment_count + p.PST_like_count + p.PST_dislike_count + p.PST_scrap_count) AS engagement
FROM posts p WHERE p.is_valid=1 ORDER BY engagement DESC LIMIT 5;
```

2026-08-14 small 실측: `posts.json` 앞 3건이 `[10, 4, 9]`, 참여도 순위도 `10(447) → 4(267)
→ 9(229)`로 일치. 반응만으로 보지 않고 **참여도 합**으로 보는 이유는, 한 글의 활성 반응
상한이 사용자 수라 인기글끼리 반응 수가 금방 포화되기 때문이다(small에서 상위 글이 전부
100 = 사용자 수).

> **이 순서가 깨질 수 있는 경로가 있다.** 시더는 이 순서를 **생성 랭크**로 만든다 —
> 참여 데이터를 붙일 때 쓴 배열 인덱스가 곧 랭크라 자기완결적이다. 그런데 체크포인트를
> DB에서 손으로 재구성하면서 `ORDER BY PST_id`로 뽑으면 그 연결이 끊긴다. **ID는 동시
> 레인의 완료 순, 랭크는 작업 순**이라 머리 부분이 국소적으로 뒤섞이기 때문이다.
>
> 2026-08-16 large에서 실제로 그렇게 됐다 — `posts.json[0]`의 참여도가 17,384인데 실제
> 1위는 45,075였다. 전체 분포는 멱법칙 그대로였고(0–9위 평균 22,158 → 10k+ 평균 2.9)
> 어긋남은 머리 안에서의 뒤섞임이었지만, "index 0 = 최고 인기글"이라는 계약은 거짓이 됐다.
>
> 복구는 `node datasets/resort-by-engagement.js <profile>` — **DB의 실측 참여도**로 순서를
> 다시 매긴다. 생성 랭크라는 간접 지표 대신 측정된 사실을 쓰므로 이후 ④ 검증이 정의상
> 통과한다. 지문은 바뀌지 않는다(순서는 지문 입력이 아니다). 대신 `meta.json`의
> `postProcessed`에 후처리 기록이 남는다.

### ④ 작성 활동 분포

```sql
SELECT COUNT(*) AS authors_with_posts FROM (
  SELECT USR_id FROM posts WHERE is_valid=1 GROUP BY USR_id) a;

SELECT USR_id, COUNT(*) AS posts FROM posts WHERE is_valid=1
GROUP BY USR_id ORDER BY posts DESC LIMIT 5;
```

`AUTHOR_SKEW = 1.3` 기준 large 예상: 작성자 약 4,900명, 최다 작성자가 전체의 약 20%.
최다 작성자가 30%를 넘으면 편중이 과하다 — 작성자 기반 조회를 측정할 수 없게 된다.
