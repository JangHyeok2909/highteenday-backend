# Datasets — 부하 테스트 시드 데이터

## 설계 원칙

부하 테스트 결과는 **데이터 분포**에 극도로 민감하다. 균등분포 데이터로는
현실의 병목(단일 row 락 경합, 캐시 히트 편중, 헤비 유저 팬아웃)이 재현되지 않는다.

| 축 | 분포 | 근거 |
|----|------|------|
| 작성 활동량 | 사용자별 Zipf(s≈1.7) | 커뮤니티의 1% 법칙 — 소수 헤비 유저가 콘텐츠 대부분 생산 |
| 게시글 인기도 | 게시글별 Zipf | 조회/반응의 ~80%가 상위 ~10% 글에 집중 (Hot Data) |
| 친구 관계 | 학교 내 80% 클러스터링 | 실제 서비스는 같은 학교끼리 연결됨 → 채팅/알림 팬아웃도 클러스터 안에서 발생 |
| 반응 종류 | LIKE 85% : DISLIKE 15% | 일반 커뮤니티 비율 |
| 익명 여부 | 글 50%, 댓글 60% | 익명 커뮤니티 특성 |

k6 스크립트도 같은 분포로 **접근**한다: `scripts/lib/data.js`의 `hotPost()`가
Zipf 샘플링으로 인기글을 편중 조회하므로, 생성 분포와 접근 분포가 함께 Hot Data를 만든다.

## 스케일 프로파일 (`profiles.json`)

| 프로파일 | 사용자 | 게시글 | 댓글 | 반응 | 친구쌍 | 용도 |
|---------|-------:|-------:|-----:|-----:|-------:|------|
| smoke | 20 | 50 | 150 | 300 | 20 | 스크립트 동작 확인 (1분 내) |
| small | 100 | 500 | 2k | 5k | 200 | 로컬 개발 반복 실험 |
| medium | 1,000 | 10k | 40k | 100k | 3k | 표준 실험 (EXP 기본값) |
| large | 10,000 | 100k | 400k | 1M | 30k | 인덱스/페이징 병목 재현 |
| xlarge | 100,000 | 500k | 2M | 5M | 200k | 운영 1년 후 규모 가정 |

## 생성 방법

```bash
# 서버가 떠 있어야 한다 (environment/ 참고)
node datasets/seed.js --profile medium --base http://localhost:18080 --concurrency 10
```

- **API 기반 생성**이다. SQL 직접 삽입보다 느리지만:
  - 스키마 변경에 깨지지 않는다 (엔티티 컬럼명 하드코딩 없음)
  - 서비스 로직(비정규화 카운터, 알림 팬아웃, HOT 점수)이 실제와 동일하게 만들어진다
  - 생성 과정 자체가 1차 쓰기 부하 테스트를 겸한다
- 결정론적 PRNG(고정 시드)라 **같은 프로파일 → 항상 같은 데이터** (재현성).
- Node 18+ 가 필요하다 (전역 `fetch` 사용).
- `large` 이상은 시간이 오래 걸린다(수 시간). 야간 실행을 권장하며,
  더 빠른 적재가 필요하면 `SHOW CREATE TABLE`로 스키마를 덤프한 후 SQL 벌크 삽입으로
  전환하되, **비정규화 카운터(likeCount 등)와 Redis 상태를 수동으로 정합시켜야 한다.**

### 실패 정책 — 목표 수량을 채우지 못하면 실패다

시더는 "요청을 보낸 도구"가 아니라 **"정확히 만들었음을 증명하는 도구"**다. 단계마다 목표
수량을 채웠는지 검문하고, 못 채우면 다음 단계로 넘어가지 않는다. 예전에는 1단계가 통째로
실패해도 2단계가 그대로 시작돼 오류가 단계마다 증폭됐다 — 닉네임 길이 제한 때문에 10,000명
중 100명만 가입했는데 이후 전 단계가 그 100명 위에서 돌아 데이터셋이 무너진 실측 사례가 있다.

설정은 **서로 다른 두 축**이다.

| 옵션 | 답하는 질문 | 기본값 |
|---|---|---|
| `--tolerance <pct>` | 무엇을 실패로 볼 것인가 (단계별 허용 실패율) | `0` |
| `--on-failure <mode>` | 허용치를 넘겼을 때 어디서 멈출 것인가 | `stage` |

```bash
# 데드락이 잦은 large 에서 0.1% 까지 허용하고, 넘기면 즉시 중단
node datasets/seed.js --profile large --tolerance 0.1 --on-failure immediate
```

**`--on-failure` 모드**

| 모드 | 동작 | 언제 |
|---|---|---|
| `stage` (기본) | 진행 중인 단계는 끝까지 돌리고 다음 단계 전에 멈춘다 | 실패 건수를 다 보고 원인 파악 |
| `immediate` | 허용치를 넘는 순간 그 단계도 중단한다 | 오래 걸리는 생성에서 설정 오류 조기 발견 |
| `continue` | 끝까지 돌린 뒤 요약만 보고한다 | "무엇이 얼마나 실패하는가" 한 번에 조사 |

**허용치(`--tolerance`)의 규칙**

- **단계마다 따로** 적용된다. 전체 합으로 보면 "반응 단계만 100% 실패"가 다른 단계의
  성공에 묻힌다.
- 허용 건수는 **내림**이다 — 목표 50건에 1%면 0건이다. 반올림하면 "1%를 줬는데 2%가 통과"한다.
- 기본이 0인 이유: 데이터셋이 명세에 미달하면 그 위에서 잰 수치가 근거를 잃고, 미달을
  허용하면 "그 몇 건이 어느 리소스인가"를 추적할 방법이 없다.
- 그래도 여는 이유: BTL-003 인기글 카운터 데드락처럼 **서버가 실제로 갖고 있는 병목** 때문에
  large 규모에서 소수 손실이 반복된다. 병목을 고치기 전까지의 타협점을 명시적으로 고를 수 있어야 한다.
- 허용치가 단계를 살렸다면 로그와 `meta.json` 양쪽에 남는다. 조용히 넘어가면 0%로 만든
  데이터셋과 구별되지 않는다.

**종료 코드**: `0` 모든 단계가 허용치 안 · `1` 허용치 초과 · `2` 실행 오류/잘못된 인자.
허용치를 넘긴 경우 **어느 모드든 JSON 산출물을 쓰지 않는다** — 반쪽짜리 데이터셋이 파일로
남으면 다음 실행이 그걸 정상으로 착각한다.

"목표"는 작업 목록 길이가 아니라 **프로파일이 선언한 수량**이다. `uniquePairs()`가 유일
조합을 다 못 찾아 작업이 300건에서 148건으로 줄면, 148건을 다 성공해도 **152건 미달**로
잡힌다. 계획 단계의 부족과 실행 단계의 실패는 원인이 다르지만 결과는 같다.

### 재실행 안전성 — 두 종류의 위험

- **누적형**(회원·게시글·댓글): 다시 돌리면 더 만들어진다. 깨끗한 DB에서 시작하는 것이 전제다.
  다만 이미 존재하는 계정의 중복 가입(409)과 이미 성립한 친구 관계(409)는 **성공으로 센다** —
  시더가 만들려는 것은 "요청을 보냈다"가 아니라 "그 상태가 성립한다"이기 때문이다.
- **토글형**(반응·스크랩): 같은 요청을 두 번 보내면 **취소된다**([KI-54](../../docs/defects/KI-54-toggle-non-idempotent.md)).
  응답을 못 받은 요청을 그냥 재시도하면 서버가 이미 만든 상태를 되돌린다.

토글형은 그래서 재시도 정책이 다르다. `ensureToggled()`가 실패를 두 갈래로 가른다.

| 실패 종류 | 예 | 처리 |
|---|---|---|
| 확실히 적용 안 됨 | 데드락(롤백), 커넥션 고갈, `ECONNREFUSED` | 그대로 재시도 |
| 적용 여부 모름 | `ECONNRESET`, `socket hang up`, `fetch failed` | **재요청하지 않고** `GET /api/posts/{id}`로 상태 조회 |

조회 결과가 목표 상태면 첫 요청이 적용된 것이므로 성공 처리하고, 목표 상태가 아니면 적용되지
않은 것이 확인됐으므로 그때 재시도한다. 조회마저 실패하면 아무것도 단정할 수 없으므로
재시도하지 않고 실패로 남긴다 — **불확실하면 다시 보내지 않고 확인한다**가 원칙이다.

## 산출물

```
datasets/generated/<profile>/
├── users.json    # [{email, nickname}]  — 비밀번호는 전 계정 공통 PerfTest123!
├── posts.json    # [{id, boardId}]      — 인기순 정렬 (index 0 = 최고 인기글)
├── boards.json   # [{id, name}]
└── meta.json     # 생성 지문 — "같은 규칙과 같은 규모로 만든 데이터인가"
```

`users.json`에는 **세션이 확인된 계정만** 들어간다. 예전에는 생성 계획을 그대로 썼기 때문에
가입에 실패한 계정이 파일에 남아 k6가 존재하지 않는 계정으로 로그인을 시도했다. 세션이
잡혔다는 것은 가입·로그인·학교 배정을 전부 통과했다는 증거다.

`meta.json`의 `fingerprint`는 **생성기 코드(`seed.js` + `sampling.js`) · 프로파일 파라미터 ·
단계별 실제 생성 개수(`stageCounts`)**를 해싱한 값이다.

`stageCounts`가 지문에 들어가는 것이 허용치(`--tolerance`)를 열 때 특히 중요하다. 예전
지문에는 users·posts·boards 개수만 들어가서, **댓글이 5% 모자란 데이터셋과 온전한
데이터셋의 지문이 같았다.** 그러면 회귀 판정이 두 실행을 같은 조건으로 비교한다.
지금은 단계 하나만 미달해도 지문이 갈린다.

허용 정책 자체(`tolerance.pct`)는 지문에 **넣지 않는다.** 지문이 답해야 하는 질문은 "이
데이터가 무엇인가"이지 "어떤 설정으로 만들었나"가 아니다 — 허용치 1%로 돌렸는데 손실이 0이면
0%로 돌린 것과 같은 데이터이므로 같은 지문이어야 한다. 대신 `tolerance` 항목에 사람이 읽을
기록으로 남는다(어느 단계가 몇 건 부족한 채 통과했는지). `perf-run.js`가 이 값을 읽어 실행 레코드에 싣고, 비교
조건에서 프로파일 이름과 **함께** 판정한다(blocking). 이름만 조건이던 시절에는 샘플러를
고쳐 데이터를 다시 만들어도 값이 그대로 `large`라, 인기 분포가 완전히 달라진 데이터셋이
옛 실행과 같은 조건으로 비교됐다.

생성 시각은 지문에 넣지 않는다. 같은 생성기·같은 프로파일로 다시 시드하면 LCG 시드가
고정이라 통계적으로 동일한 데이터셋이 나오고, 그걸 매번 다른 것으로 취급하면 재시드할
때마다 기준선이 전부 무효가 되어 정작 막으려던 것과 무관하게 비교가 끊긴다. 반면 시드가
부분 실패하면 생성 개수가 달라져 지문이 바뀐다 — 그건 실제로 다른 데이터셋이 맞다.

k6에서 `-e DATASET=<profile>` 로 선택한다. `generated/`는 `.gitignore` 대상
(데이터가 아니라 **생성기와 프로파일**이 버전 관리 대상이다).

## 실측으로 확인한 문제: 세션 실패가 데이터셋을 조용히 무너뜨렸다

`seed.js`는 작성자를 `zipf(users.length)`로 뽑은 뒤 그 사용자의 세션이 없으면
**작업을 조용히 버렸다**(`if (!s) return`). 예외를 던지지 않으니 실패로 집계되지 않고
"완료" 카운터만 올라가, 데이터가 크게 미달해도 성공으로 보고됐다.

Zipf는 낮은 인덱스(헤비 유저)를 압도적으로 자주 뽑으므로 **상위 몇 명만 실패해도 손실이
증폭**된다. small 프로파일 실측:

| | 명세 | 수정 전 | 수정 후 |
|---|---:|---:|---:|
| users | 100 | 92 | **100** |
| posts | 500 | **187** (실패 0으로 보고) | **500** |
| comments | 2000 | **729** | **1902** (미생성 98건을 명시 보고) |
| 작성자 분포 | Zipf | 12, 12, 11, 8, 8 (**균등**) | 158, 64, 35, 19, 14 (**멱법칙**) |

분포가 균등해지면 이 프로젝트가 전제하는 Hot Data가 사라져 **BTL-001(랜덤 페이지네이션),
BTL-003(핫 로우 경합), BTL-004(캐시 스탬피드)가 재현되지 않는다.**

수정: 살아있는 세션만 모아(`liveAuthors()`) 그 위에서 Zipf를 돌린다. 개수와 분포 형태가
모두 보존된다. 아울러 `pooled()`는 "처리 개수"가 아니라 **실제 생성 개수**를 보고하고,
목표에 미달하면 경고한다.

> 남은 미생성분은 앱의 실제 결함이다 — 대부분 핫 로우 UPDATE 데드락(BTL-003)이고
> 일부는 `Could not open JPA EntityManager`(커넥션 풀 고갈, BTL-002). 시드 단계의
> 낮은 동시성에서도 재현된다는 점 자체가 관측 결과다.

## 인기 편중 샘플러는 `scripts/lib/sampling.js` 하나만 쓴다

`seed.js`는 예전에 자체 `zipf()`를 갖고 있었고, 부하 스크립트(`scripts/lib/data.js`)에도
**글자까지 같은 식**이 복제돼 있었다. 그 식 `floor(n^(u^1.7)) % n`은 `u < 1`이라 결과가
항상 1 이상이어서 **index 0을 구조적으로 뽑지 못했다**(S-03).

결과가 이랬다. `posts.json`은 인기순으로 정렬되므로 위 산출물 표대로 index 0이 최고
인기글이어야 하는데, 실제로는 **댓글·반응·스크랩이 하나도 붙지 않은 글**이 그 자리에
있었다. 진짜 최고 인기글은 index 1이었고, 그 한 글에 전체 참여의 19~27%가 몰렸다
(정상 분포에서 1위의 몫은 8~13%다). 즉 핫 로우 경합 실험의 대상과 강도가 모두 틀려 있었다.

이제 규칙은 `scripts/lib/sampling.js`에만 있고 `seed.js`와 `data.js`가 함께 가져다 쓴다.
한쪽만 고치면 "가장 인기 있는 글을 조회했는데 댓글이 0건"인 모순이 생기기 때문이다.
`tools/test/sampling.test.js`가 이 단일 출처를 구조적으로 강제한다.

> **이 변경 이후 생성한 데이터셋만 위 산출물 표의 설명("index 0 = 최고 인기글")과 일치한다.**
> 이전에 만들어 둔 `generated/<profile>/`은 index 0이 여전히 비어 있는 글이다.
> 재생성 전에는 인기 편중을 전제한 실험(BTL-003 등)의 결과를 그대로 믿으면 안 된다.

### small 프로파일의 한계: 반응 편중은 사용자 수에 갇힌다

반응은 (사용자, 게시글) 쌍이 유일하고 재요청은 토글이라, **한 글의 최대 반응 수 = 사용자 수**다.
small(100명)에서는 최고 인기글이 100개를 넘길 수 없어 상위 10% 집중도가 54.4%에 그친다
(명세 기대 ~80%). 캐시/핫 로우 실험은 `medium` 이상에서 할 것.

## 검증

생성 후 분포가 의도대로인지 확인:

```sql
-- 상위 10% 게시글이 전체 반응의 몇 %를 가져갔는가 (~80% 기대)
SELECT SUM(CASE WHEN rk <= total/10 THEN cnt ELSE 0 END) / SUM(cnt) AS hot_ratio
FROM (
  SELECT PST_id, COUNT(*) cnt,
         RANK() OVER (ORDER BY COUNT(*) DESC) rk,
         COUNT(*) OVER () total
  FROM post_reaction GROUP BY PST_id
) t;
```

### index 0이 정말 최고 인기글인지 (S-03 회귀 확인)

재생성한 데이터셋에서 반드시 확인한다. 예전에는 이 자리가 참여 데이터가 하나도 없는
글이었고, 그 사실이 어디에도 드러나지 않았다.

```bash
# posts.json 앞쪽 3건의 게시글 ID를 뽑는다 (index 0 이 최고 인기글이어야 한다)
node -e "console.log(require('./generated/medium/posts.json').slice(0,3).map(p=>p.id).join(', '))"
```

```sql
-- 반응이 가장 많은 게시글 상위 5건. 1위의 PST_id가 위에서 얻은 index 0의 ID와 같아야 한다.
SELECT PST_id, COUNT(*) AS reactions
FROM post_reaction
GROUP BY PST_id
ORDER BY reactions DESC
LIMIT 5;
```

두 값이 어긋나면 `posts.json`의 정렬 전제가 깨진 것이므로, 인기 편중을 전제한 실험
결과를 신뢰할 수 없다.
