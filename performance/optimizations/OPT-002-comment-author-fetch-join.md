# OPT-002: 댓글 목록의 작성자 조회를 패치 조인으로 전환

> 대상 병목: BTL-005 (잔여항) | 선행 최적화: OPT-001 | 적용 커밋: `d3b4eb5`

> 상태: **적용**
> 측정: 2026-09-04 | 데이터셋 medium (`sha256:24ddff07519b`)

## 한 줄 요약

댓글 목록 API가 **댓글 작성자를 한 명씩 따로 읽던 것**을 목록 쿼리에서 함께 읽도록
바꿨다. 요청당 쿼리 수가 **112개에서 3.9개로(−96.5%)** 줄었고, 전체 p95 가
**57.2ms 에서 34.3ms 로(−40.1%)** 줄었다.

무엇보다 **쿼리 수가 데이터 크기와 무관해졌다.** 댓글이 6개인 글과 4,040개인 글이
똑같이 4개의 쿼리를 쓴다.

---

## 1. 무엇이 문제였나

### 1-1. OPT-001 이 남긴 잔여항

OPT-001 은 같은 엔드포인트에서 **반응 확인(2N)** 만 걷어냈다. 요청당 쿼리는
`3 + U + 2N` 에서 `3 + U + 1` 이 됐고, 남은 `U` 가 이 최적화의 대상이다.
`U` 는 **그 게시글 댓글의 서로 다른 작성자 수**다.

실측(OPT-001 §5-2)으로 요청당 112개 중 **약 108개가 작성자 조회**였다.

### 1-2. 원인 — 코드 경로

`Comment.user` 는 `LAZY` 다(`domain/comments/Comment.java:23`). 그리고 댓글 목록
쿼리(`CommentRepository.findByPost`)는 작성자를 함께 읽지 않았다.

```java
// 변경 전
@Query("select c from Comment c where c.isValid=true and c.post=:post")
List<Comment> findByPost(Post post);
```

그래서 DTO 를 만드는 순간 프록시가 하나씩 풀렸다.

```java
// dtos/CommentDto.java · fromEntity
.userId(comment.getUser().getId())               // 프록시 초기화 → SELECT 1회
.author(comment.getUser().getNicknameValue())    // 이미 초기화됨 → 추가 쿼리 없음
```

**작성자 한 명당 한 번**이지 댓글 한 건당 한 번은 아니다. 같은 사람이 댓글을 여러 개
달았으면 두 번째부터는 영속성 컨텍스트의 1차 캐시에서 나온다. 그래서 비용이 `N` 이
아니라 `U` 에 비례한다.

이 SELECT 들은 `CommentDto.fromEntity` 안에서 나가므로 **서비스 계층에도, 컨트롤러에도
쿼리처럼 보이는 코드가 없다.** 코드를 읽어서는 발견되지 않고, 요청당 쿼리 수를 세야
드러난다(`metrics/QueryCountFilter`).

### 1-3. 각 쿼리는 느리지 않았다

작성자 조회는 기본 키 조회다(`users.USR_id`). 1행을 읽고 인덱스를 그대로 탄다.
OPT-001 과 같은 구조의 문제다 — **싼 쿼리를 여러 번 왕복하는 것**이 비용이다.

## 2. 무엇을 어떻게 바꿨나

**변수는 하나다.** 목록 쿼리에 작성자 패치 조인을 넣은 것 외에는 아무것도 건드리지
않았다.

### 2-1. 리포지토리 — 패치 조인

`domain/comments/CommentRepository.java`

```java
@Query("select c from Comment c join fetch c.user where c.isValid=true and c.post=:post")
List<Comment> findByPost(Post post);
```

`@ManyToOne` 패치 조인이라 **결과 행 수가 변하지 않는다.** 댓글 한 건에 작성자는 한
명뿐이므로 조인이 행을 부풀리지 않고, 컬렉션 패치 조인에서 필요한 `distinct` 도,
"페이징을 메모리에서 한다"는 경고도 발생하지 않는다.

`left join` 이 아니라 내부 조인을 쓴 이유는 `USR_id` 가 `nullable = false` 이기
때문이다(`Comment.java:24`). 작성자 없는 댓글은 스키마상 존재할 수 없어 외부 조인이
걸러낼 행이 없다.

### 2-2. 호출부는 그대로다

바꾼 것이 리포지토리 한 줄뿐이라 `CommentService`·`CommentController`·
`CommentAnonymizationService`·`CommentDto` 는 손대지 않았다. 이미 `comment.getUser()`
로 작성자를 읽고 있었고, 그 호출이 이제 쿼리를 발생시키지 않을 뿐이다.

`getCommentById`(단건 조회)도 같은 `findByPost` 를 쓰므로 함께 개선된다. 익명 번호를
매기려면 같은 게시글 댓글 전체가 필요해서 목록과 같은 경로를 타기 때문이다.

### 2-3. 버린 대안

이 기록의 핵심이다. 같은 자리를 다시 볼 때 "왜 이렇게 했지"에 답하기 위한 것이다.

| 대안 | 쿼리 수 | 버린 이유 |
|---|---:|---|
| `@BatchSize(size = 100)` 을 `Comment.user` 에 | 1 + ⌈U/100⌉ | **1 로 내려가지 않는다.** 게시글 8(U=450)에서 5개가 남는다. 게다가 엔티티에 붙는 설정이라 `Comment.user` 를 건드리는 **모든 경로**의 동작이 같이 바뀐다 — 이 엔드포인트 하나를 고치려고 전역 동작을 바꾸는 셈이다 |
| `hibernate.default_batch_fetch_size` 전역 설정 | 1 + ⌈U/n⌉ | 위와 같은 문제에 폭발 반경만 더 넓다. 애플리케이션 전체의 지연 로딩 방식이 바뀌어 **변수 하나 원칙**을 지킬 수 없다 |
| `@EntityGraph(attributePaths = "user")` | 1 | 효과는 같다. 다만 이 메서드는 이미 JPQL 을 직접 쓰고 있어서, **무엇을 거르는지(JPQL)와 무엇을 함께 읽는지(애너테이션)가 두 곳으로 갈린다.** 쿼리 모양을 알려면 두 군데를 합쳐 읽어야 한다. 또 `@EntityGraph` 는 `left join` 을 만드는데 여기서는 넓기만 하고 얻는 것이 없다 |
| DTO 프로젝션 (`select new CommentDto(...)`) | 1 | 필요한 컬럼만 읽으므로 전송량까지 줄어드는 가장 좋은 안이다. 그런데 호출부 셋이 **엔티티를 받아야 동작한다** — `commentReactionService.findMyReactions(comments, user)`, `commentAnonymizationService.anonymize(post, comments)`, `c.getUser().getId()` 로 하는 소유자 판정. 셋을 같이 고치면 변경 규모가 이 문제의 크기를 넘고 **변수가 둘 이상이 되어 측정이 무의미해진다.** 별도 과제로 남긴다 |
| 작성자만 두 번째 쿼리로 일괄 조회 (OPT-001 방식) | 2 | 목록을 받은 뒤 작성자 id 를 모아 `findAllById` 하는 방식. 사용자 행이 **U개만** 전송되어 §6-1 의 중복 전송이 없다. 버린 이유는 왕복이 하나 더 필요한데 그 대가로 얻는 것이 전송량뿐이고, 코드도 더 길어지기 때문이다. **§6-1 의 전송량이 실제로 문제가 되면 이 안으로 돌아온다** |

### 2-4. 변경 규모

```
CommentRepository.java        +11줄 (쿼리 1줄 수정 + 주석)
CommentRepositoryTest.java    신규 3개 테스트
```

## 3. 검증 ① — 단위 테스트

`domain/comments/CommentRepositoryTest.java` (`@DataJpaTest` · H2)

핵심 계약이 "결과가 맞다"가 아니라 **"작성자를 함께 읽는다"** 라서, 쿼리 수 자체를
테스트로 고정했다. Hibernate 통계(`Statistics.getPrepareStatementCount()`)로 실제
실행된 문장 수를 센다.

| 테스트 | 무엇을 고정하나 |
|---|---|
| 작성자를 함께 읽어 온다 | `Hibernate.isInitialized(comment.getUser())` 가 참 |
| 작성자 닉네임을 전부 읽어도 쿼리는 1개다 | 문장 수 정확히 1 |
| 삭제된 댓글은 제외한다 | `isValid` 조건이 패치 조인 때문에 깨지지 않았는지 |

**이 테스트가 실제로 N+1 을 잡는지 음성 대조로 확인했다.** 패치 조인을 다시 뺀 상태로
돌리면 문장 수가 `1 → 4` (목록 1 + 작성자 3)로 늘며 두 테스트가 실패한다.

> 이 검증에서 가장 중요한 코드 한 줄은 `em.clear()` 다. 영속성 컨텍스트를 비우지 않으면
> 준비 단계에서 저장한 `User` 들이 1차 캐시에 남아 **패치 조인이 없어도 추가 쿼리가
> 나가지 않는다.** 그 상태의 테스트는 통과하지만 아무것도 검증하지 못한다.

전체 스위트 **725개 통과 · 실패 0**.

## 4. 검증 ② — 단일 요청 쿼리 수 (결정적, 부하 없음)

앱을 재빌드한 뒤 medium 에 요청을 한 번씩 보내고 `http_server_queries` 누적값의 차이를
읽었다. **부하가 없으므로 잡음이 0 이고 통계가 필요 없다.** OPT-001 §4 와 같은 절차·같은
게시글이다.

| 게시글 | 댓글 수 N | 서로 다른 작성자 U | OPT-001 시점 `3+U+1` | **이번 실측** | 모델 |
|---:|---:|---:|---:|---:|---:|
| 247 | 6 | 5 | 9 | **4** | 4 ✅ |
| 2 | 492 | 130 | 134 | **4** | 4 ✅ |
| 8 | 4,040 | 450 | 454 | **4** | 4 ✅ |

세 건 모두 오차 0 이다. 남은 4개는 **인증 1 + 게시글 1 + 댓글 목록 1 + 반응 일괄 1** 이고,
여기에는 댓글 수에도 작성자 수에도 비례하는 항이 없다.

**요청당 쿼리 수가 데이터 크기와 무관해졌다는 것이 이 최적화의 실제 성과다.** 댓글이
6개인 글과 4,040개인 글이 같은 수의 쿼리를 쓴다.

> **게시글 8 의 댓글 수가 이 문서 안에서 두 값으로 나온다** — 이 표는 4,040, 바로 아래
> 응답 정합성 절은 4,046 이다. 쿼리 수를 잰 시점에는 직전에 돌린 `scripts/comments.js`
> 스모크가 댓글 몇 건을 지운 상태였고, 그 뒤 부하 세트가 회차마다 스냅샷을 복원해
> 원래 상태로 되돌렸기 때문이다. 두 시점 모두 작성자 수는 450 명으로 같고, 쿼리 수가
> 상수 4 라는 결론은 댓글 수에 의존하지 않는다.

### 응답 정합성

쿼리 모양이 바뀌었으므로 **응답이 같은 값을 내는지**를 DB 와 직접 대조했다. 대상은 댓글이
가장 많은 게시글 8(활성 댓글 4,046건 · 작성자 450명)이다.

```
응답 댓글 수            4,046건 = DB 4,046건
실명 댓글               1,586건 = DB 1,586건
익명 댓글               2,460건
```

실명 댓글 1,586건의 **(댓글 id, 작성자 id, 닉네임) 세 값을 DB 와 전량 대조**했다.

```
API 에만 있는 조합   0건
DB 에만 있는 조합    0건
```

익명 보장도 함께 확인했다 — 익명 댓글 2,460건 중 `userId` 가 노출된 것 0건,
`profileUrl` 이 노출된 것 0건이다. 익명 번호(`익명N`)와 `익명(글쓴이)` 구분도 유지된다.

**패치 조인이 작성자를 언제 읽는지만 바꾸고 무엇을 읽는지는 바꾸지 않았다는 직접
증거다.** `@ManyToOne` 내부 조인이라 행이 늘지도 줄지도 않는다는 §2-1 의 주장이
4,046행 규모에서 확인됐다.

> 검증 중에 API 응답의 JSON 키가 `isAnonymous` 가 아니라 `anonymous` 라는 것을
> 발견했다. Lombok 이 `boolean isAnonymous` 의 getter 를 `isAnonymous()` 로 만들고
> Jackson 이 그것을 `anonymous` 로 직렬화하기 때문이다(`isLiked`→`liked`,
> `isOwner`→`owner` 도 같다). **이 최적화와 무관한 기존 동작**이지만, 응답을 대조할 때
> 키 이름을 잘못 알면 검증 자체가 헛돈다 — 실제로 첫 시도에서 그렇게 됐다.

| comment_list 응답 | 약 15ms | 16.4ms | ✅ 거의 맞음 |
| **종단 p95 개선폭** | **20% 안팎이 상한** | **40.1%** | ❌ **상한을 2배 초과** |

**엔드포인트 수준 예측은 맞았는데 종단 백분율만 틀렸다.** 원인은 계산 방식이다. 그 상한은
*평균* 절감치(요청당 21ms)를 전체 workload 에 비례 배분해서 얻은 값이다. 그런데 시스템의
p95 를 만드는 것은 평균적인 요청이 아니라 **댓글이 많은 게시글의 요청**이고, 그런 요청에서
없앤 쿼리는 평균 108개가 아니라 최대 450개다.

실제로 comment 기능의 절감폭은 평균 −18.0ms 인데 p95 는 −78.7ms 로 **4.4배**다.

**교훈: 평균 기반 상한은 평균의 상한이지 꼬리의 상한이 아니다.** N+1 처럼 비용이 데이터
크기에 비례하는 문제는 꼬리에 편중돼 있어서, 평균으로 환산한 예측이 구조적으로 개선폭을
과소평가한다. 다음에 착수 여부를 판단할 때는 **꼬리 요청의 절감치를 따로 계산해야 한다.**

## 6. 부작용 · 트레이드오프

### 6-1. 같은 사용자 행이 여러 번 읽힌다 — 우려는 실재했고, 이득이 더 컸다

패치 조인은 댓글 행마다 작성자 행을 붙여 읽는다. 게시글 8 은 댓글 4,040개에 작성자
450명이므로 **같은 사용자 행이 평균 약 9회 중복해서 읽힌다.** 지연 로딩은 영속성 컨텍스트
덕분에 작성자당 한 번만 읽었으므로, 왕복 횟수를 줄이는 대신 읽는 행 수가 늘어난 것이다.

착수 전에는 이것이 이득을 상쇄할 수 있다고 봤다. **측정은 양쪽을 다 보여준다.**

| 지표 | Before | After | 변화 |
|---|---:|---:|---:|
| MySQL 초당 읽은 행 | 5,935 | 7,294 | **+22.9%** |
| MySQL QPS | 544.3 | 274.8 | −49.5% |
| 요청당 DB CPU 시간 | 8.43ms | 6.35ms | **−24.6%** |

**쿼리 수는 절반인데 읽은 행 수는 오히려 23% 늘었다.** 중복 읽기가 실제로 일어나고 있다는
직접 증거다. 그럼에도 요청당 DB CPU 시간은 25% 줄었다 — **왕복 108회를 없앤 이득이 추가
행 읽기 비용보다 훨씬 크다.**

행 읽기가 싼 이유는 버퍼풀 적중률이 100% 이기 때문이다(Before·After 동일). 사용자 데이터가
전부 메모리에 있어 중복 읽기가 디스크 I/O 를 만들지 않는다. **데이터가 버퍼풀보다 커지면
이 균형은 달라질 수 있다.** 그때는 §2-3 에 적어 둔 "작성자만 두 번째 쿼리로 일괄 조회"
(왕복 2회 · 사용자 행 U개만 읽음)로 돌아가면 된다. 지금 데이터에는 그럴 이유가 없다.

### 6-2. 쿼리당 DB 시간이 6.4배가 됐다 — 악화가 아니다

| 지표 | Before | After |
|---|---:|---:|
| 요청당 쿼리 수 | 112.22 | 3.92 |
| 요청당 DB 시간 | 22.22ms | 4.98ms |
| **쿼리당 DB 시간** | **0.198ms** | **1.272ms** |

**없앤 108개가 이 엔드포인트에서 가장 싼 쿼리였기 때문**이다. 작성자 조회는 기본 키로
1행을 읽는다. 그 싼 쿼리들이 분모에서 빠지면 남은 쿼리들의 평균 단가는 당연히 올라간다.
여기에 목록 쿼리가 조인으로 무거워진 몫이 더해진다.

**쿼리당 비용은 이런 최적화의 성패를 판정하는 데 쓸 수 없다.** 봐야 할 것은 요청당
총량이고, 그것은 22.22ms → 4.98ms 로 줄었다. OPT-001 §6-1 에서 같은 지표가 호스트 클럭
때문에 +27.7% 움직였던 것과는 원인이 다르다 — 이번에는 **쿼리 구성이 바뀐 결과**다.

### 6-3. After 3회차의 auth 이상치

기능별 평균만 보면 auth 가 81.2ms → 102.1ms 로 **+25.8%** 나빠진 것처럼 보인다. 회차별로
풀면 한 회차에 몰려 있다.

```
auth 평균   Before  83.3  87.6  84.5  75.8  74.6
            After   77.9  79.4  188.8  89.1  75.3     ← 3회차만 2배
```

**3회차(`05-08-55`)를 빼면 auth 평균은 80.4ms 로 Before(81.2ms)와 같다(−0.9%).**

이 최적화와 인과 관계가 없다고 보는 근거는 셋이다. 첫째, auth 시간의 대부분은 로그인이고
로그인 비용은 비밀번호 해싱(CPU)이라 **댓글 쿼리 경로와 만나지 않는다.** 둘째, 그 회차는
GC 최대 정지가 108ms 로 다른 회차(21~46ms)의 2~5배였다. 셋째, 같은 회차에서 p95·요청당
DB CPU·앱 CPU 가 전부 동시에 최고값이었다 — 특정 경로가 아니라 **회차 전체가 눌린 형태**다.

**회차를 제외하지 않고 그대로 뒀다.** p95 판정 지표의 변동계수가 5.2% 로 충분히 안정적이고,
포함해도 종단 결론이 바뀌지 않기 때문이다. OPT-001 §7 처럼 제외를 정당화하려면 오염의
독립 증거가 필요한데, 여기서는 GC 정지 하나뿐이라 근거가 약하다.

### 6-4. `findByPost` 를 쓰는 모든 경로가 작성자를 읽게 된다

현재 호출부는 댓글 목록과 단건 조회 둘뿐이고, 둘 다 DTO 를 만들면서 작성자를 읽으므로
낭비가 없다. 앞으로 **작성자가 필요 없는 호출부**가 생기면 그때는 불필요한 조인이 된다.
그 시점에 메서드를 나눠야지, 지금 미리 나누지 않는다.

### 6-5. 정합성

없음. 읽어 오는 시점만 달라졌고 읽는 값은 같다. 근거는 세 층이다.

1. **응답 전량 대조**(§4 응답 정합성) — 댓글 4,046건짜리 게시글에서 실명 댓글 1,586건의
   (댓글 id, 작성자 id, 닉네임)이 DB 와 완전히 일치했고, 익명 댓글 2,460건에서
   `userId`·`profileUrl` 노출이 0건이었다.
2. **단위 테스트**(§3) — 삭제된 댓글 제외 조건이 패치 조인 때문에 깨지지 않는지 고정했다.
3. **부하 세트**(§5) — 5회 전부 오류율 0.000%, 체크 통과율 100%.

쓰기 경로·트랜잭션 경계·이벤트 발행은 건드리지 않았다.
