## 1. 남은 과제 ① — 신뢰 확인 줄이 **포화된 자원을 지목하지 않는다** ← 최우선

### 지금 상태

첫 그리드(신뢰 확인 줄)가 이렇게 나온다.

```
이 실행은 판정에 쓸 수 있다
  측정 MEASURED   체제 HEADROOM   오류율 0.00%
```

포화일 때는 이렇다.

```
판정 전에 확인이 필요하다
  측정 MEASURED   체제 SATURATED (p95 는 큐 대기다. 앱 지연으로 인용 금지)   오류율 0.00%
```

### 무엇이 부족한가

**`SATURATED` 라고만 말하고 "무엇이" 포화됐는지 말하지 않는다.** 자원마다 처방이 다르다.

| 포화된 자원 | 뜻하는 것 | 다음에 볼 곳 |
|---|---|---|
| **커넥션 풀** | 대기줄이 생겼다. p95 에 대기 시간이 섞임 | 풀 크기 · 커넥션 보유 시간 |
| **CPU (throttled)** | 상한에 묶였다. 처리율이 CPU 에 걸림 | 요청당 CPU · CPU 상한 |
| **CPU 사용률** | 여유가 없다. 부하가 조금만 늘어도 대기 | 운용점 재검토 |
| **힙 / GC** | 메모리 압박 | 할당률 · 힙 크기 |

`saturation.js` 는 이미 신호별로 `level` 을 계산해 `record.saturation.signals` 에 담는다.
**데이터는 있고 화면이 안 쓴다.**

### 왜 최우선인가 — E-51 이 근거다

반복 세트에서 회차 하나가 2.4배 느렸고, 원인은 **커넥션 풀 고갈**이었다(20개 대기, 풀 100%).
그런데 그 회차의 리포트 첫 줄은 `체제 NEAR_LIMIT` 이라고만 말한다. **"풀이 찼다"를 보려면
문서 중간의 자원 섹션을 펼쳐야 한다.**

이 발견에 도달하기까지 원인 후보 7개를 기각해야 했다 — 힙 잔존, 버퍼풀 콜드, Docker 볼륨,
호스트 CPU, JVM 워밍업, 스케줄러, JIT. **그중 어느 것도 리포트 첫 화면이 답해 주지
않았다.** 첫 줄에 `커넥션 풀 100% · 대기 20` 이 있었다면 첫 5분에 끝났을 조사였다.

### 요구사항

**첫 그리드가 "이 측정을 신뢰할 수 있는가"에 완결적으로 답해야 한다.**

- 포화된 자원이 있으면 **어느 자원인지, 얼마인지, 임계가 얼마인지** 첫 줄에서 보인다
- 포화가 없으면 그 사실도 **명시적으로** 말한다 (침묵이 아니라 판정)
- 자원이 여러 개 걸리면 **가장 심한 것부터** 나열한다

### 표시안

```
┌ 판정 전에 확인이 필요하다 ─────────────────────────────────────────
│  측정 MEASURED    체제 NEAR_LIMIT    도달률 99.5%    오류율 0.00%
│  ⚠ 커넥션 풀 대기 20 (임계 warn 1 / fail 5) · 풀 사용률 100%
└──────────────────────────────────────────────────────────────────

┌ 이 실행은 판정에 쓸 수 있다 ───────────────────────────────────────
│  측정 MEASURED    체제 HEADROOM    도달률 99.5%    오류율 0.00%
│  자원 여유 있음 — 신호 5개 전부 임계 이하 (최고 CPU 53%)
└──────────────────────────────────────────────────────────────────
```

두 번째 줄이 핵심이다. **정상일 때도 "무엇을 확인했고 얼마였는지"를 남긴다** — 경고가 없는
것과 "확인했고 정상"은 다르다.

## 2. 남은 과제 ② — 신뢰도 항목에 **3단계 색**이 필요하다

### 지금 상태

`sectionTrust` 의 판정이 **2단계(초록/빨강)** 다.

```css
.trust-item.ok  .trust-v { color: var(--good-text); }
.trust-item.bad .trust-v { color: var(--critical); }
```

### 무엇이 부족한가

**신뢰도를 낮추는 축은 대부분 3단계다.** 2단계로 누르면 정보가 사라진다.

| 항목 | 초록 (신뢰 가능) | **주황 (애매)** | 빨강 (신뢰 불가) |
|---|---|---|---|
| **측정 무결성** | `MEASURED` | **`PARTIAL`** — 참고 지표 결측 | `UNMEASURED` |
| **측정 체제** | `HEADROOM` | **`NEAR_LIMIT`** — 큐가 생기기 시작 | `SATURATED` |
| 도달률 | ≥ 99% | **95 ~ 99%** | < 95% |
| 오류율 | 0% | **0 초과 ~ 1%** | ≥ 1% |
| 측정 창 | 완전 | — | `windowIncomplete` |

**`PARTIAL` 과 `NEAR_LIMIT` 이 지금 빨강으로 눌린다.** 둘 다 "판정은 유효하되 주의"인데
`UNMEASURED`·`SATURATED` 와 같은 색이면 구분이 사라진다.

`NEAR_LIMIT` 의 실제 의미가 그 차이를 보여 준다 — E-51 의 이상 회차가 정확히 이 상태였고,
**판정을 못 할 값은 아니지만 표본에서 빼야 하는 값**이었다. 빨강도 초록도 아니다.

### 요구사항

**신뢰도를 낮추는 모든 항목을 3단계 색으로 표시한다.**

```
초록  이 값은 판정을 방해하지 않는다
주황  판정은 가능하지만 해석에 조건이 붙는다 / 표본에서 뺄 후보다
빨강  이 값으로 판정하면 안 된다
```

색만으로 끝내지 않는다 — **주황·빨강에는 이유를 한 줄로 붙인다.** 색은 훑기용이고 판단
근거는 문자다. 색맹 대응이기도 하다.

카드 전체의 테두리 색도 **가장 나쁜 항목의 색**을 따른다. 지금은 `ok`/`bad` 2단계다.

### 기존 배지와의 관계

`b-PASS` / `b-WARN` / `b-FAIL` 배지가 이미 3단계로 정의돼 있다(작업량 섹션에서 사용 중).
**신뢰 확인 줄도 같은 색 토큰을 쓴다** — 화면 안에서 색의 뜻이 하나여야 한다.

## 3. 자기 리뷰 — 이 두 요구가 최선인가

### 반론 1. 첫 줄이 길어져 훑기 어려워지지 않나 — **부분 유효. 조건을 단다**

포화 신호가 5개인데 전부 나열하면 첫 줄이 세 줄이 된다. 그러면 "한눈에"가 깨진다.

**조건:** 임계를 넘은 것만 나열하고, **최대 2개까지**만 첫 줄에 둔다. 3개 이상이면
`외 N건` 으로 접고 자원 섹션 링크를 건다. 정상일 때는 **한 줄 요약**만 남긴다.

### 반론 2. 색 3단계가 "주황 남발"로 이어지지 않나 — **유효. 임계를 실측에서 가져온다**

주황이 자주 뜨면 곧 초록과 구분이 안 되고, T-41 의 경보 피로가 색으로 재발한다.

**조건:** 주황 임계를 감이 아니라 **`saturation.js` 의 `warn` 값**에서 가져온다. 그 값은
E-46 조사의 실측 근거를 갖는다. 새 임계를 이 화면에서 발명하지 않는다 — 설계 원칙 3.

### 반론 3. 도달률·오류율까지 3단계로 할 필요가 있나 — **기각**

오류율은 0% 아니면 문제라고 볼 수도 있다. 그러나 실측에서 `errorRate 0.0001` 같은 값이
나온다(요청 하나가 실패). 그것을 빨강으로 칠하면 진짜 실패와 구분이 없어진다.
**2단계로 누르면 정보가 사라진다는 원칙이 여기에도 적용된다.**

### 반론 4. 이 두 과제가 서로 독립인가 — **아니다. 순서가 있다**

②(3단계 색)가 먼저다. ①(포화 자원 지목)이 만드는 새 항목도 그 색 체계를 써야 하므로,
색을 먼저 정하지 않으면 두 번 고치게 된다.

## 4. 남은 과제 ③ — `rules.json` 의 `gate` / `display` 분리 (미착수)

1차 리뉴얼의 자기 리뷰에서 나왔으나 구현하지 않았다.

**문제.** `rules.json` 은 CI 를 실패시킬 기준(`gate`)인데, 표시용 판정색이 같은 값을 쓴다.
그러면 **"화면에 주황을 띄우려고 게이트 임계를 낮추는" 압력**이 생기고, 거짓 FAIL 이 늘어
T-41 의 경보 피로가 재발한다.

**제안.**

```json
{
  "key": "infra.flat.mysql.slowQueries",
  "gate":    { "fail": { "gt": 2000 } },
  "display": { "warn": { "gt": 300 }, "attention": { "gt": 1000 } }
}
```

출처는 한 곳으로 유지하되(원칙 3) 용도를 나눈다.

**우선순위는 낮다.** ①②를 먼저 한 뒤, `display` 임계에 넣을 근거 데이터가 쌓였을 때 한다.

## 5-b. 남은 과제 ④ — **게이지 지표를 `max` 단독으로 보여주면 오독된다** (실사용 증거 확보)

> 2026-08-27 추가. 과제 ①의 하위 항목이자 **실제로 오독이 발생한 사례**다.
> 상세 경위는 [perf-comment-nplus1-diagnosis.md](../investigations/perf-comment-nplus1-diagnosis.md) 참고.

### 무슨 일이 있었나

`normal-day-2026-08-26T00-06-28` 리포트를 읽고 병목을 **커넥션 풀 고갈**로 판단했다.
근거는 `pool.hikariActive` 가 **10/10** 이라는 것이었다. 실제 값은 이랬다.

```
pool.hikariActive   avg 1.85 / p95 3.35 / max 10
pool.hikariPending  avg 1.0  / p95 1.0  / max 20
pool.hikariAcquireP95Ms  0.98ms
saturation.acquireShare  0.11%
```

**풀이 응답시간에 기여한 비율은 0.11% 였다.** 진짜 병목은 요청당 319.4 쿼리(N+1)였고,
`max 10` 은 원인이 아니라 그 N+1 의 꼬리가 남긴 그림자였다.

### 무엇이 부족한가

게이지(gauge)는 주기 샘플링이라 `max` 가 "한 번 그렇게 찍혔다"는 뜻이다. 그런데 리포트에서
`max` 가 단독으로 눈에 들어오면 "계속 그랬다"로 읽힌다. **같은 `max 10` 이 전혀 다른 상태를
가리킨다:**

| 실행 | 풀 avg / max | 대기 max | 획득 p95 | 실제 상태 |
|---|---:|---:|---:|---|
| 08-19T09-46-07 | **10.0** / 10 | 180 | **6,659ms** | 지속 고갈 |
| 08-26T00-06-28 | **1.85** / 10 | 20 | **0.98ms** | 순간 스침 |

### 요구사항

1. **게이지 계열은 `avg / p95 / max` 를 함께 표시한다.** `max` 단독 노출 금지.
   대상: `pool.hikariActive`, `pool.hikariPending`, `pool.tomcatBusy`,
   `mysql.threadsRunning`, `cpu.cores`, `jvm.threadsLive` 등 `gaugeStats()` 로 만든 전부.
2. **판정값은 `max` 가 아니라 `acquireShare` 다.** "커넥션 대기가 p95 에서 차지하는 비율"이
   원인인지 증상인지를 가르는 유일한 값이므로, 풀 섹션의 **대표 숫자**로 올린다.
3. **비율 지표는 분모를 함께 적는다.** `mysql.rowsReadPerSec` 단독은 의미가 없다.
   `qps` 로 나눈 **쿼리당 읽은 행**이 풀스캔 판별값이고, 이번 실행에서 그 값은 0.865였다.
   `selectScan` 도 절대 건수가 아니라 **전체 쿼리 대비 비율**로 보여야 한다(997건 = 0.059%).

### 왜 과제 ①과 묶어야 하나

과제 ①이 "포화된 자원을 지목하라"이고, 이 항목은 **"지목할 때 어떤 값으로 지목하느냐"**다.
`max` 로 지목하면 이번 같은 오독이 재발한다. **①의 표시안을 확정할 때 이 규칙을 함께 넣는다.**

## 6. 열어 둔 것

- **접기 기본값.** 지금은 자원 섹션이 "이상 있으면 펼침"이다. 병목 가설은 항상 접힘이다.
  후자를 "심각도 높은 항목이 있으면 펼침"으로 바꿀지는 정하지 않았다.
- **`display` 임계의 근거.** 게이트 임계는 SLO 에서 왔지만 표시 임계는 근거가 약하다.
  실측 분포의 백분위를 쓰는 방법이 있으나 표본이 아직 적다.
