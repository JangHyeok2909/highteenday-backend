# 성능 테스트 환경·데이터셋·CI 발견 사항

검토일: 2026-08-05
추가 조사일: 2026-08-06
쉬운 설명 기준 재정리: 2026-08-11

검토 범위:

- `performance/environment/`
- `performance/datasets/`
- `performance/regression/*.yml`

라인 번호는 검토 당시 HEAD 기준이다. 이후 코드가 변경되면 실제 위치와 다를 수 있다.
항목 번호는 기존 리뷰의 F-01~F-38을 E-01~E-38로 바꾼 식별자를 유지한다. 추가 조사 항목은 E-39~E-45다.

E-32의 해결 내용은 2026-08-05 작업을 기준으로 한다.

## 이 문서가 답하는 질문

성능 테스트는 애플리케이션 코드만 재는 일이 아니다. 같은 코드도 CPU, 데이터 크기, 캐시 상태,
Prometheus 수집 간격, 시딩 방법에 따라 전혀 다른 결과를 낸다. 이 문서는 다음 조건이 실제로
고정되고 기록되는지 확인한다.

```text
호스트와 Docker 자원
        +
애플리케이션·MySQL·Redis 설정
        +
데이터셋의 크기와 분포
        +
Prometheus가 볼 수 있는 지표
        +
CI 실행·보존·게시 절차
```

이 다섯 영역 중 하나라도 실행마다 달라지면, 응답시간 차이를 애플리케이션 변경 때문이라고
단정할 수 없다.

## 먼저 알아야 할 결론

- k6와 측정 대상이 같은 Windows PC에서 실행돼 CPU 경합이 결과에 섞인다(E-01).
- 호스트 지표가 없고(E-09), Windows Docker Desktop에서는 cAdvisor도 컨테이너별 지표를
  만들지 못할 수 있다(E-10). 이 경우 리포트의 CPU 공백은 정상 상태가 아니라 관측 실패다.
- 데이터셋 이름만 기록할 뿐, 실제 생성 수량·시더 버전·데이터 분포가 목표와 같은지 충분히
  검증하지 않는다(E-15~E-22). 고정 난수 seed와 새 데이터셋 지문도 현재 구조에서는 실제 DB가
  같다는 것을 보장하지 못한다(E-41~E-45).
- CI 워크플로는 설치되지 않았고, 그대로 설치해도 시딩과 PR 게이트가 제대로 작동하지 않는다
  (E-23~E-31).
- 운영과 로컬 테스트의 토폴로지·하드웨어 차이가 기록되지 않아 결과를 운영 용량으로 직접
  환산할 수 없다(E-03, E-35).
- MySQL exporter는 기본 상태만 보여주며 느린 SQL을 쿼리별로 특정할 수 없다(E-39).

## 용어

- **SUT(System Under Test)**: 성능을 측정하려는 대상 시스템. 여기서는 HighTeenDay 애플리케이션과 관련 데이터 저장소를 뜻한다.
- **부하 발생기**: k6처럼 테스트 요청을 만들어 SUT로 보내는 프로그램
- **VU(Virtual User)**: k6가 동시에 동작시키는 가상 사용자
- **스크레이프**: Prometheus가 대상 시스템에서 지표를 가져오는 작업
- **TSDB**: Prometheus가 시간에 따른 지표를 저장하는 시계열 데이터베이스
- **데이터셋 프로파일**: smoke, small, medium, large, xlarge처럼 테스트 데이터 규모를 정의한 설정
- **시딩**: 성능 테스트에 필요한 사용자, 게시글, 댓글 등의 초기 데이터를 생성하는 작업
- **게이트**: 성능 결과가 허용 기준을 넘었는지 판정해 빌드의 통과 또는 실패를 결정하는 규칙

## 측정 유효성

### E-01. [CRITICAL] 부하 발생기와 측정 대상이 같은 호스트에서 실행됨 — 상태: **부분 해결** (2026-08-16) — 계측은 됨, 물리적 분리는 아님

> **물리적 분리는 하지 않았다.** 장비가 하나뿐이라 그건 이 항목으로 풀 수 있는 문제가
> 아니다. 대신 **"분리하지 못했다면 최소한 얼마나 먹었는지는 기록한다"**를 구현했다.
>
> **무엇을 했나.** `perf-run.js`에 `--loadgen local|docker`를 추가했다. `docker`면 k6가
> `perf-k6`라는 이름의 컨테이너로 뜨고, 그 이름 덕에 **cAdvisor가 부하 발생기를 별도
> 컨테이너로 계측한다.** `--cpus`로 상한도 걸 수 있다. 지표 카탈로그에 `loadgen` 그룹
> (CPU·throttling·메모리)을 만들고, `regression/rules.json`에 `loadgen.throttledPct` 규칙을
> 넣었다.
>
> **가장 중요한 산출물은 `loadgen.throttledPct`다.** 이 값이 0이 아니면 그 실행의 지연은
> 서버가 아니라 **부하 발생기가 만든 것일 수 있다.** 발생기가 먼저 한계에 걸리면 요청을
> 제때 못 보내고 그 지연이 서버 응답시간으로 기록되는데, 서버를 아무리 고쳐도 사라지지
> 않는 가짜 병목이다. 이제 그 경우를 사후에 가를 수 있다.
>
> **임계를 앱보다 낮게 잡았다**(warn 1% / fail 5% vs 앱의 1% / 10%). 앱의 throttling은
> *측정된 사실*이지만 발생기의 throttling은 *측정이 오염됐다는 신호*라 훨씬 적은 양에도
> 반응해야 한다. 다만 `gate:false`다 — `gate:true`는 동시에 "필수 지표" 선언이라(T-08)
> `--loadgen local` 실행이 전부 `UNMEASURED`가 되어 판정 자체가 막힌다.
>
> **버린 대안 — node_exporter만 추가.** 원래 요청은 그것이었으나 성립하지 않는다. WSL2
> 백엔드라 node-exporter가 보는 "호스트"는 VM이고 `k6.exe`는 그 밖이라 **잡히지 않는다**
> (E-09 참고). 부하 발생기를 보려면 VM 안으로 들여야 한다.
>
> **`local`과 `docker`는 비교 조건이 다르다.** 왕복 경로가 다르기 때문이다 —
> `local`은 포트 포워딩으로 `localhost:18080`, `docker`는 컨테이너 네트워크로 `app:8080`.
> `conditions.js`를 v4로 올려 blocking 조건으로 넣었다. 값이 없는 과거 실행은 `local`로
> 본다 — 추측이 아니라 사실이다(컨테이너 옵션이 생기기 전에는 그것뿐이었다).
>
> **k6 버전을 맞춰야 한다.** 처음 `grafana/k6:0.49.0`으로 돌렸더니 `scripts/lib/config.js`의
> 객체 스프레드(`...extra`)에서 SyntaxError로 죽었다. 로컬이 v2.1.0이라 `grafana/k6:2.1.0`
> 으로 맞췄다. 버전이 다르면 문법 문제를 넘어 비교 조건 자체가 달라진다.
>
> **실측 (large, 10 VU · 45초)**: 부하 발생기 CPU 최대 **0.026 코어** · throttled **0.194%** ·
> 메모리 **145.5MB**. 같은 구간 앱은 **1.239 코어** — 발생기가 앱의 **1/48**이다.
> 이 수치가 앞선 관측 하나를 설명한다. 반복 측정에서 경로 오버헤드 179ms(CV 17.8%)가
> 나왔는데, **그 원인이 부하 발생기의 CPU 부족은 아니다.** throttled가 사실상 0이라 4코어
> 상한에 걸린 적이 없다. 원인 후보를 하나 지웠다.
>
> **남은 것**: 물리적 분리(별도 머신/VM), 그리고 CI에서의 사용. 공유 러너에서는 이 방식도
> 같은 머신 안이라 의미가 제한된다.

#### (아래는 해결 전 상태의 기록이다)

**문제**

k6와 SUT가 같은 컴퓨터의 CPU, 메모리, 디스크, 네트워크를 함께 사용한다.

`performance/environment/README.md:32-33`도 부하 발생기와 SUT를 분리하는 것을 첫 번째 원칙으로 설명한다. 같은 호스트에서 실행하면 k6가 사용하는 자원이 애플리케이션 성능 결과에 섞이기 때문이다. 하지만 현재는 이를 막거나 경고하는 장치가 없다.

`performance/scripts/lib/config.js:10`의 기본 대상 주소도 `localhost:18080`이다.

**현재 실행 환경**

기록된 23개 실행의 executor는 모두 동일한 단일 호스트다. 하나의 Windows 데스크톱에서 다음 구성 요소가 함께 실행됐다.

- k6
- Spring 애플리케이션
- MySQL
- Redis
- Prometheus
- Grafana
- 익스포터 3종

CI 초안도 같은 방식이다. `ubuntu-latest` 한 대에 전체 스택을 띄우고 k6까지 설치한다.

**영향**

k6가 CPU를 많이 사용하면 애플리케이션의 응답 시간이 늘어날 수 있다. 이 경우 리포트만 보고는 애플리케이션이 느린 것인지, 부하 발생기가 자원을 빼앗은 것인지 구분하기 어렵다.

현재는 E-09의 node_exporter 부재 때문에 호스트 전체 자원 사용량을 측정할 수 없어 오염 정도도 확인할 수 없다.

**필요한 조치**

부하 발생기를 별도 호스트에서 실행해야 한다. 분리가 어려운 환경에서는 최소한 호스트 지표를 수집하고, 같은 호스트에서 실행한 결과임을 런 기록에 남겨야 한다.

### E-02. [HIGH] 서비스에 설정한 CPU 한계 합계가 크고 관측 도구에는 한계가 없음 — 상태: 미해결

**문제**

주요 서비스에 설정한 CPU 한계는 다음과 같다.

- MySQL: 2.0 vCPU
- Redis: 1.0 vCPU
- 애플리케이션: 2.0 vCPU
- 합계: 5.0 vCPU

여기에는 k6가 사용할 CPU가 포함되지 않는다.

반면 Prometheus, Grafana, 각종 익스포터, cAdvisor에는 `deploy.resources` 설정이 없다. 이 프로세스들은 성능 측정 중 CPU를 제한 없이 사용할 수 있다.

**영향**

호스트의 실제 CPU 수가 충분하지 않으면 서비스와 관측 도구가 서로 CPU를 빼앗는다. 관측 도구가 사용한 CPU 때문에 애플리케이션이 느려져도, 현재 수집기는 주로 `perf-app`과 `perf-mysql`만 조회하므로 그 원인이 리포트에 보이지 않는다.

호스트 사양도 E-03과 E-35처럼 기록돼 있지 않아 5 vCPU 배분이 실제 장비에 적절한지 판단할 근거가 없다.

**필요한 조치**

호스트 CPU 수를 먼저 명시하고 서비스별 CPU 예산을 다시 계산해야 한다. 관측 도구의 자원 사용량도 제한하거나 별도로 측정해야 한다.

### E-03. [HIGH] 성능 테스트 환경이 운영 환경과 다르지만 차이를 설명할 운영 사양이 없음 — 상태: 미해결

**문제**

운영 환경과 성능 테스트 환경의 구조가 다르다.

- 운영: EC2의 host 네트워크를 사용하고 데이터베이스는 RDS에 있음
- 성능 테스트: 같은 호스트의 Docker 브리지 네트워크에서 애플리케이션과 MySQL 컨테이너가 함께 실행됨

네트워크 경로, 데이터베이스 실행 위치, 자원 경합 조건이 모두 다르다.

그런데 `performance/environment/README.md`의 하드웨어 표는 CPU, 메모리, 디스크 항목이 모두 “실측 기입” 플레이스홀더로 남아 있다.

**영향**

테스트에서 사용하는 2 vCPU, 2.5GB 같은 한계값이 운영 환경을 어떻게 축소하거나 재현한 것인지 알 수 없다. 따라서 테스트 결과를 운영 용량이나 운영 병목과 직접 연결하기 어렵다.

**필요한 조치**

운영과 성능 테스트 환경의 사양 및 토폴로지를 모두 기록해야 한다. 서로 다른 부분은 왜 다른지, 결과 해석 시 어떤 보정이 필요한지 명시해야 한다.

### E-04. [MEDIUM] 데이터 규모는 크게 달라지지만 MySQL과 Redis 메모리는 항상 같음 — 상태: 미해결

**문제**

데이터셋은 smoke의 게시글 50개부터 xlarge의 게시글 50만 개까지 약 10,000배 차이가 난다.

하지만 모든 프로파일이 다음 메모리 설정을 함께 사용한다.

- MySQL buffer pool: 1GB
- Redis maxmemory: 384MB

**영향**

large나 xlarge 데이터셋의 실제 사용 데이터가 메모리에 들어가지 않으면 MySQL buffer pool miss와 Redis eviction이 증가한다.

이 변화는 애플리케이션 코드의 회귀가 아니라 단순히 데이터 크기에 비해 메모리가 부족해서 발생할 수 있다. 하지만 `rules.json`은 이를 애플리케이션 성능 신호처럼 게이트한다.

**필요한 조치**

데이터셋별로 예상 작업 집합 크기를 기록해야 한다. 데이터 규모를 늘릴 때 인프라 메모리도 함께 조정할지, 고정된 작은 장비의 한계를 측정할지 실험 목적을 명확히 구분해야 한다.

### E-05. [MEDIUM] MySQL 설정 파일이 실제 컨테이너에 연결되지 않음 — 상태: 미해결

**문제**

`performance/environment/mysql/perf.cnf`가 존재하지만 MySQL 컨테이너에 마운트되지 않는다. 따라서 파일을 수정해도 실제 성능 테스트 설정에는 반영되지 않는다.

같은 MySQL 튜닝 값이 다음 세 곳에 중복돼 있다.

- `mysql/perf.cnf`
- `docker-compose.perf.yml`
- `docker-compose.seed.yml`

`docker-compose.seed.yml`에는 Docker Compose의 `command`가 기존 명령과 병합되지 않고 전체를 교체하므로 옵션을 빠뜨리면 조용히 설정이 사라진다는 경고도 있다. 하지만 세 설정이 같은지 확인하는 자동 검증은 없다.

**영향**

한 파일만 수정하면 seed 환경과 측정 환경의 MySQL 설정이 달라질 수 있다. 파일이 존재한다는 이유로 적용됐다고 오해할 수도 있다.

**필요한 조치**

MySQL 설정의 기준을 한 곳으로 통합하고 실제 컨테이너가 그 설정을 사용하는지 자동으로 확인해야 한다.

### E-06. [MEDIUM] 운영에서 확인해야 할 테이블 이름 문제를 성능 환경에서만 우회함 — 상태: 미해결

**문제**

성능 환경은 MySQL에 `--lower-case-table-names=1`을 설정한다. 이 옵션은 테이블 이름의 대소문자 차이를 무시하게 해 BTL-008에서 다루는 문제를 피한다.

운영 환경에서 대소문자를 구분한다면, 운영에서 발생할 수 있는 문제를 성능 테스트에서는 재현하지 못한다.

또한 이 옵션은 MySQL 데이터 디렉터리를 처음 만들 때만 적용된다. 기존 볼륨을 사용하는 경우 옵션을 바꿔도 적용되지 않을 수 있지만 별도 경고가 없다.

**영향**

성능 테스트는 통과하지만 운영에서는 테이블 이름 차이로 쿼리가 실패할 수 있다. 실행자는 옵션이 적용됐다고 생각하지만 실제 기존 볼륨에는 적용되지 않은 상태도 생길 수 있다.

**필요한 조치**

운영과 같은 테이블 이름 정책을 사용해 BTL-008을 실제로 재현해야 한다. 컨테이너 시작 시 현재 MySQL 설정값도 확인해야 한다.

### E-07. [MEDIUM] 데이터 생성과 성능 측정이 서로 다른 애플리케이션 설정을 사용함 — 상태: 미해결

**문제**

seed용 Docker Compose 오버라이드는 측정 환경보다 강한 애플리케이션 설정을 사용한다.

- Hikari 풀: 10 → 50
- JVM 힙: 1GB → 2GB
- flush 관련 설정 완화
- slow query log 비활성화
- performance schema 비활성화

API로 데이터를 생성하는 목적은 비정규화 카운터, 알림 팬아웃, 핫스코어 같은 부수효과까지 실제 서비스와 같은 경로로 만드는 것이다. 하지만 이 과정이 측정 환경보다 5배 큰 커넥션 풀에서 실행된다.

**영향**

측정 환경에서는 실패하거나 지연될 쓰기 작업이 seed 환경에서는 성공할 수 있다. 시딩 과정에서 드러나야 할 풀 고갈이나 느린 쿼리 문제도 숨겨진다.

시딩이 끝난 뒤 설정이 정상으로 돌아왔는지는 수동 `curl` 두 줄로 확인해야 한다. 확인을 빠뜨리면 다른 설정으로 성능 테스트를 실행할 수 있다.

**필요한 조치**

데이터 생성에만 필요한 예외 설정과 실제 측정 설정을 명확히 구분하고 자동 검증해야 한다. 가능하면 측정 환경과 동일한 애플리케이션 설정으로 시딩해야 한다.

### E-08. [MEDIUM] warmup이라는 이름이 실제 동작과 다르며 테스트는 항상 콜드 상태에서 시작함 — 상태: **해결** (2026-08-12)

> 이 항목이 "환경 관점에서 본 같은 문제"라고 스스로 표시한 T-03(`perf-findings-tools.md`)과
> 함께 해결했다 — 구현 상세·대안·검증은 그쪽에 적었다. 이 항목의 "필요한 조치" 두 가지를
> 그대로 충족한다.
>
> 1. **"실제 warmup 트래픽 단계를 만들고"** — `--warmup`이 이제 `perf-run.js`를 거쳐 k6에
>    `-e WARMUP`으로 전달되고, 시나리오는 그 값으로 실제 ramp-up stage 길이를 만든다
>    (`scripts/lib/phases.js`의 `stagesFor()`). CI 주석이 말하던 "JIT 워밍업 구간 제외"가
>    이제 실제로 그 구간 동안 real traffic이 흐른다는 뜻이 됐다 — 예전처럼 Prometheus
>    조회 시작점만 미루는 게 아니다.
> 2. **"warmup 종료 후 같은 구간의 k6 및 인프라 지표만 판정에 사용"** — `k6.phases.measure`
>    (k6 지표)와 `collect.js`의 `measureWindow()`(인프라 지표)가 둘 다 같은
>    `run.phasePlan`에서 파생되므로 항상 같은 시간대를 본다.
>
> **콜드 스타트를 일반 회귀와 분리하는 부분**은 이미 존재하던 `cold-start.js`가 계속
> 담당한다 — 이번에 `mode:'cold-start', warmupSec:0`으로 명시적으로 선언해, 다른
> 시나리오와 달리 "앞부분을 warmup으로 제외"하는 정책을 이 시나리오에는 적용하지
> 않도록 못박았다(전체 구간이 `phase:measure`로 태깅됨 — 콜드 상태 자체가 측정 대상이라는
> 이 시나리오의 목적을 그대로 보존).
>
> Docker 재시작·Redis FLUSHALL로 실험 사이를 콜드하게 만드는 README의 절차 자체는
> 건드리지 않았다 — 그건 EXP-000류 "환경 리셋" 실험 설계의 영역이고, 이번 작업의
> 범위는 "warmup이 실제로 무엇을 하는가"였다.

**문제**

CI 주석은 warmup을 “JIT 워밍업 구간 제외”라고 설명한다. 하지만 실제 `--warmup`은 Prometheus 조회 시작 시점만 뒤로 이동한다. k6 트래픽에서 warmup 단계를 실행하는 기능은 없다.

이는 도구 문서의 T-03과 같은 문제를 환경 관점에서 본 것이다.

한편 README는 실험 사이에 다음 작업을 하도록 안내한다.

- Docker 컨테이너 재시작
- Redis `FLUSHALL`

이 절차는 JVM, 애플리케이션 캐시, Redis 캐시를 의도적으로 차갑게 만든다.

**영향**

각 실행은 콜드 스타트 상태에서 시작하지만 k6의 p95에는 콜드 구간이 포함된다. 반면 일부 Prometheus 지표에서는 warmup 시간이 제외된다. 같은 리포트의 지표가 서로 다른 상태와 시간 구간을 나타낸다.

**필요한 조치**

실제 warmup 트래픽 단계를 만들고, warmup 종료 후 같은 구간의 k6 및 인프라 지표만 판정에 사용해야 한다. 콜드 스타트를 측정하려는 실험은 일반 회귀 테스트와 분리해야 한다.

### E-09. [HIGH] 호스트 지표를 수집하는 node_exporter가 없음 — 상태: **해결** (2026-08-16)

> **무엇을 했나.** `docker-compose.perf.yml`에 `prom/node-exporter:v1.8.2`를 `perf-node-exporter`로
> 추가하고 Prometheus에 `job: host`로 등록했다. 지표 카탈로그에 `host` 그룹을 만들어
> CPU 사용률·코어당 run queue·iowait·steal·가용 메모리·컨텍스트 스위치를 실행 기록에
> 싣는다. 수집 지표가 92개에서 110개로 늘었다.
>
> **이 항목이 놓치고 있던 것 — "호스트"가 무엇인가.** Docker Desktop이 WSL2 백엔드로 돌기
> 때문에 컨테이너 안의 node-exporter가 보는 것은 **Windows가 아니라 WSL2 VM**이다
> (커널 `6.18.33.2-microsoft-standard-WSL2`, 코어 20, 메모리 16.5GB). 앱·MySQL·Redis는 그
> 안에 있으므로 정확히 측정되지만, **Windows에서 직접 도는 `k6.exe`는 잡히지 않는다.**
> 그래서 E-01(부하 발생기 분리)은 이것만으로 해결되지 않는다 — 별도로 처리했다.
>
> **고민한 대안 — windows_exporter.** Windows 호스트 자체를 재려면 그쪽이 맞다. 채택하지
> 않았다. 측정 대상(앱·DB·Redis)이 전부 VM 안에 있어 **판정에 필요한 포화도는 VM 기준**이고,
> Windows 전체 지표는 다른 프로그램(브라우저·IDE)까지 섞여 해석이 어렵다. 부하 발생기를
> 보려는 목적이라면 k6를 VM 안으로 들이는 편이 더 직접적이다(E-01 참고).
>
> **막힌 곳 두 군데.** ① 흔한 예제의 `/:/host/root:ro,rslave` 는 WSL2에서 거부된다
> (`path / is mounted on / but it is not a shared or slave mount`). `rslave`는 실행 중 새로
> 붙는 마운트를 따라가기 위한 것이고 필요한 지표는 전부 `/proc`·`/sys`에서 나오므로 뺐다.
> ② Prometheus에 `--web.enable-lifecycle`이 없어 HTTP 재적용이 안 된다 — 컨테이너를
> 재시작했다.
>
> **쿼리 함정 하나.** `node_load1 / count(count by (cpu) (node_cpu_seconds_total))`을 그대로
> 쓰면 왼쪽에는 `instance`·`job` 레이블이 있고 오른쪽 집계에는 없어 **벡터 매칭이 실패해
> 빈 결과**가 된다. `scalar()`로 접어야 한다. 실측에서 "없음"으로 나와 발견했다.
>
> **검증**: `up{job="host"}=1` 확인 후 실제 실행에서 `host.*` 11개 항목이 `run.json`에
> 실리는 것을 확인했다(코어 20, CPU 사용률 최대 3.41%, 코어당 run queue 최대 0.025,
> steal 0%, 가용 메모리 12.4GB).

#### (아래는 해결 전 상태의 기록이다)

**문제**

`prometheus.yml`에 등록된 수집 대상은 다음 네 종류뿐이다.

- Spring 애플리케이션
- MySQL
- Redis
- 컨테이너

호스트 운영체제 지표를 제공하는 node_exporter는 없다.

**수집하지 못하는 정보**

- 호스트 전체 CPU 사용률
- 실행 대기 중인 프로세스 수
- CPU steal
- 페이지 캐시
- 디스크 지연
- 호스트 메모리 압박

**영향**

E-01처럼 k6와 SUT를 같은 호스트에서 실행할 때, 부하 발생기나 Docker Desktop이 시스템 자원을 얼마나 사용했는지 알 수 없다. 애플리케이션 병목과 호스트 자원 경합을 구분할 수 없다.

**필요한 조치**

### E-10(원문). 최초 관측 기록 — 2026-08-05

**문제**

`performance/environment/README.md:238-278`은 Docker Desktop과 containerd 조합에서 cAdvisor가 컨테이너별 시계열을 만들지 못한다고 설명한다.

- 네트워크 사용량
- 디스크 사용량

**필요한 조치**

> **2026-08-17 실측 — 이 항목이 지적한 것보다 문제가 크다.**
>
> 원문은 "샘플이 적어 흔들린다"는 정밀도 문제로 적혀 있다. 그런데 실측해 보니
> **짧은 실행은 흔들리는 게 아니라 아예 다른 동작점을 잰다.**
>
> 같은 시나리오·같은 200 VU·같은 데이터셋으로 측정 구간만 바꿔 잰 값이다.
>
> | 측정 구간 | measure 요청 수 | **RPS** | P95 |
> |---|---:|---:|---:|
> | 1200초 (기준선) | 29,650 | **18.0** | 11,858ms |
> | 300초 (진단) | 6,340 | **10.5** | 13,891ms |
>
> **처리량이 40% 낮게 나온다.** VU 수도 부하 모델도 같은데 그렇다. 이 시스템은 CPU가
> 100% 포화라 큐가 정상 상태에 도달하는 데 시간이 걸리는데, 300초는 그 과도 구간을
> 벗어나지 못한다. 워밍업을 300초에서 180초로 줄인 것도 겹쳤다.
>
> 즉 짧은 실행의 값은 **부정확한 것이 아니라 다른 질문에 대한 답**이다. 정밀도를 보정해서
> 쓸 수 있는 종류가 아니다.
>
> 실무 규칙: **측정 구간을 줄인 실행을 정상 구간 실행과 비교하지 않는다.**
> `measurementProfile`이 blocking 조건이라 자동 판정은 이미 막고 있다 — 막지 못하는 것은
> 사람이 손으로 하는 비교다(E-46에서 실제로 그 실수를 했다).

**문제**

Prometheus는 지표를 5초마다 수집한다. 그런데 기록된 실행 중에는 26~52초짜리가 많아 실행당 샘플이 약 5~10개뿐이다.

`increase()`는 적은 샘플을 바탕으로 구간 전체 값을 외삽한다. `slowQueries`와 `hikariTimeouts` 게이트도 이 추정값을 사용한다.

다음 세 쿼리는 1분 범위를 하드코딩한다.

- CPU rate
- MySQL 최대 QPS
- Redis 최대 처리량

실행 시간이 1분보다 짧으면 쿼리가 테스트 시작 전의 데이터까지 포함한다.

**영향**

샘플 수가 적어 작은 시간 차이에도 결과가 크게 흔들릴 수 있다. 이전 실행의 데이터나 시작 전 유휴 구간이 섞이면서 실제 피크가 낮아질 수도 있다.

**필요한 조치**

게이트용 실행의 최소 시간을 정해 충분한 샘플을 확보해야 한다. 쿼리 범위도 실제 실행 구간을 넘지 않도록 조정해야 한다.

### E-12. [MEDIUM] 모든 데이터셋이 같은 Prometheus 저장소와 같은 라벨을 사용함 — 상태: 미해결

**영향**

지표만 보고 어느 데이터셋 또는 어느 실행에서 나온 값인지 확인하기 어렵다. 실행 시간이 겹치거나 조회 구간이 잘못 계산되면 서로 다른 실행의 지표가 섞일 수 있다.

**필요한 조치**

### E-13. [MEDIUM] 테스트 도중 수집 대상이 죽어도 감지하지 못함 — 상태: 미해결

**필요한 조치**

실행 구간 전체의 타깃 `up` 상태와 예상 샘플 수를 확인해야 한다. 수집 상태도 타깃별, 지표 그룹별로 기록해야 한다.

### E-14. [MEDIUM] 인증 없는 Prometheus 원격 쓰기 경로가 네트워크에 노출됨 — 상태: **해결** (2026-08-14)
> `docker-compose.perf.yml`의 포트 바인딩을 전부 루프백으로 좁혔다. `"9090:9090"`은 Docker가
> `0.0.0.0`에 붙이므로 같은 네트워크의 누구나 접근할 수 있는데, `--web.enable-remote-write-receiver`에는
> **인증이 없다.** 외부에서 임의 지표를 써 넣어 측정을 오염시키거나 질의 API로 전체 지표를
> 읽어 갈 수 있었다. 카페·회사 공용 와이파이에서 부하 테스트를 돌리면 그대로 노출된다.
>
> **조사 중 더 심한 것을 함께 발견해 같이 막았다.** 원 발견은 Prometheus만 지목했는데,
> 실제로는 데이터 저장소도 전부 열려 있었다.
>
> | 서비스 | 문제 | 조치 |
> |---|---|---|
> | Prometheus 9090 | 인증 없는 remote-write 수신 | `127.0.0.1` 고정 |
> | Grafana 3001 | 익명 열람 허용 + 기본 비밀번호 `perf` | `127.0.0.1` 고정 |
> | MySQL 13316 | root 비밀번호 기본값 `perfroot` | `127.0.0.1` 고정 |
> | Redis 16389 | **인증 없음**(`redis-perf.conf`에 `requirepass` 없음) | `127.0.0.1` 고정 |
> | 앱 18080 | — | `${APP_BIND_ADDR:-127.0.0.1}` |
>
> **앱 포트만 변수로 둔 이유.** 부하 발생기를 다른 호스트로 분리하면(E-01) 원격 k6가 이
> 포트에 붙어야 한다. 그때만 `APP_BIND_ADDR=0.0.0.0`으로 **명시적으로** 연다. 기본값이
> 열려 있는 것과 필요할 때 여는 것은 다르다.
>
> **버린 대안 — Prometheus·Redis에 인증을 붙이는 것.** 더 근본적이지만 로컬 실험 환경에
> 자격 증명 관리 부담을 더한다. 그 자격 증명이 또 `.env.perf.example`에 들어가면 E-34와 같은
> 문제가 반복된다. 루프백 바인딩은 설정 한 줄이고 되돌리기도 쉽다. 원격 접근이 필요하면
> SSH 터널을 쓴다(`ssh -L 9090:localhost:9090 <host>`).
>
> 검증: `docker compose config`로 다섯 서비스 전부 `host_ip: 127.0.0.1`을 확인했다.

**문제**

Prometheus는 다음 설정으로 실행된다.

- `--web.enable-remote-write-receiver` 활성화
- 9090 포트를 모든 인터페이스에 공개

Grafana도 다음 기본 접근 정보를 사용한다.

- 관리자 계정: `admin/perf`
- 익명 뷰어 허용

**영향**

공유 네트워크에서 접근 가능한 경우 제3자가 Prometheus에 임의의 시계열을 쓸 수 있다. 이 저장소의 데이터가 성능 기준선을 만드는 데 사용되므로 조작된 지표가 회귀 판정에 영향을 줄 수 있다.

Grafana를 통해 내부 성능 정보도 노출될 수 있다.

**필요한 조치**

포트를 로컬 인터페이스 또는 격리된 네트워크에만 바인딩해야 한다. 원격 쓰기가 꼭 필요하지 않으면 비활성화하고, 필요한 경우 인증과 접근 제어를 추가해야 한다.

### E-18. [MEDIUM] 시딩을 다시 실행하면 기존 데이터 위에 대부분의 데이터를 중복 생성함 — 상태: 미해결

**문제**

시더는 계정 생성에서 409 응답이 발생한 경우만 기존 데이터로 보고 건너뛴다. 게시글, 댓글, 반응은 시딩을 다시 실행할 때마다 전량 새로 만든다.

`bootstrap`에는 게시글이 이미 존재하면 실행을 거부하는 보호 장치가 있다. 하지만 CI는 `bootstrap`을 거치지 않고 `seed.js`를 직접 호출해 이 보호 장치를 우회한다.

**2026-08-13 추가 확인 — 반응과 스크랩은 단순 누적보다 더 위험하다.**

기존 설명의 “반응을 전량 새로 만든다”는 표현은 실제 서비스 동작을 충분히 설명하지 못한다.
`PostReactionService.likeReact()/dislikeReact()`와 `ScrapService.toggleScrap()`은 같은
사용자·게시글 조합에 같은 요청이 다시 오면 기존 상태를 취소할 수 있는 토글 API다.

따라서 기존 DB에 시더를 다시 실행하거나, 결과를 확인하지 못한 요청을 재전송하면 데이터가
중복되는 데서 끝나지 않는다. 좋아요·싫어요·스크랩이 **생성 전 상태로 되돌아갈 수 있다.**
`seed.js`의 “reactions/scraps는 멱등이라 재시도가 안전하다”는 주석도 실제 서비스 구현과
일치하지 않는다.

**근거**

목표가 500개였지만 실제 데이터가 1065개로 늘어난 사고 사례가 문서에 기록돼 있다.

**영향**

같은 프로파일 이름을 사용해도 시딩 횟수에 따라 실제 데이터 규모가 달라진다. 성능 실행 간 비교가 무의미해질 수 있다.

**필요한 조치**

시딩을 멱등하게 만들거나 기존 데이터가 있으면 명확히 실패해야 한다. CI도 반드시 같은 보호 절차를 사용해야 한다.
토글 API는 재전송 횟수에 의존해서는 안 된다. 깨끗한 DB에서 한 번만 실행하거나, 요청 후 현재
상태를 조회해 목표 상태와 비교하는 방식으로 바꿔야 한다.

### E-19. [MEDIUM] 목표 수량보다 적게 생성돼도 실행 기록에 남지 않음 — 상태: 미해결

**문제**

사용자와 게시글처럼 중복되면 안 되는 조합을 만들 때 최대 시도 횟수를 `목표 수량 × 20`으로 제한한다. 가능한 고유 조합을 충분히 찾지 못하면 목표 수량에 도달하기 전에 생성을 중단한다.

- 부족 사실은 stdout 경고로만 출력
- 런 기록에는 프로파일 이름만 저장
- 실제로 생성된 사용자, 게시글, 댓글, 반응 수량은 저장하지 않음
- 드리프트 검사는 양의 방향에 치우쳐 있어 부족분을 같은 수준으로 검출하지 못함

현재 `pooled()`는 `ok / failed / skipped / retried`를 계산하고 콘솔에 출력하지만 그 결과를
호출자에게 반환하지 않는다(`performance/datasets/seed.js:200-253`). 실패나 건너뜀이 있어도
예외를 던지지 않으므로 다음 단계가 계속 실행되고 마지막 JSON과 `meta.json`도 승격된다.

특히 다음 두 값은 실제 성공 수량이 아니다.

- `users.json`: 가입·로그인·학교 배정 성공 여부와 무관하게 `buildUsers()`가 계획한 사용자 전부
- `meta.json`의 `counts.users`: 같은 계획 배열의 `users.length`

즉 콘솔에 “실패 N건”이 표시돼도 프로세스 종료 코드는 0이고, 산출물은 정상 데이터셋처럼 남을
수 있다. 사용자가 경고를 보지 못하는 문제를 넘어 **자동화가 실패를 판정할 구조 자체가 없다.**

**영향**

같은 `large` 프로파일이라도 실제 데이터 수량이 다를 수 있다. 경고 로그를 놓치면 미달 데이터셋을 정상 데이터셋으로 사용하게 된다.

**필요한 조치**

시딩 결과에 목표 수량과 실제 수량을 함께 저장해야 한다. 필수 데이터가 허용 오차보다 부족하면 시딩을 실패 처리해야 한다.
각 단계는 `target / attempted / succeeded / failed / skipped / retried`를 반환해야 하며, 후속
단계와 산출물에는 성공이 확인된 리소스만 전달해야 한다.

### E-20. [MEDIUM] 데이터 생성기 버전이 실행 기록에 남지 않음 — 상태: **해결** (2026-08-16)

> **무엇을 했나.** 이 항목이 요구한 "시더 코드 + 프로파일 설정 + 난수 시드를 포함한
> 데이터셋 버전"이 `meta.json`의 `generatorVersion`·`fingerprint`로 저장되고,
> `perf-run.js`가 읽어 실행 기록의 `datasetFingerprint`에 싣는다. 여기에 더해
> **`generatorVersion`과 무관하게 DB 상태 자체가 같은지**를 보는 상태 지문 축이 추가돼
> (2026-08-16), 생성기가 같아도 데이터가 달라진 경우까지 잡힌다.
>
> **왜 두 축이 다 필요한가.** 생성기 버전은 "다음에 만들면 다른 데이터가 나오는가"에
> 답하고, 상태 지문은 "지금 들어 있는 것이 같은가"에 답한다. 생성기를 안 바꿔도 쓰기
> 테스트가 데이터를 바꾸면 후자만 달라진다 — 이 항목이 걱정한 반대 방향의 사고다.
>
> **검증**: 현재 large의 `generatorVersion` `c8aeaa589d4d`, 생성 지문
> `sha256:bb5fdd9cb816`, 상태 지문 `sha256:c230eee635a4`가 실행 기록과 인덱스 양쪽에
> 실리는 것을 확인했다. 설계: `performance/DATASET-STATE.md`.

#### (아래는 해결 전 상태의 기록이다)

**문제**

난수 생성기의 초기값은 고정돼 있지만, 데이터를 만드는 코드 자체는 변경될 수 있다. 실제 코드에도 “이 커밋 이후 시드 데이터는 이전과 다르다”는 주석이 있다.

현재 런 기록에는 k6 스크립트 해시만 저장한다. 데이터셋 생성기 버전이나 생성 결과 해시는 저장하지 않는다.

**영향**

프로파일 이름과 난수 시드가 같아도 생성기 코드가 바뀌면 데이터의 관계와 분포가 달라질 수 있다. 하지만 회귀 엔진은 이를 모르고 이전 실행과 현재 실행을 비교한다.

**필요한 조치**

시더 코드, 프로파일 설정, 난수 시드를 포함한 데이터셋 버전을 계산해 런 기록에 저장해야 한다.

### E-21. [MEDIUM] 시더의 재시도가 연구 대상인 쓰기 실패를 숨김 — 상태: 미해결

**문제**

시더는 데드락이나 커넥션 풀 고갈이 발생하면 최대 6회까지 백오프하며 재시도한다.

그럼에도 smoke 시딩에서 댓글 2.7%가 생성되지 않은 기록이 있다. 이는 BTL-002와 BTL-003이 실제 시딩 과정에서도 발생했음을 보여준다.

반면 k6의 측정 스크립트에는 같은 재시도 정책이 없다.

**2026-08-13 추가 확인 — 전송 오류 재시도는 결과가 불명확하다.**

`isRetryable()`은 `ECONNRESET`, `EPIPE`, `socket hang up`, `fetch failed`도 재시도한다
(`performance/datasets/seed.js:191-195`). 코드 주석은 이런 오류를 “요청이 서버에 닿지 않은
것이 확실하다”고 설명하지만, TCP 연결이 응답 도중 끊겼다면 서버 트랜잭션은 이미 커밋됐을 수
있다. 클라이언트가 응답을 못 받았다는 사실만으로 서버 미처리를 증명할 수 없다.

이 경우 게시글·댓글 POST를 재전송하면 중복 생성될 수 있고, E-18의 토글 요청을 재전송하면
성공했던 상태를 다시 취소할 수 있다. 데드락처럼 서버가 롤백을 보장한 실패와 네트워크 결과
불명확 실패를 같은 재시도 정책으로 묶으면 안 된다.

**영향**

데이터를 만들 때와 실제 부하를 측정할 때 실패 처리 방식이 다르다. 시딩에서는 재시도로 숨겨진 문제가 측정에서는 즉시 오류로 나타나므로 두 결과를 직접 비교하기 어렵다.

시더가 성공으로 끝나도 일부 데이터가 유실됐을 수 있다.

**필요한 조치**

시딩 재시도 횟수와 최종 실패 수를 결과에 기록해야 한다. 측정 시나리오와 시더의 재시도 차이도 실험 조건에 명시해야 한다.
재시도 원인을 `롤백 확정 / 요청 전 실패 / 결과 불명확`으로 구분하고, 결과 불명확 쓰기는
idempotency key나 사후 상태 조회 없이 자동 재전송하지 않아야 한다.

### E-22. [MEDIUM] 데이터셋을 바꿔도 이전 Redis 캐시가 남을 수 있음 — 상태: **부분 해결** (2026-08-16) — 프로파일 전환 경로는 그대로

> **해결된 부분 — 스냅샷 복원 경로.** `tools/snapshot.js`의 복원 절차에 `FLUSHALL`이
> **선택이 아니라 필수 단계**로 들어갔다. 이유는 이 항목이 적은 "옛 캐시가 남는다"보다
> 심각하다. Redis에는 아직 DB로 내려가지 않은 **조회수 버퍼**가 들어 있어서, DB만 과거로
> 되돌리고 Redis를 남기면 스케줄러가 **미래 상태의 버퍼를 과거 데이터 위에 얹는다.**
> 캐시된 게시글 목록도 복원 후 DB에 없는 ID를 가리킬 수 있다.
>
> 그 대가로 복원 직후 캐시는 항상 cold이고, 그 사실을 `cacheState: cold`로 기록한다.
>
> **고민한 대안 — 프로파일별 Redis 볼륨 분리.** 이 항목이 제안한 방식이다. 채택하지
> 않았다. 볼륨을 나눠도 **같은 프로파일 안에서 DB만 되돌리고 캐시를 남기는** 위 문제는
> 그대로 남는다. 문제의 본질이 "프로파일 간 오염"이 아니라 "DB와 캐시의 시점 불일치"라,
> 복원 절차에서 비우는 쪽이 정확하다.
>
> **남은 부분.** 프로파일을 바꿔 `docker compose up -d`만 하는 경로는 여전히 이전 캐시를
> 남긴다. `bootstrap.js`를 거치면 처리되지만 CI는 그것을 호출하지 않는다. 이 경로는
> CI 작업(E-23~E-31)과 함께 다뤄야 한다.

#### (아래는 해결 전 상태의 기록이다)

**문제**

MySQL은 데이터셋 프로파일별로 다른 볼륨을 사용한다. Redis는 모든 프로파일이 같은 상태를 공유한다.

Redis `FLUSHALL`은 `bootstrap`에서만 실행한다. 하지만 CI는 `bootstrap`을 호출하지 않는다. 로컬에서도 프로파일만 바꿔 `docker compose up -d`를 실행하면 이전 프로파일의 캐시가 그대로 남을 수 있다.

**영향**

large 데이터셋을 실행하면서 small 데이터셋에서 만든 캐시를 사용할 수 있다. 캐시 적중률, 메모리 사용량, eviction 결과가 현재 데이터셋이 아닌 이전 실행 상태의 영향을 받는다.

**필요한 조치**

프로파일 전환 시 Redis를 자동 초기화하거나 프로파일별 Redis 볼륨을 사용해야 한다. 캐시를 유지하는 실험이라면 그 상태를 런 메타데이터에 기록해야 한다.

develop 병합 → main 반영 → EC2 배포
```

성능 테스트가 실패해도 이미 병합되거나 배포된 뒤일 수 있다.

**필요한 조치**

PR 단계에서 실행되는 성능 검사를 만들고 필수 체크로 연결해야 한다. 배포도 필요한 성능 게이트가 통과한 커밋만 진행하도록 연결해야 한다.

### E-25. [HIGH] 현재 CI 시딩 단계는 필수 초기화가 없어 실패함 — 상태: 미해결

### E-26. [HIGH] 공유 GitHub Actions 러너에서 전체 스택과 부하 발생기를 함께 실행함 — 상태: 미해결

**문제**

`ubuntu-latest`는 일반적으로 2~4 vCPU의 공유 가상 머신이다. 이 한 대에서 애플리케이션, MySQL, Redis, 관측 스택, k6를 모두 실행한다.

현재 `rules.json`의 노이즈 하한은 로컬 Windows 데스크톱 결과를 기준으로 조정됐다. CI 전용 노이즈 하한이나 정상 편차는 없다. 환경 이름은 분리돼 있지만 판정값은 CI 특성에 맞게 보정되지 않았다.

**영향**

공유 러너의 이웃 작업과 가상화 상태에 따라 결과가 크게 흔들릴 수 있다. 게이트 기준이 실제 CI 노이즈보다 좁으면 코드 변경과 관계없는 실패가 반복될 수 있다.

**필요한 조치**

재현 가능한 전용 러너를 사용하거나 CI에서 반복 실행해 정상 편차를 측정해야 한다. CI 전용 기준선과 판정 정책도 별도로 만들어야 한다.

### E-27. [HIGH] GitHub Actions 캐시에 저장한 기준선 이력이 쉽게 사라지거나 잘못 복원될 수 있음 — 상태: 미해결

**문제 1: 브랜치 범위가 다름**

Actions 캐시는 브랜치 범위에 제한된다. 주간 cron은 기본 브랜치에서 실행되므로 `develop`에서 만든 이력을 읽지 못할 수 있다. 이 경우 매주 기준선 없이 시작한다.

**문제 2: 캐시는 영구 저장소가 아님**

캐시는 다음 조건에서 사라질 수 있다.

- 7일 동안 사용하지 않으면 축출
- 저장소 전체 캐시가 10GB 한도를 넘으면 축출

**문제 3: 키 설계가 정확한 이력을 찾지 못함**

캐시 키에 `run_number`가 들어가므로 새 실행은 항상 정확한 키를 찾지 못한다. 대신 `restore-keys`의 접두사 일치로 복원한다.

이 접두사에는 브랜치, 시나리오, 데이터셋 조건이 충분히 들어 있지 않아 관련 없는 최신 캐시를 가져올 수 있다.

**영향**

기준선이 갑자기 사라져 첫 실행처럼 처리되거나, 다른 조건의 실행 이력을 기준선으로 사용할 수 있다.

**필요한 조치**

회귀 이력은 캐시가 아닌 영속 저장소에 보관해야 한다. 복원 키에도 환경, 브랜치, 시나리오, 데이터셋 같은 비교 조건을 포함해야 한다.

### E-28. [MEDIUM] CI 결과는 대시보드에 게시되지 않고 로컬 결과만 저장소에 커밋됨 — 상태: 미해결

**영향**

저장소 크기는 로컬 리포트 때문에 계속 늘어나지만, 자동으로 생성된 CI 결과는 한곳에서 추적할 수 없다.

### E-29. [MEDIUM] 공개 Pages에 내부 실행 정보가 그대로 포함됨 — 상태: **해결** (2026-08-14)
> `performance/tools/sanitize-reports.js`를 만들고 Pages 워크플로에 **정화 + 게시 직전 재검증**

> 실행 메모를 게시본에서만 제거한다. 저장소 원본(`performance/reports/`)은 그대로 두어
> 로컬 분석에는 영향이 없다.
>

> `deploy` job은 **2026-08-04에 실제로 성공한 이력이 있다**(`gh run view 30913250257`).
> "설정 안 했으니 괜찮다"가 아니라 이미 한 번 나갔던 경로다. 현재는 Pages API가 404라
> 비활성 상태이고, 2026-08-09 실행은 deploy 단계에서 실패했다.
>
> 커밋된 `run.json` 100건을 전수 조사한 결과: 자격 증명은 없었고, 실행자 4종

>

>
> 1. **파싱하지 않고 문자열로 지운다.** `run.json`에서 지울 값 목록을 모은 뒤 사이트의 모든
>    텍스트 파일에서 통째로 치환한다. 같은 값이 `run.json`·`report.html`·`summary.txt`에
>    중복돼 있어서, 각각 따로 파싱하면 하나를 빠뜨렸을 때 조용히 샌다. **버린 대안은

> 함께 피했다. 실패 로그에는 종류와 개수만 찍고 값은 찍지 않는다 — CI 로그도 게시본과 같은
> 수준으로 공개될 수 있다.

>
> **남은 위험.** 저장소에 커밋되는 원본에는 내부 정보가 그대로 남는다. 이건 의도된 것이며
> (로컬 분석에 필요하다) 저장소가 비공개라는 전제에 기댄다. 저장소를 공개로 전환한다면
> 이 전제가 깨지므로 별도 판단이 필요하다.

**문제**

Pages에 게시되는 리포트에는 다음 정보가 포함될 수 있다.

- executor 호스트명: `사용자명@호스트명`
- 내부 브랜치 이름
- dirty 상태가 붙은 커밋 SHA
- 사용자가 입력한 자유 텍스트 노트
- 내부 호스트명과 포트

현재 공개 전 마스킹이나 허용 목록 검사가 없다.

**영향**

성능 결과와 함께 내부 개발 환경 정보가 공개된다. 자유 텍스트 노트에 민감한 내용이 들어가도 그대로 게시될 수 있다.

**필요한 조치**

공개 리포트에 포함할 메타데이터를 허용 목록 방식으로 제한해야 한다. 호스트명, 내부 주소, 자유 텍스트는 제거하거나 마스킹해야 한다.

### E-30. [MEDIUM] CI 자격 증명 관리와 실패 진단 및 정리 절차가 없음 — 상태: 미해결

CI는 예제 파일에 들어 있는 MySQL root 비밀번호와 HS512 키를 사용한다. GitHub Actions의 `secrets.*`를 참조하는 부분은 없다.

`docker compose down -v`에 해당하는 정리 단계가 없다. 실패한 실행의 컨테이너나 데이터가 다음 단계에 남을 수 있다.

**영향**

실패 원인을 재현하고 분석하기 어렵다. 예제 자격 증명이 다른 환경으로 복사돼 재사용될 위험도 있다.

**필요한 조치**

실패 여부와 관계없이 로그를 아티팩트로 저장하고 teardown을 실행해야 한다. 테스트 전용 자격 증명임을 명확히 하고 운영 자격 증명과 혼용되지 않도록 해야 한다.

### E-31. [MEDIUM] CI에서 설치하는 k6 버전이 고정되지 않음 — 상태: 미해결

**필요한 조치**

### E-33. [HIGH] 실제 `.env.perf` 설정이 예제와 다르며 실행 기록에도 남지 않음 — 상태: 미해결

**문제**

현재 로컬 설정과 예제 설정의 데이터셋 프로파일이 다르다.

- `.env.perf.example`: `DATASET_PROFILE=medium`

`.env.perf`를 Git에서 제외한 설정 자체는 올바르다. 문제는 각 실행에서 실제로 사용한 로컬 설정을 충분히 기록하지 않는다는 점이다.

Docker Compose에 전달한 프로파일과 k6의 `-e DATASET` 값이 달라도 오류가 발생하지 않는다.

**영향**

기록된 실행이 실제로 어떤 데이터셋에서 수행됐는지 저장소만으로 재현하기 어렵다. MySQL은 large 데이터를 사용하지만 k6는 medium이라고 기록하는 모순도 가능하다.

**필요한 조치**

실행 시작 시 Compose 프로파일과 k6 데이터셋 값을 비교해 다르면 실패해야 한다. 실제 적용된 환경 설정의 비민감 항목도 런 메타데이터에 저장해야 한다.

### E-34. [MEDIUM] 실행 가능한 HS512 서명 키가 예제와 기본값에 커밋돼 있음 — 상태: **부분 해결** (2026-08-14) — 운영 키 대조 미완
> **저장소 쪽은 막았다.** `docker-compose.perf.yml`의 `JWT_KEY: ${JWT_KEY:-<실제 키>}`를
> `${JWT_KEY:?...}`로 바꿔 **값이 없으면 컨테이너가 뜨지 않게** 했다. `.env.perf.example`의
> `JWT_KEY=`는 빈 값으로 비웠다. `docker compose config`로 확인: 키 없이 실행하면
> `required variable JWT_KEY is missing a value: JWT_KEY 를 지정해야 한다 - openssl rand -base64 64 ...`로
> 거부된다.
>
> **버린 대안 — 기본값을 무해한 더미 키로 교체.** HS512는 64바이트 미만이면 로그인이 500으로
> 실패하므로(이 파일 다른 항목의 실측), "무해하면서 동작하는" 더미가 존재하지 않는다. 결국
> 실행 가능한 키를 다시 넣게 되고 같은 문제가 재발한다. `:?`로 **없으면 실패**시키는 편이
> 조용히 약한 키로 뜨는 것보다 낫다.
>
> **실측한 노출 범위(값은 출력하지 않고 지문으로만 확인).**
> - 저장소는 **비공개**다(`gh repo view` → `isPrivate: true`). 공개 노출은 아니다.
> - 문제의 키 지문 `sha256:56ac0fdcaa7296d0`(길이 88)가 **세 곳에 동일**하게 있었다:
>   `docker-compose.perf.yml` 기본값(커밋됨), `.env.perf.example`(커밋됨),
>   `.env.perf`(로컬, gitignore).
> - 이 키는 `origin/develop`에 **푸시돼 있다**(`origin/main`에는 없음). 즉 저장소 읽기
>   권한이 있는 사람은 전부 볼 수 있다.
> - `src/test/resources/application-test.properties`의 키는 지문이 다르고
>   (`sha256:8d15371191de5a50`) 이름 그대로 테스트 전용이라 별개다.
>
> **남은 작업 — 운영 키가 같은지 확인.** GitHub Secret은 읽을 수 없으므로 저장소만 보고
> 증명할 수 없다. `deploy.yml:112`가 EC2의 `.env`에 `JWT_KEY=%s`를 쓰므로, **EC2에서 지문만
> 비교**한다(값 출력 없음).
>
> ```bash
> grep '^JWT_KEY=' .env | cut -d= -f2- | tr -d '\r\n' | sha256sum | cut -c1-16
> # 결과가 56ac0fdcaa7296d0 이면 운영 키가 저장소에 노출된 것이다 → 즉시 교체 + 토큰 무효화
> ```
>
> 히스토리에 남은 키를 지우는 것(force-push 또는 history rewrite)은 하지 않았다. 공유
> 브랜치라 팀원 작업을 깨뜨리고, 비공개 저장소라 위험 대비 비용이 크다. **키 교체가
> 히스토리 삭제보다 확실한 대응**이다 — 지워도 이미 클론한 사본에는 남는다.

### E-34(구). 실행 가능한 HS512 서명 키가 예제와 기본값에 커밋돼 있음 — 원문 기록

**문제**

`.env.perf.example:14`에는 실제 JWT 서명에 사용할 수 있는 512비트 HS512 키가 들어 있다. 같은 값이 Docker Compose 기본값에도 중복돼 있다.

파일 헤더는 “실제 값을 커밋하지 말라”고 설명하지만, 형식만 맞춘 가짜 표시가 아니라 실제로 토큰을 서명할 수 있는 값을 커밋한 상태다.

운영도 같은 환경 변수 이름을 사용한다. 예제 설정을 운영 설정으로 복사하면 이 공개 키를 그대로 사용할 수 있다.

**영향**

운영에서 같은 키를 재사용하면 누구나 유효한 JWT를 위조할 수 있다. 현재 문서에는 이 키를 운영에서 사용하면 안 된다는 명확한 경고도 없다.

**필요한 조치**

예제 값은 운영에서 사용할 수 없는 명백한 플레이스홀더로 바꾸고 시작 시 실제 키 입력을 요구해야 한다. 성능 테스트 전용 키라는 경고와 운영 재사용 금지 안내도 추가해야 한다.

### E-35. [MEDIUM] 재현성의 기준이 되는 환경 명세가 비어 있음 — 상태: 미해결

**문제**

문서는 “모든 실험은 이 문서에 기록한 환경에서만 유효하다”고 선언한다. 하지만 다음 핵심 정보가 플레이스홀더로 남아 있다.

- CPU 모델 및 코어 수
- RAM
- 디스크 종류와 성능
- Docker 및 Docker Compose 버전
- 운영체제와 가상화 환경

BTL-002의 핵심 조건인 HikariCP 설정도 “확인 후 기입” 상태다. seed 오버라이드에는 실제 값이 존재하지만 정본 환경 명세에는 반영되지 않았다.

**영향**

같은 코드를 실행해도 장비와 설정이 달라지면 결과를 재현할 수 없다. 현재 문서가 정한 기준으로는 재현 가능한 실험이 하나도 없다.

**필요한 조치**

실행 도구가 환경 정보를 자동 수집해 런 기록에 저장하도록 해야 한다. 문서의 기준 환경 표도 실제 값으로 채워야 한다.

### E-36. [MEDIUM] Windows와 Docker Desktop 전용 우회 설정이 공통 환경 명세에 섞여 있음 — 상태: 미해결

**문제**

현재 정본 환경에는 Windows와 Docker Desktop에서만 필요한 설정이 포함돼 있다.

- 바인드 마운트 권한 문제를 피하기 위해 MySQL 튜닝을 CLI 옵션으로 전달
- cAdvisor가 동작하지 않지만 문서에 적힌 대안 네 가지는 적용하지 않음
- 컨테이너 이름을 `perf-mysql`과 `perf-redis`로 고정
- 애플리케이션 주소를 `localhost:18080`으로 고정

Linux에서는 이 우회가 필요하지 않거나 다른 지표 집합을 수집할 수 있다.

**영향**

Windows 실행과 Linux 실행이 서로 다른 지표를 수집하는데도 회귀 엔진은 시나리오와 환경 이름만 보고 비교할 수 있다. 같은 “perf” 환경으로 기록됐지만 실제 측정 조건은 다를 수 있다.

**필요한 조치**

공통 환경 설정과 운영체제별 오버레이를 분리해야 한다. CLI 도구로 추출할 때 일반화해야 할 하드코딩 목록으로도 관리해야 한다.

### E-37. [LOW] Docker 리소스 한계가 실제로 적용됐는지 확인하지 않음 — 상태: 미해결

**문제**

CPU와 메모리 한계는 `deploy.resources.limits`에 정의돼 있다. 이 설정의 적용 여부는 Docker Compose 버전과 실행 방식에 영향을 받을 수 있다.

하지만 다음 정보와 확인 절차가 없다.

- 지원하는 최소 Docker Compose 버전
- 실제 적용 여부를 확인하는 `docker inspect` 검사

**영향**

리소스 한계가 무시되면 컨테이너는 제한 없이 실행된다. 그런데 `saturation.cpuPct`는 한계가 적용됐다고 가정하고 CPU 포화도를 계산하므로 결과가 잘못될 수 있다.

**필요한 조치**

지원 버전을 명시하고 실행 전에 컨테이너의 실제 CPU 및 메모리 한계를 확인해야 한다.

### E-38. [LOW] Grafana 데이터소스 UID가 고정되지 않음 — 상태: 미해결

**문제**

Grafana 데이터소스는 이름만 지정하고 `uid`는 지정하지 않는다.

`docker compose down -v`로 Grafana 데이터를 초기화하면 새 UID가 생성될 수 있다. 대시보드 JSON이 이전에 생성된 UID를 참조하면 데이터소스를 찾지 못한다.

**영향**

환경을 깨끗하게 다시 만들었을 때 대시보드가 데이터 없음 상태로 열릴 수 있다.

**필요한 조치**

프로비저닝 파일에서 데이터소스 UID를 고정하고 대시보드도 같은 UID를 참조하도록 해야 한다.

## MySQL 익스포터 추가 조사

### E-39. [HIGH] mysqld-exporter가 기본 지표만 수집해 느린 쿼리를 특정할 수 없음 — 상태: 미해결

추가 조사일: 2026-08-06

**문제**

`performance/environment/docker-compose.perf.yml:160`의 mysqld-exporter에는 다음 연결 정보만 전달한다.

- `--mysqld.address`
- `--mysqld.username`

추가 collector 옵션이 없어 `global_status`와 `global_variables` 같은 기본 지표만 수집한다.

2026-08-06에 실제 Prometheus 시계열을 확인한 결과는 다음과 같다.

```text
mysql_perf_schema_*                 → 0개 시계열
mysql_info_schema_innodb_metrics_*  → 0개 시계열
```

**MySQL 자체 준비 상태**

같은 Docker Compose 파일의 MySQL에는 다음 기능이 이미 켜져 있다.

- `--performance-schema=ON`
- `--slow-query-log=1`
- `--log-queries-not-using-indexes=1`

즉 MySQL은 분석용 데이터를 만들고 있다. 성능 스키마와 느린 쿼리 로그의 오버헤드는 이미 부담하지만, 익스포터가 해당 데이터를 가져오지 않아 관측에는 사용하지 못한다.

**진단 과정에서 끊기는 지점**

현재 가능한 진단 흐름은 다음과 같다.

```text
“시스템이 느리다” 확인  →  “어느 쿼리인가” 확인  →  EXPLAIN으로 원인 분석
         가능                        불가능                    수동으로 가능
```

`performance/tools/lib/regression.js`의 `bottleneckHints()`는 QPS와 RPS 비율을 이용해 “요청당 쿼리가 많으므로 N+1일 수 있다”는 수준까지 알려준다.

하지만 어느 쿼리가 몇 번 실행됐는지는 알 수 없다. 댓글 N+1을 다루는 EXP-005는 이 질문에 답해야 하므로 현재 수집 정보만으로는 진행이 막힌다.

**mysqld-exporter v0.15.1에서 사용할 수 있는 옵션**

다음 옵션은 `--help` 출력으로 확인했다.

```yaml
- --collect.perf_schema.eventsstatements
- --collect.perf_schema.eventsstatements.limit=50
- --collect.info_schema.innodb_metrics
- --collect.engine_innodb_status
- --collect.perf_schema.tablelocks
- --collect.perf_schema.indexiowaits
```

각 옵션의 목적은 다음과 같다.

| 옵션 | 목적 |
|---|---|
| `eventsstatements` | 쿼리 digest별 실행 횟수와 시간 통계. 쿼리 특정에 가장 중요 |
| `eventsstatements.limit=50` | 수집할 쿼리 digest를 상위 50개로 제한 |
| `innodb_metrics` | InnoDB 내부 카운터 수집 |
| `engine_innodb_status` | `SHOW ENGINE INNODB STATUS`를 통해 데드락 정보 수집 |
| `tablelocks` | 테이블 락 통계 수집 |
| `indexiowaits` | 인덱스별 I/O 대기 통계 수집 |

**모든 옵션을 기본으로 켜면 안 되는 이유**

1. **시계열 수가 크게 늘어날 수 있다.**

   쿼리 digest 50개마다 여러 지표가 생성되므로 Prometheus 시계열 수가 급증한다.

   현재 `metrics-catalog.js`는 “지표 하나를 숫자 하나로 저장한다”는 구조다. `collect.js:81`도 다음과 같이 단일 값을 저장한다.

   ```javascript
   flat[spec.key] = value
   ```

   상위 N개 쿼리처럼 여러 행이 나오는 결과를 어떻게 저장하고 표시할지는 별도 설계가 필요하다.

2. **관측 자체가 측정 대상을 느리게 만들 수 있다.**

   `eventsstatements` 수집은 무료가 아니다. 모든 실행에서 항상 활성화하면 성능을 분석하기 위한 관측 기능이 오히려 성능 결과를 바꿀 수 있다.

**권장 방식**

이 collector들은 기본 성능 환경에 항상 켜지 말고, 원인 분석이 필요할 때만 사용하는 별도 Docker Compose 오버레이로 분리하는 것이 적절하다.

예시 파일명:

```text
performance/environment/docker-compose.deep.yml
```

`performance/tools/README.md`도 심층 분석 도구는 병목 범위를 좁힌 뒤 짧게 사용해야 한다고 설명한다. 프로파일러 오버헤드가 측정을 오염시킬 수 있기 때문이다.

**적용 순서**

1. 도구 문서의 T-29에서 다루는 기존 무료 MySQL 지표를 먼저 카탈로그에 등록
2. 실제 실험을 시작
3. 쿼리 특정이 정말 필요한 단계에서 E-39의 심층 collector 활성화

필요가 확인된 뒤에 켜야 관측 오버헤드와 얻는 정보의 가치를 정확히 비교할 수 있다.

### E-40. [참고] EXPLAIN은 자동 수집 지표가 아니라 원인 분석 결과물임 — 상태: 해당 없음

**판단**

## 데이터셋 생성기 추가 조사 — 2026-08-13

### E-41. [HIGH] 고정 난수 seed가 비동기 시딩에서 동일한 데이터를 보장하지 못함 — 상태: 미해결

**문제**

`performance/datasets/seed.js:74-79`는 전역 변수 하나를 사용하는 LCG `rand()`를 두고
“같은 프로파일이면 항상 같은 데이터”라고 설명한다. 난수 수열 자체는 고정돼 있지만, 그 수열의
각 값을 어느 작업이 가져가는지는 고정돼 있지 않다.

`pooled()`는 여러 lane을 `Promise.all()`로 동시에 실행한다(`seed.js:200-237`). 각 lane은 HTTP
응답을 받은 순서대로 다음 작업을 가져간다. 게시글 작성자·게시판·본문·익명 여부, 반응 종류처럼
worker 안에서 `rand()`를 호출하는 값은 **어느 HTTP 요청이 먼저 끝났는가**에 따라 다른 작업에
배정된다. 재시도 지터도 같은 전역 `rand()`를 소비하므로 데드락·커넥션 대기 횟수가 달라지면
그 이후의 전체 난수 배정이 밀린다(`seed.js:227`).

```text
고정된 난수 수열
  + 실행마다 달라질 수 있는 HTTP 완료 순서
  + 실패할 때만 소비하는 재시도 지터
  = 같은 프로파일이어도 다른 사용자·게시물 관계
```

**기존 문서와 충돌하는 부분**

`seed.js`의 데이터셋 지문 주석과 `perf-findings-tools.md`의 T-02 후속 기록은 생성 시각을 지문에서
제외한 이유로 “고정 LCG이므로 같은 규칙·프로파일이면 통계적으로 같은 데이터가 나온다”는 전제를
사용한다. 분포의 큰 모양은 비슷할 수 있지만, 핫 게시물의 작성자·익명 여부·반응 종류와 친구
그래프가 같다는 보장은 없다. 락 경합과 캐시 핫키는 이런 개별 관계에도 영향을 받는다.

**영향**

- 같은 지문을 가진 두 데이터셋이 실제 행 연결과 핫키 구성이 다를 수 있다.
- 시딩 동시성이나 서버 상태 차이가 애플리케이션 성능 변화처럼 결과에 섞일 수 있다.
- “고정 seed이므로 재시딩으로 스냅샷을 복원할 수 있다”는 운영 절차를 신뢰할 수 없다.

**필요한 조치**

네트워크 요청을 시작하기 전에 모든 생성 작업과 난수 기반 속성을 단일 스레드에서 계획 파일로
확정해야 한다. worker는 이미 정해진 작업을 전송만 해야 하며 재시도 지터는 데이터 생성용 PRNG와
별도 난수원을 사용해야 한다. 같은 계획 파일로 깨끗한 DB 두 개를 만든 뒤 핵심 관계와 분포가
같은지 자동 비교해야 한다.

### E-42. [HIGH] 같은 사용자 세션의 동시 토큰 갱신이 refresh rotation과 경쟁함 — 상태: 미해결

**문제**

large 시딩은 액세스 토큰 수명 30분보다 오래 걸릴 수 있다. 이를 처리하기 위해 `Session.json()`은
401을 받으면 `/api/token/refresh`를 호출하고 원 요청을 한 번 다시 보낸다
(`performance/datasets/seed.js:127-147`).

문제는 댓글·반응·스크랩 작업이 같은 사용자를 여러 lane에서 동시에 고를 수 있다는 점이다.
각 사용자는 `Session` 객체 하나와 쿠키 `Map` 하나만 갖고 있고, 사용자별 직렬화나 refresh
single-flight가 없다. 같은 사용자의 요청 둘이 동시에 401을 받으면 같은 refresh token으로 두
번 갱신을 시도할 수 있다.

서버는 refresh token을 회전한다.

- `TokenProvider.reissueTokens()`가 새 access·refresh token을 발급
- `TokenService.saveOrUpdate()`가 기존 refresh token 캐시 키를 삭제하고 DB 값을 새 토큰으로 변경

두 갱신이 경쟁하면 한 요청은 이미 폐기된 토큰을 사용해 실패할 수 있다. 둘 다 진행되더라도
공유 쿠키 `Map`에는 응답이 도착한 순서대로 값이 덮여, DB에 마지막으로 남은 refresh token과
클라이언트 쿠키가 다를 수 있다.

**영향**

- 30분을 넘는 large 시딩의 후반 단계에서 401과 부분 데이터가 몰릴 수 있다.
- 같은 코드·프로파일이라도 네트워크 타이밍에 따라 성공 수량이 달라진다.
- 인증 실패가 데이터 생성 실패, 재시도, 난수 소비 변화로 연쇄 전파된다.

**필요한 조치**

사용자별 refresh를 single-flight로 묶어 한 갱신 결과를 같은 세션의 대기 요청들이 공유하게 해야
한다. 또는 동일 사용자의 요청을 한 lane에서 직렬화해야 한다. 테스트에서는 액세스 토큰 수명을
짧게 만든 전용 설정으로 같은 Session의 동시 401을 재현하고, refresh 한 번만 발생하며 이후
요청이 모두 새 쿠키를 사용하는지 확인해야 한다.

### E-43. [HIGH] 실패한 친구 쌍과 다른 사람의 요청이 채팅 데이터로 이어질 수 있음 — 상태: 미해결

**문제 1 — 정확한 친구 요청을 못 찾으면 마지막 요청을 대신 수락함**

`createFriendships()`는 받은 신청 목록에서 신청자의 `userId`가 같은 항목을 찾는다. 찾지 못하면
다음 코드로 목록의 마지막 요청을 대신 선택한다(`performance/datasets/seed.js:527`).

```javascript
const req = r2.data.find((q) => q.userId === sa.userId) || r2.data[r2.data.length - 1];
```

동시에 여러 친구 신청이 들어온 상태에서는 방금 보낸 신청이 아닌 다른 사용자의 신청을 수락할
수 있다. 오류로 중단해야 할 상태를 임의의 정상 관계로 바꾸는 fallback이다.

**문제 2 — 실제 성공 여부와 무관하게 시도한 쌍 전체를 채팅에 넘김**

`pooled()`는 성공한 item 목록을 반환하지 않는다. `createFriendships()`도 작업 후에 원래 만든
`pairs` 전체를 반환하고(`seed.js:511-535`), `createChat()`은 그 배열을 그대로 잘라 채팅방을
만든다(`seed.js:537-554`). 친구 신청·수락이 실패하거나 세션이 없어 skip된 쌍도 채팅방 생성
후보가 된다.

**영향**

- 친구 그래프의 학교 클러스터 비율과 목표 쌍 수가 실제와 달라진다.
- 친구가 아닌 사용자로 채팅방 생성을 시도해 후반 단계 실패가 늘어난다.
- 친구·채팅 저니의 데이터 부족을 애플리케이션 성능 문제로 오해할 수 있다.

**필요한 조치**

정확한 신청자를 찾지 못하면 즉시 실패해야 하며 임의 fallback을 사용하면 안 된다. `pooled()`가
성공 item을 반환하게 하고, 채팅방은 친구 관계가 실제로 수락된 쌍만 사용해야 한다. 시딩 후에는
채팅 참여자 두 명이 활성 친구 관계인지 SQL 또는 API로 전수 검증해야 한다.

### E-44. [HIGH] 데이터셋 지문이 부분 실패와 실행 중 DB 변화를 식별하지 못함 — 상태: **해결** (2026-08-16)

> 이 항목은 **두 가지 다른 결함**을 하나로 묶고 있었고, 각각 다른 시점에 다른 방식으로
> 해결됐다.
>
> **① 부분 실패를 식별하지 못하는 문제 (2026-08-14).** 생성 지문에 `stageCounts`(단계별
> 실제 생성 수)가 들어갔다. 이전에는 users·posts·boards 세 수량만 해싱해서 "댓글이 5%
> 모자란 데이터셋"과 온전한 것의 지문이 같았다. 지금은 댓글·반응·스크랩·친구·채팅방까지
> 전부 지문에 반영된다. 자세한 내용은 `ROADMAP.md`의 P0-1.
>
> **② 실행 중 DB 변화를 반영하지 못하는 문제 (2026-08-16).** 이건 생성 지문을 아무리
> 정교하게 만들어도 해결되지 않는다 — 생성 지문은 **생성 시점에 고정되는 값**이기 때문이다.
> 그래서 별도 축을 만들었다. `tools/lib/dbstate.js`가 실행 직전에 DB를 직접 세어 상태
> 지문을 계산하고, `conditions.js`(v3)가 그것을 blocking 조건으로 쓴다. 이 항목이 요구한
> `datasetInstanceId`는 **스냅샷 ID + 상태 지문 두 값**으로 구현됐다 — 스냅샷 ID는 "어느
> 사본에서 출발했나", 상태 지문은 "실제로 그 상태였나"에 각각 답한다. ID만 두면 복원이
> 실패했는지 알 수 없다.
>
> **지문에서 뺀 값과 그 이유.** `tokens`(VU가 로그인할 때마다 회전), `posts.view_count`
> 합(Redis 버퍼를 스케줄러가 flush), hot post 테이블(스케줄러가 씀). 넣었다면 **읽기만
> 해도 매번 불일치가 나 복원이 무한히 반복된다.** 실측이 확인했다 — 읽기가 섞인 실행 뒤
> `posts.sumViewCount +47`, `daily_hot_post` 4,996→5,004이 관측됐고 core 지문은 그대로였다.
> 버리지 않고 `volatile`로 따로 기록해 "쓰기가 있었나"와 "조회수만 올랐나"를 구분한다.
>
> **행 수만으로는 부족하다는 것도 실측으로 드러났다.** `MAX(pk)`를 함께 넣은 덕에
> `posts.js`(생성→수정→삭제)가 남긴 변화를 잡았다 — `posts.count`는 100,000 그대로인데
> `posts.maxId`만 100,000→100,001이었다. 소프트 삭제라 행 수가 돌아왔기 때문이다.
>
> **검증**: `strict` 자동 복원 왕복 실측, 단위 테스트 20개, 전체 227개 통과.
> 설계 문서 `performance/DATASET-STATE.md`.

#### (아래는 해결 전 상태의 기록이다)

**문제**

현재 데이터셋 지문은 `seed.js`, 공용 샘플러, 프로파일 파라미터와 다음 세 수량만 해시한다
(`performance/datasets/seed.js:580-602`).

```text
users.length   = 가입 성공 수가 아니라 계획한 사용자 수
posts.length   = ID를 받은 게시글 수
boards.length  = 조회된 게시판 수
```

실제 댓글·반응·스크랩·친구·채팅방·메시지·알림 수는 지문에 들어가지 않는다. E-19처럼 해당
단계가 일부 실패해도 사용자·게시글·게시판 수가 같으면 같은 지문이 만들어진다.

지문은 생성 시점의 recipe만 나타내며 그 뒤의 DB 상태도 반영하지 않는다. 쓰기 부하 테스트가
게시글·댓글·반응을 누적하거나 채팅 테스트가 메시지를 추가해도 `meta.json`은 바뀌지 않는다.
현재 large DB에도 시드가 만들지 않은 채팅 메시지가 후속 테스트로 누적돼 있지만 프로파일과
지문은 그대로다.

**영향**

- 내용이 다른 두 DB가 같은 `{profile, fingerprint}` 조건으로 기준선 비교를 통과할 수 있다.
- 데이터 미달이나 실행 간 드리프트를 막기 위해 도입한 blocking 조건이 거짓 안전 신호가 된다.
- 같은 지문을 근거로 이전 기준선을 선택해 실제 데이터 변화가 코드 회귀로 보일 수 있다.

**필요한 조치**

생성 manifest에 모든 단계의 목표·성공·실패·skip·재시도 수와 실제 DB 검증 수량을 넣어야 한다.
검증이 끝난 DB·Redis 스냅샷마다 별도 `datasetInstanceId`를 부여하고, 실행 기록에는 recipe 지문과
instance ID를 모두 저장해야 한다. 읽기 테스트는 실행 전후 핵심 수량이 달라지면 기준선 자격을
잃고, 쓰기 테스트는 같은 스냅샷을 복원한 뒤 시작해야 한다.

### E-45. [HIGH] 현재 large DB의 댓글 카운터가 실제 활성 댓글 수와 일치하지 않음 — 상태: 미해결

### E-46. [CRITICAL] 같은 조건인데 세션이 바뀌면 성능이 45% 달라짐 — 상태: **해결** (2026-08-21) — 원인은 환경이 아니라 포화 상태 측정이었다

> **해결 기록 (2026-08-21) — 원인 규명 + 무해화.**
>
> **무엇이었나.** "같은 조건인데 세션이 바뀌면 성능이 45% 달라진다"는 현상 자체는 실재했다.
> 그러나 **원인 해석이 틀렸다.** 환경이 45% 변한 것이 아니라, **용량의 1.5배를 밀어 넣은
> 포화 상태에서 측정**했기 때문에 작은 환경 변동이 크게 증폭됐다.
>
> 증폭 경로는 세 단계다.
> 1. `normal-day` 가 200 VU 로 돌았는데 이 환경의 용량은 도착률 약 4~5/s 다. 앱 CPU 가
>    `1.998/2.0` 으로 붙고 Hikari 10 개 앞에 145 개가 대기했다.
> 2. closed model 에서 VU 가 고정이면 리틀의 법칙에 따라 `R = N / X` 가 **기계적으로**
>    성립한다. 실측 상관 **0.962** 로, p95 는 애플리케이션 지연이 아니라 **처리량의 그림자**
>    였다.
> 3. 포화 근처에서는 이용률이 1 에 가까워질수록 대기가 `1/(1-ρ)` 로 발산한다. 보정 곡선에서
>    부하를 25%(4/s→5/s) 올리자 p95 가 **30배**(402ms→11,871ms)가 됐다.
>
> 그래서 세션마다 호스트 유효 용량이 10~20% 오르내리면 ρ 가 임계선 양쪽을 넘나들었고,
> "세션마다 레벨이 통째로 다르다"로 보였다. **환경 변동은 방아쇠였고 증폭기는 우리가 설정한
> 부하였다.**
>
> **무엇을 어떻게 고쳤나.**
> 1. **open model 전환**(S-27) — `-e RATE` 로 `ramping-arrival-rate` 를 쓴다. 도착률을 고정해
>    coordinated omission 을 끊고, 못 따라가면 **도달률 미달로 드러나게** 했다.
> 2. **운용점을 절벽 아래로** — 보정 곡선(3/4/5 세 점)으로 용량을 확인하고 **RATE=4** 를
>    판정용 운용점으로 정했다. 앱 CPU 37~45%, Hikari 대기 0, acquire 1ms.
> 3. **포화 자동 감지**(`tools/lib/saturation.js`) — 커넥션 대기·throttled·CPU 사용률·
>    acquire 비중·도달률 다섯 신호로 판정하고, 포화면 **판정보다 먼저** 경고를 띄운다.
>    영역이 다른 기준선과의 비교도 막는다.
> 4. **계측 결함 제거**(T-37) — 호스트 프로브를 구간별로 나누고 원시 표본을 보존했다.
>
> **고민한 대안과 버린 이유.**
> - *환경을 고정한다(전원 설정·PMU·cpuset)* → **실측으로 버렸다.** `PROCTHROTTLEMIN` 을
>   5%→100% 로 올린 뒤 3회를 재니 p95 가 오히려 **+47%** 나빠졌고 `% Processor Performance`
>   는 내려갔다(E-49). 노트북의 이기종 CPU·Hyper-V 위에서 유효 처리 능력을 고정하는 것은
>   장비 교체 없이는 어렵다.
> - *드리프트 원인을 끝까지 규명한다* → 버렸다. 닷새를 썼고 후보 12개를 기각했지만, **규명
>   자체가 목적이 아니었다.** 필요한 것은 "개선 전후를 비교할 수 있는 측정"이고, 증폭기를
>   제거하면 원인이 미규명이어도 그게 가능해진다.
> - *`normal-day` 를 통째로 open model 로 바꾼다* → 버렸다. `seriesHash` 가 갈려 저장된
>   저장된 실행과의 비교가 즉시 끊긴다. 명시적 옵트인으로 두고 판정용 측정에만 쓴다.
> - *Before/After 를 반드시 연달아 잰다* → **완화했다.** 아래 검증에서 4시간 간격 차이가
>   1.5% 로 측정됐으므로, 텀이 있어도 그 폭을 오차 막대로 쓰면 된다.
>
> **어떻게 검증했나.** 코드를 전혀 바꾸지 않고 4시간 간격으로 두 세트를 쟀다(2026-08-20).
>
> | 세트 | 시각 | 유효 n | comment p95 | 세트 안 CV |
> |---|---|---:|---:|---:|
> | Before-A | 16:06~16:32 | 2 | 2,201ms | 16.8% |
> | Before-B | 20:32~21:10 | 4 | **2,169ms** | **3.2%** |
>
> **세트 간 −1.5%.** 포화 시절 하루 안에 28~48% 왕복하던 것과 대비된다. 세트 안 CV 도
> 7.07% → 3.2% 로 내려갔다.
>
> 결정적으로, **이 4시간 동안 환경은 실제로 18% 느려졌다** — 유휴 CPU 벤치 single 이
> 4,962~5,062ms 에서 5,795~5,970ms 로 올랐다. 그런데 앱 성능은 1.5% 변했다.
> **환경 18% 변동 → 앱 1.5% 변동**, 즉 같은 변동이 12분의 1 로 줄었다.
>
> **남은 부작용 / 후속 작업.**
> 1. **환경 변동이 사라진 것이 아니다.** 증폭기만 제거했다. **포화 영역으로 들어가면 즉시
>    재발한다** — Before-A 의 `#115` 가 실증했다(도착률 4.00/s 를 지켰는데도 앱 CPU 39%→81%,
>    p95 358ms→5,634ms). 그래서 포화 감지는 상시 장치로 남아야 한다.
> 2. **포화 영역 실행 49건은 아카이브로 분리했다**(2026-08-21). 저장된 119건에 포화 판정을
>    돌려 `SATURATED` 인 것만 `reports/archive/runs/` 로 옮겨 기준선 후보에서 뺐다
>    (`reports/archive/README.md`). 이 값들은 애플리케이션 지연으로 인용할 수 없고 새
>    운용점의 기준선으로도 못 쓴다.
> 3. **고정 도착률에서 남는 3.2% 변동은 미규명**이다. 다만 판정을 막지 않는다.
> 4. **다른 시나리오는 확인하지 않았다.** `read-heavy`·`write-heavy` 등도 같은 방식으로
>    만들어졌으니 포화일 가능성이 높다.
> 5. 이 항목이 CRITICAL 이었던 이유("저장된 기준선을 Before 로 쓸 수 없다")는 해소됐지만,
>    **2번 때문에 과거 기준선은 여전히 쓸 수 없다.** 새 운용점에서 기준선을 새로 쌓아야 한다.
>

## 캐시 상태 축 추가 조사 — 2026-08-18

### E-47. [MEDIUM] 캐시 상태를 재고 기록하지만 판정에는 쓰지 않고, warm/cold 라벨 근거도 캐시가 아닌 키를 센다 — 상태: 미해결

> **쉽게 말하면.** 코드가 두 군데에서 "웜에서 잰 값과 콜드에서 잰 값은 같은 실험이 아니다"
> 라고 적어 놓고, 정작 기준선을 고를 때는 그 값을 보지 않는다. 게다가 warm/cold를 가르는
> 기준이 캐시가 아닌 Redis 키까지 세고 있어서, 앱이 한 번이라도 돌면 라벨이 영구히 warm으로
> 굳는다.

#### 문제 1: `cacheState`가 비교 조건이 아니다

`perf-run.js`의 `preflight()`는 실행 직전 Redis 상태를 재서 `cacheState`(`warm`/`cold`/
`unknown`)와 `cacheKeysBefore`를 레코드에 싣는다. `repository.js`의 `toIndexEntry()`도
이 값을 인덱스에 평탄화하며 이유를 이렇게 적어 두었다.

> warm 에서 잰 값과 cold 에서 잰 값은 같은 실험이 아니다. 이력 표에서 그 사실을
> 구분하려면 인덱스에 있어야 한다.

그런데 `conditions.js`의 `CONDITIONS` 목록에는 `cacheState`가 없다. 현재 조건은 7개뿐이다.

```text
scenario · environment · dataset · loadProfile · loadgen · scriptVersion · measurementProfile
```

`findBaseline()`은 이 목록만 보고 후보를 거른다. 따라서 **콜드로 시작한 실행과 웜으로
시작한 실행이 서로의 기준선이 될 수 있다.** 코드가 스스로 "같은 실험이 아니다"라고 선언한
축이 판정 경로에는 연결되지 않은 상태다.

#### 문제 2: warm/cold 판정이 캐시가 아닌 키를 센다

`dbstate.js`의 `computeCacheState()`는 `RT:` 접두사가 아닌 모든 Redis 키를 캐시 키로 센다.
`RT:`(세션 리프레시 토큰)를 뺀 이유는 주석에 명시돼 있다.

> VU 가 로그인만 해도 쌓이는데 그걸 warm 이라고 부르면 **모든 실행이 warm 으로 기록되어
> 이 값이 무의미해진다.**

그런데 앱이 쓰는 키 중 캐시가 아닌 것이 `RT:`만이 아니다.

| 키 | 성격 | TTL | 부하와 무관하게 생기나 |
|---|---|---|---|
| `board:{id}:posts`, `posts:{id}`, `board:{id}:count` | 진짜 읽기 캐시 | 5~60분 | 아니오 |
| `viewed:{postId}:{userId}` | 조회수 중복 방지 마커 | 1시간 | 조회가 있으면 대량 생성 |
| `post:views:{postId}` | 조회수 버퍼 | 없음 | 스케줄러가 드레인할 때까지 잔존 |
| `hot:leaderboard:day:{yyyyMMdd}` | 인기글 ZSET | **없음**(KI-20) | **예 — 스케줄러가 5분마다 쓴다** |

특히 `hot:leaderboard:day:*`는 `HotScoreScheduler`가 부하와 무관하게 5분마다 쓰고 TTL이
없어 `FLUSHALL` 전까지 사라지지 않는다. 즉 앱이 한 번이라도 떠 있었으면 이 키가 남아
`cacheKeys > 0`이 되고, 실제 읽기 캐시(`board:*`, `posts:*`)가 전부 만료됐어도 라벨은
`warm`이 된다. `RT:`를 제외해서 막으려던 실패 모드가 다른 접두사로 그대로 재현된다.

#### 왜 지금은 티가 안 나는가

기록된 20개 실행이 **전부 `cold`**다. 두 경로가 매번 Redis를 비우기 때문이다.

- `repeatability.js`가 회차 사이마다 `redis-cli FLUSHALL`을 실행한다
- `guard=strict`의 스냅샷 복원도 `FLUSHALL`을 포함한다

그래서 현재 절차를 그대로 따르는 한 문제 1도 문제 2도 발동하지 않는다. **잠재 결함이다.**
`perf-run.js`를 단독으로 연속 실행하거나 `guard=off`로 돌리는 순간 둘이 동시에 터진다 —
라벨은 무조건 `warm`이 되고(문제 2), 그 warm 실행이 cold 실행의 기준선으로 선택된다(문제 1).

#### 근거

- `tools/lib/conditions.js` — `CONDITIONS` 배열에 `cacheState` 없음
- `tools/lib/repository.js` — `toIndexEntry()`가 `cacheState`를 인덱스에 담으며 "같은
  실험이 아니다"라고 서술
- `tools/lib/dbstate.js` — `computeCacheState()`의 `if (!k.startsWith('RT:')) cache++`
- `infrastructure/redis/RedisHotPostRanking.java`, `services/domain/HotPostService.java` —
  `hot:leaderboard:day:` 접두사, TTL 미설정
- `reports/index.json` — `cacheState`가 기록된 20건 전부 `cold`

#### 필요한 조치

두 가지를 따로 정해야 한다.

1. **캐시 키 판정을 화이트리스트로 바꾼다.** `board:`·`posts:` 접두사만 캐시로 세고
   `viewed:`·`post:views:`·`hot:`은 `RT:`와 함께 제외한다. 접두사 목록은 앱의
   `RedisPostsCache`·`RedisViewCountStore`·`RedisHotPostRanking`이 실제로 쓰는 값과
   맞춰야 하므로, 한쪽이 바뀌면 다른 쪽도 바뀌는 결합이 생긴다는 점은 감수한다.
2. **`cacheState`를 조건으로 승격할지 결정한다.** blocking으로 넣으면 값이 없는 과거
   실행 38건이 통째로 비교 불가가 된다(`SCHEMA_VERSION`도 올려야 한다). degrading이면
   경고만 뜨고 비교는 유지된다. 현재 절차상 항상 cold라 실익이 크지 않으므로, `guard=off`
   실행을 허용할 계획이 생길 때 함께 정하는 편이 낫다.

> 관련: E-08(warmup 이름과 실제 동작), E-22(데이터셋 전환 시 Redis 잔존), KI-20(핫랭킹
> ZSET TTL 없음), T-02(비교 가능성 조건)

### E-48. [HIGH] 이 환경에서는 하드웨어 성능 카운터를 쓸 수 없다 — 상태: **확정** (2026-08-19)

> **쉽게 말하면.** "CPU 1초에 명령어를 몇 개 실행했는가"를 재는 경로가 WSL2 게스트 안에
> 하나도 없다. E-46(세션 간 편차)의 남은 질문이 정확히 그 값을 요구하는데, 이 환경에서는
> 원리적으로 답할 수 없다는 것이 실측으로 확정됐다.

#### 확인 방법과 결과

`docker run --rm --privileged alpine` 으로 게스트 안의 이벤트 소스를 직접 열거했다.

```
/sys/bus/event_source/devices/
  breakpoint  kprobe  msr  power  software  tracepoint  uprobe
```

| 경로 | 상태 | 잴 수 있었을 값 |
|---|---|---|
| `cpu` / `cpu_core` / `cpu_atom` | **없음** | IPC, 캐시 미스, 명령어·사이클 수 |
| `msr` 이벤트 | `tsc`·`smi`·`pperf` 뿐 — **aperf/mperf 없음** | 실효 클럭 주파수 |
| `power` 이벤트 | **비어 있음** | RAPL 패키지 전력 |
| `/sys/devices/system/cpu/cpu0/cpufreq/` | **없음** | 스케일링 주파수 |

CPU 는 i7-13700H(P코어·E코어 혼합, 논리 20개)다. 베어메탈 리눅스라면 `cpu_core` 와
`cpu_atom` 이 보여야 하는데 둘 다 없다. `/proc/cpuinfo` 에 `hypervisor` 플래그가 있고,
Hyper-V 가 게스트에 PMU 를 노출하지 않는 것이 원인이다.

#### 영향

`perf stat` 계열 진단이 전부 불가능하다. 따라서 **고정 작업량 벤치(cpu-bench)가 "환경이
지금 얼마나 빠른가"를 재는 유일한 수단**이다. 이것은 차선책이 아니라 남은 유일한 선택지다.

#### 해제 조건

이 제약은 코드로 풀 수 없다. Windows 의 Hyper-V 가 게스트 PMU 를 노출하도록 바뀌거나,
측정 환경을 베어메탈 리눅스로 옮겨야 한다. 후자는 부하 발생기 물리 분리(P1-9)와 같은
장비 문제이므로 함께 다루는 편이 낫다.

> 관련: E-46(세션 간 편차), E-09(node-exporter 가 보는 "호스트"는 WSL2 VM), T-36(요청당
> 지표의 처리량 붕괴), P1-9(부하 발생기 물리 분리)

#### → 정정 (2026-08-19): "코드로 풀 수 없다"는 틀렸다 — 기본값이 꺼져 있을 뿐이다

위 결론은 **관측된 상태를 제약으로 오독한 것**이다. `arch_perfmon` 이 없는 것은 사실이지만,
그 원인은 Hyper-V 의 구조적 한계가 아니라 **WSL 의 기능 토글이 기본값 off** 이기 때문이다.

설치된 `C:\Program Files\WSL\wslservice.exe` 에서 확인한 사실이다.

- `.wslconfig` 의 `[wsl2]` 섹션이 **`hardwarePerformanceCounters` 키를 지원**한다.
  내부 이름은 `EnableHardwarePerformanceCounters` 이고, `EnableGpuSupport`·`EnableGuiApps`
  와 나란히 놓인 평범한 기능 플래그다.
- 같은 섹션에 `safeMode` 키가 있다. 안전 모드는 기능을 최소화하는 문제 해결용 모드이므로
  켜져 있으면 이 기능도 함께 꺼진다. 현재 이 머신에는 `.wslconfig` 파일 자체가 없어
  safeMode 는 기본값(off)이다.
- 설치된 WSL 은 **2.7.10.0** 이다. 이 기능은 0.50.2 부터 들어갔으므로 이 빌드에 포함된다.

적용 방법은 `%USERPROFILE%\.wslconfig` 에 아래를 넣고 `wsl --shutdown` 후 재기동하는 것이다.

```ini
[wsl2]
hardwarePerformanceCounters=true
```

**아직 검증하지 않았다.** 켠 뒤 `/proc/cpuinfo` 에 `arch_perfmon` 이 나타나고
`/sys/bus/event_source/devices/` 에 `cpu_core`·`cpu_atom` 이 생기는지 확인해야 확정된다.

##### 켜기 전에 알아야 할 것 — 이것도 환경 변경이다

1. `wsl --shutdown` 은 Docker Desktop 의 VM 을 통째로 내린다. perf 스택 컨테이너가 전부
   멈추므로 실행 중인 측정이 있으면 죽는다.
2. VM 재기동 직후 3회는 5~14% 느리다(perf-session-drift.md 5절). 벤치가 정상 범위로
   돌아온 뒤 측정을 시작해야 한다.
3. **PMU 가상화 자체가 오버헤드를 줄 수 있다.** 켠 뒤의 성능이 끈 상태와 같은지 확인하지
   않으면, E-46 을 조사하려고 E-46 의 관측 조건을 바꾼 셈이 된다. 켜기 직전에 같은 조건
   세트를 확보해 두고 켠 뒤 세트와 비교해야 한다.

> 관련: E-46(세션 간 편차), T-36(요청당 지표의 처리량 붕괴), E-09(node-exporter 가 보는
> "호스트"는 WSL2 VM)

> **쉽게 말하면.** Windows 전원 계획이 "균형 조정"이고 **최소 프로세서 상태가 5%** 다.
> 부하가 가벼우면 CPU 가 내려가고 무거우면 터보가 걸린다. 앱 컨테이너는 2코어 quota 에
> 완전히 붙어 있어서 **CPU 시간은 상수인데 그 시간 동안의 클럭이 변한다** — 같은 2 CPU
> 초로 처리하는 실제 명령량이 실행마다 달라진다.

#### 확인된 설정

```
전원 구성표      : 381b4222-f694-41f0-9685-ff5bb260df2e (균형 조정)
PROCTHROTTLEMIN  : 0x05   ← 최소 프로세서 상태 5%
PROCTHROTTLEMAX  : 0x64   ← 100%
AC EPP           : 45%
이기종 스케줄링   : Automatic
CPU              : i7-13700H (P-core 6 + E-core 8, 논리 20)
```

CPU 는 노트북용 H 시리즈라 전력 관리가 공격적이다. 그리고 게스트에는 P/E 구분이 노출되지
않는다 — WSL 은 20 CPU 를 균일 SMT 토폴로지처럼 보여주므로 게스트 스케줄러는 어느 vCPU 가
P-core 인지 알 수 없다.

컨테이너에도 코어 고정이 없다.

```
cpu.max              = 200000 100000   (100ms 당 200ms = 2코어 quota)
cpuset.cpus.effective = 0-19           (20개 어디서든 실행)
CpusetCpus           = ""              (고정 없음)
```

즉 **"코어 2개를 떼어 준 것"이 아니라 "20개 중 아무 데서나 2코어어치 시간을 쓰게 한 것"**
이다. Docker 문서도 `--cpus` 는 CFS quota 이고 특정 CPU 지정은 별도의 `--cpuset-cpus` 라고
구분한다.

#### 실측 — 주파수가 실행마다 24%포인트 움직인다

2026-08-19 실행 16건의 `% Processor Performance`(실제 주파수 ÷ 공칭 주파수) 평균이다.

| 세트 | Windows CPU 평균 | 주파수 평균 | p95 평균 |
|---|---:|---:|---:|
| 오후 (#84~88) | 28.6~31.3% | **94.3~104.7%** | 13,769ms |
| 저녁 (#90~98) | 39.8~50.9% | **113.9~117.6%** | 10,685ms |

순위상관은 **p95 ↔ 주파수 −0.43**, **p95 ↔ Windows CPU −0.47** 이다. 호스트가 바쁠수록
클럭이 높고 앱이 빨랐다. 이 문서 8.3절의 이전 관측(주파수 86.0 → 107.8% 상승, p95 와
순위상관 −0.70)과 같은 방향이다.

유휴 상태에서도 호스트가 완전히 조용하지 않다 — 측정 시점에 Docker Desktop 6.2%,
vmmemwsl 5.9%, IDE·브라우저 등으로 **전체 CPU 23.9%, 주파수 107.9%** 였다. 즉 "유휴
기준선"조차 다른 앱의 활동 수준에 따라 달라진다.

#### 왜 이게 크게 증폭되는가

앱이 CPU quota 에 완전히 붙어 있으면(`cpu.cores.avg 1.998 / 2.0`) 처리율은 곧 "그 CPU
시간 동안의 유효 명령량"이다. 클럭이 20% 내려가면 처리율이 20% 내려간다. 그리고 부하가
closed model(`ramping-vus` 200 VU)이라 응답시간은 `R = N / X` 로 기계적으로 늘어난다.
작은 클럭 변화가 큰 p95 차이로 증폭되는 경로다. 상세는
[perf-session-drift.md](../investigations/perf-session-drift.md) 8-d 절.

#### 남은 불확실성 — 역인과

**주파수 상관만으로 인과를 확정할 수 없다.** 처리율이 높으면 VM 이 CPU 를 더 쓰고 터보가
더 걸리므로 `p95 ↓ → 클럭 ↑` 일 수도 있다. 가르려면 **고정 작업량 벤치를 찍으면서 동시에
호스트 주파수를 기록**해야 한다. 벤치는 스스로 부하를 늘리지 않으므로 역인과가 없다.
현재 `tools/idle-bench-logger.js` 에 호스트 카운터가 없는 것이 그 공백이다.

#### 대응 — 클럭 고정

```powershell
# 고정
powercfg /setacvalueindex SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMIN 100
powercfg /setactive SCHEME_CURRENT

# 되돌리기 (원래 값 5%)
powercfg /setacvalueindex SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMIN 5
powercfg /setactive SCHEME_CURRENT
```

**주의.** 노트북이라 클럭 고정은 발열과 배터리에 영향을 준다. 지속 부하에서 열 스로틀링이
걸리면 오히려 다른 변동이 생길 수 있으므로, 고정 후에도 주파수를 계속 기록해 실제로
평평해졌는지 확인해야 한다.

**cpuset 고정만으로는 부족하다.** Hyper-V 의 virtual processor 자체가 서로 다른 host
logical processor 로 이동할 수 있어, 게스트에서 cpuset 을 지정해도 물리 코어가 고정되지
않는다.

#### 완료 기준

1. 클럭 고정 후 `% Processor Performance` 의 실행 간 변동이 크게 줄었다.
2. 같은 조건 세트의 CV 가 7.07%(2026-08-19 9회차 세트) 대비 유의하게 내려갔다.
3. 세트 간 레벨 차이(오후 13,769ms 대 저녁 10,685ms 수준)가 줄었다.
4. 유휴 벤치 로거가 호스트 CPU·주파수를 함께 기록한다.

> 관련: E-46(세션 간 편차), E-48(PMU 활성화), T-36(요청당 지표의 처리량 붕괴),
> S-06(open/closed model), perf-session-drift.md 8-d

#### → 정정 (2026-08-20) — 이 항목의 인과 주장을 철회한다

위 실측(주파수 ↔ p95 −0.43)은 **심슨의 역설**이었다. 절차가 동일한 구간에서 다시 계산하면
부호가 뒤집힌다.

| 범위 | 절차 | 주파수 ↔ p95 |
|---|---|---:|
| 전체 16건 | 혼재 | −0.432 |
| #84~88 | loadbench 없음 | **−1.000** |
| #90~98 | loadbench 있음 | **+0.400** |

집단 구분선이 하필 **2026-08-19 저녁에 우리가 도입한 계측 변경**(실행 전 벤치 1→3회,
warmup 에 loadbench 추가)과 일치한다. 게다가 **loadbench 는 hostProbe 창 안에서 실행된다** —
설명 변수 안에 CPU 를 태우는 도구를 넣어 놓고 그 값으로 상관을 낸 셈이다.

**"클럭을 고정했다"는 표현도 근거가 없다.** 이 머신의 전원 구성표에 노출된 프로세서 설정은
`PROCTHROTTLEMIN`·`PROCTHROTTLEMAX` 두 개뿐이고, 이기종 코어 클래스별 설정과 EPP 는 숨김
상태라 열거되지 않는다. **변경이 모든 코어 클래스에 적용됐는지 확인할 수 없다.** 실측도
같은 방향이다 — 적용 후에도 유휴 주파수는 70~89%였고, 고정 전후 벤치가 4,994 대 4,995ms 로
차이가 없었다.

그리고 최소 성능 상태 100% 는 터보·패키지 전력 한계·열 한계·P/E 배치·Hyper-V vCPU 이동·
QoS·EPP 를 고정하지 않는다. 노트북에서는 오히려 발열 상승 → 팬 정책 변경 → 후반 열
스로틀링이라는 **새로운 드리프트**를 만들 수 있다.

**`% Processor Performance` 해석도 과했다.** 이 카운터는 FREQUENCY 와 별개의 타입이고
`_Total` 집계라 유휴 코어까지 포함한다. **WSL 이 실제로 돈 논리 프로세서의 물리 클럭이
아니다.** "주파수가 20% 낮았다"가 아니라 "Windows 가 본 시스템 전체 정규화 성능이 낮았다"가
맞다.

##### 그래도 남는 것

loadbench 는 40초 × 2코어로 600초 창의 약 0.67% 다. 이것만으로 창 평균이 17%포인트
오르지는 않으므로 **두 세트의 격차 자체는 여전히 미설명**이다. 상위 계층은 버릴 대상이
아니라 제대로 재야 할 대상이다.

##### 항목 재정의

이 항목의 제목을 좁은 의미의 "클럭 미고정"에서 다음으로 읽어야 한다.

> **Windows / Hyper-V / 이기종 CPU 계층에서 실행별 유효 처리 능력이 통제되지 않는다.**
> 여기에는 최소 성능 상태뿐 아니라 P/E 코어 배치, Windows QoS 분류, Hyper-V virtual
> processor 의 호스트 논리 프로세서 이동, 패키지 전력·열 한계, EPP, 다른 호스트 프로세스와의
> 전력 공유가 모두 포함된다. **현재 계측으로는 이들을 서로 가를 수 없다.**

##### 올바른 검증 설계 (앞의 "대응" 절을 대체한다)

전원 설정을 한 번 바꾸고 3회 돌리는 방식으로는 확정할 수 없다. 순서는 이렇다.

1. **계측을 먼저 고친다** — T-37. 구간 분리, 논리 프로세서별 수집, 샘플링 간격 단축,
   원시 시계열 보존.
2. **모든 실험군의 절차를 통일한다** — loadbench 유무·시점·횟수를 같게. 한쪽에만 있으면
   그 자체가 교란이다.
3. **교차 설계로 A/B 한다** — `A-B-B-A-B-A-A-B` 또는 무작위 순서, **조건당 최소 5회**.
   각 실행 전 AC 전원·팬 모드·배터리 충전 상태·배경 프로세스·시작 온도(또는 충분한 cooldown)
   ·스냅샷 복원 여부를 동일하게 맞춘다.
4. **결과를 네 갈래로 해석한다.**

   | 결과 | 해석 |
   |---|---|
   | 고정 작업 처리량과 앱 처리량이 **함께** 증가, CV 감소 | 전원/성능 상태가 주요 기여 요인 |
   | `_Total` 주파수만 증가, 고정 작업 처리량은 그대로 | 집계 카운터의 착시 |
   | 고정 작업만 빨라지고 앱 p95 는 동일 | p95 의 주원인은 큐잉 구조 |
   | CV 는 줄지만 후반에 다시 열화 | 열·패키지 전력 효과 |

5. **실험 후 전원 설정을 원래 값으로 되돌린다**(AC 최소 프로세서 상태 5%).

> 관련: [perf-session-drift.md](../investigations/perf-session-drift.md) 8-e, T-37(hostProbe 계측 결함)

##### 실측 — 개입은 예측과 **반대 방향**으로 작동했다 (2026-08-20)

`PROCTHROTTLEMIN` AC 를 5% → 100% 로 올린 뒤 같은 절차로 3회차를 재고, 변경 전
#90~98(n=9, 같은 절차)과 비교했다.

| 지표 | A: 변경 전 (n=9) | B: 변경 후 (n=3) | 변화 |
|---|---:|---:|---|
| p95 평균 | 10,685ms | **15,721ms** | **+47%** (나빠짐) |
| 반복 처리율 | 5.96 회/초 | **4.67 회/초** | **−22%** |
| p95 CV | 7.07% | 8.12% | 거의 동일 |
| `% Processor Performance` 평균 | 114.8% | **102.5%** | **−12%p (내려감)** |
| Windows CPU 평균 | 44.3% | 27.2% | −17%p |
| 유휴 벤치 single | 5,187ms | 5,040ms | −3% (빨라짐) |
| **부하 중 벤치 single** | 6,364ms | **5,581ms** | **−12% (빨라짐)** |

세 가지가 드러난다.

1. **최소 성능 상태를 올렸는데 `% Processor Performance` 가 오히려 내려갔다.** 이 카운터가
   코어 클럭이 아니라 **시스템 전체 활동 수준의 대리 지표**임을 보여준다. Windows CPU 가
   44% → 27% 로 함께 내려간 것과 방향이 같다. 앞선 −0.43 상관이 왜 나왔는지도 이걸로
   설명된다 — 호스트가 바쁘면 카운터가 오른다.
2. **고정 작업량 벤치는 빨라졌는데 앱은 크게 느려졌다.** 같은 절차 안에서 두 계열이 또
   반대로 움직였다. **환경의 순수 CPU 처리 능력으로 앱 처리율을 설명할 수 없다.**
3. **개입이 성능을 악화시켰을 가능성이 있다.** 노트북에서 모든 코어의 최소 성능을 올리면
   패키지 전력·온도가 올라 실제 작업 코어의 터보 여력이 줄어든다는 우려가 있었는데, 관측
   방향이 그와 일치한다.

**다만 확정할 수 없다.** n=3, 교차 설계 아님, 시간대·배경 프로세스 다름, 그리고 이 환경은
개입 없이도 레벨이 ±28% 움직인다(8-b.5). **개입이 원인인지 자연 변동인지 가르지 못한다.**

**조치.** 전원 설정을 원래 값(AC 최소 프로세서 상태 5%)으로 되돌렸다. 이 결과는 "전원 설정을
바꾸면 안 된다"의 근거가 아니라, **교차 설계 없이 전후 비교로 판단하면 안 된다**의 근거다.

### E-50. [INFO] 호스트 CPU 에 16% 폭의 일중 주기가 있다 — 상태: **해결(무해 확인)** (2026-08-25) — 앱 측정에는 전달되지 않는다

> **해결 기록 (2026-08-25) — 관측 + 무해 확인.**
>
> **무엇을 발견했나.** `tools/idle-bench-logger.js` 가 134시간 동안 남긴 814표본을 분석하니,
> 호스트 CPU 속도에 **하루를 주기로 16% 폭의 재현 가능한 변동**이 있었다. KST 09시에
> 빨라지고 18시에 느려지는 계단 모양이고, 6일 내내 같은 패턴이 반복된다.
> 반면 **일 단위 중앙값은 1.7% 안에서 안정적**이다(08-20 ~ 08-25).
>
> **왜 이 항목이 필요한가.** E-46 조사가 닷새 동안 "환경이 세션마다 변한다"를 전제로
> 삼았는데, 그 전제의 실제 모양이 처음으로 데이터로 나왔다. **환경은 무작위로 드리프트하지
> 않는다 — 하루 주기로 두 레벨을 오간다.**
>
> **그런데 앱에는 전달되지 않는다.** RATE=4 실행 11건에서 실행 직전 벤치(`run.cpuBench`)와
> 앱 전체 p95 의 피어슨 상관이 **r = −0.006** 이다. 벤치는 낮 4,940~5,062ms, 밤
> 5,795~5,970ms 로 17% 차이가 뚜렷한데 앱 p95 는 구분되지 않는다(낮 371ms, 밤 364ms).
> **포화 이하에서는 CPU 여유가 37~50% 남아 있어 코어가 조금 느려져도 큐가 생기지 않는다.**
>
> 이는 E-46 해결(증폭기 제거)이 **전체 p95 에서도 작동한다는 독립적 증거**다.
> `perf-session-drift.md` 0.6절은 `comment` 기능별 p95 의 세트 평균 두 개로 같은 결론에
> 도달했는데, 여기서는 전체 p95 를 표본 11개의 상관계수로 확인했다.
>
> **고민한 대안과 버린 이유.**
> - *측정 시각을 고정한다(예: 항상 20~22시)* → **버렸다.** 처음에는 세트 평균 비교에서
>   "시간대가 앱 p95 를 31% 움직인다"고 판단했으나, 표본 단위 상관을 내니 r = −0.006 이었다.
>   **세트 평균 두 개를 비교하고 그 사이에 있는 다른 변수를 원인으로 지목한 오류**였다.
> - *CPU 클럭을 고정한다(`PROCTHROTTLEMIN 100`)* → **버렸다.** E-49 가 이미 실측으로
>   기각했다(고정 전후 유휴 벤치 4,994 대 4,995ms). 이번에 **기각 근거가 시간대에 교락됐을
>   가능성을 검토했으나 뒤집지 못했다** — 클럭 고정 세트는 KST 10:22, 즉 CPU 가 가장 빠른
>   시간대에 돌았고 그 유리한 조건에서도 p95 가 +47% 나빴다. 교락은 기각을 **강화**한다.
> - *유휴 로거를 상시 가동한다* → **버렸다.** 추적 파일에 계속 기록해 작업 트리가 `+dirty`
>   로 유지된다. 그 상태의 실행 기록은 "어느 코드로 잰 값인지" 증명할 수 없다. 질문이
>   생겼을 때만 켠다.
>
> **어떻게 검증했나.** 8절의 재현 명령으로 시간대별 중앙값을 재계산할 수 있다. 상관 분석은
> `reports/runs/<runId>/run.json` 의 `run.cpuBench.axes.single.ms` 와
> `k6.phases.measure.p95` 를 쓴다.
>
> **부수 발견 — 조사 중 세운 가설 하나를 기각했다.** `#115`(도착률을 지켰는데도 포화로 넘어간
> 회차)의 원인이 환경 스파이크로 보였으나, **그 회차의 실행 직전 벤치는 4,987ms 로 정상**
> 이었다. 스파이크로 보인 표본은 전부 `underLoad: true`, 즉 **부하 테스트와 경합하며 찍힌
> 값**이었다(역인과). `#115` 의 원인은 여전히 미규명이다.
>
> **남은 부작용 / 후속 작업.**
> - **규칙 신설: `underLoad: true` 표본은 환경 판단에 쓰지 않는다.** E-49 정정이 이미 같은
>   함정(`loadbench` 가 hostProbe 창 안에서 실행됨)을 기록했는데 **두 번째 재발**이다.
>   환경을 보려면 `run.cpuBench`(실행 직전)나 `underLoad: false` 표본만 쓴다.
> - `run.cpuBench` 를 회차 무효화 조건으로 승격할지는 **열어 둔다.** `#115` 가 벤치 정상인데
>   포화됐으므로 필요조건일 수는 있어도 충분조건은 아니다.
> - 3.1절의 원인 추정(Windows 전원 관리)은 **확인하지 않았다.** 호스트 주파수를 유휴 로거에
>   붙여야 확인되며, E-49 완료 기준 4번이 같은 것을 요구한다. 다만 이 항목의 결론(무해)은
>   원인을 몰라도 성립한다.
>

### E-51. [HIGH] 반복 세트의 이상 회차는 순서가 아니라 **커넥션 풀 고갈**로 갈린다 — 상태: **해결(운용 규칙 확정)** (2026-08-26)

> **해결 기록 (2026-08-26) — 원인 규명 + 기존 장치로 무해화.**
>
> **무엇을 발견했나.** 반복 세트에서 회차 하나가 2~3배 느린 일이 반복됐다. 처음에는
> **"1회차가 항상 느리다"** 로 읽혔으나, 5회 세트를 완주해 보니 **이상 회차가 2회차**였다.
> 순서가 아니라 **커넥션 풀이 100% 차고 대기가 생긴 회차**가 느리다.
>
> | 회차 | p95 | **Hikari 대기** | Hikari% | CPU% | 포화 판정 |
> |---|---:|---:|---:|---:|---|
> | 1 | 388ms | **0** | 40% | 52% | HEADROOM |
> | **2** | **921ms** | **20** | **100%** | 62% | **NEAR_LIMIT** |
> | 3 | 345ms | **0** | 60% | 42% | HEADROOM |
> | 4 | 335ms | **0** | 40% | 42% | HEADROOM |
> | 5 | 306ms | **0** | 30% | 53% | HEADROOM |
>
> **대기가 생긴 회차만 느리다. 예외가 없다.** 전날 중단된 세트에서는 같은 사건이 1회차에
> 일어났고(대기 29, `hikariPct` 100%), 그래서 "1회차 효과"로 오인됐다.
>
> **사건의 모양.** 2026-08-25 1회차의 measure 구간을 5초 간격으로 확대하면 이렇다.
>
> ```
> 시각(UTC)   대기   사용중   CPU코어
> 11:05:40     16     10      1.02
> 11:05:45     29     10      1.65
> 11:05:55      6     10      2.01   ← CPU 상한 도달
> 11:06:00      6     10      2.00
> 11:06:45      4     10      1.97
> ```
>
> **약 20초 동안 풀(크기 10)이 꽉 차고 최대 29개 스레드가 줄을 섰다.** 그 구간에서 CPU 가
> 2.00 코어(상한)에 닿는다. measure 구간 전체가 아니라 **후반 20초짜리 사건**이다.
>
> **CV 에 미치는 영향이 결정적이다.**
>
> ```
> 5회 전부      p95 CV 56.68%  ·  p99 CV 13.09%
> 이상 회차 제외  p95 CV  9.9%  ·  p99 CV 10.9%
> ```
>
> **이상치 하나가 p95 CV 의 대부분을 만든다.** MDE 로 환산하면 5배 차이다.
>
> **고민한 대안과 버린 이유.**
> - *첫 회차를 항상 예열로 버린다* → **버렸다.** 5회 세트에서 1회차는 정상(388ms)이었고
>   2회차가 튀었다. 순서 기반 규칙은 이 세트에서 틀린 회차를 버린다.
> - *`hikariPending > 0` 을 새 무효화 규칙으로 추가한다* → **불필요하다.**
>   `tools/lib/saturation.js` 의 `hikariPending` 신호(warn 1 / fail 5)가 **이미 두 세트
>   모두에서 해당 회차를 `NEAR_LIMIT` 으로 잡아냈다.** 새 규칙을 만들면 같은 판정이 두
>   곳에 생겨 T-40 과 같은 불일치를 부른다.
> - *풀 크기를 늘려 사건을 없앤다* → **측정 시스템의 일이 아니다.** 풀 크기는 애플리케이션
>   구성이고, 바꾸면 측정 대상이 달라져 기존 계열과의 비교가 끊긴다. 병목 쪽(BTL-002)에서
>   다룰 문제다.
>
> **확정된 운용 규칙.**
> **반복 세트에서 포화 판정이 `HEADROOM` 이 아닌 회차는 표본에서 뺀다.** 순서는 보지 않는다.
> 5회를 확보하려면 `--runs 6` 으로 여유를 두는 것을 검토한다(이상 회차 발생률이 두 세트에서
> 각 1회였다).
>
> **기각한 원인 후보 — 전부 실측으로 확인했다.**
>
> | 후보 | 기각 근거 |
> |---|---|
> | 앱 상태·JVM 힙 잔존 | 클래스 로드 수 차이 **0.0%** (27,249 대 27,262). 힙은 프로세스 종료 시 사라진다 |
> | MySQL 버퍼풀 콜드 | 적중률 세 회차 **전부 100.0%** |
> | Docker 볼륨 | `snapshot.js:251` 이 `find /to -mindepth 1 -delete && tar -xf` 로 **매회 전체 교체** |
> | 호스트 CPU 변동 | 실행 직전 벤치 5,935 / 5,821 / 5,965ms — 동일 (E-50) |
> | JVM 워밍업 부족 | **warmup 구간은 1회차가 오히려 빠르다**(403ms 대 456ms). 느려지는 것은 measure 후반 |
> | 스케줄러 간섭 | measure 구간 내 스케줄러 총 소요가 1회차 2,510ms / 3회차 3,619ms — **더 무거운 3회차가 더 빠르다** |
> | JIT 컴파일 | `jitCompileMs` 가 1회차에서 +43% 이지만 **CPU 경합의 결과다.** measure 300초 × 2코어 대비 3.6% 로 p95 2.5배를 설명하지 못한다 |
>
> **왜 특정 회차에서만 고갈되는가 — 규명됐다 (2026-08-26 추가).**
>
> **"같은 요청"이 아니다. 회차마다 다른 글을 뽑는다.** `hotIndex()` 의 난수원이
> `Math.random` 이라(`sampling.js:116`) 시드가 없고, 그 위에 **요청 비용이 542배 벌어져
> 있다** — medium 데이터셋의 게시글별 댓글 수가 평균 7.2개인데 `postId 1` 은 3,908개다.
> Zipf 분포상 그 글이 요청의 **9.9%**(1,347건 중 약 134회) 를 가져가고,
> `comment_list` 는 페이징이 없어 한 건에 쿼리 약 7,800개를 쓴다(KI-27 의 2N+α).
>
> **다만 무거운 요청 하나로는 터지지 않는다.** max 20초·29초짜리 요청이 있던 회차도 대기가
> 0이었다 — 한 건은 커넥션 하나만 쓰므로 풀 10개 중 9개가 남는다. **갈리는 것은 동시에 몇
> 개가 무거운가**이고, 스파이크 회차만 `p99/p90` 이 4.15(나머지 1.6~1.9), 동시 처리량이
> 2.52(나머지 1.16~1.51)였다.
>
> **부수 발견 — 표본 추출이 CV 의 상당 부분을 만든다.** 몬테카를로 2,000회로 총 작업량
> 변동을 재니 **CV 4.76%**(최대/최소 1.49배)였고, 실측 요청당 쿼리 CV 가 **5.74%** 로
> 거의 일치한다. **현재 MDE 에는 앱 성능 변동이 아닌 것이 섞여 있다.**
>
> 해결안(고정 시드 / 공통 난수 CRN)의 트레이드오프 검토는 상세 문서 6절. **결론은 KI-27
> 실험 이후로 미룬다** — 기대 개선 폭이 표본 분산보다 훨씬 크고, 지금 바꾸면 확보한 Before
> 5회가 무효가 되며, KI-27 수정 자체가 542배 편중을 없애기 때문이다.
>

### E-52. [HIGH] 환경 설정이 프로파일화돼 있지 않아 **어느 볼륨에 쓰는지 모르고 실행**한다 — 상태: **부분 해결(검문 추가)** (2026-09-01)

> **무엇을 겪었나.** `smoke` 데이터셋을 만들려고 실행한 명령이 **`large` 볼륨에 `small`
> 데이터를 부었다.** 게시글 +507건, 댓글 +1,465건이 large 데이터셋에 섞였다.

> 데이터셋을 다시 만들어야 했다.
>
> 실행한 명령은 하나다.
>
> ```bash
> node datasets/seed.js smoke
> ```
>
> **세 가지가 동시에 어긋났고, 셋 다 조용했다.**

> | # | 무엇이 | 왜 조용했나 |

> (total=10, active=10, idle=0, waiting=0)
> ```
>

> 이미 DB 에 1,465건이 들어간 뒤**였다. 산출물을 안 쓰는 것과 DB 를 안 건드리는 것은 다르다.
>
> ---
>
> **막을 장치는 이미 있었다. 우회했을 뿐이다.**
>
> `bootstrap.js` 가 정확히 이 사고를 막는 검문을 갖고 있다 — 마운트된 볼륨과 `--profile`
> 일치, 게시판 선삽입, `daily_hot_post` 생성, Redis FLUSHALL, 중복 시드 차단. 그 주석에는
> *"이 확인이 없으면 medium 데이터를 small 볼륨에 부어버린다"* 라고 이 사고가 그대로
> 적혀 있다.

> 것을 막는 것은 아무것도 없었다.

> **이것이 이 항목의 요지다.** 개별 실수(인자 형식, 볼륨 확인)가 아니라, **환경 설정이

> 데이터셋 규모   datasets/profiles.json   (--profile)
> 대상 볼륨       environment/.env.perf    (DATASET_PROFILE) ← 명령에 안 보인다

> 다른 맥락에서 이미 정리한 결론이 그대로 적용된다 — *"사람이 매번 기억해야 하는 절차는
> 결국 지켜지지 않는다."*
>

>
> **한 조치 (2026-09-01).** `seed.js` 에 두 검문을 넣었다. 근본 해결이 아니라 **같은

> | 마운트 볼륨 ↔ 프로파일 | 불일치면 즉시 종료(1). `bootstrap.js` 를 쓰라는 안내를 함께 낸다 |

> 알리고 계속한다 — 도커를 안 쓰는 사용처를 통째로 막지 않기 위해서다.
> `--no-volume-check` 로 끌 수 있고, 껐다는 사실은 로그에 남는다.
>
> **남은 것 — 환경 프로파일화.** 검문은 틀린 조합을 거절할 뿐, 맞는 조합을 만들어 주지
> 않는다. 규모·볼륨·자원·부하 수준을 **하나의 이름으로 묶어** 그 이름만 고르면 나머지가
> 따라오게 하는 것이 근본 해결이다. 이 방향은 별도 과제로 둔다.
>
> **관련:** E-07(데이터 생성과 측정이 서로 다른 앱 설정을 사용), E-12(모든 데이터셋이 같은
> Prometheus 라벨을 공유), `environment/bootstrap.js`, `environment/docker-compose.seed.yml`

### E-53. [HIGH] 짧고 깊은 호스트 정지를 포화 판정이 통과시킨다 — 상태: 미해결 (2026-09-03 관측)

> **한 줄 요약.** 3.2초짜리 GC 정지와 커넥션 풀 100% 포화가 있었던 실행 두 건을
> `saturation.js` 가 둘 다 `HEADROOM` 으로 판정했다. 임계값이 **지속적인** 포화에 맞춰져
> 있어 **짧고 깊은** 정지를 보지 못한다.

#### 무엇을 겪었나

OPT-A(댓글 반응 일괄 조회)의 After 세트 5회를 쟀다. 앞 3회는 서로 3ms 안에 들어올 만큼
일치했는데, 하루 뒤에 이어 붙인 4·5회가 전혀 다른 값을 냈다.

| 회차 | 측정 시각 (UTC) | 전체 p95 | 전체 p99 | 포화 판정 |
|---|---|---:|---:|---|
| 1 | 09-01 12:42 | 65ms | 150ms | HEADROOM |
| 2 | 09-01 12:54 | 63ms | 150ms | HEADROOM |
| 3 | 09-01 13:06 | 60ms | 152ms | HEADROOM |
| 4 | 09-02 08:36 | 133ms | **3,616ms** | HEADROOM |
| 5 | 09-02 08:48 | 296ms | **2,769ms** | HEADROOM |

4·5회의 p99 는 최적화 **이전**(Before 5회 평균 1,831ms)보다도 나쁘다. 그런데도 판정기는
다섯 회차 모두 "여유 있음, p95 를 애플리케이션 지연으로 읽어도 된다"고 말했다.

#### 애플리케이션 문제가 아니라는 증거

**요청당 쿼리가 2개뿐인 엔드포인트도 같이 멈췄다.** 이것이 결정적이다.

| 기능 p99 | 3회차(정상) | 4회차 | 5회차 |
|---|---:|---:|---:|
| `board` — 요청당 쿼리 **2개** | **13ms** | 3,366ms | 2,314ms |
| `chat` | 32ms | 3,807ms | 3,108ms |
| `notification` | 36ms | 2,336ms | 1,412ms |
| `post` | 88ms | 3,196ms | 2,902ms |
| `comment` (최적화 대상) | 180ms | 406ms | 326ms |

쿼리 2개를 던지고 4.5ms 만에 끝나던 `board` 가 3.4초가 되려면 프로세스나 그 아래 계층이
통째로 멈추는 수밖에 없다. 그리고 **정작 이번에 손댄 `comment` 가 가장 덜 나빠졌다** —
오염이 특정 코드 경로가 아니라 전역이라는 뜻이다.

정지의 흔적도 기록에 남아 있다.

```
4회차   DB 커넥션 풀 사용률 100% 도달
5회차   GC 최대 정지 3,255ms · GC p95 2,000ms      (정상 회차는 최대 39ms)
        커넥션 대기 최대 7 스레드
공통    앱 컨테이너 CPU throttled 3.36% / 5.41%    (정상 회차는 0.00%)
        호스트 CPU 순간 최고 90.0% / 88.9%          (정상 회차는 42.9% / 35.9%)
```

힙 사용량은 450~510MB 로 평소와 같았다. **메모리 압박이 아니라 CPU 를 받지 못해 생긴 GC
정지**다. 호스트 CPU 평균은 네 회차 모두 11~13% 로 비슷했고 **순간 최고치만 두 배로 뛰었다** —
지속 경합이 아니라 스파이크다.

#### 왜 판정기가 통과시켰나

`saturation.js` 의 네 신호 중 이 상황에 반응할 수 있는 것은 `cpuThrottled` 하나인데,
주의 임계가 30% 다. 실측은 5.41% 였다.

| 신호 | 주의 | 포화 | 4·5회차 실측 | 걸렸나 |
|---|---:|---:|---:|---|
| `hikariPending` (대기 스레드 평균) | 1 | 5 | 0.00 / 0.35 | ✗ |
| `cpuThrottled` | 30% | 80% | 3.36% / 5.41% | ✗ |
| `cpuUtil` (상한 대비) | 75% | 90% | 15% / 16% | ✗ |
| `acquireShare` (획득이 p95 에서 차지하는 비율) | 20% | 40% | 1% 미만 | ✗ |
| `achievedRate` | 98% | 90% | 100.0% / 99.4% | ✗ |

임계값 자체는 틀리지 않았다. **2026-08-20 보정 곡선은 도착률을 올려 가며 만든 곡선이라,
"부하가 용량을 넘어 큐가 지속적으로 쌓이는" 상태를 겨냥한다.** 이번 건은 성질이 다르다 —
부하는 계획대로 4/s 로 들어갔고(도달률 100.0%/99.4%), 처리하는 쪽이 **간헐적으로 몇 초씩
멈췄다.** 평균으로 접으면 그 정지가 희석돼 어느 신호에도 안 걸린다.

4회차의 풀 지표가 그 희석을 그대로 보여 준다.

```
정상 회차(3회)   pool.hikariActive  평균 0.35 / 최대 2      pool.hikariPending  평균 0 / 최대 0
4회차            pool.hikariActive  평균 0.76 / 최대 10     pool.hikariPending  평균 0 / 최대 0
5회차            pool.hikariActive  평균 1.00 / 최대 8      pool.hikariPending  평균 0.35 / 최대 7
```

4회차는 **커넥션 10개를 전부 쓴 순간이 있었는데 대기 스레드는 평균도 최대도 0** 이다.
Prometheus 스크레이프 간격(5초)이 그 짧은 포화의 대기 구간을 건너뛴 것이다. 그리고 판정기가
보는 신호는 `hikariPending.avg` 하나뿐이라, 이미 수집돼 있는 `hikariActive.max = 10` 은
어디에서도 판정에 쓰이지 않는다.

#### 왜 이것이 E-46 과 같은 종류의 빈칸인가

E-46 은 "지표는 전부 있었는데 **아무도 그 조합을 측정 무효화 조건으로 선언하지 않아서**"
닷새를 썼다. 이번에도 GC 정지·풀 사용률·호스트 CPU 최고치가 전부 수집돼 있었다. 없는 것은
데이터가 아니라 **선언**이다.

차이는 축이다. E-46 은 **부하가 용량을 넘은 경우**(수요 초과)를 다뤘고, 이번은 **용량이
일시적으로 사라진 경우**(공급 붕괴)다. 현재 판정기에는 뒤쪽 축이 아예 없다.

#### 무엇을 했나

**판정 세트에서 4·5회차를 제외하고 다시 쟀다.** 다만 결과를 보고 나서 마음에 안 드는 회차를
빼는 것은 사후 선별이므로, **재측정 전에 제외 기준을 먼저 문서에 못 박았다.**

> 요청당 쿼리가 2개 이하인 엔드포인트(`GET /api/boards`)의 p99 가 **1초를 넘는 회차**는
> 애플리케이션이 아니라 환경을 측정한 것으로 보고 판정 세트에서 제외한다.
> 보조 증거는 GC 최대 정지 1초 초과, 호스트 CPU 순간 최고치 80% 초과다.

이 기준을 고른 이유는 **해석의 여지가 없기 때문**이다. 쿼리 2개짜리 요청이 1초를 넘었다면
그 시간은 어디서 왔든 애플리케이션 로직이 아니다. 임계값을 튜닝해야 하는 비율 지표와 달리
"이 값이 나오면 물리적으로 불가능하다"는 형태라, 나중에 다른 사람이 봐도 같은 판정을 낸다.

#### 이번 사건이 증명한 것 — 계측을 두 겹으로 둔 이유

같은 실행에서 두 지표가 정반대로 움직였다.

| 지표 | 1회 | 2회 | 3회 | 4회(오염) | 5회(오염) | 변동계수 |
|---|---:|---:|---:|---:|---:|---:|
| `comment_list` 요청당 쿼리 수 | 120 | 110 | 114 | 113 | 109 | **4.0%** |
| 전체 p95 | 65ms | 63ms | 60ms | 133ms | 296ms | **82.2%** |

**호스트가 3초씩 멈추는 동안에도 요청당 쿼리 수는 흔들리지 않았다.** 코드가 발행하는 문장
수는 환경 속도와 무관하기 때문이다. OPT-A 의 효과(1,507 → 113, −92.5%)는 오염된 회차를
포함해도 그대로 성립한다.

이것이 최적화마다 **결정적 계측(요청당 쿼리 수)** 과 **통계적 계측(지연 5회 세트)** 을 함께
두는 이유다. 앞의 것은 "코드가 의도대로 바뀌었나"에 답하고 환경 잡음에 면역이며, 뒤의 것은
"사용자가 겪는 시간이 줄었나"에 답하고 환경 잡음에 취약하다. 하나만 있으면 이번 같은 실행
앞에서 결론을 낼 수 없다.

#### 제안 — 판정기에 공급 붕괴 축을 추가한다

지속 포화를 보는 지금 신호들에 더해, **짧고 깊은 정지**를 보는 신호를 넣는다.
전부 이미 수집 중인 값이라 새 계측은 필요 없다.

| 신호 | 값 | 주의 | 포화 | 근거 |
|---|---|---:|---:|---|
| `gc.pauseMaxMs` | 이미 수집 중 | 1,000ms | 3,000ms | 정상 회차는 29~39ms. 두 자릿수에서 네 자릿수로 뛰는 값이라 경계가 넓다 |
| 호스트 CPU 순간 최고 | `hostprobe.jsonl` 0열 | 80% | 95% | 정상 36~43%, 오염 89~90% |
| `pool.hikariActive.max / pool.hikariMax` | 둘 다 이미 수집 중 | 90% | 100% | 평균이 아니라 **최고치**를 봐야 짧은 포화가 보인다 |

세 번째가 특히 중요하다. 지금 풀 신호는 `hikariPending.avg` 하나뿐이라 **평균으로 접히면서
짧은 100% 포화가 0.00 으로 보고된다.** `hikariActive.max` 는 이미 저장돼 있고 4회차에서
10(=풀 전체)을 기록했는데, 판정에 쓰이지 않아 아무 데도 드러나지 않았다. 새 계측이 아니라
**이미 있는 값을 판정에 연결하는 일**이다.
