# performance/tools 분석 도구 발견 사항

검토일: 2026-08-05
추가 조사일: 2026-08-06
쉬운 설명 기준 재정리: 2026-08-11

라인 번호는 검토 당시 HEAD 기준이다. 이후 코드가 변경되면 실제 위치와 다를 수 있다.
항목 번호는 기존 조사에서 사용한 식별자를 그대로 유지했다.

해결 또는 부분 해결로 표시한 변경 사항은 별도 표기가 없으면 2026-08-05 작업 내용을 기준으로 한다.

## 이 문서가 답하는 질문

이 문서는 k6가 만든 숫자가 `run.json`과 HTML 리포트로 바뀌는 과정이 정확한지 검토한다.
구체적으로 다음 단계를 다룬다.

```text
k6 원자료
   → summary 저장
   → Prometheus 조회
   → 이전 실행 선택
   → 절대·상대 규칙 평가
   → PASS/WARN/FAIL
   → HTML 리포트와 이력
```

어느 한 단계에서 값을 잘못 읽거나 비교 대상을 잘못 고르면, 원자료가 정확해도 최종 판정은
틀릴 수 있다. 그래서 각 항목은 “코드 버그가 있는가?”뿐 아니라 “사람이 리포트를 보고 어떤
잘못된 결론을 내리는가?”까지 설명한다.

## 먼저 알아야 할 결론

- 과거에는 점이 포함된 인프라 키를 읽지 못해 규칙 32개 중 25개가 SKIP됐다. T-01에서 수정했다.
- **비교 가능한 기준선의 정의가 없다**는 문제는 T-02에서 해결했다. 실행 조건을 일급 개념으로
  분리해, 데이터셋이나 부하 프로파일이 다른 실행은 기준선에서 제외하고 그 사유를 리포트에
  표시한다. **느린 실행이 기준선 후보에서 사라지던 문제도 S-10에서 해결했다**(2026-08-13).
  기준선 자격은 이제 성능 결과가 아니라 측정 무결성으로만 판정한다.
- **“문제 없음”과 “측정하지 못함”이 분리되지 않던 문제는 T-08에서 해결했다**(2026-08-13).
  판정(`verdict`)과 나란한 측정 상태(`measurementStatus`) 축을 만들고, 필수 지표 결측은
  전용 종료 코드 3으로 끝낸다. 판정을 값이 아니라 **표본 수**로 시작하는 것이 핵심이다 —
  k6는 표본이 0건인 서브메트릭도 0으로 채워 주기 때문에, 값만 보면 “요청 0건”이 “P95 0ms에
  오류 0%”인 완벽한 실행으로 둔갑한다.
- 일부 PromQL은 짧은 피크, 컨테이너 재시작, 트래픽 0인 Redis를 실제와 다르게 표현한다(T-18).
- MySQL 락·트랜잭션·풀스캔 원자료가 이미 Prometheus에 있지만 수집 카탈로그가 읽지 않는다(T-29).
- 자동 테스트는 추가됐고 기준선 선택은 T-02 작업에서 회귀 테스트로 덮였다. 그러나 Prometheus
  결측과 시나리오별 규칙은 아직 보호되지 않는다(T-19).

## 항목을 읽는 순서

각 발견은 가능한 한 다음 내용을 포함한다.

- **문제:** 코드가 현재 무엇을 잘못하고 있는가
- **영향:** 리포트와 의사결정이 어떻게 틀어지는가
- **근거:** 코드 위치와 실제 실행값은 무엇인가
- **해결 내용:** 이미 수정했다면 무엇을 바꾸고 어떻게 검증했는가
- **필요한 조치:** 아직 해결되지 않았다면 다음 결정과 구현은 무엇인가

처음 읽는 사람은 T-01 → T-02 → T-08 → T-18 → T-29 순서로 보면 전체 위험을 가장 빨리
이해할 수 있다.

## 용어

- **게이트**: 성능 결과가 허용 기준을 넘었는지 판정해 빌드의 통과 또는 실패를 결정하는 규칙
- **기준선**: 현재 성능 결과와 비교할 이전 실행 결과
- **결측 지표**: 수집 실패 등으로 현재 값을 확인할 수 없는 지표
- **SKIP**: 값을 평가하지 않고 판정을 생략한 상태
- **노이즈 억제**: 변화가 너무 작거나 기준값이 너무 낮아 의미 있는 비교가 아니라고 판단해 판정을 생략하는 처리

## CRITICAL

### T-01. 인프라 규칙 32개 중 25개가 실제로 평가되지 않음 — 상태: 해결

**문제**

`performance/tools/lib/regression.js:30-32`의 `pick()`은 점으로 구분된 키를 중첩 객체 경로로 해석한다. 예를 들어 `infra.flat.saturation.cpuPct`를 다음과 같은 중첩 구조에서 찾으려고 한다.

```text
infra
└─ flat
   └─ saturation
      └─ cpuPct
```

하지만 실제 `infra.flat`은 중첩 객체가 아니라, 키 자체에 점이 들어 있는 평면 맵이다.

```text
infra.flat["saturation.cpuPct"]
```

실제 데이터 구조는 `performance/tools/lib/metrics-catalog.js:477-489`와 `performance/tools/collect.js:90-91`에서 확인할 수 있다.

**영향**

`pick()`이 인프라 지표를 찾지 못해 현재 값을 모두 `undefined`로 반환했다. 그 결과 인프라 규칙은 실패 여부를 평가하지 않고 전부 SKIP 처리됐다.

특히 `throttledPct`, `slowQueries`, `hikariTimeouts`는 게이트 지표인데도 이 문제가 생긴 이후 한 번도 정상적으로 작동할 수 없었다.

**근거**

`normal-day-2026-08-05T09-39-43/run.json`에는 다음 결과가 저장돼 있다.

```text
counts = { total: 32, fail: 5, skipped: 25 }
```

같은 파일의 `infra.flat`에는 다음과 같은 실제 값이 존재했다.

- `cpu.throttledPct = 99.98`
- `pool.hikariTimeouts = 5316`
- `pool.hikariPending.max = 205`

그런데 회귀 비교 표에서는 해당 지표가 모두 “현재 값 없음”으로 표시됐다.

반면 `regression.js:239-245`의 `bottleneckHints`는 브래킷 방식으로 키를 조회하기 때문에 정상 작동했다. 이 때문에 같은 리포트 안에서 병목 설명은 “CPU throttling 발생”이라고 표시하면서, 회귀 비교 표는 “현재 값 없음”이라고 표시하는 모순도 발생했다.

**해결 내용**

`pick()`이 남은 경로 전체와 일치하는 키가 있으면 그 키를 먼저 사용하도록 수정했다.
`performance/tools/test/regression.test.js`에 회귀 테스트도 추가했다.

문제가 발생했던 normal-day 실행을 다시 분석한 결과는 다음과 같다.

- skipped: 25개 → 0개
- throttling 및 Hikari 관련 게이트: 총 6건이 정상적으로 FAIL 처리

**남은 작업**

이미 저장된 과거 실행 결과에는 잘못된 판정이 그대로 남아 있다. 필요한 경우 다음 명령으로 다시 판정해야 한다.

```bash
node tools/collect.js --all --force --no-wait
```

### T-02. 부하 조건이 다른 실행을 기준선으로 선택함 — 상태: 해결 (2026-08-09) / **후속 보강 2026-08-13**
> **2026-08-13 보강 — 조건이 "선언된 의도"를 다 담지 못하던 구멍 두 개를 막았다.** S-03 수정
> 도중 드러났다: 샘플러(`scripts/lib/sampling.js`)를 바꿔 트래픽 분포가 완전히 달라졌는데도
> 옛 실행이 `exact` 비교 가능으로 판정됐다. T-02가 만든 조건 표는 정상 작동했고, **조건 값
> 자체가 변화를 반영하지 못한 것**이 원인이다.
>
> **(A) 스크립트 지문 범위 확대.** `tools/perf-run.js`의 `scriptVersion()`이 진입 파일 하나만
> 해싱했다. 트래픽 형태를 정하는 코드는 진입 파일이 아니라 공용 모듈이라, `sampling.js`를
> 바꿔도 `scenarios/normal-day.js`의 해시는 그대로였다. 이제 진입 파일 + `TRAFFIC_SHAPING_FILES`
> (`workload.js`·`data.js`·`sampling.js`)를 경로와 함께 해싱한다. 등급은 **degrading 유지** —
> blocking으로 올리면 부하 코드를 손볼 때마다 이력이 끊겨 추세 분석이 상시 리셋된다.
>
> **버린 대안 ① `scripts/lib/` 디렉터리 전체 해싱.** 구현은 가장 쉽지만 `config.js`·`session.js`·
> `summary.js`처럼 부하 형태와 무관하게 자주 바뀌는 파일이 섞여 거의 모든 실행이 `degraded`가
> 된다. 경고가 상시 켜지면 아무도 안 보므로 장치가 사실상 사라진다.
> **버린 대안 ② import 그래프 정적 분석.** 가장 정확하지만 k6 ESM 그래프를 Node에서 파싱해야
> 해 비용이 크다. 목록 관리 부담은 `fingerprint.test.js`의 존재 검사로 대신한다.
>
> **(B) 데이터셋 조건에 생성 지문 추가.** `dataset` 조건이 프로파일 이름(`"large"`) 문자열
> 하나였다. 시드를 재생성해도 이름은 그대로라 **분포가 달라진 데이터셋이 옛 실행과 blocking
> 검사를 통과**했다. 이제 `{profile, fingerprint}` 객체이며, `datasets/seed.js`가 생성 시점에
> `generated/<profile>/meta.json`을 남기고 `perf-run.js`가 읽어 싣는다. 지문은 생성기 코드
> (`seed.js`+`sampling.js`) · 프로파일 파라미터 · **실제 생성 개수**를 해싱한다.
>
> **생성 시각은 일부러 뺐다.** 같은 생성기·같은 프로파일로 재시드하면 LCG 시드가 고정이라
> 통계적으로 동일한 데이터가 나온다. 시각을 넣으면 재시드할 때마다 기준선이 전멸해, 막으려던
> 것과 무관하게 비교가 끊긴다. 반대로 시드가 부분 실패하면 생성 개수가 달라져 지문이 바뀐다 —
> 그건 실제로 다른 데이터셋이 맞다(과거 실측: 500건 목표에 187건).
>
> **왜 k6가 아니라 Node에서 읽는가:** k6의 `open()`은 파일이 없으면 예외를 던져 init 컨텍스트
> 전체를 죽인다. 이 변경 이전에 만든 데이터셋(`meta.json` 없음)으로도 실행은 되어야 하므로,
> 존재 확인이 가능한 `perf-run.js` 쪽에서 읽어 env로 넘긴다.
>
> `conditions.js`의 `SCHEMA_VERSION`을 1→2로 올렸다. `dataset`은 blocking이라 `seriesHash`에
> 들어가는데, 값 형태가 바뀌었으므로 과거 계열과 섞이면 추세 그래프에서 지문 도입 시점이
> 성능 급락으로 보인다.
>
> **검증(시뮬레이션 실측).** 지문 없는 과거 실행 3건 + 재생성 후 첫 실행으로 `findBaseline()`을
> 돌렸다. 기준선 `null`, `hadPriorCandidates: true`(→ `incomparable`, "첫 실행" 오보 없음),
> 탈락 3건, 사유에 blocking(`데이터셋: large (지문 없음) → large (sha256:...)`)과
> degrading(`부하 스크립트: ... → ...`)이 **둘 다** 기록됐다. 계열 해시도 갈라졌다.
> 두 번째 실행은 다시 `exact`, 그 뒤 스크립트만 바꾼 실행은 `degraded`로 기준선을 유지했다.
> `tools/test/fingerprint.test.js` 12건 추가, 전체 195건 통과.
>
> **남은 부작용.** `repository.test.js`의 픽스처가 옛 문자열 형식을 쓰고 있어 함께 고쳤다.
> **저장된 과거 실행 전부가 새 실행과 비교 불가 상태가 된다** — 의도한 결과이며, S-03 수정
> 이후 새 기준선을 만드는 것이 전제다.
>
> **2026-08-13 추가 경계 — 지문은 실제 DB 동일성 증명이 아니다.** 위 기록은 생성 시각을 뺀
> 근거로 고정 LCG가 같은 데이터를 만든다고 설명했지만, E-41에서 전역 난수가 비동기 HTTP 완료
> 순서와 재시도 지터에 따라 서로 다른 작업에 배정됨을 확인했다. 또한 E-44처럼 현재 지문은
> 댓글·반응·스크랩·친구·채팅의 실제 성공 수량과 생성 뒤 DB 변화를 포함하지 않는다. 따라서
> 이 보강은 “생성 규칙과 일부 규모가 다르면 비교를 막는 장치”이지 “두 DB가 같다”는 보증이
> 아니다. 실제 동일 시작 상태는 검증된 스냅샷과 `datasetInstanceId`로 별도 해결해야 한다.

**문제**

`performance/tools/lib/repository.js:203-214`의 `findPrevious()`는 다음 세 조건만 사용해 기준선을 선택한다.

- 시나리오가 같은가
- 실행 환경이 같은가
- 이전 실행의 임계값 검사가 실패하지 않았는가

하지만 데이터 크기, 최대 VU, 실행 시간은 비교하지 않는다. `toIndexEntry()`가 `dataset`과 `vusMax`를 저장하고 있지만(124행, 130행), 기준선을 찾을 때는 사용하지 않는다.

**영향**

부하 규모가 전혀 다른 두 실행을 비교해 정상적인 차이를 성능 회귀로 오판할 수 있다. 반대로 더 약한 조건의 실행을 기준선으로 사용하면 실제 회귀를 과장하거나 잘못 해석할 수 있다.

**근거**

large 데이터셋, 200 VU, 1650초로 실행한 normal-day 결과가 다음 실행을 기준선으로 선택했다.

- 실행 ID: `normal-day-2026-08-04T06-38-42`
- 데이터셋: small
- 최대 VU: 15
- 실행 시간: 545초

리포트는 p95가 101ms에서 60001ms로 증가했다고 보고했다. 하지만 현재 실행은 기준선보다 부하가 약 13배 크고 데이터도 약 100배 많아 직접 비교할 수 있는 조건이 아니었다.

**해결 내용**

원인을 “필터에 조건 두 개가 빠졌다”가 아니라 **서로 다른 두 질문이 하나로 뭉뚱그려져 있었다**고 정리했다.

- 시간축 질문: 이력상 직전 실행은 무엇인가
- 실험 설계 질문: 이 실행의 대조군으로 유효한 실행은 무엇인가

기존 `findPrevious()`는 앞의 질문만 답하면서 뒤의 질문은 “시나리오가 같으면 조건도 같겠지”라고 가정하고 있었다.

그래서 **실행 조건(conditions)을 일급 개념으로 분리**해 `performance/tools/lib/comparability.js`를 새로 만들었다. 이 파일의 `CONDITIONS` 표 한 곳에 조건을 선언하면 기준선 선택, 리포트 표시, 추세 계열 분리가 모두 따라온다. 조건이 하나 늘 때마다 판정 엔진에 분기를 덧대지 않아도 된다.

조건마다 불일치의 성격이 다르므로 **등급(materiality)** 을 두 가지로 나눴다.

| 등급 | 의미 | 처리 |
|---|---|---|
| `blocking` | 수치가 무의미해짐 | 기준선 자격 박탈, 상대 비교 생략 |
| `degrading` | 수치가 의심스러움 | 비교는 하되 경고 표시, FAIL을 WARN으로 완화 |

데이터셋이 다른 두 실행의 p95를 나란히 놓는 것은 “믿을 수 없는 비교”가 아니라 애초에 비교가 아니다. 반면 부하 스크립트 지문이 바뀐 경우는 대개 주석 한 줄 수정이고 수치는 대체로 유효하다. 그래서 앞의 넷은 `blocking`, 스크립트 지문은 `degrading`으로 뒀다(`comparability.js:54-89`).

기준선 탐색 함수는 `findPrevious()`에서 `findBaseline()`으로 교체했다(`repository.js:231`). 이 함수는 “직전 실행”이 아니라 **비교 가능한 가장 최근 실행**을 고르고, 탈락한 후보와 그 사유를 함께 돌려준다. 조건이 엄격해지면 기준선 없는 실행이 흔해지는데, 그때 필요한 것은 침묵이 아니라 “8월 4일 실행이 있었지만 데이터셋이 small에서 large로 바뀌어 비교하지 않았다”는 문장이기 때문이다.

함께 처리한 것은 다음과 같다.

- **부하 프로파일을 실제로 기록하기 시작했다.** k6의 `handleSummary(data)`가 받는 `data.options`에는 `summaryTrendStats`, `summaryTimeUnit`, `noColor` 세 개뿐이고 부하 설정이 들어 있지 않다(실측 확인). 대신 k6가 해석을 끝낸 선언 값인 `exec.test.options.scenarios`를 저장한다.
- **`baselineStatus`를 신설했다**(`regression.js:259`). 값은 `compared`, `incomparable`, `first-run` 셋이다. 기준선이 없다는 사실이 조용한 PASS로 새면 고치기 전보다 나쁘기 때문에 상태를 명시한다. 이때도 절대 게이트는 계속 동작한다.
- **추세 계열을 분리했다.** `recentRuns()`가 시나리오 이름만으로 묶고 있어서 small/15VU 실행과 large/200VU 실행이 한 선에 섞이고 있었다. 기준선 선택과 똑같은 결함이 추세 그래프에도 있었던 것이다. 이제 `seriesHash`로 계열을 가른다(`repository.js:274-281`).
- `analyze()`에 있던 `scriptVersion` 사후 강등 특수 분기를 위 등급 메커니즘으로 흡수했다.

**선택하지 않은 대안**

가장 먼저 떠오르는 방법은 k6 요약의 `vusMax`를 조건에 넣는 것이었지만 **버렸다.** `vusMax`는 설정값이 아니라 `vus_max` 지표의 최대치, 즉 **관측값**이기 때문이다.

`ramping-vus` 시나리오에서는 설정한 피크와 값이 같아 문제가 드러나지 않는다. 그러나 `scenarios/breakpoint.js`가 쓰는 `ramping-arrival-rate`는 목표 도착률을 유지하려고 VU를 동적으로 할당한다. 즉 **서버가 느려질수록 `vusMax`가 올라간다.** 이것을 조건으로 쓰면 다음 순서가 만들어진다.

```text
진짜 회귀 발생 → vusMax 상승 → 기준선 부적격 → 상대 비교 생략 → 게이트 통과
```

회귀가 심할수록 검사에서 면제되는, 스스로를 무력화하는 필터가 된다. 그것도 한계 탐색이 목적인 유일한 시나리오에서 그렇게 된다. 같은 이유로 `durationSec`(실제 수행 시간)도 조건에서 뺐다. 조건은 선언된 `stages`이고, 실제로 얼마나 걸렸는지는 결과다.

**검증**

- 회귀 테스트로 고정했다: `performance/tools/test/comparability.test.js`, `repository.test.js`, `regression.test.js`
- 실측 확인 결과는 다음 세 가지다.
  - 같은 조건 → 정상 비교
  - 부하 또는 데이터셋 변경 → 상대 비교 생략 + 사유 표시
  - 스크립트만 변경 → 경고 후 비교

**남은 작업**

- **데이터셋 시드 매니페스트 해시**가 없다. 프로파일 이름만으로는 다른 `seed.js`가 만든 `large`를 구분하지 못한다.
- **인프라 스펙 해시**가 없다. `docker-compose.seed.yml`의 HikariCP 50, `sync_binlog=0` 설정을 되돌리지 않은 채 측정하는 실패 모드를 잡지 못한다.

둘 다 `comparability.js`의 `CONDITIONS` 표에 한 줄씩 추가하면 된다.

저장된 과거 실행은 조건 정보가 없어 기준선 후보에서 제외된다. 이는 의도된 동작이다(사용자 결정).

### T-03. `--warmup`이 인프라 지표에만 적용됨 — 상태: **해결** (2026-08-12)

> warmup/measure/rampdown을 k6 실행 계획의 1급 개념으로 승격했다. 신규
> `performance/scripts/lib/phases.js`(`buildPhasePlan`/`phaseAt`/`stagesFor`/`scopeThresholds`
> 등 순수 함수)를 각 시나리오가 가져다 `run.phasePlan`을 구성하고,
> `scripts/lib/config.js`의 `tags()`/`check()`가 `exec.instance.currentTestRunDuration`
> 기준으로 요청마다 `phase` 태그를 다시 계산해 붙인다(캐시하지 않음 — iteration이 경계를
> 넘는 경우 대응). `scripts/lib/summary.js`는 `k6.overall`을 `k6.all`(전체 구간, 진단용)과
> `k6.phases.{warmup,measure,rampdown}`(phase 태그로 분리 추출, 게이트용)으로 나눠 기록한다.
> `performance/tools/collect.js`의 `measureWindow()`는 `record.run.phasePlan`
> (`measureStartOffsetSec`/`measureSec`)만으로 Prometheus 창을 계산한다 — CLI `--warmup`
> 인자를 더 이상 받지 않는다(`parseArgs`에서 제거). `perf-run.js --warmup <sec>`는 이제
> collect.js가 아니라 k6에 `-e WARMUP=<sec>`로 직접 전달되어 시나리오의 ramp-up stage
> 길이 자체를 바꾼다. `regression/rules.json`의 `k6.overall.*` 7개 키를
> `k6.phases.measure.*`로 옮겨 Node 회귀 게이트도 같은 구간을 보게 했다.
> `tools/lib/conditions.js`에 `measurementProfile`(mode/warmupSec/measureSec/rampdownSec/
> gatePhase) blocking 조건을 추가해, 측정 구간 설계가 다른 실행끼리는 기준선으로 못 쓰게 막았다.
>
> **고민한 대안과 버린 이유**
> (a) k6 지표도 collect.js에서 시간 기준으로 재계산 — k6 raw metric은 태그별로만
> 분리되지 시각 기준 슬라이싱을 지원하지 않아 불가능. (b) 모든 시나리오를 phase별로
> 별도 k6 scenario로 분리(cache-warm 방식) — 일반 회귀 시나리오는 VU별 쿠키 세션
> 연속성이 깨져서 기각, cache-warm처럼 애초에 phase 간 세션 연속성이 필요 없는 경우만
> 예외로 허용했다. (c) k6 builtin `iterations`에 동적 phase 태그를 실어 TPS를 phase별로
> 내는 방법 — k6가 iteration 완료 시점에 직접 기록하는 값이라 스크립트가 태그를 못
> 붙인다. 대신 `workload.js`에 `phase_iterations` 커스텀 Counter를 추가해 iteration
> 끝에서 직접 세는 방식으로 대체했다.
>
> **검증**: `cd performance && node --test tools/test/*.test.js` — phases.js 순수 로직
> 19개, `metricsByPhase`(S-17 회귀 포함) 8개, collect.js `measureWindow` 8개(rampdown
> 제외·조기 종료 clamp·재수집 재현성 포함), comparability `measurementProfile` 10개 등
> 총 100개 테스트 통과. k6 바이너리가 이 환경에 없어 실제 부하 실행 검증은 못 했다 —
> 아래 T-03 관련 후속 작업 참고.
>
> **남은 부작용/후속 작업**: 저장된 과거 `run.json`은 `k6.overall`/`infra.window.
> warmupExcludedSec` 스키마 그대로 남는다(재해석하지 않음) — `k6.phases.measure`가
> 없으므로 `pick()`이 새 rules.json 키를 못 찾아 SKIP되고, 재수집(`--force`) 해도
> `run.phasePlan`이 없어 그 사실이 그대로 유지된다(의도된 동작). 실제 k6 실행 환경에서
> `k6 inspect`/실측 실행으로 phase 태그가 기대대로 붙는지 확인이 아직 안 됐다.
>
> **후속 수정 (2026-08-13): threshold 평가 범위를 measure 구간으로 일원화.**
> 최초 구현은 `PHASED_THRESHOLDS`에 `DEFAULT_THRESHOLDS`(태그 없는 SLO)를 그대로 얹어서,
> 같은 기준이 전체 구간과 measure 구간에 이중으로 걸렸다. warmup 구간의 느린 응답 하나로
> measure 결과와 무관하게 k6가 FAIL을 내는 상태였고, 이는 warmup을 선언한 목적 자체를
> 무효로 만든다. 시나리오별 커스텀 threshold(`name:login`, `op:write` 단독 abortOnFail 등)도
> 같은 이유로 전체 구간을 평가하고 있었다 — 램프업 중 로그인 폭주로 조기 중단될 수 있었다.
>
> 수정 내용: `config.js`에 기준값만 담은 `COMMON_SLO_THRESHOLDS`를 분리하고,
> `DEFAULT_THRESHOLDS`(= 분해축 + 공통 SLO, 전체 구간)와 `PHASED_THRESHOLDS`(= 분해축 +
> phase 진단축 + measure로 스코프된 공통 SLO)가 그 하나의 정의에서 갈라져 나오게 했다.
> `PHASED_THRESHOLDS`에는 태그 없는 SLO가 더 이상 없다. 시나리오 고유 기준은 새 헬퍼
> `measureOnly()`(= `scopeThresholds(t, {phase:'measure'})`)를 통과시켜 9개 phase
> 시나리오(cache-warm·chat-heavy·exam-week·notification-heavy·peak-hour·read-heavy·
> registration-day·soak·write-heavy) 전부를 measure 스코프로 옮겼다. 단독 스크립트 13개와
> 진단 시나리오 5개는 `DEFAULT_THRESHOLDS`를 그대로 써서 전체 구간 판정을 유지한다.
>
> 덮어쓰기 성립 여부를 확인했다: `buildSelector()`가 태그 키를 정렬하므로 시나리오가 만든
> `http_req_failed{phase:measure}`·`http_req_duration{op:write,phase:measure}`는 공통 게이트와
> 문자열이 동일한 키다. 따라서 시나리오 값이 공통 값을 대체하며 한 대상에 두 기준이
> 겹치지 않는다(peak-hour 2% vs 공통 1% 같은 모순 제거). `chat_ws_rtt`처럼 커스텀 메트릭도
> `chat-ws.js`가 `phaseTag()`로 phase를 실어 보내므로 서브메트릭이 실제로 존재한다.
>
> **abortOnFail 평가 시점도 함께 옮겼다.** k6의 `delayAbortEval`은 threshold 스코프와 무관하게
> 테스트 시작부터 세므로, measure로 스코프해도 지연이 warmup보다 짧으면 표본 몇 건으로 평가가
> 시작된다. 새 헬퍼 `abortDelayAfterMeasure(PLAN, N)`이 `measureStartOffsetSec + N`을 계산해
> 넘긴다(chat-heavy 7분, peak-hour 5분, registration-day 4분, soak 15분, write-heavy 6분 —
> 전부 "measure 시작 + 원래 관측 시간"). 기준 수치 자체는 하나도 바꾸지 않았다. 진단 시나리오
> 5개(stress/spike/breakpoint/chaos/failover)의 중단 정책은 손대지 않았다.
>
> **threshold 정의를 `scripts/lib/thresholds.js`로 분리했다** — config.js는 `k6/http`를
> import해서 Node 테스트가 로드할 수 없다. 순수 데이터만 옮기고 config.js가 재수출하므로
> 호출부(시나리오·스크립트 30여 개)는 그대로다. 새 테스트 `tools/test/thresholds.test.js`(19건)와
> `tools/test/scenario-thresholds.test.js`(7건, 시나리오 소스 감사)를 추가했다.
>
> **k6 실측으로 검증했다** (k6 v2.1.0, [[k6-binary-path-workaround]] 경로). `k6 inspect`로
> 시나리오 9개의 해석된 threshold 키에 bare 공통 SLO가 하나도 없고 게이트가 전부
> `{...,phase:measure}`임을 확인했다. 임시 프로브 스크립트와 로컬 스텁 서버로 판정 4사례를
> 실행했다: warmup 불량+measure 정상 → PASS(exit 0), warmup 정상+measure 불량 → FAIL(exit 99),
> cold-start 전 구간 불량 → FAIL, 단독 스크립트 전 구간 불량 → FAIL(bare 키 위반).
>
> 그 과정에서 두 가지 실제 동작을 발견해 반영했다.
>   1. 진단축 `http_req_failed{phase:X}: rate<1`은 warmup 요청이 **전부** 실패하면 rate가
>      정확히 1이 되어 FAIL 한다 — 집계 축이 판정에 끼는 셈이라 `rate<=1`로 고쳤다
>      (`tools/lib/report.js`의 느슨한 threshold 필터 정규식도 함께 갱신).
>   2. k6는 **등록되지 않은 메트릭**에 걸린 threshold를 만나면 실행을 시작하지 못하고 중단한다
>      (`invalid threshold defined on phase_iterations{phase:measure}`). PHASED_THRESHOLDS를
>      쓰는 시나리오는 그 Counter를 만드는 `scenarios/lib/workload.js`를 반드시 로드해야 한다는
>      뜻이라, 감사 테스트로 고정했다.

**문제**

`performance/tools/collect.js:200-204`는 warmup 시간을 Prometheus 조회 구간에서만 제외한다. k6의 p95와 오류율은 warmup을 포함한 전체 실행 구간으로 계산한다.

따라서 같은 리포트 안에서도 다음 두 종류의 지표가 서로 다른 시간대를 설명한다.

- k6 지표: warmup을 포함한 전체 구간
- 인프라 지표: warmup을 제외한 구간

**영향**

서로 다른 시간 범위에서 측정한 값을 같은 실행 결과처럼 비교하게 된다.

또한 warmup 값은 `infra.window`에만 저장되고 인덱스와 기준선 조건에는 포함되지 않는다. warmup 길이가 다른 실행끼리 비교하면 `gc.count`나 `slowQueries`처럼 구간 누적값을 사용하는 지표가 시간 차이만큼 증가하거나 감소한 것처럼 보일 수 있다.

**필요한 조치**

k6 지표와 인프라 지표가 같은 분석 구간을 사용하도록 맞춰야 한다. 기준선을 선택할 때도 warmup 조건이 같은지 확인해야 한다.

### T-04. 한 번씩만 실행한 결과를 비교하며 타임아웃 상한도 인식하지 못함 — 상태: 미해결

이 항목에는 서로 연결된 두 가지 문제가 있다.

#### 문제 1: 반복 실행 없이 한 번의 결과만 비교함

현재 판정은 현재 실행 한 번과 기준선 실행 한 번을 비교한다. 실행 편차나 분산을 측정하지 않는다.

`performance/regression/rules.json:19`에는 “반복 실행 편차 근거”라는 설명이 있지만 실제 구현은 없다.

노이즈 하한도 상대 비율이 아니라 절대값으로 적용한다. 요청량이 적은 시나리오에서는 큰 비율의 변화도 작은 절대 변화로 판단해 무시할 수 있다.

**근거**

실제 실행에서 RPS가 17.3% 감소했지만 다음과 같은 이유로 PASS 처리됐다.

```text
변화 0.92 < 하한 1.00
```

#### 문제 2: 타임아웃 때문에 잘린 값을 실제 지연 시간처럼 비교함

p95가 `60000.96ms`로 표시된 사례가 있다. 이는 실제 응답 시간이 아니라 k6의 60초 타임아웃 상한에 걸려 잘린 값이다.

현재 게이트는 이 값이 측정 상한이라는 사실을 모른다. 이후 시스템이 더 느려져도 결과가 계속 약 60초로 표시되므로 변화율은 0%에 가까워지고 PASS할 수 있다.

같은 실행에서 다음 신호도 함께 나타났다.

- `errorRate = 0.558`
- `checkRate = 0.443`

두 지표를 함께 보면 요청 절반 이상이 정상 처리되지 않았음을 알 수 있지만, 현재 판정 로직은 이를 타임아웃 검열 신호로 사용하지 않는다.

**필요한 조치**

반복 실행 결과로 정상 편차 범위를 계산해야 한다. 타임아웃 상한에 걸린 지연 시간은 일반적인 p95 변화율로 비교하지 말고 오류율, checkRate와 함께 별도의 실패 상태로 판정해야 한다.

### T-07. 스크립트 버전 판정이 실제 변경 범위를 제대로 반영하지 못함 — 상태: 미해결

이 항목에도 반대 방향의 두 가지 문제가 있다.

#### 문제 1: 실제 요청 동작이 바뀌어도 버전이 같다고 판단할 수 있음

`performance/tools/perf-run.js:88-95`는 시나리오 진입 파일 하나만 SHA-256으로 해시한다.

하지만 실제 요청 구성과 실행 동작은 다음 공통 파일에도 들어 있다.

- `performance/scripts/lib/session.js`
- `performance/scripts/lib/data.js`
- `performance/scripts/lib/config.js`
- `performance/scenarios/lib/workload.js`

이 파일들이 바뀌어도 `scriptVersion`은 바뀌지 않는다. 따라서 서로 다른 동작의 실행 결과를 같은 버전으로 비교할 수 있다.

#### 문제 2: 진입 파일이 조금만 바뀌어도 실패 판정이 약해짐

`performance/tools/lib/regression.js:183-188,200`은 `scriptChanged`가 참이면 FAIL을 WARN으로 낮춘다.

진입 파일에 주석 한 줄만 추가해도 스크립트 변경으로 판단한다. 이 상태에서는 실제 성능 회귀가 발생해도 빌드가 게이트를 통과할 수 있다. 이를 강제로 실패 처리할 `--strict` 같은 옵션도 없다.

**필요한 조치**

실제 실행에 영향을 주는 모든 파일을 버전 계산에 포함해야 한다. 단순히 스크립트가 바뀌었다는 이유만으로 모든 실패를 WARN으로 낮추지 말고, 필요하면 엄격하게 판정할 수 있는 정책을 제공해야 한다.

### T-08. 필수 지표를 수집하지 못해도 테스트가 통과함 — 상태: **해결** (2026-08-13)

> **무엇을 어떻게 고쳤나 — 2층 구조**
>
> *1층 (`scripts/lib/phases.js`의 `metricsByPhase`)*: 표본이 0건인 phase의 통계를 `null`로
> 되돌린다. 판정 근거는 값이 아니라 표본 수다 — `http_reqs{phase:X}` 서브메트릭이 요약에
> 존재하고 그 `count`가 0이며, iteration 수도 0/미집계일 때만 결측으로 본다. 그때
> `avg/min/med/max/p90/p95/p99`와 `rps·errorRate·checkRate`를 전부 `null`로 만들고,
> `httpReqs`(0)와 `iterations`(null)는 결측의 증거로 남긴다.
>
> *2층 (`tools/lib/regression.js`의 `analyze`)*: `null`을 세 갈래로 나눈다. 새 함수
> `isApplicable()`이 "이 실행에 해당 없는 규칙"(진단 시나리오의 measure 규칙)을 먼저
> 걸러내고, `isRequired()`가 나머지를 필수/참고로 가른다. 결과로
> `measurementStatus`(MEASURED/PARTIAL/UNMEASURED)와 `missingRequired`·`missingOptional`·
> `notApplicable`을 `verdict`와 **별도 필드로** 반환한다. `collect.js`가 이미 계산해 두고
> 리포트 표시에만 쓰던 `window.incomplete`도 여기서 PARTIAL 강등 조건으로 연결했다.
>
> *필수의 정의*: `gate: true`를 그대로 쓴다. 면제 조건은 둘 — measure 게이트는
> `phasePlan.gatePhase === 'measure'`인 실행에서만, 인프라 게이트는 `rules.json`의 새
> `requirements.infraRequiredEnvironmentPrefixes`(`["perf"]`)에 prefix가 걸리는 환경에서만
> 필수다. `validateRequirements()`가 그 블록의 형식을 검증한다.

> *종료 코드*: `collect.js`에 3(측정 불가)을 신설했다. 게이트 회귀(1)와 동시에 성립하면

> 수집 종료 코드를 그대로 전달하므로 수정하지 않았다.
>
> *파급*: `repository.js`의 인덱스 엔트리에 `measurementStatus`를 넣고 `findBaseline()`이
> `UNMEASURED` 실행을 기준선 후보에서 제외한다. 리포트는 요약 지표보다 위에 측정 상태
> 배너를 그리고(`sectionMeasurement`), "평가 불가" 집계를 필수/참고/해당없음 셋으로 쪼갠다.
>
> **고민한 대안과 버린 이유**
>
> - *`rules.json`에 독립 `required` 필드를 추가한다*(원래 계획, `ROADMAP.md`):
>   버렸다. `gate:true`가 이미 "이 지표가 나쁘면 빌드를 세운다"는 선언이고, 그 지표가 없으면

>   32개 규칙 전부에 유지해야 할 필드가 하나 늘어난다. 예외가 실제로 생기면 그때
>   `required:false` 오버라이드를 더하는 편이 낫다.
> - *`regression.js`에서 `null`만 검사한다*(첫 설계): **실측으로 기각했다.** k6는 threshold가
>   참조한 서브메트릭을 표본이 0건이어도 0으로 채워 요약에 실어 준다. 그래서 measure 구간이
>   비면 값이 `null`이 아니라 0으로 들어오고, `p95:0`은 절대 게이트(500ms 상한)를 통과하며
>   기준선 대비로는 "100% 개선"으로 읽힌다. 값만 보는 층에서는 이걸 가려낼 수 없어서 1층이
>   필요했다.
> - *표본 0건이면 phase 버킷 자체를 만들지 않는다*: 버렸다. 버킷이 없으면 "그 구간을
>   선언하지도 않았다"와 "선언했는데 못 쟀다"가 다시 구별되지 않는다. 버킷은 만들되 통계만
>   `null`로 두어, 저장된 `run.json`만 보고도 결측을 재구성할 수 있게 했다.
> - *`http_reqs` 서브메트릭이 없으면 결측으로 본다*: 버렸다. 서브메트릭 부재는 "0건"이 아니라
>   "그 축을 선언하지 않았다"는 뜻이다. 기존 테스트(`phases.test.js`)가 이 구분을 바로
>   잡아냈다. 적극적 증거(축이 존재하고 count가 0)가 있을 때만 결측으로 판정한다.
> - *`iterations` 없이 `http_reqs`만 본다*: 버렸다. WebSocket 위주 구간은 HTTP 요청이 0이어도
>   iteration이 실제로 돈다. 한쪽만 보면 정상 구간을 결측으로 오판한다.
> - *진단 시나리오의 measure 결측을 "참고 결측"으로 센다*: 버렸다. 그러면 진단 실행이 항상
>   PARTIAL로 표시돼, 정작 익스포터가 죽었을 때의 PARTIAL 신호가 묻힌다. `isApplicable()`로
>   "해당 없음"을 세 번째 분류로 분리한 이유다.
> - *환경을 정확히 일치로 판정한다*: 버렸다. 실제 이력의 환경 값이
>   `perf`·`perf-mi-smoke`·`perf-mi-before`·`perf-s02-ab`라, 정확히 일치로 걸면 변형 셋이 전부

> - *`UNMEASURED`를 `verdict`의 네 번째 값으로 만든다*: 버렸다. "서버가 느리다"와 "재지
>   못했다"는 고칠 대상도 고칠 사람도 달라서, 한 필드에 넣으면 다시 섞인다. 종료 코드도

> - *게이트 회귀(1)를 측정 불가(3)보다 우선한다*: 버렸다. 게이트 회귀는 측정을 고치면 다음

>   모든 실행의 판정이 계속 무의미해진다. 계통적 고장을 먼저 알린다.

>
> ⑷ *종료 코드 end-to-end*. 현행 스키마의 합성 런 2개를 만들어 `collect.js`를 끝까지

**문제**

따라서 “지표가 정상 범위에 있다”와 “지표를 아예 측정하지 못했다”를 구분하지 못한다.

**실패 시나리오**

`performance/tools/collect.js:212-214`에서 Prometheus에 연결하지 못하면 `infra.flat = {}`가 된다. 모든 인프라 지표가 결측되지만 결과는 다음처럼 처리된다.

- 인프라 규칙: SKIP
- 전체 판정: PASS
- 프로세스 종료 코드: 0

Prometheus 자체가 죽거나 개별 익스포터 하나가 멈춘 경우에도 같은 문제가 생길 수 있다.

**영향**

성능 게이트가 필요한 데이터를 전혀 수집하지 못한 상태에서도 정상 결과처럼 통과한다.

**필요한 조치**

게이트에 필요한 지표가 없으면 단순 SKIP이 아니라 “평가 불가” 상태로 처리해야 한다. 필수 지표와 선택 지표를 구분하고, 필수 지표 결측 시 어떤 종료 코드를 반환할지 정책을 정해야 한다.

### T-14. `perf-run`이 잘못된 실행 결과를 수집할 수 있음 — 상태: 해결

**기존 문제**

`performance/tools/perf-run.js:173-177`은 실행 ID를 전달하지 않고 `collect`를 호출했다. `collect.js:248-250`은 pending 목록의 마지막 항목을 선택했고, `repository.js:59-67`은 목록을 알파벳순으로 정렬했다.

결국 가장 최근 실행이 아니라 이름이 알파벳순으로 마지막인 실행을 선택했다.

예를 들어 수집에 실패한 `timetable-*` pending 실행이 하나 남아 있으면, 이후 auth, boards, comments, posts 실행을 수집할 때도 계속 그 timetable 실행을 선택할 수 있었다. 두 실행을 동시에 수행해도 같은 충돌이 발생할 수 있었다.

**해결 내용**

- `perf-run` 실행 전후의 스테이징 목록 차이로 현재 실행 ID를 식별
- 식별한 실행 ID를 `collect`에 직접 전달
- k6가 급사해 결과 파일이 없으면 수집을 건너뛰고 실패 종료
- 인자 없이 `collect`를 실행할 때는 알파벳순이 아니라 파일 수정 시간 기준으로 최신 항목 선택

### T-15. `index.json` 손상 시 실행 이력이 조용히 사라질 수 있음 — 상태: 해결

**기존 문제**

`performance/tools/lib/repository.js:45-48`은 `index.json`을 바로 덮어썼다. 임시 파일을 완전히 쓴 뒤 교체하는 원자적 저장 방식을 사용하지 않았다.

또한 `saveRun()`은 인덱스 전체를 읽고 수정한 다음 다시 쓰는 방식이었다. 저장 도중 프로세스가 종료되거나 여러 프로세스가 동시에 접근하면 파일이 일부만 기록될 수 있었다.

`loadIndex()`는 JSON 파싱에 실패하면 오류를 알리지 않고 다음 값을 반환했다.

```json
{ "runs": [] }
```

그 뒤 `saveRun()`이 실행되면 손상된 인덱스를 실행 한 개만 들어 있는 새 인덱스로 덮어썼다. 그 결과는 다음과 같다.

1. 이전 실행 이력이 사라짐
2. `findPrevious()`가 기준선을 찾지 못함
3. 현재 실행을 “첫 실행”으로 처리
4. 회귀 게이트가 비교 없이 통과

**해결 내용**

- JSON을 임시 파일에 먼저 기록한 뒤 rename하는 원자적 저장 방식 적용
- 파일이 없는 정상적인 빈 이력과 JSON이 손상된 상태를 구분
- 파일이 손상되면 예외와 rebuild 안내를 표시
- `history.js --rebuild` 복구 경로가 작동하는지 확인

실행 번호의 동시성 및 재번호 문제는 T-28에서 별도로 다룬다.

### T-16. 수집 실패가 성공 종료 코드로 바뀔 수 있음 — 상태: 해결

### T-29. MySQL 락·트랜잭션·풀스캔 지표가 수집 카탈로그에서 빠져 있음 — 상태: 미해결

추가 조사일: 2026-08-06

**문제**

`performance/tools/lib/metrics-catalog.js:221`의 MySQL 그룹에는 다음 10개 지표만 등록돼 있다.

- `maxConnections`
- `slowQueries`
- `qps`
- `qpsMax`
- `bufferPoolHitPct`
- `rowsReadPerSec`
- `abortedConnects`
- `threadsRunning`

최초 리뷰 기록에는 9개로 적혀 있었으나 실제 카탈로그 항목은 10개다(코드로 재확인). `gaugeStats()`가 만드는 avg·max·p95까지 세면 평면 키는 16개다. 구현을 수정할 때 카탈로그의 실제 항목 수도 함께 확인해야 한다.

Prometheus에는 이보다 많은 MySQL 지표가 이미 들어오고 있다. 익스포터 설정을 바꾸거나 새로운 수집 경로를 만들 필요는 없다. 현재는 지표 카탈로그에 등록하지 않아 보고서에서 사용하지 못하는 상태다.

**왜 중요한가**

`performance/bottlenecks/` 의 병목 카탈로그는 BTL-003, 즉 인기글 카운터의 락 경합을 “확정” 상태로 기록하고 있으며 실측 데드락도 재현됐다고 설명한다.

하지만 현재 등록된 `innodbRowLockWaits`는 `Innodb_row_lock_current_waits`를 사용한다. 이 값은 조회하는 순간에 락을 기다리는 트랜잭션 수만 보여주는 스냅샷이다. 테스트 구간 전체에서 락 대기가 얼마나 발생했는지, 총 대기 시간이 얼마였는지는 알 수 없다.

따라서 현재 도구만으로는 이미 확인한 락 병목을 제대로 측정할 수 없다. EXP-003을 수행할 때 필요한 판단 근거가 부족하다.

**실측 확인 결과**

다음 PromQL이 실제 Prometheus에서 값을 반환하는 것을 2026-08-06에 확인했다.

| `mysql.rowLockTimeMaxMs` | `max_over_time((mysql_global_status_innodb_row_lock_time_max)[$RANGE:])` | 가장 길었던 단일 락 대기 시간. 검증값: 84 |

### T-18. 일부 Prometheus 지표가 실제 상태와 다르게 표시될 수 있음 — 상태: 미해결

현재 PromQL에는 서로 다른 여섯 가지 문제가 있다. 이 때문에 보고서가 이벤트 수를 부정확하게 표시하거나, 짧은 부하 급증을 놓치거나, 정상 상태를 장애로 판단할 수 있다.

#### 문제 1: 누적 이벤트 수를 정확한 정수처럼 표시함

`increase(...[$RANGE])`는 조회 구간의 시작과 끝에 데이터가 부족하면 값을 외삽해 추정한다. 실제 카운터가 정수 단위로 증가하더라도 결과는 소수가 될 수 있다.

실제로 `slowQueries`가 `839.155…`로 계산된 사례가 있다. 이는 느린 쿼리가 정확히 839.155번 발생했다는 뜻이 아니다.

현재 보고서는 이 값을 실제 발생 횟수처럼 취급한다. 정확한 횟수가 아니라 구간 추정치라는 사실을 표시하거나, 표시 및 판정 방식을 조정해야 한다.

#### 문제 2: 테스트 중 짧게 발생한 피크가 전체 평균에 묻힘

`rate(...[$RANGE])`는 테스트 전체 구간의 초당 평균 증가율을 계산한다.

부하 테스트에는 보통 사용자를 서서히 늘리는 램프 구간이 포함된다. 짧은 시간 동안 CPU 사용량이나 요청량이 크게 증가해도, 나머지 시간이 낮은 부하였다면 전체 평균은 낮게 나온다.

피크를 계산하는 `*Max` 지표도 존재하지만 현재 게이트 규칙에서는 사용하지 않는다. 따라서 순간적인 병목을 놓칠 수 있다.

#### 문제 3: Prometheus 계산 간격 때문에 짧은 피크를 놓칠 수 있음

Prometheus는 원본 지표를 5초마다 수집하지만, 일부 서브쿼리는 기본 `evaluation_interval`인 15초 간격으로 계산된다.

5초 동안만 발생한 피크가 15초 계산 지점 사이에 있으면 최대값이나 p95가 실제보다 낮게 계산될 수 있다.

`cpu.cores.*` 지표에는 `rate[1m]`가 하드코딩돼 있다. 이 값은 `saturation.cpuPct`를 계산할 때 사용된다. CPU가 10초 동안 최대치에 도달해도 1분 평균에 희석되므로 짧은 CPU 포화를 놓칠 수 있다.

#### 문제 4: 컨테이너 이름이 환경에 따라 달라지면 지표가 모두 누락될 수 있음

컨테이너 쿼리는 이름이 정확히 `perf-app`인 컨테이너를 찾는다.

Docker Compose v2는 프로젝트 이름을 컨테이너 이름 앞에 붙일 수 있다. 실제 이름이 달라지면 쿼리가 대상을 찾지 못하고 관련 지표가 모두 `null`이 된다.

현재 판정 로직은 결측 지표를 SKIP한 뒤 전체 테스트를 PASS할 수 있다. 따라서 단순한 이름 차이 때문에 인프라 검사가 전부 비활성화될 수 있다.

또한 현재 `max()` 집계 방식은 컨테이너가 테스트 도중 재시작될 경우 재시작 전후의 카운터를 올바르게 합산하지 못할 수 있다.

#### 문제 5: 다른 MySQL 또는 Redis 서버의 지표가 섞일 수 있음

MySQL과 Redis PromQL에는 대상 `job`이나 `instance`를 제한하는 조건이 없다.

같은 Prometheus에 여러 MySQL 또는 Redis 익스포터가 연결돼 있으면 테스트 대상이 아닌 서버의 지표까지 결과에 섞일 수 있다. 보고서가 어느 서버의 상태를 나타내는지 보장할 수 없다.

쿼리에서 테스트 대상 익스포터를 명확하게 선택해야 한다.

#### 문제 6: Redis 요청이 없을 때 적중률을 0%로 표시함

`redis.hitRatioPct`는 분모가 0이 되는 것을 막기 위해 `clamp_min(x, 1)`을 사용한다.

캐시 요청이 한 번도 없으면 적중률을 계산할 수 없다. 하지만 현재 수식은 이 경우를 0%로 계산한다. 보고서만 보면 캐시 요청이 없었던 정상 상태를 “캐시 적중률 0%” 또는 “캐시 붕괴”로 오해할 수 있다.

트래픽이 없을 때는 0%가 아니라 “평가할 데이터 없음”으로 처리해야 한다.

### T-20. 서로 다른 두 개의 회귀 판정 시스템이 함께 존재함 — 상태: 해결

**기존 문제**

### T-27. 이력 추세 계산이 중요한 변화를 숨길 수 있음 — 상태: 미해결

**문제 1: 이전 중앙값이 0이면 추세를 표시하지 않음**

이전 실행들의 중앙값이 0일 때 추세 계산을 중단한다. 따라서 slow query가 0건에서 80건으로 증가하는 것처럼 중요한 변화가 추세에서 사라질 수 있다.

0을 분모로 비율을 계산할 수 없다는 이유는 있지만, 변화 자체를 숨기는 것은 적절하지 않다. 비율 대신 절대 변화 또는 별도 상태로 표시해야 한다.

**문제 2: 실행 조건이 다른 결과를 같은 추세로 묶음**

현재는 시나리오 이름만으로 실행을 그룹화한다. 데이터셋, VU, 환경이 다른 실행도 하나의 추세로 합쳐진다.

문서의 각주에서는 실행 조건 차이에 주의하라고 설명하지만 실제 계산은 이 조건을 구분하지 않아 설명과 동작이 일치하지 않는다.

### T-30. [HIGH] `repeatability.js`가 변동계수만 내고 추세를 검출하지 않음 — 상태: 미해결

> **2026-08-17 갱신 — 우선순위를 HIGH로 올린다.**
>
> 조건이 전혀 다른 두 세트에서 **모두** 강한 추세가 나왔다.
>
> | 세트 | 회차 | Spearman | 전체 변화 | 도구가 보고한 것 |
> |---|---|---|---|---|
> | 기준선 (08-16) | 5 | **+0.90** | +9.0% | `P95 CV = 3.12%` |
> | 진단 (08-17) | 8 | **−0.88** | −6.3% | `P95 CV = 4.26%` |
>
> **두 번 다 도구는 "이만큼 흔들렸다"고만 말했다.** 한 번은 계속 느려지고 있었고 한 번은
> 계속 빨라지고 있었는데, 어느 쪽도 보고서에 나타나지 않았다.
>
> 이건 표시 누락이 아니라 **판정 오류로 이어진다.** CV는 MDE의 입력이고 MDE는 "이 개선이
> 진짜인가"를 가르는 기준이다. 추세가 섞인 CV로 계산한 MDE는 틀린 값이다.
>
> 세트 2는 선형 추세보다 **계단**이 더 잘 맞았다(잔차 CV 4.26% vs 3.53%). 그러니 조치에
> 선형 추세 검출만 넣으면 부족하다 — **"이 세트는 무작위 표본이 아니다"를 알리는 것**이
> 목적이지 추세의 모양을 맞히는 것이 목적이 아니다.



**쉽게 말하면**

반복 측정 도구가 "얼마나 흔들렸나"만 말하고 **"한쪽으로 계속 갔나"는 말하지 않는다.**
그래서 값이 매 회차 느려지고 있어도 사람이 표를 직접 보고 눈치채야 한다.

**현재 동작**

`tools/repeatability.js`는 회차별 값에서 평균·표준편차·CV·최소·최대를 계산해 출력한다.
회차의 **순서 정보는 쓰지 않는다.** 그래서 `[10, 12, 11, 13, 12]`와 `[10, 11, 12, 12, 13]`이
같은 CV로 보고된다. 앞은 무작위 흔들림이고 뒤는 추세인데 구분되지 않는다.

**왜 문제인가**

CV는 MDE(최소 검출 가능 개선폭) 계산의 입력이고, 그 계산은 **회차가 서로 독립**이라고
가정한다. 추세가 섞여 있으면 CV가 무작위 성분을 과대평가하고, 그 결과 MDE도 틀린다.
방향도 한쪽으로만 틀리지 않는다.

- 연달아 비교하면 실제 노이즈가 CV보다 **작아서** MDE가 과도하게 보수적이 된다
- 시간을 두고 비교하면 추세가 **편향**으로 들어와 MDE로는 못 걸러진다

**증거**

EXP-001 5회 세트에서 실제로 발생했다(E-46). 도구는 `P95 CV = 3.12%`만 보고했고, 추세는
사람이 원자료를 다시 정렬해 본 뒤에야 드러났다.

```text
Spearman 순위상관(시간 vs P95) = 0.90
추세 제거 후 CV = 1.72%   (원본 3.30%)
```

**보고서에 이 사실이 전혀 없었다.** 판정 문구는 "같은 조건 반복 시 p95가 평균 대비 이만큼
흔들린다"인데, 실제로는 흔들린 게 아니라 **기울어져 있었다.**

**필요한 조치**

1. 회차 순서와 값의 **순위상관(Spearman)** 을 계산해 함께 출력한다. 계산이 간단하고
   표본 5개에서도 방향은 잡힌다.
2. 상관이 임계(예: |ρ| ≥ 0.7)를 넘으면 **경고를 띄운다** — "이 세트에는 추세가 있어 CV를
   무작위 노이즈로 해석하면 안 된다".
3. **추세 제거 후 CV를 함께 보고**한다. 두 값을 나란히 두면 무작위 성분과 추세 성분의
   비중이 바로 보인다.
4. 결과 JSON(`reports/repeatability/*.json`)에도 넣어 나중에 재해석할 수 있게 한다.

임계값을 얼마로 할지는 정하지 않았다. 표본 5개에서 |ρ|=0.9는 우연으로도 드물지 않으므로
(무작위 순열에서 |ρ|≥0.9가 나올 확률은 약 8%), 경고는 띄우되 단정하지 않는 문구여야 한다.

관련: E-46(실제로 발생한 드리프트), T-04(반복 측정), T-27(이력 추세 계산)

> | 지표 | `k6.all` | `phases.measure` | 문서에 실린 값 |
> |---|---:|---:|---|
> | p95 | 11,821.4ms | 12,231.2ms | `k6.all` |
> | p99 | 16,524.0ms | 16,906.5ms | `k6.all` |
> | rps | 22.6 | 17.5 | `k6.all` |
>
> 워밍업의 낮은 부하 구간이 섞여 **전체 쪽이 낙관적으로 나온다.** p95 기준 3.4% 차이다.
>
> **왜 심각한가 — 범위가 섞인 문서가 만들어졌다.** `EXP-001`은 6절에 "판정은 measure
> 구간만 본다"고 선언해 놓고, 7.1 반복 정밀도 표는 전체 구간 값(도구 출력)이고 7.2 SLO
> 대조는 measure 구간 값(`rawMetrics`에서 수동 추출)이었다. **한 문서 안에서 두 범위가
> 섞였는데 어느 쪽인지 표기도 없었다.**
>
> 그 표의 CV가 MDE의 입력이므로, 판정 기준이 다른 범위에서 계산된 값 위에 서 있었다.
>
> **어떻게 고쳤나.** `phasePlan.gatePhase`가 가리키는 구간을 읽는다. `gatePhase`가 없는
> 진단 시나리오는 `all`로 되돌리되, **어느 범위를 썼는지 결과 행(`scope`)에 남긴다** —
> 범위가 섞이면 값이 아니라 해석이 틀리기 때문에 사후에 구분할 수 있어야 한다.
>
> **버린 대안 — `all`을 유지하고 문서에만 "전체 구간"이라고 표기.** 재계산이 없어 싸지만,
> 판정 기준(measure)과 정밀도 근거(all)의 범위가 계속 달라진다. MDE는 "이 개선이 노이즈보다
> 큰가"를 재는 값이라 **게이트가 보는 것과 같은 범위**에서 나와야 한다.
>
> **후속 작업**: EXP-001의 기준선 수치를 measure 구간으로 다시 잡아야 한다. CV가 바뀌면
> MDE도 다시 정한다.
>

> **2026-08-18 후속 — 이 수정이 부작용을 하나 만들었고 함께 고쳤다.**
>
> `k` 를 `k6.all` 에서 `phases.measure` 로 바꾸면서, 같은 함수가 쓰는 `serverMeanMs()` 는
> 그대로 두었다. 그쪽은 **실행 전체 구간**(warmup+measure+rampdown)을 Prometheus 에
> 질의한다. 그래서 뺄셈의 두 항이 서로 다른 구간이 됐다.
>
> ```text
> 경로 오버헤드 = k6 avg(measure 구간) − 서버측 평균(전체 구간)
>                 ↑ 부하가 걸린 구간      ↑ 워밍업의 낮은 부하가 섞여 낮아짐
> ```
>
> 실측(2026-08-18 세트, 1회차): 같은 실행에 대해
>
> | 서버측 평균 질의 창 | 값 | 경로 오버헤드 |
> |---|---:|---:|
> | 전체 1,638초 (수정 전) | 7,208.5ms | **1,033.9ms** |
> | measure 1,200초 (수정 후) | 8,164.6ms | **77.8ms** |
>
> **13배 부풀려져 있었다.** 이 값이 크게 나오자 "부하 발생기 경로에 문제가 생겼나"를
> 의심하게 만들었는데, 실제로는 측정 창이 어긋난 것뿐이었다.
>
> **수정**: `serverMeanMs(run)` 가 `phasePlan.gatePhase` 구간만 질의한다. 창의 길이뿐
> 아니라 **끝 시각**도 그 구간의 끝으로 맞춘다 — `increase()` 는 지정 시각에서 뒤로 창을
> 잡으므로, 끝 시각이 실행 종료면 rampdown 이 섞인다. `gatePhase` 가 없는 진단 시나리오는
> 전체 구간으로 되돌린다.
>
> **재계산 결과**: 세트 A 경로 오버헤드 78ms, 세트 C 126ms. 세션 간 열화(E-46)의 주 원인이
> 아니라는 것도 이 값으로 확인됐다 — 48ms 늘었을 뿐인데 전체 지연은 5,000ms 넘게 늘었다.
>
> **교훈**: 한 값이 두 소스의 뺄셈이면, **한쪽 소스의 범위를 바꿀 때 다른 쪽도 같이 봐야
> 한다.** 이번엔 같은 함수 안 20줄 거리였는데도 놓쳤다.

> 관련: S-26(같은 사건에서 드러난 RPS 분모 오류), T-03·S-08(measure 일원화), EXP-001

### T-32. [CRITICAL] 스크립트 지문만 달라도 절대 SLO 게이트가 통째로 꺼짐 — 상태: **해결** (2026-08-18)

> **쉽게 말하면.** 부하 스크립트에 **주석 한 줄만 고쳐도** "응답이 SLO를 넘었다"는 판정이
> 경고로 낮아지고 CI가 통과했다. 정작 스크립트를 고치는 실행이야말로 게이트가 가장 필요한
> 때인데, 그때만 꺼졌다.

#### 현재 동작 (수정 전)

`regression.js`의 `analyze()`는 비교 등급이 `degraded`(= blocking 조건은 같고 **스크립트
지문만** 다름)이면 전체 판정을 `FAIL → WARN`으로 낮추고 게이트를 열었다.

```js
const degraded = !!(comparability && comparability.level === 'degraded');
if (degraded && verdict === 'FAIL') { downgradedFrom = 'FAIL'; verdict = 'WARN'; }
...
gateFailed: gateFailures.length > 0 && !degraded,
```

문제는 이 강등이 **실패 사유를 구분하지 않았다**는 점이다. 판정에는 두 종류가 있다.

| 사유 | 무엇을 보나 | 기준선을 읽나 | degraded의 영향 |
|---|---|---|---|
| 상대 | 직전 대비 증감률 | **읽는다** | 기준선이 다르면 값이 무의미 → 강등이 맞다 |
| 절대 | SLO 상한 초과 여부 | **안 읽는다** | 등급과 무관하게 유효 → 강등하면 안 된다 |

`evaluateRule()`의 절대 판정은 `baseline`을 아예 참조하지 않는다. 기준선을 믿을 수
있는지와 무관하게 유효한데, 기준선 문제 때문에 함께 무력화됐다.

#### 왜 문제인가 — 판정 강도가 차이 크기에 대해 역전됐다

차이가 **작을수록** SLO 강제가 약해졌다.

| 기준선과의 차이 | 비교 등급 | SLO 위반 시 결과 |
|---|---|---|
| 없음 | `exact` | FAIL, CI 중단 |
| **스크립트 주석 한 줄** | `degraded` | **WARN, CI 통과** |
| 데이터셋 변경(더 큰 차이) | `incomparable` | FAIL, CI 중단 |
| 기준선 자체가 없음 | — | FAIL, CI 중단 |

`conditions.js`는 blocking 등급을 설명하며 "절대 게이트는 계속 돈다 — regression.js의
안전 바닥"이라고 선언해 두었다. 더 약한 degrading 불일치가 그 바닥을 뚫고 있었다.

`regression.js` 상단 주석이 절대 게이트를 둔 이유로 든 "매번 9%씩 나빠지며 영원히 통과하는
삶은 개구리" 문제가, 스크립트 수정이라는 다른 경로로 되살아난 셈이다.

#### 근거 — 저장된 실행으로 재현

`normal-day-2026-08-18T02-10-50`의 `run.json`을 그대로 쓰고 measure p95만 SLO(500ms) 위인
9,999ms로 올린 뒤, 기준선의 `scriptVersion`만 바꿔 `analyze()`를 직접 호출했다.

```text
① exact                    verdict=FAIL gateFailed=true   gateFail수=3
② degraded(스크립트만 다름)  verdict=WARN gateFailed=false  gateFail수=3   ← 게이트 열림
③ incomparable(데이터셋)    verdict=FAIL gateFailed=true   gateFail수=3
```

②의 개별 규칙 판정은 이랬다 — **증거는 그대로 남아 있는데 게이트만 꺼졌다.**

```text
counts = { total: 33, fail: 7, warn: 0, gateFail: 3, ... }
k6.phases.measure.p95        verdict=FAIL gate=true reasons=["absolute:FAIL 9999 > 상한 500"]
k6.phases.measure.p99        verdict=FAIL gate=true reasons=["absolute:FAIL 9999 > 상한 1200"]
infra.flat.cpu.throttledPct  verdict=FAIL gate=true reasons=["absolute:FAIL 99.92 > 상한 10.00"]
```

`counts.gateFail = 3`인데 `gateFailed = false`다. 리포트를 열면 빨간 줄 세 개와 "절대 상한
초과"라는 사유가 보이는데 `collect.js`는 exit 0으로 끝난다. **조용한 통과가 아니라 "보이는데
안 막는" 통과**라 오히려 알아채기 어렵다.

저장된 58개 실행 중 `degraded`는 **0건**이었다. 관측된 사고가 아니라 잠복 결함이었지만,
트리거가 이 저장소에서 가장 흔한 작업(k6 스크립트 수정)이라 시간 문제였다.

#### 어떻게 고쳤나

강등을 실패 사유별로 나눴다. 판단 근거는 각 비교 결과에 이미 들어 있던 `reasons[].type`이라
새 상태를 만들 필요가 없었다.

```js
const isAbsoluteFail = (c) => c.reasons.some((r) => r.type === 'absolute' && r.level === 'FAIL');
const absoluteGateFailures = gateFailures.filter(isAbsoluteFail);

// 강등은 상대 사유로만 실패했을 때에만
if (degraded && verdict === 'FAIL' && absoluteGateFailures.length === 0) { ... }

gateFailed: absoluteGateFailures.length > 0 || (gateFailures.length > 0 && !degraded),
```

`evaluateRule()`은 손대지 않았다 — 거기는 처음부터 옳게 동작하고 있었고, 문제는 집계
단계에만 있었다.

`absoluteGateFailures`(키 목록)를 결과에 노출해 콘솔과 HTML 리포트가 **강등했는지, 아니면
절대 위반이 있어 게이트를 유지했는지**를 구분해 말하게 했다. 아무 말도 안 하면 사람은
"조건이 다르다"를 "어차피 통과"로 읽는다.

**버린 대안 — degraded일 때 강등을 아예 없애기.** 단순하지만 원래 의도를 버린다. 주석 한
줄에도 지문이 바뀌므로, 증감률 실패까지 CI를 세우면 스크립트를 고칠 때마다 빌드가 깨진다.
그러면 사람은 게이트를 통째로 끄게 된다.

#### 검증

`tools/test/regression.test.js`에 회귀 테스트 5개를 남겼다.

| 테스트 | 고정하는 성질 |
|---|---|
| degraded 여도 절대 SLO 위반은 게이트를 유지한다 | 우회로 차단 |
| degraded 에서 절대는 통과하고 상대만 실패하면 그대로 강등한다 | 원래 의도 보존 |
| 판정 강도가 비교 등급에 대해 역전되지 않는다 | 네 등급 전부 FAIL·gateFailed=true |
| 같은 게이트가 절대·상대 양쪽으로 실패해도 강등하지 않는다 | 사유 혼재 시 안전한 쪽 |
| gate:false 규칙의 절대 실패만으로는 게이트가 닫히지 않는다 | 정보 제공용 규칙과의 분리 |

전체 스위트 238건 통과. 실데이터 재현도 네 경우 모두 `FAIL / gateFailed=true`로 바뀐 것을
확인했다.

> 관련: T-02(비교 가능성 도입), T-08(측정 상태 축), S-10(기준선 자격), conditions.js의
> materiality 등급 정의

### T-33. [LOW] 유효 회차가 1회면 반복 정밀도를 CV 0%로 보고함 — 상태: **해결** (2026-08-18)

> **쉽게 말하면.** 10회 중 9회가 무효 처리돼도 콘솔에는 "CV 0.00% — 완벽하게 재현된다"로
> 보인다. 실제로는 편차를 계산할 표본이 없었던 것이다.

#### 현재 동작

`tools/repeatability.js`의 `stats()`는 표본이 1개일 때 표준편차를 0으로 둔다.

```js
const sd = n < 2 ? 0 : Math.sqrt(...);   // n=1 → sd=0
...
cvPct: mean === 0 ? null : (sd / mean) * 100,   // → 0
```

#### 왜 문제인가

출력 문구가 값의 뜻을 단정한다.

```text
▶ 판정 지표: P95 CV = 0.00%  (같은 조건 반복 시 p95가 평균 대비 이만큼 흔들린다)
```

이 도구의 존재 이유는 "회귀 임계값 20%가 자연 편차보다 큰가"에 답하는 것이다. CV 0%는 그
질문에 "자연 편차가 없다"고 답하는 셈인데, 실제로는 **답할 근거가 없었다**는 뜻이다.
무효 회차 경고(`⚠ 무효 9회`)는 표 아래에 따로 찍히지만, 판정 지표 줄과 붙어 있지 않아
표만 보면 놓친다.

같은 문서의 다른 곳(`trendStats`, `metricsByPhase`)은 "측정 안 된 값은 0이 아니라 없는
값이어야 한다"는 원칙을 이미 지키고 있다. 이 함수만 예외다.

#### 해결 내용

`n < 2`이면 `sd`와 `cvPct`를 모두 `null`로 두고, 표에는 `—`를, 판정 지표 줄에는 "유효 표본
부족(1회)"을 찍도록 수정했다. `n=1`, `n=2` 경계 회귀 테스트를 추가했고 전체 241개 테스트가
통과했다.

> 관련: T-30(추세 미검출), T-04(반복 실행), EXP-000

### T-34. [HIGH] 반복측정이 전 회차 무효여도 프로세스가 성공으로 종료됨 — 상태: **해결** (2026-08-18)

> **쉽게 말하면.** 내부 5회가 모두 실패해 유효한 측정값이 하나도 없어도, 바깥 실행기는
> 종료 코드 0만 보고 "반복측정 완료"로 기록했다. 실제 밤새 첫 시도에서 `0/5 valid`인 세트가
> 성공으로 넘어가 다음 항목까지 진행됐다.

#### 영향

무인 실행기, CI, 사람이 확인하는 셸 모두 반복측정 결과가 유효한지 알 수 없었다. 따라서
"명령이 끝났다"와 "요청한 반복측정을 모두 얻었다"가 구분되지 않았고, 실행 목록의 완료 상태도
거짓으로 기록될 수 있었다.

#### 해결 내용

`resultExitCode(validCount, requestedRuns)`를 추가해 요청한 모든 회차가 유효할 때만 0을 반환하고,
일부 또는 전부 무효이면 2를 반환하게 했다. `5/5`, `4/5`, `0/5` 경계 테스트를 추가했으며 전체
241개 테스트가 통과했다.

> 관련: T-04(반복 실행), T-08(측정 상태 축), T-33(표본 부족 표시)

### T-35. [HIGH] 같은 성능 스택에서 `perf-run` 둘을 동시에 실행할 수 있음 — 상태: **해결** (2026-08-18)

> **쉽게 말하면.** 문서에는 “동시에 두 개 이상 돌리지 않는다”고 적혀 있었지만 프로그램은
> 막지 않았다. 고아로 남은 무인 실행기와 수동 실행이 겹치자 한쪽이 데이터셋 복원을 위해
> MySQL·앱을 재시작했고, 다른 쪽은 실행 도중 `connection refused`를 대량 발생시켰다.

#### 영향

두 실행은 같은 앱·DB·Redis·Prometheus와 호스트 CPU를 공유한다. 부하가 겹치면 성능 수치가
오염되고, `guard=strict` 복원까지 겹치면 실행 중인 대상 서버가 내려간다. 결과 파일을 서로
잘못 고르는 문제는 T-14에서 막았지만, 측정 대상 자체가 중간에 바뀌는 문제는 남아 있었다.

#### 해결 내용

`tools/lib/run-lock.js`에 PID가 포함된 배타 잠금을 추가하고 `perf-run.js`가 실행 초기에 이를
획득하게 했다. 살아 있는 PID의 잠금이 있으면 두 번째 실행은 종료 코드 2로 거부한다. 강제
종료로 잠금 파일만 남은 경우에는 PID가 죽은 것을 확인한 뒤 자동 교체한다. 동시 획득 거부,
정상 재획득, 죽은 PID 복구를 포함한 테스트를 추가했으며 전체 245개 테스트가 통과했다.

> 관련: T-14(현재 실행 ID 식별), T-15(인덱스 원자적 쓰기), T-28(실행 번호 동시성)

### T-36. [HIGH] CPU 포화 상태에서 "요청당 자원" 지표가 전부 처리량의 역수로 붕괴한다 — 상태: **부분 해결** (2026-08-19)

> **쉽게 말하면.** `efficiency.appCpuMsPerReq` 가 올랐다는 것은 "같은 일을 더 비싸게 하고
> 있다"가 아니라 그냥 "처리량이 떨어졌다"를 다른 단위로 쓴 것이다. 앱이 CPU 상한에 붙어
> 있으면 분자가 상수라 이 지표에는 새 정보가 없다.

#### 근거 — 실측

2026-08-19 normal-day 5분 창 세트 4회차까지의 값이다.

| 회차 | 요청 수 | 앱 CPU초 | 600,000 ÷ 요청 수 | 실측 `appCpuMsPerReq` | 차이 |
|---:|---:|---:|---:|---:|---:|
| 84 | 7,374 | 599.8 | 81.35 | 82.58 | 1.5% |
| 85 | 6,224 | 599.6 | 96.33 | 97.05 | 0.7% |
| 86 | 6,767 | 599.9 | 88.65 | 90.33 | 1.9% |
| 87 | 5,774 | 600.0 | 103.91 | 104.40 | 0.5% |

measure 300초 × 상한 2코어 = 600 CPU초이고, 앱은 `cpu.throttledPct 99.86%` 로 상한에
완전히 붙어 있다. 그래서 앱 CPU초가 상수가 되고, "요청당 CPU" 는 정의상 `600,000 ÷ 요청 수`
가 된다. 실측 오차 0.5~1.9% 로 그 항등식이 확인된다.

`efficiency.queriesPerReq` 도 같은 함정에 있다. 총 MySQL 문 수를 요청 수로 회귀하면

```
Q = 858,621 + 153.5 × 요청수      (고정분 2,862 문/초)
```

로, 부하와 무관한 고정분이 존재한다(아래 정정 참고). 처리량이
떨어지면 이 지표는 기계적으로 오른다. `dbCpuUsPerQuery` 역시 MySQL CPU초가 388~395초로
거의 고정이라 같은 문제를 겪는다.

> **→ 정정 (2026-08-20).** 위 회귀는 실행 4건으로 낸 값이라 고정분을 과대추정했다.
> **실행 16건으로 다시 계산하면 `Q = 397,726 + 228.6 × 요청수`, 고정분 1,326 문/초로
> 전체의 20.3% 다**(43.8% 아님). 즉 요청당 실제 부하 유래 쿼리는 **228.6개**다. 결론의
> 방향(요청당 지표가 처리량과 순환한다)은 바뀌지 않지만 숫자는 이쪽이 맞다.
>
> 함께 정정한다 — 본문의 `cpu.throttledPct 99.86%` 는 **"벽시계 시간의 99.86% 를 정지로
> 잃었다"가 아니다.** 이 값은 `nr_throttled / nr_periods`, 즉 **quota 에 걸린 CFS period 의
> 비율**이다. "앱이 사실상 매 period 마다 quota 를 다 쓴다"는 강한 증거이고 결론은
> 유지되지만, 손실 시간으로 읽으면 안 된다.
>
> 그리고 **이 붕괴의 더 근본적인 형태**가 있다. closed model(`ramping-vus`)에서 VU 가
> 고정되면 응답시간은 리틀의 법칙에 따라 `R = N / X` 로 기계적으로 정해진다. 실측에서
> `200 ÷ 처리율` 과 p95 의 상관이 **0.962** 로, Hikari acquire(0.944)보다 높다. 즉 요청당
> 지표뿐 아니라 **p95 자체가 처리량의 함수**다. 상세는
> [perf-session-drift.md](../investigations/perf-session-drift.md) 8-d 절.


#### 영향

세션 간 편차(E-46)를 쫓을 때 이 지표들을 설명 변수로 쓰면 **순환 논증**이 된다. 설명하려는
대상(처리량)을 설명 변수로 쓰는 셈이기 때문이다. 실제로 이 세트를 분석하다 "주파수 ×
요청당 쿼리 수로 거의 설명된다"는 결론에 도달했다가, 두 설명 변수가 모두 처리량의 함수임을
확인하고 철회했다.

요청 구성비는 이 붕괴의 원인이 아니다 — 같은 4회차에서 post 42.55~42.77%, read
89.73~90.42% 로 거의 고정이었다.

#### 부분 해결 — 부하 중 대조 벤치 도입

순환을 깨려면 **분자가 처리량과 무관한** 지표가 필요하다. cpu-bench 는 알려진 고정량의
일을 시키고 시간을 재므로 이 조건을 만족한다. 부하가 도는 동안 이 값을 찍으면 갈린다.

- 벤치도 같은 비율로 느려짐 → 컨테이너 밖 공유 층(클럭·캐시·메모리)
- 벤치는 평소값인데 앱만 느림 → 컨테이너 또는 JVM 안

하드웨어 성능 카운터로 IPC 를 직접 재는 쪽이 정답이지만 이 환경에서는 불가능하다(E-48).

구현은 `tools/lib/loadbench.js` 와 `loadbench-worker.js` 다. 벤치를 **warmup 구간**에
넣는다 — 부하는 걸려 있는데 통계에는 잡히지 않는 유일한 구간이라, measure 를 오염시키지
않고 "부하 중 환경 속도" 를 얻는다. 시점은 warmup 의 1/3 지점이고, warmup 이 120초 미만
이거나 지정되지 않았으면 **재지 않는다**(측정 창 침범 방지). `--loadbench-at <초>` 로 직접
지정할 수 있다. 워커를 별도 프로세스로 둔 이유는 hostprobe 와 같다 — `perf-run.js` 가 k6 를
`spawnSync` 로 돌려 부모의 이벤트 루프가 막히므로, 부모 안의 타이머는 k6 가 끝난 뒤에야
깨어난다.

함께 `perf-run.js` 의 실행 전 벤치를 `repeat: 1` → `3` 으로 올렸다(환경변수
`PERF_BENCH_REPEAT`). 1회 표본이 4,883~7,736ms 로 튀어 근거로 쓸 수 없던 문제다.

#### 남은 일

- `efficiency.appCpuMsPerReq` 와 `dbCpuUsPerQuery` 의 카탈로그 설명에 **"CPU 포화 상태에서는
  해석 불가"** 조건을 명시한다. 현재 설명("오르면 같은 일을 더 비싸게 하고 있다")은
  비포화 상태에서만 성립한다.
- `queriesPerReq` 에서 배경 쿼리를 분리한다. 유휴 구간의 배경 QPS 기준선을 재거나,
  `Com_select`·`Com_commit`·`Com_begin` 등 문 종류별 카운터를 카탈로그에 넣는다.
- 부하 중 벤치의 실제 진단값은 아직 없다. 배관 확인(5 VU, CPU 12%)만 마쳤고, 포화 부하에서
  찍은 값이 있어야 판별이 성립한다.

#### 검증

성능 도구 테스트 255개가 통과했다(기존 245 + 신규 10). 신규 테스트는 시점 계산 경계
(warmup 120초 미만·미지정·NaN), 벤치 종료 시각이 warmup 안에 들어오는지, 미완료 시 값을
만들어내지 않는지를 고정한다. 배관은 Run #89 로 확인했다 — `run.loadBench` 에 3축 × 3표본과
유휴 대비 변화율이 기록됐다.

> 관련: E-46(세션 간 편차), E-48(PMU 사용 불가), T-33(유효 표본 1회의 CV), 드리프트 문서
> 12절 실험 9(벤치 repeat 상향)

### T-37. [HIGH] 호스트 프로브가 판정 구간과 다른 창을 재고, 집계값만 남기며, 자기 계측기의 부하를 포함한다 — 상태: **해결** (2026-08-20)

> **무엇을 어떻게 고쳤나.** 네 결함을 한 번에 처리했다.
>
> 1. **구간 정렬** — `hostprobe.stop()` 이 원시 표본을 반환하고, `perf-run.js` 가 이를
>    `<runId>.hostprobe.jsonl` 사이드카로 보존한다. 구간 경계(`run.phasePlan`)는 k6 요약에서
>    오므로 perf-run 시점에는 알 수 없다. 그래서 **경계를 아는 `collect.js` 에서**
>    `hostprobe.sliceByPhase()` 로 잘라 `run.hostProbe.phases.{warmup,measure,rampdown}` 을
>    만든다. k6·Prometheus 창 정렬(T-03/S-08)과 같은 원칙을 호스트 프로브에도 적용한 것이다.
> 2. **자기 오염 격리** — `hostprobe.mark()` 로 loadbench 실행 구간을 기록한다. 구간 분리로
>    loadbench 는 warmup 에 갇히므로 measure 요약이 오염되지 않는다.
> 3. **코어별 수집** — `Processor Information(*)` 와일드카드로 논리 프로세서별 CPU·정규화
>    성능을 함께 받고, `\Process(vmmem*)\% Processor Time` 으로 **호스트 측 가상화 비용**을
>    추가했다. 요약에는 `coresBusy`(50% 이상 사용 중인 코어 수)와 `topCores` 를 싣는다.
> 4. **간격 5초 → 1초** — 5초짜리 고정 작업 벤치와 겹쳐 보려면 구간당 표본이 필요하다.
>
> **고민한 대안과 버린 이유.**
> - *perf-run 이 직접 구간을 계산한다* → 버렸다. measure 길이는 시나리오 기본값에서 오므로
>   `--warmup` 만으로는 알 수 없다. 추정해서 자르면 조용히 틀린 창을 쓰게 된다.
> - *요약만 남기고 원시는 계속 버린다* → 버렸다. 바로 그것 때문에 과거 실행을 다시 자를 수
>   없었다. 사이드카 하나가 수백 KB 인데 그 값어치를 이미 실패로 배웠다.
> - *코어별 계열을 요약에 전부 싣는다* → 버렸다. 논리 20개 × 2지표 × 4통계면 run.json 이
>   불필요하게 커진다. 파생값만 싣고 원본은 사이드카에 둔다.
> - *헤더 칼럼 수로 행을 검증한다*(기존 방식) → **버렸고, 이게 실제 버그였다.** 와일드카드
>   인스턴스 확장 개수가 실행마다 흔들려(헤더 42셀 / 행 50셀) **모든 행이 버려지고 표본 0개**
>   가 됐다. typeperf 는 요청 순서대로 칼럼을 내므로 앞쪽 고정 카운터의 위치는 불변이다.
>   그래서 길이가 어긋나면 `resolveIndex()` 가 **위치 기반으로 폴백**해 코어별 매핑만
>   포기하고 고정 카운터는 살린다. 전부 버리는 것보다 낫다.
>
> **어떻게 검증했나.** 단위 테스트 10개를 추가해 전체 265개가 통과했다 — 구간 경계 포함/제외,
> warmup 부하가 measure 요약에 섞이지 않음, 헤더/행 길이 불일치 시 위치 폴백, 폴백 상태에서도
> 고정 카운터 정상 요약. 그리고 `spawnSync` 로 부모를 막은 상태를 재현해 예전 코드가 표본 0개,
> 고친 코드가 17표본을 내는 것을 확인했다.
>
> 실제 실행(medium · warmup 120s · measure 30s · loadbench +30s)으로 배관을 확인했다.
>
> | 구간 | 표본 | Windows CPU | 정규화 성능 | **vmmem** | 바쁜 코어 |
> |---|---:|---:|---:|---:|---:|
> | warmup | 110 | 17.00% | 87.43 | **123.45%** | 1.82 |
> | measure | 26 | 12.64% | 77.89 | **49.41%** | 1.31 |
> | rampdown | 122 | 9.31% | 72.01 | 38.22% | 0.61 |
>
> **warmup 의 vmmem 123% 대 measure 49%** 가 이 작업의 필요성을 그대로 보여준다. 예전에는
> 이 셋이 하나의 평균으로 뭉개졌고, 그 안에 우리가 넣은 loadbench 부하가 섞여 있었다.
> `marks` 에 loadbench 구간(02:32:24 ~ 02:33:03)이 기록됐고 원시 표본 258개가
> `hostprobe.jsonl` 로 보존됐다.
>
> **남은 부작용.** 저장된 과거 실행에는 원시 표본이 없으므로 **소급 구간 분리가 불가능하다.**
> `run.hostProbe.phases` 가 없는 실행은 전체 구간 평균이라는 뜻이며, measure 구간 지표와
> 상관분석하면 안 된다. 그리고 코어별 매핑은 헤더 길이가 맞을 때만 채워진다 — 폴백 상태에서는
> `coresBusy`·`topCores` 가 비고, 그 사실은 `hostProbe.counters` 에 항목이 없는 것으로 드러난다.

> **쉽게 말하면.** 호스트 지표와 p95 를 나란히 놓고 상관을 냈는데, **둘이 서로 다른 시간
> 구간의 값**이었다. 게다가 그 창 안에서 우리가 추가한 CPU 벤치가 돌고 있었다. 원시
> 시계열은 저장되지 않아 사후에 구간을 다시 자를 수도 없다. 이 결함 때문에 실제로
> **잘못된 인과 결론을 냈다가 철회했다**(E-49, perf-session-drift.md 8-e).

#### 결함 4가지

**① 측정 창이 판정 구간과 다르다.** `hostprobe.start()` 는 k6 를 띄우기 직전에 켜지고
종료 직후 꺼진다(`tools/perf-run.js`). 따라서 `run.hostProbe` 의 평균은
**warmup + measure + rampdown 전체**(600초) 값이다. 그런데 비교 대상인 p95 는
`k6.phases.measure` 즉 **measure 300초**만이다. 서로 다른 창을 상관분석했다.

k6 지표와 Prometheus 창은 T-03/S-08 에서 `run.phasePlan` 하나로 정렬시켰는데,
**호스트 프로브만 그 정렬에서 빠져 있다.**

**② 계측기 자신의 부하가 창 안에 있다.** 2026-08-19 저녁 도입한 `loadbench` 는 warmup 의
1/3 지점에서 3축 × 3회(약 40초, 2코어)를 돈다. 이 구간이 hostProbe 창 안이다. 즉
**설명 변수 안에 CPU 를 태우는 도구가 들어 있다.** 그 값으로 상관을 내면 계측기가 만든
신호를 관측 대상의 성질로 오독하게 된다.

**③ `_Total` 집계만 남는다.** 수집 카운터는
`\Processor Information(_Total)\% Processor Performance` 등 전체 집계다. 이기종 CPU
(P-core 6 + E-core 8)에서 이 값은 유휴 코어까지 포함한 시스템 전체 정규화 성능이라,
**WSL 이 실제로 실행된 논리 프로세서의 상태를 알 수 없다.** 또한 PERFORMANCE 는
FREQUENCY 와 별개의 카운터 타입이므로 물리 MHz 로 읽으면 안 된다.

**④ 원시 시계열이 삭제된다.** `hostprobe.stop()` 이 워커의 JSONL 을 읽어 요약(avg/min/max/
p95)만 `run.json` 에 남기고 임시 파일을 지운다. 그래서 **저장된 과거 실행에서 measure
구간만 다시 잘라 분석하는 것이 불가능하다.** 이미 그 필요가 실제로 발생했다.

부수적으로 **샘플링 간격이 5초**라 5초짜리 고정 작업 벤치와 겹쳐 보면 표본이 1~2개뿐이다.

#### 영향

이 결함들 때문에 다음 오류가 실제로 발생했다.

- 통합 상관 −0.43 을 주파수 인과의 근거로 제시 → 절차 동일 구간에서 +0.40 으로 부호가
  뒤집혀 **철회**(8-e.1)
- 두 세트의 호스트 CPU 평균 차이(28.6~31.3% 대 39.8~50.9%)를 환경 차이로 해석 → 일부는
  loadbench 를 창에 넣은 결과

#### 조치 방향

1. **창을 `run.phasePlan` 에서 파생시킨다.** warmup / measure / rampdown 을 분리해 각각
   요약하고, 게이트·상관 분석에는 **measure 구간만** 쓴다. k6·Prometheus 와 같은 원칙
   (T-03/S-08)을 호스트 프로브에도 적용한다.
2. **loadbench 구간을 별도 표식으로 남기고 measure 요약에서 제외한다.**
3. **논리 프로세서별로 수집한다** — `% Processor Performance`, `% Processor Time`,
   `% Processor Utility`, `% Performance Limit`, Performance Limit Flags. 여기에
   VmmemWSL 프로세스 CPU 와 Hyper-V virtual/logical processor 카운터를 더한다.
4. **원시 시계열을 실행 디렉터리에 보존한다.** 사후 재질의가 가능해야 한다.
5. **샘플링 간격을 0.5~1초로 줄인다**(최소한 벤치와 겹치는 구간에서는).

#### 완료 기준

1. `run.hostProbe` 에 phase 별 요약이 들어가고, 상관 분석이 measure 구간만 쓴다.
2. loadbench 구간이 표식으로 구분되어 요약에서 빠진다.
3. 논리 프로세서별 계열이 저장된다.
4. 원시 시계열이 실행 디렉터리에 남아 사후 재질의가 가능하다.
5. 위를 갖춘 뒤 전원 설정 A/B 를 교차 설계로 재실행했다(E-49).

> E-49(유효 CPU 처리 능력), perf-session-drift.md 8-e

### T-38. [HIGH] `op` 축의 read·write 응답시간이 리포트에 0 으로 표시된다 — 상태: **해결** (2026-08-25)

**쉽게 말하면**

리포트의 `오퍼레이션별 응답시간` 표에 `auth` 만 값이 있고 `read`·`write` 는 0 이다. 실제로는
값이 있는데 **읽는 위치가 틀렸다.**

**무엇이 문제인가**

같은 축 안에서 레코드 모양이 두 가지다.

```json
"auth":  { "count":154,  "p95":347.6, ... }                          ← 최상위
"read":  { "count":6840, "byPhase": { "measure": { "p95":436.9 } } } ← 중첩
"write": { "count":602,  "byPhase": { "measure": { "p95":49.2  } } } ← 중첩
```

`tools/lib/report.js` 에 `byPhase` 를 처리하는 코드가 **한 줄도 없다**(grep 0건). 그래서
중첩된 것은 `p95` 가 `undefined` → 0 으로 렌더된다. `feature` 축은 값이 최상위에 있어
정상 표시되므로 문제가 눈에 띄지 않았다.

**왜 HIGH 인가 — 병목 판정을 직접 방해한다**

| op | 실제 p95 | 실제 p99 | 요청 수 | 리포트 표시 |
|---|---:|---:|---:|---|
| **read** | **436.9ms** | **2,179ms** | 6,840 | **0** |
| write | 49.2ms | 90.8ms | 602 | **0** |
| auth | 347.6ms | 602.6ms | 154 | 정상 |

이 실행의 전체 p99 는 2,148ms 인데 `read` 의 p99 가 2,179ms 다. **p99 를 만드는 것이 read
라는 결정적 단서를 리포트가 감추고 있다.** 화면에는 요청의 2% 인 `auth` 만 보이므로,
읽는 사람은 인증이 유일한 느린 축이라고 오해하게 된다.

**추정 원인.** phase 인식 집계(T-03/S-08) 도입 때 일부 축만 `byPhase` 구조로 바뀌었고
렌더가 따라오지 않았다.

**해야 할 일.** `report.js` 의 breakdown 렌더에 `row.byPhase?.[gatePhase] ?? row` 형태의
정규화를 넣는다. 저장된 원자료는 멀쩡하므로 **재측정이 아니라 재생성으로 복구된다.**

> 관련: T-03·S-08(구간 정렬), T-39(축 자체가 없는 문제)

### T-39. [HIGH] 어떤 API 가 병목인지 알 수 없다 — `name` 태그를 붙이고도 수집하지 않는다 — 상태: **해결** (2026-08-25)

**쉽게 말하면**

리포트의 가장 세밀한 축이 `feature`(도메인 묶음)다. 그런데 **`comment` 하나에 엔드포인트가
4개**(목록 조회·작성·수정·삭제) 들어 있다. "댓글이 느리다"까지는 알 수 있어도 **"댓글의
어느 API 가 느린가"는 알 수 없다.**

**결정적인 부분 — 데이터는 이미 붙고 있다**

`scripts/lib/config.js:90` 의 태그 헬퍼가 **엔드포인트 식별자를 이미 실어 보낸다.**

```js
export function tags(feature, op, name, extra) {
  const t = { feature, op, name: name || feature, ...extra };
  ...
}
```

호출부도 그렇게 쓰고 있다 — `tags('comment', 'read', 'comment_list')`.

**그런데 수집되지 않는다.** 저장된 원자료의 서브메트릭 86개 중 `name:` 을 포함한 것이
**0개**다.

```
수집된 태그축:  feature 26 · phase 20 · page 10 · op 6 · expected_response 1
```

k6 는 **threshold 로 선언된 서브메트릭만** 요약에 집계한다. `scripts/lib/thresholds.js:71`
이 `feature`·`op`·`page` 축만 만들고 `name` 축은 만들지 않는다. 즉 **태그 비용은 매 요청
지불하면서 수확은 하지 않는 상태**다.

**왜 HIGH 인가**

병목을 좁히는 마지막 한 단계가 통째로 없다. `feature=comment` 까지 좁힌 뒤에는 리포트를
떠나 코드를 읽어야 하는데, 그 단계에서 **어느 핸들러를 볼지 리포트가 알려주지 못한다.**
읽기·쓰기·수정·삭제의 성격이 완전히 다른데 한 값으로 뭉개진다.

**고치는 비용이 생각보다 싸다**

`thresholds.js` 는 **`TRAFFIC_SHAPING_FILES` 에 없다**(`perf-run.js:241`). 따라서 여기에 축을
추가해도 **`scriptVersion` 이 바뀌지 않고 기존 계열과의 비교도 끊기지 않는다.**

**단, 재측정이 필요하다.** 저장된 실행에는 `name` 서브메트릭이 없으므로 과거 실행에 소급
적용되지 않는다. **KI-27 Before 세트를 이 축과 함께 다시 재는 것을 검토할 가치가 있다** —
"어느 API 인가"를 Before/After 양쪽에서 봐야 개선을 그 API 에 귀속시킬 수 있다.

**주의.** 축을 늘리면 서브메트릭 수가 늘어 k6 메모리와 remote-write 부하가 커진다.
현재 86개에서 엔드포인트 수만큼 증가한다. smoke 로 먼저 확인한다.

> 관련: T-38(같은 축의 렌더 결함), S-09(한계 시나리오의 기능별 분해)

### T-40. [MEDIUM] 병목 가설의 임계가 포화 판정과 30배 어긋난다 — 상태: **해결** (2026-08-25)

**쉽게 말하면**

같은 실행에서 두 섹션이 반대로 말한다.

```
병목 가설 1순위 : CPU throttling 발생 (8.6%)   ← 점수 100, 최고 순위
자원 포화도     : CPU 50% · throttled 8.6%     ← 여유 있음
```

**무엇이 문제인가 — 같은 지표에 임계가 두 개다**

| 판정 장치 | CPU throttled 임계 | 8.6% 일 때 |
|---|---|---|
| `tools/lib/saturation.js` | warn **30** / fail **80** | `ok` |
| `tools/lib/regression.js:489` | **> 1 → 100점** | **1순위 병목** |

30배 차이다. 게다가 `bottleneckHints` 는 **고정 점수**라 8.6% 든 71% 든 똑같이 100점이다 —
심각도가 반영되지 않는다.

**왜 문제인가.** 읽는 사람이 두 섹션 중 어느 쪽을 믿어야 할지 알 수 없고, 결국 **둘 다
믿지 않게 된다.** 실제 사용자 피드백이 그랬다 — *"포화가 아닌데도 왜 있는지 모르겠다."*

**더 큰 구조 문제.** 같은 지표를 **세 곳이 각자 판정**한다.

```
regression/rules.json    → 게이트      (p95 500ms, p99 1200ms, ...)
tools/lib/saturation.js  → 측정 체제   (throttled warn 30 / fail 80)
tools/lib/regression.js  → 병목 가설   (throttled > 1 → 100점)
```

`rules.json` 주석은 *"코드 수정 없이 이 파일만 고쳐서 기준을 바꾼다"* 를 설계 의도로 적어
두었는데, 실제로는 두 곳이 코드에 임계를 하드코딩하고 있다.

**해야 할 일.** 임계를 `rules.json` 하나로 모으고 나머지가 읽게 한다. 점수는 고정값이 아니라
**임계 대비 초과 배율**로 매긴다.

> 관련: E-46(포화 판정 도입), T-22(시나리오별 판정 규칙)

### T-41. [MEDIUM] 변화율이 노이즈를 큰 변화처럼 표시한다 — `noiseFloor` 가 실측 노이즈보다 작다 — 상태: **해결** (2026-08-25)

**쉽게 말하면**

리포트 상단에 `평균 응답시간 93ms ▲ +26.4%` 라고 크게 뜬다. 그런데 **아무것도 바뀌지 않아도
그 정도는 움직인다.**

**수치**

| 항목 | 값 |
|---|---:|
| `avg` 실측 표준편차 (RATE=4, n=4) | **11.3ms** |
| `rules.json` 의 `avg` noiseFloor | **3ms** |
| 이 실행의 실제 변화량 | 약 19.5ms (≈1.7σ) |

**노이즈 범위인데 +26.4% 로 표시된다.** 다른 지표도 같다.

| 지표 | 실측 표준편차 | noiseFloor | 배율 |
|---|---:|---:|---:|
| p95 | 26.7 ~ 57.6ms | 5ms | **5~11배 작음** |
| p99 | 58.6 ~ 104.9ms | 15ms | **4~7배 작음** |
| avg | 2.6 ~ 11.3ms | 3ms | 경계 |

**`rules.json` 이 막으려던 현상이 그대로 일어나고 있다.** 그 파일 주석은 이렇게 적어 두었다.

> 상대 변화율만 쓰면 이런 항목이 매 실행마다 회귀로 잡히고, 팀은 곧 그 알림을 무시하게
> 된다(경보 피로). 값은 이 환경에서 같은 시나리오를 반복 실행했을 때의 편차를 근거로 정한다.

**장치는 옳게 설계됐고 값이 실측에서 나오지 않았다.** 현재 값은 포화 시절 감각으로 잡힌
것으로 보인다.

**부수 문제 — `p95` 는 fail 임계 자체가 노이즈보다 작다.**

```
p95 단일 실행 비교 MDE = 27.2 ~ 44.7%
rules.json p95 fail    = 20%
```

아무것도 바꾸지 않아도 노이즈만으로 FAIL 이 날 수 있다.

**해야 할 일.** `noiseFloor` 를 실측 표준편차 기반으로 재산정하고(≈2σ), 노이즈 범위 안의
변화는 화살표 대신 **"노이즈 범위"** 로 명시한다. 숨기면 "왜 안 보이지" 가 되고 보여주면
무시하게 되므로, **판정 결과 자체를 표시**하는 것이 답이다.

## T-38 ~ T-41 해결 기록 (2026-08-25) — 리포트 리뉴얼

> 네 항목을 개별 버그가 아니라 **하나의 설계 결함**으로 보고 함께 고쳤다. 근본 원인은
> 리포트가 **"값 표시"와 "판단 지원"을 구분하지 않는 것**이었다 — 165개 지표를 나열하면서
> 각 값이 좋은지 나쁜지는 화면에 없었다. 진단·설계·자기 리뷰는
> [perf-report-redesign.md](../design/perf-report-redesign.md).

**T-38 — `op` 축 렌더.** `report.js` 에 `normalizeCell()` 을 넣어 `byPhase[gatePhase]` 를
최상위 통계로 접어 준다. `count` 는 최상위에 있으므로 얹어서 돌려준다. 저장된 원자료는
멀쩡했으므로 재측정 없이 재생성으로 복구됐다.

**T-39 — API 축.** `thresholds.js` 에 `BREAKDOWN_NAMES` 42개를 선언했다. 태그는 원래부터
`config.js:90` 이 붙이고 있었고 수확만 안 하던 상태였다. `summary.js` 는 축 이름을
하드코딩하지 않아(태그 키를 그대로 축으로 씀) **수정이 필요 없었다.**
`report.js` 는 `name: '엔드포인트별'` 라벨을 이미 갖고 있었고 데이터만 없었다 — 축 순서를
`name` 우선으로 바꿨다.

> **실측 확인 (smoke, 2026-08-25).** 서브메트릭 86 → **170개**(`name` 84개 추가).
> 엔드포인트별 p95 상위: `comment_list` **17.3초**(198건) · `chat_rooms` 5.9초 ·
> `hot_daily` 5.3초. **지금까지 `comment` 하나로 뭉개져 있던 값이 분리됐다.**
> 카디널리티가 약 두 배가 됐으나 k6 실행·remote-write 에 문제 없었다.

**T-40 — 임계 일원화.** `bottleneckHints` 를 고정 점수에서 **심각도 기반**으로 바꿨다
(`pushScaled(base, value, warnAt, failAt, ...)`). 임계는 `saturation.js` 의 `SIGNALS` 와
같은 값을 쓰고, warn 미만이면 **아예 표시하지 않는다.** `rules.json` 의
`cpu.throttledPct` 절대 임계도 warn 1/fail 10 → **warn 30/fail 80** 으로 맞췄다.

> **효과.** 재생성 결과 `CPU throttling(8.6%)` 이 병목 1순위에서 사라지고 실제 병목 두 개
> (`요청당 쿼리 275` · `slow query 147/1000`)만 남았다. 회귀 판정에서도 throttling 경고가
> 사라져 실제 SLO 위반 1건(p99)만 남는다.

**T-41 — noiseFloor 재산정.** p95 5→115ms, p99 15→210ms, avg 3→23ms. 근거는 RATE=4 반복
세트 2건의 표준편차 중 큰 쪽 × 2. `regression.js` 가 `withinNoise`·`noiseFloor` 를
비교 결과에 실어 보내고, `report.js` 가 화살표 대신 **"노이즈 범위 ±23ms"** 로 적는다.
`changePct` 는 건드리지 않았다 — noiseFloor 가 AND 조건이라 절대 하한만으로 임계가 노이즈
위로 올라간다.

**함께 고친 것 — `k6.all` 가드.** 옛 스키마(전체 구간 통계가 `k6.overall`)를 가진 실행
34건이 재생성에서 죽고 있었다. `report.js`·`collect.js` 양쪽에
`record.k6.all || record.k6.overall || {}` 가드를 넣었다. **재생성 실패 34건 → 0건.**

**화면 구조 재배치.** 문서 순서가 진단 순서의 역순이었다(79% → 76% → 32% → 11%).

| | 전 | 후 |
|---|---:|---:|
| Breakdown (어디가 느린가) | 79% | **16%** |
| 작업량 (요청당 비용) | 70%, 인프라 접기 안 | **28%, 독립 섹션** |
| 자원 (인프라 12개 섹션) | 32~72% | **31%, 접힘** |
| 병목 가설 (답) | **11%** | 90%, 접힘 |

신설: **신뢰 확인 줄**(측정·체제·도달률·오류율을 항상 한 줄로). 그 전에는 포화 판정이
`SATURATED` 일 때만 나와 **정상임을 확인할 방법이 리포트에 없었다.**
신설: **가장 느린 API/기능 경고 줄** — 요청 수 상위 구간에서 기여도로 선정한다.

> 실측: 전체 p95 8.25초인 smoke 에서 `가장 느린 API: comment_list 17.32s — 전체 P95의
> 2.1배 (198건 · 전체 요청의 35%)` 가 상단에 표시됐다.

**검증.** 단위 테스트 17건 통과(`repeatability`·`run-lock` 은 Node 18 필요라 제외).
저장된 73건 전체 재생성 성공. smoke 1회 완주.

**남은 것.**
- **Before 세트에는 `name` 축이 없다.** 저장된 실행에 소급되지 않으므로, "어느 API 가
  좋아졌는가"를 말하려면 Before 를 다시 재야 한다.
- `rules.json` 의 `gate`/`display` 임계 분리는 하지 않았다 — 설계 문서 §6 반론 4 참조.
  지금은 게이트 임계 하나로 표시까지 겸한다.
- `noiseFloor` 는 n=3·4 표본에서 나왔다. 정식 5회 세트 후 재검토 대상이다.

### T-42. [HIGH] `run.commit` 이 실제로 측정된 코드를 가리키지 않는다 — 상태: **미해결**

**쉽게 말하면**

모든 실행 기록에 `commit: f915176e` 같은 값이 붙어 있어서, 그 커밋의 코드를 잰 것처럼
보인다. **아니다.** 그 값은 실행할 때의 **작업 트리 git HEAD** 일 뿐이고, 부하를 받는
것은 컨테이너 안의 이미지다. 둘은 아무 관계가 없다.

**현재 동작**

`tools/perf-run.js` 가 `git rev-parse HEAD` 로 읽어 `PERF_COMMIT` 으로 넘긴다. 그런데
앱은 `environment-app` 이미지로 뜨고, 그 이미지는 `docker compose up -d --build` 를
쳤을 때만 다시 만들어진다. 실험 절차에서 실제로 쓰는 두 명령은 이미지를 건드리지 않는다.

| 명령 | 컨테이너 | 이미지 | 코드 |
|---|---|---|---|
| `docker restart perf-app` (`--reset restart` 가 매 회차 쓰는 것) | 껐다 켬 | 그대로 | **그대로** |
| `docker compose up -d app` | 설정 바뀌면 재생성 | **기존 것 재사용** | **그대로** |
| `docker compose up -d --build app` | 재생성 | 다시 빌드 | 반영됨 |

**왜 문제인가**

실측으로 확인했다(2026-08-31).

```
perf-app 이미지 : environment-app:latest, 생성 2026-08-14 13:41 KST (이미지는 이것 하나뿐)
컨테이너 안 jar : app.jar, Aug 14 04:41

jar 안 클래스 검색
  QueryCountFilter   : 0건   ← 커밋 d29d9eb 이 추가한 것. 없다
  QueryMetricsConfig : 0건
  CommentController  : 2건
```

즉 **8/14 이후에 저장된 모든 실행이 8/14 코드를 잰 것**인데, 기록에는 그때그때의
작업 트리 HEAD 가 박혀 있다. EXP-006 의 Before(8/26, `f915176e` 로 기록)와
After(8/29, `d1f97cd` 로 기록)도 실제로는 같은 바이너리였다.

이게 두 방향으로 틀리게 만든다.

1. **없는 차이를 있다고 읽는다.** EXP-006 을 쓰면서 커밋 두 개가 다르니 "바이너리가
   44커밋 다르므로 지연 비교가 무효"로 결론냈다. 컨테이너를 열어 보고서야 틀린 줄 알았다.
2. **있는 차이를 없다고 읽는다.** 이쪽이 더 위험하다. 코드를 고치고 이미지를 다시 만들지
   않은 채 실행하면, 기록은 새 커밋을 가리키는데 잰 것은 옛 코드다. 개선 실험이
   "효과 없음"으로 나와도 **정말 효과가 없는 것인지 코드가 안 들어간 것인지 구분할
   근거가 기록에 없다.**

**비교 판정도 이걸 못 막는다.** `tools/lib/comparability.js` 의 조건 목록에 앱 바이너리가
없다.

| 등급 | 조건 |
|---|---|
| blocking | `scenario` · `environment` · `dataset` · `loadProfile` · `loadgen` · `measurementProfile` |
| degrading | `loadBench` · `remoteWrite` · `scriptVersion` |

`scriptVersion` 은 **k6 부하 스크립트**의 지문이지 앱이 아니다. EXP-006 에서 `incomparable`
판정이 뜬 것은 내가 `--env perf-pool20` 이라는 이름표를 붙였기 때문이고, 이름표를
기본값으로 뒀다면 두 세트는 같은 계열로 묶여 한 추세선에 그려졌을 것이다.

**근거**

- `performance/experiments/EXP-006-pool-sizing/README.md` §9.3
- `docker inspect perf-app --format '{{.Image}}'` → 생성 2026-08-14
- `docker exec perf-app sh -c "grep -c QueryCountFilter app.jar"` → 0
- `tools/lib/comparability.js` 의 `CONDITIONS` 목록

**필요한 조치**

1. **실행마다 이미지 다이제스트를 기록한다.** `docker inspect <app컨테이너> --format
   '{{.Image}}'` 한 줄이면 되고, 이 값은 코드가 바뀌면 반드시 바뀐다.
2. **비교 조건에 degrading 등급으로 추가한다.** blocking 으로 넣으면 이미지를 다시 만들
   때마다 계열이 갈려 추세선이 상시 리셋된다 — `comparability.js:54` 가 `scriptVersion`
   을 degrading 에 둔 것과 같은 이유다.
3. **`commit` 필드의 의미를 문서에 명시한다.** 지우지는 않는다. "어떤 소스로 실험을
   설계했는가"는 그 자체로 쓸모가 있다. 다만 **"무엇을 쟀는가"가 아니라는 것**이
   기록에 드러나야 한다.
4. 여력이 되면 빌드 시 커밋을 이미지 라벨로 굽는다(`--label commit=$(git rev-parse HEAD)`).
   그러면 다이제스트를 사람이 읽을 수 있는 값으로 되돌릴 수 있다.

**소급 적용은 안 된다.** 저장된 실행에는 이미지 다이제스트가 없으므로, 과거 실행의
`commit` 은 앞으로도 "무엇을 쟀는지 모르는 값"으로 남는다. 8/14 이후 실행은 전부 8/14
이미지라는 것만 이 항목의 기록으로 남긴다.
