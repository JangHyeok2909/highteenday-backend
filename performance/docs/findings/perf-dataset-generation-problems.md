## 이 문서의 범위

이 문서는 수정 작업 지시서가 아니다. 구현 순서, 담당자, 일정, 커밋 계획을 정하는 대신 다음
질문에만 답한다.

1. 성능 데이터셋은 어떤 과정을 거쳐 만들어지고 사용되는가?
2. 그 과정의 어느 지점에서 데이터의 의미가 틀어졌는가?
3. 실제 생성 파일과 DB에는 어떤 흔적이 남아 있는가?
4. 이 상태가 성능 수치와 기준선 해석을 어떻게 왜곡하는가?
5. 지금 무엇을 사실로 알고 있고, 무엇은 아직 추론인가?

관련 작업 상태와 실행 계획은 `ROADMAP.md`, `perf-findings-scripts.md`,

이해하기 위한 설명서다.

## 가장 짧은 결론

현재 문제는 단순히 “랜덤 함수 한 줄이 틀렸다”가 아니다.

```text
잘못된 샘플링 규칙
  → 가장 인기 있어야 할 posts[0]에 참여 데이터가 하나도 붙지 않음
  → posts[1]에 댓글과 반응이 과도하게 몰림
  → 그 상태로 JSON과 DB가 만들어짐
  → 이후 k6 샘플러 코드만 올바르게 바뀜
  → 새 k6는 이제 비어 있는 posts[0]을 인기글이라고 자주 조회함
  → 부하 스크립트의 의미와 실제 데이터의 의미가 정반대로 어긋남
```

여기에 다음 문제가 함께 겹쳐 있다.

- 생성 수량이 부족해도 경고만 하고 성공 종료할 수 있다.
- JSON에 기록된 사용자가 실제 로그인·학교 배정에 성공했는지 보장하지 않는다.
- 실제 댓글 행 수와 게시글의 `commentCount`가 다르다.
- 반응·스크랩은 토글 API인데 재시도를 안전하다고 간주한다.
- 같은 `large` 볼륨도 테스트를 반복할수록 데이터가 변한다.
- 생성기나 샘플러가 바뀌어도 데이터셋 이름은 계속 `large`라서 비교 시스템이 구분하지 못한다.
- 문서가 말하는 작성자 분포·단체 채팅·메시지 이력과 실제 생성 결과가 다르다.

따라서 현재 `large`는 “10,000명·100,000글이 있는 데이터셋”이라는 **크기 정보**는 대체로
맞지만, “인기순 정렬·정확한 카운터·같은 조건의 반복 가능한 기준 상태”라는 **의미 정보**는
신뢰할 수 없다.

## 먼저 알아야 할 구조: 데이터셋은 JSON 파일만을 뜻하지 않는다

이 프로젝트에서 성능 데이터셋은 네 층으로 이루어진다.

```text
1. 생성 규칙
   profiles.json + seed.js + 난수 규칙
            │
            ▼
2. 실제 DB 상태
   users / posts / comments / reactions / scraps / friends / chat
            │
            ├──────────────┐
            ▼              ▼
3. k6용 JSON 색인       DB의 비정규화 값
   users.json            posts.commentCount 등
   posts.json
   boards.json
            │
            ▼
4. k6 접근 규칙
   hotPost() / randomPost() / pageIndex()
```

JSON 파일에는 댓글, 반응, 스크랩, 친구, 채팅 데이터가 들어 있지 않다. JSON은 k6가 “어느
사용자로 로그인하고 어느 게시글 ID를 조회할지” 알기 위한 색인일 뿐이다. 실제 부하의 무게는
MySQL 안에 들어 있는 댓글·반응·관계 데이터가 결정한다.

그래서 `posts.json`의 길이가 100,000이라고 해서 데이터셋이 정상이라는 뜻은 아니다.

- 그 ID가 DB에 실제로 존재하는가?
- `posts[0]`이 정말 가장 인기 있는 글인가?
- 댓글·반응·스크랩이 의도한 비율로 붙었는가?
- 게시글에 저장된 카운터가 실제 관계 행 수와 일치하는가?
- 같은 이름의 데이터셋이 실행 사이에 변하지 않았는가?

이 조건까지 맞아야 비로소 같은 데이터셋이라고 말할 수 있다.

## 문제 1. 옛 샘플러는 index 0을 절대 선택할 수 없었다

수정 전 `data.js`와 `seed.js`에는 같은 수식이 복사돼 있었다.

```javascript
Math.floor(Math.pow(n, Math.pow(u, 1 + skew))) % n
```

여기서 `u`는 0 이상 1 미만이다. 항목이 5개라고 생각하면 계산 결과는 다음처럼 제한된다.

```text
u = 0                → 5^0 = 1
u가 1에 가까워짐    → 결과는 5에 가까워지지만 5보다 작음
Math.floor()         → 가능한 값은 1, 2, 3, 4
% 5                  → 여전히 1, 2, 3, 4
```

따라서 배열의 첫 번째 값인 index 0은 확률이 낮은 것이 아니라 **수학적으로 불가능**했다.
표본을 100번 뽑든 1억 번 뽑든 한 번도 나오지 않는다.

마지막 `% n`도 도움이 되지 않는다. 나머지 연산이 0을 만들려면 앞의 값이 정확히 `n`이어야
하지만, 앞의 식은 절대 `n`에 도달하지 못한다. 이 `% n`은 실제로 아무 일도 하지 않는 코드였다.

이것은 배열 인덱스와 사람에게 익숙한 순위 표기를 혼동한 전형적인 한 칸 밀림이다.

```text
사람의 순위: 1등, 2등, 3등 ...
배열 인덱스: 0번, 1번, 2번 ...
```

수식은 1등부터 시작한다고 생각했지만, 그 값을 그대로 배열 인덱스로 사용했다.

## 문제 2. 같은 버그가 부하와 시드 양쪽에 있었다

이 버그는 두 군데에 똑같이 존재했다.

- `performance/scripts/lib/data.js`: k6가 조회할 인기글 선택
- `performance/datasets/seed.js`: 댓글·반응·스크랩을 붙일 게시글과 헤비 작성자 선택

이 때문에 과거에는 두 잘못이 우연히 서로 맞물려 있었다.

```text
시드 생성기: posts[0]에 참여 데이터를 붙이지 않음
k6 부하:     posts[0]을 조회하지 않음
```

이 상태가 올바른 것은 아니지만, 적어도 k6는 비어 있는 글을 인기글이라고 조회하지는 않았다.
문제가 훨씬 선명해지는 순간은 한쪽만 고쳤을 때다.

현재 작업 트리의 `data.js`와 `seed.js`는 공용 `sampling.js`를 사용하도록 수정돼 있다.
새 `hotIndex()`는 index 0부터 마지막 index까지 모두 선택하며 관련 표본 테스트도 통과한다.
하지만 이미 만들어진 JSON과 DB는 자동으로 바뀌지 않는다.

```text
새 k6:       posts[0]을 인기글로 자주 선택
기존 DB:     posts[0]은 댓글·반응·스크랩이 하나도 없는 글
결과:        “가장 인기 있는 글 조회”라는 이름으로 가장 가벼운 글을 조회
```

코드 수정과 데이터 재생성은 하나의 변경으로 취급해야 하는데, 현재는 코드만 앞서가고 데이터가
옛 상태에 남아 있다.

## 실제 증거 1. 현재 생성 파일은 샘플러 수정 이전 세대다

현재 `performance/datasets/generated/`에는 세 프로파일이 있다.

| 프로파일 | 사용자 | 게시글 | 생성 시각 | 특징 |
|---|---:|---:|---|---|
| smoke | 20 | 50 | 2026-08-05 13:16:12 | 옛 샘플러로 생성 |
| small | 100 | 500 | 2026-07-31 13:22:16 | 옛 닉네임 규칙 `perf_user_*`까지 사용 |
| large | 10,000 | 100,000 | 2026-08-05 15:19:55 | 옛 샘플러로 생성 |

파일 구조 자체는 정상이다.

- 사용자 수와 게시글 수는 프로파일 명세와 일치한다.
- 이메일과 게시글 ID는 각 파일 안에서 중복되지 않는다.
- 게시글의 `boardId`는 모두 `boards.json`에 존재한다.

하지만 이 검사는 “파일 모양이 맞다”만 확인한다. 인기순이라는 의미와 DB 관계 데이터의 정합성은
보장하지 않는다.

## 이 버그가 과거 성능 결과에 준 영향

### 핫 로우 경합

핫 로우는 많은 요청이 동시에 한 DB 행을 갱신하는 상황이다. 과거에는 진짜 1위인
`posts[0]`이 아니라 `posts[1]`에 부하가 몰렸다. 더 중요한 점은 그 한 행이 댓글 요청의 약
19%를 받았다는 것이다.

새 분포에서 1위 한 항목의 몫은 `large` 기준 약 8.6%다. 따라서 과거 데이터 생성 중 관측한
최상위 행의 경합은 현실적인 새 분포보다 강했을 가능성이 높다.

다만 이것이 BTL-003 자체를 거짓으로 만들지는 않는다. 동시성 5에서도 데드락이 실제 발생했고,
단일 게시글 row에 비정규화 카운터를 쓰는 구조적 경합도 실제 코드에 존재한다. 믿기 어려운 것은
“경합이 존재하는가”가 아니라 **“그 경합이 어느 정도인가”라는 크기**다.

### 게시글 상세와 댓글 목록 응답시간

과거 k6는 참여 데이터가 많은 `posts[1]`을 지나치게 자주 조회했다. 댓글 목록, 반응 상태,
캐시 지역성은 그 한 글에 과도하게 집중됐다. 반대로 새 코드와 옛 데이터 조합은 비어 있는
`posts[0]`을 자주 조회하므로 응답시간을 실제보다 좋게 만들 수 있다.

### 게시판 페이지

같은 옛 함수를 `zipfIndex(5)`로 사용했기 때문에 0페이지는 한 번도 조회되지 않았다.

```text
0페이지  0.0%
1페이지 60.9%
2페이지 19.0%
3페이지 11.7%
4페이지  8.4%
```

이 문제는 현재 코드에서 페이지 전용 가중치 `[55%, 20%, 12%, 8%, 5%]`로 분리됐다. 다만
이것도 새 코드의 성질이며, 저장된 과거 실행이 소급해서 올바른 페이지 분포로 바뀌지는 않는다.

## 문제 3. 생성 수량이 부족해도 데이터셋이 성공한 것처럼 끝날 수 있다 — 해결 (2026-08-14)

> **해결됨.** 단계마다 검문해서 목표 수량을 못 채우면 다음 단계로 넘어가지 않고 종료 코드
> 1로 끝난다. 미달 시 JSON 산출물도 쓰지 않는다. 허용치를 열고 싶으면 `--tolerance <pct>`로
> 명시해야 하고(기본 0), 허용치가 단계를 살렸다면 로그와 `meta.json` 양쪽에 남는다.
> 검문 기준은 작업 목록 길이가 아니라 프로파일이 선언한 수량이라, `uniquePairs()`가 조합을
> 덜 확보한 경우도 미달로 잡힌다. 실행법은 `performance/datasets/README.md`의 "실패 정책",
> 결정 근거는 `ROADMAP.md`의 P0-1 기록 참고.
>
> 아래는 수정 전 상태의 기록이다.

`seed.js`의 `pooled()`는 각 단계의 성공, 실패, 건너뜀, 재시도를 센다. 이 개선 덕분에 과거처럼
실패를 완전히 숨기지는 않는다. 하지만 현재 동작은 **경고에서 멈춘다**.

```text
목표 400,000건
실제 성공 399,957건
→ “43건 미생성” 경고 출력
→ 다음 단계 계속 진행
→ users.json / posts.json / boards.json 저장
→ 프로세스 정상 종료 가능
```

`pooled()`는 집계 결과를 호출자에게 반환하지 않고, 목표 미달 시 예외도 던지지 않는다. 그래서
사람이 긴 로그 중간의 경고를 놓치면 불완전한 데이터셋이 정상 산출물처럼 남는다.

현재 large DB도 이 상태의 흔적을 가지고 있다.

| 항목 | 명세 | 현재 전체 행 | 현재 활성 행 |
|---|---:|---:|---:|
| 사용자 | 10,000 | 10,000 | 10,000 |
| 게시글 | 100,000 | 100,195 | 100,021 |
| 댓글 | 400,000 | 399,957 | 399,956 |
| 반응 | 1,000,000 | 999,972 | 999,929 |
| 스크랩 | 80,000 | 80,190 | 80,154 |

이 표는 “시드가 정확히 이만큼 틀렸다”는 뜻은 아니다. 게시글과 스크랩의 초과분, 일부 무효
행은 시드 후 실행한 k6 쓰기 테스트가 만든 것이다. 오히려 그 사실이 다음 문제를 보여 준다.

> 데이터셋은 생성 직후에도 미달할 수 있고, 생성 후에는 성능 테스트 때문에 다시 변한다.
> 그런데 둘 다 계속 같은 `large`라는 이름을 쓴다.

## 문제 4. users.json의 사용자 수가 실제 사용 가능한 사용자 수를 뜻하지 않는다

생성기는 먼저 목표 사용자 객체를 메모리에 만든다. 그다음 회원가입, 로그인, 학교 배정을
수행한다. 일부가 실패해도 마지막에는 처음 만든 `users` 배열 전체를 `users.json`으로 쓴다.

따라서 다음 세 숫자가 서로 다를 수 있다.

```text
프로파일에 선언한 사용자 수
users.json에 들어 있는 사용자 수
실제로 로그인하고 필요한 API를 사용할 수 있는 사용자 수
```

현재 large는 10,000명 모두 존재하고 학교도 배정돼 있어 이 항목은 실제로 충족한다. 하지만
코드 구조상 부분 실패를 막아 주는 보장은 없다.

- 가입 409는 모두 “기존 계정”으로 간주한다.
- 로그인 실패는 해당 세션을 비워 둔 채 다음 사용자로 진행한다.
- 학교 배정 실패도 경고 후 전체 생성을 계속할 수 있다.
- 마지막 JSON은 세션이나 학교 성공 여부를 보지 않고 예정 사용자 전원을 저장한다.

이런 사용자가 JSON에 섞이면 k6는 그 계정을 정상 사용자로 배정한다. 결과는 인증 401, 학교
API 400, 친구 검색 실패처럼 나타나며, 서버 성능이 아니라 데이터 준비 실패를 측정하게 된다.

## 문제 5. 실제 댓글 수와 posts.commentCount가 다르다 — 원인 해결 (2026-08-14)

> **애플리케이션을 고쳤다.** `Post.incrementCommentCount()`의 `this.commentCount++`
> (읽고-더하고-쓰기)를 `PostRepository`의 원자 UPDATE로 교체했다
> (`set p.commentCount = p.commentCount + 1`). 감소는 `where p.commentCount > 0`으로
> 하한을 DB가 보장한다. 엔티티의 증감 메서드는 삭제하고 "다시 만들지 말 것" 주석을 남겼다.
> 상세는 [`docs/defects/KI-53`](../../../docs/defects/KI-53-comment-counter-lost-update.md).
>
> **이 수정이 재생성의 선행 조건이었다.** 시더는 Zipf로 인기글에 댓글을 몰아넣고 동시성
> 10으로 돌리므로, **시더 자신이 드리프트를 만든다**. 실측으로 확인했다 — 같은 게시글에
> 동시 댓글 30건을 넣자 성공 6건인데 카운터는 3건만 올랐다. 고치지 않고 재생성했다면
> 새 데이터셋도 끝나는 순간 이미 카운터가 어긋나 P0-2 완료 기준("카운터 == 실제 개수")을
> 통과하지 못했을 것이다.
>
> **기존 large의 13,284건 불일치는 소급 복구되지 않는다** — 재생성으로만 해소된다.
>
> 아래는 발견 당시의 기록이다.

`Post`는 목록과 HOT 점수 계산에서 조인을 줄이기 위해 댓글·좋아요·싫어요·스크랩 수를 자체
컬럼에 저장한다. 이것을 비정규화 카운터라고 한다.

```text
실제 댓글 행                 comments 테이블
빠른 조회용 댓글 수          posts.PST_comment_count
```

두 값은 같아야 한다. 현재 large에서는 같지 않다.

| 비교 | 값 |
|---|---:|
| 활성 댓글 행 | 399,956 |
| 모든 활성 게시글의 `commentCount` 합 | 386,672 |
| 부족한 카운트 | 13,284 |
| 차이 | 약 3.32% |
| 카운터가 실제와 다른 게시글 | 70개 |

특히 옛 분포의 최고 인기글인 ID 3에서 대부분의 차이가 발생한다.

```text
ID 3의 실제 활성 댓글:     76,569
ID 3의 저장된 commentCount: 65,473
차이:                       11,096
```

원인은 인기글에 댓글을 동시에 생성할 때 여러 트랜잭션이 `commentCount++`를 수행하면서 일부
갱신이 유실된 것으로 보인다. 실제 댓글 INSERT는 성공했지만, 같은 게시글 row의 숫자 갱신은
경쟁 과정에서 덮어써진 것이다.

이 불일치는 다음에 직접 영향을 준다.

- 게시글 목록과 상세 응답에 표시되는 댓글 수
- `HotScoreCalculator`가 계산하는 인기 점수
- 인기글 정렬과 캐시 워킹셋
- 댓글 수가 많은 글을 대상으로 한다고 믿는 성능 실험

즉 데이터의 관계 행은 존재하지만, 애플리케이션이 읽는 요약값은 다른 세계를 보여 준다.

반응 카운터와 스크랩 카운터는 현재 전체 합 기준으로 거의 일치한다. 댓글 카운터의 큰 오차가
특히 두드러진다.

> **이 문서는 "데이터가 틀렸다"까지만 다룬다.** 왜 댓글만 틀리고 스크랩은 안 틀리는지,
> 애플리케이션의 어느 코드가 그렇게 만드는지, 어떻게 고칠지는 저장소의
> [`docs/defects/KI-53`](../../../docs/defects/KI-53-comment-counter-lost-update.md)에 있다
> (목록 항목은 `docs/KNOWN-ISSUES.md`의 KI-53).
> 요약하면 댓글은 `commentCount++`(메모리 증감)이고 스크랩은 DB 재계산 후 대입이라,
> 전자만 갱신 유실에 노출된다 — 재조회 결과 스크랩 불일치는 **0건**이다.
> **데이터를 재생성해도 코드를 안 고치면 같은 불일치가 다시 쌓인다.**

## 문제 6. 데이터셋은 테스트를 실행할 때마다 변한다

성능 시나리오는 읽기만 하지 않는다.

- 게시글을 만들고 수정하고 소프트 삭제한다.
- 반응과 스크랩을 토글한다.
- 친구 신청을 만들고 수락한다.
- 채팅방과 메시지를 만든다.
- 알림과 카운터를 누적한다.

그래서 첫 번째 `large` 실행과 열 번째 `large` 실행은 이름은 같아도 DB 상태가 다르다.

현재 DB의 게시글 수가 명세 100,000보다 많은 것도 이 흔적이다.

```text
전체 게시글 100,195
활성 게시글 100,021
무효 게시글    174
```

정상적인 게시글 쓰기 사이클도 삭제가 소프트 삭제이므로 행을 제거하지 않는다. 성공적으로
생성하고 삭제할 때마다 전체 테이블 크기와 인덱스에는 흔적이 남는다. 실행이 중단되거나 Location
처리가 실패하면 활성 글도 남을 수 있다.

이 문제는 단순히 수량이 몇십 개 늘었다는 데 그치지 않는다.

- OFFSET 쿼리가 지나가는 행 수가 달라진다.
- 인덱스와 버퍼풀의 내용이 달라진다.
- 이미 친구인 비율과 아직 신청 가능한 상대 비율이 달라진다.
- 반응·스크랩 토글의 시작 상태가 달라진다.
- 채팅 메시지 페이지 깊이가 실행 순서에 따라 달라진다.

따라서 `DATASET=large`라는 문자열만 같다고 같은 입력 조건이라고 판단할 수 없다.

## 문제 7. 재실행과 재시도의 안전성 가정이 실제 API와 다르다 — 시더 쪽 해결 (2026-08-14)

> **시더는 더 이상 이 결함에 데이터를 잃지 않는다.** `ensureToggled()`가 실패를 두 갈래로
> 가른다 — 데드락·커넥션 고갈처럼 **확실히 롤백된** 경우는 그대로 재시도하고,
> 응답 유실(`ECONNRESET`·`socket hang up` 등)처럼 **적용 여부를 모르는** 경우는 재요청 대신
> `GET /api/posts/{id}`로 상태를 조회해 판정한다. 조회도 실패하면 재시도하지 않고 실패로
> 남긴다. 원칙은 "불확실하면 다시 보내지 말고 확인한다"이다.
> 친구 신청의 409(이미 친구)도 가입 409와 같이 성공으로 센다 — 목표 상태가 이미 성립했기 때문이다.
>
> **서버는 그대로다.** 토글 API가 멱등하지 않다는 사실 자체는 애플리케이션 결함으로
> 별도 등록돼 있다 — [`docs/KNOWN-ISSUES.md`의 KI-54](../../../docs/defects/KI-54-toggle-non-idempotent.md).
> 실사용자와 프론트엔드는 여전히 노출돼 있고, `PUT`/`DELETE` 분리로만 닫힌다.
> 아래는 그 결함의 상세 설명이다.

### 반응과 스크랩은 멱등 요청이 아니라 토글이다

멱등은 같은 요청을 여러 번 보내도 최종 상태가 한 번 보낸 것과 같은 성질이다.

```text
멱등 예시: “좋아요 상태를 true로 설정”을 두 번 실행
토글 예시: “좋아요를 뒤집기”를 두 번 실행
```

현재 반응과 스크랩 API는 토글이다.

- 이미 LIKE 상태에서 LIKE 요청을 다시 보내면 취소된다.
- 이미 스크랩된 글에 POST를 다시 보내면 스크랩이 취소된다.

그런데 `seed.js`는 전송 오류를 “서버에 요청이 도착하지 않은 것이 확실하다”고 보고 재시도한다.
TCP 연결이 끊겼다는 사실만으로 서버가 처리하지 않았다고 단정할 수는 없다. 서버가 커밋한 뒤
응답을 보내는 과정에서 연결이 끊겼을 수도 있다.

그 경우 재시도는 다음처럼 동작한다.

```text
첫 요청: 서버에서 좋아요 생성 성공, 응답만 유실
재시도: 같은 좋아요 요청을 다시 전송
최종 상태: 좋아요 취소
```

게시글과 댓글 생성도 같은 전송 모호성이 있다. 첫 요청이 이미 INSERT를 커밋했다면 재시도는
중복 행을 만들 수 있다. 성공한 재시도의 ID만 JSON에 기록되므로 첫 번째 숨은 행은 산출물에도
나타나지 않는다.

### 전체 시드 재실행도 안전하지 않다

기존 계정은 409로 건너뛰지만 게시글과 댓글은 매번 새로 생성된다. 반응과 스크랩은 기존 상태를
토글할 수 있고 친구 관계도 이미 존재한다. 따라서 같은 DB에 `seed.js`를 다시 실행하는 것은
“같은 데이터 재현”이 아니라 기존 데이터 위에 다른 변경을 쌓는 작업이다.

`environment/bootstrap.js`가 게시글이 이미 있으면 재시드를 막는 이유도 이 때문이다. 다만
이 보호는 bootstrap을 거쳐 실행할 때만 적용되며 `seed.js` 직접 실행에는 적용되지 않는다.

## 문제 8. 장시간 생성 중 토큰 갱신이 서로 경쟁할 수 있다 — 실제로 터짐, 해결 (2026-08-15)

> **"할 수 있다"가 아니라 실제로 일어났다.** 2026-08-14 large 재생성이 이 문제로 중단됐다.
>
> ```text
> register  10,000/10,000   성공
> login     10,000/10,000   성공
> school    10,000/10,000   성공
> posts    100,000/100,000  성공
> comments 399,977/400,000  ← 23건이 401 "Unauthorize request" 로 실패 → 시드 중단
> ```
>
> 앞선 단계가 전부 통과한 뒤 **액세스 토큰 수명(30분)을 넘긴 시점부터** 나타났다.
> 실패율은 0.006%지만 허용치가 0이라 시드가 멈췄고, 그때까지의 수 시간이 날아갔다.
> (fail-fast 자체는 의도대로 동작했다 — 조용히 미달한 데이터셋을 만들지 않았다.)
>
> **원인**: `Session.json()`이 401을 받으면 각자 `POST /api/token/refresh` 를 호출했다.
> 인기 작성자 한 명이 여러 댓글 작업에 동시에 뽑히면 같은 세션으로 여러 요청이 병렬로
> 나가는데, 토큰 만료 순간 그 요청들이 **동시에 401을 받고 각자 갱신**한다. 서버가 refresh
> token 회전을 하므로 먼저 성공한 하나가 나머지의 토큰을 무효화하고, 뒤늦은 갱신은 401로
> 실패한다.
>
> **조치 2가지**
> ⑴ `Session.refreshOnce()` — 진행 중인 갱신이 있으면 그 Promise를 함께 기다린다. 갱신은
> 세션당 한 번만 일어나고 나머지는 새 토큰으로 재시도한다. 쿠키가 `this.cookies` 한 곳에
> 모이므로 누가 갱신했든 결과가 공유된다.
> ⑵ `isRetryable()`에 401 추가 — 401은 인증 거절이라 **서버가 일을 하지 않은 것이 확실**
> 하므로 재시도해도 중복이 생기지 않는다. ⑴로 좁힌 잔여 경로를 한 겹 더 덮는다.
> 세션이 영구히 죽었다면 `MAX_ATTEMPTS`(6) 후 정상적으로 실패로 잡힌다.
>
> **버린 대안 — 허용치를 0에서 올리는 것.** `--tolerance 0.01` 이면 23건은 통과했을
> 것이다. 하지만 그건 원인을 그대로 둔 채 증상만 가리는 선택이고, 그 뒤로는 "몇 건
> 모자란 데이터셋"이 조용히 정상으로 기록된다. 실패 원인이 **재시도로 안전하게 복구
> 가능한 종류**임을 확인했으므로 허용치는 0으로 두고 복구 경로를 고치는 쪽을 택했다.
>
> **함께 고친 것 — 실패가 남긴 낡은 산출물.** 중단된 실행은 정책대로 JSON을 쓰지 않았지만,
> **볼륨 폐기 이전 세대의 `users/posts/boards.json`이 그대로 남아 있었다.** 그 파일의 게시글
> ID는 새 DB에 존재하지 않는다. `meta.json`이 없어 지문 비교는 막히지만 k6는 `posts.json`을
> 직접 읽으므로 없는 ID로 요청을 보내게 된다. 이제 **생성 시작 시점에 기존 산출물을 지운다** —
> 성공하면 새로 쓰고 실패하면 남지 않으므로, "파일이 있으면 현재 DB를 설명한다"가 유지된다.

large 생성은 액세스 토큰 수명 30분보다 오래 걸릴 수 있다. `Session.json()`은 요청이 401을
받으면 refresh token으로 새 access/refresh token을 받은 뒤 요청을 한 번 다시 보낸다.

문제는 하나의 사용자 `Session`이 동시에 여러 생성 작업에 사용될 수 있다는 점이다. 인기
작성자 한 명이 여러 댓글 작업의 작성자로 동시에 선택되면 같은 세션으로 여러 HTTP 요청이
병렬 실행된다.

토큰이 만료되는 순간에는 다음 경쟁이 가능하다.

```text
같은 사용자의 요청 A, B가 동시에 401 수신
요청 A가 refresh 성공 → refresh token rotation으로 기존 토큰 폐기
요청 B가 이미 폐기된 옛 refresh token으로 갱신 시도
요청 B는 401 또는 토큰 오류
```

현재 `Session`에는 사용자별 refresh를 하나로 합치는 잠금이나 공유 Promise가 없다. 실패한
작업은 최종적으로 생성 수량 미달로 이어질 수 있고, 앞에서 본 것처럼 그 미달은 경고만 남긴 채
전체 시드가 성공 종료할 수 있다.

## 문제 9. 고정 난수 시드만으로 완전한 재현성이 생기지는 않는다

`seed.js`는 고정된 LCG 난수 생성기를 사용하고 “같은 프로파일이면 항상 같은 데이터”라고
설명한다. 난수 수열 자체는 재현 가능하다. 하지만 난수를 소비하는 순서는 완전히 고정돼 있지
않다.

일부 `rand()` 호출은 동시 작업의 HTTP 응답 이후에 실행된다.

- 어떤 lane이 먼저 응답을 받는가
- 어느 요청이 재시도되는가
- 재시도 지터가 몇 번 소비되는가
- 토큰 갱신이 발생하는가

이 조건에 따라 다음 난수를 어떤 작업이 가져가는지가 달라질 수 있다. 즉 같은 시작 seed를 써도
네트워크 타이밍과 실패 양상이 다르면 작성자, 게시판, 반응 종류, 이후 친구쌍이 달라질 수 있다.

DB를 새로 만들면 auto-increment ID도 새로 부여된다. 같은 분포를 재현하는 것과 같은 ID·같은
관계를 완전히 재현하는 것은 다른 문제다.

현재 생성기는 **비슷한 통계적 분포를 반복**할 수는 있지만, **바이트 단위로 동일한 데이터셋을
항상 재생성한다**고 말하기는 어렵다.

## 문제 10. 게시글 인기도와 작성자 활동량이 같은 파라미터를 공유한다 — 해결 (2026-08-14)

> **두 축을 분리했다.** `sampling.js`가 `HOT_SKEW = 1.07`(글 인기)과
> `AUTHOR_SKEW = 1.3`(작성 활동)을 따로 선언하고, `seed.js`의 단일 `zipf()`를
> `hotPost()`·`hotAuthor()`로 갈랐다. 두 값이 다시 합쳐지면 테스트가 막는다.
>
> **문서의 1.7은 채택하지 않았다.** 이 항목이 지적한 대로 그 값은 옛 버그 수식의 상수를
> 잘못 읽은 것이라, 진짜 Zipf에 넣으면 옛 코드가 만들던 것보다 훨씬 극단적이 된다.
> large 시뮬레이션에서 s=1.7은 **한 사람이 전체 게시글의 38%를 쓰고 10,000명 중 8,639명이
> 글 0건**이었다. 작성자 기반 조회가 1,361명만 대상이 되고, 단일 사용자 핫로우가 정작
> 재려던 BTL-003을 가린다.
>
> | s | 글 쓴 사용자 | 최다 작성자 | 상위 100명 |
> |---:|---:|---:|---:|
> | 1.07 | 7,996 | 9.9% | 58.0% |
> | **1.3 (채택)** | **4,893** | **19.9%** | **79.9%** |
> | 1.7 | 1,361 | 38.4% | 96.2% |
> | 옛 DB 실측 | 7,438 | 21.8% | 66.7% |
>
> 1.3은 **최다 작성자 비중**이 옛 DB에 가장 가깝다. 옛 분포가 순수 Zipf가 아니라 모든
> 지표가 맞지는 않는다(작성자 수는 적고 상위 100명 비중은 높다 — 머리가 더 무겁다).
> 이번 재생성의 목적은 수식 교정이지 부하 모델 변경이 아니라는 판단으로 골랐다.
> 운영 로그가 쌓이면 실측값으로 교체할 잠정값이다.
>
> 아래는 발견 당시의 기록이다.

현재 공용 `hotIndex()`는 `s=1.07`을 기본값으로 쓴다. `seed.js`의 `zipf()`는 이 기본값을
게시글 선택과 작성자 선택에 모두 사용한다.

하지만 두 분포는 의미가 다르다.

- 게시글 인기도: 어느 글에 댓글·반응·스크랩이 몰리는가
- 작성자 활동량: 어느 사용자가 글과 댓글을 많이 쓰는가

`datasets/README.md`는 작성자 분포를 `Zipf(s≈1.7)`이라고 설명하지만 현재 구현은 게시글과
동일한 `s=1.07`이다. 옛 수식의 `1 + skew = 1.7`을 Zipf 지수 1.7로 해석한 흔적이지만,
옛 수식은 정확한 `1/r^1.7` Zipf 분포가 아니었다.

즉 지금 확인된 것은 다음 두 가지다.

1. 문서에 적힌 작성자 `s≈1.7`과 현재 코드의 값은 일치하지 않는다.
2. 게시글과 작성자가 반드시 같은 집중도를 가져야 한다는 실측 근거는 없다.

이것은 index 0 버그처럼 명백한 계산 오류라기보다, 서로 다른 현실 가정을 하나의 상수로 묶은
모델링 문제다.

현재 large DB의 옛 작성자 분포는 매우 강하게 편중돼 있다.

```text
게시글을 한 건 이상 쓴 사용자: 7,438 / 10,000
최다 작성자 게시글:            21,852
상위 100명 게시글 비중:         66.73%

댓글을 한 건 이상 쓴 사용자:   9,807 / 10,000
최다 작성자 댓글:              87,418
상위 100명 댓글 비중:           66.86%
```

새 `s=1.07`을 작성자에도 적용하면 이 분포 자체가 달라진다. 따라서 샘플러 교체는 단순한
off-by-one 수정뿐 아니라 “헤비 유저가 얼마나 헤비한가”라는 부하 모델 변경도 포함한다.

## 문제 11. 유일한 사용자-게시글 쌍 제약이 반응 분포를 평평하게 만든다

> **실측으로 확인됐고, 영향이 예상보다 크다 (2026-08-16 large 재생성).** 이 항목은 원래
> "분포가 문서 설명과 다르다"는 **데이터 정확성** 문제로 적혀 있었는데, 실제로는
> **측정을 왜곡하는 문제**이기도 하다.
>
> | 종류 | 가장 뜨거운 글 | 전체 | 최상위 비중 | 시딩 재시도율 |
> |---|---:|---:|---:|---:|
> | 댓글 (제약 없음) | 34,084 | 400,000 | **8.52%** | 0.87% |
> | 스크랩 (제약 있음, 미포화) | 5,022 | 79,998 | 6.28% | 1.96% |
> | 반응 (제약 있음, **포화**) | 9,999 | 999,998 | **1.00%** | 0.59% |
>
> 시뮬레이션 예측(large 1위 글 1.00%)이 실측과 정확히 맞았다. 사용자 10,000명이 상한이라
> 9,999에서 막힌다.
>
> **그래서 반응 부하로 핫로우 경합(BTL-003)을 재면 실제보다 약하게 나온다.** 유니크 제약이
> 부하 분산기 노릇을 하기 때문이다. 반면 운영 트래픽에는 그 상한이 없다 — 토글 API라
> 한 사용자가 눌렀다 취소했다 다시 누르면 같은 행이 매번 갱신된다(KI-54).
>
> 스크랩이 재시도율 1위(1.96%)인 것도 이 구조로 설명된다. 목표 수량(80,000)이 상한
> (10,000×게시글)에 한참 못 미쳐 **포화되지 않고** Zipf 그대로 6.28%가 한 행에 몰린다.
> 반응은 포화돼 퍼지고, 스크랩은 안 퍼진다.
>
> 조치는 데이터셋이 아니라 **실험 설계** 쪽이다 —
> [EXP-003](../../experiments/EXP-003-hot-row-contention/README.md)에 경고와
> 보완안(댓글 경로 병행 또는 토글 반복)을 달았다.

반응과 스크랩은 `(사용자, 게시글)` 조합이 유일하다. 한 사용자가 같은 글에 여러 개의 활성
좋아요를 만들 수 없으므로 한 게시글이 가질 수 있는 활성 반응의 최대치는 사용자 수다.

예를 들어 small은 사용자가 100명이다.

```text
어떤 글이 아무리 인기 있어도 활성 반응은 최대 100개
```

샘플러가 같은 인기글을 더 뽑아도 이미 그 글에 반응한 사용자가 다시 나오면 조합을 버리고 다른
표본을 뽑는다. 이 rejection 과정은 원래 멱법칙 분포의 머리를 잘라서 더 평평하게 만든다.

현재 새 `hotIndex()`와 프로파일 수량을 이용해 유일 조합 생성 과정을 시뮬레이션하면 다음처럼
나온다. 이 표는 실제 DB 측정이 아니라 현재 알고리즘의 고정 시드 시뮬레이션이다.

| 프로파일 | 목표 반응 | 1위 글 활성 반응 비중 | 상위 10% 누적 비중 |
|---|---:|---:|---:|
| smoke | 300 | 6.67% | 30.00% |
| small | 5,000 | 2.00% | 48.30% |
| medium | 100,000 | 1.00% | 70.94% |
| large | 1,000,000 | 1.00% | 80.87% |

README는 small만 반응 편중이 사용자 수에 갇힌다고 설명하지만, 원리는 모든 프로파일에
적용된다. large는 전체 수량이 충분히 커서 상위 10% 누적 비중이 약 80%로 돌아오지만, 1위
글 하나의 비중은 사용자 수 상한 때문에 1%에서 막힌다. medium도 목표 80%에 못 미친다.

댓글에는 사용자-게시글 유일 제약이 없으므로 같은 샘플러를 써도 더 강한 머리 집중도가 유지된다.
현재 DB에서도 이 차이가 보인다.

| 현재 large 실측 | 상위 10,000글 비중 | 한 글의 최대 행 수 |
|---|---:|---:|
| 댓글 | 88.92% | 76,569 |
| 반응 | 80.51% | 9,992 |
| 스크랩 | 90.92% | 8,263 |

같은 “인기글 편중”이라는 말 아래에서도 댓글, 반응, 스크랩의 실제 분포는 제약 때문에 서로
다르다.

## 문제 12. 친구와 채팅 데이터가 문서의 설명을 모두 충족하지 않는다 — 폴백·연쇄 해결 (2026-08-14)

> **두 가지를 고쳤다.**
> ⑴ 친구 수락의 **폴백을 제거**했다. 예전에는 방금 보낸 신청을 못 찾으면 받은 요청 목록의
> 마지막 항목을 수락했는데(`|| r2.data[r2.data.length - 1]`), 신청이 몰린 사용자는 그 순간
> **엉뚱한 사람의 신청**을 수락한다. 그렇게 생긴 관계 위에 채팅방이 만들어져 "같은 학교
> 클러스터"라는 전제가 조용히 깨진다. 이제 못 찾으면 실패로 남긴다.
> ⑵ `createFriendships()`가 시도 쌍이 아니라 **실제로 친구가 된 쌍만** 채팅 단계로 넘긴다.
> 예전에는 실패한 쌍으로 방 생성을 시도해, 수 시간짜리 large 실행이 마지막 단계에서
> 무너질 수 있었다. 409(이미 친구)는 목표 상태가 성립하므로 포함시킨다.
>
> **단체방과 메시지 히스토리는 여전히 없다.** 아래 지적 중 그 부분은 그대로 남아 있다 —
> 채팅 REST 성능은 계속 `chat-ws.js` 실행 순서에 의존한다.

생성기 상단 설명은 “친구 쌍 일부가 1:1 방 + 소수의 단체방”이라고 말한다. 실제
`createChat()`은 친구쌍 일부에 대해 1:1 방만 만든다. 단체방 생성 코드는 없다.

현재 large DB:

```text
활성 1:1 채팅방: 9,000
활성 단체방:         0
활성 메시지:       482
```

메시지 482개도 시드가 만든 것이 아니다. `seed.js`는 “메시지 히스토리는 chat-ws.js 첫
실행이 자연스럽게 쌓는다”고 명시하고 방만 만든다.

이 때문에 채팅 REST 성능은 실행 순서에 의존한다.

```text
chat-ws 실행 전  → 방은 많지만 메시지 이력은 비어 있음
chat-ws 실행 후  → 일부 방에만 메시지가 쌓임
반복 실행 후     → 메시지 수와 페이지 깊이가 계속 증가
```

단체방 팬아웃, 큰 방 참여자 조회, 오래된 메시지 커서 페이징을 측정한다고 생각해도 현재 기본
시드만으로는 그 상태가 만들어지지 않는다.

친구 생성에도 별도 위험이 있다. 친구 신청 수락 시 방금 보낸 사람의 요청을 정확히 찾지 못하면
받은 요청 목록의 마지막 항목으로 폴백한다. 여러 신청이 동시에 들어온 사용자는 의도한 요청이
아닌 다른 요청을 수락할 가능성이 있다. 또한 `createFriendships()`는 실제 성공한 쌍이 아니라
시도 대상으로 만든 `pairs` 전체를 채팅 단계에 넘긴다. 친구 생성 실패가 있으면 채팅방 생성도
연쇄적으로 실패할 수 있다.

## 문제 13. 데이터셋 이름만 같으면 비교 시스템은 같은 데이터로 본다

성능 실행의 비교 조건에서 데이터셋은 `small`, `medium`, `large` 같은 프로파일 이름 하나다.

하지만 같은 `large` 안에서도 다음이 달라질 수 있다.

- 옛 샘플러로 생성했는지 새 샘플러로 생성했는지
- 실제 성공 수량이 몇 개인지
- 생성 후 몇 번의 쓰기 테스트를 수행했는지
- 댓글 카운터를 정합화했는지
- 친구와 채팅 메시지가 얼마나 누적됐는지
- 난수 규칙과 생성기 코드가 어느 버전인지

현재 generated 디렉터리에는 이 정보를 담는 manifest가 없다. `users.json`, `posts.json`,
`boards.json` 세 파일만 있다.

`perf-run.js`의 `scriptVersion`도 실행 진입 파일 하나만 해싱한다. `normal-day.js`가 그대로인
상태에서 `scripts/lib/data.js`나 `sampling.js`만 바뀌면 트래픽 분포는 바뀌어도 진입 파일
지문은 같을 수 있다.

결국 비교 시스템은 다음 두 실행을 같은 조건으로 볼 수 있다.

```text
Before: 옛 샘플러 + posts[0]이 비어 있는 large + 쓰기 실행 전 DB
After:  새 샘플러 + 재생성한 large + 여러 쓰기 실행 후 DB

기록: 둘 다 dataset = "large"
```

이 경우 응답시간 차이가 애플리케이션 코드 때문인지, 데이터 생성 규칙 때문인지, 누적된 DB
상태 때문인지 분리할 수 없다.

## 문제 14. 현재 기본 Node로는 생성기를 실행할 수 없다

현재 셸의 기본 `node`는 `v14.21.3`이다. `seed.js`와 `bootstrap.js`는 전역 `fetch`를 사용하기
때문에 Node 18 이상을 요구하고, 시작 시 이를 검사해 종료한다.

즉 현재 터미널에서 문서의 명령을 그대로 실행하면 데이터 생성이 시작되지 않는다.

```text
node datasets/seed.js ...
→ Node 18+ 필요 오류
```

이것은 데이터 의미를 왜곡하는 문제는 아니지만, 재생성 과정에서 반드시 마주치는 현재 환경의
실행 조건이다. 코드 주석은 Node 22.23.1 사용 예를 안내하고 있으며, 이번 분석의 샘플러 테스트는
별도 번들 Node 24.19.0에서 실행했다.

## 현재 무엇을 믿을 수 있는가

### 믿을 수 있는 사실

- generated의 smoke/small/large JSON은 각 파일 안에서 사용자 이메일과 게시글 ID가 중복되지 않는다.
- 세 프로파일의 사용자·게시글 배열 길이는 `profiles.json` 명세와 일치한다.
- large DB에는 사용자 10,000명이 모두 존재하고 학교도 배정돼 있다.
- 친구 방향 행 60,000개와 1:1 방 9,000개가 존재한다.
- 옛 샘플러가 index 0을 선택하지 못한 사실은 수식과 실제 DB 양쪽에서 확인된다.
- 현재 공용 `sampling.js`의 범위·분포·페이지 가중치 테스트는 통과한다.
- 현재 전체 Node 테스트는 번들 Node 24.19.0에서 183개 모두 통과한다.
- 댓글 실제 행 수와 `posts.commentCount`가 불일치한다.
- 현재 large DB는 명세 생성 직후의 깨끗한 상태가 아니라 이후 쓰기 테스트가 누적된 상태다.

### 제한적으로만 믿을 수 있는 것

- 과거 실험은 핫 로우 경합과 데드락이 실제 존재한다는 증거로는 사용할 수 있다.
- 과거 실험의 P95/P99는 그 당시 잘못된 집중도에서 나온 값이라는 조건을 붙여야 한다.
- 현재 large의 상위 10% 집중도는 계산할 수 있지만, 새 샘플러로 재생성했을 때의 분포로 볼 수 없다.
- 프로파일 이름은 데이터 규모를 대략 설명하지만 정확한 DB 상태나 생성 세대를 식별하지 못한다.

### 현재 그대로 믿으면 안 되는 것

- `posts.json[0]`이 최고 인기글이라는 설명
- 새 샘플러 코드와 기존 generated 데이터가 한 세트라는 가정
- 같은 `large` 이름이면 반복 실행 조건이 같다는 가정
- `seed.js`가 정상 종료하면 모든 목표 수량이 충족됐다는 가정
- `users.json` 길이가 실제 사용 가능한 계정 수와 항상 같다는 가정
- `posts.commentCount`가 실제 댓글 수와 같다는 가정
- 반응·스크랩 재시도나 시드 재실행이 안전하다는 가정
- 기본 시드에 단체방과 충분한 메시지 이력이 있다는 가정
- 고정 PRNG 하나만으로 데이터셋 전체가 완전히 동일하게 재현된다는 가정

## 확인된 사실과 추론을 구분해서 보기

| 구분 | 내용 |
|---|---|
| 사실 | 옛 샘플러의 치역은 `1..n-1`이며 index 0을 만들지 못한다. |
| 사실 | large의 `posts[0]`인 ID 15에는 댓글·반응·스크랩이 0개다. |
| 사실 | `posts[1]`인 ID 3에 활성 댓글 76,569개가 붙어 있다. |
| 사실 | 실제 댓글 399,956개와 저장 카운터 합 386,672개가 다르다. |
| 사실 | 생성 실패와 목표 미달은 경고만 하고 전체 생성을 계속할 수 있다. |
| 사실 | 반응과 스크랩 API는 동일 요청 반복 시 상태가 뒤집힐 수 있는 토글이다. |
| 사실 | 현재 large DB는 게시글·스크랩 등이 명세보다 많고 무효 행도 존재한다. |
| 사실 | 현재 시드는 단체방과 메시지를 생성하지 않는다. |
| 추론 | 과거 최상위 row 경합의 크기는 새 분포보다 과장됐을 가능성이 높다. |
| 추론 | 댓글 카운터 손실은 인기글 동시 `commentCount++`의 lost update 영향으로 보인다. |
| 추론 | 새 k6와 옛 DB 조합은 인기글 상세/댓글 응답을 실제보다 빠르게 보이게 할 수 있다. |
| 추론 | refresh rotation 경쟁은 large 장시간 생성 중 일부 401 미생성을 만들 수 있다. |

추론은 코드 구조와 수치에 근거하지만, 해당 원인을 단독 실험으로 격리한 것은 아니다. 특히
현재 DB는 시드 후 여러 성능 실행을 거쳤으므로 현재 총행 수의 모든 차이를 시더 하나의 책임으로
돌리면 안 된다.

## 이 문제를 이해할 때 헷갈리기 쉬운 지점

### “JSON 개수는 맞는데 왜 데이터셋이 잘못됐다는가?”

JSON은 ID 목록이다. 댓글·반응·스크랩의 실제 상태와 비정규화 카운터는 DB에 있다. ID 100,000개가
있어도 첫 ID가 빈 글이고 카운터가 실제와 다르면 부하의 의미는 틀릴 수 있다.

### “샘플러 테스트가 통과했는데 왜 아직 해결이 아닌가?”

테스트는 새 함수가 올바른 숫자를 뽑는다는 것을 증명한다. 이미 생성된 DB를 새 분포로 다시
만들어 주지는 않는다. 코드 검증과 데이터 마이그레이션은 별개다.

### “과거 결과는 전부 버려야 하는가?”

전부 같은 가치로 버릴 필요는 없다. 데드락 로그와 락 경합의 존재는 실제 관측이다. 하지만
정상 분포에서의 정확한 처리량·지연·경합 크기와 직접 비교하는 기준선으로는 부적합하다.

### “현재 large는 행 수가 거의 맞는데 충분하지 않은가?”

성능 테스트에서는 어느 행에 데이터가 몰렸는지가 전체 행 수만큼 중요하다. 100만 반응이 있어도
최상위 글이 누구인지, 카운터가 정합한지, 실행마다 같은 시작 상태인지가 다르면 다른 실험이다.

### “고정 seed면 언제나 같은 결과 아닌가?”

고정 seed는 같은 난수 수열을 만든다. 비동기 HTTP 완료 순서와 재시도가 그 수열을 어떤 작업이
가져가는지 바꿀 수 있다. 통계적 모양은 비슷해도 관계와 ID가 완전히 같다는 보장은 아니다.

## 용어 정리

| 용어 | 이 문서에서의 뜻 |
|---|---|
| index | 배열 위치. 첫 번째는 0이다. |
| rank | 순위. 사람에게 익숙한 첫 번째 순위는 1등이다. |
| Zipf/멱법칙 | 소수의 상위 항목이 대부분의 선택을 받는 편중 분포. |
| 핫 로우 | 동시에 많은 요청이 읽거나 갱신하는 특정 DB 행. |
| 비정규화 카운터 | 빠른 조회를 위해 관계 행 수를 게시글 자체에 복사해 둔 숫자. |
| lost update | 동시에 읽은 옛 값을 각각 갱신하면서 한쪽 증가분이 덮어써지는 현상. |
| 멱등 | 같은 요청을 반복해도 최종 상태가 한 번 실행한 것과 같은 성질. |
| 토글 | 요청할 때마다 켜짐과 꺼짐을 뒤집는 동작. 두 번 실행하면 원상 복귀한다. |
| 기준선 | 이후 실행의 성능 증감을 비교하는 기준 실행. |
| 데이터셋 fingerprint | 생성 규칙, seed, 수량, 상태가 같은 데이터임을 식별하는 지문. 현재는 없다. |

## 최종 이해

이 문제의 핵심은 “데이터가 조금 덜 현실적이다”가 아니다.

성능 실험은 서버 코드뿐 아니라 **어떤 데이터가 있고, 어떤 행을 얼마나 자주 선택하는가**까지
입력 조건으로 삼는다. 현재는 그 입력 조건을 설명하는 이름과 실제 내용이 다르다.

```text
이름: 최고 인기글
실제: 참여 데이터 0건

이름: large 데이터셋
실제: 생성 세대와 실행 누적 상태를 식별할 수 없음

이름: 댓글 400,000개
실제: 행 수 미달 + 게시글 카운터 13,284개 손실

이름: 재현 가능한 고정 시드
실제: 비동기 순서·재시도·DB 누적으로 완전한 동일성은 없음

이름: 현실적인 친구·채팅 데이터
실제: 단체방 0개, 메시지는 이전 테스트 실행에 의존
```

그래서 현재 성능 숫자를 읽을 때 가장 먼저 물어야 할 질문은 “P95가 몇 ms인가?”가 아니다.

> 이 실행이 읽은 데이터와 선택 분포가, 리포트에 적힌 데이터셋 이름이 의미하는 상태와 정말
> 같았는가?

현재 상태에서는 그 질문에 확실하게 “그렇다”고 답할 수 없다. 이것이 데이터셋 생성 문제의
본질이다.
