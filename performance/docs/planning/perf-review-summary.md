# 성능 테스트 시스템 리뷰 — 현재 결론과 실행 순서

- 최초 검토: 2026-08-05
- 마지막 갱신: **2026-08-25** (E-46 해결 반영)

## 한 문장 결론

이 시스템은 **성능 데이터를 모으는 능력은 충분하지만, 그 데이터를 비교하고 PASS/FAIL로
판정하는 과정에는 아직 신뢰성 문제가 있다.** 따라서 현재 결과는 원자료와 기능별 지표를
중심으로 분석하고, 자동 판정은 기준선·결측·측정 구간을 확인한 뒤 사용해야 한다.

> **2026-08-25 추가 — 무엇보다 먼저 확인할 것: 그 실행이 포화 상태였는가.**
>
> E-46 해결(2026-08-21)로 드러난 사실이다. 저장된 실행 119건 중 **49건이 용량을 넘긴
> 상태에서 측정**됐고, 그 실행들의 p95 는 애플리케이션 지연이 아니라 **커넥션 풀 큐 대기
> 시간**이다. 49건은 `reports/archive/runs/` 로 분리했다.
>
> 포화 상태에서는 같은 조건의 세션 간 편차가 **45%** 였다. 포화 이하 운용점(도착률 4/s,
> open model)에서는 **4시간 간격에 1.5%** 다. 같은 시스템, 같은 코드, 같은 데이터셋이다.
>
> 그래서 이 문서의 모든 "믿을 수 있는가" 판단에 축이 하나 추가된다 —
> **지표가 있는가(측정 무결성)** 와 **그 값이 무엇을 뜻하는가(측정 체제)** 는 다른 문제다.
> 상세는 [perf-session-drift.md](../investigations/perf-session-drift.md),
> 레벨 판정은 [perf-trust-levels.md](perf-trust-levels.md).

## 무엇을 믿을 수 있고, 무엇을 조심해야 하나

| 결과 | 현재 판단 | 이유 |
|---|---|---|
| k6 원시 지표 | 조건부로 사용 가능 | 실제 요청 결과지만 사용자 모델과 집계 구간의 영향을 받음 |
| Prometheus 원시 시계열 | 조건부로 사용 가능 | 수집된 값은 유용하지만 cAdvisor 등 환경에 따라 빠지는 지표가 있음 |
| 기능별·작업별 breakdown | 원인 분석에 유용 | 전체 p95보다 어떤 기능이 느렸는지 분리해서 볼 수 있음 |
| 저장된 PASS/FAIL | 그대로 신뢰하면 안 됨 | 과거에는 인프라 규칙 누락, 현재는 기준선 자격과 결측 처리 문제가 남아 있음 |
| 이전 실행 대비 증감률 | 기준선 상태 확인 후 사용 | 조건이 다른 실행은 이제 자동으로 제외되지만, 기준선 자체가 없는 경우가 흔함 |
| 운영 용량 예측 | 현재 불가 | 로컬 단일 호스트와 운영 EC2·RDS 토폴로지가 다름 |
| **포화 상태에서 잰 p95** *(2026-08-25 추가)* | **애플리케이션 지연으로 인용 금지** | 값은 정확하지만 재고 있는 대상이 다르다 — 커넥션 풀 큐 대기다. `SATURATED` 판정 시 리포트가 판정보다 먼저 경고한다 |
| **`normal-day` 외 시나리오** *(2026-08-25 추가)* | **판정 보류** | 용량 곡선을 그려 본 적이 없다. 같은 방식으로 만들어졌으므로 포화일 가능성이 높다 |

여기서 “조건부로 사용 가능”은 숫자가 가짜라는 뜻이 아니다. **숫자가 설명하는 조건을 같이
봐야 한다**는 뜻이다. 예를 들어 p95가 1초라는 값은 사실이어도, 그 p95가 게시글 조회가 아니라
로그인 요청에 의해 만들어졌다면 “게시글 조회 p95가 1초”라고 말할 수 없다.

> **측정 시스템의 문제와 애플리케이션의 문제는 다르다.** 이 문서는 앞의 것을 다룬다.
> 성능 테스트를 돌리다 발견한 **서버 자체의 정합성 결함**은 저장소의
> `docs/KNOWN-ISSUES.md`에 있다 — 댓글 카운터 유실(KI-53), 토글 API 비멱등성(KI-54),
> 게시판 글 개수 캐시 부활(KI-56), 캐시 경로의 빈 목록 반환(KI-57).
> 상세 분석은 [`docs/defects/`](../../../docs/defects/). 측정을 아무리 정확하게 만들어도
> 그쪽은 사라지지 않는다.

## 현재 가장 중요한 문제 6개

### 1. 상대 비교가 아예 이뤄지지 않을 수 있음 — T-02·S-10에서 해결

관련: T-02(해결), S-10(해결, 2026-08-13)

기준선 선택은 원래 “같은 조건에서 실행한 직전 결과”를 찾아야 한다. 두 문제가 있었고 둘 다
해결됐다.

- ~~데이터셋과 VU가 다른 실행을 기준선으로 선택할 수 있다.~~ → **해결**(T-02, 2026-08-09).
  실행 조건을 일급 개념으로 분리해, 시나리오·환경·데이터셋·부하 프로파일이 다르면 기준선에서
  제외하고 그 사유를 리포트에 남긴다.
- ~~threshold에 실패한 실행은 기준선 후보에서 제외된다.~~ → **해결**(S-10, 2026-08-13).
  기준선 자격을 측정 무결성(`UNMEASURED`·measure 구간 미완 제외)과 실행 조건의 비교 가능성
  으로만 판정한다. threshold 결과는 자격이 아니라 “그 실행의 당시 성능 상태”로 리포트에
  표시된다.

EXP-000에서는 동일한 `posts.js` 실행 12건이 모두 threshold에 실패해, 12번째 실행에서도
기준선을 찾지 못하고 매번 “첫 실행”으로 표시됐다. 이제 느린 Before가 기준선이 되므로 개선
전후 비교가 성립한다. 느린 기준선 대비 개선이 거짓 PASS가 되지는 않는다 — 절대 게이트는
기준선과 무관하게 돌기 때문에 3,800ms → 2,200ms(SLO 500ms)는 “42% 개선”과 “FAIL”을 함께
보고한다.

반대 방향의 오염(부하를 약하게 주거나 작은 데이터셋으로 빠르게 나온 실행이 기준선이 되는
문제)은 T-02의 실행 조건 비교가 막는다. 실제로 기준선 오염을 만든 것은 “실패한 느린 실행”이
아니라 “조건이 다른 빠른 실행”이었다.

기준선을 못 찾은 사실도 숨겨지지 않는다. T-02가 도입한 `baselineStatus`
(`compared` / `incomparable` / `first-run`)에 더해, S-10에서 탈락 사유를 `reasonCode`
(`unmeasured` / `window-incomplete` / `conditions`)로 구조화해 콘솔과 HTML 리포트가 같은
문장을 쓰게 했다. 후보가 전부 탈락한 실행을 `first-run`으로 잘못 보고하던 문제도 함께
고쳤다. 저장된 과거 실행은 조건 정보가 없어 여전히 기준선 후보에서 제외되는데, 이는 의도된
동작이며 S-10 수정으로 소급 복구되지 않는다.

### 2. 짧은 실행의 전체 p95가 BCrypt 로그인에 지배됨

관련: S-01, S-02(해결), T-03, EXP-000

기존에는 매 iteration마다 로그인해 전체 요청의 약 20%가 BCrypt였다. 2026-08-11 수정으로
VU마다 한 번만 로그인하도록 바뀌어 로그인 비율은 2.1%까지 내려갔다.

그러나 20 VU가 시작과 동시에 로그인하면 2코어 애플리케이션에서 BCrypt 작업이 한꺼번에
경합한다. 60초처럼 짧은 실행에서는 이 느린 로그인 20건이 여전히 전체 p95 또는 p99에 들어갈
수 있다. S-02 수정으로 인증은 `op:auth`, 도메인 쓰기는 `op:write`로 분리됐지만, 전체 HTTP
지표에는 둘 다 계속 포함된다. 따라서 다음 두 값은 구분해 읽어야 한다.

- 게시글 기능 자체의 지연
- 시나리오 시작 시 세션을 만드는 비용

### 3. 필수 지표가 없어도 결과가 통과할 수 있음 — T-08에서 해결(2026-08-13)

관련: T-08(해결), T-18, E-10

예전에는 지표를 읽지 못하면 판정기가 그 규칙을 SKIP했고, SKIP은 최종 FAIL을 만들지
않았다. 그래서 CPU·MySQL·Redis 지표가 비어 있어도 테스트가 통과했다.

지금은 판정(`verdict`)과 측정 상태(`measurementStatus`)가 별도 축이다. 게이트 지표를
하나라도 받지 못하면 `UNMEASURED`가 되고 종료 코드 3으로 끝난다. “CPU 문제가 없다”와
“CPU를 측정하지 못했다”가 서로 다른 결과로 저장된다.

같은 작업에서 더 위험한 경로 하나를 새로 찾아 함께 막았다. k6는 threshold가 참조한
서브메트릭을 표본이 0건이어도 0으로 채워 준다. 그래서 조기 종료로 측정 구간이 비면
“P95 0ms, 오류율 0%”라는 완벽해 보이는 실행이 만들어지고, 그건 SKIP조차 되지 않는다.
`scripts/lib/phases.js`가 표본 수를 먼저 보고 그런 구간의 통계를 `null`로 되돌린다.

~~Windows Docker Desktop에서 cAdvisor가 컨테이너별 시계열을 만들지 못하는 환경 문제는
그대로 남아 있다(E-10).~~ → **2026-08-14 실측으로 정정.** Run #38에서 인프라 지표 92개가
전부 수집됐고 `measurementStatus`는 `MEASURED`였다. E-10은 현재 주 환경에서 재현되지 않는다.

그동안 E-10의 근거로 본 실행(2026-08-11)의 결측 원인은 cAdvisor가 아니라
`Prometheus 미응답`이었다 — 그 실행의 `infra.errors`에 그대로 기록돼 있다. 스택이 떠 있지
않았던 것이며, T-08은 그 상황을 정확히 `UNMEASURED`로 잡아냈다. 즉 이 절이 말하는 장치는
의도대로 작동했고, 잡아낸 대상을 잘못 해석했던 것이다.

여기서 남는 실질적 위험은 **실행 전에 수집 경로가 살아 있는지 확인하는 절차가 없다는
것**이다(E-13, P0-4). 없으면 스택을 안 띄운 채 20분짜리 테스트를 돌리고 나서야 측정 불가를
보게 된다.

### 4. k6가 만드는 사용 패턴이 실제 사용 패턴과 다름

관련: S-03, S-04, S-06, S-07, S-11~S-19

대표적인 예는 다음과 같다.

- Zipf 샘플러가 가장 인기 있는 `index 0`을 절대 선택하지 못한다.
- 게시판 첫 페이지가 한 번도 조회되지 않는다.
- 한계 탐색 시나리오가 closed model이라 서버가 느려질수록 발생 요청도 줄어든다.
- VU 수가 계정 수보다 많아 여러 VU가 같은 계정을 공유한다.
- 쓰기·알림·친구 저니가 데이터를 소모하지만 실행 사이에 복원하지 않는다.

이 문제들은 서버 코드가 같아도 측정 결과를 바꾼다. 따라서 “부하를 많이 보냈다”보다
“어떤 사용 행동을 어떤 비율과 시간 분포로 보냈는가”를 먼저 확인해야 한다.

### 5. 부하 발생기와 측정 대상이 같은 컴퓨터를 사용함

관련: E-01, E-02, E-09

k6, 애플리케이션, MySQL, Redis, Prometheus, Grafana가 같은 Windows 데스크톱에서 CPU와
메모리를 나눠 쓴다. EXP-000이 확인한 BCrypt CPU 경합은 k6가 같은 호스트의 CPU를 추가로
사용할 때 더 심해질 가능성이 있다.

호스트 지표를 수집하는 node_exporter도 없어 오염 정도를 숫자로 확인할 수 없다. 절대 성능을
주장하려면 발생기를 분리해야 하고, 당장 분리가 어렵다면 최소한 호스트 자원 사용량을 기록해야
한다.

### 6. CI가 실제 품질 게이트로 연결되지 않음

관련: E-23~E-31

성능 회귀 워크플로 초안은 있지만 `.github/workflows/`에 설치되지 않았다. 그대로 설치해도
PR 트리거가 없고, 시딩 절차는 bootstrap을 건너뛰어 실패하며, 공유 러너의 성능 노이즈도 크다.

현재 성능 테스트는 “자동으로 머지를 막는 게이트”가 아니라 “로컬에서 실행해 분석하는 도구”다.
로컬 측정 무결성을 먼저 고친 뒤 CI 역할을 결정해야 한다.

## 2026-08-18 재독 — "결과가 아니라 코드를 다시 읽어서" 나온 것들

지금까지 발견은 대부분 **실행 결과를 보다가** 나왔다. 이번에는 반대로, 저장된 58개 실행이
전부 정상으로 보이는 상태에서 판정 코드와 앱 코드를 다시 읽었다. 5건이 나왔고 그중 하나는
**저장된 실행 어디에서도 발동한 적이 없어 결과만 봐서는 영영 안 보이는 종류**였다.

| 항목 | 무엇 | 왜 결과로는 안 보였나 |
|---|---|---|
| T-32 (해결) | degraded 강등이 절대 SLO 게이트까지 껐다 | 저장된 58건 중 `degraded`가 0건 — 조건이 갖춰진 실행이 아직 없었다 |
| T-33 (해결) | 유효 표본 1회일 때 CV를 0%로 보고 | 지금까지 유효 표본이 항상 2회 이상이었다 |
| E-47 | 캐시 상태를 재지만 판정에 쓰지 않고, 라벨 근거도 부정확 | 절차에 `FLUSHALL`이 있어 20건 전부 `cold` — 라벨이 항상 맞았다 |
| KI-56 | 게시판 글 개수 캐시가 만료 후 1로 부활 | 실행마다 Redis를 비우므로 캐시 만료 구간에 들어가지 않는다 |
| KI-57 | `page × size ≥ 50`이면 빈 목록 반환 | 부하 스크립트가 `size=10`·페이지 0~4만 쓴다 — 구조적으로 못 밟는다 |

**교훈은 하나다.** "테스트가 통과했다"와 "그 경로가 실행됐다"는 다르다. 뒤의 셋은 전부
부하 시나리오가 **밟지 않는 경로**에 있었다. 부하 모델을 넓히는 것(S-14·S-19 계열)이
커버리지 문제이기도 하다는 근거로 쓸 수 있다.

## 다음 실험을 시작할 수 있는 조건

다음 조건을 만족하기 전에는 “개선 전과 개선 후의 차이”를 확정적인 회귀 결과로 발표하지 않는다.

- **모든 회차의 포화 판정이 `HEADROOM` 이다.** *(2026-08-25 추가, 가장 먼저 확인할 것)*
  `SATURATED` 나 `NEAR_LIMIT` 이 섞이면 그 회차의 p95 는 큐 대기라 같은 모집단이 아니다.
  새 시나리오나 새 환경이면 **용량 곡선을 최소 3점 먼저 그린다.** `normal-day` 는
  `RATE=4`(open model)로 확정돼 있다.
  *(2026-08-26 보강: 반복 세트에서 이 조건에 걸리는 회차는 **순서와 무관하게** 표본에서
  뺀다. 두 세트에서 각각 1회차와 2회차가 걸렸고, 원인은 커넥션 풀이 15초간 고갈된 사건이다
  — E-51.)*
- **개선 폭이 MDE 를 넉넉히 넘는지 본다 — 경계에 걸리면 `queriesPerReq` 를 함께 본다.**
  *(2026-08-26 추가)* 부하 대상을 매 회차 무작위로 뽑는데 요청 비용이 542배 벌어져 있어,
  **앱이 동일해도 총 작업량이 CV 4.8% 로 달라진다.** 지연만 달라지고 `queriesPerReq` 가
  같다면 표본 탓일 수 있다. 상세: [perf-request-cost-skew.md](../investigations/perf-request-cost-skew.md).
- **개선 폭이 MDE 를 넘는지 확인한다 — 지표에 따라 문턱이 다르다.** *(2026-08-25 추가)*
  새 운용점 실측(3세트 10회) 기준 5회 세트 비교 MDE 는 **전체 p95 12~20%, p99 4~6%** 다.
  옛 확정치(CV 3.12% → 5%·10%)는 포화 상태 값이라 무효다.
  **주의: 퍼센트 문턱이 높아진 것은 측정이 나빠져서가 아니다** — 절대 표준편차는
  369ms → 27~58ms 로 6~14배 줄었고, 분모가 되는 p95 평균이 11,821ms → 278~364ms 로 작아진
  결과다. 잡아낼 수 있는 개선의 **절대 크기는 465ms → 34~73ms 로 좋아졌다.**
  상세: [perf-trust-levels.md](perf-trust-levels.md) "측정 가능한 최소 개선 폭".
- 비교 대상의 데이터셋·부하 프로파일·스크립트 버전이 일치한다. 이 검사는 T-02 수정으로
  자동화됐지만, 리포트에 표시된 조건을 눈으로 한 번 더 확인한다.
- 기준선이 실제로 선택됐다. 즉 `baselineStatus`가 `compared`이고 `baselineRunId`가 기록돼 있다.
  `incomparable`이나 `first-run`이면 상대 증감률은 존재하지 않는다.
- 필수 인프라 지표의 결측 여부가 리포트에 표시된다.
- 같은 조건을 여러 번 실행해 평균뿐 아니라 분산과 CV를 확인한다.
- 전체 p95와 함께 기능별 p90·p95·p99, 요청 수를 기록한다.
- 테스트 중 timeout 상한에 걸린 값은 검열된 값으로 표시한다.
- 작업 트리가 깨끗하고 실행 기록의 commit에 `+dirty`가 붙지 않는다.
