## 먼저 알아야 할 결론

현재 시스템은 테스트를 실행하고 보고서를 만들 수 있고, **포화 이하 운용점에서는 재현도
된다**(4시간 간격 −1.5%). 남은 제약은 다음과 같다.

**아직 유효한 제약**

1. **판정용 측정은 포화 이하에서만 해야 한다.** *(2026-08-25 신설, 가장 중요)*
   `normal-day` 는 `RATE=4`(open model)로 확정됐다. 포화 상태의 p95 는 애플리케이션 지연이
   아니라 커넥션 풀 큐 대기이며, 그 영역에서는 세션 간 편차가 45% 다. 도착률을 고정해도
   절벽을 넘을 수 있으므로(`#115`) 매 실행의 포화 판정을 확인한다.
2. **`normal-day` 외 시나리오는 용량 곡선이 없다.** `read-heavy`·`write-heavy` 등은 같은
   방식으로 만들어졌으므로 포화일 가능성이 높다. 쓰기 전에 최소 3점을 재야 한다.
3. **판정 지표를 아직 안 골랐다.** 옛 MDE 확정치(CV 3.12% → 5%·10%)는 포화 상태 값이라
   무효다. 새 운용점에서 3세트 10회를 이미 쟀고, 5회 세트 MDE 가 **전체 p95 기준 12~20%,
   p99 기준 4~6%** 다. 세트를 더 돌려도 CV 는 안 줄어든다 — 지표를 고르는 것이 일이다.
   *(퍼센트 문턱이 올라간 것은 측정이 나빠져서가 아니다. 절대 표준편차는 369ms → 27~58ms
   로 줄었고 p95 평균이 11,821ms → 278~364ms 로 작아진 결과다.)* → 아래 P0.
4. 한 번의 실행끼리 비교하며, 60초 타임아웃에 잘린 값도 실제 지연처럼 다룬다.
5. 저장된 과거 실행 119건 중 49건이 `SATURATED` 로 아카이브됐다. 남은 70건도 전부
   안전하지는 않다(`NEAR_LIMIT` 6건).

## P0 — 다음 신뢰 가능한 성능 비교 전에 반드시 처리

### 0. 외부 노출 가능성부터 확인

#### 현재 위험

- 성능 환경 Compose와 예제 파일에 실행 가능한 HS512 키가 기본값으로 들어 있다.
- 운영 배포는 GitHub Secret의 `JWT_KEY`를 사용하지만, 실제 운영 키가 공개된 성능 키와 다른지는
  저장소만 보고 증명할 수 없다.
- 인증 없는 Prometheus 원격 쓰기 경로가 외부 네트워크에 노출될 가능성이 있다.
- Pages 게시 작업은 성능 보고서 디렉터리의 내부 메타데이터까지 공개할 수 있다.

이 항목은 “현재 운영 키가 유출됐다”는 확정 판정이 아니다. **확인하지 않은 상태의 피해 규모가
너무 크기 때문에 가장 먼저 검사하는 항목**이다.

#### 할 일

- 운영 `JWT_KEY`가 공개된 성능 키와 다름을 값 출력 없이 지문 비교로 확인한다.
- 같다면 운영 키를 즉시 교체하고 기존 토큰을 무효화한다.
- 성능 Compose의 실행 가능한 기본 키를 제거하고 로컬 전용 환경 변수 입력을 강제한다.
- Prometheus remote-write 수신 포트의 바인딩과 방화벽 범위를 확인한다.
- Pages 게시 대상에서 executor, 내부 경로, 커밋·호스트 정보, 환경 설정을 제거하거나 마스킹한다.

#### 완료 기준

- [ ] 운영 JWT 키가 공개 성능 키와 다르다는 확인 결과만 기록되고 원문 키는 어디에도 출력되지 않음
- [ ] 성능 환경이 명시적인 로컬 키 없이는 시작되지 않음
- [ ] remote-write 경로가 로컬 또는 허용된 사설 네트워크에서만 접근 가능
- [ ] 공개 Pages 산출물에 내부 실행 메타데이터가 없음

관련: E-14, E-29, E-34

### 1. 시더를 “요청을 보낸 도구”가 아니라 “정확히 만들었음을 증명하는 도구”로 변경 — 대부분 완료 (2026-08-14)

> **완료된 것** (`performance/datasets/seed.js`, 실행법은 `datasets/README.md`의 "실패 정책")
>
> - `pooled()`가 결과를 반환하고 `main()`이 **단계마다 검문**한다. 미달이면 다음 단계로
>   넘어가지 않고 종료 코드 1로 끝난다. 미달 시 JSON 산출물을 쓰지 않는다 —
>   반쪽짜리 데이터셋이 파일로 남으면 다음 실행이 정상으로 착각한다.
> - **허용 실패율과 중단 시점을 별도 축으로 분리**했다. `--tolerance <pct>`(기본 0,
>   단계별 적용, 내림)와 `--on-failure stage|immediate|continue`(기본 stage).
>   허용치가 단계를 살렸으면 로그·`meta.json` 양쪽에 남는다.
> - 검문 기준은 작업 목록 길이가 아니라 **프로파일이 선언한 수량**이다. `uniquePairs()`가
>   조합을 덜 확보해 작업이 300→148건으로 줄면 148건을 다 성공해도 152건 미달로 잡힌다.
> - `users.json`에 **세션이 확인된 계정만** 담는다(계획 목록이 아니라).
> - **토글 재시도를 분리**했다(`ensureToggled()`). 데드락·커넥션 고갈은 확실히 롤백된
>   것이므로 그대로 재시도하고, 응답 유실(`ECONNRESET`·`socket hang up` 등)은 재요청 대신
>   `GET /api/posts/{id}`로 상태를 조회해 판정한다. 조회도 실패하면 재시도하지 않는다.
> - `meta.json`의 지문에 **`stageCounts`(단계별 실제 생성 수)** 를 넣었다. 이전에는
>   users·posts·boards만 들어가서 "댓글이 5% 모자란 데이터셋"과 온전한 것의 지문이 같았다.
> - 부수적으로 **`crypto` import 누락 버그**를 고쳤다. 전 단계를 다 돌린 마지막에
>   `crypto.createHash is not a function`으로 죽어, **데이터셋 지문 기능이 지금까지 한 번도
>   성공한 적이 없었다.** 이번 수정으로 `meta.json`이 처음 생성됐다.
>
> **검증**: 실패를 주입해 세 모드를 각각 확인(stage=단계 완주 후 중단, immediate=허용치
> 초과 시점 중단, continue=끝까지 돌린 뒤 두 번째 실패까지 발견). 허용치 경계는 50건 중
> 2건 실패 상황에서 0%→실패, 2%(1건 허용)→실패, 5%(2건 허용)→통과로 확인.
> 지문 분리는 stageCounts만 다른 identity 세 개로 확인.
>
> **남은 것** — 아래 "할 일"의 4·5·7·8번:
> 계획을 요청 전에 확정해 난수 소비 순서를 네트워크와 분리하는 것(재현성),
> 세션 동시 갱신 경쟁, 친구·채팅 fallback 제거, 생성 후 SQL 재확인.
> 이 넷은 P0-2(재생성)의 차단 요인은 아니다.

#### 현재 문제

- 병렬 작업의 실패는 로그에만 남고 전체 프로세스를 실패시키지 않는다.
- `users.json` 등 생성 산출물이 실제 성공한 리소스가 아니라 만들려고 계획한 리소스를 포함할 수 있다.
- 회원·게시물·댓글 생성은 재실행하면 누적되고, 반응·스크랩 API는 토글이라 재시도하면 원래 상태로
  되돌아갈 수 있다.
- 응답을 받지 못한 쓰기 요청을 재시도하면 서버에는 이미 생성된 리소스가 중복될 수 있다.
- 하나의 세션을 여러 비동기 작업이 공유하면 토큰 갱신 시점에 경쟁할 수 있다.
- 전역 난수를 비동기 완료 순서대로 소비하므로 고정 seed만으로 정확한 재현성을 보장하지 못한다.
- 친구 요청 수락의 fallback과 “시도한 친구 쌍” 재사용 때문에 실제 친구가 아닌 사용자로 채팅방을
  만들 수 있다.

#### 할 일

1. 각 단계가 `target / attempted / succeeded / failed / skipped`를 반환하게 한다.
2. 필수 단계에서 실패가 하나라도 있으면 다음 단계와 산출물 승격을 중단하고 non-zero로 종료한다.
3. 이후 단계에는 **성공이 확인된 ID만** 전달한다.
4. 각 생성 작업의 계획을 네트워크 요청 전에 단일 스레드에서 확정해 파일로 남긴다.
5. 사용자별 세션을 분리하고 같은 세션을 동시에 갱신하지 않는다.
6. POST 재시도와 토글 재시도 정책을 분리한다. 결과가 불명확한 토글은 재요청하지 말고 현재 상태를
   조회해 목표 상태와 비교한다.
7. 친구·채팅은 실제 성공한 관계 ID를 기준으로 연결한다. 임의 fallback은 제거한다.
8. 모든 단계가 끝난 뒤 API 또는 SQL로 실제 수량을 다시 읽어 목표와 대조한다.

#### 현재 문제

생성기의 버전·프로파일·생성 수량을 기록해도 테스트 도중 DB가 바뀌는 문제까지 잡지는 못한다.
현재 large DB의 채팅 메시지가 후속 테스트로 증가한 것처럼, `large`라는 이름과 생성 당시 지문은
같은데 실제 상태는 달라질 수 있다.

읽기 테스트와 쓰기 테스트도 같은 정책을 사용할 수 없다.

- 읽기 테스트: 실행 전후 데이터가 변하지 않아야 한다.
- 쓰기 테스트: 매 실행 전에 같은 스냅샷으로 복원하거나, 변화량을 별도 실행 조건으로 기록해야 한다.

#### 할 일

- 검증이 끝난 DB와 Redis 상태를 하나의 불변 스냅샷으로 만든다.
- 각 실행에 `datasetInstanceId`, 스냅샷 ID, 생성 manifest 지문을 기록한다.
- 핵심 테이블의 활성 행 수와 카운터 합을 실행 전후에 기록한다.
- 쓰기 시나리오는 스냅샷 복원 후 실행하도록 래퍼에서 강제한다.
- 읽기 시나리오에서 상태 변화가 발견되면 측정 결과를 기준선 후보에서 제외한다.
- Redis flush·warm 정책을 실행 조건에 포함한다.

1. 성능 테스트 표준 호스트를 정한다. cAdvisor가 정상 동작하는 Linux 호스트를 우선 후보로 둔다.

##### 지금 무엇이 없나

관측이 **두 갈래로 갈라져 있고 한쪽만 시계열이다.**

| | 실행 중 시계열 | 사후 재질의 | 저장 |
|---|---|---|---|
| 인프라 (앱·MySQL·Redis·컨테이너·호스트) | ✅ 5초 간격 | ✅ 30일 | Prometheus + `run.json`에 요약 |
| **k6 (p95·RPS·오류율·VU)** | ❌ **없음** | ❌ **불가** | 파일 요약본 하나뿐 |

k6는 실행이 끝난 뒤 `handleSummary()`에서 요약본 하나를 남긴다. 20분 실행이면 그 20분 동안
p95가 어떻게 움직였는지는 **어디에도 기록되지 않는다.**

##### 왜 문제인가 — 하필 판정 지표가 그쪽이다

SLO는 k6 기준으로 정의돼 있다(읽기 P95 < 300ms, 쓰기 < 500ms). 서버측 Micrometer 지표로
대신 보면 **큐 대기가 빠진다** — CPU가 100% 포화인 상태에서는 그 대기가 꼬리에 몰리므로
p95·p99에서 크게 벌어질 수 있다. 실측에서 평균은 61ms 차이였지만(k6 5,419ms vs 서버측
5,358ms) 그건 평균이고 판정은 꼬리로 한다.

`k6_vus`가 없어 **"그 순간 몇 명이 붙어 있었나"** 도 모른다. 램프업 곡선과 지연 상승을
겹쳐 보는 것이 부하 분석의 기본인데 지금은 그게 안 된다.

##### 실제로 막힌 사례

"측정 구간을 20분에서 5분으로 줄여도 되나"에 답하려다 막혔다. 저장된 실행에서 **앞 5분만
잘라 p95를 다시 계산할 방법이 없었다** — 데이터가 존재한 적이 없기 때문이다. 결국 서버측
평균이라는 대리 지표로 답했고 결론을 내리지 못했다.

remote-write가 켜져 있었으면 추가 실행 0회로 답이 나왔다.

##### 이미 절반은 준비돼 있다

- Prometheus 수신기가 켜져 있다 — `docker-compose.perf.yml:154`의
  `--web.enable-remote-write-receiver`
- Grafana 대시보드 **1행 세 패널이 k6 지표를 참조하도록 이미 만들어져 있다**
  (`k6 RPS`, `k6 Latency P50/P95/P99`, `k6 Error Rate / VUs`) — 지금은 빈 그래프다.
  `README.md`는 이 배치를 "읽는 순서 = 병목 추적 순서"라고 설명하는데 **그 출발점이 비어
  있다.**
- `metrics/README.md`와 `MANUAL.md`에 명령어까지 적혀 있다

**빠진 것은 `perf-run.js`가 그 옵션을 넘기지 않는 것 하나다**(현재 참조 0건).
Prometheus에 `k6_*` 지표 이름 48개가 남아 있는 것은 과거에 손으로 몇 번 써 본 흔적이고,
30일 보존이 지나 데이터는 사라졌다.

##### 전송 방식이 목적을 가른다 — 히스토그램이어야 한다

**문서와 `MANUAL.md`에 적힌 명령은 `TREND_STATS` 방식인데, 그대로 켜면 목적을 달성하지
못한다.**

```bash
K6_PROMETHEUS_RW_TREND_STATS="p(50),p(95),p(99),avg,max"   # 계산된 통계값만 전송
```

이 방식은 5초마다 **이미 계산된 p95 하나**를 보낸다. 그런데 **분위수는 구간끼리 합산되지
않는다** — 5초 구간 p95 240개를 평균해도 20분 p95가 나오지 않는다. 즉 "저장된 실행에서 앞
5분만 잘라 p95를 다시 계산"이 **근사치밖에 안 된다.**

원본 분포(버킷)를 보내야 임의 구간의 분위수를 정확히 계산할 수 있다.

```promql
histogram_quantile(0.95, sum(rate(k6_http_req_duration[5m])))
```

##### 필요한 것 세 가지 — 확인 결과

| 항목 | 상태 |
|---|---|
| k6 의 `K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM` | ✅ **2.1.0 바이너리에 존재 확인** (`grep -a` 로 심볼 확인) |
| Prometheus `--enable-feature=native-histograms` | ❌ **없음** — 현재 플래그는 `--config.file` · `--storage.tsdb.retention.time` · `--web.enable-remote-write-receiver` 셋뿐 |
| `perf-run.js` 가 옵션 전달 (docker 모드 주소 포함) | ❌ 미구현 |

##### 이걸로 무엇에 답할 수 있나 — 실행 시간 단축

**"측정 구간을 얼마나 줄여도 되는가"에 답이 나온다.**

```text
각 회차의 measure 구간에서 앞 N분만 잘라 p95 계산  (N = 1, 2, ... 20)
  → 각 N 에 대해 회차 간 CV 를 구한다
  → CV 가 허용 범위에 드는 가장 작은 N 이 답
```

CV 가 곧 MDE 의 입력이므로 **"N=8분이면 CV 3.5%, MDE 11%" 같은 교환 비율 표**가 나온다.

**이 사후 분석이 타당한 이유**: 뒤의 시간은 앞의 측정에 영향을 줄 수 없다. 20분 측정의 앞
5분과, 애초에 5분만 측정한 실행의 그 5분은 같은 시스템 상태다(워밍업 300초가 동일하므로).
그래서 잘라 보기가 짧은 실행을 제대로 흉내 낸다.

##### 단서 세 가지

1. **첫 답은 여전히 세트 1회(2시간 반)가 든다.** 켜는 것만으로 과거 실행이 소급되지 않는다.
   **그 이후로는 공짜다** — 조건이 바뀔 때마다 재실행 없이 다시 답할 수 있다.
2. **드리프트(E-46)가 추정치를 보수적으로 만든다.** 20분 세트는 2시간 반에 걸쳐 도므로
   그동안의 드리프트가 CV 에 섞인다. 짧게 줄이면 세트 전체가 짧아져 드리프트가 덜 쌓이므로
   실제 CV 는 더 낮을 수 있다. 방향이 안전한 쪽이라 문제는 아니다.
3. **이 조건에서만 유효하다.** `normal-day` · `medium` · CPU 포화 기준이다. `large` 로 가면
   디스크 I/O 가 붙어 다시 재야 한다(재계산만 하면 된다).

##### 혼동하지 말 것 — 정착 시간과 표본 충분성은 다르다

| | 무엇 | 실측 |
|---|---|---|
| 정착 시간 | 시스템이 정상 상태에 도달하는 시간 | **약 1분** (서버측 평균 기준) |
| 표본 충분성 | p95 *추정치*가 회차 간 안정되는 데 필요한 시간 | **미상** — 위 분석이 답할 값 |

20분을 도는 것은 정착을 기다려서가 아니라 **꼬리 표본을 모으려고**다.
20분이면 요청 29,000건 중 상위 5%가 약 1,450건이고, 5분이면 약 360건이다.
**정착 직후에 끊으면 시스템은 안정됐지만 추정치가 흔들린다.**

##### 주의할 점

1. **컨테이너 모드는 주소가 다르다.** `local`은 `http://localhost:9090/api/v1/write`,
   `--loadgen docker`는 `http://prometheus:9090/api/v1/write`다. `perf-run.js`의 docker
   인자 조립에 `K6_PROMETHEUS_RW_*` 통과 목록을 추가해야 한다.
2. **비교 조건이 바뀐다.** 부하 발생기가 하는 일이 늘어나므로 엄밀히는 같은 조건이 아니다.
   다만 영향은 측정 가능하다 — `loadgen.cores`가 0.108/4 코어로 여유가 크다. 켠 뒤
   `loadgen.throttledPct`를 확인한다.
3. **실험적 기능이다.** 옵션 이름이 `experimental-prometheus-rw`다. k6 버전에 따라 동작이
   바뀔 수 있으므로 버전 고정과 함께 다룬다.
4. **저장 공간이 는다.** 시계열이 수백 개 늘어나고 보존은 30일이다.

##### 언제 하나

**기준선을 새로 잡는 시점에 함께 한다.** 조건이 바뀌어 어차피 새 기준선이 필요하므로 앱
CPU 한계 변경 실험과 묶으면 전환 비용이 0이다. 그 전에 smoke로 전송 여부와 발생기 부담을
먼저 확인한다(`performance/docs/README.md` 의 smoke 규칙).

### 4-b. PMU(하드웨어 성능 카운터)를 켜서 "CPU 1초가 왜 다른 양의 일을 하는가"에 답한다

> **한 줄 요약.** WSL 이 하드웨어 성능 카운터를 게스트에 노출하는 기능을 갖고 있는데
> 기본값이 꺼져 있다. `.wslconfig` 한 줄로 켤 수 있고, 켜면 "같은 CPU 1초가 얼마나
> 효율적으로 쓰였나"(IPC)를 처음 잴 수 있다. 상태: **미적용, 절차 확정** (2026-08-19)

#### 우선순위 재검토 (2026-09-01) — P0 에 둘 근거가 사라졌다

**이 항목이 P0 였던 이유는 "같은 CPU 1초가 왜 회차마다 다른 양의 일을 하는가"에 답할
유일한 계측기라서였다. 그 질문은 PMU 없이 답이 나왔다.** 앱 CPU 가 상한에 붙은 채 처리량만
변한 것은 하드웨어 효율이 달라진 것이 아니라 **큐가 그 차이를 흡수하고 있었기** 때문이다.
운용점을 포화 이하(open model `RATE=4`)로 내리자 세트 사이 차이가 45% → 1.5% 로 줄었다
(2026-08-21).

IPC 자체는 여전히 쓸모가 있다 — 코드 변경이 CPU 효율을 바꿨는지는 요청당 CPU 시간보다
IPC 가 더 직접적으로 답한다. 다만 **이것 때문에 막혀 있는 판정이 지금은 없으므로** 우선순위를
다시 매길 때 P0 밖으로 내려도 된다.

아래 절차와 설계는 그대로 유효하므로 보존한다.
#### 왜 필요한가 — 지금 답할 수 없는 질문

2026-08-19 시점에 남아 있던 질문은 하나로 좁혀져 있었다(아래 "우선순위 재검토" 참조 —
이 질문은 그 뒤 포화 판정으로 답이 나왔다).

> **같은 CPU 1초가 왜 회차마다 다른 양의 일을 하는가.**

2026-08-19 세트의 실측이 이 질문을 만든다. 앱 컨테이너가 CPU 상한(2코어)에 완전히 붙어
있어서 measure 300초짜리 실행의 앱 CPU 소비량이 599.6~600.0초로 **고정**인데, 처리한 요청
수만 7,374 → 6,224 → 6,767 → 5,774 로 변한다. 투입은 상수고 산출만 변한다.

문제는 **현재 지표로는 그 이유를 물을 수 없다**는 것이다(T-36). 풀어야 할 등식은 이렇다.

```
CPU 시간 = 명령어 수 ÷ (사이클당 명령어 × 클럭 주파수)
```

| 항 | 지금 관측되는가 |
|---|---|
| 클럭 주파수 | **부분적** — Windows 전체 평균, 5초 표본. 컨테이너별로도 정밀하게도 못 봄 |
| 사이클당 명령어(IPC) | **전혀 안 됨** |
| 요청당 명령어 수 | **전혀 안 됨** (`queriesPerReq` 는 대리 지표이고 배경 쿼리 43.8% 로 오염) |

`efficiency.*` 계열은 분자(CPU 시간)가 상한에 묶여 고정이고 분모(요청 수)만 변해서 전부
처리량의 역수로 붕괴한다. 그래서 이들을 설명 변수로 쓰면 순환 논증이 된다. 상세 근거와
실측 회귀식은 [perf-findings-tools.md](../findings/perf-findings-tools.md) T-36 에 있다.

#### 현재 상태 — 2026-08-19 확인 결과

**게스트에 PMU 가 노출돼 있지 않다**는 것은 실측으로 확정됐다.

```
/proc/cpuinfo flags        → pdpe1gb, hypervisor   (arch_perfmon 없음)
/sys/bus/event_source/devices/
                           → breakpoint kprobe msr power software tracepoint uprobe
                             (cpu / cpu_core / cpu_atom 없음)
msr 이벤트                  → tsc, smi, pperf       (aperf/mperf 없음)
power 이벤트                → 비어 있음             (RAPL 전력 불가)
/sys/devices/system/cpu/cpu0/cpufreq/  → 없음
커널                       → 6.18.33.2-microsoft-standard-WSL2
CPU                        → i7-13700H (P·E 혼합, 논리 20개)
```

`arch_perfmon` 은 "이 CPU 에 아키텍처 PMU 가 있다"를 알리는 플래그다. Linux 는 이 플래그와
CPUID leaf 0Ah 를 보고 PMU 드라이버를 붙인다. 없다는 것은 **하이퍼바이저가 CPUID 단계에서
PMU 의 존재 자체를 가리고 있다**는 뜻이고, 그래서 게스트 안에서는 권한을 올려도(`--privileged`
확인 완료) 보이지 않는다.

**원인은 Hyper-V 의 구조적 한계가 아니라 WSL 기능 토글의 기본값이다.** 설치된
`C:\Program Files\WSL\wslservice.exe` 에서 확인했다.

- `.wslconfig` 의 `[wsl2]` 섹션이 **`hardwarePerformanceCounters`** 키를 지원한다.
  내부 이름은 `EnableHardwarePerformanceCounters` 이고, `EnableGpuSupport`·`EnableGuiApps`
  와 나란히 놓인 평범한 기능 플래그다.
- 같은 섹션에 `safeMode` 키가 있다. 안전 모드는 기능을 최소화하는 문제 해결용 모드라
  켜져 있으면 이 기능도 함께 꺼진다.
- 설치된 WSL 은 **2.7.10.0**. 이 기능은 0.50.2 부터 들어갔으므로 이 빌드에 포함된다.
- 이 머신에는 **`.wslconfig` 파일 자체가 없다.** 따라서 safeMode 는 기본값(off)이고,
  실제로 추가할 것은 한 줄뿐이다.

#### 적용 절차

**실행 중인 측정이 없을 때만 한다.** 4단계가 Docker Desktop 의 VM 을 통째로 내린다.

1. `docker ps` 로 `perf-k6` 가 없고, `reports/overnight/` 에 도는 실행기가 없는지 확인한다.
2. `%USERPROFILE%\.wslconfig` 를 만든다(없으면 새로 생성).

   ```ini
   [wsl2]
   hardwarePerformanceCounters=true
   ```

   safeMode 는 기본이 off 이므로 적지 않아도 된다. 명시하고 싶으면 `safeMode=false` 를
   같은 섹션에 넣는다.
3. Docker Desktop 을 종료한다(트레이 아이콘 → Quit). 먼저 종료하지 않으면 재기동 때
   컨테이너 상태가 어긋날 수 있다.
4. `wsl --shutdown` — 모든 WSL2 배포판과 Docker 의 VM 이 내려간다.
5. Docker Desktop 을 기동하고 perf 스택을 올린다.

   ```bash
   cd performance
   DATASET_PROFILE=medium docker compose -f environment/docker-compose.perf.yml \
     --env-file environment/.env.perf up -d
   ```
6. 아래 "검증" 을 수행한다.
7. **벤치가 정상 범위로 돌아온 뒤에 측정을 시작한다.** VM 재기동 직후 3회는 5~14% 느리다
   ([perf-session-drift.md](../investigations/perf-session-drift.md) 5절). `node tools/cpu-bench.js --repeat 3`
   의 `single` 이 4,950~5,050ms 로 돌아오는지 확인한다.

#### 검증 — 무엇을 보면 켜진 것인가

```bash
# ① 아키텍처 PMU 플래그가 생겼는가 — 이게 1차 관문이다
docker run --rm alpine grep -o arch_perfmon /proc/cpuinfo | head -1

# ② 코어 PMU 이벤트 소스가 생겼는가 (하이브리드 CPU 라 cpu_core / cpu_atom 로 갈린다)
docker run --rm --privileged alpine ls /sys/bus/event_source/devices/

# ③ 덤으로 실효 주파수 MSR 이 열렸는가 (aperf/mperf 가 있으면 게스트 안에서 클럭을 직접 잰다)
docker run --rm --privileged alpine ls /sys/bus/event_source/devices/msr/events/
```

①이 나오지 않으면 켜지지 않은 것이다. ②에 `cpu_core`(또는 `cpu`)가 보이면 성공이다.

③은 별개 문제다. aperf/mperf 는 코어 PMU 가 아니라 MSR 계열이라 함께 열린다는 보장이 없다.
열리면 **호스트 전체 평균이 아니라 게스트 안에서 잰 실효 주파수**가 생기므로, 현재
`freqPct`(Windows typeperf, 5초 표본)의 정밀도 한계가 해소된다. 안 열려도 ①②만으로 목적은
달성된다.

#### perf 를 실제로 돌리기 위한 조건

PMU 가 열려도 바로 `perf stat` 이 되는 것은 아니다. 세 가지가 더 필요하다.

1. **`kernel.perf_event_paranoid` 완화.** 현재 값은 `2` 이고, 이 값에서는 자기 프로세스
   외의 이벤트나 시스템 전역 측정이 금지된다. 컨테이너 안에서 낮춘다.

   ```bash
   docker run --rm --privileged alpine sysctl -w kernel.perf_event_paranoid=-1
   ```

   VM 재기동 때마다 초기화되므로, 도구화할 때는 측정 시작 전에 한 번 설정하는 절차로 넣는다.
2. **컨테이너 권한.** `--privileged` 또는 최소한 `--cap-add PERFMON`(구 커널은 `SYS_ADMIN`)
   이 필요하다.
3. **perf 바이너리.** Alpine 은 community 저장소의 `perf`, Debian 계열은 `linux-perf` 를 쓴다.
   WSL2 커널 버전과 배포판 perf 버전이 다르면 경고가 뜨지만 대체로 동작한다. 안 되면
   `linux-tools-generic` 을 쓰거나 커널 소스에서 빌드한다.

**무엇을 측정 대상으로 삼는가.** 두 가지 방법이 있다.

- **cgroup 단위**: `perf stat -e cycles,instructions -G <앱 컨테이너 cgroup 경로>` —
  앱만 정확히 잰다. 경로는 `/sys/fs/cgroup/` 아래에서 컨테이너 ID 로 찾는다.
- **시스템 전역**: `perf stat -a` — 측정 중에는 다른 작업을 하지 않는 것이 원래 규칙이라
  전역 값이 곧 perf 스택의 값에 가깝다. 설정이 훨씬 단순하다.

먼저 전역으로 시작해 값이 나오는지 확인하고, 앱과 MySQL 을 분리해 볼 필요가 생기면 cgroup
단위로 넘어간다.

#### 켜지면 무엇을 잴 수 있게 되는가

| 이벤트 | 답하는 질문 |
|---|---|
| `instructions`, `cycles` | **IPC** — 같은 명령어를 더 느리게 실행했는가 |
| `instructions` ÷ 요청 수 | **요청당 명령어 수** — 앱이 실제로 더 많은 일을 했는가 |
| `cache-references`, `cache-misses`, `LLC-load-misses` | 메모리 계층 경합이 원인인가 |
| `msr/aperf`, `msr/mperf` (열리면) | 게스트 안에서 잰 실효 클럭 주파수 |
| `stalled-cycles-frontend/backend` | 정체가 명령어 공급인가 실행인가 (하이브리드 코어에서 미지원일 수 있음) |

**핵심은 분해가 완성된다는 것이다.**

```
요청당 CPU 시간 = 요청당 명령어 수 ÷ (IPC × 실효 주파수)
                  └── 앱 동작        └── 미세구조  └── 클럭
```

이 세 항은 서로 독립이고, **어느 것도 처리량으로 계산되지 않는다.** T-36 이 지적한 순환이
해소되고, "CPU 1초가 왜 다른 양의 일을 하는가" 가 처음으로 답 가능한 질문이 된다.

#### 도구 통합 — 이 작업의 실제 산출물

지표가 손으로만 나오면 회차마다 사람이 붙어야 하므로 실행 기록에 자동으로 남겨야 한다.
`hostprobe`·`loadbench` 와 같은 워커 프로세스 패턴을 쓴다(`perf-run.js` 가 k6 를 `spawnSync`
로 돌려 부모 이벤트 루프가 막히므로, 부모 안의 타이머·스트림은 동작하지 않는다).

- `tools/lib/perfstat.js` + `perfstat-worker.js` (가칭) — measure 창과 **같은 시간대**에
  `perf stat` 을 돌린다. 창 정렬은 `run.phasePlan` 에서 파생시켜 k6·Prometheus 와 같은
  기준을 쓴다(T-03/S-08 과 같은 원칙).
- 결과를 `run.perfStat` 으로 저장한다. `collect.js` 가 상태 블록을 통째로 병합하므로
  수집기 수정은 필요 없다(`loadbench` 에서 확인된 경로).
- 지표 카탈로그(`tools/lib/metrics-catalog.js`)에 파생 지표를 추가한다.

  | 키 | 계산 | 의미 |
  |---|---|---|
  | `cpu.ipc` | instructions ÷ cycles | 사이클당 명령어 |
  | `efficiency.instructionsPerReq` | instructions ÷ 요청 수 | 요청당 실제 작업량 |
  | `cpu.effectiveFreqPct` | aperf ÷ mperf (열리면) | 게스트 기준 실효 클럭 |
  | `cache.llcMissPct` | LLC-load-misses ÷ cache-references | 메모리 계층 경합 |

- 단위 테스트는 `loadbench.test.js` 와 같은 수준으로 넣는다 — 창 정렬, 미완료 시 값을
  만들어내지 않는 것, PMU 미노출 환경에서 조용히 건너뛰고 사유를 남기는 것.

#### 위험 — 이것도 환경 변경이다

1. **`wsl --shutdown` 이 Docker VM 을 내린다.** 실행 중인 측정이 있으면 죽는다. 볼륨과
   이미지는 유지되지만 컨테이너는 재생성될 수 있다.
2. **재기동 직후 3회는 5~14% 느리다.** 벤치가 정상 범위로 돌아온 뒤 시작한다.
3. **PMU 가상화 자체가 오버헤드를 줄 수 있다.** 이게 가장 중요한 위험이다. 확인하지 않으면
   **측정 환경을 조사하려고 그 측정 환경 자체를 바꾼 셈**이 된다.
4. **실행 조건이 바뀐다.** 엄밀히는 PMU on/off 가 서로 다른 환경이다. 오버헤드가 무시할
   수준으로 확인되면 같은 계열로 이어 쓰고, 유의미하면 `seriesHash` 에 반영해 계열을
   갈라야 한다(T-02 의 비교 가능성 조건).

#### 오버헤드 대조 실험 — 반드시 함께 한다

- **Before (PMU off)**: 2026-08-19 실험 7 세트 10회. **이 세트가 그 대조군이다** —
  PMU 를 켜기 전에 확보해 두는 것이 이 순서의 이유다.
- **After (PMU on)**: 같은 명령으로 10회.
  ```bash
  node tools/repeatability.js scenarios/normal-day.js --runs 10 \
    --warmup 180 --hold 5m --dataset medium --env perf --loadgen docker --reset restart \
    --note "PMU on 대조 — 가상화 오버헤드 확인"
  ```
- **비교 방법**: 세트 평균끼리 비교하지 않는다. 세트 안에 방향성 성분이 있어서 평균 비교는
  차이를 과대평가한다(드리프트 문서 8.4, 실측 11.7% 대 6.2%). **같은 회차 위치끼리** 비교한다.
- **판정**: 회차 위치별 차이가 그 설정의 CV 범위(5분 창 기준 2.4~5.3%) 안에 들어오면
  오버헤드는 무시 가능으로 본다.

#### 완료 기준

이 항목을 문서에서 지우려면 다섯 가지를 모두 만족해야 한다.

1. `arch_perfmon` 이 게스트에 보이고, `/sys/bus/event_source/devices/` 에 `cpu_core`
   (또는 `cpu`)가 있다.
2. `perf stat` 이 `instructions`·`cycles` 를 0 이 아닌 값으로 돌려준다.
3. PMU on/off 대조 세트로 오버헤드를 정량화하고, 계열을 이어 쓸지 가를지 결정했다.
4. `run.json` 에 IPC 와 요청당 명령어 수가 자동으로 기록된다.
5. [perf-findings-environment.md](../findings/perf-findings-environment.md) 의 E-48 에 검증 결과를
   기록했다.

#### 안 되면 — 확인 순서

1. `.wslconfig` 위치가 맞는지 확인한다(`%USERPROFILE%\.wslconfig`, `C:\Users\<이름>` 바로 아래).
   `wsl --shutdown` 을 실제로 거쳤는지도 확인한다 — 재기동 없이는 반영되지 않는다.
2. `safeMode` 가 켜져 있지 않은지 확인한다. 켜져 있으면 이 기능도 함께 꺼진다.
3. **Windows 가상화 기반 보안(VBS / Core Isolation / 메모리 무결성)** 을 확인한다.
   이 계층이 PMU 노출을 막을 수 있다. 끄는 것은 보안 설정 변경이므로 사용자 승인이 필요하다.
4. 그래도 안 되면 E-48 의 원래 결론(PMU 사용 불가)으로 돌아가고, **부하 중 cpu-bench**
   (`tools/lib/loadbench.js`, 2026-08-19 도입)로 진행한다. 그쪽은 IPC 를 분해하지는 못하지만
   "컨테이너 밖이냐 안이냐" 는 가른다.

관련: E-46(해결), E-48, T-36, E-09, E-13, P1-9(부하 발생기 물리 분리)

### 5. HTTP 2xx가 아니라 “사용자가 일을 끝냈는가”를 검증

#### 현재 문제

현재 일부 요청은 상태코드만 확인한다. 본문이 비었거나 다음 단계에 필요한 ID가 없어 저니가
중간에 사라져도 성공으로 보일 수 있다. 선언한 저니 비율과 실제 선택·완료 비율도 다를 수 있다.

#### 할 일

- 각 요청에 상태코드와 최소 응답 스키마·필수 ID 검사를 함께 둔다.
- 저니마다 `selected / started / completed / skipped / failed` Counter를 기록한다.
- skip 이유를 `데이터 없음 / 선행 단계 실패 / 인증 실패 / 기능 오류`로 구분한다.
- 알림·친구·채팅처럼 상태를 소비하는 저니는 실행 전 가용 작업 수를 확인한다.
- 목표 저니 비율과 실제 완료 비율을 리포트에 나란히 표시한다.

#### 완료 기준

- [ ] 빈 목록 때문에 아무 일도 하지 않은 iteration이 성공으로 집계되지 않음
- [ ] 모든 저니의 선택 수와 완료 수를 리포트에서 확인할 수 있음
- [ ] 목표 비율과 실제 완료 비율의 차이가 허용 범위 안임
- [ ] skip이 많으면 원인을 한 문장으로 설명할 수 있음

관련: S-12, S-16, S-19

### 6. 한 번의 수치와 60초 상한을 회귀 결과로 사용하지 않기

#### 현재 문제

- 현재 실행 한 번과 기준선 한 번을 비교한다.
- 자연 편차보다 작은 변화도 회귀처럼 보일 수 있고, 반대로 절대 noise floor 때문에 큰 비율 변화가
  숨을 수 있다.
- `60000ms` 부근 p95는 실제 응답 시간이 아니라 클라이언트 timeout에 잘린 값일 수 있다.

#### 할 일

- 같은 조건을 최소 5회 실행해 중앙값, 사분위 범위, CV를 저장한다.
- 단일 run이 아니라 비교 세트끼리 비교한다.
- 반복 편차보다 작은 변화는 확정 회귀로 판정하지 않는다.
- timeout 수와 원인을 별도 Counter로 기록한다.
- 지연이 timeout 상한에 닿은 실행은 `CENSORED`로 표시하고 일반 p95 변화율 비교에서 제외한다.
- `CENSORED` 실행은 오류율, check 성공률, 완료 iteration, dropped iteration을 함께 판정한다.

#### 완료 기준

- [ ] 기준선과 현재값 모두 반복 횟수·중앙값·CV를 가짐
- [ ] 반복 수가 부족하면 확정 PASS/FAIL을 내리지 않음
- [ ] timeout 상한값이 성능 개선률로 계산되지 않음
- [ ] 리포트에서 `MEASURED`와 `CENSORED`를 구분함

#### 실행 시간 — 반복 세트를 감당 가능하게 만들기 (2026-08-18 분석)

##### 왜 이 항목에 붙는가

위의 "최소 5회 반복"이 계속 미뤄지는 실질적 이유는 시간이다. 현행 `normal-day` 1회가
**29.05분**이라 5회 세트에 **145분**이 든다. 실행 시간을 줄이지 못하면 이 항목의 할 일
전체가 실행되지 않는다. 그래서 "얼마나 줄여도 신뢰가 유지되는가"를 먼저 정한다.

##### 결론 — 신뢰 가능한 최소 실행 시간

| 구간 | 현행 | 신뢰 가능한 최소 | 근거 상태 |
|---|---:|---:|---|
| warmup | 300초 | **300초 (유지)** | **미검증** — 줄일 근거가 아직 없다 |
| measure | 1,200초 | **300초** | 실측 + 분산 분해로 확인 |
| rampdown | 120초 | **120초 (유지)** | iteration p99가 129.6초 — 이미 최소에 가깝다 |
| k6 실행 합계 | 27.0분 | **12.0분** | |
| 고정 오버헤드(재시작·health·FLUSHALL·스크레이프 대기) | 2.05분 | 2.05분 | 실측 |
| **회차당 사이클** | **29.05분** | **14.05분** | |

```text
권장 세트: 8회 × 14.05분 = 112분   (현행 5회 × 29.05분 = 145분)
```

```bash
node tools/repeatability.js scenarios/normal-day.js \
  --dataset medium --loadgen docker --runs 8 \
  --hold 300 --note "짧은 반복 세트"
```

`--hold`는 `repeatability.js`와 `perf-run.js`가 이미 그대로 전달한다. **코드 변경이 필요
없다.** `--warmup`을 지정하지 않으면 `scenarios/normal-day.js:29`의 기본값 300초가 그대로
쓰이므로 warmup은 현행과 동일하게 유지된다 — 바뀌는 것은 measure 하나뿐이다.

| | 현행 20분 × 5회 | 권장 5분 × 8회 |
|---|---:|---:|
| 세트 총 시간 | 145분 | **112분** |
| p95 CV | 4.85% (실측) | ~5.3% (추정) |
| 세트 대 세트 MDE (`2·CV·√(2/n)`) | 6.85% | **5.29%** |
| CV 추정치 자체의 오차 (`1/√(2(n−1))`) | ±35% | ±27% |

**시간·민감도·CV 신뢰도 세 축이 모두 개선된다.** 회차 수가 늘어난 효과가 창 축소 손실보다
크기 때문이다.

##### 근거 1 — 저장된 세 세트가 이미 답을 갖고 있었다

`reports/repeatability/` 재계산 결과다.

| 세트 | 구성 | 회차 | p95 평균 | p95 CV | RPS CV | 사이클 | 총 시간 |
|---|---|---:|---:|---:|---:|---:|---:|
| A (08-16) | warmup 5분 + measure **20분** | 5 | 11,821ms | **3.12%** | 2.64% | 29.3분 | 144분 |
| B (08-17) | warmup 3분 + measure **5분** | 8 | 12,838ms | **4.26%** | 3.98% | 12.2분 | 96분 |
| C (08-18) | warmup 5분 + measure **20분** | 5 | 17,695ms | **4.85%** | 3.50% | 29.4분 | 145분 |

**측정 창이 4배 짧은 B가 20분짜리 C보다 CV가 낮다.** 창 길이가 편차의 주된 원인이라면
나올 수 없는 순서다.

> 주의: A·B는 T-31 수정 이전 도구라 `k6.all`(전체 구간) 기준이고 C만 `measure` 구간
> 기준이다. 절대값을 나란히 놓으면 안 된다. 다만 A↔B는 서로 같은 기준이며 그쪽에서도
> 창을 4배 줄였을 때 CV는 1.4배 증가에 그쳤다.

##### 근거 2 — 편차의 93%는 창 길이와 무관하다

한 회차의 p95가 흔들리는 원인은 둘로 나뉜다.

- **분위수 표본오차** — 유한한 요청 수로 p95를 추정하는 통계적 오차. `1/√n`으로 줄어들므로
  **창 길이에만 의존**한다.
- **시스템 잡음** — 회차마다 JVM·OS·VM 상태가 달라 생기는 실제 성능 차이. 창을 늘려도
  안 줄어든다.

분위수 표준오차 `√(p(1−p)/n) ÷ f(x_p)`를 쓰고, 밀도 `f`는 `(p99−p95)/0.04`로 근사했다.

| 세트 C 기준 | 값 |
|---|---:|
| measure 구간 요청 수 | 약 22,600건 |
| 표본오차 성분 `q(20분)` | **1.22%** |
| 관측 CV | 4.85% |
| 시스템 잡음 성분 `s = √(4.85² − 1.22²)` | **4.69%** |

창을 줄이면 `q(T) = 1.22% × √(20/T)` 만 커진다.

| measure | 꼬리 표본 수(약 18 RPS) | 예상 CV | 20분 대비 |
|---:|---:|---:|---:|
| 20분 | 1,080건 | 4.85% | 기준 |
| 10분 | 540건 | 5.00% | +3.1% |
| 8분 | 432건 | 5.07% | +4.5% |
| 6분 | 324건 | 5.19% | +7.0% |
| **5분** | **270건** | **5.29%** | **+9.1%** |
| 4분 | 216건 | 5.42% | +11.9% |
| 3분 | 162건 | 5.65% | +16.5% |
| 2분 | 108건 | 6.07% | +25.2% |

**"CV 열화 10% 이내"를 기준으로 삼으면 하한은 4.6분이다.** 5분은 그 바로 위이고, 여유를
두고 싶으면 6분(+7.0%)을 쓴다. 3분 이하는 꼬리 표본이 200건 밑으로 떨어져 권하지 않는다.

##### 근거 3 — 표본 수집 속도는 못 올린다

"VU를 늘려 요청을 빨리 모으면 되지 않나"는 이 조건에서 통하지 않는다. EXP-001에서 앱
컨테이너 CPU 포화도 100.1%, throttled 99.79%다. 2코어를 전부 쓰고 있어 약 18 RPS가 물리적
상한이다. VU를 늘리면 요청 수는 그대로이고 대기열만 길어진다.

**표본을 늘리는 유일한 레버가 시간**이고, 그 대가가 위 표의 `q(T)`다.

##### 한계 — 이 결론이 답하지 않는 것

1. **표본오차 모델은 요청 독립을 가정한다.** 대기열 때문에 연속 요청이 자기상관을 가지므로
   실효 표본 수가 `n`보다 작고, `q(T)`는 과소평가다. 방향이 짧은 창에 불리하므로 위 표는
   낙관적일 수 있다. 다만 세트 B가 실측으로 반대 방향을 보여 큰 왜곡은 아니라고 본다.
2. **세트 사이 편차는 더 이상 이 계산의 제약이 아니다.** 포화 이하 운용점에서는 4시간
   간격으로 잰 두 세트가 −1.5% 차이였다(2026-08-21 해결). 다만 **위 표 자체가 포화 상태에서
   잰 세트로 만들어졌다** — 그때의 CV 는 애플리케이션 지연의 재현성이 아니라 큐 길이의
   흔들림을 잰 값이다. 새 운용점에서 창 길이별 표본오차를 다시 계산해야 한다.
3. **`measurementProfile`은 blocking 조건이다**(`tools/lib/conditions.js:126`). 짧은 세트는
   자기만의 계열이므로 Before/After 둘 다 짧은 설정으로 재야 한다. 20분 기준선과 직접
   비교할 수 없다.

##### 남은 과제 A — warmup 최소값 구하기 (미측정)

**구조부터 확인해야 한다.** `stagesFor()`(`scripts/lib/phases.js:74`)는 warmup 구간 전체를
`0 → 200 VU` 선형 ramp 한 개로 만들고, `startVusFor()`가 0을 돌려준다. 즉 ramp가 끝나는
그 순간 measure가 시작하며, **"200 VU 도달 후 안정화를 기다리는 시간"이 0초다.**

```text
t=0 ──────── ramp 0→200 ──────── t=300 ──── measure(200 VU 고정) ──── t=1500
                                   ↑ 여기서 바로 판정이 시작된다
```

그래서 최소 warmup은 `ramp 시간 + 정착 시간`의 합으로 봐야 하고, 둘은 방향이 반대다
(ramp를 짧게 하면 스탬피드가 생겨 정착이 늘어난다).

판정 기준은 두 개이고 두 번째가 목적함수다.

- **(a) 정상성** — measure 구간 안에서 p95가 시간 추세를 보이지 않는다.
- **(b) 재현성** — warmup을 더 늘려도 회차 간 CV가 더 줄지 않는다.

(a)만으로는 부족하다. 매번 안정되긴 하는데 **매번 다른 값으로** 안정될 수 있다 — 포화
영역에서 재던 시절에 실제로 그랬다. (b)는 반복 세트로만 답할 수 있다.

| 단계 | 작업 | 비용 | 답하는 것 |
|---|---|---|---|
| 1 | Prometheus 시계열로 구성요소별 정착 시점 확인 | 0회 (보존 30일) | warmup 후보 범위 |
| 2 | `--warmup 60 --hold 1200` 진단 실행 1회 + csv 원자료 분석 | 약 30분 | 정착 시간 실측 (a) |
| 3 | 후보 warmup으로 8회 세트 | 약 2시간 | 재현성 (b), 채택 여부 |

1단계에서 볼 지표: `rate(jvm_compilation_time_seconds_total[30s])`(JIT),
`jvm_memory_used_bytes{area="nonheap"}`(코드 캐시), Redis `hits/(hits+misses)`(캐시 적중률
98.5% 도달), `hikaricp_connections_pending`(정상 수준 192 도달),
`rate(http_server_requests_seconds_count[30s])`(처리량). 가장 늦게 평평해지는 지표가 하한을
정한다. 단 ramp가 300초에 걸쳐 있어 그 구간의 변화는 "정착"이 아니라 "부하 증가"이므로,
1단계만으로는 정착 종료 시점을 확정할 수 없다 — 그래서 2단계가 필요하다.

2단계 실행:

```bash
node tools/perf-run.js scenarios/normal-day.js \
  --dataset medium --loadgen docker \
  --warmup 60 --hold 1200 --no-gate \
  --k6:out "csv=/perf/reports/raw/warmup-probe.csv" \
  --note "warmup 정착 시간 진단"
```

t=60부터 VU가 200 고정이므로 이후 변화는 순수 정착이다. csv를 1분 슬롯 20개로 잘라 슬롯별
p95를 그리면 정착 곡선이 나온다. ramp 60초는 스탬피드를 만들어 정착 시간을 **과대추정**하는
방향이라 안전한 쪽이다.

> **이 csv 방식이 위 4번 항목의 Prometheus native-histogram 계획보다 싸고 정확하다.**
> native-histogram은 Prometheus 기능 플래그 활성화가 선행돼야 하고, `TREND_STATS` 방식은
> 분위수가 구간끼리 합산되지 않아 근사치만 나온다. 요청 단위 원자료는 임의 창의 분위수를
> 정확히 재계산한다. 경로가 `/perf/...`인 것은 `dockerK6Args()`(`tools/perf-run.js:115`)가
> `performance/`를 컨테이너의 `/perf`에 마운트하기 때문이며, `--k6:` 접두사 통과는
> `tools/perf-run.js:365`가 이미 지원한다. 다만 `repeatability.js`는 이 인자를 회차에
> 넘기지 않으므로, 세트 단위로 원자료를 남기려면 한 줄 추가가 필요하다.

##### 남은 과제 B — rampdown 최소값 구하기 (측정은 됐고 판단이 남음)

`rawMetrics.iteration_duration`을 꺼내 보면 rampdown이 기다려 줘야 하는 시간이 바로 나온다.

| 실행 | 중앙값 | p90 | p95 | p99 | 최대 |
|---|---:|---:|---:|---:|---:|
| 08-18 03-09 (measure 20분) | 31.0초 | 95.3초 | 108.3초 | 129.6초 | **165.0초** |
| 08-18 02-40 (measure 20분) | 32.5초 | 95.0초 | 106.5초 | 129.7초 | **167.9초** |
| 08-17 15-46 (measure 5분) | 26.6초 | 72.5초 | 82.0초 | 99.0초 | 114.2초 |
| 08-18 05-12 (measure 20분) | 29.6초 | 88.6초 | 100.4초 | **120.6초** | 159.0초 |

**현행 120초는 넉넉한 값이 아니라 p99 언저리다.** 08-18 05-12 실행은 p99가 120.6초로 rampdown 길이와 거의 정확히 일치한다 — 즉 iteration 100건 중 1건은 지금도 배출 시간을 다 쓴다. 줄일 대상이 아니다. 길이가 이렇게 긴
이유는 산술로 확인된다 — Little의 법칙으로 `평균 iteration = VU ÷ 처리량 = 200 ÷ 4.06 ≈ 49초`
이고 실측 평균 43초와 맞는다. 포화 상태라 요청 하나가 12~17초씩 걸리는데 `journeyBrowse`는
그런 요청을 6~8개 연달아 하고 사이사이 think time까지 넣는다.

무엇을 지킬 것이냐에 따라 최소값이 갈린다.

| 지키려는 것 | 필요 rampdown | 비고 |
|---|---|---|
| iteration을 하나도 안 끊는다 | 약 **170초** | 현행보다 길어야 한다 |
| `k6.all` 오류율 0 유지 | 현행 120초로 **실측 달성 중** | 08-18 실행 27,573건 전부 성공, 전 구간 오류율 0 |
| 판정 구간(measure)만 온전하면 된다 | **0초도 가능** | `gatePhase: 'measure'`라 rampdown은 판정 밖 |

논리적으로 맞는 것은 세 번째다. 다만 **지금은 그게 안전한지 확인할 수단이 없다.** 끊긴
iteration을 셀 방법이 없기 때문이다 — `phase_iterations`(`scenarios/lib/workload.js`)도 k6
내장 `iterations`도 **끝난 것만** 센다. 실측에서 둘 다 6,522로 일치하는데 이건 "끊긴 게
없다"가 아니라 "끊긴 걸 볼 수 없다"는 뜻이다.

**계측 세 줄이면 확정된다.** `mixedIteration()` 맨 앞에 시작 카운터를 넣고,
`scripts/lib/thresholds.js`에 selector를 선언해 서브메트릭을 만든다
(`BREAKDOWN_PAGES`가 `http_reqs{page:N}`을 `count>=0`으로 선언한 것과 같은 방식).

```javascript
// scenarios/lib/workload.js
const startedIterations = new Counter('started_iterations');

export function mixedIteration(profile) {
  const phase = currentPhase();
  if (phase) startedIterations.add(1, { phase });
  // ... 기존 본문
}
```

그러면 `started_iterations{phase:rampdown} − phase_iterations{phase:rampdown}` 이 끊긴
iteration 수가 된다. rampdown을 120/60/30/0초로 바꿔 1회씩만 돌려도 곡선이 나온다(약 1시간).

**확인 전에는 건드리지 않는다.** iteration p95가 108초라 중간값이 의미가 없고, 선택은
사실상 "170초(하나도 안 끊음)" 아니면 "30초(끊김을 받아들이고 measure만 지킴)" 둘 중
하나다. 현행 120초는 얼마나 끊기는지 모르는 어중간한 지점이다.

##### 완료 기준 (실행 시간)

- [ ] `--hold 300` 8회 세트를 돌려 p95 CV가 20분 세트 대비 1.3배 이내임을 확인
- [ ] warmup 정착 시간을 csv 원자료로 실측하고, 후보값으로 재현성(b)까지 검증
- [ ] `started_iterations` 카운터로 rampdown 구간의 끊긴 iteration 수를 관측 가능하게 만듦
- [ ] 위 셋이 끝난 뒤 확정한 `measurementProfile`을 EXP-001 재기준선의 조건으로 고정

## P1 — 운영 용량과 실제 트래픽을 말하기 전에 처리

### 7. stress·spike의 요청 도착률을 서버 속도와 분리

#### 남은 문제

- closed model에서는 서버가 느려질수록 VU가 다음 요청을 늦게 보내 부하가 자동으로 줄어든다.
- breakpoint는 arrival-rate를 사용해도 `maxVUs` 부족으로 서버보다 부하 발생기가 먼저 한계에
  걸릴 수 있다.
- VU 수보다 계정이 적으면 여러 가상 사용자가 같은 계정 상태와 토큰을 공유한다.

#### 할 일과 완료 기준

- stress·spike를 목적에 맞는 arrival-rate executor로 전환한다.
- 정상 구간 실측 RPS를 기준으로 단계별 목표 arrival rate를 정한다.
- `preAllocatedVUs / maxVUs / dropped_iterations`를 함께 저장한다.
- 계정 수를 최대 동시 활성 세션보다 크게 준비한다.
- 부하 발생기 VU 부족과 서버 포화를 서로 다른 종료 이유로 표시한다.

#### small 프로파일의 계정 부족 — 구체적 결정이 필요하다

위 "계정 수를 최대 동시 활성 세션보다 크게 준비한다"의 실제 사례다. 지금 **small 은
`normal-day` 를 돌릴 수 없다.**

| 프로파일 | 계정 수 | `normal-day` 기본 200 VU |
|---|---:|---|
| smoke | 20 | 10배 부족 |
| **small** | **100** | **2배 부족** |
| medium | 1,000 | 5배 여유 |
| large | 10,000 | 50배 여유 |

VU 2개가 한 계정을 공유하면 같은 계정으로 동시 요청이 나가고, **토큰 갱신이 경쟁해 401 이
발생한다** — 서버가 refresh token 을 회전시키므로 먼저 갱신한 쪽이 나머지를 무효화한다.
시더에서 겪은 것과 같은 사고다(`perf-dataset-generation-problems.md` 의 생성 문제 8).
그렇게 오른 오류율은 **서버 성능이 아니라 테스트 설계가 만든 값**이다.

##### 선택지 둘 — 아직 정하지 않았다

**(A) small 의 계정 수를 늘린다** (`profiles.json` 의 `users: 100` → 300 이상)

- 장점: small 로도 표준 시나리오를 그대로 돌릴 수 있다. 빠른 반복 확인이 가능해진다
- 단점: **데이터셋 지문이 바뀌어 재생성이 필요**하고, 기존 small 스냅샷·기준선이 무효가
  된다. 사용자가 3배가 되면 친구·채팅 관계 수도 함께 손봐야 비율이 유지된다
- 주의: 계정만 늘리고 게시글을 그대로 두면 **작성자당 게시글이 3분의 1로 줄어**
  작성 활동 분포(`AUTHOR_SKEW`)가 달라진다. 그것도 다른 데이터셋이다

**(B) small 실행 시 VU 상한을 강제한다**

- 장점: 데이터셋을 안 건드린다. 즉시 적용 가능
- 단점: 부하 조건이 달라져 medium·large 기준선과 비교되지 않는다(`loadProfile` 이 blocking).
  small 은 "빠른 확인용"으로만 남고 판정에는 못 쓴다
- 구현: `perf-run.js` 가 `DATASET` 과 VU 를 대조해 계정 수를 넘으면 **거부하거나 경고**한다.
  프로파일별 계정 수는 `profiles.json` 에 이미 있으므로 조회만 하면 된다

##### 어느 쪽이든 필요한 것 — 자동 검사

**지금은 아무 경고 없이 그냥 돈다.** 사람이 계정 수를 기억하고 있어야 한다.
어느 안을 택하든 `perf-run.js` 가 시작 시점에 `VUS > profiles[DATASET].users` 를 검사하고
알려 주어야 한다. 이 검사가 없으면 같은 실수가 반복된다.

##### 판단 근거가 될 것

`normal-day` 를 small 로 돌릴 일이 실제로 있는지가 핵심이다. **"빠르게 먼저 재 본다"는
목적으로는 쓸모가 없다** — 부하 모델이 시간 기반이라 데이터셋을 줄여도 실행 시간이 줄지
않는다(smoke·small·medium 모두 회당 27분). 실행 시간 단축은 `--hold` 로 해야 한다.

그렇다면 small 의 용도는 "스크립트 개발 중 빠른 확인"뿐이고, 그건 VU 를 낮춰도 되는
작업이다. **그 경우 (B)가 비용이 훨씬 싸다.**

관련: S-06, S-07, S-18

### 8. 정상 회귀와 한계 탐색의 성공 조건을 분리

#### 남은 문제

normal-day와 stress·spike·breakpoint·chaos는 목적이 다르다. 한계에 도달하는 것이 목적인
시나리오에 일반 p95 SLO를 적용하면 정상적인 실험도 실패가 된다. 반대로 모든 지표를 독립 게이트로
두면 같은 현상을 중복 판정하고 오탐 가능성이 커진다.

#### 할 일과 완료 기준

- 시나리오를 `regression / capacity / resilience / diagnostic`으로 분류한다.
- 분류별 필수 지표, 종료 조건, PASS 의미를 별도 규칙 집합으로 만든다.
- 배포 차단 지표와 병목 진단 지표를 분리한다.
- p95·p99·TPS·RPS 중 대표 게이트와 보조 진단값을 정한다.
- 기능별 breakdown이 실제 병목 원인 설명에 연결되게 한다.

관련: S-09, T-22, T-23, T-24

### 9. 부하 발생기와 측정 대상을 분리하고 운영과의 차이를 기록 — 계측 완료 (2026-08-16), 분리는 미해결

> **"분리가 불가능한 실험은 부하 발생기 CPU·메모리를 함께 기록한다"는 아래 항목을 구현했다.**
> `perf-run.js --loadgen docker`로 돌리면 k6가 `perf-k6` 컨테이너로 뜨고 cAdvisor가 별도로
> 계측한다. `--cpus`로 상한도 건다.
>
> **핵심은 `loadgen.throttledPct`다.** 0이 아니면 그 실행의 지연은 서버가 아니라 **부하
> 발생기가 만든 것일 수 있다** — 발생기가 먼저 한계에 걸리면 요청을 제때 못 보내고 그
> 지연이 서버 응답시간으로 기록된다. 서버를 고쳐도 사라지지 않는 가짜 병목이다.
> 임계는 앱보다 낮게(warn 1% / fail 5%) 잡았고 `gate:false`다 — `gate:true`면
> `--loadgen local` 실행이 전부 UNMEASURED가 되어 판정이 막힌다(T-08).
>
> **`local`과 `docker`는 비교 조건이 다르다.** 왕복 경로가 다르므로(`localhost:18080` vs
> `app:8080`) `conditions.js`를 v4로 올려 blocking 조건에 넣었다. 미기록 과거 실행은
> `local`로 본다 — 그때는 다른 방식이 없었으니 추측이 아니라 사실이다.
>
> **실측 (large, 10 VU · 45초)**: 발생기 CPU 최대 0.026코어 · throttled 0.194% · 메모리
> 145.5MB. 같은 구간 앱은 1.239코어 — **발생기가 앱의 1/48**이다. 이 수치가 반복 측정에서
> 나온 경로 오버헤드 179ms(CV 17.8%)의 원인 후보 하나를 지운다 — **CPU 부족이 아니다.**
>
> **남은 것**: 물리적 분리(별도 머신/VM), 운영 EC2·RDS 사양 기록, 데이터 규모별 메모리 정책,
> Compose·MySQL 설정을 실행 manifest에 남기기, Windows/Docker Desktop 오버레이 분리.

#### 남은 문제

현재 단일 호스트 실행에서는 k6, 앱, DB, Redis, 관측 도구가 같은 CPU·메모리·디스크를 경쟁할 수
있다. 또한 로컬 Docker와 운영 EC2·RDS의 토폴로지·사양 차이를 기록하지 않아 로컬 결과를 운영
용량으로 환산할 근거가 없다.

#### 할 일과 완료 기준

- 부하 발생기를 별도 호스트 또는 VM으로 분리한다.
- 분리가 불가능한 실험은 부하 발생기 CPU·메모리를 함께 기록하고 “로컬 상대 비교”로 제한한다.
- 운영 EC2·RDS·Redis 사양과 네트워크 토폴로지를 비밀값 없이 기록한다.
- 데이터 규모별 MySQL·Redis 메모리 정책을 정한다.
- 실제 적용된 Compose 설정, MySQL 설정, 리소스 limit을 실행 manifest에 남긴다.
- 공통 환경과 Windows/Docker Desktop 오버레이를 분리한다.

### 10-b. 자원 튜닝은 무엇으로 판정하는가 — 종단 p95 로는 판정할 수 없다

> **한 줄 요약.** 커넥션 풀 크기나 CPU 상한 같은 **자원 손잡이**를 바꾼 뒤 판정용
> 운용점(`RATE=4`)에서 p95 를 비교하면 거의 항상 "변화 없음"이 나온다. 그건 손잡이가
> 효과 없다는 뜻이 아니라 **그 운용점이 애초에 그 자원에 제약받지 않았다**는 뜻이다.
> 상태: **방법론만 정리, 구현 없음** (2026-09-01)

#### 왜 그런가 — 구조적인 긴장이다

풀 크기를 10 → 20 으로 올렸다고 하자. `RATE=4` 는 포화 아래 운용점이므로 그 실행의
`pool.hikariPending.max`(커넥션을 기다리는 요청 수)는 0 이다. **대기줄이 없는데 대기줄을
넓히면 아무 일도 일어나지 않는다.** p95 가 그대로인 것은 당연하고, 그 결과는 풀에 대해
아무것도 증명하지 않는다.

풀 효과가 수치로 보이려면 `pending > 0` 인 부하가 필요한데, 그건 포화 근처다. 그리고
**포화에서의 p95 는 애플리케이션 지연이 아니라 큐 대기 시간**이라 개선 근거로 인용할 수
없다(`performance/bottlenecks/README.md` ②). 정리하면 이렇다.

- 포화 **아래**에서 재면 → 효과가 보이지 않는다
- 포화**에서** 재면 → 보이긴 하는데 그 수치를 인용할 수 없다

이 긴장은 없앨 수 없다. 없앨 것이 아니라 **판정 대상을 바꿔야 한다.**

#### 무엇으로 판정하는가 — 세 단계

1. **손잡이의 국소 지표를 1차 근거로 쓴다.** 자원 손잡이의 효과는 자기 바로 앞의 대기줄에
   가장 먼저 나타난다. 넷 다 이미 카탈로그에 있는 값이다.
   - `pool.hikariPending.max` — 풀 앞 대기줄 길이 (`tools/lib/metrics-catalog.js:504`)
   - `pool.hikariAcquireP95Ms` — 커넥션 획득 p95 (`metrics-catalog.js:515`)
   - `mysql.threadsConnected.max` — DB 쪽 실제 연결 수 (`metrics-catalog.js:301`)
   - `efficiency.stackCpuMsPerReq` — 요청 1건의 총 CPU 비용

2. **용량 곡선의 이동을 2차 근거로 쓴다.** 자원을 늘린 효과의 본질은 "같은 부하에서 더
   빠름"이 아니라 **"더 높은 부하까지 안 무너짐"**이다. 도착률을 2·3·4·5·6 으로 훑어
   **절벽이 어느 도착률로 옮겨갔는지**를 본다. 2026-08-20 보정 곡선(S-27)에서 절벽이
   4/s 와 5/s 사이에 있었으므로, 그 경계가 5/s 로 밀렸다면 그것이 개선의 증거다.

3. **종단 p95 는 마지막에 보조 확인으로만.** 포화 아래 운용점에서 "나빠지지 않았다"를
   확인하는 용도이지, "좋아졌다"의 근거가 아니다.

#### 이 판정을 하려면 도구에 무엇이 필요한가

- **도착률 스텝 실행** — 한 번의 실행 지시로 여러 도착률을 훑는 부하 프로파일.
  지금은 `--rate` 를 바꿔 가며 사람이 여러 번 친다.
- **교차(A/B) 실행기** — A 세트를 먼저 몰아 재고 B 세트를 나중에 몰아 재면 남은 잡음이
  집단 간 편향이 된다. `ABAB` 또는 `ABBA` 로 교대하면 쌍 안 잡음으로 바뀐다.
  `performance/tools/level-series.ps1` 이 이미 야간 반복 실행기이므로 여기에 얹는다.
  - 교란 하나를 미리 짚어 둔다: 환경을 바꾸려면 컨테이너를 재생성해야 하고, 그러면
    **JIT 상태와 MySQL 버퍼풀이 비워진다.** 이건 피할 대상이 아니라 교차로 상쇄되는
    항목이다 — A 와 B 가 매 회차 똑같이 그 비용을 치르기 때문이다. 다만 warmup 이
    버퍼풀을 다시 채울 만큼 긴지는 실측해야 한다.
- **환경 축의 기록과 검증** — 아래 10-c.

관련: S-27(보정 곡선), BTL-002(커넥션 풀), EXP-006(풀 크기 실험), `bottlenecks/README.md` ②

### 10-c. 실행 조건 축을 데이터셋·환경·부하 셋으로 분리한다

> **한 줄 요약.** 지금 실행 조건 세 축은 엄밀함의 수준이 완전히 다르다. 데이터셋은 지문까지
> 검증하는데 **환경은 `--env` 로 사람이 손으로 친 문자열 하나**이고, 그 값은 실제 컨테이너
> 설정과 아무 연결이 없다.
> 상태: **설계만, 구현 없음** (2026-09-01)

#### 남은 문제 — 세 축의 비대칭

| 축 | 선언 위치 | 적용값 검증 | 비교 조건 값 |
|---|---|---|---|
| 데이터셋 | `datasets/profiles.json` | 생성 지문 + 실행 직전 DB 실측(`tools/lib/dbstate.js`) | `{profile, fingerprint, state}` |
| 부하·측정 | 없음 (매번 플래그) | k6 가 실제 돌린 옵션을 그대로 읽음 | `loadProfile`, `measurementProfile` |
| **환경** | **없음** | **없음** | **`--env` 문자열** |

`tools/perf-run.js:448` 의 `--env` 는 값을 받아 기록에만 싣는다. 그리고 **`perf-run.js` 는
스택을 띄우지 않는다** — `docker compose ... up -d` 는 사람이 따로 친다. 그래서 기록에
`environment: "perf"` 라고 적혀 있어도, 그 순간 앱 컨테이너가 2코어였는지 4코어였는지,
Hikari 풀이 10 이었는지 20 이었는지를 **기록만으로는 알 수 없다.** EXP-006 이 계열을 가른
것은 누군가 `--env perf-pool20` 이라고 손으로 쳐 준 덕분이다.

이게 위험한 이유는 **선언한 값과 실제 적용된 값이 어긋난 사고를 이미 두 번 겪었기**
때문이다.

- `tools/lib/appimage.js` 헤더(T-42) — 2026-08-14 에 만든 이미지가 3주 동안 돌았는데
  기록에는 그때그때의 HEAD 커밋이 박혔다.
- `environment/docker-compose.perf.yml:17` — 바인드 마운트된 `my.cnf` 가 world-writable 로
  올라가면 mysqld 가 **조용히 무시하고 기본값으로 떨어진다.** 지금 MySQL 튜닝을 설정
  파일이 아니라 CLI 플래그로 넘기는 이유다.

**따라서 이 작업의 본질은 "프로파일에 이름 붙이기"가 아니라 "적용값을 읽어서 검증하기"다.**
이름만 JSON 파일로 옮기면 손으로 치던 문자열이 파일로 옮겨간 것뿐이고, 같은 사고가 그대로
재발한다.

#### 왜 한 프로파일로 합치지 않는가

세 축을 하나의 합성 이름(`medium+pool20+judge`)으로 묶자는 안은 **비용 구조가 맞지 않는다.**

| 축 | 바꾸는 비용 | 물리적 결합 |
|---|---|---|
| 부하 | 0초 (k6 플래그) | 없음 |
| 환경 | 약 40초 (컨테이너 재생성) | 없음 |
| 데이터셋 | 수십 분 ~ 수 시간 (시딩) | `docker-compose.perf.yml:282` — 볼륨 이름이 `perf-mysql-data-${DATASET_PROFILE}` |

합치면 풀 크기 하나 바꾸려는데 볼륨 이름이 달라져 **large 를 통째로 다시 시딩**해야 한다.
셋을 직교로 두고 명령줄에서 조합한다.

```bash
node tools/env-apply.js --env pool20                    # 별도 단계 — 스택 재생성
node tools/perf-run.js scenarios/normal-day.js \
     --env pool20 --dataset medium --load judge
```

#### 설계

**(1) 프로파일 파일에 `extends` 를 둔다.** `environment/env-profiles.json`:

```json
{
  "profiles": {
    "perf":   { "app":   { "cpus": "2.0", "memory": "2560m" },
                "mysql": { "cpus": "2.0", "memory": "2g",
                           "bufferPool": "1G", "maxConnections": 200 },
                "redis": { "cpus": "1.0", "memory": "512m" },
                "pool":  { "hikariMax": 10 } },
    "pool20": { "extends": "perf", "pool": { "hikariMax": 20 } },
    "cpu4":   { "extends": "perf", "app":  { "cpus": "4.0" } }
  }
}
```

전체 값을 복사한 프로파일은 기준이 바뀔 때 조용히 갈라진다. `pool20` 이 `cpus: "2.0"` 을
복사해 갖고 있으면, 나중에 기준을 4코어로 올렸을 때 `pool20` 만 2코어로 남는다.
`extends` 는 **"기준에서 풀 크기 하나만 다르다"**를 자료구조로 강제하고, 리포트가 보여줘야
할 diff 와 정확히 같은 형태다.

기준 프로파일 이름을 `default` 가 아니라 **`perf`** 로 두는 것이 중요하다. 저장된 모든
실행의 `run.environment` 가 `"perf"` 이므로, 이름을 맞추면 아래 (5)의 소급 이관이
"추측"이 아니라 "이름이 같은 것끼리 잇는 일"이 된다.

**(2) compose 를 변수화하되 기본값을 현재값과 같게 둔다.** `cpus: "${APP_CPUS:-2.0}"` 형태다.
이 기능을 안 쓰는 사람에게는 아무 변화가 없고, `perf` 프로파일이 정의상 지금까지 돌던
설정과 같아진다.

**(3) 이름을 비교 조건 값으로 쓰지 않는다.** `tools/lib/conditions.js:70` 이 데이터셋에
대해 이미 같은 논증을 적어 뒀다 — *"프로파일 이름만으로는 부족하다. 생성기를 고쳐 데이터를
다시 만들어도 이름은 그대로 `large` 라서…"*. 환경도 같다. `pool20` 의 내용을 25 로 고치고
이름을 안 바꾸면 **서로 다른 두 실험이 같은 계열로 묶인다.** 반대로 이름만 바꾸면 같은
설정인데 계열이 갈린다. 조건이 읽는 값은 적용값과 그 지문이어야 한다.

```js
run.environment = {
  profile: 'pool20',                 // 표시용
  applied: { appCpus: 2.0, hikariMax: 20, mysqlBufferPool: 1073741824, ... },
  fingerprint: 'a3f1c9e02b47',       // applied 의 sha256[:12]
  declaredMismatch: []               // 선언과 다른 항목이 있으면 실행을 막는다
};
```

**(4) 적용값은 손잡이마다 독립된 경로로 되읽는다.**

| 손잡이 | 읽는 곳 | 왜 이 경로인가 |
|---|---|---|
| 앱·MySQL·Redis CPU/메모리 | `docker inspect` → `HostConfig.NanoCpus`, `HostConfig.Memory` | compose 파일이 아니라 **커널에 실제로 걸린 상한** |
| Hikari 최대 풀 | `pool.hikariMax` — **이미 매 실행 수집 중**(`metrics-catalog.js:509`) | 환경변수를 되읽으면 안 된다. Spring 이 그 값을 반영했는지는 풀 자신에게 물어야 안다 |
| MySQL max_connections | `mysql.maxConnections` — **이미 매 실행 수집 중**(`metrics-catalog.js:306`) | 설정 무시 사고를 잡는 유일한 경로 |
| MySQL 버퍼풀 크기 | `SELECT @@innodb_buffer_pool_size` (신규) | 위와 같음 |

**위 표의 2·3행이 이 항목의 난이도를 크게 낮춘다.** 두 값은 이미 저장된 모든 실행에 들어
있으므로, 아래 소급 이관이 맞았는지를 **저장된 데이터로 직접 대조할 수 있다.** 가정이
아니라 확인이 된다.

**(5) 조건 전환은 `SCHEMA_VERSION` 을 4 → 5 로 올린다**(`tools/lib/conditions.js:45`).
문자열을 객체로 바꾸면 blocking 조건이 달라져 `seriesHash`(`comparability.js:57`)가 전부
바뀐다.

오해하기 쉬운 점 하나 — `schemaVersion` 자체가 해시에 들어가므로 **소급 이관을 해도 옛
해시와는 어차피 안 이어진다.** 이관이 지키는 것은 다른 것이다: 이관 후 옛 실행들이 **서로
같은 새 해시**를 갖느냐다. 이관을 안 하면 `applied: null` 인 실행과 값이 있는 실행이 갈려
추세선이 반토막 난다.

이관 근거는 `loadgen` 조건이 이미 쓴 논리(`conditions.js:110`)와 같다 — *"값이 없는 과거
실행은 `local` 로 본다. 추측이 아니라 사실이다."*

- `environment === 'perf'` → `perf` 프로파일 값으로 채운다. 그 값들은 해당 기간 내내
  compose 에 하드코딩돼 있었고 git 이력이 증명한다
- `'perf-pool20'` → `perf` + `hikariMax: 20`
- 그 외 라벨 → `applied: null` 로 둔다. **모르는 것을 채우지 않는다**

실행은 `reports/runs/*/run.json` 을 훑는 일회성 스크립트 + `node tools/history.js --rebuild`.

**(6) 대조 실행은 blocking 을 약화시키지 않고 별도 축으로 선언한다.** 자원 튜닝은 환경이
다른 두 실행을 **일부러** 비교하는 일인데 blocking 이 그걸 끊는다. 그렇다고 `environment` 를
degrading 으로 내리면 안 된다 — CPU 상한이 바뀌면 수치는 정말로 비교 불가이고, 경고로
내리면 진짜 회귀가 통과한다.

- `perf-run.js --contrast environment` 로 **의도를 실행 전에 기록**한다
- `seriesHash(conditions, { except: ['environment'] })` 로 대조 계열 해시를 만든다
- 두 기록이 같은 `contrast.axis` 를 갖고 **불일치가 그 축 하나뿐**일 때만
  `comparable-contrast` 를 돌려주고, 리포트가 "환경 대조 — 이 차이는 의도된 것"으로 표시
- 게이트는 그 축 차이로 실패시키지 않되, 포화 판정과 측정 무결성은 그대로 요구

**`--contrast` 를 사후에 붙일 수 있으면 안 된다.** 숫자가 좋게 나온 뒤 "비교 가능으로
바꾸자"가 되면, 그건 `tools/lib/report.js:485` 가 막으려는 바로 그 실패다.

#### 단계 — 계열을 끊는 작업을 맨 뒤로

| 단계 | 내용 | 계열 영향 |
|---|---|---|
| 1 | 부하 프로파일 파일 + `--load` 플래그 (이미 되는 것에 이름만 붙임) | 없음 |
| 2 | compose 변수화 + `env-apply.js` + 적용값 검증. 결과는 `run.environmentApplied` 에 **참고용으로만** 기록 | 없음 |
| 3 | 조건을 그 값으로 전환 + `SCHEMA_VERSION` 5 + 소급 이관 + `--rebuild` | **전면 재계산** |
| 4 | `--contrast` + 교차 A/B 실행기 (10-b) | 없음 |

3단계를 맨 뒤로 미는 이유: 2단계를 한동안 돌려 **적용값을 실제로 모아 본 뒤에** 계열을
끊어야, 이관이 맞았는지 대조할 근거가 생긴다.

#### 하지 말아야 할 것

- **`perf-run.js` 가 환경을 자동 적용하게 만들지 않는다.** 적용 = 컨테이너 재생성 = 예열
  상태 파괴다. `env-apply` 는 명시적인 별도 단계로 두고, `perf-run.js` 는 **검증하고
  기록만** 한다.
- 프로파일 이름을 조건 값으로 쓰지 않는다 (위 3).
- `environment` 를 degrading 으로 내리지 않는다 (위 6).
- 데이터셋을 합성 프로파일에 넣지 않는다 (볼륨 결합).

덤으로 얻는 것: 프로파일 레지스트리가 생기면 **오타가 즉시 잡힌다.** 지금은
`--env perfpool20` 이라고 잘못 쳐도 조용히 새 계열이 만들어지고, 나중에 "왜 비교가 안
되지"로 돌아온다. 등록되지 않은 이름은 실행 전에 죽는다.

관련: T-02(비교 가능성 조건), T-42(앱 이미지), S-03(데이터셋 지문), EXP-006(풀 크기 실험), 10-b

## P2 — 로컬 판정이 신뢰 가능해진 뒤 자동화

### 11. CI를 “실행됨”이 아니라 “재현되고 PR을 안전하게 막음”까지 완성

#### 남은 문제

- 성능 회귀 워크플로가 실제 PR 게이트로 설치되어 있지 않다.
- 현재 예시 흐름은 DB 초기화·시딩이 불완전하고 공유 러너의 노이즈가 크다.
- Actions 캐시는 기준선 저장소로 신뢰하기 어렵다.
- k6 버전, 환경 설정, 자격 증명 실패 진단, 정리 절차가 고정되지 않았다.
- 결과 공개 전에 내부 정보 제거가 보장되지 않는다.

#### 구현 순서

1. P0·P1 완료 조건을 CI preflight로 만든다.
2. MySQL·Redis 초기화와 검증된 스냅샷 복원을 자동화한다.
3. k6·Node·Docker 이미지 버전을 고정한다.
4. 안정된 전용 또는 self-hosted runner에서 반복 실행한다.
5. 기준선과 원자료를 캐시가 아닌 명시적인 영속 저장소에 둔다.
6. PR에서는 짧고 반복 가능한 회귀 세트만 실행한다.
7. 야간 작업에서 용량·stress·장시간 시나리오를 실행한다.
8. 판정 안정성을 확인한 뒤에만 branch protection과 배포 차단에 연결한다.
9. 실패 원인과 정리 결과를 artifact로 남기고, 공개 보고서는 마스킹 후 게시한다.

#### 완료 기준

- [ ] 깨끗한 PR에서 같은 조건의 반복 실행이 재현됨
- [ ] 인프라 또는 시딩 실패가 성능 FAIL과 구분됨
- [ ] 기준선 유실·잘못된 브랜치 복원 없이 비교됨
- [ ] 실제 회귀를 넣은 검증 PR이 병합을 막음
- [ ] 내부 메타데이터가 공개 artifact에 포함되지 않음

관련: E-23, E-24, E-25, E-26, E-27, E-28, E-29, E-30, E-31

## P3 — 정확성 기반을 만든 뒤 정리할 기술 부채

### 12. 판정·이력 코드의 장기 드리프트 방지

#### 남은 문제

- 스크립트 지문은 주요 트래픽 분포 파일을 반영하지만, 세션·요청 설정 등 실제 동작에 영향을 주는
  모든 변경과 “주석만 바뀐 변경”을 완전히 구분하지 못한다.
- 스크립트가 달라지면 판정을 완화하는 정책만 있고 엄격한 비교 정책이 없다.
- 증감률·포맷팅·추세 지표 목록이 여러 파일에 중복돼 있다.
- 보고서·history·PromQL 생성 경로의 자동 테스트가 충분하지 않다.
- 이전 중앙값이 0이거나 실행 번호가 충돌할 때 이력과 추세가 왜곡될 수 있다.
- 설정과 공통 코드가 여러 시나리오에 중복되어 서로 달라질 수 있다.

#### 할 일과 완료 기준

- 지문 대상 파일을 명시적인 manifest로 관리하고 엄격 모드를 추가한다.
- 의미 없는 변경과 트래픽 의미 변경의 정책을 분리한다.
- 증감률·포맷팅·추세 지표를 공통 모듈 하나로 모은다.
- report, history, PromQL, 동시 수집에 대한 테스트를 추가한다.
- 실행 ID 충돌 방지와 원자적 번호 부여를 구현한다.
- 시나리오 설정의 단일 출처를 만든다.
- Grafana datasource UID와 데이터셋 라벨 규칙을 고정한다.

관련: T-07의 남은 정책, T-19, T-21, T-27, T-28, S-21, E-12, E-38

### 공통 규칙

1. **동시에 두 개 이상 돌리지 않는다.** 전부 같은 Windows 호스트와 WSL2 VM을 공유하므로
   서로의 측정값을 오염시킨다. 아래 순서대로 하나씩 이어 붙인다.
2. **Node 18 이상으로 실행한다.** 현재 셸 기본이 `v16.20.2`이고, 그대로 실행하면 도구가
   `전역 fetch 없음`으로 **즉시 죽는다**(실제로 겪었다). `nvm use 22` 를 먼저 하거나
   `C:\Users\user\AppData\Local\nvm\v22.23.1\node.exe` 를 절대 경로로 쓴다.
3. **시작 직전에 `node tools/cpu-bench.js` 를 한 번 찍는다.** VM·Docker 재시작 직후 3회는
   5~14% 느리다([perf-session-drift.md](../investigations/perf-session-drift.md) 5절). 값이 평소(single 약
   4,950~5,050ms)로 돌아온 뒤 시작한다.
4. **도구를 고친 직후라면 걸지 않는다.** `performance/docs/README.md` 의 smoke 규칙대로 3~5분짜리
   확인을 먼저 통과시킨다. 밤새 돌려놓고 아침에 배관 오류로 전부 버리는 것이 최악이다.

### 1. 시나리오 스모크 순회 — 다른 항목의 선행 조건

**실행 기록을 세어 보니 시나리오 17개 중 `normal-day` 하나만 돌아간 적이 있다.** 나머지
16개는 저장된 실행이 0건이다 — 즉 **끝까지 도는지 아무도 확인한 적이 없다.** 이 목록의
4번(soak, 2시간)도 그중 하나다. 검증 없이 걸면 아침에 "3분 만에 죽어 있음"을 발견하게 된다.

`performance/docs/README.md` 의 규칙("긴 실행을 걸기 전에 3~5분짜리 smoke 로 배관을 확인한다")이
정확히 이 상황을 위한 것이다. 확인 대상은 성능이 아니라 **도구가 망가지지 않았는지**다.

```bash
# ① HOLD·VUS·WARMUP 을 받는 10개 — 1분짜리로 줄여서 확인
for s in read-heavy peak-hour exam-week chat-heavy notification-heavy \
         registration-day write-heavy cache-warm cold-start soak; do
  node tools/perf-run.js scenarios/$s.js --dataset smoke --vus 5 \
    --warmup 30 --hold 1m --loadgen docker --no-gate --note "스모크 배관 확인"
done

# ② DURATION 을 받는 3개
for s in deep-paging chaos failover; do
  node tools/perf-run.js scenarios/$s.js --dataset smoke --vus 5 \
    --duration 1m --loadgen docker --no-gate --note "스모크 배관 확인"
done

# ③ 손잡이 이름이 다른 2개
node tools/perf-run.js scenarios/breakpoint.js --dataset smoke --loadgen docker --no-gate \
  -e RAMP=2m -e MAX_VUS=50 -e TARGET_RATE=20 --note "스모크 배관 확인"
node tools/perf-run.js scenarios/spike.js --dataset smoke --loadgen docker --no-gate \
  -e SPIKE_VUS=20 --note "스모크 배관 확인"

# ④ 길이 손잡이가 아예 없는 1개 — 27분 그대로 걸린다. 맨 뒤에 둔다
node tools/perf-run.js scenarios/stress.js --dataset smoke --loadgen docker --no-gate \
  --note "스모크 배관 확인"
```

**왜 넷으로 나누는가.** 시나리오마다 길이를 줄이는 환경변수가 다르다. `spike` 는
`SPIKE_VUS` 로 크기만 바꿀 수 있고 길이는 650초로 고정이며, **`stress` 는 환경변수를 하나도
읽지 않아** 13단계 27분이 통째로 돈다. 이 둘이 순회 시간의 절반을 차지한다.

아침에 볼 것은 세 가지뿐이다.

- 실행이 오류 없이 끝났는가
- `phases.measure` 가 비어 있지 않은가 (구간 태깅이 동작하는가)
- `infra.flat` 항목 수가 정상인가 (Prometheus 연결이 살아 있는가)

**성능 수치는 보지 않는다.** smoke 데이터셋은 게시글 50건이라 전부 버퍼풀에 들어가고,
medium(10,000건)과는 다른 병목이 나온다. smoke 는 도구 확인용이고 판정은 medium 이상이다.

### 2. normal-day 5분 창 연속 10회 — 예열 판별 (완료)

```bash
node tools/repeatability.js scenarios/normal-day.js --runs 10 \
  --warmup 180 --hold 5m --dataset medium --env perf --loadgen docker --reset restart \
  --note "반복성 — 5분 창 연속 10회"
```

2026-08-18 오전 5회 세트에서 **아무것도 바꾸지 않았는데 p95 가 한 시간 만에 11.2%
좋아졌다**(15,564 → 13,823ms, 회차와의 순위상관 −0.90). 같은 구간에 Windows 호스트의 CPU
실동작 주파수가 86.0 → 107.8% 로 같이 올랐다. 두 가지 해석이 가능하다.

- **예열** — 호스트가 저전력 상태에서 시작해 반복 부하로 클럭이 올라간 것
- **누적 열화** — 환경이 한 시간 규모에서도 계속 느려지는 것

**연속 10회가 이 둘을 가른다.** 예열이면 1~5회차에서 내려간 뒤 6~10회차가 평평해지고,
드리프트면 끝까지 내려간다.

**반드시 한 번에 돌려야 한다.** 5회씩 두 번 나눠 재면 사이의 공백에서 호스트가 다시 식어
두 가설이 같은 예측을 내놓는다 — 실험이 성립하지 않는다.

아침에 볼 것: 회차별 p95 를 6회차 기준으로 앞뒤로 나눠 각각 기울기를 낸다. 뒤 절반의
기울기가 0에 가까우면 예열이다.

**결과(2026-08-21).** 두 가설 다 아니었다 — 이 세트는 200 VU 포화 상태였고, 회차 간
변동은 큐 길이의 흔들림이었다. 포화 이하로 내리면 사라진다.

### 3. normal-day 20분 measure 5회

```bash
node tools/repeatability.js scenarios/normal-day.js --runs 5 \
  --dataset medium --env perf --loadgen docker --reset restart \
  --note "반복성 — 재부팅 후 20분 창 세트"
```

`--warmup`·`--hold` 를 주지 않는 것이 핵심이다. 시나리오 기본값(warmup 300초 / measure
1,200초)이 그대로 적용돼 **주계열 `seriesHash=4307755dd860`** 에 붙는다. 세션 A(08-16)·
C(08-18 새벽)·D와 자동 비교되는 유일한 설정이다.

**이 한 세트가 남은 실험 두 개를 동시에 끝낸다.**

- **실험 2 (재부팅 후 반복 측정)**: 5분 창에서는 2026-08-18 오전 5회로 해소됐고 결론은
  바뀌지 않았다(재부팅해도 복귀하지 않음). 다만 **20분 창은 여전히 실행 62 하나뿐**이라,
  주계열에서 확정하려면 이 세트가 필요하다.
- **실험 6 (measure 창을 5분으로 줄여도 되는가)**: 이건 **추가 실행 0회로 끝난다.**
  remote-write가 켜져 있어 k6 지표가 Prometheus에 시계열로 남으므로, 20분 실행 하나를
  5분씩 네 토막으로 잘라 p95를 다시 계산하면 된다. 한 실행 안을 자르는 것이므로 창 길이만
  다른 비교가 성립한다. 지금까지 그 데이터를 가진 실행이 없어서 막혀 있었다.

아침에 볼 것: `measure p95`의 세트 평균이 08-16 세션 A(12,231ms) 쪽인지, 08-18 세션 C/D
(16,344~18,501ms) 쪽인지. 후자면 재부팅 무효가 n=6으로 확정된다.

### 4. soak 2시간 1회 — 밤에만 가능한 유일한 실행

```bash
node tools/perf-run.js scenarios/soak.js --dataset medium --loadgen docker
```

옵션을 주지 않으면 기본값이 150 VU · warmup 5분 · **measure 2시간** · rampdown 5분이다.

> **1번을 먼저 통과시킬 것.** `soak` 는 저장된 실행이 0건이다 — 2시간을 무인으로 걸기 전에
> 1분짜리로 끝까지 도는지 확인한다.

**왜 밤에만 가능한가.** 누수는 정의상 시간에 비례해 쌓이므로 12분짜리 실행으로는 원리적으로
보이지 않는다. 대상은 네 가지다.

- 힙 사용량과 Old Gen의 **기울기** (메모리 누수)
- `pool.hikariActive` 의 우상향 (커넥션 누수)
- WebSocket 세션 누적 (끊긴 세션 미정리)
- ViewCount·HotScore 스케줄러의 flush 지연 누적

판정은 절대값이 아니라 **기울기가 0인가**다. 우상향하면 누수다.

주의 두 가지. 첫째, 측정 구간 오류율이 2%를 넘으면 k6가 자동 중단하므로 아침에 실행이
일찍 끝나 있으면 그것 자체가 결과다. 둘째, 2시간 동안 데이터가 계속 늘어나므로 끝난 뒤
데이터셋 상태가 스냅샷과 크게 벌어진다. 다음 실행이 `guard=strict` 로 자동 복원하지만,
복원에 MySQL·앱 재기동이 들어가 몇 분 더 걸린다.

### 5. 데이터 크기 대조 — medium → large → medium

**아직 아무도 답하지 않은 질문이다: 지금의 병목(앱 CPU 2코어)이 데이터가 커져도 그대로인가.**
지금까지의 판정은 전부 `medium` 에서 나왔는데, 두 프로파일은 **버퍼풀 경계를 사이에 두고
갈라진다.**

| | medium | large |
|---|---:|---:|
| MySQL 볼륨 | 510MB | **2,703MB** |
| InnoDB 버퍼풀 | 1GB | 1GB |
| 버퍼풀에 다 들어가는가 | **예** (적중률 100%) | **아니오** |

즉 medium 에서는 디스크 I/O 가 사실상 0 이라 MySQL 이 CPU 만 쓴다. large 에서는 읽기 미스가
생겨 **병목이 앱 CPU 에서 MySQL I/O 로 옮겨갈 수 있다.** 만약 그렇다면 EXP-002~005 의
우선순위가 통째로 바뀐다 — 커넥션 풀이나 N+1 보다 데이터 접근 패턴이 먼저가 된다.

```bash
node tools/repeatability.js scenarios/normal-day.js --runs 5 --warmup 180 --hold 5m \
  --dataset medium --env perf --loadgen docker --reset restart --note "크기 대조 A1 medium"
node tools/repeatability.js scenarios/normal-day.js --runs 5 --warmup 180 --hold 5m \
  --dataset large  --env perf --loadgen docker --reset restart --note "크기 대조 B large"
node tools/repeatability.js scenarios/normal-day.js --runs 5 --warmup 180 --hold 5m \
  --dataset medium --env perf --loadgen docker --reset restart --note "크기 대조 A2 medium"
```

**왜 medium 을 두 번 재는가 — 이게 이 실험의 핵심이다.** medium 5회 → large 5회로 끝내면
large 가 항상 **나중에** 측정된다. 그런데 8절에서 확인했듯 세트 안에는 시간에 따른 추세가
있어서, 뒤에 온 쪽이 유리해진다. **"large 가 빨랐다"가 데이터 크기 때문인지 순서 때문인지
구분되지 않는다.** medium 을 앞뒤로 두 번 재면 그 사이의 추세 크기를 직접 알 수 있고,
large 값에서 그만큼을 빼면 크기만의 효과가 남는다.

`--env` 를 `perf` 로 두어도 안전하다. 데이터셋은 **blocking 비교 조건**이라 medium 실행이
large 실행의 기준선으로 잘못 선택되는 일이 없다.

소요에는 large 복원 시간이 포함돼 있다 — 볼륨이 2.7GB 라 회당 82초로, medium 보다 회차마다
약 1분씩 더 걸린다.

아침에 볼 것: `mysql.bufferPoolHitPct` 가 large 에서 100% 밑으로 떨어졌는가, 그리고
`efficiency.dbCpuUsPerQuery` 와 앱 CPU throttling 중 어느 쪽이 움직였는가.

### 6. normal-day flush 리셋 5회 — CV의 구성 요소 분리

```bash
node tools/repeatability.js scenarios/normal-day.js --runs 5 \
  --warmup 180 --hold 5m --dataset medium --env perf-flush \
  --loadgen docker --reset flush \
  --note "CV 분해 — 앱 재시작 없이 Redis만 비움(JIT 웜업 성분 제거)"
```

**무엇을 가르는 실험인가.** 지금 기록된 CV(5분 창 4.55~5.83%)는 `--reset restart` 로 잰
값이라 **매번 콜드 JVM에서 시작하는 데서 오는 JIT 웜업 편차가 섞여 있다.** 앱을 재시작하지
않고 Redis만 비우는 `flush` 모드로 같은 5회를 돌리면 그 성분만 빠진다.

- CV가 뚜렷하게 떨어지면 → 웜업 편차가 실측 노이즈의 주성분이다. MDE(최소 검출 가능
  개선폭)를 낮출 여지가 생기고, 측정 절차를 바꿀 근거가 된다.
- 거의 같으면 → 웜업은 편차 원인이 아니다. 후보 하나가 지워진다.

**`--env` 를 `perf-flush` 로 따로 두는 이유**가 2·3번과 다르다. 리셋 모드는 비교 조건
(`conditions.js`의 축)에 **기록되지 않는다.** 같은 `perf` 환경에 넣으면 restart 세트와
flush 세트가 절차가 다른 채로 섞이고, 기준선 자동 선택이 그걸 구분하지 못한다. 이 실험은
세트 **안**의 CV만 보면 되고 과거 실행과의 자동 비교가 필요 없으므로, 분리하는 쪽이 맞다.

### 7. 유휴 상태 cpu-bench 반복 — 비용 거의 0

부하 실행이 전부 끝난 뒤 남는 시간에 건다. 5초짜리 벤치라 호스트에 실질적 부하가 없다.

```bash
while true; do
  # --json 은 여러 줄로 나온다 — 줄바꿈을 지워야 한 줄에 한 레코드(JSONL)가 된다
  bench=$(node tools/cpu-bench.js --json | tr -d '\n')
  printf '{"at":"%s","bench":%s}\n' "$(date -u +%FT%TZ)" "$bench" >> reports/idle-cpu-bench.jsonl
  sleep 600
done
```

**왜 유휴 상태여야 하는가.** 환경 속도가 스스로 움직이는지를 앱 성능과 **분리해서** 재려면
부하가 없어야 한다. 그런데 지금 있는 cpu-bench 값은 전부 **부하 실행에
붙여서** 찍은 것이라, 값이 흔들려도 그게 시간 탓인지 부하 탓인지 가르지 못한다. 부하 없이
밤새 10분 간격으로 찍으면 **"부하와 무관하게 시간만 흘러도 환경이 느려지는가"** 에
독립적으로 답하는 시계열이 처음 생긴다.

아침에 볼 것: `single`·`parallel`·`ctxswitch` 세 축이 밤새 우상향하는가. 셋 다 오르면 CPU
클럭 층, `single`만 평평하면 스케줄링·시스템 콜 층이다.

**아침에 딱 하나만 먼저 할 것.** 예열 가설이 맞다면 **밤새 유휴 상태였던 직후의 첫 실행이
가장 느려야 한다.** 그러니 다른 작업을 하기 전에 `normal-day` 를 5분 창으로 한 번(12.5분)
먼저 재 둔다. p95 가 15,500ms 대에서 시작하면 예열 가설이 맞고, 13,800ms 대면 틀렸다.
비용 12분에 예측 하나를 검증한다.

### 밤에 돌리면 안 되는 것

**stress · spike · breakpoint 계열.** P1-7이 미해결이다. 요청 도착률이 서버 응답 속도에
묶여 있어(closed-loop), 서버가 느려지면 부하도 같이 줄어든다. 포화점과 최대 처리량을
묻는 시나리오에서 이건 치명적이라 **밤을 태워도 해석할 수 없는 숫자가 나온다.** 부하 모델을
고친 뒤에 돌린다.

**포화 이하 운용점을 확인하지 않은 시나리오의 기준선 대량 축적**(read-heavy, deep-paging,
write-heavy 등). 시나리오마다 용량이 다른데 `RATE=4` 는 `normal-day` 기준으로만 확인된
값이다. 용량 곡선을 그려 보지 않은 시나리오를 밤새 쌓으면 **포화 상태의 세트를 쌓게 되고**,
그 값은 애플리케이션 지연으로 인용할 수 없다. 시나리오별 보정 곡선을 먼저 그린다.

**EXP-002~005의 Before/After 쌍.** After는 코드 변경을 적용한 뒤에야 시작할 수 있어
사람이 중간에 개입해야 한다. 무인 실행에 맞지 않는다. 다만 **밤에 Before 만 걸고 아침에
After 를 잇는 것은 이제 가능하다** — 같은 운용점에서 재기만 하면 시간 간격은 문제가
아니다(4시간 간격 −1.5%). 무인 실행에 넣지 않는 이유는 재현성이 아니라 사람 개입뿐이다.
