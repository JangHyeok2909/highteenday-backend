# perf-debug-trace-guide — 디버거로 측정 시스템을 추적하는 방법과 기록 양식

성능 측정 시스템은 "숫자를 만들어 내는 기계"다. 그 숫자를 믿으려면 기계 안에서 값이
어떻게 흘러가는지 **직접 눈으로 봐야 한다.** 코드를 읽는 것과 디버거로 멈춰 세워 값을
보는 것은 다르다. 읽기는 "이렇게 될 것이다"를 알려 주고, 디버거는 "실제로 이랬다"를
알려 준다. 이 저장소가 지금까지 겪은 오판(E-46 포화 상태를 앱 지연으로 읽은 일, T-01
판정 규칙 25개가 조용히 건너뛰어진 일)은 전부 전자를 후자로 착각해서 생겼다.

이 문서는 네 부분이다.

| 부 | 내용 | 언제 읽나 |
|---|---|---|
| **0부** | 개념 사전 — 이 문서를 읽는 데 필요한 모든 용어 | 처음 한 번, 이후엔 모를 때만 찾아보기 |
| **1부** | 준비와 원칙 — 무엇에 어떻게 붙고, 어디서는 멈추면 안 되는가 | 처음 한 번, 환경 세팅할 때 |
| **2부** | 트레이싱 가이드 — **어떤 흐름을 어떤 순서로 추적할 것인가** | 추적을 시작할 때마다 |
| **3부** | 세션 기록 양식 — 추적한 결과를 남기는 틀 | 추적 한 건이 끝날 때마다 |

추적한 사실은 반드시 어딘가로 흘러가야 한다. [perf-findings-tools.md](../findings/perf-findings-tools.md)
의 발견 항목이 되거나, [perf-measurement-explained.md](perf-measurement-explained.md)의
설명을 고치거나, 최소한 3부의 세션 기록으로 남아야 한다. **추적만 하고 아무 데도 안 남으면
2주 뒤에 같은 자리를 처음부터 다시 판다.**

# 0부. 개념 사전

여기 있는 용어는 2부의 트레이싱 가이드에서 설명 없이 쓴다. 모르는 단어가 나오면 이리로
돌아온다. **"이 정도는 알겠지"라고 생략하지 않는 것이 이 문서의 규칙이다.**

## 0.1 디버거 일반 용어

**디버거(debugger)**
실행 중인 프로그램을 원하는 지점에서 멈추고, 그 순간의 변수 값을 들여다보고, 한 줄씩
진행시킬 수 있게 해 주는 도구다. `console.log`를 코드에 박아 넣는 것과 목적은 같지만,
**코드를 고치지 않아도 되고**, 미리 찍기로 정하지 않은 변수까지 그 자리에서 볼 수 있다는
점이 다르다.

**브레이크포인트(breakpoint, 중단점)**
"이 줄에 도달하면 멈춰라"라고 표시해 둔 지점이다. 프로그램이 그 줄을 실행하기 **직전**에
멈춘다. 즉 그 줄이 만들 결과는 아직 없고, 그 줄이 쓰는 입력값은 이미 있다.

**조건부 브레이크포인트(conditional breakpoint)**
"이 줄에 도달하되, 조건이 참일 때만 멈춰라"다. 예를 들어 실행 20개를 순회하는 반복문에서
`runId === 'normal-day-2026-08-19T09-46-07'` 일 때만 멈추게 할 수 있다. 반복문 안을
추적할 때 이걸 모르면 "계속(continue)"을 열아홉 번 누르게 된다. **이 저장소의 추적은
대부분 반복문 안이라 사실상 필수 기능이다.**

**로그포인트(logpoint)**
멈추지 않고 값만 찍는 브레이크포인트다. Chrome DevTools에서는 줄 번호를 우클릭해
"Add logpoint"로 만든다. 시간에 민감한 코드(1부 1.5)에서 `console.log`를 코드에 넣지
않고도 값을 볼 수 있는 거의 유일한 방법이라 중요하다.

**스텝 오버 / 스텝 인 / 스텝 아웃 (step over / into / out)**
멈춘 상태에서 한 걸음씩 진행시키는 세 가지 방법이다.

- **스텝 오버**: 현재 줄을 실행하고 **다음 줄**로 간다. 그 줄이 함수를 부르면 그 함수는
  통째로 실행되고 안으로 들어가지 않는다. "이 함수는 이미 믿는다"일 때 쓴다.
- **스텝 인**: 현재 줄이 부르는 함수 **안으로** 들어간다. "이 함수가 수상하다"일 때 쓴다.
- **스텝 아웃**: 지금 함수를 끝까지 실행하고 **부른 쪽으로** 돌아온다. 잘못 들어갔을 때
  빠져나오는 용도다.

**콜스택(call stack, 호출 스택)**
"지금 여기까지 어떻게 왔는가"를 보여 주는 함수 호출 목록이다. 맨 위가 현재 함수이고
아래로 갈수록 자기를 부른 쪽이다. 예를 들어 `evaluateRule`에서 멈추면 콜스택은
`evaluateRule ← analyze ← processRun ← main` 처럼 보인다. **어떤 경로로 이 값이
들어왔는지**를 알려 주기 때문에 값 자체보다 중요할 때가 많다.

**스코프(scope, 변수 영역)**
멈춘 시점에 접근 가능한 변수들의 목록이다. 디버거 화면에서 지역(Local) / 클로저(Closure) /
전역(Global)으로 나뉘어 보인다. 여기서 값을 펼쳐 보는 것이 추적의 핵심 행위다.

**감시식(watch expression)**
"이 식의 값을 계속 보여 줘"라고 등록해 두는 것이다. `record.k6.phases.measure.rps` 처럼
깊이 들어간 값을 매번 펼치지 않아도 되게 해 준다.

**REPL / 콘솔 평가**
멈춘 상태에서 콘솔에 아무 JavaScript 식이나 쳐서 그 자리의 값으로 계산해 볼 수 있다.
`Object.keys(record.infra.flat).length` 같은 것을 즉석에서 물어보는 용도다. **추적에서
가장 많이 쓰게 되는 기능**인데, 있는 줄 모르고 넘어가기도 쉬운 기능이다.

## 0.2 Node.js 실행과 디버깅 구조

**Node.js**
JavaScript를 브라우저 밖에서 실행하는 런타임이다. 이 저장소의 측정 도구
(`performance/tools/**`)는 전부 Node로 도는 프로그램이다. 이 머신의 버전은 **v16.20.2**
이고, 코드 곳곳이 이 버전을 전제로 짜여 있다. 예를 들어 `tools/lib/promql.js`는 Node 16에
전역 `fetch`가 없어서 내장 `http` 모듈로 HTTP 클라이언트를 직접 구현했다.

**인스펙터 프로토콜과 `--inspect-brk`**
Node는 자신을 디버깅할 수 있는 창구를 열어 줄 수 있다. `node --inspect-brk <파일>`로
실행하면 Node가 디버깅용 포트(기본 9229)를 열고 **첫 줄에서 멈춘 채** 누군가 붙기를
기다린다. `--inspect`만 쓰면 포트만 열고 그냥 진행하기 때문에, 몇 초 만에 끝나는 측정
도구는 붙기도 전에 종료된다. **그래서 항상 `-brk`를 쓴다.**

**Chrome DevTools로 붙기**
크롬 주소창에 `chrome://inspect`를 치면 "Remote Target" 목록에 방금 띄운 Node 프로세스가
뜬다. `inspect`를 누르면 크롬 개발자도구와 똑같은 화면이 열리고, 거기서 브레이크포인트를
찍는다. **브라우저를 디버깅하는 것이 아니라 Node를 디버깅하는 것**이고, 화면만 크롬 것을
빌려 쓰는 구조다.

**`debugger;` 문**
코드 안에 `debugger;` 한 줄을 넣으면 그 지점이 브레이크포인트가 된다. 디버거가 붙어 있지
않으면 아무 일 없이 지나간다. 파일을 편집해야 하므로 임시 수단이고, **추적이 끝나면
반드시 지운다.**

**동기(synchronous)와 비동기(asynchronous)**
동기 코드는 한 줄이 끝나야 다음 줄이 시작된다. 비동기 코드는 "요청만 걸어 두고 다음 줄로
넘어간 뒤, 결과가 오면 나중에 이어서" 실행된다. `collect.js`의 Prometheus 조회는
비동기(`await`)이고, `perf-run.js`의 k6 실행은 동기(`spawnSync`)다. 디버깅에서 중요한
차이는 **비동기 경계를 넘으면 콜스택이 끊겨 보인다**는 점이다. `await` 뒤에서 멈추면
"누가 나를 불렀는지"가 스택에 온전히 남지 않을 수 있다.

**이벤트 루프(event loop)**
Node가 "지금 할 일"을 하나씩 꺼내 처리하는 단일 처리 라인이다. 핵심은 **한 번에 하나만
처리한다**는 것이다. 그래서 어떤 동기 작업이 오래 걸리면 그동안 다른 모든 콜백(타이머,
네트워크 응답 처리)이 **전부 밀린다.**

**`spawnSync` / `spawn` (자식 프로세스)**
`spawnSync`는 다른 프로그램(k6, docker, powershell 등)을 실행하고 **끝날 때까지 기다린다.**
기다리는 동안 이벤트 루프가 통째로 멈춘다. `perf-run.js`가 k6를 이렇게 부르기 때문에,
k6가 도는 27분 동안 `perf-run.js` 프로세스는 아무 콜백도 처리하지 못한다. 이 사실이
`hostprobe`/`loadbench`를 별도 워커 프로세스로 분리한 이유다(각 파일 머리말에 그 사고
기록이 있다). `spawn`은 반대로 기다리지 않고 백그라운드로 띄운다.

**부모 프로세스 / 자식 프로세스와 디버깅**
디버거는 **붙은 그 프로세스 하나만** 본다. `perf-run.js`에 디버거를 붙여도 그것이 실행한
k6나 `collect.js`는 다른 프로세스라 브레이크포인트가 걸리지 않는다. 자식을 보고 싶으면
**그 자식 명령을 따로 `--inspect-brk`로 직접 실행**해야 한다. 이 문서의 추적 전략이 대부분
"`collect.js`를 직접 부른다"인 이유가 이것이다.

**CommonJS와 ES 모듈 (`require` vs `import`)**
`performance/tools/**`는 CommonJS(`require`)로 짜여 있고, `performance/scripts/**`와
`scenarios/**`는 ES 모듈(`import`)이다. k6가 ES 모듈 문법만 받기 때문이고,
`performance/scripts/package.json`에 `{"type":"module"}` 선언이 있다. 실무적 의미는 하나다.
**k6용 순수 로직 파일은 Node에서 `await import()`로 불러올 수 있고, 그래서 브레이크포인트를
찍을 수 있다.** `tools/test/sampling.test.js`, `tools/test/phases.test.js`가 이미 그 방식이다.

**JDWP 원격 디버깅**
Java 진영의 디버깅 창구다. JVM을 `-agentlib:jdwp=...,address=*:5005` 옵션으로 띄우면
IntelliJ가 그 포트로 붙어 Java 코드에 브레이크포인트를 걸 수 있다. 이 저장소에서는 Docker
안에서 도는 Spring Boot 앱을 볼 때 쓴다. 다만 **부하 측정 중에는 쓰면 안 된다**(1부 1.5).

## 0.3 이 측정 시스템의 도메인 용어

**k6**
부하를 만들어 내는 도구다. Go로 작성된 단일 실행 파일이고, 그 안에 자체 JavaScript
엔진(goja)을 품고 있어 우리가 쓴 `scripts/*.js`를 해석해 실행한다. **Node가 아니다.**
그래서 Node 디버거가 붙지 않는다(1부 1.4).

**VU (Virtual User, 가상 사용자)**
동시에 요청을 보내는 가상 사용자 한 명이다. `--vus 20`은 20명이 동시에 굴러간다는 뜻이다.

**closed model / open model (닫힌 모델 / 열린 모델)**

- **closed model**: VU 수를 고정한다. 사용자는 응답을 받아야 다음 요청을 보낸다. 서버가
  느려지면 **부하도 저절로 줄어든다.** 이 현상을 coordinated omission(협조적 누락)이라
  부르고, 판정용 수치로 쓰면 안 되는 이유가 된다.
- **open model**: 초당 도착률을 고정한다(`--rate`). 서버가 느려져도 요청은 같은 속도로
  계속 들어온다. 실제 서비스에 가깝고, 이 저장소는 판정에 이 모델을 쓴다.

**phase(구간): warmup / measure / rampdown**
한 번의 실행은 세 구간으로 나뉜다.

- **warmup**: 부하를 올리며 JIT 컴파일·커넥션 풀·캐시를 데우는 구간. **판정에 쓰지 않는다.**
- **measure**: 부하가 목표치로 유지되는 구간. **이 구간만이 판정 대상이다.**
- **rampdown**: 부하를 내리는 구간. 판정에 쓰지 않는다.

**phasePlan**
위 세 구간의 길이와 시작 오프셋을 담은 계획표다. `scripts/lib/phases.js`의
`buildPhasePlan()`이 만들고 k6 요약에 실려 저장된다. **이 값이 이후 모든 시간 계산의 유일한
출처다.** k6의 threshold 판정, Prometheus 조회 창, 호스트 표본 구간 나누기가 전부 이걸
읽는다. 예전에는 각자 따로 계산해서 서로 다른 시간대를 보고 있었다(T-03/S-08).

**threshold(임계값)**
k6가 스스로 내리는 합격·불합격 기준이다. 예를 들어 "measure 구간의 p95는 500ms 미만"이다.
미달하면 k6는 종료 코드 99로 끝난다.

**p95 / p99(백분위 지연)**
응답 시간을 느린 순서로 줄 세웠을 때 95%(또는 99%) 지점의 값이다. "100건 중 95건은 이 값보다
빨랐다"는 뜻이고, 평균보다 사용자 체감에 가깝다.

**RPS (Requests Per Second)**
초당 처리한 요청 수다. 분모를 무엇으로 두느냐가 함정이고, 실제로 그 사고가 났다(S-26).
k6의 기본 `rate`는 **전체 테스트 시간**으로 나누기 때문에, measure 구간의 요청 수를 전체
실행 시간으로 나눈 값이 저장돼 있었다. 지금은 `collect.js`가 다시 계산해 바로잡는다.

**runId / run.json / 스테이징과 승격**
한 번의 실행에는 `normal-day-2026-08-19T09-46-07` 같은 ID가 붙는다. 파일은 두 단계로 존재한다.

- **스테이징**: k6가 남긴 `reports/runs/<runId>.k6.json`, `perf-run.js`가 남긴
  `<runId>.dbstate.json`, 호스트 표본 `<runId>.hostprobe.jsonl`
- **승격(promote)**: `collect.js`가 이것들을 합치고 판정까지 끝낸 뒤 최종 레코드 `run.json`을
  만들어 정식 보관 위치로 옮긴다

승격을 **맨 마지막에** 하는 이유는 중간에 실패해도 원본이 남아 재시도할 수 있게 하기 위해서다.

**infra 지표 / `infra.flat`**
Prometheus에서 가져온 서버 쪽 지표(CPU, MySQL, Redis, 커넥션 풀 등)를 `cpu.throttledPct`
처럼 점으로 이어진 평평한 키-값 표로 만든 것이다. 판정 규칙이 이 키를 읽는다. **키 하나를
못 읽으면 그 규칙은 조용히 건너뛰어진다** — T-01이 정확히 그 사고였고, 규칙 32개 중 25개가
한 번도 작동하지 않았다.

**baseline(기준선)**
"이번 실행과 비교할 대조군"이다. 시간상 직전 실행이 아니라 **비교 가능한 가장 최근 실행**
이다. 이 구분이 없던 시절 200VU·large 실행이 15VU·small 실행을 기준선으로 잡아
"+59,000% 회귀"를 보고한 적이 있다.

**conditions / seriesHash(비교 가능성)**
두 실행이 "같은 실험"인지를 정하는 조건들(시나리오, 환경, 데이터셋, 부하 프로파일 등)이
`tools/lib/conditions.js`에 표로 선언돼 있다. 그 조건 묶음을 해시로 압축한 값이
**seriesHash**다. **해시가 다르면 두 실행은 나란히 놓을 수 없다.** 도구는 이미 이걸로
막고 있었는데 사람이 표를 손으로 나란히 놓아서 틀렸다(E-46).

**게이트(gate)**
회귀가 감지되면 종료 코드를 0이 아닌 값으로 만들어 CI를 실패시키는 장치다. `--no-gate`로
끄면 관찰만 한다.

**포화(saturation)**
시스템이 처리 용량을 넘어선 상태다. 이때의 p95는 **애플리케이션 지연이 아니라 큐 대기
시간**이다. 같은 코드가 포화 이하에서 278ms, 포화에서 10,000ms를 냈다 — 38배 차이의 정체는
코드가 아니라 대기줄이었다. 이 축을 표시하지 않아 닷새를 날렸고, 그래서
`tools/lib/saturation.js`가 생겼다.

**measurementStatus**
"이 실행의 지표를 판정에 쓸 수 있는가"를 나타내는 상태다. 필수 지표가 비어 있으면
"문제 없음"이 아니라 **"측정하지 못함"** 으로 읽어야 한다. 포화 여부와는 **다른 축**이다.
지표가 전부 멀쩡해도 포화 상태면 그 값의 의미가 달라지기 때문이다.

**CV(변동계수) / MDE(최소 검출 가능 효과)**

- **CV**: 같은 조건으로 여러 번 쟀을 때 값이 얼마나 흔들리는지를 백분율로 나타낸 것이다
  (표준편차 ÷ 평균). 이 저장소에서 108.77%가 나온 적이 있는데, 평균만큼 흔들린다는 뜻이다.
- **MDE**: 그 흔들림 속에서 "개선됐다"고 말할 수 있는 **최소한의 개선 폭**이다. CV가 크면
  MDE도 커지고, 작은 개선은 아무리 진짜여도 증명할 수 없다.

**hostprobe / loadbench**

- **hostprobe**: 측정 중 호스트(내 PC)의 CPU 상태를 주기적으로 표본 추출하는 워커다.
- **loadbench**: 부하가 걸린 상태에서 CPU 기준 벤치마크를 돌려 "기계 자체가 느렸는가"를
  가리는 장치다. warmup 구간에서만 돈다 — measure 구간을 침범하면 그 실행을 오염시킨다.

## 0.4 파이프라인 전체 그림

추적을 시작하기 전에 **전체가 몇 단계인지**를 머리에 넣어 둔다. 2부의 모든 흐름은 이 그림
위의 한 조각이다.

```text
[1단계] 실행 준비            tools/perf-run.js  main()
   · 실행 잠금 획득 (동시 실행 금지)
   · git 메타데이터·데이터셋 지문 수집
   · preflight(): 데이터셋 상태 확인 / 필요 시 복원
   · 유휴 CPU 벤치 → hostprobe 시작
        ↓
[2단계] 부하 생성            k6 (별도 프로세스, Go 런타임)
   · scripts/lib/config.js → phases.js 로 phasePlan 결정
   · 시나리오 실행 → threshold 판정
   · handleSummary() 가 reports/runs/<runId>.k6.json 을 씀
        ↓                    (perf-run 은 spawnSync 로 여기서 통째로 멈춰 있다)
[3단계] 실행 후 기록         tools/perf-run.js  postflight()
   · loadbench/hostprobe 정지 → <runId>.dbstate.json, <runId>.hostprobe.jsonl 로 남김
        ↓
[4단계] 수집·판정            tools/collect.js  processRun()   ← 추적의 주 무대
   · k6.json + dbstate 병합
   · hostprobe 를 구간별로 다시 요약
   · RPS 분모 보정 (S-26)
   · measureWindow(): phasePlan 으로 Prometheus 조회 창 계산
   · collectInfra(): 카탈로그를 순회하며 PromQL 실행 → infra.flat
   · findBaseline() → comparability → regression.analyze() → PASS/WARN/FAIL
   · saturation.assess(): 포화 여부를 별도 축으로 판정
   · saveRun() → HTML 리포트 → promoteStaged()
        ↓
[5단계] 이력·추세            tools/history.js, tools/lib/trends.js
   · 여러 회차에 걸친 CV·MDE·안정성 계산과 이력 페이지 렌더
```

**4단계가 이 시스템의 심장이다.** 부하를 다시 걸지 않고도 저장된 실행만으로 4·5단계 전체를
몇 초 안에 재현할 수 있다(1부 1.3). 그래서 추적의 대부분은 여기서 이루어진다.

# 1부. 준비와 원칙

## 1.1 추적 대상은 세 층이고, 붙는 방법이 전부 다르다

"성능 측정 시스템"이라고 부르는 것은 사실 성격이 다른 세 덩어리가 맞물린 것이다. 각각
런타임이 다르기 때문에 **디버거를 붙이는 방법도, 붙일 수 있는지 여부도 다르다.**

| 층 | 무엇 | 런타임 | 붙는 방법 | 브레이크포인트 |
|---|---|---|---|---|
| 측정 도구 | `tools/*.js`, `tools/lib/*.js` | Node.js 16 | `node --inspect-brk` + Chrome DevTools | **가능. 주 대상** |
| 부하 스크립트 | `scripts/*.js`, `scenarios/*.js` | k6 내부 JS 엔진(goja) | 없음 | **불가.** 1.4 참고 |
| 대상 서버 | Spring Boot 앱 | JVM (Docker 컨테이너) | JDWP 원격 디버그(IntelliJ) | 가능하지만 **측정 중 금지** |

이 저장소의 IDE 설정은 IntelliJ(`.idea/`)뿐이고 `.vscode/`는 없다. IntelliJ Community
버전에는 JavaScript/Node 디버거가 아예 없기 때문에, **Node 도구 디버깅은 IDE와 무관한
`--inspect-brk` + Chrome DevTools 조합을 기본으로 삼는다.** IntelliJ Ultimate를 쓴다면
Node.js 실행 구성으로 대체해도 되고, 이 문서의 정차 지점 목록은 그대로 유효하다.

## 1.2 Node 도구에 디버거를 붙이는 절차

처음이라면 이 순서를 그대로 따라 한다. 예시는 저장된 실행 하나를 다시 판정하는 것이다.

**1) 대상 실행 ID를 하나 고른다.**

```bash
cd performance
ls reports/runs | head
```

`normal-day-2026-08-19T09-46-07` 처럼 생긴 이름이 실행 ID(runId)다.

**2) 디버그 모드로 띄운다.**

```bash
node --inspect-brk tools/collect.js normal-day-2026-08-19T09-46-07 --force --no-wait
```

터미널에 `Debugger listening on ws://127.0.0.1:9229/...` 가 뜨고 **거기서 멈춘다.** 아직
아무 코드도 실행되지 않은 상태다.

**3) 크롬에서 붙는다.**
주소창에 `chrome://inspect` → "Remote Target" 아래의 `tools/collect.js` 항목에서
`inspect` 클릭 → DevTools 창이 열리고 첫 줄에서 멈춰 있다.

**4) 파일을 찾아 브레이크포인트를 찍는다.**
DevTools에서 `Ctrl+P`를 누르고 `collect.js`를 입력하면 소스가 열린다. 왼쪽 줄 번호를
클릭하면 파란 표시가 붙고 그게 브레이크포인트다. 조건을 걸려면 줄 번호를 **우클릭 →
"Add conditional breakpoint"** 다.

**5) 실행을 재개한다.**
`F8`(또는 재생 버튼)을 누르면 다음 브레이크포인트까지 달린다. 멈추면 오른쪽 Scope 패널에서
변수를 펼치고, 아래 콘솔에 식을 쳐서 값을 물어본다.

**6) 끝나면 프로세스를 확실히 종료한다.**
멈춰 있는 프로세스는 실행 잠금을 쥐고 있다(1.5 마지막 항목). 터미널에서 `Ctrl+C`로 끝낸다.

> DevTools를 여는 것이 번거로우면 보고 싶은 파일에 `debugger;` 한 줄을 임시로 넣어도 된다.
> 다만 **추적이 끝나면 반드시 지운다.** 남은 채로 커밋되면 이후 실행이 아무도 붙지 않은
> 상태로 영원히 멈춰 선다.

## 1.3 부하를 걸지 않고 추적한다 — 가장 중요한 원칙

측정 도구의 판정 로직은 **이미 저장된 실행 결과를 다시 먹이는 것만으로 전부 재현된다.**
2시간짜리 부하를 다시 돌릴 이유가 없다. 다음 네 가지가 무부하 재현 수단이다.

| 목적 | 명령 | 걸리는 시간 |
|---|---|---|
| 저장된 실행 하나를 다시 수집·판정 | `node tools/collect.js <runId> --force --no-wait` | 수 초 |
| 저장된 실행 전부 재판정 | `node tools/collect.js --all --force --no-wait` | 수십 초 |
| 이력·추세 페이지 재생성 | `node tools/history.js` | 수 초 |
| 순수 로직만 단위로 | `node tools/test/<대상>.test.js` | 1초 내외 |

**단위 테스트가 브레이크포인트를 찍기 가장 쉬운 자리다.** 픽스처(입력 데이터)가 이미
코드 안에 있어서 Prometheus도 Docker도 필요 없다. Node 16에는 `node --test` 러너가 없어
`tools/test/all.js`가 각 테스트 파일을 **한 프로세스에서 `require`** 하는 구조라, 파일
하나만 직접 실행해도 되고 전체를 띄워 놓고 특정 함수에서 멈춰도 된다.

```bash
node --inspect-brk tools/test/regression.test.js
```

**부하가 꼭 필요한 경우**는 세 가지뿐이다. 실행 흐름 자체(1단계~3단계의 순서), 실행 잠금,
워커 타이밍. 이때도 짧게 끝낸다.

```bash
node tools/perf-run.js scripts/posts.js --dataset smoke --vus 5 --duration 1m --loadgen docker
```

`performance/docs/README.md` 의 smoke 규칙과 같은 근거다. **도구의 결함은 데이터 규모와 무관하다.**
반대로 성능 판정은 smoke로 할 수 없다 — 게시글 50건은 전부 버퍼풀에 들어가 medium(1만 건)과
다른 병목을 낸다. **smoke는 도구 확인용, 성능 판정은 medium 이상.**

## 1.4 k6 스크립트는 왜 붙지 않고, 그럼 어떻게 보나

k6는 Go로 만든 프로그램이고 JavaScript를 자체 엔진으로 해석한다. Node가 아니므로
`--inspect-brk`도 없고 Chrome DevTools도 붙지 않는다. **k6 스크립트에는 브레이크포인트를
찍을 수 없다.** 대신 세 가지로 대체한다.

**(1) 한 번만 돌려서 흐름을 본다.**

```bash
node tools/perf-run.js scripts/posts.js --dataset smoke --vus 1 --duration 10s --no-collect
```

`--no-collect`를 붙이면 수집 단계로 넘어가지 않아 확인이 빠르다.

**(2) 출력으로 값을 본다.** k6의 `console.log`는 그대로 터미널에 찍힌다. VU가 여럿이면
출력이 폭주하므로 한 VU의 첫 반복으로 좁힌다.

```javascript
if (__VU === 1 && __ITER === 0) console.log(JSON.stringify(plan));
```

**(3) 순수 로직은 Node로 끌어와 브레이크포인트를 찍는다.** k6 런타임 API를 import하지
않는 파일(`scripts/lib/phases.js`, `sampling.js`, `thresholds.js`)은 Node에서
`await import()`로 그대로 로드된다. 이미 그렇게 하는 테스트가 있다.

```bash
node --inspect-brk tools/test/phases.test.js
node --inspect-brk tools/test/sampling.test.js
```

**이 분리는 우연이 아니라 설계다.** 각 파일 머리말에 "Node 테스트가 직접 로드해 검증해야
하므로 k6 전용 모듈을 import하지 않는다"고 적혀 있다. 즉 **k6 쪽 로직 중 중요한 것은 이미
전부 Node에서 추적 가능한 형태로 빼 두었다.**

## 1.5 브레이크포인트가 측정을 오염시키는 자리 — 여기서는 멈추지 않는다

디버거로 멈추는 것은 **시간을 조작하는 행위**다. 일반 애플리케이션에서는 무해하지만,
시간 자체가 측정 대상인 성능 도구에서는 그게 곧 결과 왜곡이다. 다음 네 곳은 규칙으로
정해 둔다.

**(1) 부하가 흐르는 동안의 Spring 앱**
브레이크포인트에 걸린 요청 스레드가 멈추면 그 스레드가 쥔 DB 커넥션도 함께 묶인다.
커넥션 풀이 마르고, 뒤따르는 모든 요청의 대기 시간이 늘고, p95 분포가 통째로 달라진다.
**그 실행의 수치는 버려야 한다.** 앱 코드를 뜯어야 한다면 부하를 끄고 요청 한 건을 손으로
보내면서 본다.

**(2) `hostprobe` / `loadbench` 워커**
(`tools/lib/hostprobe-worker.js`, `tools/lib/loadbench-worker.js`)
이들은 정해진 간격으로 표본을 뜨는 코드다. 여기서 멈추면 표본 간격이 벌어져 "측정 중
호스트 상태"라는 값 자체가 실제와 달라진다. 여기서는 브레이크포인트 대신 **로그포인트나
출력 파일**로 본다.

**(3) `spawnSync` 호출 경계**
(`tools/perf-run.js:595` k6 실행, `tools/perf-run.js:666` collect 실행)
부모는 자식이 끝날 때까지 이벤트 루프째로 멈춰 있다. 여기서 디버거로 또 멈춰도 **자식은
계속 돌고 있다.** 자식 쪽을 보고 싶으면 부모를 따라가려 하지 말고, 그 자식 명령을 따로
`--inspect-brk`로 직접 실행한다(1.3의 무부하 재현이 바로 그 방법이다).

**(4) 실행 잠금(`tools/lib/run-lock.js`)**
`perf-run.js`는 시작할 때 잠금 파일을 만들어 같은 성능 스택에서 실행이 겹치는 것을 막는다.
잠금이 남아 있으면 다른 실행은 "이미 실행 중"으로 거절된다. 죽은 프로세스의 잠금은 PID
확인으로 자동 회수되지만, **브레이크포인트에서 멈춘 프로세스는 살아 있으므로 회수되지
않는다.** 추적을 끝냈으면 프로세스를 확실히 종료한다.

## 1.6 추적을 시작하기 전 체크리스트

1. **무엇을 확인할 것인지 한 문장으로 쓴다.** 이게 안 되면 디버거를 켤 준비가 안 된 것이다.
2. **부하 없이 재현할 수 있는지 먼저 확인한다.** 대부분 가능하다(1.3).
3. **재수집이 저장된 결과를 덮어쓴다는 점을 인지한다.** `--force`는 `run.json`과 HTML
   리포트를 다시 만든다. 원자료(`k6.json`)는 건드리지 않지만, 판정 결과는 바뀔 수 있다.
   확인이 필요하면 추적 전에 `git status`로 현재 상태를 확인해 둔다.
4. **Prometheus가 떠 있는지 본다.** 안 떠 있어도 `collect.js`는 돌지만 인프라 지표가 통째로
   비고, 그 상태의 판정은 "지표 없음" 경로를 타게 된다. 그 경로를 보려는 게 아니라면 먼저
   환경을 띄운다.

# 2부. 트레이싱 가이드 — 무엇을 어떤 순서로 추적할 것인가

## 2.1 우선순위를 정한 기준

흐름을 아무 데서나 시작하면 길을 잃는다. 다음 네 기준으로 순위를 매겼다.

1. **틀리면 모든 수치가 함께 틀어지는가.** 시간 창(measure 구간)이 틀리면 그 위의 모든
   판정이 무의미해진다. 개별 리포트 서식보다 훨씬 위다.
2. **이미 사고가 난 이력이 있는가.** T-01(규칙 25개 무작동), E-46(포화 오독),
   S-26(RPS 분모), T-03/S-08(창 불일치)은 전부 실제로 잘못된 결론을 만든 자리다. 같은
   자리를 다시 밟을 확률이 가장 높다.
3. **사람이 손으로 착각하기 쉬운가.** 도구가 "비교 불가"라고 말하는데 사람이 표를 나란히
   놓아 틀린 적이 있다. 그런 자리는 눈으로 한 번 봐 두는 값이 크다.
4. **무부하로 재현되는가.** 같은 값어치면 부하 없이 볼 수 있는 흐름을 먼저 본다.

## 2.2 우선순위 표

| 순위 | 흐름 | 한 줄 목적 | 무부하 재현 |
|---|---|---|---|
| **P0-1** | 실행 한 번의 골격 | 1~4단계가 실제로 어떤 순서로 일어나는지 몸으로 안다 | 아니오(smoke 필요) |
| **P0-2** | measure 시간 창 결정 | 모든 수치가 **어느 시간대**의 값인지 확정한다 | 예 |
| **P0-3** | 기준선 선택과 비교 가능성 | 무엇과 비교했고, 왜 다른 것들은 탈락했는지 본다 | 예 |
| **P0-4** | PASS / WARN / FAIL 판정 | 판정이 갈리는 정확한 지점과 건너뛴 규칙을 본다 | 예 |
| **P0-5** | 포화 판정 | 이 수치가 앱 지연인지 큐 대기인지 가른다 | 예 |
| **P1-6** | 인프라 지표 수집 | `infra.flat` 키가 어떻게 채워지고 왜 비는지 본다 | 예(Prometheus 필요) |
| **P1-7** | 호스트 표본 구간 나누기 | 호스트 CPU 값이 measure 구간만 반영하는지 확인한다 | 예 |
| **P1-8** | 저장·승격·재수집 멱등성 | 재수집이 값을 망가뜨리지 않는지 확인한다 | 예 |
| **P1-9** | 데이터셋 가드와 사전 점검 | 실행이 거부·복원되는 조건을 본다 | 예 |
| **P2-10** | k6 phasePlan과 threshold 조립 | 구간과 판정 기준이 어떻게 만들어지는지 본다 | 예(테스트로) |
| **P2-11** | 부하 샘플링(Zipf) | 어떤 글에 요청이 몰리도록 설계됐는지 본다 | 예(테스트로) |
| **P2-12** | 추세·CV·MDE 계산 | "몇 회 더 재야 증명되는가"의 근거를 본다 | 예 |
| **P2-13** | 리포트 렌더링 | 화면의 숫자가 레코드의 어느 필드인지 잇는다 | 예 |

**P0 다섯 개는 순서대로 하는 것을 권한다.** P0-2에서 시간 창을 확정해야 P0-3의 비교가
의미를 갖고, P0-3에서 대조군을 확정해야 P0-4의 판정을 읽을 수 있다. P0-5는 그 판정을
**어떻게 해석할지**를 정하는 축이라 마지막이다.

## P0-1. 실행 한 번의 골격

**목적.** `perf-run.js`가 k6를 부르기 전에 무엇을 준비하고, k6가 끝난 뒤에 무엇을
기록하는지를 순서대로 확인한다. 이 흐름을 한 번 통과하면 나머지 흐름이 전체의 어디쯤인지
감이 생긴다.

**왜 1순위인가.** 나머지 흐름은 전부 이 골격의 부분집합이다. 지도 없이 부분부터 파면
"이 값이 어디서 왔는지"를 매번 거슬러 올라가야 한다.

**진입 명령.** 이 흐름만은 무부하 재현이 안 된다. 가장 짧은 smoke로 돈다.

```bash
cd performance
node --inspect-brk tools/perf-run.js scripts/posts.js --dataset smoke --vus 5 --duration 30s --no-collect
```

`--no-collect`로 수집 단계를 잘라 낸다. 수집은 P0-2 이후에 따로, 무부하로 본다.

**정차 지점.**

| # | 위치 | 무엇을 확인하나 |
|---|---|---|
| 1 | `tools/perf-run.js:449` `main()` 첫 줄 | `parseArgs()` 결과 — CLI 인자가 어떤 객체가 됐나 |
| 2 | `acquireRunLock()` 호출 직후 | 잠금 파일 경로와 그 안의 pid |
| 3 | `gitMeta()` 반환 직후 | 브랜치·커밋·실행자가 실행 기록에 어떻게 박히나 |
| 4 | `datasetFingerprint()` 반환 직후 | 데이터셋 지문이 있나 없나(없으면 비교 대상에서 빠진다) |
| 5 | `tools/perf-run.js:313` `preflight()` | 데이터셋 상태 확인 결과와 guard 모드 |
| 6 | k6 인자 배열 `args` 완성 직후 | `-e VUS=`, `-e RATE=`, `--summary-trend-stats`가 실제로 어떻게 조립됐나 |
| 7 | `tools/perf-run.js:595` `spawnSync` 직전 | **여기서 부모가 멈춘다.** k6 시작 시각 `k6StartedAt` 확인 |
| 8 | `spawnSync` 반환 직후 | k6 종료 코드(`k6.status`) — 99면 threshold 미달 |
| 9 | `newIds` 계산부 | 이번 실행이 남긴 결과 파일을 어떻게 식별하나 |
| 10 | `tools/perf-run.js:382` `postflight()` | `dbstate.json`에 무엇이 실려 나가나 |

**꼭 봐야 할 값.** `env`(k6에 넘기는 환경변수 전체), `args`(k6 명령줄 전체),
`stateBlock`(실행 조건 기록), `k6.status`.

**함정.** 7번에서 멈춘 채 오래 두면 k6는 이미 돌고 있는데 부모만 정지한 상태가 된다.
측정에는 영향이 없지만(부모는 어차피 대기 중이다), 잠금이 계속 잡혀 있다는 점은 같다.

**이어지는 흐름.** 10번에서 나온 `runId`를 들고 P0-2로 간다.

## P0-2. measure 시간 창 결정

**목적.** "이 실행의 수치는 몇 시 몇 분부터 몇 분까지의 값인가"를 확정한다. k6 지표,
Prometheus 지표, 호스트 표본이 **같은 시간대**를 가리키는지 눈으로 확인한다.

**왜 2순위인가.** 시간 창이 어긋나면 그 위의 모든 비교가 무의미해진다. 실제로 예전에는
`--warmup`이 수집기에서만 시작 시각을 밀었고 k6 지표는 전체 구간으로 계산돼 있었다
(T-03/S-08). 서로 다른 창의 값을 상관분석해 **잘못된 인과 결론을 냈다가 철회한 적도
있다**(`perf-session-drift.md` 8-e).

**진입 명령.**

```bash
node --inspect-brk tools/collect.js <runId> --force --no-wait
```

**정차 지점.**

| # | 위치 | 무엇을 확인하나 |
|---|---|---|
| 1 | `tools/collect.js:307` `processRun()` 첫 줄 | `k6rec.run.phasePlan` — 계획표가 실려 있나 |
| 2 | `tools/collect.js:82` `measureWindow()` 진입 | 입력이 되는 `run.phasePlan`, `k6StartedAt` |
| 3 | `measureWindow()` 반환 직전 | `from`, `to`, `durationSec`, **`mode`**, `incomplete` |
| 4 | `record.k6.phases` 접근부 | k6가 계산한 measure 구간과 3번의 창이 같은 시간대인가 |

**꼭 봐야 할 값.**

- `window.mode` — `'measure'`가 아니면 **measure 구간이라는 개념이 없는 실행**이다.
  과거 `run.json`이거나 진단용 시나리오다. 이 경우 전체 구간으로 폴백하되 그 사실이
  `mode`에 남는다. 조용히 "이것도 measure"라고 우기지 않는 설계다.
- `window.incomplete` — 조기 종료로 창이 잘렸는지 여부.
- `phasePlan.measureStartOffsetSec`, `measureSec` — 계획된 구간.

**함정.** `to`를 실행 종료 시각으로 두지 **않는다.** `measureSec`만큼만 뒤로 가서
rampdown을 제외한다. 이 한 줄을 놓치면 "왜 창이 실행 끝보다 이른가"에서 헤맨다.

**이어지는 흐름.** 이 창이 P1-6(인프라 조회)과 P1-7(호스트 표본 나누기)의 입력이 된다.

## P0-3. 기준선 선택과 비교 가능성

**목적.** 이번 실행이 **무엇과 비교됐는지**, 그리고 후보들이 **왜 탈락했는지**를 본다.

**왜 3순위인가.** 이 저장소가 가장 크게 틀린 자리다. 조건 판정이 없던 시절 200VU·large
실행이 15VU·small 실행을 기준선으로 잡아 "+59,000% 회귀"를 보고했다. 지금은 도구가 막지만,
**사람이 리포트 두 개를 손으로 나란히 놓는 것은 못 막는다.** 실제로 그렇게 틀렸다(E-46).
그래서 "도구가 어떤 근거로 거절하는지"를 눈으로 봐 둘 값어치가 크다.

**진입 명령.** 위와 같다. 단위로 보려면 `node --inspect-brk tools/test/comparability.test.js`.

**정차 지점.**

| # | 위치 | 무엇을 확인하나 |
|---|---|---|
| 1 | `tools/lib/repository.js:399` `findBaseline()` | 후보 목록이 어디서 오나(`index.json`) |
| 2 | `tools/lib/repository.js:329` `eligibilityOf()` | 후보가 기준선 **자격**을 갖췄는지 판정 |
| 3 | `tools/lib/comparability.js:40` `conditionsOf()` | 이 실행의 조건 묶음이 어떻게 추출되나 |
| 4 | `tools/lib/comparability.js:79` `compare()` | 조건별 일치·불일치가 어떻게 판정되나 |
| 5 | `tools/lib/comparability.js:57` `seriesHash()` | 조건 묶음이 어떤 해시로 압축되나 |
| 6 | `findBaseline()` 반환 직전 | `baseline`, `rejected`, `hadPriorCandidates` |

**꼭 봐야 할 값.**

- `search.baseline` — `null`이면 **상대 비교가 아예 실행되지 않았다.** 리포트의 증감률이
  비어 있는 이유가 여기다.
- `search.rejected` — 탈락 사유 목록. 최근 몇 건만 담긴다.
- `search.hadPriorCandidates` — 후보가 있었는데 전부 탈락한 것인지, 정말 첫 실행인지를
  가른다(S-10). `rejected`의 길이로는 판단할 수 없어서 따로 있는 값이다.
- `seriesHash` — 이 값이 다르면 두 실행은 **다른 실험**이다.

**함정.** 조건 값에는 **측정 결과가 하나도 들어가면 안 된다.** `conditions.js` 머리말이
그 이유를 길게 설명한다. 관측값인 `vusMax`를 조건에 넣으면, 서버가 느려질수록 VU가 늘어
기준선이 부적격이 되고 → 비교가 생략되고 → 게이트를 통과한다. **회귀가 심할수록 면제되는
필터**가 된다. 조건에 무엇이 들어가고 무엇이 빠지는지 볼 때 이 관점으로 본다.

## P0-4. PASS / WARN / FAIL 판정

**목적.** 판정이 갈리는 정확한 지점을 본다. 특히 **어떤 규칙이 건너뛰어졌고 그 이유가
무엇인지**를 확인한다.

**왜 4순위인가.** T-01이 여기서 났다. 규칙 32개 중 25개가 `infra.flat`의 키를 못 읽어
조용히 SKIP되고 있었고, 원자료에는 Hikari 대기 205개, CPU throttling 99.98%가 찍혀 있는데
자동 판정은 통과였다. **"실패가 안 떴다"와 "규칙이 안 돌았다"는 전혀 다른 말이다.**

**진입 명령.** 무부하 재수집 또는 `node --inspect-brk tools/test/regression.test.js`.

**정차 지점.**

| # | 위치 | 무엇을 확인하나 |
|---|---|---|
| 1 | `tools/lib/regression.js:299` `analyze()` 진입 | 규칙 목록과 현재 레코드가 들어오는 모양 |
| 2 | `tools/lib/regression.js:138` `isApplicable()` | 이 규칙이 이 실행에 적용되는가 |
| 3 | `tools/lib/regression.js:162` `isRequired()` | 값이 없을 때 SKIP인가 실패인가 |
| 4 | `tools/lib/regression.js:38` `pick()` | **점으로 이어진 키를 실제로 찾아내는가** |
| 5 | `tools/lib/regression.js:180` `evaluateRule()` | 방향성·노이즈 플로어·기준선 하한·절대 게이트 적용 |
| 6 | `analyze()` 반환 직전 | 규칙별 결과 배열과 최종 등급 |

**꼭 봐야 할 값.**

- 4번에서 `pick(record.infra.flat, '<키>')`가 `undefined`를 반환하는 규칙의 개수.
  **이것이 T-01의 재발 여부를 재는 직접적인 값이다.**
- `evaluateRule()` 안의 네 방어선이 각각 어디서 발동하는가.
  1. **방향성** — 지표마다 어느 쪽이 나쁜지가 규칙에 선언돼 있다(TPS는 내려가면 나쁘고,
     p95는 올라가면 나쁘다).
  2. **노이즈 플로어** — 절대 변화가 작으면 비율이 커도 무시한다(2ms → 3ms는 +50%지만 무시).
  3. **기준선 하한** — 기준값이 너무 작으면 비율 비교를 건너뛴다(0에 가까운 분모 방지).
  4. **절대 게이트** — 직전보다 좋아졌어도 SLO를 넘으면 실패다. 매번 9%씩 나빠지며 영원히
     통과하는 "삶은 개구리"를 막는 장치다.

**함정.** 규칙 결과가 SKIP이면 리포트에서 눈에 잘 띄지 않는다. 6번에서 **SKIP 개수를 직접
세어 본다.** 콘솔에 이렇게 물어보면 된다.

```javascript
results.filter(r => r.status === 'SKIP').map(r => r.key)
```

## P0-5. 포화 판정

**목적.** 이 실행의 p95가 **애플리케이션 지연인지 큐 대기인지**를 가르는 판정을 따라간다.

**왜 5순위인가(그리고 왜 P0인가).** 이 축이 없어서 닷새를 날렸다. `normal-day` 실행의
p95 10,000~17,000ms를 앱 지연으로 읽고 원인을 호스트·커널·전원 관리에서 찾았는데, 같은
앱·같은 데이터셋·같은 커밋을 포화 이하(도착률 4/s)에서 재면 **278ms**였다. 38배 차이의
정체는 코드가 아니라 대기줄이었다. 신호는 처음부터 전부 있었다 — Hikari 획득 p95가 전체
p95의 57%, 대기 145개, CPU throttled 99.86%. **읽는 사람이 그 축을 몰랐을 뿐이다.**

**진입 명령.** 무부하 재수집 또는 `node --inspect-brk tools/test/saturation.test.js`.

**정차 지점.**

| # | 위치 | 무엇을 확인하나 |
|---|---|---|
| 1 | `tools/lib/saturation.js:110` `assess()` 진입 | 어떤 신호(`SIGNALS`)를 보는가 |
| 2 | `tools/lib/saturation.js:95` `achievedRate()` | 목표 도착률 대비 실제 처리율 |
| 3 | `assess()` 반환 직전 | 판정 결과(regime)와 근거 신호 목록 |
| 4 | `tools/lib/saturation.js:171` `regimeMismatch()` | 기준선과 **상태(regime)가 다른가** |

**꼭 봐야 할 값.** `record.saturation.regime`, 발동한 신호 목록,
`record.saturation.baselineRegimeMismatch`.

**함정 두 가지.**

1. **포화 판정은 게이트를 실패시키지 않는다.** stress 계열 시나리오는 포화가 목적이기
   때문이다. 그래서 "FAIL이 안 떴으니 정상"이 아니다. 이 값은 **해석 지침**이다.
2. **`measurementStatus`와 다른 축이다.** 지표가 전부 멀쩡해도 포화면 값의 의미가 달라진다.
   두 값을 같은 칸에서 읽지 않는다.

## P1-7. 호스트 표본 구간 나누기

**목적.** 호스트 CPU 값이 **measure 구간만** 반영하는지 확인한다.

**왜 이 순위인가.** 예전 요약은 warmup+measure+rampdown 전체 평균이었는데, 비교 대상인
p95는 measure 구간만이었다. 서로 다른 창을 상관분석해 **잘못된 인과 결론을 냈다가 철회

**진입 명령.** 무부하 재수집 또는 `node --inspect-brk tools/test/hostprobe-phase.test.js`.

**정차 지점.**

| # | 위치 | 무엇을 확인하나 |
|---|---|---|
| 1 | `processRun()` 안 `loadHostProbeRaw()` 직후 | 원시 표본이 몇 줄인가 |
| 2 | `tools/lib/hostprobe.js:249` `sliceByPhase()` | 시간축을 어떻게 세 구간으로 자르나 |
| 3 | `tools/lib/hostprobe.js:197` `resolveIndex()` | 열 이름과 값 배열을 어떻게 맞추나 |
| 4 | `tools/lib/hostprobe.js:221` `summarize()` | 구간별 요약이 어떻게 계산되나 |

# 3부. 세션 기록 양식

## 3.1 무엇을 한 세션으로 볼 것인가

**질문 하나가 한 세션이다.** 2부의 흐름 하나를 통째로 도는 것이 아니라, 그 흐름에서 답하고
싶은 질문 하나가 단위다. 예를 들어 P0-4를 추적하더라도 세션은 "지금 저장된 실행에서 SKIP된
규칙이 몇 개이고 이유가 무엇인가" 하나다. 한 세션에서 세 가지를 확인하려 들면 기록이 섞여
나중에 아무것도 못 찾는다.

세션에는 `TR-01`부터 일련번호를 붙인다. 이 번호는 발견 ID(`T-##` / `S-##` / `E-##`)와 다른
계열이다. **추적은 발견이 아니라 관측 행위**이고, 관측 결과 결함이 확인되면 그때 별도로
발견 ID를 발급해 `perf-findings-*.md`에 올린다.

## 3.2 양식

아래 블록을 통째로 복사해 3.4의 보관소에 붙여 넣고 채운다.

````markdown
### TR-nn. <한 줄 질문 — "무엇을 확인하려 했나">

- **날짜**: YYYY-MM-DD
- **추적한 흐름**: P0-4 (2부 기준). 여러 개면 전부 적는다
- **관련 발견/문서**: T-##, E-##, perf-session-drift.md 등. 없으면 "없음"
- **결론**: <한 문장. "확인됨 / 반증됨 / 판단 불가" 중 하나로 시작한다>

**1) 확인하려던 질문과 사전 가설**

> 디버거를 켜기 전에 코드를 읽고 세운 예상을 쓴다. **틀릴 수 있는 형태**로 쓴다.
> 예: "infra.flat 에 pool.hikariPending 키가 없어서 규칙 3개가 SKIP될 것이다."
> "확인해 보겠다" 같은 문장은 가설이 아니다.

**2) 대상과 실행한 명령**

```bash
cd performance
node --inspect-brk tools/collect.js normal-day-2026-08-19T09-46-07 --force --no-wait
```

대상 실행 ID, 데이터셋, 환경이 무엇이었는지 함께 적는다. 무부하 재현이 아니라 부하를
걸었다면 그 사실과 이유를 반드시 적는다.

**3) 브레이크포인트 위치**

| # | 파일:줄 | 함수 | 왜 여기서 멈췄나 |
|---|---|---|---|
| 1 | tools/lib/regression.js:38 | `pick()` | flat 키 조회가 실패하는지 직접 보려고 |

줄 번호는 **추적 당시의 값**을 적는다. 문서 본문의 줄 번호와 달라졌다면 그 사실도 적는다.

**4) 관측한 값**

```text
rule.key         = 'pool.hikariPending.avg'
pick(flat, key)  = undefined
Object.keys(flat).length = 41
SKIP 규칙 수      = 3
```

**요약하지 말고 본 그대로 적는다.** 요약한 값은 나중에 다른 가설을 검증하는 데 쓸 수 없다.
길면 잘라도 되지만, 자른 사실을 표시한다.

**5) 실제로 흐른 경로**

```text
processRun() → analyze() → isApplicable() [true]
             → pick(flat, 'pool.hikariPending.avg') → undefined   ← 예상과 다름
             → isRequired() [false] → SKIP
```

예상과 갈라진 지점을 화살표로 표시한다. 이 칸이 콜스택과 분기를 재구성하는 근거다.

**6) 확정된 사실과 아직 추측인 것**

> 사실과 추측을 **한 문장 안에 섞지 않는다.**
> 사실: "이 실행에서 규칙 3개가 키 부재로 SKIP됐다."
> 추측: "Prometheus 익스포터 설정이 바뀌어서일 수 있다 — 확인하지 않았다."

**7) 후속**

> 발견 항목을 등록했는가(어느 ID), 어떤 문서를 고쳤는가, 남은 의문은 무엇인가.
> 아무것도 안 했으면 "없음"이라고 명시한다. **빈칸으로 두지 않는다.**
````

## 3.3 양식이 이 순서인 이유

- **결론을 맨 위에 둔 것**은 세션이 쌓이면 목록만 훑게 되기 때문이다. 스크롤해야 결론이
  나오는 기록은 안 읽힌다.
- **사전 가설을 먼저 쓰게 한 것**이 이 양식의 핵심이다. 값을 본 뒤에 가설을 쓰면 언제나
  자기가 맞았던 것처럼 보인다. 틀린 가설이 남아야 "그때 왜 그렇게 생각했는지"를 재구성할
  수 있고, 그게 다음 추적의 출발점이 된다.
- **관측값을 요약하지 않는 것**은 이 문서군의 공통 규칙(분량보다 재구성 가능성)과 같다.
- **6번에서 사실과 추측을 나눈 것**은 E-46의 교훈이다. 관측값(포화 신호)은 정확했는데
  해석(앱 지연)이 추측이었고, 그 둘이 한 문장에 섞여 있어서 닷새 동안 아무도 의심하지
  않았다.
- **7번을 강제하는 것**은 추적이 개인 메모로 끝나는 것을 막기 위해서다. 장부에 아무것도
  남지 않으면 그 추적은 없었던 것과 같다.
