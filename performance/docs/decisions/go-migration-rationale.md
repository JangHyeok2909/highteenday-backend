# 측정 도구 Go 이식 — 명분과 계획

> 기준 시점: 2026-08-25
> 답하는 질문: **"측정 도구를 JavaScript에서 Go로 옮길 정당한 이유가 있는가? 있다면 무엇을
> 어떤 순서로 옮기고, 옮기는 동안 측정의 무결성을 어떻게 지키는가?"**
> 성격: 이 문서는 **결함 장부가 아니라 결정 기록(ADR) + 실행 계획**이다. 다른
> `perf-*.md` 가 "무엇이 잘못됐나"를 다루는 것과 달리, 여기는 "무엇을 하기로 했고 왜인가"를
> 다룬다.
> 짝 문서: 시스템이 무엇을 재는지는 [perf-measurement-explained.md](../guides/perf-measurement-explained.md),
> 오픈소스화 목표는 아래 1-2 절에서 다룬다.

---

## 이 문서가 필요한 이유

두 가지 위험을 미리 막기 위해서다.

**첫째, 명분을 지어낼 위험.** "Go가 빠르다"는 이유로 이식을 정당화하면 나중에 무너진다.
아래 1부에서 보듯 **이 시스템에서 속도는 근거가 되지 못한다.** 틀린 명분 위에 몇 주를 쓰면
그 시간 전체가 방어할 수 없는 작업이 된다. 그래서 기각한 명분을 살아남은 명분보다 먼저,
더 자세히 적는다.

**둘째, 이식 중에 측정 연속성을 잃을 위험.** 이 저장소에는 과거 실행 기록이 누적돼 있고,
판정 로직이 미세하게 달라지면 그 기록 전체가 비교 불가능해진다. `tools/cpu-bench.js:59` 에
이미 경고가 붙어 있다 — *"⚠ 이 명령은 바꾸지 않는다. 과거 기록(5,013ms)과 비교하는 유일한
연결고리다."* 이식은 이 경고를 정면으로 위협하는 작업이다.

2부의 **차등 테스트(differential testing)** 가 둘째 위험에 대한 답이고, 동시에 "내가
이해했다고 착각하는 것"에 대한 답이기도 하다.

---

## 가장 짧은 결론

**오케스트레이터 계층만 Go로 점진 이식한다. k6 시나리오는 JS로 남긴다. 성능은 근거가 아니다.**

- **살아남은 명분:** ① k6 런타임과의 언어 정합성 ② 단일 바이너리 배포 ③ 동시성 구조 단순화
  ④ 코드 레벨 이해 확보
- **기각한 명분:** 실행 속도, 메모리 효율, 의존성 관리 — 셋 다 이 코드베이스에 해당하지 않는다
- **무결성 장치:** 이식한 모듈은 JS 원본과 **동일 입력에 대해 바이트 단위로 동일한 출력**을
  내야 한다. 이것이 통과 조건이자 "이해했다"의 정의다
- **중단 가능:** 1단계만 하고 멈춰도 손해가 없다. JS 원본은 끝까지 지우지 않는다

# 1부 — 명분

## 1-0. 먼저 기각한 명분 (이 절이 가장 중요하다)

명분을 세울 때 가장 먼저 할 일은 **쓰지 않기로 한 이유를 확정하는 것**이다. 아래 셋은
Go 이식을 정당화할 때 흔히 쓰이지만, 이 시스템에서는 전부 거짓이다. 스스로 먼저 기각해
두면 나중에 누가 되물어도 흔들리지 않는다.

### 기각 ①. "Go로 바꾸면 측정이 빨라진다" — 거짓

**JS 코드는 계산을 거의 하지 않는다.** 측정값을 만들어내는 작업은 전부 외부 프로세스가
수행하고, JS는 그것을 실행하고 결과를 읽는 오케스트레이터일 뿐이다.

가장 분명한 증거가 `tools/cpu-bench.js` 다. 이름은 "CPU 벤치마크"지만 계산을 JS로 하지
않는다. 실제 작업은 Docker 컨테이너 안의 셸 한 줄이다.

```
dd if=/dev/zero bs=1M count=3000 | md5sum        # single 축
```

JS가 하는 일은 `spawnSync` 로 컨테이너를 띄우고 벽시계 시간을 재는 것뿐이다. 마찬가지로
부하는 k6가, 호스트 지표는 `typeperf` 가 만든다. **오케스트레이터를 Go로 바꿔도 `dd` 가
빨라지지 않는다.**

> 이건 오히려 설계가 잘 됐다는 증거다. 측정 도구 자신이 CPU를 쓰면 측정 대상을 방해한다.
> 지금 구조는 그 위험이 구조적으로 없다.

### 기각 ②. "Go는 동시성 성능이 좋다" — 이 시스템에는 무관

시나리오 최대 VU는 1,000이다. k6가 감당하기에 여유 있는 규모이고, 애초에 **측정 대상 앱이
CPU 2코어로 제한**돼 있다. 부하 생성기가 병목일 수 없는 구조다. 리포트가 다루는 데이터도
JSONL 수십~수백 줄 규모라 파싱 처리량은 논점이 아니다.

### 기각 ③. "Go는 의존성 관리가 깔끔하다" — 비교 대상이 없다

`performance/package.json` 에는 **`dependencies` 항목 자체가 없다.** 전체 코드가
`fs`, `path`, `child_process`, `os`, `crypto`, `http` 같은 Node 내장 모듈만 쓴다. 따라서:

- `node_modules` 비대화 → 해당 없음
- npm 공급망 보안 위험 → 해당 없음
- 의존성 버전 충돌 → 해당 없음

Node의 대표적 약점이 이 프로젝트에는 존재하지 않으므로, 그 약점을 해결한다는 명분도
성립하지 않는다.

---

## 1-1. 명분 A — Go는 이 스택의 모국어다

**등급: 강함. 되물어도 무너지지 않는다.**

**사실.** k6는 Go로 작성된 프로그램이다. 부하를 실제로 만들어내는 HTTP 커넥션 풀, VU
스케줄러, 메트릭 집계는 전부 Go 코드가 수행한다. JavaScript는 k6에 내장된 JS 엔진(goja)
위에서 "매 반복에 무엇을 요청할지"를 기술하는 얇은 층이다.

**따라서 k6를 확장하려면 언어 선택권이 없다.** xk6(k6 확장 빌드 시스템)로 만드는 커스텀
모듈 — 커스텀 메트릭 출력기, 미지원 프로토콜, 자체 임계값 로직 — 은 **Go로만** 작성된다.

**왜 이게 지금 우리에게 걸리는가.** 현재 `tools/collect.js`(551줄)와
`tools/lib/metrics-catalog.js`(918줄)가 하는 일이 **정확히 xk6 출력 확장이 하는 일**이다.
k6 실행이 끝난 뒤 결과 파일을 파싱해서 지표를 정리하는 작업이다. 이 계층이 Go가 되면,
나중에 "실행 후 파싱"을 "실행 중 직접 출력"으로 승격시킬 경로가 열린다. JS로는 그 경로가
아예 없다.

**한 줄 요약:** 도구 체인을 측정 런타임과 같은 언어로 맞추면 확장 지점이 생긴다.

## 1-2. 명분 B — 단일 바이너리 배포

**등급: 강함. 다만 오픈소스화를 실제로 착수할 때만 유효하다.**

이 측정 시스템의 최종 목표는 **CLI 로 추출해 오픈소스로 공개하는 것**이고, 그때 내세울
핵심은 **"CI 한 줄로 성능 게이트"** 다.

이 목표에 한해 Go가 명확히 우월하다.

| | 사용자가 해야 하는 일 |
|---|---|
| **Go** | 바이너리 하나 내려받아 실행 |
| **Node** | Node 런타임 설치 → 버전 확인 → 스크립트 경로 지정 |

**보조 증거 — 이미 이식성 비용을 치르고 있다.** `tools/test/all.js` 주석에 이렇게 적혀 있다:
*"Node 16 은 `node --test` CLI 러너가 없어(18+) 파일을 직접 require 한다."* 즉 구버전
Node에서도 테스트가 돌게 하려고 러너를 우회 구현해 두었다. 이런 종류의 유지 비용은 단일
바이너리에서 **정의상 사라진다.**

**주의.** 이 명분은 "지금 당장"의 이유가 아니다. 배포를 실제로 시작하지 않으면 실현되지
않는 이득이다. 그래서 계획 4단계에 배치했다.

## 1-3. 명분 C — 동시성 구조가 실제로 단순해진다

**등급: 중간. 절반만 사실이므로 말할 때 정확히 말해야 한다.**

**Problem.** `tools/perf-run.js` 는 k6를 `spawnSync` 로 실행한다. `spawnSync` 는 자식
프로세스가 끝날 때까지 **Node의 이벤트 루프를 통째로 정지**시킨다. 부하 테스트가 도는 27분
동안 부모 프로세스의 어떤 타이머도, 어떤 스트림 콜백도 실행되지 않는다.

**Impact.** 부하가 도는 **중에** 무언가를 재야 하는 기능이 전부 불가능해진다.

**Evidence.** `tools/lib/hostprobe-worker.js:5-17` 주석에 실측 실패가 남아 있다.
typeperf의 stdout을 부모에서 듣게 했더니 27분 내내 콜백이 한 번도 안 불려 **표본이 0개**가
됐고, typeperf가 파일로 쓰게 했더니 버퍼가 안 비워져 **7바이트짜리 빈 파일**이 남았다.
해법으로 별도 프로세스 2개를 만들었다.

```text
tools/lib/hostprobe.js         328줄  ┐ 호스트 지표 샘플링
tools/lib/hostprobe-worker.js  102줄  ┘   프로세스 분리 + 파일로 결과 전달
tools/lib/loadbench.js         168줄  ┐ 워밍업 중간 대조 벤치
tools/lib/loadbench-worker.js   46줄  ┘   동일
─────────────────────────────────────────
                               644줄
```

**Go에서는.** `exec.Command().Run()` 은 호출한 고루틴 하나만 막는다. 워커 스크립트도, 파일을
통한 결과 전달도, "부모가 언제 죽어도 표본이 남게" 하는 방어 코드도 필요 없다.

**절반만 사실인 부분 — 반드시 이렇게 말할 것.** Node에서도 비동기 `spawn` 을 쓰면 같은
문제가 풀린다. **언어의 한계가 아니라 동기 API를 고른 결과다.** 그러므로 주장은
*"JS로는 불가능하다"* 가 아니라 **"Go에는 이 실수를 할 API가 없다"** 여야 한다. 전자로
말하면 아는 사람에게 즉시 걸린다.

## 1-4. 명분 D — 코드 레벨 이해 확보

**등급: 강함. 숨기면 오히려 약해진다.**

**현재 상태(사실).** 이 시스템의 저자는 각 장치의 역할은 알지만 **코드 레벨 이해는 얕다.**
`performance/` 아래 JS는 18,280줄이고, 상당 부분이 여러 세션에 걸쳐 축적됐다.

**선택지는 둘이었다.**

1. JS 문법을 익혀 가며 18,280줄을 읽는다
2. Go를 익혀 가며 오케스트레이터를 한 모듈씩 다시 짠다

**2를 택하는 이유.** 읽기만 하는 이해는 검증되지 않는다. "읽었다"와 "이해했다" 사이에
객관적 경계가 없다. 반면 **다시 짜면 통과/실패가 나온다** — 차등 테스트가 그 경계를
만들어 준다(2부). 그리고 그 과정에서 배우는 언어가 커리어에 쓰이는 쪽이면 같은 시간에
두 가지를 얻는다.

**이 명분을 숨기지 말 것.** "레거시를 이해하기 위해 이식했고, 이해했음을 차등 테스트로
증명했다"는 서사는 그 자체로 강하다. **레거시 인수인계와 구조가 같기 때문이다.**
혼자 만든 시스템이라 남이 쓴 코드를 넘겨받아 본 경험이 없다는 약점에 대한 답으로도 쓸 수 있다. 어설픈 기술적 포장을 씌우는 것보다 A·B·C와 나란히 놓는 편이
훨씬 신뢰를 준다.

## 1-6. 되물음에 대한 준비된 답

이식을 설명할 때 실제로 나올 질문들이다. 답을 미리 고정해 둔다.

**Q. 왜 Go인가? 성능 때문인가?**
아니다. 측정 작업은 전부 외부 프로세스(k6·docker·typeperf)가 수행하고 오케스트레이터는
계산을 하지 않는다. 이식으로 측정이 빨라지지 않는다. 이유는 셋이다 — 측정 런타임인 k6
자체가 Go라 확장 경로가 열리고, 배포가 단일 바이너리가 되며, 실행 중 계측을 위해 만든
워커 프로세스가 고루틴으로 대체된다.

**Q. 전부 옮기나?**
아니다. k6 시나리오 3,900줄은 JS로 남는다. k6가 JS만 받기 때문이다. 그리고 이건 약점이
아니라 설계다 — 오픈소스 CLI에서 사용자가 자기 시나리오를 써 넣는 확장 지점이 된다.

**Q. 이미 도는 시스템을 왜 건드리나? 위험하지 않나?**
위험은 "판정 로직이 미묘하게 달라져 과거 기록과 비교 불가능해지는 것"이다. 그래서 모든
이식 모듈은 JS 원본과 동일 입력에 대해 바이트 단위로 같은 출력을 내야 통과다. CI가 강제한다.
JS 원본은 이식이 끝날 때까지 지우지 않으므로 언제든 되돌릴 수 있다.

**Q. 동시성 문제는 JS로도 풀 수 있지 않나?**
맞다. 비동기 `spawn` 으로 풀린다. 언어의 한계가 아니라 API 선택의 결과다. Go의 이점은
"그 실수를 할 API가 없다"는 것이지 "JS로 불가능하다"가 아니다.

**Q. 학습이 목적이면 사이드 프로젝트로 하면 되지 않나?**
학습만이 목적이면 그렇다. 그런데 여기에는 이해해야 할 기존 시스템이 있고, 이식은 그
이해를 강제로 확보하는 수단이다. 새 프로젝트로는 "남이 짠 코드를 정확히 이해했음을
증명하는" 경험을 얻을 수 없다.

# 2부 — 무결성 장치: 차등 테스트

## 2-1. 무엇을 막으려는가

이식에는 두 가지 실패 방식이 있고, 하나의 장치로 둘 다 막는다.

| 위험 | 증상 | 발견되지 않으면 |
|---|---|---|
| **측정 연속성 파괴** | 판정 로직이 미세하게 달라짐 | 누적된 과거 실행 기록 전체가 비교 불가능해진다 |
| **이해했다는 착각** | 조건 하나를 놓쳤는데 본인은 모름 | 잘못된 판정이 조용히 나간다 |

## 2-2. 방법

같은 입력을 JS 버전과 Go 버전에 넣고, **출력이 한 글자도 다르지 않은지** 확인한다.

```bash
# 같은 입력으로 양쪽을 돌리고 출력을 비교한다
node performance/tools/history.js --json > /tmp/js.json
./perfctl history --json                 > /tmp/go.json

diff /tmp/js.json /tmp/go.json    # 출력이 비어야 통과
```

기계 판독 형식(`--json`)이 있는 도구는 그대로 쓰면 되고, 없으면 이식 대상 모듈에
**JSON 덤프용 진입점을 먼저 만들어 둔다.** 사람이 읽는 형식(HTML 리포트, 콘솔 배너)은
공백·줄바꿈 차이로 오탐이 나므로 비교 대상에서 뺀다 — 대신 그 형식을 만드는 **원본 데이터
구조**를 비교한다.

**부동소수 주의.** JS는 모든 숫자가 `double` 이다. Go에서 `float64` 로 맞추고, JSON 출력 시
자릿수 표현이 같은지 확인한다(예: JS에서 `0.1 + 0.2` 는 `0.30000000000000004` 로 출력된다).
이 차이는 1단계 `trends.js`(통계 계산)에서 반드시 만나므로 미리 알아 둔다.

## 2-3. 기존 테스트 3,711줄은 명세서다

`tools/test/` 는 단순한 테스트가 아니라 **판정 규칙을 정밀하게 적어 둔 문서**다.

| `phases.test.js` | 441 | (스크립트 구간 계산) | — |
| `repository.test.js` | 297 | `lib/repository.js` | 500 |

## 2-4. 작업 루프 — 테스트를 먼저 옮긴다

모듈 하나마다 이 순서를 지킨다.

1. **JS 테스트를 읽는다** — 이 모듈이 무엇을 보장하는지 파악한다
2. **Go 테스트를 먼저 쓴다** — 아직 구현이 없으니 컴파일 실패한다
3. **Go 구현을 쓴다** — 테스트가 통과할 때까지
4. **차등 테스트** — 같은 입력에 JS와 Go의 출력이 동일한지 확인
5. **커밋** — 커밋 본문에 차등 테스트 결과를 적는다

**2번이 핵심이다.** 테스트를 먼저 옮기면 원본을 읽지 않고는 진행이 불가능해진다. 대충 읽고
넘어가는 것을 구조적으로 막는다.

# 3부 — 이식 계획

## 3-0. 전제 교정: JS는 "쓰지 않는다"이지 "읽지 않는다"가 아니다

이식은 원본을 읽는 일이다. `saturation.js` 180줄을 Go로 옮기려면 그 180줄이 무슨 판정을
하는지 읽어야 한다. **JS를 쓰지 않을 수는 있어도 읽지 않을 수는 없다.**

다행히 비용 차이가 크다.

- **JS를 쓰기** — 비동기, 프로토타입, `this` 바인딩, 이벤트 루프까지 알아야 한다. 이
  저장소가 실제로 밟은 함정(`spawnSync` 가 이벤트 루프를 막는 문제)이 정확히 그 영역이다
- **JS를 읽기** — 이 코드베이스는 `require`, 함수, 객체, 배열, `map`/`filter` 가 거의
  전부다. **의존성이 0개**라 프레임워크 관용구도 없다. 반나절이면 읽는 데 지장 없다

**목표를 이렇게 고정한다: JS는 읽기만 하고, 쓰는 언어는 Go로 한다.**

## 3-1. 지금 무엇이 JS로 짜여 있는가

`performance/` 아래 JS 총 **18,280줄**. 성격이 완전히 다른 세 덩어리이고, 이 구분이 계획의
전부다.

| 덩어리 | 줄 수 | 하는 일 | 이식 |
|---|---|---|---|
| `tools/` (`lib`·`test` 포함) | 12,756 | 실행 오케스트레이션·수집·판정·리포트 | **대상** |
| `scripts/`, `scenarios/` | 3,900 | k6 부하 시나리오 (VU가 실행하는 코드) | **불가** |
| `datasets/`, `environment/` | 1,624 | 시드 데이터 생성, 환경 부트스트랩 | 제외 |

## 3-2. 의존 그래프 — 이식 순서는 여기서 나온다

`tools/lib/` 내부 의존을 실제로 뽑은 결과다. 화살표는 "무엇을 필요로 하는가"다.

```text
[잎 — 아무것도 필요로 하지 않음]
  saturation(180)  trends(400)  format(92)  conditions(241)
  metrics-catalog(918)  run-lock(77)  grafana(89)  guard(87)
  hostprobe(328)  loadbench(168)  promql(177)  dbstate(237)

[1단계 의존]
  comparability(166) ─> conditions

[2단계 의존]
  regression(552) ─> comparability
  repository(500) ─> comparability

[3단계 의존]
  report(817)        ─> format, comparability, repository
  detail-report(289) ─> format, comparability, trends, report
```

**잎부터 올라간다.** 잎 모듈은 다른 모듈을 몰라도 되므로 Go를 처음 쓰기에 안전하고,
차등 테스트도 입력·출력이 단순해 만들기 쉽다.

## 3-3. 0단계 — 안전망 (코드 이식 전)

이식을 시작하기 전에 해 둘 것.

- [ ] Go 개발 환경 설치, `go mod init` 로 모듈 생성
- [ ] 현재 JS 도구가 만드는 산출물을 **골든 파일**로 고정해 둔다 (기존 리포트 몇 개를
      입력·출력 쌍으로 저장). 차등 테스트의 기준선이 된다
- [ ] 차등 비교 스크립트 한 개 작성 — 모듈 이름을 받아 JS/Go 양쪽을 돌리고 `diff` 하는 형태

**디렉터리 배치 제안**

```text
performance/
  tools/            ← JS 원본. 이식이 끝날 때까지 그대로 둔다
  gotools/          ← 새로 만든다
    go.mod
    cmd/perfctl/main.go
    internal/saturation/
    internal/trends/
    ...
```

`gotools/` 라는 이름을 쓰는 이유는 **JS와 공존한다는 사실이 이름에서 드러나야** 하기
때문이다. 나중에 오픈소스로 분리할 때 별도 저장소로 옮긴다.

## 3-4. 1단계 — Go 기본 문법 + 시스템의 판정 기준

**조건: 의존 0개, 파일 I/O 0개, 순수 함수.** Go를 처음 쓰기에 가장 안전한 구간이다.

| 순서 | 파일 | 줄 수 | 테스트 | 배우는 Go | 배우는 도메인 |
|---|---|---|---|---|---|
| 1 | `lib/saturation.js` | 180 | 115줄 ✅ | struct, map, 상수, switch | **포화 판정** |
| 2 | `lib/format.js` | 92 | — | `fmt`, 문자열 | 출력 형식 |
| 3 | `lib/trends.js` | 400 | 214줄 ✅ | slice, 정렬, float64 | **통계** — median·MDE·추세 |
| 4 | `lib/conditions.js` | 241 | — | 비교·구조체 | 실행 조건 비교 |

### 왜 `saturation.js` 가 첫 파일인가

세 가지 이유가 겹친다.

1. **완전한 순수 함수다.** `require` 가 하나도 없고 파일도 건드리지 않는다. 입력(지표
   객체)을 받아 판정을 돌려줄 뿐이다. Go 문법에만 집중할 수 있다.
2. **테스트가 있다.** `saturation.test.js` 115줄이 명세 역할을 한다.
3. **시스템에서 가장 비싸게 배운 교훈이 여기 압축돼 있다.** 모듈 주석이 *"닷새를 날린
   오류가 여기서 나왔다"* 로 시작한다 — `normal-day` 의 p95 10,000~17,000ms 를
   애플리케이션 지연으로 읽고 호스트·커널·전원 관리를 뒤졌는데, 실제로는 커넥션 풀
   **큐 대기**였고 포화 이하(도착률 4/s)에서 재니 **278ms** 였다. 38배 차이다. 상세는
   [perf-session-drift.md](../investigations/perf-session-drift.md).

**첫 파일로 이보다 나은 것이 없다.** 문법 학습 난이도는 가장 낮은데 도메인 밀도는 가장 높다.

## 3-5. 2단계 — 구조체·에러 처리·파일 I/O

| 순서 | 파일 | 줄 수 | 테스트 | 배우는 Go |
|---|---|---|---|---|
| 5 | `lib/comparability.js` | 166 | 206줄 ✅ | `crypto/sha256`, 인터페이스 |
| 6 | `lib/repository.js` | 500 | 297줄 ✅ | `os`, `encoding/json`, **error 반환 관례** |
| 7 | `lib/regression.js` | 552 | 625줄 ✅ | 복합 판정 로직 (파일 로드는 1곳뿐) |
| 8 | `lib/promql.js` | 177 | — | `net/http` 클라이언트 |

Go의 `if err != nil` 관례를 여기서 처음 만난다. JS의 예외와 사고방식이 다르므로 시간을
들일 구간이다.

- `repository.js` 는 `fs` 호출이 14곳으로 이 계층에서 가장 I/O가 많다. Go의 파일 처리와
  에러 전파를 익히기에 적당하다.
- `regression.js` 는 이름과 달리 대부분 순수 판정 로직이고, 파일을 읽는 곳은
  `regression.js:113` 한 군데(기준선 JSON 로드)뿐이다. **테스트가 구현보다 길므로**
  명세를 따라가기 좋다.

## 3-6. 3단계 — 동시성 (명분 C를 코드로 증명하는 곳)

| 순서 | 파일 | 줄 수 | 배우는 Go |
|---|---|---|---|
| 9 | `lib/hostprobe.js` + `hostprobe-worker.js` | 430 | 고루틴, 채널, `context` 취소 |
| 10 | `lib/loadbench.js` + `loadbench-worker.js` | 214 | `time.After`, `exec.Command` |

워커 파일 2개가 사라지고 전체 줄 수가 크게 준다. **이 커밋 하나가 명분 C의 증거물이다** —
"구조가 단순해진다"는 주장이 아니라 diff로 남는다.

**주의:** `hostprobe-worker.js:20` 에 typeperf 타임스탬프가 로캘 형식이라 ISO 8601을 직접
붙인다는 기록이 있다. 이 처리를 빠뜨리면 조용히 깨진다.

## 3-7. 4단계 — 오케스트레이터와 배포

| 순서 | 파일 | 줄 수 | 배우는 Go |
|---|---|---|---|
| 11 | `lib/run-lock.js` | 77 | 프로세스 잠금, `syscall` |
| 12 | `perf-run.js` | 682 | CLI 플래그, 시그널 처리, 프로세스 수명 |
| 13 | `collect.js` | 551 | 수집 파이프라인 |
| 14 | `history.js` | 525 | 시계열 조회 |
| 15 | `lib/report.js` | 817 | `html/template` |
| 16 | `lib/detail-report.js` | 289 | 위에 의존 |

`report.js` 를 마지막에 두는 이유는 **HTML 생성이 Go에서 가장 불편한 작업**이기 때문이다.
JS는 문자열 조립이 자연스럽지만 Go는 `html/template` 를 써야 한다. 문법이 손에 익은 뒤에
하는 편이 낫다.

여기까지 오면 `go build` 한 번으로 단일 바이너리가 나오고 **명분 B가 달성된다.**

## 3-8. 옮기지 않는 것

| 대상 | 줄 수 | 이유 |
|---|---|---|
| `scripts/`, `scenarios/` | 3,900 | **k6가 JS만 받는다.** 선택지 없음 |
| `datasets/seed.js` 외 | 1,381 | 이 프로젝트 전용 데이터 생성. 배포물이 아님 |

**시나리오가 JS로 남는 것은 약점이 아니라 설계다.** 오픈소스 CLI에서 사용자가 자기
시나리오를 써 넣는 확장 지점이 된다. *"Go 바이너리가 JS 시나리오를 받아 k6에 넘긴다"* —
k6 기반 CI 도구들의 일반적인 형태다.

# 4부 — 안전장치

## 4-1. 반드시 지킬 것

1. **JS 원본을 지우지 않는다.** 최소한 4단계가 끝날 때까지 양쪽이 공존해야 차등 테스트가
   성립한다.
2. **`cpu-bench.js` 의 벤치 명령을 문자 하나도 바꾸지 않는다.**
   `dd if=/dev/zero bs=1M count=3000 | md5sum` 는 과거 기록 5,013ms와의 유일한 연결고리다.
   Go로 옮기더라도 **명령 문자열을 그대로 복사**한다.
3. **주석을 번역해서 함께 옮긴다.** 이 코드베이스의 진짜 자산은 로직이 아니라 실패
   기록이다 — typeperf 타임스탬프의 로캘 의존성, `&` 를 셸에 맡겼다가 병렬 벤치가
   5,984ms → 541ms 로 "빨라진 것처럼 보인" 사건(`cpu-bench.js:52`). 주석을 버리면 같은
   함정을 다시 밟는다.
4. **모듈 하나 = 커밋 하나.** 커밋 본문에 차등 테스트 결과를 적는다.
5. **도구를 고쳤으면 smoke 로 확인한다.** [README.md](../README.md) 의 smoke 규칙이 그대로 적용된다.
   Go 이식본도 `tools/` 를 고친 것과 같은 취급이다.

## 4-2. 하지 말 것

- **기능을 함께 추가하지 않는다.** 이식과 개선을 한 커밋에 섞으면 차등 테스트가 성립하지
  않는다(출력이 달라지므로). 개선 아이디어는 별도로 적어 두고 이식이 끝난 뒤에 한다.
- **"Go답게" 구조를 바꾸지 않는다.** 1차 이식은 **1:1 번역**이 목표다. 구조 개선은 차등
  테스트가 통과한 뒤 별도 커밋으로.
- **성능을 명분으로 적지 않는다.** 커밋 메시지에도, 문서에도. 1-0 참조.

## 4-3. 중단 기준 — 언제 그만둬도 되는가

**1단계만 하고 멈춰도 손해가 없다.** Go 기초를 익혔고, 시스템의 판정 기준(포화·추세)을
코드 레벨로 이해했고, JS 시스템은 그대로 돈다.

그만둘 신호:

- 성능 개선 작업(로드맵의 "병목 루프 완주")이 이식 때문에 3주 이상 멈춰 있다
- 차등 테스트가 통과하지 않는데 원인을 못 찾는 상태가 며칠 이어진다 — 이때는 **그 모듈을
  이해하지 못한 것**이므로, 억지로 넘기지 말고 JS 원본을 더 읽는다
- 오픈소스화 계획이 취소된다 → 명분 B가 사라지므로 4단계는 무의미해진다. 3단계까지만 하고
  멈추면 된다

# 6부 — ADR 요약 (인용용)

> **결정.** 성능 측정 도구의 오케스트레이터 계층(`performance/tools/`, 12,756줄)을
> Node.js에서 Go로 점진 이식한다. k6 시나리오(3,900줄)는 JS로 유지한다.
>
> **근거.**
> 1. **런타임 정합성** — k6 자체가 Go로 작성돼 있고 xk6 확장은 Go로만 가능하다. 도구
>    체인을 측정 런타임과 같은 언어로 맞추면, 지표 수집을 "실행 후 파싱"에서 "실행 중
>    직접 출력"으로 승격시킬 경로가 열린다.
> 2. **배포** — CLI 오픈소스화가 로드맵의 최종 목표다(G7). 단일 바이너리는 Node 런타임
>    설치 요구와 버전 호환 유지 비용을 없앤다.
> 3. **동시성** — `spawnSync` 가 이벤트 루프를 막는 문제를 우회하려고 워커 프로세스
>    2개(644줄)를 두고 있다. 고루틴이면 필요 없다. Node에서도 비동기 API로 해결 가능하지만
>    Go에는 그 실수를 할 API가 없다.
> 4. **이해 확보** — 이 시스템은 솔로로 축적됐고 코드 레벨 이해가 저자 본인에게도 얕다.
>    이식은 그 이해를 강제로 확보하는 수단이며, 차등 테스트로 이해의 정확성을 검증한다.
>
> **성능은 근거가 아니다.** 측정 작업(k6·docker·typeperf)은 전부 외부 프로세스가 수행하며
> 오케스트레이터는 계산을 하지 않는다. 이식으로 측정이 빨라지거나 정확해지지 않는다.
> 의존성 관리 역시 근거가 아니다 — 현재 npm 의존성이 0개다.
>
> **무결성 보장.** 모든 이식 모듈은 JS 원본과 동일 입력에 대해 바이트 단위로 동일한 출력을
> 내야 한다(CI 강제). 과거 측정 기록과의 비교 가능성이 유지된다.
>
> **되돌릴 수 있음.** JS 원본은 이식 완료 시점까지 삭제하지 않는다. 어느 단계에서
> 중단하더라도 기존 시스템은 그대로 동작한다.
