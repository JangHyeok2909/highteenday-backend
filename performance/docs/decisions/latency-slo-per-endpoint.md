# 지연 목표는 전역 p99 하나가 아니라 엔드포인트 그룹별로 둔다

> 기준 시점: 2026-09-04
> 답하는 질문: **"전체 p99 를 30ms 로 만들 수 있는가? 없다면 목표를 어떻게 다시 세워야
> 하는가?"**
> 성격: **결정 기록(ADR).** 병목 문서가 "무엇이 느린가"를 다루는 것과 달리, 여기는
> "무엇을 목표로 삼기로 했고 왜인가"를 다룬다.
> 근거 데이터: OPT-002 After 세트 5회(`normal-day-2026-09-04T04-44-49` 외 4건)

---

## 1. 무엇을 물었나

OPT-002 로 전체 p95 가 34.3ms, p99 가 80.9ms 가 된 시점에 **"p99 를 30ms 안으로
넣으려면 무엇을 더 해야 하나"** 를 검토했다.

## 2. 결론

**전역 p99 30ms 는 지금 워크로드 구성에서 도달할 수 없고, 도달 가능하게 만드는 방법이
성능 개선이 아니다.** 목표를 **엔드포인트 그룹별 p99** 로 나눈다.

## 3. 근거 — 로그인 하나가 상한을 만든다

전체 p99 가 30ms 라는 말은 **전체 요청의 99% 가 30ms 이내**라는 뜻이다. 지금은 이렇다.

```
측정 구간 전체 요청   34,471건 (After 5회 합계)
30ms 초과            4,053건 = 11.76%
목표                 345건 이하 = 1.00%
```

여기서 `login` 이 결정적이다.

```
login 최솟값   71.4  70.6  74.8  73.2  73.7 ms   (5회차 전부)
login 건수     585건 = 전체의 1.70%
```

**가장 빠른 로그인조차 30ms 의 2.4배**이고, 로그인은 전체의 1.70% 다. 1.70% > 1.00%
이므로 **다른 모든 요청이 0ms 가 되어도 전체 p99 는 로그인 분포 안에 떨어진다.**
즉 전역 p99 의 하한이 약 71ms 다.

원인은 쿼리가 아니다. `configs/AppConfig.java:17` 이 `new BCryptPasswordEncoder()`,
즉 **strength 10** 이다. BCrypt 는 2^10 라운드를 일부러 돌아 무차별 대입을 늦추는
알고리즘이고, 70~90ms 는 설계대로 나온 값이다. 앱이 2코어라 동시 로그인이 겹치면
큐가 생겨 p99 가 910ms 까지 벌어진다.

**strength 를 낮추면 목표에 가까워지지만, 그것은 성능 최적화가 아니라 비밀번호 해싱
강도를 낮추는 보안 결정이다.** 지연 목표를 맞추려고 할 일이 아니다.

## 4. 버린 대안

| 대안 | 버린 이유 |
|---|---|
| BCrypt strength 를 10 → 8 로 | 약 4배 빨라져 20ms 대가 되지만 **해싱 강도를 1/4 로 낮춘다.** 지연 목표와 맞바꿀 성질의 값이 아니다 |
| 전역 p99 목표를 80ms 로 완화 | 숫자는 맞출 수 있지만 **정보가 사라진다.** 게시판 목록(현재 p99 12ms)이 60ms 로 나빠져도 통과한다 |
| 로그인만 통계에서 제외 | 제외 규칙이 하나 생기면 다음 예외도 정당화된다. 그리고 **로그인이 느린 것은 실제 사용자 경험**이라 안 재는 것은 답이 아니다 |
| 로그인 결과 캐싱 / 세션 연장 | 인증 설계 변경이다. 지연 목표 때문에 인증 수명을 늘리는 것은 순서가 거꾸로다 |

## 5. 결정 — 그룹별 목표

| 그룹 | 목표 p99 | 현재 | 무엇을 해야 도달하나 |
|---|---|---|---|
| 읽기 (`post_detail`, `board_list`, `chat_rooms`) | **30ms** | 12~24ms | 유지 |
| 목록 (`comment_list`, `post_list`, `hot_daily`) | **30ms** | 48~97ms | 댓글 목록 페이징 (§6) |
| 쓰기 (`comment_create`, `post_create`, `*_reaction`) | **50ms** | 84~135ms | [BTL-014](../../bottlenecks/BTL-014-write-path-sync-postprocessing.md) |
| 검색 (`post_search`) | **30ms** | 206ms | [BTL-013](../../bottlenecks/BTL-013-post-search-like-fullscan.md) |
| 인증 (`login`) | **150ms** | 910ms | 큐잉 완화 — 해싱 강도는 건드리지 않는다 |

**이렇게 나누면 각 목표가 "무엇을 고쳐야 도달하는지"와 직접 연결된다.** 전역 하나짜리
목표에서는 로그인 때문에 전체가 실패로 찍히고, 그 신호가 "어디를 고쳐라"를 가리키지
않았다.

쓰기 목표만 50ms 로 다른 이유는 **커밋 fsync 가 하한을 만들기 때문**이다
(`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`). 내구성을 유지하는 한 이 비용은
없앨 수 없고, 없애는 선택은 성능이 아니라 데이터 보존에 관한 결정이다.

## 6. 부수적으로 확인된 것 — 남은 30ms 초과 요청의 구성

전역 목표를 포기한다고 해서 느린 요청이 사라지는 것은 아니므로, 무엇이 남아 있는지
같이 기록한다.

| 요청 | 건수 | 30ms 초과 | 자기 비율 | 지분 | 진단 |
|---|---:|---:|---:|---:|---|
| `comment_list` | 5,367 | 1,692 | 31.5% | **41.8%** | 쿼리는 상수 4개지만 **응답 크기가 댓글 수에 비례**. 4,046건 글의 응답이 1.6MB, 비-DB 시간이 70% |
| `login` | 585 | 585 | 100% | 14.4% | BCrypt — §3 |
| `post_search` | 364 | 364 | 100% | 9.0% | BTL-013 |
| `comment_create` | 353 | 308 | 87% | 7.6% | BTL-014 |
| `post_list` | 2,887 | 232 | 8.0% | 5.7% | 미진단 |
| `post_reaction` | 480 | 209 | 43.5% | 5.2% | BTL-014 |
| `hot_daily` | 2,887 | 122 | 4.2% | 3.0% | 요청당 쿼리 14개 |
| `post_create` | 433 | 109 | 25.2% | 2.7% | BTL-014 |
| `post_detail` | 9,831 | 97 | 1.0% | 2.4% | 미진단 |

> **초과 건수는 추정이다.** k6 원자료의 개별 요청 시간을 세지 않고, 회차별 분위수
> (최소·중앙·p90·p95·p99·최대) 사이를 선형보간해 계산했다. 순위와 규모는 신뢰할 수
> 있지만 건수 자체를 인용할 때는 이 한계를 함께 적어야 한다. `login`·`post_search` 의
> 100% 만은 최솟값이 30ms 를 넘으므로 추정이 아니라 확정이다.

**가장 큰 단일 항목은 여전히 `comment_list`(41.8%)이고, 성격이 바뀌었다.** OPT-001·
OPT-002 가 쿼리 수를 1,507 → 3.9 로 만들어 DB 문제는 끝났는데, 이제 **댓글 4,046개를
DTO 로 만들고 익명화 루프를 돌고 JSON 으로 직렬화하는 앱 비용**이 남았다. 중앙값은
7.1ms 로 이미 빠르고 꼬리만 느리다 — 전형적인 페이징 부재 형태다.

다만 **댓글 목록 페이징은 쿼리 튜닝이 아니라 도메인 설계 변경**이다.
`CommentAnonymizationService.java:26` 이 매기는 "익명N" 의 N 은 **게시글 전체 댓글의
등장 순서**라, 페이지로 자르면 2페이지의 "익명3" 이 1페이지의 "익명3" 과 다른 사람이
된다. 같은 이유로 지금 단건 조회도 댓글 전체를 읽고 있다. 익명 번호를 페이지와 무관하게
결정하는 방법을 먼저 정해야 페이징을 할 수 있다.
