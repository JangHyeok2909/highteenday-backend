# EXP-001: 기준선 측정 — Normal Day 200 VU

> 상태: **완료** (2026-08-16) — H1 기각, 병목은 앱 CPU 2코어 한계
> 날짜: 2026-08-16 | 관련: 없음 (모든 실험의 전제)

## 1. 목적

평상시 트래픽(200 VU, 읽기 중심)에서 현재 시스템의 성능 기준선을 확보한다.
이후 모든 최적화의 Before 값이다.

**단일 실행이 아니라 5회 반복 세트로 잡는다.** 이유는 아래 "왜 반복인가"에 적었다.

## 2. 가설

> **H1**: 200 VU Normal Day 부하에서 읽기 P95 < 300ms, 쓰기 P95 < 500ms,
> 오류율 < 1%를 충족할 것이다. 근거: Tomcat 400 스레드 대비 낮은 동시성,
> 게시글 목록/HOT은 Redis 캐시 경로.

- 반증 조건: 어느 하나라도 SLO 초과 시 기각 — 초과 지표가 곧 첫 병목 후보.

**사전 관측 하나가 이미 H1을 의심하게 한다.** 본 실행 전 짧은 확인(워밍업 20초·측정 40초)
에서 앱 컨테이너 CPU가 **한계인 2.000 코어에 정확히 붙었다.** 같은 구간 부하 발생기는
0.108 코어(상한 4)에 throttled 0.201%라 발생기 쪽 한계는 아니다. 즉 서버가 CPU 상한에
먼저 닿는 그림이며, 그 상태에서 SLO를 지킬 수 있는지가 이 실험의 실제 관전 포인트다.

## 3. 배경

CLAUDE.md의 Performance Guidelines(캐시, 커서 페이징, 카운터 버퍼링)가 실제로 SLO를
지키는지 수치로 확인한 적이 없다.

### 왜 반복인가 — 이 실험이 늦어진 진짜 이유

기준선은 원래 첫 실험이었는데 지금까지 못 잡았다. **잡을 수 없었기 때문이다.**

```text
쓰기 저니가 데이터를 남김
  → 다음 실행의 시작 상태가 다름
  → 같은 조건이라 기록되지만 실제로는 다른 실험
  → 반복해서 얻은 편차가 "환경 노이즈"가 아니라 "데이터 증가분"을 잼
```

2026-08-16에 데이터셋 상태 고정(P0-3)이 끝나면서 이 전제가 성립했다. 이제 `strict` guard가
매 회차를 같은 상태 지문에서 출발시킨다. **그래서 이번에 얻는 변동계수(CV)가 비로소
"측정의 흔들림"만 뜻한다.**

CV 값 자체에 합격선은 없다. **알기만 하면 된다** — 이후 "p95가 X% 좋아졌다"는 주장이
노이즈보다 큰지 판단하는 데 쓰인다.

### 이 기준선이 재는 것과 못 재는 것 — 버퍼풀 경계

medium 의 MySQL 볼륨은 **513MB**이고 버퍼풀은 **1GB**다. **데이터가 통째로 메모리에
올라간다.** 그래서 이 기준선은 **디스크 읽기를 거의 재지 않는다.**

9절 병목 분석의 결과가 그 그림과 맞는다 — CPU 포화 100.1%에 Redis 적중률 98.5%로, 병목이
전적으로 CPU다.

| 이 기준선으로 판정 가능 | 판정 불가 |
|---|---|
| CPU 효율 개선 (N+1 제거, 직렬화, 불필요 연산) | **인덱스·쿼리 계획** — 전부 메모리라 차이가 안 난다 |
| 애플리케이션 로직 최적화 | **페이징 깊이·커서 전환** — 깊은 페이지가 없다 |
| | 캐시 전략 — 이미 98.5%라 개선 여지가 안 보인다 |

**인덱스나 페이징을 개선하려면 large 기준선이 따로 필요하다**(볼륨 2,703MB로 버퍼풀의
2.7배). `conditions.js`가 데이터셋을 blocking 으로 보므로 두 기준선은 서로를 대체하지
않는다. 상세: `datasets/README.md` 의 "프로파일이 갈리는 진짜 기준".

**large 가 "더 정확한" 것이 아니다.** 디스크 I/O 라는 변동 요인이 붙어 CV 가 커지고 MDE 도
커질 가능성이 높다 — 더 현실적이지만 더 둔감하다.


### 부하 발생기를 컨테이너로 돌리는 이유

`local`(Windows 네이티브 `k6.exe`)로 돌리면 **부하 발생기를 아무도 측정하지 못한다.**
cAdvisor는 컨테이너만 보고, node-exporter가 보는 "호스트"는 WSL2 VM이라 그 밖의 프로세스가
잡히지 않는다. 그러면 "지연이 서버 탓인가 발생기가 못 따라간 탓인가"를 사후에 가를 수 없다.

두 모드는 서버로 가는 경로가 다르므로(`localhost:18080` 포트 포워딩 vs `app:8080` 컨테이너
네트워크) **비교 조건이 다르다**(`conditions.js` v4, blocking). 이 기준선은 `docker`로
잡았으므로 앞으로의 비교도 `docker`로 해야 한다.

## 5. 실행 방법

```bash
# 선행: medium 프로파일로 전환하고 앱을 재시작해 Flyway가 그 볼륨에 적용되게 한다
DATASET_PROFILE=medium docker compose -f environment/docker-compose.perf.yml \
  --env-file environment/.env.perf up -d
docker restart perf-app

# 상태가 스냅샷과 같은지 확인
node tools/snapshot.js verify medium

# 본 실행 — 5회 반복. 회차마다 앱 재시작 + FLUSHALL + 스냅샷 복원이 자동으로 들어간다
node tools/repeatability.js scenarios/normal-day.js \
  --dataset medium --loadgen docker --runs 5 --note "EXP-001 기준선 세트"
```

`repeatability.js`가 회차마다 `perf-run.js`를 부르고, `perf-run.js`가 k6 실행 → 인프라 지표
수집 → 회귀 판정 → 리포트 생성까지 처리한다. 별도 워밍업 스크립트나 수동 baseline 저장은
필요 없다.

> **실행 중에는 `scenarios/`·`scripts/`·`tools/`·`regression/rules.json`을 수정하면 안 된다.**
> 회차마다 새로 읽히므로 중간에 바꾸면 회차 간 조건이 달라져 세트 전체가 무효가 된다.
>
> 기준선 저장도 사람이 하지 않는다. 예전 문서에 있던
> `tools/compare.js --save-baseline`과 `regression/baseline.json`은 **더 이상 존재하지
> 않는다.** 지금은 `repository.js`의 `findBaseline()`이 "조건이 같고 정상 측정된 가장 최근
> 실행"을 자동으로 고른다.

## 6. 측정 지표

| 역할 | 지표 | 판정 기준 |
|------|------|-----------|
| 1차 | `http_req_duration{op:read,phase:measure}` P95 | < 300ms |
| 1차 | `http_req_duration{op:write,phase:measure}` P95 | < 500ms |
| 1차 | `http_req_failed` rate | < 1% |
| **재현성** | **P95의 변동계수(CV)** | 합격선 없음 — **값을 기록하는 것이 목적** |
| 측정 유효성 | `loadgen.throttledPct` | > 1%면 발생기 오염 의심 |
| 측정 유효성 | `measurementStatus` | 5회 모두 `MEASURED`여야 표본으로 인정 |
| 측정 유효성 | `stateMatchedSnapshot` | 회차마다 `true` (다르면 그 회차 제외) |
| 보조 | RPS/TPS, CPU(app·mysql·host), heap, hikari, redis hit | 기준선 기록용 |

**판정은 `measure` 구간만 본다.** 워밍업 300초와 램프다운 120초는 진단 정보로 남기되
게이트에 넣지 않는다.

### timeout 검열 — 이번 결과 해석의 주의점

k6 클라이언트 타임아웃이 **60초**다. 사전 확인에서 이미 `max=56.37s`가 관측됐으므로,
본 실행의 p99가 **상한에 잘린 값일 가능성이 실재한다.** 잘린 값은 "실제 응답 시간"이
아니라 "우리가 기다려 준 시간"이라 개선률 계산에 넣으면 무의미한 숫자가 나온다.

**이 검열 처리는 아직 구현되지 않았다**(P0-6의 남은 절반). 따라서 이번 결과에서 p99가
60,000ms 근처면 그 값은 **그대로 쓰지 말고 검열 대상으로 표시**해야 한다.

### 6.1 사전 판정 기준 — 결과를 보기 전에 확정 (2026-08-16, 측정 중 작성)

숫자를 본 뒤에 기준을 정하면 기준을 숫자에 맞추게 된다. 그래서 결과가 나오기 전에 적는다.

#### (1) 회차를 표본에서 빼는 조건

아래 중 하나라도 해당하면 **그 회차를 뺀다.**

| 조건 | 왜 빼나 |
|---|---|
| `measurementStatus === 'UNMEASURED'` | 필수 지표가 없어 판정이 성립하지 않는다 |
| `windowIncomplete === true` | measure 구간을 다 채우지 못했다 — 시간 조건 자체가 다르다 |
| `stateMatchedSnapshot === false` | 어떤 데이터에서 잰 것인지 확정할 수 없다 |

`PARTIAL`이지만 `windowIncomplete`가 아닌 회차는 **뺀다고 하지 않는다.** 그건 참고 지표
몇 개가 빠진 것이고 p95 자체는 온전하기 때문이다(S-10과 같은 논리 — 느린 것과 못 잰 것은
다르다).

#### (2) 세트 전체를 폐기하는 조건

| 조건 | 조치 |
|---|---|
| 유효 회차가 **4회 미만** | 세트 폐기, 전체 재실행 |
| 어느 회차든 `loadgen.throttledPct > 1%` | 세트 폐기 — 발생기가 한계에 걸렸으면 그 지연은 서버 것이 아니다 |

**모자란 회차만 이어서 채우지 않는다.** 시간이 벌어지면 그사이 호스트 상태(다른 프로그램,
디스크 캐시)가 달라져 세트 안의 편차가 측정 노이즈가 아니라 세션 간 차이를 재게 된다.

#### (3) 검열 규칙

k6 타임아웃 60초에 닿은 값은 실제 응답 시간이 아니다. **어떤 회차든 해당 지표가
57,000ms(상한의 95%) 이상이면 그 지표를 `CENSORED`로 표시하고 CV 계산과 이후 개선률
비교에서 제외한다.**

60초에 정확히 닿은 경우만 잡으면 59.8초 같은 값이 빠져나가므로 여유를 둔다. 검열된 지표는
p95·p99 대신 **오류율·check 성공률·완료 iteration 수**로 판정한다.

#### (4) 대표값

**중앙값을 쓴다.** 5회 중 하나가 튀었을 때 평균은 끌려가지만 중앙값은 버틴다. 산포는
CV(변동계수)로 표기한다.

#### (5) CV를 개선 판정에 쓰는 방법 — MDE

**MDE(최소 검출 가능 개선폭)** 는 "이보다 작은 변화는 노이즈와 구분되지 않는다"는 값이다.
CV를 `c`라 할 때:

| 비교 방식 | MDE (근사) | 근거 |
|---|---|---|
| 단일 실행 vs 단일 실행 (**현행 도구**) | **≈ 3 × c** | 두 값의 차이가 갖는 상대 표준오차는 `c·√2`, 그 2배를 유의 기준으로 |
| 5회 세트 vs 5회 세트 | **≈ 1.3 × c** | 평균의 표준오차가 `c/√5`로 줄어 차이의 상대 표준오차가 `c·√(2/5)` |

예를 들어 CV가 10%로 나오면 지금 도구로는 **30% 이상 좋아져야** 개선이라고 말할 수 있고,
세트 비교로 바꾸면 **13%**로 내려간다. 이 차이가 "비교 단위를 run 세트로 전환"(P0-6의 남은
항목)을 해야 하는 정량적 근거다.

**전제와 한계를 같이 적는다.** 이 계산은 회차가 서로 독립이고 분포가 대략 정규라고 가정한다.
상태 고정 덕분에 독립은 대체로 성립하지만, **CV 자체가 표본 5개에서 추정한 값이라 불확실
하다** — 표본이 이 정도면 CV 추정치의 오차가 수십 %에 이른다. 그래서 MDE는 **올림해서
보수적으로** 쓴다(예: 계산값 26% → 30%로 잡는다).

#### (6) H1 판정

- **중앙값 기준으로 판정한다.** 읽기 P95 중앙값 < 300ms, 쓰기 P95 중앙값 < 500ms,
  오류율 중앙값 < 1%.
- 회차 간 편차가 SLO 경계를 걸치면(예: 5회 중 2회만 초과) 통과/기각 대신 **"경계"** 로
  기록하고, 그 사실 자체를 결론에 남긴다. 경계값을 통과로 반올림하지 않는다.
- 하나라도 기각되면 그 지표가 **첫 병목 후보**다(2절의 반증 조건).

### 7.4 MDE — 이 기준선으로 무엇을 주장할 수 있나

| 항목 | 값 | 보수적 사용값 |
|---|---:|---:|
| P95 CV | 3.12% | — |
| MDE (단일 실행 비교, ≈ 3 × CV) | 9.4% | **10%** |
| MDE (5회 세트 비교, ≈ 1.3 × CV) | 4.1% | **5%** |

**이보다 작은 변화는 개선이라고 말하지 않는다.** 현행 도구는 단일 실행끼리 비교하므로
지금 기준은 **10%**다. 비교 단위를 세트로 바꾸면 5%까지 내려간다 — 그 전환의 정량적 근거가
이 표다.

> ### ⚠ 이 MDE는 더 이상 쓰지 않는다 (2026-08-21 갱신)
>
> **이 세트는 포화 영역에서 측정됐다.** 200 VU 는 이 환경의 용량(도착률 약 4~5/s)을 크게
> 넘는 값이라, 앱 CPU 가 상한에 붙고 커넥션 대기가 쌓인 상태에서 잰 값이다. 포화 근처에서는
> 이용률이 1 에 가까워질수록 대기가 `1/(1-ρ)` 로 발산하므로, 호스트의 작은 변동이
> 응답시간에서 수십 배로 증폭된다. 회차가 갈수록 느려지던 것(Spearman +0.90)도 그 증폭의
> 결과였다.
>
> 그래서 위 CV·MDE 는 **애플리케이션 지연의 재현성이 아니라 포화 상태의 불안정성**을 잰
> 값이다. 이 세트를 포함한 포화 실행 49건은 `reports/archive/runs/` 로 분리했고 기준선
> 후보에서 빠졌다.
>
> 지금 판정용 운용점은 **open model `RATE=4`** 다(앱 CPU 37~45%, Hikari 대기 0). 그 조건에서
> 다시 잰 값은 세트 안 CV **3.2%**, 코드를 안 바꾸고 4시간 간격으로 잰 두 세트 차이
> **−1.5%** 다. **새 운용점의 기준선은 새로 쌓아야 한다** — 이 문서의 값은 인용하지 않는다.

13절에 적혀 있던 "기준선 대비 ±10%"는 근거 없이 정한 숫자였는데, 실측 MDE가 공교롭게 같은
값으로 나왔다. **이제는 근거가 있다.**

### 무엇이 원인이 아닌지부터 배제된다

이번에 추가한 `host`·`loadgen` 지표(E-09·E-01)가 결론을 확정해 준다.

- **환경이 아니다** — 호스트는 20코어 중 19.7%만 쓰고 run queue도 코어당 0.47이다.
- **측정 도구가 아니다** — 부하 발생기는 0.07코어(상한 4), throttled 0.026%다.
- **캐시가 아니다** — Redis 적중률 98.5%다.

남는 것은 **앱 컨테이너에 걸린 CPU 2코어 한계** 하나다. `cpu.throttledPct 99.79%`는 cgroup이
거의 항상 CPU를 뺏고 있다는 뜻이고, 그 결과 요청이 큐에 쌓여 Hikari 대기 192개로 이어진다.

**Hikari 포화는 원인이 아니라 결과일 가능성이 높다.** 풀 크기(10)가 작아 보이지만, CPU가
100% throttled인 상태에서는 커넥션을 늘려도 처리할 CPU가 없다. 풀을 먼저 키우는 것은
순서가 틀렸다 — CPU 한계를 올린 뒤 다시 봐야 한다.

- 부하 발생기 모드 (`docker`) — `local`로 잰 값과는 비교되지 않는다
- 부하 스크립트 지문 (`scenarios/lib/workload.js` · `scripts/lib/data.js` · `sampling.js`)
- 측정 구간 설계 (warmup 300 / measure 1200 / rampdown 120)

앞의 넷은 `conditions.js`가 자동으로 감지해 비교를 막는다. 마지막 하나는 감지되지 않으므로

## 12. 결론

**H1 기각.** 200 VU Normal Day에서 읽기 P95 12,120ms(기준 300ms의 40배), 쓰기 P95
12,021ms(기준 500ms의 24배)다. 오류율만 0%로 통과했다.

세 가지를 얻었다.

1. **기준선이 생겼다.** medium `sha256:aae4bccfae5e`, 상태 `sha256:ffe696d17416`,
   `--loadgen docker`, 5회 세트. 이 조건이 같은 실행끼리는 이제 비교가 성립한다.
2. **MDE가 정해졌다.** P95 CV 3.12% → 단일 실행 비교에서 **10%**, 세트 비교에서 **5%**.
   앞으로 이보다 작은 변화는 개선이라 부르지 않는다.
3. **첫 병목이 지목됐다.** 앱 컨테이너 CPU 2코어 한계. 호스트·부하 발생기·캐시는 전부
   배제됐다.

**이 결과의 성격을 오해하면 안 된다.** "서비스가 12초 걸린다"가 아니라 **"2코어로 제한한
컨테이너에 200 VU를 걸면 12초 걸린다"** 이다. 운영 용량에 대한 주장이 아니다 — 로컬 상대
비교의 출발점일 뿐이고, 로컬에서 운영 용량을 말할 수 없다는 것은
`perf-trust-levels.md`가 이미 정리해 둔 한계다.

## 13. 향후 개선

- **다음 실험은 CPU 한계를 올리고 재측정하는 것이다.** 다만 자원 한계 변경은 SUT를 바꾸는
  것이라 **이 기준선과 비교되지 않는다** — 새 기준선을 다시 잡아야 한다(11절 참고).
  `conditions.js`가 자원 한계 변경은 감지하지 못하므로 사람이 챙겨야 한다.
- Hikari 풀 크기는 CPU 한계를 올린 뒤에 다시 본다. 지금 키우면 원인이 아닌 것을 고치게 된다.
- **비교 단위를 run 세트로 전환**하면 MDE가 10%에서 5%로 내려간다(7.4절). 그만큼 작은
  개선까지 검출할 수 있다.
- ~~timeout 검열(CENSORED) 구현 후 재해석~~ → 이번 결과는 최대 p99 17.7초로 상한(60초)과
