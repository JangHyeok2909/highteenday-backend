# EXP-005: 댓글 조회 쿼리 폭발 (N+1) 검증

> 상태: **완료** (2026-09-04) — H1 채택 · H2/H3 기각
> 날짜: 2026-08-26 ~ 2026-09-04 | 관련: BTL-005(해소) · OPT-001 · OPT-002

## 1. 목적

댓글 목록 API가 댓글 수에 비례해 쿼리를 발행하는지(N+1) 확인하고,
있다면 JOIN FETCH/배치 로딩으로 개선해 효과를 수치화한다.

## 2. 가설

리포트에서 관측된 것은 셋이다 — ① slow query 로그에 쌓인 쿼리가 많다, ② 초당 읽은 행 수가
크다, ③ MySQL 의 CPU·메모리는 여유인데 커넥션 풀만 포화다. 아래 **H1~H3 은 ①②를 설명하는
경쟁 가설**이고, **H4 는 그것들이 어떻게 ③으로 이어지는지에 대한 가설**이다.

따라서 이 실험의 일은 "N+1 이 있는지 보는 것"에서 **"셋 중 무엇이 지배적인지 가르는 것"**
으로 넓어진다. 채택된 하나만 `optimizations/OPT-XXX` 로 승격한다 — 한 번에 하나만 고친다.


> **`normal-day-2026-08-26T00-06-28` 리포트 기준의 1차 판단과 반증 요약**
> (판단 과정 전문은 [perf-comment-nplus1-diagnosis.md](../../docs/investigations/perf-comment-nplus1-diagnosis.md))
>
> **H1 (N+1)** — 1차 판단의 근거: `comment_list` 가 가장 느렸고(read p99 2.22s), 요청당 쿼리가
> 319개였으며 slow query 도 759건으로 많았다. **반증에서 살아남은 부분과 아닌 부분:**
> `comment_list` 가 문제라는 판단은 유효했지만, slow query 는 N+1 과 무관하다. N+1 은 지연 로딩이
> 연관 객체를 건마다 다시 조회하는 문제이고 개별 쿼리는 빠르다. slow query 는 인덱스를 못 타는
> 쿼리에서 나오며 대부분 `post_search` 의 `LIKE` 검색이었다. 결정적 단서는 **요청당 쿼리 수**였다 —
> 엔드포인트별 쿼리 수와 SQL 단위 실행 횟수 계측(`metrics/`)을 이 실험을 위해 추가해, 어느
> 엔티티에서 N+1 이 나는지까지 특정할 수 있게 됐다.
>
> **H2 (인덱스 미사용 풀스캔)** — 1차 판단의 근거: 초당 읽은 행 4,910/s, 풀테이블 스캔 997건.
> **반증:** 쿼리당 읽은 행 수(초당 읽은 행 ÷ 초당 쿼리)가 약 1행이었다. 풀스캔이 지연의 원인이라면
> 이 값이 훨씬 커야 한다. 풀스캔이 나는 곳은 `post_search` 의 `LIKE` 검색이고 비중이 낮다.
>
> **H3 (트랜잭션 길이)** — 1차 판단의 근거: MySQL 의 CPU·메모리는 여유인데 커넥션 풀만 포화였으므로,
> H1·H2 로 응답이 길어져 커넥션을 오래 쥔 결과일 것이라고 봤다. **반증:** 2026-08-29 실행(EXP-006)에서
> 풀을 2배로 늘려도 응답 시간과 MySQL CPU 가 변하지 않았고, 다른 실행에서도 풀 포화는 간헐적이었다
> (`RATE=4` 로 의도적으로 낮춘 부하). 커넥션 고갈이 원인이라면 커넥션 획득 p95 가 응답 시간을
> 밀어 올려야 하는데, 그 값은 포화되지 않았을 때와 거의 같았다. 최대 사용 수만 찍힌 순간적
> 스파이크였다.

| 캐시 상태 | warm |

## 5. 시나리오 / 실행 방법

```bash
# 1단계 (기능 검증): 단일 요청의 쿼리 수 세기 — 부하 없이
#   댓글 5개 글 vs 100개 글 각각 curl 1회 → p6spy 로그의 쿼리 수 비교
docker logs perf-app --tail 0 -f | grep -c "select" &   # 또는 spy.log 확인
curl -s "localhost:18080/api/posts/<댓글5개글>/comments" > /dev/null
curl -s "localhost:18080/api/posts/<댓글100개글>/comments" > /dev/null

# 2단계 (부하 검증): 댓글 열람 편중 부하에서 지연 분포
node tools/perf-run.js scripts/comments.js --dataset medium -e VUS=50 -e DURATION=5m --loadgen docker
```

## 6. 측정 지표

| 지표 | 어디서 | 무엇을 가른다 |
|---|---|---|
| 엔드포인트별 요청당 쿼리 수 | `http.server.queries` (`metrics/QueryCountFilter`) | H1 의 직접 증거. 어느 API 가 쿼리를 쓰는지 |
| SQL 별 실행 횟수 | `QueryCountRecorder` detail 모드 `topSql` | **어느 엔티티**의 N+1 인지 |
| 쿼리당 읽은 행 수 | `mysql.rowsReadPerSec ÷ mysql.qps` | H2 판별 — 풀스캔이면 1행보다 훨씬 커야 한다 |
| 커넥션 획득 p95 | HikariCP | H3 판별 — 풀 대기가 응답을 늘렸다면 커야 한다 |
| slow query 건수 | `mysql.slowQueries` | H1 과 slow query 가 같은 것인지 |

> 이 실험을 하려고 **계측을 먼저 만들었다.** 시작 시점에는 요청당 쿼리 수를 엔드포인트별로
> 볼 방법이 없어서 p6spy 로그를 세는 수밖에 없었다. `metrics/` 패키지(p6spy 리스너 →
> ThreadLocal 누적기 → 서블릿 필터 → Micrometer)가 그 결과물이다.

## 7. 결과 — 가설 판정

**H1 (N+1) 채택. H2 (인덱스 미사용 풀스캔) · H3 (트랜잭션 길이) 기각.**

### H1 채택 근거 — 실측

`GET /api/posts/{postId}/comments` 의 요청당 쿼리 수를 재고, 부하 없는 단발 요청으로
모델과 대조했다.

| 게시글 | 댓글 N | 작성자 U | 실측 쿼리 | 모델 `3 + U + 2N` |
|---:|---:|---:|---:|---:|
| 247 | 6 | 5 | 20 | 20 ✅ |
| 2 | 492 | 130 | 1,117 | 1,117 ✅ |
| 8 | 4,047 | 450 | 8,547 | 8,547 ✅ |

**오차 0 이다.** N+1 이 있다는 정성적 확인이 아니라 **쿼리 수를 식으로 예측할 수 있다**는
뜻이고, 그래서 무엇을 없애면 몇 개가 줄어드는지 착수 전에 계산할 수 있었다.

두 갈래를 각각 없앴다.

| 항 | 정체 | 없앤 방법 | 결과 |
|---|---|---|---|
| `2N` | 댓글마다 좋아요·싫어요를 각각 확인 | 댓글 id 일괄 조회 1회 ([OPT-001](../../optimizations/OPT-001-comment-reaction-batch.md)) | 1,507 → 112 |
| `U` | 작성자 LAZY 프록시 초기화 | `join fetch c.user` ([OPT-002](../../optimizations/OPT-002-comment-author-fetch-join.md)) | 112 → **3.9** |

종단 p95 는 **226.7ms → 57.2ms → 34.3ms** 로 두 단계에 걸쳐 −84.9% 줄었다.

### H2 기각 근거 — 실측으로 재확인

기각 사유였던 "쿼리당 읽은 행 수가 약 1행"은 개선 후에도 유지된다. 그리고 결정적으로,
**N+1 을 완전히 걷어냈는데 slow query 건수가 변하지 않았다.**

```
slow query   OPT-001 전후  659 → 653건 (−0.9%)
             OPT-002 전후  653 → 660건 (+1.1%)
```

두 번의 독립적인 확인이다. **slow query 는 N+1 과 무관하다** — 대부분 `post_search` 의
`LIKE` 검색이고, 그것은 이 실험의 대상이 아니라 별개 병목이다.

### H3 기각 근거 — 실측으로 재확인

커넥션 획득 p95 가 OPT-001 전후로 0.95ms → 0.95ms 로 **전혀 움직이지 않았다.** 응답이
−74.8% 빨라졌는데 커넥션 획득 대기가 그대로라는 것은, 애초에 그것이 응답 시간의 구성
요소가 아니었다는 뜻이다.

원인은 "쿼리가 느린 것"이 아니라 **싼 쿼리를 너무 많이 왕복하는 것**이었다. 반응 확인

## 12. 결론

**N+1 은 실재했고, 두 갈래였으며, 둘 다 없앴다.** 요청당 쿼리 수가 댓글 수·작성자 수에
비례하던 것에서 **상수 4개**가 됐다.

이 실험에서 가장 값어치 있었던 것은 답이 아니라 **가르는 방법**이다. 세 가설 모두
"리포트에서 보이는 것"으로는 그럴듯했다.

- H2 를 가른 것은 **쿼리당 읽은 행 수**였다. 풀스캔이면 이 값이 커야 하는데 약 1행이었다.
- H3 을 가른 것은 **커넥션 획득 p95** 였다. 풀 대기가 원인이면 이 값이 응답과 함께 움직여야
  하는데 전혀 움직이지 않았다.
- H1 을 확정한 것은 **엔드포인트별 요청당 쿼리 수**였고, 그 지표는 이 실험을 위해 새로
  만들었다.

**세 가설 모두 "무엇이 참이면 이 값이 이렇게 나와야 한다"를 먼저 적었기 때문에 가를 수
있었다.** 지표를 나중에 보고 해석했다면 셋 다 맞는 이야기로 보였을 것이다.

## 13. 향후 개선

- `post_search` 의 `LIKE` 전체 스캔 — 이 실험이 H2 를 기각하며 "slow query 의 진짜 주인"으로
  지목한 대상이다. 별도 병목으로 분리했다
- 댓글 목록의 페이징 — 쿼리 수는 상수가 됐지만 **응답 크기는 여전히 댓글 수에 비례**한다.
  댓글 4,046건짜리 게시글의 응답은 1.6MB 이고, 비-DB 시간이 응답의 70% 다
