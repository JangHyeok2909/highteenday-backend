## 0. 한 줄 결론

**요청 하나의 비용이 542배까지 벌어지는데 대상을 매번 무작위로 뽑는다.** 그래서
① 무거운 요청이 우연히 겹치면 커넥션 풀이 15초간 고갈되고(스파이크),
② 겹치지 않아도 회차마다 총 작업량이 CV 4.8% 로 달라진다(표본 추출 분산).

**둘 다 앱 성능이 변해서가 아니다. 매번 다른 질문을 던지기 때문이다.**

## 1. 현상 — 반복 세트에서 한 회차만 2배 느리다

`normal-day` · RATE=4 · medium 을 5회 반복한 결과다(2026-08-26).

| 회차 | p95 | p99 | **Hikari 대기** | Hikari% | CPU% | 포화 판정 |
|---|---:|---:|---:|---:|---:|---|
| 1 | 388ms | 2,151ms | **0** | 40% | 52% | HEADROOM |
| **2** | **921ms** | 2,268ms | **20** | **100%** | 62% | **NEAR_LIMIT** |
| 3 | 345ms | 1,676ms | **0** | 60% | 42% | HEADROOM |
| 4 | 335ms | 1,844ms | **0** | 40% | 42% | HEADROOM |
| 5 | 306ms | 1,775ms | **0** | 30% | 53% | HEADROOM |

**대기가 생긴 회차만 느리다. 예외가 없다.**

세트 CV 로 보면 이상치 하나가 결과를 지배한다.

```
5회 전부      p95 CV 56.68%  ·  p99 CV 13.09%
이상 회차 제외  p95 CV  9.9%  ·  p99 CV 10.9%
```

**MDE 로 환산하면 5배 차이다.** 회차 하나를 어떻게 다루느냐가 판정 해상도를 좌우한다.

### 1.1 처음에는 "1회차 효과"로 오인했다

전날 중단된 세트에서는 같은 사건이 **1회차**에 일어났다. 그래서 "첫 회차는 항상 느리다"는
가설이 먼저 섰고, 저장된 반복 세트 10건을 전수 조사했다.

| 체제 | 1회차가 느린 경우 | 평균 차이 |
|---|---|---|
| 포화 세트 (5건) | 1/5 | **−3.0%** (오히려 빠름) |
| 비포화 세트 (5건) | 4/5 | +175.0% |

**포화 상태에서는 1회차 효과가 없다.** p95 가 큐 대기라 초기 과도 상태가 묻히기 때문이다.
E-46 이 밝힌 대로 포화는 증폭기이자 **은폐기**다.

그리고 5회 세트에서 이상치가 2회차로 나오면서 **순서 가설은 기각됐다.**

## 2. 사건의 해부 — 15초짜리 단일 사건

스파이크 회차(`normal-day-2026-08-26T00-06-28`)를 초 단위로 본다. measure 구간은
23:59:22 ~ 00:04:22 UTC 다.

### 2.1 대기는 딱 한 번, 15초 동안만 생겼다

```
23:59:52 ~ 00:00:02   최대 대기 20   (5초 간격 표본 122개 중 3개)
```

**실행 10분 중 15초짜리 단일 사건이다.** 회차 전체가 느린 것이 아니다.

### 2.2 시간축 — 무엇이 먼저였나

```
시각        대기  사용중  CPU   MySQL실행중   QPS   slowQ/s   Tomcat진행중
23:59:45     0     3    0.68      3        5029    2.30         4
23:59:50     0     2    0.99      2        4412    2.70         3
23:59:55     6    10    1.66      8        5590    2.70        20   ← 사건 시작
00:00:00    20    10    2.01      2        5192    2.50        31   ← CPU 상한 도달
00:00:05    16    10    1.99      6        5819    3.20        27
00:00:10     0     7    1.85      4        8622    3.10         8   ← 해소
00:00:15     0     1    1.35      2        8956    2.50         2   ← 밀린 요청 통과
```

**`slowQ/s` 가 전혀 움직이지 않는다**(2.1~3.2 일정). 느린 쿼리가 방아쇠가 아니다.
**GC 도 아니다** — 정지시간 0.00~0.02 초/초, 힙 200~773MB 로 평소와 같다.

### 2.3 부하가 몰린 것이 아니다 — 이것이 방향을 갈랐다

```
시각        k6 RPS    VU
23:59:50     17.5     42
23:59:55     14.5     46
00:00:00     11.0     55   ← RPS 는 떨어지는데 VU 만 증가
00:00:05     15.6     67
00:00:10     23.5     63   ← 밀렸던 것이 한꺼번에 통과
```

**k6 가 보내는 요청은 오히려 줄었다.** open model 이라 도착률은 고정인데 응답이 안 오니
VU 가 39 → 67 로 쌓인다. **원인은 부하 쪽이 아니라 서버 안에 있다.**

### 2.4 HikariCP 내부 — 커넥션 **보유 시간**이 터진다

```
시각        커넥션생성/s  획득/s   획득시간합/s   사용시간합/s   idle
23:59:50       0.00      31.4       0.01        1.43        8
23:59:55       0.00      37.8       0.04        1.14        0   ← idle 0
00:00:00       0.00      20.0      16.81        4.07        0
00:00:05       0.00      27.8      21.01        9.45        0
00:00:10       0.00      53.8       2.16       15.22        3
```

**커넥션 생성은 0이다** — 풀이 새로 만드느라 느린 것이 아니다.
**`사용시간합` 이 1.14 → 15.22 초/초로 13배 뛴다.** 커넥션을 쥐고 있는 시간이 폭증하며
`idle` 이 8 → 0 이 되어 풀이 바닥난다.

### 2.5 피해 패턴 — 원인과 피해자가 분리된다

같은 세트의 정상 회차(`00-44-37`)와 API 별로 비교한다.

| API | 스파이크 p95 | 정상 p95 | 배율 |
|---|---:|---:|---:|
| **`comment_list`** | 1,906ms | 1,830ms | **1.0배** |
| `comment_create` | 64ms | 64ms | 1.0배 |
| `post_create` | 63ms | 58ms | 1.1배 |
| `login` | 633ms | 307ms | 2.1배 |
| `hot_daily` | 109ms | 30ms | 3.7배 |
| **`post_update`** | 674ms | 32ms | **21배** |
| **`post_delete`** | 587ms | 24ms | **25배** |
| **`my_posts`** | 284ms | 9ms | **32배** |

**`comment_list` 만 변화가 없다** — 원래도 느리기 때문이다. 반면 평소 10~30ms 짜리 짧은
요청들이 20~32배로 튄다. **자기가 느려진 것이 아니라 커넥션을 못 얻어 기다린 것이다.**

> **이 표가 원인 지목의 핵심이다.** 만약 앱 전체가 느려졌다면 모든 API 가 비슷한 배율로
> 올라야 한다. 특정 API 만 무사하고 나머지가 튀는 것은 **자원 경합의 서명**이다.

### 2.6 방아쇠는 꼬리 몇 건이다

```
                    p95      p99      max
스파이크 회차      1,906    6,773   18,004ms
정상 회차          1,830    2,572   10,023ms
```

**p95 는 같은데 p99 가 2.6배다.** `comment_list` 중 극단적으로 느린 몇 건이 스파이크
회차에만 있었다.

### 3.1 7번(JIT)에서 배운 것 — 인과 방향을 뒤집을 뻔했다

`jitCompileMs` 와 p95 의 상관이 RATE=4 실행 14건에서 **r = 0.811** 로 강했다. 그래서 한때
JIT 을 유력 후보로 봤다.

정규화하니 뒤집혔다.

```
JIT vs p95        r = 0.811
CPU% vs p95       r = 0.678
JIT/요청 vs p95   r = 0.419
요청 수 vs p95    r = 0.257
```

그리고 **지표 정의를 확인한 것이 결정적이었다** — `increase(jvm_compilation_time_ms_total[$RANGE])`
는 누적이 아니라 **measure 구간의 증가분**이다. 즉 JIT 은 CPU 를 쓰는 **경쟁자**이고,
CPU 가 밀리면 JIT 도 밀린다. **설명 변수와 결과가 같은 자원을 공유하면 상관만으로 방향을
가릴 수 없다** — E-49 정정이 이미 기록한 함정이다.

## 4. 근본 원인 — 요청 비용이 542배 벌어지고, 대상은 무작위다

### 4.1 비용 분포가 극단적으로 편중돼 있다

medium 데이터셋의 게시글별 댓글 수다.

```
총 댓글 40,086개  ·  댓글 보유 글 5,539개
평균 7.2개  ·  최대 3,908개 (postId 1)   →  542배
```

| 순위 | postId | 댓글 수 | Zipf 선택 확률 | 1,347요청 중 기대 |
|---|---:|---:|---:|---:|
| 1 | **1** | **3,908** | **9.92%** | **134회** |
| 2 | 7 | 2,201 | 5.55% | 75회 |
| 3 | 3 | 1,596 | 3.89% | 52회 |
| 4 | 5 | 1,224 | 2.96% | 40회 |
| 5 | 4 | 913 | 2.38% | 32회 |
| … | | | | |
| | **상위 10개 누적** | | **32.42%** | |

`hotIndex()` 의 Zipf(s=1.07) 분포이고 `posts.json` 은 10,000건이다.

### 4.2 그 비용이 커넥션 점유 시간으로 직결된다

`CommentController.getComments()` 는 **페이징이 없다.**

```java
@GetMapping()   // GET /api/posts/{postId}/comments
public ResponseEntity<List<CommentDto>> getComments(...) {
    List<Comment> comments = commentService.getCommentsByPost(post);   // 전체
    ...
    for (int i = 0; i < comments.size(); i++) {
        LikeStateDto likeDto = commentReactionService.getLikeSatateDto(c, user);  // 댓글마다
    }
}
```

KI-27 이 지적한 **2N+α** 구조다. 로그인 상태면 댓글마다 LIKE·DISLIKE 각 1회를 조회한다.

**postId 1 한 건이 쿼리 약 7,800개를 쓴다.** 그동안 커넥션 하나를 계속 점유한다.

### 4.3 대상 선택에 시드가 없다

```js
// scenarios/lib/workload.js:47
const p = hotPost();
if (Math.random() < 0.6) listComments(p.id);

// scripts/lib/sampling.js:116
export function hotIndex(n, s = HOT_SKEW, rng = Math.random)
```

시드 데이터 생성(`datasets/seed.js`)은 고정 시드 LCG 를 쓰지만 **k6 쪽은 `Math.random`
이다.** 분포는 같아도 **회차마다 다른 표본을 뽑는다.**

### 4.4 정량화 — 표본만으로 총 작업량이 CV 4.8% 흔들린다

`hotIndex()` 로 1,347건을 뽑는 시뮬레이션 2,000회:

```
총 조회 댓글 수 (= 총 쿼리량의 대리 지표)
  평균 938,224  ·  표준편차 44,617  ·  CV 4.76%
  최소 751,967  ·  최대 1,118,480  ·  최대/최소 1.49배
  p05 867,414  ·  p50 937,326  ·  p95 1,014,270

상위 5개 글 적중 횟수
  평균 334.5  ·  CV 4.73%
```

**실측과 대조한다.**

| 지표 | 실측 CV (5회) | 몬테카를로 예측 |
|---|---:|---:|
| **요청당 쿼리** | **5.74%** | **4.76%** |
| 총 쿼리량 | 6.92% | — |
| `comment_list` 평균 | 15.00% | — |

**5.74% 대 4.76%.** 요청당 쿼리 변동은 거의 전부 표본 추출에서 온다. 이상 회차를 빼면
2.53% 로 내려간다.

> **이것이 뜻하는 것.** 현재 MDE(p95 12.5% · p99 13.7%)에는 **앱 성능 변동이 아닌 것이
> 포함돼 있다.** 앱이 완전히 동일해도 매 회차 다른 양의 일을 한다.

### 4.5 그런데 무거운 요청 하나만으로는 터지지 않는다 ← 핵심

| 회차 | `comment_list` max | p99 | **p99/p90** | 대기 |
|---|---:|---:|---:|---:|
| 23-53-47 | 8,453ms | 2,847ms | 1.58 | **0** |
| **00-06-28** | 18,004ms | 6,773ms | **4.15** | **20** |
| 00-19-13 | **20,003ms** | 2,064ms | 1.91 | **0** |
| 00-31-58 | **28,962ms** | 2,532ms | 1.79 | **0** |
| 00-44-37 | 10,023ms | 2,572ms | 1.65 | **0** |

**29초짜리 요청이 있던 회차도 대기가 0이다.** 느린 요청 한 건은 커넥션 하나만 쓰므로
풀 10개 중 9개가 남는다.

**갈리는 것은 동시에 몇 개가 무거운가다.** `p99/p90` 비율이 스파이크 회차만 4.15 이고
나머지는 1.6~1.9 다 — 상위 1% 구간이 유독 두껍다.

리틀의 법칙(`평균 응답시간 × RPS`)으로 환산한 동시 처리량도 같은 방향이다.

```
23-53-47  1.51        00-19-13  1.16
00-06-28  2.52  ←     00-31-58  1.20
                      00-44-37  1.24
```

## 5. 확정된 메커니즘

```
① Zipf 분포 + 시드 없음        → 회차마다 다른 글 조합을 뽑는다
② postId 1 (댓글 3,908개)      → 9.9% 확률, 요청당 쿼리 약 7,800개
③ 페이징 없음 + 2N+α (KI-27)   → 댓글 수에 비례해 커넥션 점유 시간이 늘어난다
      ↓
④ 대부분의 회차: 무거운 요청이 시간축에 흩어져 커넥션 1~3개만 점유
⑤ 스파이크 회차: 무거운 요청 여러 개가 15초 안에 겹침
      ↓  동시 점유가 10개(풀 전체)에 도달, idle 0
      ↓  대기 20개 발생, Tomcat 스레드 3 → 31
      ↓  CPU 2.00코어(상한) 도달
      ↓  짧은 요청까지 20~32배 지연 (post_update 21배 · my_posts 32배)
      ↓  15초 뒤 해소, 밀린 요청이 QPS 8,900 으로 한꺼번에 통과
```

**스파이크는 버그가 아니라 구조의 확률적 결과다.** 풀 크기 10에 점유 시간이 긴 API 가
9.9% 확률로 들어오면 언젠가는 겹친다. 두 세트에서 각 1회씩 나온 빈도와도 맞는다.

## 6. 해결안 판단 — 고정 시드를 쓸 것인가

### 6.1 두 목적이 실제로 충돌한다

이 시나리오는 목적이 둘이다.

| | 목적 A: 특성 파악 | 목적 B: 변경 전후 비교 |
|---|---|---|
| 묻는 것 | "이 앱이 이런 부하에서 어떻게 되나" | "이 변경이 개선인가" |
| 필요한 것 | **현실적 변동** — 겹침 사건 포함 | **낮은 분산** — 차이를 검출 |
| 고정 시드 | ❌ 위험을 측정에서 배제 | ✅ 표본 분산 제거 |

**고정 시드의 진짜 위험은 CV 가 내려가는 것이 아니라 한 표본 경로에 갇히는 것이다.**
그 경로가 우연히 postId 1 을 110번만 뽑았다면 앞으로 영원히 그 조건만 측정한다. 그리고
**이번에 발견한 겹침 사건이 그 경로에 없으면 존재 자체를 못 본다.**

### 6.2 제안 — 공통 난수(CRN, Common Random Numbers)

시뮬레이션의 표준 분산 감소 기법이고 이 트레이드오프를 정확히 겨냥한다.

```
회차 1 → 시드 1        회차 4 → 시드 4
회차 2 → 시드 2        회차 5 → 시드 5
회차 3 → 시드 3

Before 세트도 After 세트도 같은 시드 1~5 를 쓴다
```

**목적 B:** 회차 i 의 Before 와 After 가 같은 표본을 쓰므로 두 값의 **차이에서 표본 분산이
상쇄된다**(짝지은 비교). 지금 5.74% 가 통째로 노이즈로 들어가는데 그것이 사라진다.

**목적 A:** 세트 전체는 **5개의 서로 다른 표본 경로**를 덮는다. 어느 시드에서 겹침이
일어나면 그건 **재현 가능한 사건**이 되어 오히려 연구하기 쉬워진다. 지금은 재현이 안 돼
"왜 하필 그때"를 풀지 못한다.

이것으로 시드를 만들면 회차 간 같은 표본 다중집합이 나온다. `seed.js` 의 고정 시드 LCG 를

### 6.4 한계 세 가지 — 정직하게

**① 완전히 결정론적이 되지 않는다.** 어느 요청이 **동시에** 처리되는지는 VU 스케줄링과
응답시간에 달렸다. CRN 은 "무엇을 요청하는가"를 고정할 뿐 "언제 겹치는가"는 고정하지
못한다. **이번 스파이크의 직접 원인(겹침)은 여전히 확률적이다.** 따라서 CV 가 5.74%
만큼 통째로 줄지는 않는다.

**② `scriptVersion` 이 바뀐다.** `sampling.js` 는 `TRAFFIC_SHAPING_FILES`(`perf-run.js:241`)
에 있다. 고치면 지문이 달라져 기존 실행과 **`degraded` 판정**이 된다. blocking 은 아니라
비교는 되지만 경고가 붙는다.

**③ Before 를 다시 재야 한다.** 짝지은 비교는 양쪽이 같은 시드를 써야 성립한다.
2026-08-26 에 잡은 5회 세트는 CRN 이전이라 짝이 안 맞는다. 약 1시간이 더 든다.

### 6.5 결론 — 지금은 하지 않는다

**KI-27 실험이 끝난 뒤로 미룬다.** 근거 셋이다.

1. **KI-27 은 CRN 없이도 판정된다.** 기대 효과가 요청당 쿼리 288 → 수십 개다. 표본 분산
   5.74% 가 묻힐 크기다. **작은 개선을 재야 할 때 CRN 이 필요한 것이지 지금은 아니다.**
2. **지금 바꾸면 확보한 Before 5회가 무효가 된다.**
3. **KI-27 수정 자체가 이 문제를 줄인다.** 2N+α 가 상수가 되면 postId 1 의 비용이 542배에서
   1배 수준으로 내려간다 — **표본 추출 분산의 근원이 사라진다.** 그 뒤에도 CRN 이 필요한지
   다시 재보는 것이 순서다.

### 6.6 기각한 다른 대안

- **풀 크기를 늘려 스파이크를 없앤다** → **측정 시스템의 일이 아니다.** 풀 크기는
  애플리케이션 구성이고, 바꾸면 측정 대상이 달라져 기존 계열과 비교가 끊긴다.
  병목 쪽(BTL-002)에서 다룰 문제다.
- **`hikariPending > 0` 을 새 무효화 규칙으로 추가한다** → **불필요하다.**
  `saturation.js` 의 `hikariPending` 신호(warn 1 / fail 5)가 이미 두 세트 모두에서 해당
  회차를 `NEAR_LIMIT` 으로 잡아냈다. 새 규칙을 만들면 판정이 두 곳에 생겨 T-40 과 같은
  불일치를 부른다.
- **첫 회차를 항상 예열로 버린다** → **기각.** 5회 세트에서 1회차는 정상(388ms)이었고
  2회차가 튀었다. 순서 기반 규칙은 이 세트에서 틀린 회차를 버린다.

## 7. 지금 적용하는 운용 규칙

**반복 세트에서 포화 판정이 `HEADROOM` 이 아닌 회차는 표본에서 뺀다. 순서는 보지 않는다.**

5회를 확보하려면 `--runs 6` 으로 여유를 두는 것을 검토한다(이상 회차 발생률이 두 세트에서
각 1회였다). 회차당 약 12분 45초이므로 6회면 약 78분이다.

**개선 판정에서 함께 볼 것:** 평균만 보면 개선의 절반을 놓친다. **`p99/p90` 비율과 대기
발생 여부**를 Before/After 에서 나란히 본다 — KI-27 수정이 성공하면 분산 자체가 줄어야
한다.

## 8. 남은 미확인

- **무거운 요청이 왜 하필 그 15초에 겹쳤는가.** 확률로만 설명된다. 개별 요청의 타임스탬프가
  있어야 확정되는데 k6 원자료에 요청별 시각이 남지 않는다. `--out json` 으로 개별 샘플을
  남기거나 앱에 요청별 로그를 켜야 한다. **다만 결론은 바뀌지 않는다** — 겹침이 원인이라는
  것은 동시 처리량(2.52 대 1.16~1.51)으로 이미 확인됐다.
- **다른 시나리오에도 같은 편중이 있는가.** `read-heavy`·`write-heavy` 등은 용량 곡선조차
  그려 본 적이 없다(E-46 0.7절). 같은 `hotIndex()` 를 쓰므로 같은 구조일 가능성이 높다.
- **`posts.json` 의 정렬과 실제 댓글 수가 얼마나 일치하는가.** S-03 이 재생성으로 해결됐다고
  기록하지만, 이번 조사에서 확인한 상위 12개(postId 1·7·3·5·4…)가 `posts.json` 의
  index 순서와 정확히 일치하는지는 별도로 대조하지 않았다.

## 9. 재현 방법

```bash
# 게시글별 댓글 수 분포

# 표본 추출 분산 시뮬레이션
node -e "
(async()=>{
  const m=await import('./scripts/lib/sampling.js');
  const posts=require('./datasets/generated/medium/posts.json');
  const cc={1:3908,7:2201,3:1596,5:1224,4:913,8:786,10:703,9:623,6:507,2:493};
  const c=i=>cc[posts[i].id]??7, tot=[];
  for(let t=0;t<2000;t++){let s=0;for(let i=0;i<1347;i++)s+=c(m.hotIndex(posts.length));tot.push(s);}
  const mu=tot.reduce((a,b)=>a+b)/tot.length;
  const sd=Math.sqrt(tot.reduce((s,v)=>s+(v-mu)**2,0)/(tot.length-1));
  console.log('평균',mu.toFixed(0),'CV',(sd/mu*100).toFixed(2)+'%');
})()"
```

`rate(container_cpu_usage_seconds_total{name="perf-app"}[15s])` 를 5초 간격으로 본다.
