# 호스트 CPU 의 일중 주기 — 유휴 벤치 134시간 분석

> 기준 시점: 2026-08-25
> 답하는 질문: **"측정 환경의 CPU 속도는 시간에 따라 어떻게 변하고, 그 변동이 앱 측정값에
> 전달되는가?"**
> 성격: **조사 기록.** 발견 장부의 **E-50** 항목이 "무엇이 문제인가"만 들고 있고,
> 데이터·분석·기각된 가설은 전부 여기 모은다.
> 짝 문서: [perf-session-drift.md](perf-session-drift.md)(E-46, 세션 간 편차),
> [perf-findings-environment.md](../findings/perf-findings-environment.md)(E-49, 유효 CPU 처리 능력),
> [perf-trust-levels.md](../planning/perf-trust-levels.md)(레벨 판정)

---

## 0. 한 줄 결론

**호스트 CPU 속도에는 하루를 주기로 16% 폭의 재현 가능한 변동이 있다. 그러나 포화 이하
운용점에서는 그 변동이 앱 성능으로 전달되지 않는다(상관 r = −0.006).**

그래서 실무 결론은 **"측정 시각을 고정할 필요가 없다"** 이며, 이는 E-46 해결(증폭기 제거)이
제대로 작동한다는 **독립적인 추가 증거**다.

## 1. 데이터 — 무엇을 어떻게 쟀나

`tools/idle-bench-logger.js --interval 600` 이 2026-08-19 22:52(KST)부터 2026-08-25
13:03(KST)까지 **134.2시간 동안 814개 표본**을 남겼다. 기록 파일은
`performance/reports/idle-cpu-bench.jsonl` 이다.

레코드 하나는 `cpu-bench.js` 의 3축을 한 번씩 돌린 결과다.

```json
{
  "at": "2026-08-19T13:52:01.071Z",
  "underLoad": false,
  "single": 6325, "parallel": 4497, "ctxswitch": 5806,
  "ratios": { "parallelPerSingle": 0.711, "ctxswitchPerSingle": 0.918 }
}
```

**이 벤치가 인과 분석에 적합한 이유.** 세 축 모두 Docker 컨테이너 안에서 도는 고정 작업량
(`dd | md5sum` 등)이다. 벤치가 스스로 부하를 늘리지 않으므로, 부하 테스트 지표와 달리
**역인과가 생기지 않는다.** E-49 정정이 지적한 공백이 바로 이것이었다 —
*"가르려면 고정 작업량 벤치를 찍으면서 동시에 호스트를 기록해야 한다."*

`underLoad: true` 인 26개 표본은 **부하 테스트가 도는 중에 찍힌 것**이다. 이 표본은 부하와
CPU 를 경합하므로 환경 지표로 쓰면 안 된다 — 4절에서 실제로 그 함정에 빠졌다가 빠져나온
기록을 남긴다.

## 2. 발견 ① — 일 단위 환경은 매우 안정적이다

`single` 축(코어 클럭)의 일별 중앙값이다. KST 기준.

| 날짜 | n | single | parallel | ctxswitch |
|---|---:|---:|---:|---:|
| 08-19 | 8 | 6,189 | 5,487 | 2,677 |
| 08-20 | 151 | 5,832 | 5,597 | 2,481 |
| 08-21 | 144 | 5,904 | 5,565 | 2,490 |
| 08-22 | 144 | 5,932 | 5,372 | 2,516 |
| 08-23 | 144 | 5,924 | 5,382 | 2,528 |
| 08-24 | 144 | 5,857 | 5,511 | 2,487 |
| 08-25 | 79 | 5,884 | 5,411 | 2,496 |

**08-20 ~ 08-25 의 `single` 폭은 1.7%, `ctxswitch` 는 1.9% 다.** 08-19 는 표본 8개이고

> **이 표가 E-46 조사의 원래 전제를 반박한다.** 닷새 동안 "환경이 세션마다 45% 변한다"를
> 전제로 원인을 찾았지만, 6일 연속 측정으로 보면 **일 단위 환경은 1.7% 안에서 안정적**이다.
> E-46 의 45% 는 환경이 아니라 포화가 만든 것이라는 결론과 일치한다.

전체 유휴 표본 788개를 KST 시각별로 접은 `single` 중앙값이다. 기준은 전체 중앙값 5,899ms.

| 01 | 5,909 | +0.2% | 13 | 5,471 | −7.3% |

| 03 | 5,941 | +0.7% | 15 | 5,551 | −5.9% |

하루만 떼어 보면 계단 모양이 더 분명하다. 08-20 의 시간별 중앙값이다.

```text

```

**09시와 18시가 전환점이고, 그 사이가 16% 빠르다.** 점진적 드리프트가 아니라 **스위치**다.

### 3.1 원인 — 추정이며 확인하지 않았다

가장 그럴듯한 설명은 **Windows 전원 관리**다. 밤새 머신이 유휴이면 프로세서가 낮은 P-state
에 머물고, 업무 시간에 사용자가 활동하면 높은 상태를 유지한다. E-49 가 확인한 대로 이
머신의 전원 계획은 "균형 조정"이고 **최소 프로세서 상태가 5%** 다.

**다만 이건 추론이다.** 확인하려면 호스트 주파수를 같은 시각에 기록해야 하는데,
`idle-bench-logger.js` 에는 호스트 카운터가 없다. E-49 완료 기준 4번이 그 공백을 이미
지적하고 있다.

**대안 가설로 배제하지 못한 것:** 사용자 활동으로 인한 백그라운드 작업(브라우저·IDE·
인덱싱)이 반대 방향으로 작용해야 하는데 실측은 낮이 **빠르다**. 그래서 백그라운드 부하
가설은 이 데이터와 맞지 않는다.

### 3.2 스파이크는 드물다

유휴 표본 788개를 전체 중앙값 대비로 나누면 이렇다.

| 중앙값 대비 | 개수 | 비율 |
|---|---:|---:|
| 미만 | 393 | 49.9% |
| ×1.00 ~ 1.05 | 363 | 46.1% |
| ×1.05 ~ 1.10 | 19 | 2.4% |
| ×1.10 초과 | 13 | **1.7%** |

**96% 가 중앙값 ±5% 안에 있다.** 환경은 대체로 평평하고, 드문 스파이크가 따로 존재한다.

## 4. 발견 ③ — 그 주기가 앱 성능으로 전달되지 않는다 ← 가장 중요

여기서 처음 세운 가설이 데이터로 뒤집혔다. 그 과정을 그대로 남긴다.

### 4.1 처음 세운 가설과 그 근거

측정 세트의 시각과 유휴 벤치를 대조하니 이렇게 보였다.

| 세트 | KST | 유휴 벤치 | 앱 전체 p95 평균 |
|---|---|---:|---:|
| CV validation | 13:39 | 5,482ms | 277.7ms |
| KI-27 Before-A | 16:02 | 5,107ms | 2,258.6ms *(포화 1회 포함)* |
| KI-27 Before-B | 20:42 | **6,082ms** | 363.9ms |

Before-B 는 CPU 가 가장 느린 저녁에 측정됐고(벤치 +11%), 앱 p95 도 validation 대비 +31%
였다. 그래서 **"환경 주기가 앱에 2.8배로 증폭된다"** 고 판단했고, "Before/After 를 같은
시간대에 재야 한다"는 규칙을 제안했다.

### 4.2 반증 — 실행 직전 벤치를 쓰면 상관이 사라진다

**`run.cpuBench` 가 이미 매 실행마다 저장돼 있다.** 부하를 걸기 **전에** 3축을 3회 돌린
값이다. 유휴 벤치와 달리 부하와 경합하지 않는다.

RATE=4 실행 11건의 실행 직전 벤치와 앱 p95 다.

| KST | 벤치 single | 앱 p95 |
|---|---:|---:|
| 13:29 | 5,036 | 402 |
| 13:39 | 4,984 | 305 |
| 13:52 | 4,940 | 252 |
| 14:04 | 4,980 | 276 |
| 15:58 | 4,940 | 221 |
| 16:06 | 4,962 | 784 |
| 16:19 | 5,062 | 358 |
| 20:32 | **5,901** | 425 |
| 20:44 | **5,795** | 286 |
| 20:58 | **5,970** | 376 |
| 21:10 | **5,863** | 368 |

**피어슨 상관 r = −0.006.** 사실상 0이다.

벤치는 낮 4,940~5,062ms, 밤 5,795~5,970ms 로 **17% 차이**가 뚜렷하다. 그런데 앱 p95 는
낮 평균 371ms(784 제외 시 302ms), 밤 평균 364ms 로 **구분되지 않는다.**

### 4.3 왜 4.1 이 틀렸나

validation(277.7ms) 과 Before-B(363.9ms) 의 +31% 는 **시간대 때문이 아니다.** 같은 시간대
안에서도 p95 가 221~784ms 로 흩어진다. 두 세트의 차이는 그 산포 안에 들어간다.

**세트 평균 두 개를 비교하고 그 사이에 있는 다른 설명 변수(시각)를 원인으로 지목한 것이
오류였다.** 표본 하나하나를 놓고 상관을 내면 관계가 없다.

### 4.4 이것이 뜻하는 것

**E-46 해결이 전체 p95 에서도 작동한다는 독립적 증거다.**

`perf-session-drift.md` 0.6절은 "환경 18% 변동 → 앱 1.5% 변동" 을 근거로 증폭기가
제거됐다고 결론지었다. 그 근거는 `comment` 기능별 p95 세트 평균 두 개였다. 여기서는
**전체 p95 를, 표본 11개로, 상관계수로** 확인했고 같은 결론이 나왔다.

즉 **포화 이하에서는 환경이 17% 느려져도 앱 응답시간이 따라가지 않는다.** CPU 여유가
37~50% 남아 있으므로, 코어가 조금 느려져도 요청당 처리가 늦어질 뿐 큐가 생기지 않는다.

## 5. 발견 ④ (기각) — `#115` 포화 이탈은 환경 탓이 아니다

`#115` 는 **도착률 4.00/s 를 정확히 지켰는데도 포화로 넘어간** 회차다
(`normal-day-2026-08-20T07-42-12`, 앱 CPU 100%, throttled 71.7%, p95 5,634ms).
`perf-session-drift.md` 0.7절이 "포화 감지가 상시 장치여야 하는 근거"로 인용한다.

### 5.1 처음 세운 가설

Before-A 구간의 유휴 벤치 원시 표본이 이랬다.

| KST | single | underLoad | 대응 회차 | 앱 상태 |
|---|---:|---|---|---|
| 15:32~15:52 | 5,018~5,122 | false | (부하 전) | — |
| **16:02:50** | **6,331** | **true** | #1 시작 | CPU 65%, p95 784ms (NEAR_LIMIT) |
| 16:22:50 | 5,107 | true | #2 진행 | CPU 46%, p95 358ms (HEADROOM) |
| **16:32:50** | **6,604** | **true** | #3 시작 | CPU 100%, p95 5,634ms (**SATURATED**) |
| 16:42:50 | 5,003 | false | (부하 후) | — |

세 회차가 벤치 스파이크 유무와 정확히 일치했다. 그래서 **"환경 스파이크가 앱을 절벽 너머로
밀었다"** 고 판단했다.

### 5.2 반증

`#115` 의 **실행 직전 벤치는 4,987ms** 다(샘플 5,044 / 4,969 / 4,987). 같은 시간대 정상
범위(4,940~5,062) 한가운데다.

```
실행 직전 (부하 없음)  cpuBench.single  = 4,987ms   ← 정상
부하 중                loadBench.single = 5,276ms   (샘플 5276 / 7214 / 5119)
유휴 로거 (부하 중)                     = 6,604ms   ← 스파이크
```

**환경은 정상이었다. 스파이크는 부하가 만들었다.**

### 5.3 왜 이 함정에 빠졌나 — 기록해 둘 것

스파이크로 보인 표본은 전부 `underLoad: true` 였다. **부하 테스트가 CPU 를 쓰는 중에 찍힌
벤치를 "환경 지표"로 쓴 것이다.** 앱이 포화될수록 벤치도 느려지므로 **역인과**가 생긴다.

E-49 정정이 이미 같은 함정을 기록해 두었다.

> `loadbench` 는 hostProbe 창 안에서 실행된다 — 설명 변수 안에 CPU 를 태우는 도구를 넣어
> 놓고 그 값으로 상관을 낸 셈이다.

**같은 실수가 반복됐다.** 규칙으로 굳힌다 — **`underLoad: true` 표본은 환경 판단에 쓰지
않는다.** 환경을 보려면 `run.cpuBench`(실행 직전)나 유휴 로거의 `underLoad: false` 표본만
쓴다.

### 5.4 그래서 `#115` 의 원인은 여전히 미규명이다

환경이 아니라는 것만 확정됐다. 남은 후보는 앱 내부(GC, 커넥션 재수립, 캐시 콜드 스타트)나
컨테이너 재시작 직후의 과도 상태다. `reset: "restart"` 로 매 회차 앱을 재시작하므로 후자가
유력하지만 확인하지 않았다.

## 6. 클럭 고정으로 해결할 수 있는가 — 이미 시도했고 기각됐다

3절의 주기를 보면 "측정 중에는 CPU 를 고클럭으로 고정하면 되지 않나"가 자연스러운 발상이다.
**E-49 에서 이미 실측으로 시도했고 버렸다.** 근거를 여기 모아 둔다.

### 6.1 실제로 고정되지 않았다

```powershell
powercfg /setacvalueindex SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMIN 100
powercfg /setactive SCHEME_CURRENT
```

적용 후 실측(E-49 에 기록된 두 건):

| 항목 | 결과 | 출처 |
|---|---|---|
| 고정 전후 유휴 벤치 | **4,994ms 대 4,995ms — 차이 없음** | `perf-findings-environment.md:2028` |
| 고정 전후 유휴 벤치 (다른 비교) | 5,187 → 5,040ms (−3%) | 같은 문서 말미 |
| 고정 전후 **부하 중** 벤치 | 6,364 → 5,581ms (−12%) | 같은 문서 말미 |
| 적용 후 유휴 주파수 | 70~89% (100% 로 붙지 않음) | E-49 |
| 대조 세트 p95 | 오히려 **+47%** 나빠짐 | E-49 |

**두 가지를 함께 읽어야 한다.**

1. **유휴 상태에서는 효과가 없거나 미미하다** (0% ~ −3%). 관측하려는 일중 주기가 16% 폭인
   것에 비하면 무시할 수준이다.
2. **부하 중 벤치는 −12% 빨라졌는데 앱 p95 는 +47% 나빠졌다.** 두 계열이 반대로 움직였다.
   E-49 는 이를 "환경의 순수 CPU 처리 능력으로 앱 처리율을 설명할 수 없다"의 근거로 남겼다.

어느 쪽이든 **16% 주기를 없애 줄 개입이 아니다.**

### 6.2 원리적으로 왜 안 되나

E-49 정정이 정리한 대로다.

- 이 머신의 전원 구성표에 **노출된 프로세서 설정은 `PROCTHROTTLEMIN`·`PROCTHROTTLEMAX`
  두 개뿐**이다. 이기종 코어(P/E) 클래스별 설정과 EPP 는 숨김 상태라 열거되지 않는다 →
  **변경이 모든 코어 클래스에 적용됐는지 확인할 수 없다.**
- 최소 성능 상태 100% 는 **터보·패키지 전력 한계·열 한계·P/E 배치·Hyper-V vCPU 이동·
  QoS·EPP 를 고정하지 않는다.**
- `cpuset` 고정도 부족하다 — Hyper-V 의 virtual processor 자체가 서로 다른 host logical
  processor 로 이동할 수 있다.
- 노트북이라 **발열 상승 → 팬 정책 변경 → 후반 열 스로틀링**이라는 **새로운 드리프트**를
  만들 수 있다.

### 6.3 시간대 교락 가능성을 확인했고, 기각을 뒤집지 못했다

기각 근거인 "+47%" 실험이 시간대 효과에 오염됐을 가능성을 이번에 검토했다.

| 세트 | KST | 시간대 | p95 평균 |
|---|---|---|---:|
| clock-pinned control set (E-49) | **10:22~10:47** | **낮 (빠름)** | 15,721ms |
| 비교 대상 08-19 세트 | 14:50~18:25 | 낮~저녁 | 11,628ms |

**클럭 고정 세트가 오히려 CPU 가 가장 빠른 시간대에 돌았다.** 유리한 조건에서도 더 나빴으니
시간대 교락은 기각을 약화시키지 않는다 — **오히려 강화한다.**

*(다만 두 세트 모두 포화 상태 측정이므로, "포화 이하에서 클럭 고정이 어떤 효과인지"는
아직 재본 적이 없다. 6.1 의 "벤치 1ms 차이"가 그 실험을 무의미하게 만들기는 한다.)*

### 6.4 그리고 애초에 필요하지 않다

4절의 결론이 이 논의를 무효화한다. **포화 이하에서는 환경이 17% 느려져도 앱 p95 가 따라가지
않는다.** 고정할 이유가 없다.

**클럭을 고정할 수 없다면 클럭이 이미 평평한 구간에서 재면 된다** — 는 것도 필요 없다.
어느 구간에서 재든 결과가 같기 때문이다.

## 7. 실무 규칙 — 무엇이 바뀌고 무엇이 안 바뀌나

### 바뀌지 않는 것

| 제안 | 판정 | 이유 |
|---|---|---|
| 측정 시각을 고정한다 | **불필요** | 환경 주기가 앱에 전달되지 않는다 (r = −0.006) |
| Before/After 를 같은 시간대에 잰다 | **불필요** | 같은 이유 |
| CPU 클럭을 고정한다 | **불가능하고 불필요** | 6절 |
| 야간 자동 측정을 주간 측정과 분리한다 | **불필요** | 같은 이유 |

**단, 이 판정은 포화 이하 운용점에 한한다.** 포화 상태에서 환경 변동이 앱에 어떻게
전달되는지는 재본 적이 없다. 그 상태에서 환경과 앱을 함께 잰 유일한 자료가 6.3 의 클럭 고정
세트인데, **CPU 가 가장 빠른 시간대에 돌고도 p95 가 47% 나빴다.** 환경이 좋아지면 앱도
좋아진다는 관계가 그 자료에서 나오지 않는다. 어느 쪽이든 그때는 시간대가 아니라
**포화 자체가** 측정을 무효화한다.

*(2026-09-05 정정: 이 자리에 "포화 상태에서는 작은 환경 변동이 45% 로 증폭되므로(E-46)"
라고 적혀 있었다. E-46 이 실제로 보인 것은 **용량 변동의 증폭**이고, 그 용량을 흔든 것이
환경이라는 근거는 이 문서 4·6절이 오히려 반대로 말한다. 같은 날
[perf-session-drift.md](perf-session-drift.md) 0.2 ③ 과 E-46 해결 기록도 정정했다.)*

### 바뀌는 것

| 규칙 | 근거 |
|---|---|
| **`underLoad: true` 표본은 환경 판단에 쓰지 않는다** | 5.3 — 역인과. 두 번째 재발 |
| **환경을 보려면 `run.cpuBench`(실행 직전)를 쓴다** | 매 실행에 이미 저장돼 있다 |
| 유휴 로거를 상시 돌리지 않는다 | 추적 파일에 계속 기록해 작업 트리가 `+dirty` 로 유지된다. 질문이 생겼을 때만 켠다 |

### 열어 둔 것

- **`run.cpuBench` 를 회차 무효화 조건으로 쓸 것인가.** 매력적이지만 `#115` 는 벤치가
  정상인데도 포화됐다(5.2). **필요조건일 수는 있어도 충분조건은 아니다.**
- **호스트 주파수를 유휴 로거에 붙일 것인가.** 3.1 의 원인 추정을 확인하려면 필요하다.
  E-49 완료 기준 4번이 같은 것을 요구한다. 다만 4절 이후로는 **알아도 판정이 바뀌지 않는다.**

## 8. 재현 방법

```bash
# 로거 실행 (10분 간격)
node tools/idle-bench-logger.js --interval 600

# 분석 — 시간대별 중앙값 (KST)
node -e "
const R=require('fs').readFileSync('reports/idle-cpu-bench.jsonl','utf8')
  .trim().split('\n').map(JSON.parse).filter(r=>!r.underLoad);
const med=a=>{const s=[...a].sort((x,y)=>x-y);return s[Math.floor(s.length/2)]};
const hr={}; R.forEach(r=>{const h=new Date(new Date(r.at).getTime()+9*36e5).getUTCHours();
  (hr[h]=hr[h]||[]).push(r.single)});
for(let h=0;h<24;h++) if(hr[h]) console.log(h+'시', med(hr[h])+'ms', '(n='+hr[h].length+')');
"
```

**주의: `filter(r => !r.underLoad)` 를 빼면 5절의 함정에 그대로 빠진다.**

실행 직전 벤치는 각 실행의 `reports/runs/<runId>/run.json` 의 `run.cpuBench.axes.single.ms`
에 있다.
