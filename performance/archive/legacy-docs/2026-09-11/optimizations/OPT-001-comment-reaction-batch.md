# OPT-001: 댓글 목록의 내 반응 조회를 일괄 조회로 전환

> 대상 병목: BTL-005 | 검증 실험: EXP-005 | 적용 커밋: `d346714`

> 상태: **적용**
> 측정: 2026-09-01 ~ 09-03 | 데이터셋 medium (`sha256:24ddff07519b`)

## 한 줄 요약

댓글 목록 API가 **댓글 하나마다 좋아요·싫어요를 따로 묻던 것**을 댓글 id 전체를 한 번에
넘기는 조회로 바꿨다. 요청당 쿼리 수가 **1,507건에서 112건으로(−92.6%)**, 전체 p95 가
**226.7ms 에서 57.2ms 로(−74.8%)** 줄었다.

---

## 1. 무엇이 문제였나

### 1-1. 증상

`normal-day` 시나리오에서 `comment` 기능이 **요청의 16.8% 인데 전체 응답시간의 85.9%** 를
차지했다. 엔드포인트로 좁히면 `GET /api/posts/{postId}/comments` 한 개가 평균 349ms,
p95 1,906ms 였다. 두 번째로 무거운 `GET /api/posts/{postId}` 가 6.9ms 이므로 **50배** 다.

### 1-2. 원인 — 코드 경로

댓글 N개, 서로 다른 작성자 U명인 게시글의 목록 요청 하나가 발행하던 쿼리다.

| 단계 | 위치 | 쿼리 수 |
|---|---|---:|
| 인증 사용자 조회 | `TokenAuthenticationFilter` | 1 |
| 게시글 조회 | `CommentController.getComments` | 1 |
| 댓글 목록 | `CommentRepository.findByPost` — 패치 조인 없음 | 1 |
| 작성자 이름 | `CommentDto.fromEntity` → `comment.getUser().getNicknameValue()` | **U** |
| **내 반응 확인** | `CommentController` 루프 → `CommentReactionService.getLikeSatateDto` | **2N** |

`Comment.user` 는 `LAZY` 라(`Comment.java:23`) DTO 를 만들며 프록시를 건드리는 순간
작성자마다 SELECT 가 하나씩 나갔다. 그리고 반응은 **댓글마다 두 번** 물었다 —
`getLikeSatateDto` 가 `isLikedByUser` 와 `isDislikedByUser` 를 각각 부르고, 그 둘이
각각 `existsBy...` 쿼리를 하나씩 발행하기 때문이다.

```java
// 변경 전 — CommentController.getComments
for (int i = 0; i < comments.size(); i++) {
    LikeStateDto likeDto = commentReactionService.getLikeSatateDto(c, user); // 쿼리 2회
    dto.setLiked(likeDto.isLiked());
    dto.setDisliked(likeDto.isDisliked());
}
```

즉 **요청당 쿼리 = 3 + U + 2N** 이다.

### 1-3. 각 쿼리는 느리지 않았다 — 왕복 횟수가 문제였다

반응 확인 쿼리는 `uk_comments_reactions_cmt_usr (CMT_id, USR_id)` 유니크 인덱스를 그대로
타서 **1행만 읽는다.** 인덱스가 없어서 느린 것이 아니라, 그 싼 쿼리를 **1,000번 왕복**하는
것이 비쌌다.

이것이 EXP-005 에서 H2(인덱스 미사용 풀스캔)를 기각한 근거와 같은 이야기다 — 쿼리당 읽은
행 수가 약 1행이었다. **slow query 는 이 병목과 무관하며**, 그 판단은 이 최적화 뒤에 다시
확인됐다(§5-4).

## 2. 무엇을 어떻게 바꿨나

**변수는 하나다.** 이 최적화는 반응 조회 경로만 건드렸다. 작성자 지연 로딩(U)은
**일부러 그대로 두었다** — 그쪽은 OPT-002 로 따로 잰다.

### 2-1. 리포지토리 — 일괄 조회 추가

`CommentReactionRepository.java`

```java
@Query("""
        select r from CommentReaction r
        where r.user = :user
          and r.isValid = true
          and r.comment.id in :commentIds
        """)
List<CommentReaction> findMineByCommentIds(@Param("user") User user,
                                           @Param("commentIds") Collection<Long> commentIds);
```

`r.comment.id` 는 FK 컬럼을 그대로 읽으므로 `comments` 테이블과 조인하지 않는다.

**게시글이 아니라 댓글 id 목록으로 거른 이유.** `where r.comment.post = :post` 로 써도
지금은 결과가 같고 바인딩 파라미터가 2개로 줄어든다. 그런데 그러면 조회 범위가 **목록
쿼리와 독립**이 된다. 나중에 댓글 목록에 페이징이나 필터가 붙는 순간 조회 결과가 조용히
화면보다 넓어지고, 그 불일치는 아무 데서도 드러나지 않는다. 댓글 id 로 묶으면 **화면에
그려지는 것과 조회 대상이 정의상 같다.**

### 2-2. 서비스 — 맵으로 접기

`CommentReactionService.java`

```java
public Map<Long, PostReactionKind> findMyReactions(List<Comment> comments, User user) {
    if (comments.isEmpty()) return Map.of();
    List<Long> commentIds = comments.stream().map(Comment::getId).toList();
    return commentReactionRepository.findMineByCommentIds(user, commentIds).stream()
            .collect(Collectors.toMap(r -> r.getComment().getId(), CommentReaction::getKind));
}
```

`r.getComment().getId()` 는 LAZY 프록시의 id 만 읽으므로 추가 쿼리가 없다.

`toMap` 에 병합 함수를 넣지 않았다. `uk_comments_reactions_cmt_usr` 유니크 제약이
(댓글, 사용자) 쌍당 최대 한 행을 보장하므로 키 충돌은 **일어날 수 없다.**

**반응이 없는 댓글은 맵에 넣지 않는다.** 호출부가 `kind == LIKE` 로 읽는데 없는 키는
`null` 이라 그 비교가 그대로 `false` 다. "반응 없음"을 나타내는 별도 값을 만들면 호출부가
그 값을 다시 분기해야 한다.

### 2-3. 컨트롤러 — 루프에서 조회 제거

`CommentController.java`

```java
// 변경 후
Map<Long, PostReactionKind> myReactions = commentReactionService.findMyReactions(comments, user);
for (int i = 0; i < comments.size(); i++) {
    PostReactionKind kind = myReactions.get(c.getId());
    dto.setLiked(kind == PostReactionKind.LIKE);
    dto.setDisliked(kind == PostReactionKind.DISLIKE);
    dto.setOwner(user.getId().equals(c.getUser().getId()));
}
```

좋아요·싫어요 **개수**는 손대지 않았다. 이미 `Comment` 에 비정규화돼 있어
(`likeCount`·`dislikeCount`) `CommentDto.fromEntity` 가 엔티티에서 그대로 읽는다.

### 2-4. 건드리지 않은 것

- `getLikeStateDto` 는 남겼다. 단건 토글 응답(`CommentReactionController`)이 쓴다.
- 쓰기 경로(`likeReact`·`dislikeReact`)는 그대로다. 그쪽의 체크-후-삽입 경쟁은 별개
  결함이며 OPT-003 으로 분리했다.
- 작성자 지연 로딩(U) — OPT-002.

## 3. 검증 ① — 단위 테스트

핵심 계약이 "결과가 맞다"만이 아니라 **"조회를 한 번만 한다"** 라서, 호출 횟수도 테스트로
고정했다.

| 테스트 | 무엇을 고정하나 |
|---|---|
| 댓글이 몇 개든 조회는 한 번만 한다 | `findMineByCommentIds` 1회, `existsBy...` 0회 |
| 목록에 있는 댓글 id 전부를 한 번에 넘긴다 | 캡처한 인자가 `[7,8,9]` |
| 반응 종류를 댓글 id 로 찾을 수 있게 돌려준다 | 맵 키·값 대응 |
| 반응이 없는 댓글은 맵에 없다 | 호출부의 `null` 비교 계약 |
| 댓글이 없으면 조회하지 않는다 | 빈 목록에서 쿼리 0회 |

전체 스위트 **722개 통과 · 실패 0**.

## 4. 검증 ② — 단일 요청 쿼리 수 (결정적, 부하 없음)

앱을 재빌드한 뒤 medium 에 요청을 한 번씩 보내고 `http_server_queries` 누적값의 차이를
읽었다. **부하가 없으므로 잡음이 0 이고 통계가 필요 없다.**

| 게시글 | 댓글 수 N | 서로 다른 작성자 U | 실측 쿼리 | 모델 `3 + U + 1` |
|---:|---:|---:|---:|---:|
| 247 | 6 | 5 | **9** | 9 ✅ |
| 2 | 492 | 130 | **134** | 134 ✅ |
| 8 | 4,047 | 450 | **454** | 454 ✅ |

세 건 모두 오차 0 이다. 남은 4개는 인증 1 + 게시글 1 + 댓글 목록 1 + **반응 일괄 1** 이므로,
**반응 확인이 2N 에서 정확히 1 로 줄었다는 직접 증거**다.

같은 식으로 변경 전 값을 되돌리면(`3 + U + 2N`):

```
게시글 2   1,117 → 134   (−88%)
게시글 8   8,547 → 454   (−95%)
```

### 응답 정합성

댓글 4,047개짜리 게시글에서 DB 와 대조했다.

```
내가 반응한 댓글 수      응답 20개 = DB 20개
LIKE 4건·DISLIKE 1건 표본  종류까지 전부 일치
isOwner                    898건 정상
```

| 지표 | Before | After | 변화 |

**비중이 거의 안 변한 것은 의미 있는 사실이 아니다.** DB 시간이 −90.5%, 비-DB 시간이
−88.1% 로 **두 부분이 거의 같은 비율로 줄었기 때문에** 나눈 값이 그대로인 것뿐이다.
비율은 분자와 분모가 함께 작아지면 움직이지 않는다 — 그 상태에서 "비중이 그대로니 문제도
그대로"라고 읽으면, **234ms 짜리 기회와 22ms 짜리 기회를 같은 것으로 말하게 된다.**

`dbSharePct` 가 답하는 질문은 크기가 아니라 **종류**다. "이 엔드포인트에 남은 시간이
DB 왕복 쪽인가 앱 처리 쪽인가" — 다음에 어떤 **종류**의 최적화를 시도할지 고르는 데 쓴다.
"그래서 얼마나 값어치가 있나"에는 답하지 못하며, 그 질문에는 **절대값**을 봐야 한다.

> 이번 데이터에서 비율이 **불안정해지지는 않았다.** 분모가 10분의 1로 작아졌는데도
> `dbSharePct` 의 변동계수는 1.0% → 0.6% 로 오히려 좁아졌다. 즉 비율은 **잡음이 커진
> 것이 아니라 정보량이 없어진 것**이다. 둘은 다른 문제이고, 여기서 일어난 것은 뒤쪽이다.

### 그래서 OPT-002 의 여지는 얼마인가 — 절대값으로

| 항목 | 값 | 근거 |
|---|---:|---|
| 현재 요청당 쿼리 | 112 | 실측 |
| OPT-002 가 없앨 쿼리 | 약 108 | 작성자 지연 로딩(U). 남는 것은 인증·게시글·댓글목록·반응 4개 |
| 쿼리당 DB 시간 | 0.198ms | 실측 (22.2ms ÷ 112) |
| **없앨 수 있는 DB 시간** | **약 21ms** | 108 × 0.198ms |
| 최적 시 `comment_list` 응답 | 36.1ms → **약 15ms** | 비-DB 13.9ms 는 그대로 둔 보수적 추정 |

**OPT-001 은 요청당 314ms 를 없앴고, OPT-002 의 상한은 약 21ms 다 — 15분의 1 규모다.**
`comment` 기능이 전체 시간의 36.7% 를 차지하므로, 전부 실현돼도 **종단 개선폭은 20% 안팎**이
상한이다. 5회 세트의 검출 한계(p95 기준 약 16%)와 가까워 **측정 가능하기는 하되 여유가
크지 않다.**

이 계산이 OPT-002 를 할 이유를 없애지는 않는다. 다만 **"비중이 그대로니 아직 크게 남았다"는
읽기는 틀렸다.** 남은 것은 같은 종류의 문제이지 같은 크기의 문제가 아니다.

| hot | 1.7% → 7.8% | 13.4ms → 16.2ms | 34ms → 33ms |
| chat | 1.6% → 7.7% | 7.8ms → 9.8ms | 27ms → 32ms |

**comment 외의 기능은 절대값이 하나도 빨라지지 않았다.** 비중이 오른 것은 그것들이
빨라져서가 아니라 **전체 파이가 3분의 1로 줄었기 때문**이다. 암달의 법칙이 예고한 그대로이며,
이제 어느 하나를 고쳐도 이만큼의 폭은 나오지 않는다.

## 6. 부작용 · 트레이드오프

### 6-1. comment 외 엔드포인트가 일관되게 느려졌다 — 원인은 호스트 CPU 클럭

After 세트에서 **최적화와 무관한 엔드포인트가 전부 1.4~3.4ms 느려졌다.** 회차 간 겹침이
없을 만큼 일관적이었다.

```
board  Before 4.5 4.5 4.6 4.3 4.4  →  After 6.1 5.9 6.2 5.9 5.8
post   Before 10.2 9.8 10.4 9.6 10.0 →  After 12.1 12.5 12.0 11.8 11.7
hot    Before 13.2 13.6 13.5 13.2 13.5 → After 17.6 16.7 16.9 14.9 14.9
```

**애플리케이션 회귀가 아니다.** 서버 측정으로 좁혀 보면 **쿼리 수는 그대로인데 쿼리당
시간만 늘었다.**

| 엔드포인트 | 요청당 쿼리 | 서버측 DB 시간 | 서버측 응답 |
|---|---|---|---|
| `GET /api/boards` | 2.0 → **2.0** | 0.79ms → 1.21ms | 3.57ms → 4.95ms |
| `GET /api/posts/{postId}` | 7.0 → **7.0** | 2.03ms → 2.77ms | 5.94ms → 7.87ms |
| `GET /api/hotposts/daily` | 14.1 → **14.0** | 3.40ms → 4.37ms | 12.43ms → 15.19ms |

호스트 프로브가 답을 갖고 있었다. Windows 의 `% Processor Performance` 는 실제 클럭을
기준 주파수 대비로 재는 값이다.

```
% Processor Performance   Before  122.9  118.8  116.6   (터보 부스트 작동)
                          After    91.6   95.8   92.8   (기준 클럭 이하)

% Processor Time (호스트)  Before   16.2   13.1   15.9
                          After    11.5   10.9   12.6
```

**OPT-A 가 일을 너무 많이 줄여서 호스트가 더 이상 부스트하지 않는다.** 클럭 비는
93.4/119.4 = 0.78 이므로 같은 연산이 **약 1.28배** 오래 걸린다. 관측된 증가폭
(+22~39%)이 그 범위에 들어간다.

**최적화 대상 엔드포인트 자신이 가장 깨끗한 확인이 된다.** `comment_list` 의 쿼리당 DB
시간은 **0.155ms → 0.198ms, +27.7%** 로 변했다. 예측치 +28% 와 소수점 한 자리까지 맞는다.
쿼리 종류도 인덱스도 데이터도 그대로인 채 **클럭만 느려진 상황**이라, 이 값은 사실상
클럭 비를 직접 잰 것과 같다.

**이 사실은 개선 폭을 과소평가하게 만든다.** After 세트는 Before 보다 약 25% 느린 클럭에서
측정됐다. 클럭이 고정됐다면 위 수치는 더 좋게 나왔을 것이다. 즉 **−74.8% 는 보수적인
값**이다.

관련: E-49(실행별 유효 CPU 처리 능력이 통제되지 않는다), E-50(호스트 CPU 일중 주기).

### 6-2. `IN` 절 파라미터 개수가 가변이다

댓글 수만큼 바인딩 파라미터가 붙는다. 실측 최대는 게시글 8의 **4,047개**였고 정상 동작했다.
다만 파라미터 개수가 매번 달라 **준비된 문(prepared statement) 캐시가 재사용되지 않는다.**

지금은 문제가 관측되지 않았다(요청당 쿼리 112, DB 시간 22.2ms). 만약 문 캐시 경합이
드러나면 `hibernate.query.in_clause_parameter_padding=true` 로 파라미터 개수를 2의 거듭제곱
단위로 반올림해 캐시 종류를 줄일 수 있다. **지금 켜지 않는 이유는 변수를 하나만 바꾸기
위해서**이며, 필요해지면 별도 실험으로 잰다.

### 6-3. 코드 복잡도

컨트롤러가 맵을 한 번 만들어 들고 다닌다. 루프 안에서 서비스를 호출하던 형태보다 읽기
쉬워졌다고 보기는 어렵지만, **"목록 화면은 목록만큼 조회한다"는 규칙이 코드에 드러난다.**

### 6-4. 정합성

없음. 반응 종류·개수·소유자 표시 전부 변경 전과 같은 값을 낸다(§4 응답 정합성).
읽기 전용 변경이라 쓰기 경로·트랜잭션 경계·이벤트 발행에 손대지 않았다.

## 7. 측정 과정에서 겪은 일 — After 세트 오염과 그 처리

After 세트 5회 중 2회(2026-09-02 08:36 · 08:48)가 **애플리케이션과 무관한 이유로 오염**됐다.

```
09-02 08:36   전체 p99 3,616ms   board p99 3,366ms   호스트 CPU 최고 90.0%   풀 10/10
09-02 08:48   전체 p99 2,769ms   board p99 2,314ms   GC 최대 정지 3,255ms
```

**요청당 쿼리가 2개뿐인 `board` 가 13ms 에서 3.4초**가 된 것이 결정적 증거다. 그 시간은
어디서 왔든 애플리케이션 로직이 아니다. 그런데 `saturation.js` 는 다섯 회차 모두
`HEADROOM` 으로 판정했다 — 임계값이 **지속적인** 포화에 맞춰져 있어 **짧고 깊은** 정지를
보지 못한다.

결과를 보고 회차를 빼는 것은 사후 선별이므로, **재측정 전에 제외 기준을 문서에 못 박고**
7개 회차 전부에 기계적으로 적용했다.

> 요청당 쿼리가 2개 이하인 엔드포인트(`GET /api/boards`)의 p99 가 **1초를 넘는 회차**는
> 애플리케이션이 아니라 환경을 측정한 것으로 보고 판정 세트에서 제외한다.

기준은 깨끗하게 갈렸다 — 유지된 다섯 회차의 `board` p99 는 11~13ms, 제외된 두 회차는
2,314~3,366ms 로 **200배 차이**이고 경계선에 걸친 회차가 없었다. 재측정한 두 회차는
1~3회차와 같은 자리에 떨어져 오염 진단이 확인됐다.

**이 사건이 계측을 두 겹으로 둔 이유를 증명했다.**

| 지표 | 1회 | 2회 | 3회 | 오염 A | 오염 B | 변동계수 |
|---|---:|---:|---:|---:|---:|---:|
| `comment_list` 요청당 쿼리 | 120 | 110 | 114 | 113 | 109 | **4.0%** |
| 전체 p95 | 65ms | 63ms | 60ms | 133ms | 296ms | **82.2%** |

**호스트가 3초씩 멈추는 동안에도 요청당 쿼리 수는 흔들리지 않았다.** 결정적 지표는 환경
잡음에 면역이고 통계적 지표는 아니다. 이 최적화의 효과는 오염된 회차를 포함해도 성립한다.

상세: `performance/docs/findings/perf-findings-environment.md` **E-53**.
