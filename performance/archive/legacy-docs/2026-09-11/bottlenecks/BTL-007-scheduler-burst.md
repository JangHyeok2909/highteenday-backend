# BTL-007: 스케줄러 flush 버스트가 온라인 트래픽에 주는 간섭

> 유형: Scheduler / DB / Event
> 상태: 의심
> 관련: soak / normal-day 시나리오에서 주기적 스파이크로 관찰 가능

## 증상

부하가 일정한데도 P95/P99 그래프에 **주기적인 스파이크**가 나타난다.
주기가 스케줄러 실행 간격과 일치하면 이 병목이다.

## 원인

백그라운드 스케줄러 4종이 온라인 트래픽과 같은 DB/커넥션 풀을 공유:

| 스케줄러 | 동작 | 위험 |
|----------|------|------|
| ViewCountScheduler | Redis 조회수 → DB flush | 대상 게시글 수만큼 UPDATE 버스트. 개별 UPDATE면 수천 쿼리 |
| HotScoreScheduler | HOT 점수 재계산 → Sorted Set 갱신 | 전 게시글 스캔형 쿼리일 경우 buffer pool 오염 |
| TokenCleanupScheduler | 만료 토큰 삭제 | 대량 DELETE 시 락/undo 비용 |
| SchoolMealScheduler | NEIS 외부 API 수집 | 외부 지연이 스레드 점유로 전이 가능 |

버스트 동안 HikariCP 커넥션을 스케줄러가 선점하면 (BTL-002와 결합)
온라인 요청의 대기가 증폭된다.

## 영향

- 모든 시나리오에 주기적 노이즈로 나타남 — **다른 실험의 교란 변수**이기도 하므로
  실험 문서에는 스케줄러 실행 시각을 함께 기록해야 한다
- 게시글 수가 늘수록 flush 대상이 커져 악화 (large 데이터셋에서 뚜렷)

## 재현 방법

```bash
# 일정 부하를 걸고 스파이크 주기를 스케줄러 주기와 대조
k6 run scenarios/normal-day.js -e DATASET=large -e HOLD=30m
# 앱 로그에서 스케줄러 실행 타임스탬프 추출 → Grafana annotation으로 오버레이
```

관찰 지표: P95 시계열의 주기성, 스케줄러 실행 시각과의 교차상관,
실행 중 `hikaricp_connections_active` 점프.

## 개선 전 선행 조건

공통 조건 넷은 [`README.md`의 "개선 전 공통 선행 조건"](README.md#개선-전-공통-선행-조건)에 있다.
이 병목에만 걸리는 것은 아래 넷이다.

### ① 스케줄러 지표가 카탈로그에 하나도 없다 — 필수

`tools/lib/metrics-catalog.js`를 `scheduler`/`scheduled`로 검색하면 **0건**이다.
`metrics/README.md`도 "@Scheduled 실행 시간 → JFR/로그 타임스탬프로 사후 분석"으로 남겨 두었다.

즉 지금은 스케줄러가 **언제 돌았고 얼마나 걸렸는지가 리포트에 없다.** 그런데 이 병목의 판정
방법이 "스파이크 주기와 스케줄러 주기가 일치하는가"이므로, 맞춰 볼 한쪽이 없는 상태다.

최소한 셋이 필요하다 — 실행 시각, 소요 시간, 처리 건수(flush 대상 게시글 수). Spring Boot
Actuator가 `@Scheduled` 메서드를 Micrometer `@Timed`로 계측할 수 있으므로 수집 경로 자체는
새로 만들 필요가 없다.

### ② 스케줄러 산출물은 상태 지문에서 **의도적으로 빠져 있다**

`posts.view_count` 합과 hot post 테이블은 데이터셋 상태 지문에 넣지 않는다. 스케줄러가 쓰기
때문에 넣으면 아무 일도 안 했는데 매번 불일치가 나고, `strict` 모드에서 복원이 무한히
반복된다.

대신 버리지 않고 `volatile`로 따로 기록한다. **이 병목을 다룰 때는 `stateBefore`/`stateAfter`
(core)가 아니라 `stateVolatileBefore`/`stateVolatileAfter`를 봐야 한다** — 스케줄러가 무슨
일을 했는지는 그쪽에만 남는다.

### ③ 판정을 구간 집계로 하면 스파이크가 사라진다

이 병목의 증상은 **주기적 스파이크**다. 그런데 리포트의 p95는 measure 구간 전체를 집계한
값이라 주기성을 보여주지 않는다. flush를 분산시켜 스파이크를 없애도 구간 p95는 거의 안 움직일
수 있다.

판정은 다음으로 한다.

- p95 대신 **max와 p99** — 스파이크는 꼬리에 나타난다
- **주기 자체** — Grafana 딥링크로 시간축을 보고 스파이크 간격이 사라졌는지 확인한다
  (리포트의 딥링크는 실행 구간 ±2분이 이미 박혀 있다)

### ④ 다른 실험의 교란 변수이므로 실행 시각을 기록한다

이 문서가 이미 지적한 대로 스케줄러 버스트는 **다른 모든 실험의 노이즈**다. 그래서 이 병목의
개선은 다른 병목 실험의 정밀도를 올리는 효과도 갖는다.

버스트가 실제로 얼마나 교란하는지는 ①의 스케줄러 지표가 들어와야 확인된다 — 회차별
스케줄러 실행 횟수와 p95를 나란히 놓으면 된다. 지금은 그 축이 없어서 검증할 수 없다.

## 해결 방법

| 후보 | 효과 | 트레이드오프 |
|------|------|--------------|
| flush를 배치 UPDATE(CASE WHEN / temp table JOIN)로 | 쿼리 수천→수개 | SQL 복잡도 |
| chunk 분할 + 사이 sleep | 버스트 평탄화 | flush 완료 시간 증가 |
| 스케줄러 전용 커넥션 풀 분리 | 온라인 트래픽 보호 | 풀 관리 복잡도 |
| 저트래픽 시간대로 스케줄 이동 | 즉효 | 데이터 신선도 저하 |
