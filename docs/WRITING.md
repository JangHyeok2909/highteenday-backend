# 문서 작성 규칙

> 적용 범위: 사람이 읽는 모든 마크다운. `docs/`, `performance/docs/`, ADR, README, 그리고 외부 독자에게
> 제출하는 원고. 코드 주석과 커밋 메시지는 `CLAUDE.md`의 Git Rules를 따른다.
> 요약은 `CLAUDE.md`의 **Documentation Rules**에 있다. 이 문서는 그 근거와 예문, 검사 방법이다.

## 0. 왜 이 규칙이 생겼나 (2026-09-05)

같은 날 같은 원고를 두 번 리뷰했다. 첫 리뷰는 굵게 297곳, 줄표 69개, 조사 띄어쓰기 88곳을 지적했고
원고는 그것을 전부 걷어냈다. 두 번째 리뷰에서 문장 평균 길이는 112자에서 123자로 늘고,
"N장 참조" 상호참조는 15개에서 24개로 늘어 있었다. 읽는 사람의 인상은 바뀌지 않았다.
표면을 고쳐도 문장 골격과 문서 골격이 남으면 AI가 정리한 보고서로 읽힌다.

그날 함께 발견한 것들이다. 전부 아래 규칙 하나씩에 대응한다.

| 겪은 일 | 규칙 |
|---|---|
| 원고를 둘로 나눴더니(전체본·축약본) 같은 수치가 두 곳에서 따로 바뀌었다 | 원고는 하나 (5장) |
| `-항목`처럼 하이픈 뒤 공백을 빠뜨려 목록이 한 문단으로 찍혔다 | 빌드 산출물을 열어 본다 (6장) |
| 소제목에 오타("신뢰능하게")가 들어간 채 PDF가 만들어졌다 | 제출 전 검사 (6장) |
| 6,364/10,685를 57%라고 적었다. 계산하면 59.6%다 | 백분율은 검산 (4장) |
| 같은 비교를 4장에서는 38배, 6장에서는 43배라고 적었다 | 같은 비교에 한 숫자 (4장) |
| 캡처 0장, 로그 0줄, 날짜 2개. 근거가 전부 손으로 그린 표와 SVG였다 | 날것 하나 이상 (4장) |
| 문서가 "이 문서는 …를 순서대로 적었습니다", "이 장이 6장의 전제입니다"라고 자기를 설명했다 | 자기 언급 금지 (2장) |
| 절마다 "…라는 것을 배웠습니다", "…이 핵심입니다"로 끝났다 | 교훈으로 닫지 않는다 (2장) |
| 사람이 직접 쓴 문단 하나가 나머지와 어조가 달라 이음새가 보였다 | 사람의 문장은 어조를 바꾸지 않는다 (7장) |

## 1. 원칙

1. **결론이 먼저, 짧게.** 첫 문단에 독자가 가져갈 것을 적는다. 더 짧게 쓸 수 있으면 더 짧게 쓴다.
2. **소리 내어 읽는다.** 그대로 말할 수 있는 문장만 남긴다. 말로 하지 않을 표현은 글에서도 뺀다.
3. **독자가 모르는 말을 쓰지 않는다.** 프로젝트 안에서 만든 용어와 내부 식별자는 정의 없이 밖으로 나가지 않는다.
4. **규칙은 셀 수 있어야 한다.** "간결하게"는 규칙이 아니다. "문장 70자 이내"는 규칙이다. 셀 수 없는 규칙은 6장의 검사 스크립트에 넣을 수 없고, 지켜졌는지 확인할 수 없다.

## 2. 문장

| 규칙 | 기준 | 어기면 이렇게 읽힌다 |
|---|---|---|
| 문장 길이 | 70자 이내. 150자를 넘는 문장은 0개 | 한 호흡에 판단 셋이 들어간 문장은 표로 바꾼다 |
| 문단 길이 | 3문장 이내. 넷째부터 불릿이나 표 | 벽처럼 보이는 문단은 훑어 읽기가 불가능하다 |
| 괄호 | 보충 정보만. 판단은 넣지 않는다 | "A안(…라서 안 됨), B안(…라서 안 됨), C안(…)도 버렸습니다" |
| 대비 구문 | "X가 아니라 Y"는 문서 전체 3회 이하 | 생성 문장의 가장 알려진 지문. 두세 번은 강조, 서른 번은 문체 |
| 절 끝 | 사실로 끝낸다. 교훈·경구·"…라고 생각합니다" 금지 | 교훈은 말로 하는 것이다. 문서가 대신 하면 설교로 읽힌다 |
| 자기 언급 | "이 문서는", "이 장의 본문", "먼저 밝힐 것이 있습니다" 금지 | 글이 논증을 조립하고 있다는 느낌을 준다 |
| 제목 | 결과형 명사구 하나. 끝에 마침표 없음 | "원인. 지표는 다 있었고 해석이 없었다"처럼 라벨 뒤에 경구를 붙이지 않는다 |
| 줄표(—) | 쓰지 않는다. 쉼표·마침표·괄호로 | 줄표·조사 띄어쓰기·굵게가 겹치면 번역기 티가 난다 |
| 조사·기호 | "Redis에", "16%", "3개"처럼 앞말에 붙인다 | |
| 굵게 | 수치와 제목에만 | 문장 조각마다 굵게가 있으면 강조가 강조 구실을 못 한다 |
| 나열 | 항목 수는 사실이 정한다. 셋으로 맞추지 않는다 | "세 겹", "네 층", "두 종류"가 절마다 나오면 틀이 보인다 |
| 용어 | 첫 등장에 괄호로 정의 | "포화(요청이 처리 용량을 넘어 줄을 선 상태)" |
| 날짜 | "2026년 8월", "2026-09-04"처럼 모호하지 않게 | "최근", "지난번"은 한 달 뒤에 뜻을 잃는다 |

## 3. AI 문체 신호

위키백과 편집자들이 정리한 [Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing)과
이 저장소 문서에서 실제로 나온 것을 합쳤다. 하나만 있으면 취향이고, 겹치면 문체다.

| 신호 | 이 저장소에서 나온 예 | 대신 |
|---|---|---|
| "X가 아니라 Y" / "not X, but Y" | "코드가 아니라 포화", "성능 최적화가 아니라 보안 결정" | "원인은 포화였다" |
| 도치·강조 구문 | "없었던 것은 …고 알려 주는 코드였습니다" | "…고 알려 주는 코드가 없었습니다" |
| 3항 나열 강박 | "세 겹", "네 층", "세 관문" | 항목 수는 사실대로 |
| 절 끝 경구 | "엄격함이 곧 무용함이 됩니다", "평균의 상한은 꼬리의 상한이 아닙니다" | 삭제. 앞 문장이 이미 말했다 |
| 자기 설명 | "이 기록이 본문입니다", "이 장이 6장의 전제입니다" | 삭제 |
| 이중 제목 | "사건 하나 — 닷새를 태운 오진", "고친 것. 포화 여부를 자동 판정" | "포화 여부 자동 판정" |
| 줄표 남용 | 문서당 69개 | 0개 |
| 굵게 남용 | 문서당 297곳 | 수치·제목만 |
| 의의 부풀리기 | "…을 처음부터 끝까지 만들어 봤다는 것입니다" | 무엇을 만들었는지만 |
| 정돈된 표만 있고 날것이 없음 | 캡처 0, 로그 0, 커밋 해시 0 | 캡처·로그·날짜·링크 |
| 어조가 갑자기 바뀜 | 사람이 쓴 문단 하나만 "…라고 생각합니다" | 나머지를 그쪽으로 맞춘다 |

## 4. 근거와 숫자

- 숫자마다 출처가 있어야 한다. 성능 수치는 run-id 또는 `performance/` 문서 경로, 결함은 `KI-nn`.
- 같은 비교에는 한 숫자만 쓴다. 다른 분모로 계산한 값을 나란히 두지 않는다.
- 백분율은 같은 문서 안의 두 값으로 검산되어야 한다. 검산이 안 맞으면 백분율을 빼고 두 값을 그대로 쓴다.
  "p95 10,685ms 중 6,364ms"는 독자가 스스로 나눌 수 있다.
- 한 문서에서 같은 값을 두 가지로 적지 않는다(3.9와 4). 반올림했으면 한 번만 병기하고 나머지는 통일한다.
- 날것을 근거마다 하나 이상 둔다. 캡처, 로그 한 줄, 실행 이름, 날짜, 링크. 손으로 그린 표와 SVG만 있는 문서는 생성물로 읽힌다.
- 링크는 실제로 열리는 곳으로. 저장소 안 문서는 기본 브랜치의 경로로 건다.

## 5. 구조

- **주어는 사람.** 제출용 문서는 "프로젝트에 무슨 일이 있었나"가 아니라 "누가 무엇을 했고 무엇이 남았나"를 쓴다.
  역할·기간·규모는 첫 쪽에 둔다.
- **상호참조 대신 다시 쓴다.** "4장 참조"는 독자에게 이동을 시킨다. 필요한 정보는 그 자리에 한 줄로 다시 적는다.
  문서당 3개 이하.
- **원고는 하나.** 길이가 다른 판이 필요하면 한 원고에 구간 마커를 두고 빌드로 만든다. 원고가 둘이 되면
  수치가 갈라지고, 갈라진 것은 반드시 늦게 발견된다.
- **문서 종류를 섞지 않는다.** 장부(지금 무엇을 믿을 수 없나), 조사 기록(무엇을 이미 해 봤나), 안내서(어떻게 하나)는
  읽는 목적이 다르다. `performance/docs/README.md`의 분류를 따른다.

## 6. 빌드와 제출 전 검사

빌드 산출물(HTML·PDF)을 실제로 열어 본다. 마크다운 원본만 보고 끝내지 않는다.

- [ ] 목록 기호 뒤 공백(`- 항목`). 없으면 문단으로 찍힌다
- [ ] 줄에 걸친 `**굵게**`가 별표 그대로 남지 않았다
- [ ] 제목에 오타·마침표가 없다
- [ ] 쪽수가 목표 안이다
- [ ] 아래 스크립트의 수치가 기준 안이다. **표면을 고친 뒤에도 다시 잰다.** 수치가 줄지 않았으면 고친 것이 아니다

```bash
# 문장 길이는 문자 수로 센다. awk length() 는 한글을 바이트로 세어 3배 부풀린다.
python3 - docs/some-doc.md <<'EOF'
import re, sys, io
t = re.split(r"(?m)^<!-- CUT -->\s*$", io.open(sys.argv[1], encoding="utf-8").read())[0]   # 마커가 한 줄일 때만 자른다
t = re.sub(r"```.*?```", "", t, flags=re.S)          # 코드·html 블록 제외
t = re.sub(r"<!--.*?-->", "", t, flags=re.S)                 # 주석·구간 마커 제외
t = re.sub(r"\[([^\]]+)\]\([^)]+\)", r"\1", t)            # 링크는 글자만 센다 (주소는 화면에 안 보인다)
body = [l for l in t.split("\n") if l.strip() and not l.startswith(("|", "#"))]
j = " ".join(body)
sents = [x.strip() for x in re.split(r"(?<=다\.)\s+", j) if x.strip()]
L = [len(x) for x in sents]
def n(pat): return len(re.findall(pat, j))
print(f"문장 {len(sents)}개  평균 {sum(L)/len(L):.0f}자  70자 초과 {sum(1 for x in L if x>70)}  150자 초과 {sum(1 for x in L if x>150)}   (기준 70 / 0 / 0)")
print(f"X가 아니라 Y {n(r'[가이] 아니라')}   (기준 3 이하)")
print(f"상호참조 {n(r'[0-9]{1,2}장|\([0-9]{1,2}\.[0-9]+\)')}   (기준 3 이하)")
print(f"교훈·자기언급 {n(r'핵심입니다|배웠습니다|생각합니다|배운 것은|이 문서|이 장의')}   (기준 0)")
print(f"줄표 {n(r'—')}  조사 띄어쓰기 {n(r'[A-Za-z0-9%)] [은는이가을를에의도로와과만서]')}   (기준 0 / 0)")
print(f"굵게 {n(r'[*][*]')//2}곳  링크 {n(r'https?://')}개")
for x in sents:
    if len(x) > 70: print(f"  {len(x):3d}자  {x[:60]}...")
EOF
```

## 7. Claude가 문서를 쓰거나 고칠 때

- 사용자가 직접 쓴 문장은 오타와 길이만 고친다. 어조는 바꾸지 않는다. 문서에서 유일하게 사람 목소리가 나는 자리다.
- 초안을 냈으면 6장 스크립트를 돌려 수치를 함께 보고한다. "고쳤습니다"만 말하지 않는다.
- 리뷰를 했으면 "무엇이 좋아졌나"와 함께 "무엇이 그대로 남았나"를 수치로 적는다.
- 문서 규칙 자체는 짧게 유지한다. `CLAUDE.md`에는 요약만, 근거와 예문은 이 문서에 둔다.

- Gergely Orosz, [The Tech Resume Inside Out: Common mistakes](https://thetechresume.com/samples/common-mistakes): 외부인이 모르는 내부 용어 금지, 굵게는 날짜·직함·수치에만, 장황함은 읽히지 않는다.
