# KI-54: 반응·스크랩 토글 API가 멱등하지 않음

> 목록 항목: [KNOWN-ISSUES.md · KI-54](../KNOWN-ISSUES.md#ki-54-반응스크랩-토글-api가-멱등하지-않음)
> 상태: **미해결** (고칠 시점은 아래 "지금 고치지 않기를 권하는 이유" 참고)
> 발견: 2026-08-14, 성능 테스트 데이터 생성기 분석 중
> 관련: [BTL-012](../../performance/bottlenecks/BTL-012-scrap-toggle-race-duplicate.md)(같은 API, 다른 문제 — 아래 참고), [KI-38](../KNOWN-ISSUES.md)

## 쉽게 말하면

지하철에서 하트를 한 번 눌렀는데, 터널에 들어가 응답을 못 받고 앱이 자동 재시도하면
**좋아요가 취소된다.** 사용자는 한 번 눌렀는데 결과는 안 누른 것이 된다.

## 증상

같은 요청을 두 번 보내면 상태가 원래대로 돌아온다. 응답은 두 번 다 200이다.

## 원인

두 API가 "무엇을 원하는가"가 아니라 **"현재 상태를 뒤집어라"**로 동작한다.

```java
// ScrapService.java:49 — toggleScrap()
if (alreadyScraped) {
    optional.get().cancelScrap();        // 켜져 있으면 끈다
} else {
    scrapRepository.upsertActive(...);   // 꺼져 있으면 켠다
}
```

```java
// PostReactionService.java:35 — likeReact()
if (liked && !disliked) {
    cancelState(post, user);             // 좋아요 상태에서 LIKE를 또 보내면 취소
} else {
    createReaction(post, user, LIKE);
}
```

엔드포인트는 `POST /api/posts/{id}/reaction?type=LIKE`와 `POST /api/posts/{id}/scraps`다.
**클라이언트가 "좋아요 상태로 만들어달라"고 말할 방법이 없다.**

## 왜 재시도가 위험한가

HTTP에서 응답을 못 받은 것과 서버가 처리하지 않은 것은 **클라이언트 입장에서 구분되지
않는다.**

```text
1차 요청  → 서버: 좋아요 생성 ✅ → 응답이 네트워크에서 유실
클라이언트: "실패했나 보다" → 재시도
2차 요청  → 서버: "이미 좋아요네" → 취소 ❌
최종 상태: 좋아요 없음. 양쪽 다 자기가 옳다고 믿는다
```

일반적인 재시도 상식("실패하면 다시 보낸다")이 **정확히 반대로 작동한다.**
재시도할수록 사용자의 의도에서 멀어진다.

HTTP 명세상 POST는 멱등할 의무가 없으므로 규약 위반은 아니다. 하지만 **재시도가 일상인
모바일 환경에서는 위험한 설계**다.

## 어디서 발견했나

성능 테스트 데이터 생성기(`performance/datasets/seed.js`)에서 먼저 드러났다.
시더의 재시도 조건(`seed.js:191`)은 이렇다.

```javascript
return /[Dd]eadlock/.test(m)
  || /Could not open JPA EntityManager|HikariPool|connection timeout/i.test(m)
  || /ECONNRESET|ECONNREFUSED|EPIPE|socket hang up|fetch failed|other side closed/i.test(m);
```

앞의 두 줄은 **서버가 거절한 경우**라 재시도가 안전하다. 문제는 세 번째 줄로,
`ECONNRESET`·`socket hang up`·`other side closed`는 **서버가 처리를 끝냈는데 응답만 못 받은
경우를 포함한다.** 여기서 재시도하면 위 시나리오가 그대로 재현된다.

즉 시더는 이 결함을 **증폭해서 먼저 보여준 관측 장치**였다. 시더만의 문제가 아니다.

## 영향

- **실사용자**: 네트워크가 불안정할 때 좋아요·스크랩이 저절로 취소된다. 재현이 간헐적이라
  버그 리포트가 올라와도 원인을 잡기 어렵다.
- **데이터셋 생성**: 반응·스크랩 수가 목표에 미달한 채로 "성공"으로 끝날 수 있다.
- **프로젝트 규칙과의 충돌**: `CLAUDE.md`의 REST 설계 규칙은 `POST`를 "create new resource",
  `DELETE`를 "remove resource"로 정의한다. 토글은 둘 중 어디에도 해당하지 않는다.

## 해결 방법 후보

| 방법 | 장점 | 단점 |
|---|---|---|
| **① `PUT` / `DELETE`로 분리** — `PUT /api/posts/{id}/like`(좋아요 상태로), `DELETE /api/posts/{id}/like`(해제) | 멱등해진다. 몇 번 보내도 결과가 같다. 프로젝트 REST 규칙에 맞는다 | **프론트엔드 계약 변경.** 백엔드 단독으로 끝나지 않는다 |
| **② 요청 본문에 목표 상태를 받는다** — `POST .../reaction {type:LIKE, desired:true}` | URL 구조를 안 바꾼다 | POST가 여전히 멱등하지 않은 것처럼 보인다. 절반만 고치는 셈 |
| **③ 멱등성 키(Idempotency-Key) 헤더** | 토글 의미를 유지한 채 재시도 안전 | 서버가 키-결과 저장소를 운영해야 한다. 이 규모에 과하다 |
| **④ 고치지 않고 클라이언트가 재시도하지 않게 한다** | 서버 변경 없음 | 통제할 수 없는 클라이언트(브라우저 자동 재시도, 프록시)가 남는다 |

**권고는 ①이다.** 프론트엔드는 이미 현재 상태를 알고 있다 — 게시글 상세 응답에
`likeState`·`scrapped`가 포함된다(`services/domain/PostDetailService.java:19,23`).
`PUT`과 `DELETE` 중 하나를 고르는 것은 어렵지 않다.

①을 적용하면 [KI-38](../KNOWN-ISSUES.md)(반응 API 응답의 `isLiked`/`isDisliked`가 항상
false)도 함께 정리하는 것이 자연스럽다 — 응답 계약을 어차피 손대게 된다.

## 지금 고치지 않기를 권하는 이유

①은 옳지만 **시점이 지금은 아니다.** 이유는 실험 설계 쪽에 있다.

`EXP-003`이 측정하려는 인기글 락 경합은 **현재 토글 경로의 쿼리 패턴**을 재는 것이다.
`PUT`/`DELETE`로 바꾸면 쿼리 모양이 달라진다. 그런데 지금은 데이터셋 재생성과 인기 분포
교정이 동시에 진행 중이라, **API까지 같이 바꾸면 성능 변화가 어느 것 때문인지 분리할 수
없다.**

성능 작업에서 이미 같은 교훈을 적용한 적이 있다 — 데이터 크기와 트래픽 규칙을 동시에 바꾸면
결과를 어느 쪽 탓으로도 돌릴 수 없다는 이유로 Zipf 지수를 고정했다. 같은 원칙이다.

**순서 권고**: 시더 방어 → 데이터셋 재생성 → 병목 재측정 → **그다음** 이 API 변경.

## 시더 쪽 방어 — 적용 완료 (2026-08-14)

서버는 아직 안 고쳤지만, 데이터 생성기가 이 결함에 데이터를 잃지 않도록 먼저 막았다.
`performance/datasets/seed.js`의 `ensureToggled()`다.

먼저 **실패를 두 종류로 갈랐다.** 기존 `isRetryable()`에는 성격이 다른 둘이 섞여 있었다.

| 분류 | 해당 오류 | 왜 다른가 |
|---|---|---|
| 확실히 적용 안 됨 | 데드락(롤백됨), 커넥션 고갈(트랜잭션 미개시), `ECONNREFUSED` | 응답을 받았거나 요청이 서버에 닿지 않았다 → 재시도 안전 |
| 적용 여부 모름 | `ECONNRESET`, `EPIPE`, `socket hang up`, `fetch failed`, `other side closed` | 응답만 못 받았을 뿐 서버는 처리를 끝냈을 수 있다 |

두 번째 경우에만 **재요청하지 않고 상태를 조회**한다. 새 API는 필요 없었다 —
`GET /api/posts/{postId}`(`controllers/PostController.java:35`)가 `applyUserContext()`를 거쳐
요청자 기준 상태를 이미 응답에 담는다.

> 실제 응답 키는 `liked` · `disliked` · `scrapped` 로 **평면**이다. `likeState` 로 중첩돼
> 있지 않다(실제 요청으로 확인). 문서만 보고 추측하면 틀린다.

조회 결과에 따라 세 갈래로 갈린다.

| 조회 결과 | 판단 | 처리 |
|---|---|---|
| 목표 상태다 | 첫 요청이 적용됐다 | 성공 |
| 목표 상태가 아니다 | 적용 안 된 것이 **확인**됐다 | 이제 재시도가 안전하므로 재시도 |
| 조회도 실패 | 아무것도 단정할 수 없다 | 재시도하지 않고 실패로 남김 |

세 번째가 핵심이다 — 확인이 안 되면 되돌릴 위험을 감수하지 않는다.
원칙은 **"불확실하면 다시 보내지 말고 확인한다"**이다.

모의 검증으로 다섯 경우를 확인했다: 성공 / 데드락→재시도 / 응답유실+적용됨→성공 /
응답유실+미적용→재시도 / 응답유실+조회실패→재시도 안 함.

부하 스크립트(`performance/scripts/reactions.js`)는 **그대로 둔다.** 실사용자의 토글 행동을
재현하는 것이 목적이므로 토글 호출이 맞다.

**이 방어는 시더만 보호한다.** 실사용자와 프론트엔드는 여전히 노출돼 있다 — 서버 수정(`PUT`/
`DELETE` 분리)이 있어야 닫힌다.

## BTL-012와 혼동하지 말 것

[BTL-012](../../performance/bottlenecks/BTL-012-scrap-toggle-race-duplicate.md)(스크랩 토글
경쟁 상태 → 중복 행)는 **다른 문제이며 이미 해소됐다.**

| | BTL-012 (해소) | KI-54 (이 문서) |
|---|---|---|
| 원인 | 동시 요청 **둘**이 모두 INSERT | 단일 클라이언트의 **재시도** |
| 분류 | 경쟁 상태 | API 계약(멱등성) |
| 조치 | `UNIQUE` 제약 + upsert | 미해결 |

BTL-012가 해소되어 동시성이 완벽히 처리된 **지금도** KI-54는 발생한다. 요청이 하나뿐이어도
두 번 보내면 뒤집히기 때문이다.

## 확인된 사실과 추론

**실측으로 확인한 것**

- 토글 API가 상태를 뒤집는다는 것 — 소스 확인
- 시더 재시도 조건이 "응답 유실" 케이스를 포함한다는 것 — 소스 확인
- 게시글 상세 응답에 `likeState`·`scrapped`가 포함된다는 것 — 소스 확인

**추론인 것** (별도 검증 필요)

- 실사용자가 이 결함을 겪는다는 것 — 메커니즘상 가능하지만 운영 로그로 확인하지 않았다.
  클라이언트가 실제로 자동 재시도를 하는지도 확인하지 않았다
- 시더에서 실제로 데이터 손실이 발생했다는 것 — 재시도 경로가 열려 있는 것은 사실이나,
  특정 실행에서 몇 건이 뒤집혔는지 계측하지는 않았다
